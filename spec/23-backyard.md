## 23. 運営バックヤード

**この章で決めること**: サービスを運営する側（M2Office 運営）に必要な仕組み。
**顧客向けの機能とは別に、運営を成立させる基盤が要る。**

### 23.1 位置づけ

運営バックヤードは、**顧客テナントとは完全に分離された運営専用のシステム**である。

| 観点 | 顧客テナント | 運営バックヤード |
|---|---|---|
| 利用者 | 顧客企業の従業員 | M2Office 運営 |
| 扱うデータ | 業務データ、知識、実行履歴 | テナントの状態、利用量、請求 |
| ドメイン | `<会社>.m2office.net` | 運営専用の別ドメイン |
| 認証 | Google アカウント（第16.1節） | **2 段階認証を必須とする**（第23.8.9節） |

**原則: 運営は顧客の業務データを見ない。**
運営が扱うのはメタ情報（稼働状況、利用量、請求）であり、
メールの中身や議事録の内容は対象外とする。例外手続きは第23.6節で規定する。

### 23.3 テナントのライフサイクル

```
 [申込] ──審査──→ [試用] ──有償化──→ [稼働中]
                     │                   │
                     │ 期限切れ          │ 未入金
                     ▼                   ▼
                  [失効]        [停止（閲覧のみ）]
                                         │
                                         │ 解約
                                         ▼
                                    [解約済み] ──猶予期間──→ [削除]
```

| 状態 | 意味 | 可能な操作 |
|---|---|---|
| 申込 | 受付済み、未払い出し | 審査、却下 |
| 試用 | 期限付きで利用可能 | 全機能（上限あり） |
| 稼働中 | 有償契約中 | 全機能 |
| 停止 | 未入金または規約違反 | **閲覧とエクスポートのみ。実行は不可** |
| 緊急停止 | 不正利用、乗っ取り、情報漏洩の疑い | なし（ログインを含めて止める。第23.8.6節） |
| 解約済み | 契約終了 | エクスポートのみ |
| 削除 | データ消去済み | なし |

**停止時に即座に全データを見えなくしない。**
未入金は事務的な行き違いで起きることが多く、いきなり業務が止まると顧客の被害が大きい。
実行だけを止め、閲覧とエクスポートは残す。

TBD: 試用期間の長さ、解約後の保持期間（Q-29）。停止までの猶予は 7 日と決めた（第 0.310.0 版。第23.8.6節）。

#### 23.3.1 紹介のページと申し込み・セルフの払い出し（第 0.428.0 版で案。Q-29・Q-40・Q-258、ADR-0107）

2026-10-23 に三浦さんが、サービスを紹介する Web のページを置き、**そこから申し込んで、サブドメインを決め、支払いを設定すると、サブドメインが払い出される**形を求めた。紹介のページは、WordPress（PHP）ではなく、Node.js の CMS **EmDash**（Cloudflare が 2026 年 4 月に公開。管理画面は WordPress に近く、MCP の口を内蔵する）で作る。
同日に、次の形を三浦さんが選んだ（おすすめのとおり）: EmDash は Cloudflare の上に置く、カードの支払いが通れば自動で払い出す、申し込みのときにカードを登録して試用の後に課金を始める。

**第 0.471.0 版で案、第 0.472.0 版で確定（Q-279、ADR-0113）**: クラウドの形の第 1 弾を VPS だけで守る形に改めたため、この節の Cloudflare に頼るところを次のように改める。① 紹介のページは **VPS の Caddy が出す**（EmDash を VPS の上で動かせるかを確かめ、動かせなければ静的なページにする。CMS の管理画面は WireGuard の網からだけ開ける）。② 問い合わせの鍵は VPS の設定の置き場に置く。③ ロボットよけは、Cloudflare Turnstile（Cloudflare のアカウントが要る）をやめ、**VPS の上で完結する方式**（計算を求める ALTCHA など）にする。④ 回数の制限は Caddy とアプリの二重にする。下の表はこの形に書き直した。

**第 0.475.0 版で案（Q-280、ADR-0114）**: 2026-10-27 に三浦さんが、紹介のページを WordPress ではなく、**AI でほぼ完全に操作できる形**で作ることを求めた。EmDash はまだ安定していないため第 1 弾では使わず、**CMS を置かない静的なサイト（Astro）にし、AI が中身のファイルを直して、WireGuard の網から VPS に送る**形を案とする（下の表）。

**分け方の原則: 紹介のページ（CMS）には紹介の中身だけを置き、申し込み・支払い・払い出しは M2Office の側で行う。** サブドメインの正はマスター管理画面（第23.8.8節）で、会社を作る権限を CMS に持たせない。CMS が破られても、会社を作られたり、支払いの記録を変えられたりしない。

##### 紹介のページ（静的なサイト。第 0.475.0 版で案）

| 中身 | 紹介・料金・使い方の例・よくある質問・規約とプライバシーの方針・運営主体の表示（特定商取引法の表示を含む） |
| 問い合わせ | **紹介のページでは個人の情報を集めない**（フォームを置かない）。申し込みの口（`signup.`）ができるまでは、運営の窓口のメールアドレスへのリンクにする。できたら、申し込みの口の問い合わせのフォームで受け、運営の会社の M2Office の「問い合わせの受け付け」（外部のアプリの機能 `inquiries.intake`。第13.4.2節）に渡す。鍵は申し込みの口だけが持つ |
| 申し込み | 「お申し込み」のボタンで、申し込みのページ（`signup.m2office.net`）へ移る |
| 外の部品 | 広告・外のフォントの読み込みを入れない。**アクセスの解析は Google アナリティクスを入れる**（第 0.489.0 版。2026-10-30 に三浦さんが決めた。Q-290）。同意の画面は出さずに読み込み、プライバシーの方針に、使っていること・Cookie で集めること・Google に送ること・止め方（Google のオプトアウトの部品）を書く。紹介のページだけに置き、M2Office の画面（会社の画面・体験版・マスター管理画面）には入れない |
| 守り | Caddy が安全のための見出し（HSTS・`X-Content-Type-Options` など。第20.4.6節）を付ける。WAF は通さない（受け取る入力が無いため）。CrowdSec がログを読むのは会社の画面と同じ |
| 公開前の確認 | 公開の前は、紹介のページのファイルを **BASIC 認証**で守り、検索に出さない見出しを付ける。紹介のサイトの側がパスワードを作り、bcrypt のハッシュだけを `setup.sh` に入れる。公開するときは、その答えを空にして走らせ直す（第 0.486.0 版。第20.4.6節） |
| EmDash への移り | 第 0.428.0 版の案の EmDash は、公開から間もない早期のベータで変化が大きいため、第 1 弾では使わない。EmDash も Astro の上に作られているので、落ち着いて人が画面で編集したくなったら、中身を持って移れるかを確かめる |

##### 申し込みのページと流れ

```
紹介のページ（静的なサイト。www）
  │「お申し込み」
申し込みのページ（signup.m2office.net。M2Office の申し込みの口）
  1. Google でログイン（会社の Google Workspace のアカウント。gmail.com などの個人のアカウントは断る）
  2. 会社名・希望のサブドメイン（入れるそばから空きと規則を確かめる）・プラン・最初の人数・支払いの方法（カード／請求書払い）
     ロボットよけ（VPS の上で完結する方式。計算を求める ALTCHA など）
  3a. カード: Stripe の支払いのページで、カードを登録する（試用の間は課金しない）
  3b. 請求書払い: 申し込みを受け付けたことを示し、運営の確かめを待つ
  │ Stripe からの知らせ（署名を確かめる）
払い出し（第23.8.15節の会社の作成と同じ口）
  │ 会社を「試用」で作り、申し込んだ人を最初の管理者にする
  └ 完了のページから https://<サブドメイン>.m2office.net へ。Google でログインして使い始める
```

| 項目 | 規定（案） |
|---|---|
| 申し込む人の確かめ | **Google でログインして始める**。ID トークンの `hd`（Google Workspace のドメイン）が無いアカウントは断る。メールの確かめを別に送らずに、会社のドメインとメールアドレスを確かめられる。その人が最初の管理者になる |
| 1 つのドメインに 1 社 | 同じ Google Workspace のドメインの会社がすでにあれば、新しく作らず、その会社のアドレスを示す（管理者に連絡するよう伝える） |
| サブドメイン | 規則と予約語は第20.4.3節。入れるそばから空きを確かめる。**支払いのページへ進んだ時点で 30 分だけ押さえ**、ほかの申し込みに渡さない。期限を過ぎたら放す |
| プランと人数 | 料金の表（第23.4.1節のシート利用料）から選ぶ。人数の数え方は Q-30 のとおり（月の最大の利用者の数を有力とする） |
| 試用 | **14 日**（Q-29 の試用の期間を、この案で 14 日とする）。カードを登録してから始め、試用の終わりに Stripe が課金を始める。試用の間に解約すれば課金しない。試用の終わりの 3 日前に管理者に知らせる |
| カードの扱い | **カードの番号は Stripe だけが持つ**（Stripe の支払いのページ。M2Office の画面とサーバーには来ない）。M2Office は Stripe の顧客の ID と契約の ID だけを持つ |
| 払い出しの条件 | カード: Stripe から「登録が済んだ」知らせ（署名を確かめる）が届いたら、**自動で払い出す**（審査を待たない）。請求書払い: 運営がマスター管理画面で申し込みを確かめてから払い出す（入金の確かめ方は Q-40） |
| 審査の改め | 第23.3節の「申込 ──審査──→ 試用」を、カードは「支払いの登録 → 試用（自動）」、請求書払いは「運営の確かめ → 試用」に改める。おかしな申し込み（なりすまし・規約違反）は、払い出した後でもマスター管理画面で止められる（第23.8.6節） |
| 知らせ | 払い出したら、運営にマスター管理画面の知らせを出す（新しい会社）。申し込んだ人には完了のページを出し、Stripe が登録の控えを送る |
| 途中でやめた申し込み | 支払いのページで戻った・閉じた申し込みは、押さえを放し、記録は 7 日で消す（名前とメールアドレスを長く持たない） |

#### 23.3.2 体験版（`demo.m2office.net`。第 0.484.0 版で案、第 0.485.0 版で決定・実装。Q-286、ADR-0115）

2026-10-29 に三浦さんが、**導入を考えているお客様が、Google Workspace の契約が無くても試せる体験版**を求めた。運営がデモの依頼を受けたら、ゲストの ID とパスワードを期間を限って出し、お客様は自由に使える。AI の利用は上限で抑え、作ったデータは期限が来たら自動で消す。三浦さんが、**1 社に 1 人・期限は 2 週間・AI の上限は推定 1,000 円・外部への接続（Web の調べものなど）は許す**と決めた。

| 項目 | 規定（案） |
|---|---|
| 入口 | **`demo.m2office.net` だけ**。ゲストの ID とパスワードで入る。会社のサブドメインはゲストごとに作らない（Let's Encrypt の証明書は 1 つの親のドメインで週に 50 枚までのため、ゲストごとに名前を作ると、依頼が多い週に証明書が取れなくなる） |
| 分け方 | **ゲストごとに使い捨ての「体験用の会社」を作る**。`demo` の名前で来た要求は、サブドメインではなく**ゲストのログイン状態から体験用の会社を決める**。いまの会社ごとの分離（行の単位の守り。不変則 I-2）がそのまま効き、ほかのお客様のデータは見えない。1 つの体験用の会社に入れるのは、そのゲスト 1 人だけ |
| 体験用の会社の印 | 会社に「体験」の印を付ける。会社一覧・毎晩の数・課金・注意の印には入れず、マスター管理画面の「体験」にだけ出す。サブドメインと Google Workspace のドメインは持たない |
| 中身 | 作るときに、**見本の会社のデータ**（架空の会社の規程・取引先・名刺・見積と受注・在庫・予定など）を入れた状態で始める。見本の中身はリポジトリのファイルで持ち、実在の会社や人の名前を使わない |
| Google の部分 | 見本のデータで動く（予定・メール・タスク・チャット。ADR-0003 の接続口）。Google の接続の設定は出さない |
| ゲストのロール | 体験用の会社の**管理者**にする（管理者ページも試せる）。ただし、次は止める: 利用者の招待（1 社 1 人のため）、接続の設定（Google・Gemini の自社の鍵・会社の接続（MCP）・WordPress・LINE・窓口のメール）、拡張機能のファイルの取り込み。内蔵の拡張機能は使える |
| 社外への送信 | メール・チャット・LINE・配信・WordPress への公開などの社外への送信は、**すべて行わない**（見本の接続口なので実際には送られない。送る業務は承認の後に「体験版では送りません」と終える） |
| 外部への接続 | **許す**（三浦さんが決めた）。Web の調べもの・Web のページの読み込み・競合の見回りは、本物の外のサイトに行く。国で通信を止める決まり（Q-284）と、いまの外へ出るときの守り（SSRF の防止。第16.9節）はそのまま効く。AI を使うものは下の上限に数える |
| AI | 運営の鍵（Q-285）を使う。**体験の期間を通した上限は推定 1,000 円**（月の上限ではない。月をまたいでも戻らない）。8 割と 10 割でゲストに知らせ、当たったら新しい AI の利用を止める（AI を使わない画面は使える）。運営の鍵の全体の上限（Q-285）にも数える |
| 置ける量 | ファイルの置き場は 1 社 500 MB まで（超えたら上げられない） |

### 23.6 顧客データへのアクセス統制

**運営が顧客の業務データを自由に見られる状態は、信頼を損なう。**
調査で「情報漏洩のリスク」が懸念の 33.5% を占めることからも、ここは明確に規定する。

| 段階 | 内容 |
|---|---|
| 原則 | 運営は顧客の業務データ（メール、文書、知識、個人記憶）を閲覧できない |
| 例外の発動 | 障害調査やサポートで必要な場合に限り、申請する |
| 顧客の同意 | **テナント管理者の明示的な同意を得る** |
| 期限 | 期限付きの一時アクセスとし、自動的に失効する |
| 範囲 | 必要な対象のみに限定する |
| 記録 | 誰が・いつ・何を見たかをすべて記録する |
| 通知 | アクセス後、顧客へ内容を通知する |

この仕組み自体を製品説明に明記し、契約書にも反映する。

#### 23.6.1 代理アクセスの実装（第 0.312.0 版。マスター管理画面の段 2）

三浦さんが、範囲は申請ごとに 2 段から選ぶ・期限は許す人が選ぶ・同意は会社の管理者の誰か 1 人、と決めた。

| 項目 | 規定 |
|---|---|
| 申請 | 運営管理者かサポートが、マスター管理画面の会社の詳細から、範囲と理由（必須）を書いて申請する。会社の管理者全員に M2Office の中の通知が届く |
| 範囲 | **管理者ページ**（設定・接続・業務の実行の一覧と状態・監査ログ・利用状況）か、それに加えて**業務の結果**。業務の結果で見られるのは、**許した管理者が自分で依頼した実行の中身と成果物だけ**（会社の管理者でもほかの人の実行の中身は見られないため。第6.6.8節・不変則 I-10。三浦さんが決めた）。閲覧のときは許した管理者として見るが、見られる道を限る。どちらも**見るだけ**で、書き換え・依頼・承認はできない。秘書との会話・個人の記憶・知識（社内規程など）・名刺や在庫などの各業務の台帳・Google のメールや文書・ファイルの取り出し（監査ログの書き出しを含む）は、どちらの範囲でも見られない |
| 同意 | 会社の管理者の誰か 1 人が、管理者ページの「サポートの閲覧」で許すか断る。許すときに期限を 1 時間・4 時間・1 日・3 日から選ぶ（既定 1 日）。管理者はいつでも切れる |
| 入り方 | 許されたら、申請した運営者だけが、マスター管理画面の「会社の画面を開く」で入る（1 回だけ使える 2 分の引換券で、会社の名前の画面に閲覧だけのログイン状態を張る）。画面の上に「運営のサポートが閲覧しています」と期限を出す |
| 記録 | 閲覧のたびに、どの画面（API の道）を見たかを会社の監査ログに残す（`proxy.view`）。申請・許可・断り・切ったこと・入ったことも、会社の監査ログと運営の操作の記録に残す |
| 終わり方 | 期限が来る（`expired`）・会社の管理者が切る（`revoked`）・申請した運営者が終える（`ended`。第 0.320.0 版で `revoked` から分けた。誰が終えたかを取り違えないため）。会社の画面の上の「閲覧を終える」は閲覧のログイン状態だけを終え、申請は期限まで残る |
| 終わったあとの知らせ | 期限が来るか、切られるか、運営者が終えたら、ワーカーが会社の管理者に、閲覧の回数と監査ログで中身を確かめられることを知らせる |
| 作り | 申請と許可は `proxy_grants`、閲覧のログイン状態は `proxy_sessions`（どちらも会社ごとの行レベルセキュリティ）。運営の側は決めた関数（`ops.request_proxy`・`ops.proxy_ticket` など）だけで触る。顧客向けの API は、閲覧のログイン状態の要求を、見るだけの決めた道（範囲ごとの許可の表）に限る |

### 23.7 段階的な構築

**運営バックヤードは Phase 1 から作り込む必要はない。**
自社および関連会社のみの段階では、多くを手作業で回せる。

| フェーズ | 状態 | 構築するもの |
|---|---|---|
| Phase 1 | 自社のみ（1 テナント） | **監視の最低限のみ**。請求は不要 |
| Phase 2 | 関連会社（数テナント） | テナント払い出しの自動化、稼働監視、利用量の把握。請求は手作業でよい |
| Phase 3 | 限定外販（10〜） | **請求・決済の自動化**、収益ダッシュボード、代理アクセス統制、サポート受付 |
| Phase 4 | 一般提供 | セルフサインアップの完全自動化、パートナー管理（収益分配は取り下げ（第 0.490.0 版、Q-292）） |

**ただし Phase 1 から用意しておくべきデータがある。**

| # | 項目 | 理由 |
|---|---|---|
| 1 | 実行ごとのコスト記録 | 後から遡れない。価格設計の材料になる |
| 2 | テナント・ユーザー単位の利用量集計 | 請求の基礎データ。後付けだと過去分が出せない |
| 3 | テナントの状態遷移の記録 | 契約履歴の証跡 |
| 4 | 代理アクセスの記録 | 信頼の証跡。最初から記録する |

**請求システムは後から作れるが、請求の根拠となるデータは後から作れない。**
これが本章で最も重要な結論である。

### 23.8 マスター管理画面

**この節で決めること**: 運営が全契約企業を一元的に管理する画面の構成と、そこで行える操作。

#### 23.8.1 目的

**マスター管理画面を開けば、ライセンスを契約している会社がすべて並び、
各社の契約・利用・請求・稼働の状況がひと目で分かる。** 運営のあらゆる操作はここから始まる。

| 問い | 答える場所 |
|---|---|
| どのサブドメインにどの会社が割り当たっているか | 会社一覧（第23.8.3節） |
| その会社は何シート契約し、何人使っているか | 会社一覧・会社の詳細（第23.8.5節） |
| 請求は済んでいるか、入金されているか | 会社一覧・会社の詳細の請求（第23.8.4節） |
| サーバー全体は健全に動いているか | 一覧の上部の要約と稼働状況（第23.8.7節） |
| 利用を止める必要があるか、止めたら何が起きるか | 利用の停止と再開（第23.8.6節） |

第23.5節の運営の全体指標は「全体の傾向」、マスター管理画面は
「個々の会社」を見て操作する画面として役割を分ける。前者は後者のトップに要約として載せる。

#### 23.8.2 位置と画面構成

| 項目 | 方針 |

| 置き場所 | **`ops.m2office.net`**（Q-60 で決定）。顧客には払い出さない予約語（第20.4.3節）とし、顧客テナントのサブドメインとしては使わせない |
| Cookie | ログイン状態の Cookie は `Domain` 属性を付けない（第20.7節）。**ホスト単位で閉じる**ため、顧客のサブドメインへは渡らない。これが同じドメインの下に置ける前提である |
| API | 運営用の API を顧客向け API とは別に設ける。顧客向け API から運営の操作はできない |
| 見直し | 分離をより強くしたくなったら、別のドメインへ移す。**そのときに変わるのは URL と証明書だけ**で、Cookie の扱いは変わらない |

| 契約期間 | 開始日・終了日・自動更新の有無。年間契約（第23.4.3節）にも対応する |

| B | 契約数を超える招待を拒否する | 確実だが、増員のたびに契約変更が要る |

#### 23.8.6 利用の停止と再開

第23.3節の「停止」を、マスター管理画面からの操作として規定する。

**停止は 2 種類に分ける。**

| 種類 | 使う場面 | 顧客側で起きること |
|---|---|---|
| **通常の停止** | 未入金、規約違反 | **閲覧とエクスポートのみ**。新規の実行・定時実行・外部 API は止まる。実行中の処理は完走させる（第21.2.3節） |
| **緊急停止** | 不正利用、アカウントの乗っ取り、情報漏洩の疑い | **ログインを含めて全面的に止める**。被害の拡大を防ぐことを優先する |

**通常の停止の手順**

| 段階 | 内容 |
|---|---|
| 1 | 運営者が停止を申請する。理由（未入金・規約違反など）を必ず選ぶ |
| 2 | **申請者とは別の運営者が承認する**（2 人承認）。誤った停止は顧客への影響が大きいため（第23.4.4節） |
| 3 | 顧客の管理者へ予告を通知する。予告から停止までの猶予は Q-29 |
| 4 | 猶予の後に停止する。顧客の画面には停止中である旨と、解除の方法（入金の確認など）を表示する |
| 5 | すべてを操作履歴と、顧客の監査ログの両方に残す |

**緊急停止は運営者なら誰でも発動できる**（Q-63 で決定）。事故への反応を最優先するためである。
誤った停止に備えて、次を条件とする。

| 条件 | 内容 |
|---|---|
| 理由 | 発動のときに理由の入力を必須とする |
| 周知 | 発動を**運営者全員に知らせる**。誰がいつ、どの会社を止めたかを含める |
| 事後の確認 | 事後に**別の運営者の確認**を必ず受ける |
| 顧客への通知 | 停止の直後に理由を通知する |
| 解除 | 解除は 2 人承認とする（通常の停止の再開と同じ） |

**再開**は、停止の理由が解消されたこと（入金の確認など）を記録したうえで行う。
再開も 2 人承認とする。ただし入金の消込で自動的に解消した場合は、1 人の確認でよい。

**停止中でも失わないもの**

| 対象 | 扱い |
|---|---|
| データ | 保持する。削除は解約後の保持期間を過ぎてから（第23.3節） |
| 定時実行 | 止める。再開時に、止まっていた間の回はまとめて 1 回だけ起動する（ワーカーが止まっていた場合と同じ扱い。週次ブリーフが何通も届くことを避ける） |
| 承認待ち | 残す。再開後に承認できる |

**実装上の扱い**（第 0.51.0 版で規定）

テナントの台帳（`tenants.status`）の値で、2 種類の停止を分ける（第23.8.11節）。

| 値 | 意味 | API |
|---|---|---|
| `trial`・`active` | 試用・稼働中 | すべて受け付ける |
| `suspended` | **通常の停止** | 閲覧（`GET`）と、下の表の操作だけを受け付ける。ほかの書き込みは 403 で拒否し、停止中であることを返す |
| `locked` | **緊急停止** | ログインを含めてすべて拒否する。停止の理由は画面に出さない（攻撃者に手がかりを与えないため。理由は管理者へ別に通知する） |
| `cancelled` | 解約済み | すべて拒否する。規定は「エクスポートのみ」だが、持ち出し（第11.10節。Phase 2）が未実装のため。持ち出しを実装するときに直す |

**通常の停止で受け付ける書き込み**

| 操作 | 理由 |
|---|---|
| ログインとログアウト | 閲覧にはログインが要る |
| お知らせの既読 | 閲覧の一部。業務のデータを変えない |
| ログイン中の端末のログアウト（第6.5.8節） | 乗っ取りへの備え（R-13）。停止中でも本人が端末を切れるようにする |

業務の依頼・秘書への依頼・承認の判断・設定の変更・ファイルの受け付け・Google との接続は受け付けない。
閲覧には、成果物とファイルの取り出し（ダウンロード）を含める。持ち出し（OKF のエクスポート）は Phase 2 で、できたら通常の停止でも受け付ける。

**ワーカーの扱い**

| 対象 | 扱い |
|---|---|
| 実行中（`running`）の実行 | 完走させる。承認ステップに達したら承認待ちで止まる |
| 待ち行列（`queued`）の実行 | 始めない。再開すると、そのまま続きから動く |
| 定時実行 | 起動しない。次の実行時刻を進めないため、再開したときに止まっていた間の回がまとめて 1 回だけ起動する |
| 保持期間の見回り（第14.3.2節） | 続ける。預かったデータを消す義務は、停止中も変わらない |

**画面**: 通常の停止の間は、すべての画面の上部に「ご利用を停止しています。閲覧のみできます」と、解除の方法の案内を出す。

**マスター管理画面からの停止と再開（第 0.310.0 版で実装。段 2）**: 三浦さんが、猶予は 7 日・会社への知らせは画面の中と運営者が渡す・申請と承認は運営管理者とサポート、と決めた。

| 操作 | 行える人 | 流れ |
|---|---|---|
| 通常の停止 | 申請も承認も運営管理者とサポート（申請した人とは別の人が承認する） | 理由の種類（未入金・規約違反・そのほか）と理由の文を必須にして申請 → 別の運営者が承認すると、会社の管理者に予告を届け（M2Office の中の通知と画面の上の帯）、**7 日後に止める**（ワーカーが 1 分ごとに期限の来たものを止める）。その間に解消したら、承認の前でも後でも申請を取り下げられる |
| 緊急停止 | 運営者なら誰でも（Q-63） | 理由の種類（不正利用・乗っ取り・情報漏洩の疑い・そのほか）と理由の文を必須にして発動すると、**すぐに止める**。運営の画面の上に、確認待ちの緊急停止を全員に出す。申請した人とは別の運営管理者かサポートが、事後に確認する |
| 再開 | 申請も承認も運営管理者とサポート（別の人が承認） | 理由が解消されたことを書いて申請 → 別の運営者が承認すると、止める前の状態（試用か稼働中）に戻し、会社の管理者に知らせる |

- 会社の管理者への知らせは、M2Office の中の通知（種類「ご利用」）と画面の上の帯で行う。運営の画面は社外にメールを送らず、予告・停止・再開の案内の文を出して、運営者が自分のメールなどで渡す（Q-213 と同じ考え方）。緊急停止の間はログインできないため、運営者が渡すだけ
- 申請・承認・取り下げ・確認・実際に止めたこと・再開は、すべて運営の操作の記録と、その会社の監査ログの両方に残す
- 記録はデータベースの `ops.status_requests` に持ち、状態の変更は所有者の権限で動く決めた関数だけで行う（申請した人が自分で承認できないことも関数の中で確かめる）
- **運営者が 1 人だけのとき（第 0.487.0 版。Q-288、ADR-0116）**: ほかに承認できる運営者（使える状態の運営管理者とサポート）が 1 人もいないときだけ、申請した本人が承認・事後の確認を行える。1 人で行う理由を必ず書き、申請の記録・運営の操作の記録・会社の監査ログに「1 人で行った」と残す。判定は承認・確認のたびに関数の中で行い、2 人目の運営者を足せば自動で 2 人の決まりに戻る。通常の停止の 7 日の予告は変えない
- 入金の消込による自動の再開は、請求の段（第23.4節）で足す

##### 機械の資源の図（第 0.479.0 版。Q-281）

2026-10-29 に三浦さんが、実機の VPS で稼働状況を見て、数字だけでは機械に余裕があるのか分からないので、ディスクの使用量（全体の何 % か）・CPU の負荷・メモリー・Swap などを図で分かりやすく出すよう求めた。

| 項目 | 規定 |
|---|---|
| 出すもの | **CPU の負荷**（1 分の平均の負荷をコアの数で割った割合。5 分・15 分の値も数で添える。100% を超えうる）、**メモリー**（使っている割合 ＝ 1 −使える量 ÷ 全体。第8.6.7.1節の「使える量」）、**Swap**（使っている割合。Swap が無い機械は「なし」）、**ディスク**（ファイルの置き場があるディスクの使っている割合。うちデータベースとファイルの置き場の量も添える）、**データベースの接続**（接続の数 ÷ 上限の `max_connections`） |
| いまの値の見せ方 | 項目ごとに横の棒（メーター）と「使っている量 ／ 全体（%）」を出す。**80% 以上で注意の色、90% 以上で危険の色**。色だけに頼らず、割合の数も必ず出す（第6章 色覚） |
| 推移の見せ方 | CPU の負荷・メモリー・Swap・ディスクの割合を、**直近 24 時間の折れ線**で出す（7 日に切り替えられる）。横軸は時刻、縦軸は 0〜100%（CPU の負荷は 100% を超えたら軸を伸ばす）。点に指を当てると、その時刻と値を出す |
| 標本の取り方 | API が 5 分ごとに動いている知らせ（第8.6.7.1節）を置くときに、同じ値を標本として `runtime_samples`（会社を持たない表）に足す。**7 日より古い標本は消す**（1 台で 2,016 行ほど）。ワーカーは標本を置かない（同じ機械の値が重なるため） |
| 置く場所 | 「動いている環境」の欄のすぐ下の「機械の資源」の欄。**クラウドの形は運営の画面の「稼働状況」だけ**、**ローカルの形は管理者ページの「機械」**（第8.6.7.1節と同じ。運営の機械の情報を各社の管理者に出さない） |
| 描き方 | 新しい部品（図のライブラリ）は入れず、画面の中で SVG で描く。外へは何も見に行かない |
| 推測しない | 取れなかった値（Swap の読めない OS など）は棒を出さずに「取得できなかった」と出す |
| 知らせ | この図は見るためのもの。空きが少ないなどの知らせの決まり（第23.5節）は変えない |

**実装（第 0.479.0 版）**: 集める処理は `packages/core/src/machine/runtime.ts`（`currentMachine` に負荷・Swap・ディスク、`linuxSwapOf`・`macSwapOf`、標本の `writeSample` と推移の `samples`、データベースの `DATABASE_USAGE_SQL`）、表と関数は移行 170（`runtime_samples`・`runtime_sample_series`・`ops.runtime_samples`）、画面は `packages/web/src/resource-card.tsx`（`ResourceCard`。`RuntimeCard` が推移の口を与えられたときに出す）。API は `GET /v1/admin/machine/runtime/samples`（ローカルの形）と運営の `GET /v1/ops/runtime/samples`。稼働状況の「データベース」「ファイルの置き場」の数の欄は、ディスクの内訳と接続の棒に移した

**異常の検知**は第23.5節の「異常」に従い、運営者へ通知する。

**障害の知らせ**（第 0.390.0 版。第16.11.3節 G-9）: 障害・一部の不具合・計画停止を、マスター管理画面の「障害の知らせ」から起こし、経過と終わりを書く。そのたびに対象の会社の管理者に知らせ、会社の管理者ページ「稼働の報告」に月ごとの稼働率と経過を出す。
会社ごとに見るべき異常（1 社だけ失敗が多いなど）は、会社一覧の「注意」に印を付ける。

#### 23.8.9 運営者と権限

**運営者は顧客テナントの利用者とは別に管理する。** 顧客のテナントに運営者のアカウントは置かない。

| ロール | できること |
|---|---|
| 運営管理者 | すべて。運営者の追加と権限の変更 |
| 請求担当 | 請求・入金・督促・返金の申請。停止の申請 |
| サポート | 会社の詳細の閲覧、代理アクセスの申請（第23.6節） |
| 監視 | 稼働状況と会社一覧の閲覧のみ |

| 項目 | 方針 |
|---|---|
| ログイン | 運営主体の Google Workspace のアカウントで行う（Q-62）。**第 0.481.0 版**: 提携会社の Google Workspace（か Cloud Identity）のアカウントでも入れるよう、許すドメインを複数にする（下の「提携会社の運営者」。Q-283） |
| 2 段階認証 | **必須**。未設定のアカウントはログインできない |
| 接続元 | 接続元を社内ネットワークなどに限定できるようにする |
| 権限の原則 | 必要最小限。停止・返金・解約などの重い操作は、ロールに関係なく 2 人承認（運営者が 1 人だけのときの扱いは第23.8.6節。ADR-0116） |

**提携会社の運営者（第 0.481.0 版。Q-283）**: 2026-10-29 に三浦さんが、VPS の運用やサポートを受け持つ提携会社の人が、提携会社のアカウントでマスター管理画面に入れるようにすることを求めた。いまは 1 つのドメイン（`OPS_GOOGLE_DOMAIN`）のアカウントしか入れない。個人の Gmail などを許すと、辞めた人のアカウントを会社の側で止められないため、**会社が管理する Google のアカウント（Google Workspace か Cloud Identity）のドメインを、運営主体が選んで並べる**形にする。

| 項目 | 規定 |
|---|---|
| 許すドメイン | 配備の設定 `OPS_GOOGLE_DOMAIN` に、カンマで区切って複数並べられる（例 `ops.example.co.jp,partner.example.co.jp`）。大文字と小文字は区別しない。空なら制限しない（開発だけ）。**クラウドの形の `setup.sh` は 1 つ以上を求める** |
| Google のログインの画面 | 許すドメインが 1 つのときは、いままでどおり Google の画面でそのドメインのアカウントだけを出す。複数のときは Google の画面では絞らず、ログインの後にメールアドレスのドメインで確かめる（Google の画面で絞れるのは 1 つのドメインだけのため） |
| ログインの後の確かめ | メールアドレスのドメインが許すドメインのどれかで、Google が確かめたアドレスで、**運営者として登録されていて**、無効にされていないときだけ通す。いままでどおり、その後にパスキーで確かめる |
| 運営者を足すとき | 許すドメインのどれかのアドレスだけを登録できる。ロールは提携会社の人にも同じ 3 つ（運営管理者・サポート・監視）から選ぶ。2 人の承認・操作の記録・パスキーの決まりは変えない |
| 許すドメインから外したとき | そのドメインの運営者は、次のログインから入れない。すぐに止めるときは、運営者の画面でその人を無効にする（ログイン状態も切れる） |
| 前もって要ること | Google のログインの OAuth の同意画面を「外部」にする（「内部」だと運営主体のドメインの人しか Google の画面を通れない。お客様の会社の人のログインにも「外部」が要る）。提携会社の人の端末ごとに、WireGuard の鍵を出して VPS に登録する（運営の画面は WireGuard の網からしか開けない。第20.4.6節） |
| 運営者の一覧 | 運営者のメールアドレスで、どの会社の人かが分かる（所属の欄は足さない） |

**実装（第 0.481.0 版）**: 許すドメインの読み方と確かめは `packages/core/src/ops/rules.ts`（`parseOpsDomains`・`opsDomainAllowed`）、運営の API の設定は `googleDomains`（`packages/api/src/ops/`）。`deploy/vps/setup.sh` は答えの空白を除いて小文字にそろえ、1 つ以上と形を確かめる。手順は運営者マニュアル 第 2 章「提携会社の人を運営者にする」
