## 23. 運営バックヤード

**この章で決めること**: サービスを運営する側（M2Office 運営）に必要な仕組み。
**顧客向けの機能とは別に、運営を成立させる基盤が要る。**

### 23.1 位置づけ

運営バックヤードは、**顧客テナントとは完全に分離された運営専用のシステム**である。

| 観点 | 顧客テナント | 運営バックヤード |
|---|---|---|
| 利用者 | 顧客企業の従業員 | M2Office 運営 |
| 扱うデータ | 業務データ、知識、実行履歴 | テナントの状態、利用量、請求 |
| ドメイン | `<会社>.m2office.online` | 運営専用の別ドメイン |
| 認証 | Google アカウント（第16.1節） | **2 段階認証を必須とする**（第23.8.9節） |

**原則: 運営は顧客の業務データを見ない。**
運営が扱うのはメタ情報（稼働状況、利用量、請求）であり、
メールの中身や議事録の内容は対象外とする。例外手続きは第23.6節で規定する。

### 23.2 提供する機能

| 区分 | 機能 | 対応要件 |
|---|---|---|
| テナント管理 | 申込受付、審査、払い出し、設定変更、停止、解約 | FR-607 |
| 稼働監視 | 全テナント横断の実行件数・失敗率・遅延 | FR-604 |
| 利用量管理 | クレジット消費、残量、超過の把握 | FR-419 と連動 |
| 請求管理 | 締め、請求書発行、入金消込、督促、返金 | FR-608 |
| 決済 | クレジットカード、銀行振込 | FR-609 |
| 収益管理 | 月次収益、解約率、粗利の把握 | FR-610 |
| サポート | 問い合わせの受付と対応履歴 | TBD |
| 代理アクセス | 顧客データへの一時アクセスの統制 | FR-611 |
| **マスター管理画面** | 契約企業の一覧・詳細・ライセンス・利用の停止と再開（第23.8節） | FR-613〜616 |
| 拡張機能の審査 | 申請受付、検証、認定（第12.5節） | FR-603 |
| 収益分配 | 拡張機能提供者への支払 | FR-612 |

### 23.3 テナントのライフサイクル

```
 [申込] ──審査──→ [試用] ──有償化──→ [稼働中]
                     │                   │
                     │ 期限切れ          │ 未入金
                     ▼                   ▼
                  [失効]        [停止（閲覧のみ）]
                                         │
                                         │ 解約
                                         ▼
                                    [解約済み] ──猶予期間──→ [削除]
```

| 状態 | 意味 | 可能な操作 |
|---|---|---|
| 申込 | 受付済み、未払い出し | 審査、却下 |
| 試用 | 期限付きで利用可能 | 全機能（上限あり） |
| 稼働中 | 有償契約中 | 全機能 |
| 停止 | 未入金または規約違反 | **閲覧とエクスポートのみ。実行は不可** |
| 緊急停止 | 不正利用、乗っ取り、情報漏洩の疑い | なし（ログインを含めて止める。第23.8.6節） |
| 解約済み | 契約終了 | エクスポートのみ |
| 削除 | データ消去済み | なし |

**停止時に即座に全データを見えなくしない。**
未入金は事務的な行き違いで起きることが多く、いきなり業務が止まると顧客の被害が大きい。
実行だけを止め、閲覧とエクスポートは残す。

TBD: 試用期間の長さ、解約後の保持期間（Q-29）。停止までの猶予は 7 日と決めた（第 0.310.0 版。第23.8.6節）。

### 23.4 請求管理

#### 23.4.1 課金対象

| 対象 | 算出 | 発生 |
|---|---|---|
| シート利用料 | 有効なユーザー数 × 単価 | 毎月 |
| 同梱クレジット | シート利用料に含む | 毎月 |
| 追加クレジット | 購入分 | 都度 |
| 有料拡張機能 | 提供者の価格設定に従う | 毎月または都度 |
| 導入支援 | 個別見積 | 都度 |

#### 23.4.2 請求のサイクル

| 段階 | 内容 |
|---|---|
| 1 | 月末に利用実績を締める（シート数、クレジット消費、拡張機能） |
| 2 | 請求額を確定し、請求書を発行する |
| 3 | 顧客へ通知する（メール、管理者ページ） |
| 4 | 入金を確認し消込を行う |
| 5 | 未入金は督促し、期限を過ぎたら停止処理へ移行する |

**シート数の日割りをどう扱うかを決める必要がある。**
月の途中で従業員が増減する中小企業は多い。
「月初時点の人数で課金」は単純だが、増員が翌月まで反映されず不満が出る。
TBD: 算出方法（Q-30）。月末時点の最大同時利用者数を基準とする案を有力とする。

#### 23.4.3 日本の商習慣への対応

| 項目 | 要件 |
|---|---|
| 支払方法 | クレジットカードと**銀行振込の併存**。中小企業は振込を好む場合が多い |
| 決済代行 | **Stripe** を利用する |
| 締めと支払 | 月末締め翌月末払いなど、顧客ごとの支払サイトに対応する |
| **適格請求書** | **M2Office 自身が適格請求書発行事業者として、要件を満たす請求書を発行する。登録番号は運営バックヤードの設定画面から登録する** |
| 領収書 | 発行に対応する |
| 振込手数料 | 負担の取り決めを契約に明記する |
| 年度 | 顧客の決算期に合わせた年間契約の需要がある |

**適格請求書の発行は必須である。**
インボイス対応を売りにするサービス（AG-06）の請求書が要件を満たしていなければ、
説得力を失う。自社の請求書にも第15.1節の記載要件をそのまま適用する。

#### 23.4.4 自動化の範囲

| 処理 | 自動化 | 備考 |
|---|---|---|
| 利用実績の集計 | 完全自動 | |
| 請求書の発行と送付 | 自動 | |
| カード決済 | 自動 | **Stripe** に委託 |
| 振込の入金消込 | 半自動 | 入金データの取込と照合。差異は人が確認。TBD: Stripe で扱うか別手段か（Q-40） |
| 督促 | 自動（文面は事前承認） | 段階的に文面を変える |
| 停止処理 | **人の承認を経る** | 誤った停止は顧客への影響が大きい |
| 返金 | 人の承認を経る | |

**停止と返金は自動化しない。**
金銭と業務継続に直結するため、第9.4節と同じ考え方で人の承認を必須とする。

### 23.5 運営の全体指標

| 区分 | 表示項目 |
|---|---|
| 契約 | テナント一覧と状態、新規申込、試用中、解約予定 |
| 収益 | 月次収益、シート数の推移、解約率、平均単価 |
| 原価 | クレジット消費に対する実コスト、テナント別の粗利 |
| 稼働 | 全テナントの実行件数、失敗率、遅延、承認待ちの滞留 |
| 異常 | 利用量の急増、失敗の多発、コスト上限への接近、連携の切断 |
| 請求 | 未請求、未入金、督促中、停止予定 |
| サポート | 問い合わせの件数と滞留 |
| 拡張機能 | 審査待ち、導入数、提供者別の収益 |

**「原価に対する粗利がテナント別に見えること」が最も重要である。**
クレジット制（第21.2節）の換算レートが適切かどうかは、この数字でしか判断できない。
レートが甘ければ赤字のテナントが生まれ、厳しすぎれば利用が抑制される。

### 23.6 顧客データへのアクセス統制

**運営が顧客の業務データを自由に見られる状態は、信頼を損なう。**
調査で「情報漏洩のリスク」が懸念の 33.5% を占めることからも、ここは明確に規定する。

| 段階 | 内容 |
|---|---|
| 原則 | 運営は顧客の業務データ（メール、文書、知識、個人記憶）を閲覧できない |
| 例外の発動 | 障害調査やサポートで必要な場合に限り、申請する |
| 顧客の同意 | **テナント管理者の明示的な同意を得る** |
| 期限 | 期限付きの一時アクセスとし、自動的に失効する |
| 範囲 | 必要な対象のみに限定する |
| 記録 | 誰が・いつ・何を見たかをすべて記録する |
| 通知 | アクセス後、顧客へ内容を通知する |

この仕組み自体を製品説明に明記し、契約書にも反映する。

#### 23.6.1 代理アクセスの実装（第 0.312.0 版。マスター管理画面の段 2）

三浦さんが、範囲は申請ごとに 2 段から選ぶ・期限は許す人が選ぶ・同意は会社の管理者の誰か 1 人、と決めた。

| 項目 | 規定 |
|---|---|
| 申請 | 運営管理者かサポートが、マスター管理画面の会社の詳細から、範囲と理由（必須）を書いて申請する。会社の管理者全員に M2Office の中の通知が届く |
| 範囲 | **管理者ページ**（設定・接続・業務の実行の一覧と状態・監査ログ・利用状況）か、それに加えて**業務の結果**。業務の結果で見られるのは、**許した管理者が自分で依頼した実行の中身と成果物だけ**（会社の管理者でもほかの人の実行の中身は見られないため。第6.6.8節・不変則 I-10。三浦さんが決めた）。閲覧のときは許した管理者として見るが、見られる道を限る。どちらも**見るだけ**で、書き換え・依頼・承認はできない。秘書との会話・個人の記憶・知識（社内規程など）・名刺や在庫などの各業務の台帳・Google のメールや文書・ファイルの取り出し（監査ログの書き出しを含む）は、どちらの範囲でも見られない |
| 同意 | 会社の管理者の誰か 1 人が、管理者ページの「サポートの閲覧」で許すか断る。許すときに期限を 1 時間・4 時間・1 日・3 日から選ぶ（既定 1 日）。管理者はいつでも切れる |
| 入り方 | 許されたら、申請した運営者だけが、マスター管理画面の「会社の画面を開く」で入る（1 回だけ使える 2 分の引換券で、会社の名前の画面に閲覧だけのログイン状態を張る）。画面の上に「運営のサポートが閲覧しています」と期限を出す |
| 記録 | 閲覧のたびに、どの画面（API の道）を見たかを会社の監査ログに残す（`proxy.view`）。申請・許可・断り・切ったこと・入ったことも、会社の監査ログと運営の操作の記録に残す |
| 終わったあとの知らせ | 期限が来るか切られたら、ワーカーが会社の管理者に、閲覧の回数と監査ログで中身を確かめられることを知らせる |
| 作り | 申請と許可は `proxy_grants`、閲覧のログイン状態は `proxy_sessions`（どちらも会社ごとの行レベルセキュリティ）。運営の側は決めた関数（`ops.request_proxy`・`ops.proxy_ticket` など）だけで触る。顧客向けの API は、閲覧のログイン状態の要求を、見るだけの決めた道（範囲ごとの許可の表）に限る |

### 23.7 段階的な構築

**運営バックヤードは Phase 1 から作り込む必要はない。**
自社および関連会社のみの段階では、多くを手作業で回せる。

| フェーズ | 状態 | 構築するもの |
|---|---|---|
| Phase 1 | 自社のみ（1 テナント） | **監視の最低限のみ**。請求は不要 |
| Phase 2 | 関連会社（数テナント） | テナント払い出しの自動化、稼働監視、利用量の把握。請求は手作業でよい |
| Phase 3 | 限定外販（10〜） | **請求・決済の自動化**、収益ダッシュボード、代理アクセス統制、サポート受付 |
| Phase 4 | 一般提供 | セルフサインアップの完全自動化、収益分配、パートナー管理 |

**ただし Phase 1 から用意しておくべきデータがある。**

| # | 項目 | 理由 |
|---|---|---|
| 1 | 実行ごとのコスト記録 | 後から遡れない。価格設計の材料になる |
| 2 | テナント・ユーザー単位の利用量集計 | 請求の基礎データ。後付けだと過去分が出せない |
| 3 | テナントの状態遷移の記録 | 契約履歴の証跡 |
| 4 | 代理アクセスの記録 | 信頼の証跡。最初から記録する |

**請求システムは後から作れるが、請求の根拠となるデータは後から作れない。**
これが本章で最も重要な結論である。

### 23.8 マスター管理画面

**この節で決めること**: 運営が全契約企業を一元的に管理する画面の構成と、そこで行える操作。

#### 23.8.1 目的

**マスター管理画面を開けば、ライセンスを契約している会社がすべて並び、
各社の契約・利用・請求・稼働の状況がひと目で分かる。** 運営のあらゆる操作はここから始まる。

| 問い | 答える場所 |
|---|---|
| どのサブドメインにどの会社が割り当たっているか | 会社一覧（第23.8.3節） |
| その会社は何シート契約し、何人使っているか | 会社一覧・会社の詳細（第23.8.5節） |
| 請求は済んでいるか、入金されているか | 会社一覧・会社の詳細の請求（第23.8.4節） |
| サーバー全体は健全に動いているか | 一覧の上部の要約と稼働状況（第23.8.7節） |
| 利用を止める必要があるか、止めたら何が起きるか | 利用の停止と再開（第23.8.6節） |

第23.5節の運営の全体指標は「全体の傾向」、マスター管理画面は
「個々の会社」を見て操作する画面として役割を分ける。前者は後者のトップに要約として載せる。

#### 23.8.2 位置と画面構成

| 項目 | 方針 |
|---|---|
| 置き場所 | **`ops.m2office.online`**（Q-60 で決定）。顧客には払い出さない予約語（第20.4.3節）とし、顧客テナントのサブドメインとしては使わせない |
| Cookie | ログイン状態の Cookie は `Domain` 属性を付けない（第20.7節）。**ホスト単位で閉じる**ため、顧客のサブドメインへは渡らない。これが同じドメインの下に置ける前提である |
| API | 運営用の API を顧客向け API とは別に設ける。顧客向け API から運営の操作はできない |
| 見直し | 分離をより強くしたくなったら、別のドメインへ移す。**そのときに変わるのは URL と証明書だけ**で、Cookie の扱いは変わらない |

```
┌───────────────────────────────────────────────────────────────────────┐
│ M2Office マスター管理                           運営者名   ログアウト │
├──────────┬────────────────────────────────────────────────────────────┤

```

#### 23.8.4 会社の詳細

1 社のことが 1 画面で分かるようにする。タブで区切る。

| タブ | 表示する内容 |
|---|---|
| **概要** | 会社名、サブドメイン、Workspace のドメイン、状態、契約開始日、先方の管理者（氏名・連絡先）、販売経路（直販・パートナー経由。第21.6節） |
| **ライセンス** | プラン、契約シート数、利用中のシート数と一覧（氏名とロールのみ）、契約期間、更新日、支払方法、支払サイト（第23.8.5節） |
| **利用状況** | 今月と過去 12 か月の実行件数、利用量、原価、**粗利**（第23.5節）、エージェント別の内訳、上限の設定 |
| **請求** | 請求書の一覧（発行日・金額・状態）、入金の記録、督促の段階、次回請求の見込み |
| **稼働** | 失敗率、承認の滞留、Google 連携や MCP の接続状態、直近のエラー（件数と種類のみ） |
| **履歴** | 状態の遷移、ライセンスの変更、停止と再開、代理アクセスの記録（第23.6節） |

**ここにも業務データは出さない**（第23.1節の原則）。
表示するのは件数・金額・状態・名前までであり、メール・文書・議事録・知識・会話の中身は表示しない。
利用中のシートの一覧も、氏名とロールにとどめる。

この画面から行える操作は次のとおり。いずれも操作履歴に残る（第23.8.10節）。

| 操作 | 承認 | 顧客への通知 |
|---|---|---|
| ライセンスの変更（プラン・シート数・期間） | 不要（記録のみ） | する |
| 試用期間の延長 | 不要（記録のみ） | する |
| **利用の停止・再開** | **2 人の運営者の承認**（第23.8.6節） | する |
| 解約の処理 | 2 人の運営者の承認 | する |
| 請求の取り消し・返金 | 2 人の運営者の承認（第23.4.4節） | する |
| 代理アクセスの申請 | 顧客の管理者の同意（第23.6節） | する |

#### 23.8.6 利用の停止と再開

第23.3節の「停止」を、マスター管理画面からの操作として規定する。

**停止は 2 種類に分ける。**

| 種類 | 使う場面 | 顧客側で起きること |
|---|---|---|
| **通常の停止** | 未入金、規約違反 | **閲覧とエクスポートのみ**。新規の実行・定時実行・外部 API は止まる。実行中の処理は完走させる（第21.2.3節） |
| **緊急停止** | 不正利用、アカウントの乗っ取り、情報漏洩の疑い | **ログインを含めて全面的に止める**。被害の拡大を防ぐことを優先する |

**通常の停止の手順**

| 段階 | 内容 |
|---|---|
| 1 | 運営者が停止を申請する。理由（未入金・規約違反など）を必ず選ぶ |
| 2 | **申請者とは別の運営者が承認する**（2 人承認）。誤った停止は顧客への影響が大きいため（第23.4.4節） |
| 3 | 顧客の管理者へ予告を通知する。予告から停止までの猶予は Q-29 |
| 4 | 猶予の後に停止する。顧客の画面には停止中である旨と、解除の方法（入金の確認など）を表示する |
| 5 | すべてを操作履歴と、顧客の監査ログの両方に残す |

**緊急停止は運営者なら誰でも発動できる**（Q-63 で決定）。事故への反応を最優先するためである。
誤った停止に備えて、次を条件とする。

| 条件 | 内容 |
|---|---|
| 理由 | 発動のときに理由の入力を必須とする |
| 周知 | 発動を**運営者全員に知らせる**。誰がいつ、どの会社を止めたかを含める |
| 事後の確認 | 事後に**別の運営者の確認**を必ず受ける |
| 顧客への通知 | 停止の直後に理由を通知する |
| 解除 | 解除は 2 人承認とする（通常の停止の再開と同じ） |

**再開**は、停止の理由が解消されたこと（入金の確認など）を記録したうえで行う。
再開も 2 人承認とする。ただし入金の消込で自動的に解消した場合は、1 人の確認でよい。

**停止中でも失わないもの**

| 対象 | 扱い |
|---|---|
| データ | 保持する。削除は解約後の保持期間を過ぎてから（第23.3節） |
| 定時実行 | 止める。再開時に、止まっていた間の回はまとめて 1 回だけ起動する（ワーカーが止まっていた場合と同じ扱い。週次ブリーフが何通も届くことを避ける） |
| 承認待ち | 残す。再開後に承認できる |

**実装上の扱い**（第 0.51.0 版で規定）

テナントの台帳（`tenants.status`）の値で、2 種類の停止を分ける（第23.8.11節）。

| 値 | 意味 | API |
|---|---|---|
| `trial`・`active` | 試用・稼働中 | すべて受け付ける |
| `suspended` | **通常の停止** | 閲覧（`GET`）と、下の表の操作だけを受け付ける。ほかの書き込みは 403 で拒否し、停止中であることを返す |
| `locked` | **緊急停止** | ログインを含めてすべて拒否する。停止の理由は画面に出さない（攻撃者に手がかりを与えないため。理由は管理者へ別に通知する） |
| `cancelled` | 解約済み | すべて拒否する。規定は「エクスポートのみ」だが、持ち出し（第11.10節。Phase 2）が未実装のため。持ち出しを実装するときに直す |

**通常の停止で受け付ける書き込み**

| 操作 | 理由 |
|---|---|
| ログインとログアウト | 閲覧にはログインが要る |
| お知らせの既読 | 閲覧の一部。業務のデータを変えない |
| ログイン中の端末のログアウト（第6.5.8節） | 乗っ取りへの備え（R-13）。停止中でも本人が端末を切れるようにする |

業務の依頼・秘書への依頼・承認の判断・設定の変更・ファイルの受け付け・Google との接続は受け付けない。
閲覧には、成果物とファイルの取り出し（ダウンロード）を含める。持ち出し（OKF のエクスポート）は Phase 2 で、できたら通常の停止でも受け付ける。

**ワーカーの扱い**

| 対象 | 扱い |
|---|---|
| 実行中（`running`）の実行 | 完走させる。承認ステップに達したら承認待ちで止まる |
| 待ち行列（`queued`）の実行 | 始めない。再開すると、そのまま続きから動く |
| 定時実行 | 起動しない。次の実行時刻を進めないため、再開したときに止まっていた間の回がまとめて 1 回だけ起動する |
| 保持期間の見回り（第14.3.2節） | 続ける。預かったデータを消す義務は、停止中も変わらない |

**画面**: 通常の停止の間は、すべての画面の上部に「ご利用を停止しています。閲覧のみできます」と、解除の方法の案内を出す。

**マスター管理画面からの停止と再開（第 0.310.0 版で実装。段 2）**: 三浦さんが、猶予は 7 日・会社への知らせは画面の中と運営者が渡す・申請と承認は運営管理者とサポート、と決めた。

| 操作 | 行える人 | 流れ |
|---|---|---|
| 通常の停止 | 申請も承認も運営管理者とサポート（申請した人とは別の人が承認する） | 理由の種類（未入金・規約違反・そのほか）と理由の文を必須にして申請 → 別の運営者が承認すると、会社の管理者に予告を届け（M2Office の中の通知と画面の上の帯）、**7 日後に止める**（ワーカーが 1 分ごとに期限の来たものを止める）。その間に解消したら、承認の前でも後でも申請を取り下げられる |
| 緊急停止 | 運営者なら誰でも（Q-63） | 理由の種類（不正利用・乗っ取り・情報漏洩の疑い・そのほか）と理由の文を必須にして発動すると、**すぐに止める**。運営の画面の上に、確認待ちの緊急停止を全員に出す。申請した人とは別の運営管理者かサポートが、事後に確認する |
| 再開 | 申請も承認も運営管理者とサポート（別の人が承認） | 理由が解消されたことを書いて申請 → 別の運営者が承認すると、止める前の状態（試用か稼働中）に戻し、会社の管理者に知らせる |

- 会社の管理者への知らせは、M2Office の中の通知（種類「ご利用」）と画面の上の帯で行う。運営の画面は社外にメールを送らず、予告・停止・再開の案内の文を出して、運営者が自分のメールなどで渡す（Q-213 と同じ考え方）。緊急停止の間はログインできないため、運営者が渡すだけ
- 申請・承認・取り下げ・確認・実際に止めたこと・再開は、すべて運営の操作の記録と、その会社の監査ログの両方に残す
- 記録はデータベースの `ops.status_requests` に持ち、状態の変更は所有者の権限で動く決めた関数だけで行う（申請した人が自分で承認できないことも関数の中で確かめる）
- 入金の消込による自動の再開は、請求の段（第23.4節）で足す

#### 23.8.8 サブドメインの割り当て

**サブドメインと会社の対応は、マスター管理画面が唯一の正とする。**

| 項目 | 方針 |
|---|---|

#### 23.8.9 運営者と権限

**運営者は顧客テナントの利用者とは別に管理する。** 顧客のテナントに運営者のアカウントは置かない。

| ロール | できること |
|---|---|
| 運営管理者 | すべて。運営者の追加と権限の変更 |
| 請求担当 | 請求・入金・督促・返金の申請。停止の申請 |
| サポート | 会社の詳細の閲覧、代理アクセスの申請（第23.6節） |
| 監視 | 稼働状況と会社一覧の閲覧のみ |

| 項目 | 方針 |
|---|---|
| ログイン | 運営主体の Google Workspace のアカウントで行う。TBD（Q-62） |
| 2 段階認証 | **必須**。未設定のアカウントはログインできない |
| 接続元 | 接続元を社内ネットワークなどに限定できるようにする |
| 権限の原則 | 必要最小限。停止・返金・解約などの重い操作は、ロールに関係なく 2 人承認 |

#### 23.8.10 記録

**運営者の操作はすべて記録する。**

| 項目 | 内容 |
|---|---|
| 記録する操作 | 閲覧を含むすべて。とくに状態の変更・ライセンスの変更・請求の操作・代理アクセス |
| 保存先 | 運営側の監査ログ。顧客テナントの監査ログとは別に持つ |
| 顧客への開示 | **その会社に影響する操作（停止・再開・ライセンスの変更・代理アクセス）は、顧客の監査ログにも残す**。顧客の管理者ページから確認できる |
| 改ざんの防止 | 追記のみ。運営者自身も更新・削除できない（第8.5.5節と同じ扱い） |

#### 23.8.11 データの持ち方

| データ | 置き場 | 備考 |
|---|---|---|
| テナントの台帳（会社名・サブドメイン・状態） | 共有のデータベースの `tenants` | 状態は**顧客側の画面と API が参照する唯一の値**。停止の強制はここで効く |
| 契約・ライセンス・請求・入金 | 運営専用の領域 | 顧客向けの API からは読めない。アプリのロール（`m2office_app`）には権限を与えない |

| 運営者と運営側の監査ログ | 運営専用の領域 | |
| 利用量・原価 | 顧客テナントの実行記録から集計 | 集計結果だけを運営側へ渡す。業務データは渡さない |

運営専用の領域には、運営用の API だけが専用のデータベースロールで接続する。
顧客向けの API が侵害されても、契約や請求のデータには届かないようにする。

#### 23.8.14 運営主体の設定（第 0.180.0 版。予定）

**数の取り方**: 会社ごとの数は、ワーカーが毎晩、集計の口で数えて運営の表に日ごとに残す（会社一覧の「今日」だけはその場で数える）。数えるのは件数・金額・状態だけで、業務の中身・人の名前は運営の表に移さない（利用者の名前を見るのは会社の詳細のシートの一覧だけ。第23.8.4節）。

**運営者のパスキー（第 0.317.0 版）**: 三浦さんが、最初の登録は運営管理者が出す登録の合言葉・確かめはログインのたび・なくしたときは別の運営管理者が登録をやり直させる、と決めた。

| 項目 | 規定 |
|---|---|
| 確かめ | Google でログインしたあと、**ログインのたびに**パスキー（指紋・顔・セキュリティキー）で確かめる。確かめるまでは、運営の画面のどの操作もできない（本人とパスキーの操作だけ） |
| 最初の登録 | 運営管理者が、運営者ごとに **1 回だけ使える登録の合言葉**（24 時間で切れる）を出し、本人に別の手段で渡す。本人は Google でログインしたあと、合言葉を入れてパスキーを登録する。Google のアカウントが乗っ取られても、合言葉が無ければ登録できない。最初の運営管理者の合言葉は、手元のツール（`npm run ops:operator`）が出す |
| 予備 | 1 人 5 つまで登録できる（別の端末や予備のセキュリティキー）。確かめたあとに本人が足す・削除する（最後の 1 つは削除できない） |
| なくしたとき | **別の運営管理者**が、その人のパスキーを削除して、新しい登録の合言葉を出す（その人のログイン状態も切る）。最後の 1 人の運営管理者のときは、手元のツールで行う |
| 開発 | 開発用ログイン（本番では起動を拒否する）では、パスキーを求めない |
| 記録 | 登録・確かめ・削除・合言葉を出したことを、運営の操作の記録に残す |

運営者向けの手引きは `docs/ops-manual/`（マスター管理画面 運営者マニュアル。`npm run docs:ops-manual-pdf` で PDF。会社の利用者のヘルプには入れない）。

**1 回目の実装（第 0.308.0 版）**: 三浦さんが段 1 を 2 回に分けると決めた。1 回目に、次を作った。
- 運営の API は、顧客向けの API と同じソースの別の入口（`packages/api/src/ops/`。開発は 3102 番）で動かし、名前が `ops.` で始まる要求だけを受ける（Q-212）。画面は同じ組み立ての中で、名前が `ops.` のときだけ運営の画面を出す
- データベースは `ops` スキーマ（運営者・運営のログイン状態・運営の操作の記録・機械）と、専用のロール `m2office_ops`（移行 111）。このロールには顧客の表の権限を与えず、`public` の関数も既定では呼べなくした（関数を呼べるのはアプリのロールだけにした）。会社の一覧の数・会社を作る・状態を変えるは、所有者の権限で動く決めた関数（`ops.tenant_overview`・`ops.create_tenant`・`ops.set_tenant_status`）だけで行う。数は件数・金額・状態だけを返す
- 運営者のログインは、運営の OAuth クライアント（顧客と同じもの）で Google にログインし、登録された運営者だけを通す（`OPS_GOOGLE_DOMAIN` があればそのドメインに限る）。Cookie は `ops.` のホストだけに張る。最初の運営管理者は手元のツール（`npm run ops:operator`）で作る
- 会社一覧（要約・検索・状態の絞り込み・並べ替え。数はその場で数える）・会社を作る（試用か稼働か。作ったらログインの URL と案内の文を出す）・試用と稼働の切り替え・ローカルの形の機械（登録すると受け口の鍵を 1 度だけ出す。稼働の知らせを受け、3 時間来ない・控えの失敗・空きが 10% を切る・証明書が 14 日を切ると印を付ける）・運営者・操作履歴
- 運営者の操作はすべて運営の操作の記録に、会社に影響する操作はその会社の監査ログにも残す
- **2 回目**: 会社の詳細・サーバー全体の稼働状況・毎晩の数の記録・運営主体の設定・CSV の書き出し・機械の印の運営者への知らせ

**2 回目の実装（第 0.309.0 版）**:
- **毎晩の数の記録**: クラウドの形のワーカーが、毎晩 0 時 30 分（日本時間）すぎに前の日の数を会社ごとに `ops.tenant_daily` に残す（利用中の利用者・その日に使った人・業務の実行と失敗・秘書の会話・AI の費用と呼び出し・保存の量）。所有者の権限で動く決めた関数（`m2o_ops_record_daily`）で数え、件数・金額・状態だけを移す。同じ日を数え直したら書き替える
- **会社の詳細**: 概要・利用状況（過去 12 か月の月ごと。今月はその場で数える）・稼働（30 日の失敗の割合・承認の滞留と最も古い待ち・Google の接続の数・接続先ごとの直近 24 時間の失敗・失敗した業務の種類と件数）・シート（氏名・ロール・状態・最後に使った日時。**利用者の名前を出すのはここだけ**）・履歴（会社の状態の移り変わりと、その会社への運営の操作）。失敗の理由の文は業務の中身を含みうるため出さず、業務の種類（業務の ID）と件数だけにする
- **サーバー全体の稼働状況**: 待ち行列の長さと最も古い待ち・動いている実行・直近 1 時間と今日の実行と失敗の割合・ワーカーの最後の応答（ワーカーが 1 分ごとに `worker_beats` に書く）・遅れている定時実行の数（5 分を超えたもの）・AI と Google の直近 24 時間の呼び出しと失敗と応答の速さ・データベースの大きさと接続の数・ファイルの置き場の使用量・今日と今月の AI の費用と前の月の同じ時期との比較
- **運営主体の設定**（第23.8.14節）: 運営管理者が「設定」で入れる（法人名の日本語と英語・所在地・Web・問い合わせの窓口）。顧客の側は決めた関数（`m2o_operator_profile`）で読むだけ。入れたら、内蔵の拡張機能の「提供」の表記を法人名にする（入れるまでは「M2Office」）。利用規約・請求書・資料の表紙は、それぞれを作る段で使う
- **CSV の書き出し**: 会社一覧の数を CSV で書き出す（運営の操作の記録に残す）
- **機械の印の知らせ**: 運営の画面の中で知らせる（左のメニューの「ローカルの形の機械」に印のある機械の数、会社一覧の要約に同じ数）。運営の画面からはメールなどで社外に送らない
- **閲覧の記録**: 会社の詳細を開いたことと CSV の書き出しを、運営の操作の記録に残す（一覧の読み直しは数が多く役に立たないため残さない）
