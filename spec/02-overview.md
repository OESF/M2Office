## 2. サービス概要とスコープ

**この章で決めること**: 何を、どういう形で提供するか。

### 2.1 提供形態

| 項目 | 内容 |
|---|---|
| 形態 | クラウドから提供するマルチテナント型 Web サービス（SaaS）兼 拡張プラットフォーム |
| クライアント | Web ブラウザのみ（PC 主体、スマートフォンは閲覧・承認・音声に対応） |
| テナント識別 | 企業ごとのサブドメイン。例: A 社は `a.m2office.online` |
| ログイン | **Google アカウント（OpenID Connect）**。2 段階認証は Phase 1 から必須 |
| 共通基盤 | **Google プラットフォーム（Workspace）に一本化** |
| バックエンド LLM | **Gemini を既定**（Gemini API を直接利用）。抽象化層により差し替え可能 |
| インフラ | **未決（さくら・エックスサーバー・Google Cloud の 3 候補）** |
| 想定規模 | 1 テナントあたり 10 名程度まで |
| 対象国・言語 | 日本国内、日本語 |

### 2.2 Google プラットフォームへの一本化

標準機能が依存する外部サービスは Google に統一する。
手を広げないことを明示的な方針とし、他サービスへの対応は拡張機能に委ねる。

| 機能 | 採用する Google サービス | 代替への対応 |
|---|---|---|
| メール | Gmail | 拡張機能で対応（Phase 3 以降） |
| ドキュメント | Google ドキュメント / スプレッドシート / スライド | 同上 |
| ファイル保管 | Google ドライブ | 同上 |
| カレンダー | Google カレンダー | 同上 |
| ToDo | Google Tasks | 同上 |
| メッセージ | Google Chat | 同上 |
| 会議 | Google Meet | 同上 |
| 認証 | Google アカウント（OpenID Connect） | 独自のパスワードは持たない（第16.1節） |
| LLM | Gemini | 抽象化層により差し替え可能（第20.2節） |

**この一本化により得られるもの**: 実装対象の限定、動作検証の単純化、
データ所在地と契約先の一本化、そして「社内の情報が一箇所に集まる」状態。
第1.4節の優位 A-1 は、情報が分散していては成立しない。

##### 一本化できない部分

**一本化するのは社内の基盤であり、やり取りするファイルの形式ではない。**

取引先から届くのは Excel と PDF である。請求書も証憑も見積書も、
Google の形式で届くことはまずない。
したがって、これらを読み書きする能力は共通のツールとして備える（第9.4.1節）。

### 2.3 共通基盤と拡張という構造

**この節で決めること**: 共通の部分と、会社ごとに違う部分をどう分けるか。

#### 2.3.1 中小企業の事情は個社ごとに違う

どの会社にも共通する業務がある一方で、
業種・取引先・社内の慣習によって求められるものは大きく違う。

| 共通する部分 | 会社ごとに違う部分 |
|---|---|
| メール、予定、文書、会議 | 業種固有の帳票と手順 |
| 議事録、社内規程の照会 | 取引先ごとの取り決め |
| 見積・請求の骨格 | 社内の呼び方、承認の慣習 |
| 承認、権限、記録 | 使っている業務システム |

**後者のために毎回システム全体を作り直すのは現実的でない。**

##### 供給側の構造問題

日本のソフトウェア開発では、個社の要望に応えるために
**毎回ゼロからシステムを作る**慣行が続いてきた。

| 方式 | 起きること |
|---|---|
| 受託開発 | すべてが人月の見積もりになる。費用と期間が中小企業の手に負えない |
| 汎用パッケージ | 業務に合わない部分が残る。既存システムとの連携が埋まらない |

1 社ずつ個別に作れば、**作った分しか増えない**。
生産性が上がらないまま、同じような仕組みが各社で重複して作られる。

##### AI が埋めるもの

この間を埋める役割を AI に担わせる。

| 役割 | 内容 |
|---|---|
| 既存システムどうしをつなぐ | 人手で転記していた部分を引き受ける |
| 個社固有の業務を差し込む | **土台や他の業務に影響を与えずに追加する** |

「土台に影響を与えずに差し込める」ことが要点である。
これが成り立つなら、個社対応はシステム全体の作り直しではなく、
**差分を足す作業**になる。

##### 参考にした考え方

業務手順を宣言的に記述し、必要なときに呼び出す「スキル」の形は、
Anthropic が公開するプラグイン群（付録 B）で実際に動いている。
コードもインフラも要らず、記述だけで業務が形になるという点で優れている。

**ただし、そのままでは中小企業に届かない。**
スキルの作成も導入もファイルとコマンドの操作であり、
扱えるのは技術力のある利用者に限られる。
この差を埋めるのが第2.3.3節である。

#### 2.3.2 M2Office の形

**共通基盤の上に、必要なものだけを積み上げる。**

```
          ┌──────────────────────────────────────┐
  会社ごと │  拡張（業種特化・個社固有の業務）        │ ← 必要なものだけ足す
          ├──────────────────────────────────────┤
          │  M2Office 基盤                        │
   共通   │  秘書・承認・権限・記録・知識・課金      │ ← どの会社も同じ
          ├──────────────────────────────────────┤
          │  Google Workspace                     │ ← どの会社も同じ
          └──────────────────────────────────────┘
```

| 層 | 内容 | 誰が用意するか |
|---|---|---|
| Google Workspace | メール、予定、文書、会議、チャット | 顧客が既に持っている |
| M2Office 基盤 | 秘書、承認ゲート、権限、監査、知識、課金 | **運営が提供する。全社共通** |
| 拡張 | 業種特化・個社固有の業務 | **運営・第三者・顧客自身** |

下の 2 層はどの会社でも同じである。**違いは一番上の層だけに現れる。**
フルスクラッチで作り直すのではなく、共通の土台に載せる分だけを作る。

#### 2.3.3 GUI で拡張できることが差になる

**同じ「スキルを足す」でも、その作業が誰にできるかで価値が変わる。**

業務手順を記述して AI に実行させる方式は既に存在する。
しかし既存の方式では、**スキルの作成も導入もファイルとコマンドの操作**である。

| 観点 | 既存の方式 | M2Office |
|---|---|---|
| スキルの実体 | リポジトリ内のファイル | データベース上の定義 |
| 導入 | コマンドで取り込み、再インストール | **画面から選んで有効化** |
| 設定の変更 | ファイルを書き換える | **画面から編集する** |
| 誰に扱えるか | 技術者 | **業務担当者** |
| 権限の割当 | 環境の権限に従う | **画面で人ごとに割り当てる** |
| 導入後の管理 | 各自の環境に散る | 一元管理され、記録が残る |
| **持ち運び** | リポジトリを取得し、手元で配置する | **1 つのファイル（`.m2ext`）で渡し、画面で取り込む**（第12.10節） |
| **有効・無効** | ファイルを移す・消す | **スイッチで切り替える** |
| **外部とのつながり** | 環境ごとに設定する | **会社の接続（MCP）を管理者が URL で登録する。拡張機能は同梱して、導入のときに登録できる**（第12.11節） |

**これが生産性の差になる。**
ファイルを書ける人しか扱えないなら、拡張の速度はその人数で頭打ちになる。
画面から扱えれば、業務を知っている人が自分で調整できる。

もっとも、**手順の設計まで利用者に求めるわけではない**（第12.7節）。
GUI で行えるのは既存の業務の設定変更までとし、
新しい業務の定義は開発者が担う。境界は第12.7.1節に定める。

#### 2.3.4 パートナー制度が成り立つ

**拡張が画面から導入できることは、外部に作ってもらう前提を整える。**

作る側が技術者であっても、**使う側が技術者である必要はない**。
この分離があるため、次の分担が成立する。

| 役割 | 担う人 | できること |
|---|---|---|
| 作る | インテグレーター、SaaS ベンダー、士業 | 業種特化・個社固有の拡張を作る |
| 届ける | マーケット、パートナー | 顧客に選んでもらう |
| 入れる | **顧客の管理者** | **画面から導入し、権限を割り当てる** |
| 使う | 顧客の従業員 | 業務として実行する |

運営がすべての業種・すべての業務を作ることはできない（第1.9節）。
**作れる人を増やし、入れる作業を簡単にする**ことで、
提供できる範囲を運営の開発力から切り離す。

詳しくは第12章（拡張機構）と第13.7節（パートナー制度）に定める。

### 2.5 対象業務領域

| 領域 | 含む業務 | 対象フェーズ | 提供主体 |
|---|---|---|---|
| 秘書業務 | 予定確認、情報照会、取次、記録、依頼の振り分け | Phase 1 | 公式 |
| メール・コミュニケーション | 受信箱整理、返信起案、問い合わせ一次対応 | Phase 1 | 公式 |
| 会議・議事録 | Meet の要約、議事録作成、決定事項のタスク化と共有 | Phase 1 | 公式 |
| スケジュール・タスク | 日程調整、ToDo 起票と進捗の追跡 | Phase 1 | 公式 |
| 社内ナレッジ | 規程 Q&A、ドライブ横断検索、文書作成 | Phase 1 | 公式 |
| 販売事務 | 見積書・請求書の作成、入金消込の下準備 | Phase 2 | 公式 |
| 経理・経費 | 証憑の読み取り、仕訳候補の生成、経費精算 | Phase 2 | 公式 |
| 人事・給与（HR） | 人事の台帳・勤怠・休暇・**給与計算**・賞与・社会保険・住民税・年末調整・法定の帳簿と帳票（第30章。内蔵の拡張、既定は切り。第 0.154.0 版） | Phase 3（第30.26節の段階で前倒しを検討） | 公式 |
| 業種特化 | 建設、士業、医療、小売など業種固有の業務 | Phase 3 以降 | **第三者**。M2Office の中には作らず、外のシステムを接続（L2）でつなぐ。要配慮個人情報のように社外に出せないデータは、顧客の手元のシステムに置いたまま集計だけを受け取る（第12.11.7節、ADR-0046） |
| 顧客固有 | 個社の独自業務 | 随時 | **顧客自身／インテグレーター** |

### 2.6 スコープ外

| 項目 | 理由 |
|---|---|
| 会計帳簿の正本としての保持 | 会計 SaaS の責務。M2Office は下書きと連携に徹する |
| 届出の提出の代行・労務と税務の個別の相談 | 社会保険労務士・税理士の独占業務。**給与計算そのものは第 0.154.0 版で対象にした**（会社が自社の従業員について行う計算の道具として。第30章、ADR-0049） |
| 税務申告書の作成・提出 | 税理士の独占業務に抵触しうるため扱わない |
| 法律判断・契約の可否判断 | 弁護士法との関係。下書きと論点抽出までとする |
| Google 以外のグループウェアへの標準対応 | 第2.2節の方針。拡張機能に委ねる |
| オンプレミス提供 | Phase 3 までは行わない |

**重要**: 税務・労務・法務の各領域では、M2Office の出力は常に「下書き・整理・論点提示」であり、
専門家の確認を経ることを前提とする。この境界は第15章で規定する。
