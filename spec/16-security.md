## 16. 認証・セキュリティ・権限・プライバシー

### 16.1 認証

| 項目 | 方式 | 備考 |
|---|---|---|
| ログイン | **Google アカウント（OpenID Connect）** | 独自のパスワードは保持しない |
| テナント判定 | Workspace のドメインとテナントの対応を検証 | 招待されていないドメインは拒否する |
| **2 段階認証** | **Google アカウント側の 2 段階認証を利用。Phase 1 から必須とする** | 自前実装は行わない |
| セッション | API が発行する httpOnly Cookie | 第20.7節 |
| 失効 | Workspace 側でアカウントを停止すれば M2Office も使えなくなる | 退職処理が一元化される |
| 外部協力者 | Google アカウントを持たない相手の扱い | TBD（Q-34） |

**Google アカウントに一本化することで得られるもの**

| # | 内容 |
|---|---|
| 1 | パスワードの保管・リセット・漏洩対応といった責務を自社で負わない |
| 2 | 2 段階認証を Google の仕組みに委ねられ、自前実装が不要になる |
| 3 | ログインと Google 連携の同意が同じ事業者で完結し、初期設定の手数が減る |
| 4 | 退職者のアカウント停止が Workspace 側の操作だけで反映される |

**運用上の前提**

| # | 内容 |
|---|---|
| 1 | テナント管理者に対し、Workspace 側で 2 段階認証を必須にすることを導入時に確認する |
| 2 | Google アカウントが使えない状況ではログインできない。これは受け入れる前提とする。**ただしローカルの形の機械には、機械の管理だけに使う「機械の管理者」を 1 人置く**（ID・合言葉・認証アプリの確認コード。業務の画面には入れない。第8.6.3節、第 0.374.0 版） |
| 3 | 管理者が 1 名しかいない状態を避けるため、管理者は 2 名以上の登録を推奨する |

#### 16.1.1 ログインに使う OAuth クライアント

**ログインと、Google のデータへのアクセスとで、OAuth クライアントを分ける。**

| 用途 | どのクライアントか | 求める権限 |
|---|---|---|
| **ログイン** | **運営のもの。全社で 1 つ** | `openid`・`email`・`profile` **だけ** |
| Google のデータ（メール・予定・ドライブ） | **会社のもの**。管理者ページの接続で登録する（第14.3.3節） | 使う業務が必要とする分だけ |

分ける理由は 2 つある。

| # | 理由 |
|---|---|
| 1 | **鶏と卵を避ける。** 会社の OAuth クライアントは管理者ページで登録する。そこへ入るにはログインが要る。ログインまで会社のクライアントに頼ると、最初の管理者が永久に入れない |
| 2 | **審査の重さが違う。** ログインが求めるのは基本の権限だけで、制限付きの権限を含まない。審査も CASA（第14.3.1節）も要らない。データへのアクセスと同じクライアントにすると、ログインまで審査に引きずられる |

**運営のクライアントが持つのは、誰がログインしたかを知るための権限だけである。**
メールも予定もドライブも読めない。会社のデータに触れるのは、会社のクライアントで得た許可だけである。

#### 16.1.2 ログインの経路

Google は、リダイレクト URI に **HTTPS を要求する**（例外は `localhost`）。
そのため**テナントごとのホストを、そのままリダイレクト先にはできない**。
開発の `http://<サブドメイン>.lvh.me` は、`localhost` ではないうえ HTTP であり、登録できない。

また、ログイン状態の Cookie は `Domain` を付けない（第20.7節）。
**受け取ったホストでしか有効にならない。**

この 2 つから、次の経路とする。

| 順 | 起きること | どのホストか |
|---|---|---|
| 1 | 利用者が「Google でログイン」を押す | 会社のホスト |
| 2 | どの会社かを `state` に入れて、Google の同意画面へ送る | 会社のホスト |
| 3 | Google が戻す | **運営のホスト 1 つ**（開発は `localhost`） |
| 4 | メールアドレスを取り、`state` の会社と照合する（下記） | 運営のホスト |
| 5 | **1 回限りの短命な引換券**を発行し、会社のホストへ戻す | 運営のホスト |
| 6 | 画面が引換券を差し出し、**そのホストで** Cookie を受け取る | 会社のホスト |

**リダイレクト URI を運営のホスト 1 本にできる。**
テナントが増えても、Google 側の設定を足す必要がない。

| 項目 | 規定 |
|---|---|
| 引換券 | **1 回だけ使える。** 使ったら消す。有効期間は 2 分 |
| 引換券に入れるもの | 会社と利用者の ID だけ。**利用者の名前もメールアドレスも入れない**（URL に個人の情報を載せない） |
| 戻す先 | **会社のホストだけ**。要求の `Origin` は、ホストが要求の Host と同じときだけ使う。会社のサブドメインは `<サブドメイン>.<BASE_DOMAIN>` の形のときだけ受ける（第 0.344.0 版。2026-10-12 の点検で、戻す先を外のサイトにされ引換券を盗まれる穴が見つかったため） |
| 始めたブラウザとの結び付け | 順 1 で、ブラウザに印（`m2o_login_browser`。HttpOnly）を置き、引換券は同じ印を持つブラウザでしか使えない。ほかの人が作ったログインの URL を開かされても、引換券を盗ませない（第 0.344.0 版） |
| メールアドレスの確認 | Google が確かめていない（`email_verified` が偽の）メールアドレスでは入れない（第 0.344.0 版） |
| 照合 | メールアドレスのドメインが会社の Workspace のドメインと一致し、**かつその会社の利用者として登録されている**こと。どちらか一方でも欠ければ拒否する |
| 停止された利用者 | 拒否する |
| 失敗したとき | 会社のログイン画面へ戻し、理由を平易に示す。**どこまで合っていたかは示さない**（登録の有無を外から測らせない） |
| 記録 | 監査ログ `auth.login`（成功）と `auth.login.denied`（拒否。理由つき） |

#### 16.1.3 テナントの作成

セルフサインアップは Phase 3（Q-17）、マスター管理画面は第23章であり、どちらも未実装である。
**それまでの間、テナントの作成は運営の手元のツール（CLI）で行う。**

| 項目 | 規定 |
|---|---|
| 作るもの | 会社（サブドメイン・名前・Workspace のドメイン）と、**最初の管理者 1 名** |
| サブドメイン | 第20.4.3節の規則と予約語を守る。作る前に検査する |
| 最初の管理者 | メールアドレスは Workspace のドメインに属すること。ロールは `admin`・`approver`・`member` |

| 記録 | 監査ログに残す |

### 16.3 権限区画

**この節で決めること**: 機微性の高いデータを、どう他から隔てるか。

#### 16.3.1 導入の理由

ロールと権限（第16.2節）だけでは足りない領域がある。
人事・労務が扱う給与額、評価、家族構成、健康診断の結果は、
他の業務データと同じ扱いにできない。特に健康に関する情報は
個人情報保護法の**要配慮個人情報**にあたる。

問題は、現在の設計が次の 2 つを許してしまう点にある。

| # | 問題 |
|---|---|
| 1 | 秘書は本人の権限内なら参照できる（不変則 I-9）。**人事担当者の秘書は全従業員の給与・評価を参照できてしまう** |
| 2 | 第11章の昇華をそのまま適用すると、**機微情報が全社の組織知識へ上がりうる** |

#### 16.3.2 権限区画とは

**権限区画（コンパートメント）は、データ・エージェント・知識をまとめて隔てる単位である。**

| 性質 | 内容 |
|---|---|
| 明示的な割当 | 区画に入れるのは、管理者が割り当てた**グループの所属者**と、個別に割り当てた者だけ（第16.7.5節、Q-76） |
| 既定は区画外 | ロールを持つだけでは入れない。職務として必要な者に限る |
| 流出しない | 区画内のデータは、区画外の知識・記憶・検索結果に現れない |
| 全件記録 | 区画内のデータへのアクセスは、**参照だけでも監査ログに残す** |

**HR を特別扱いするのではなく、区画という一般の仕組みを導入する。**
HR はその最初の適用例である。
将来、法務（係争案件）や経営（M&A、人事異動の検討）にも同じ仕組みを使える。

#### 16.3.3 HR 区画の範囲

| 区画に含む | 区画に含まない |
|---|---|
| 給与額、賞与、手当 | 就業規則・労務規程（全社に公開してよい） |
| 人事評価、面談記録 | 全社の集計値（総残業時間、有給取得率など個人が特定されないもの） |
| 家族構成、扶養情報 | 組織図、連絡先、所属 |
| 健康診断の結果、休職の記録 | 会議の出欠 |
| 勤怠・休暇・給与の明細・扶養・口座（第30章。第 0.154.0 版） | 勤怠と休暇の本人の分（本人参照で見られる） |
| **マイナンバー**は、人事区画とは別の**マイナンバーの区画**に置く（事務取扱担当者だけ。第30.22節） | |
| 勤怠の個人別明細 | 社内の福利厚生の案内 |
| 応募者の情報、面接の評価 | 求人原稿（公開する内容） |

**区画に含めるかどうかの基準**: その情報が漏れたとき、
本人の不利益になるか、社内の人間関係に影響するか。

#### 16.3.4 アクセスの 2 種類

**同じデータでも、誰がどの立場で見るかで扱いを分ける。**

| 種類 | 内容 | 秘書経由 | 記録 |
|---|---|---|---|
| **本人参照** | 自分に関するデータを本人が見る（自分の給与明細、自分の有給残日数） | **可** | 通常の監査ログ |
| **職務参照** | 他者のデータを職務として見る（人事担当者が全員分を確認する） | **不可** | **参照だけでも全件記録** |

この区別により、次が成立する。

- 従業員が秘書に「有給あと何日？」と聞くのは、本人参照なので問題なく答えられる。
- 人事担当者が秘書に「全員の残業時間を出して」と頼むことはできない。
  専用のエージェント（AG-11 ほか）から、記録が残る形で実行する。

**秘書は職務参照の経路にしない。** 秘書は常駐し文脈を保持するため、
機微情報が会話の流れに残りやすい。区画内の職務参照は、
目的が明確な業務エージェントに限定する。

#### 16.3.5 記憶と知識への制限

| 対象 | 扱い |
|---|---|
| 個人記憶（第11.1節） | **区画内のデータを残さない。** 本人参照で得た内容も記憶しない |
| チーム記憶 | 同上 |
| 組織知識（第11.1節） | **区画からの昇華を行わない**（第11.3節の経路を通さない） |
| 会話ログ（第11.9節） | 記録するが、区画の印を付け、学習の対象から除外する |
| 検索 | 区画外からの検索では、区画内の文書を候補にも出さない |

**「見つからない」と「権限がない」を区別しない。**
区画外の利用者に対しては、該当する情報の**存在そのものを示さない**。
「権限がありません」と返すと、情報の存在が推測できてしまう。

#### 16.3.6 エージェントとツールの扱い

| 項目 | 規定 |
|---|---|
| エージェント定義 | 区画に属するエージェントは、定義に区画を宣言する |
| 実行者 | 区画に割り当てられた者しか実行できない。実行を進めるたびに（承認の後の再開を含む）依頼した人が区画に入っているかを確かめ直し、外れていれば実行を止める |
| 承認と閲覧 | 区画に属する業務の承認を判断できるのも、その実行の中身を見られるのも、区画に入っている者だけ（第9.2.3節・第6.2.3節。第 0.366.0 版） |
| ツール | 区画内のデータに触れるツールは、区画属性を持つ |
| 混在の禁止 | 1 つの実行の中で、区画内のデータを区画外の成果物へ書き出さない |
| 拡張機能 | 第三者の拡張機能を区画に入れる場合、審査の対象に加える（第12.5節） |

#### 16.3.6.1 区画の無効化と削除（第 0.62.0 版）

区画は、使わなくなったときに**無効にする**か、**削除する**ことができる。管理者だけが行う。

| 操作 | 規定 |
|---|---|
| 無効にする | 区画は残したまま、**その間は誰も区画に入れない**。割当の設定は消さず、有効に戻すと元の割当が効く |
| 無効の間の見え方 | 区画に属する知識・業務は、**誰にも見えない・実行できない**。区画の縛りが外れて全社に見えることはない（外す側に倒さない） |
| 無効の間の割当 | 入れるグループと人の変更はできない。先に有効へ戻す |
| 削除する | **その区画に属する知識・業務が 1 つでも残っていれば断る**。何がどれだけ残っているかを示し、先に消すか区画外へ移してもらう |
| 削除でできること | 残っていなければ、区画と割当をまとめて消す。監査ログは残る（第16.6節） |
| 記録 | 監査ログ `compartment.disable`・`compartment.enable`・`compartment.delete`。区画の出入りが変わるため、管理者へも知らせる（第16.7.5節） |

**「誰にも見えない」に倒す理由**は、区画の目的が隔離だからである。
無効にした拍子に機微な情報が全社に出るくらいなら、一時的に誰も見られないほうが害が小さい。

#### 16.3.7 LLM への送信

| 項目 | 方針 |
|---|---|
| 送信範囲 | 区画内のデータを送る場合、処理に必要な最小限に絞る |
| 識別子 | 氏名を識別子に置き換えられる処理では置き換える |
| 健康情報 | TBD: 送信の可否と範囲を個別に定める（Q-47）。ローカルの形の会社では、外部の AI に渡さない決まり（第16.3.7.1節）で守る。**顧客の手元のシステムが持つ、その会社の顧客などの健康情報は、M2Office に入れない**（第 0.150.0 版で決定。個人が分からない集計だけを受け取る。第12.11.7節、ADR-0046） |
| 記録 | 何を送ったかを監査ログに残す |

#### 16.3.7.1 外部の AI に渡さない決まり（第 0.209.0 版、ADR-0059。第 0.209.0 版で実装）

**顧客の個人の情報を取り込んだら、それを外部の AI に渡さない。** 決まりで防ぐのではなく、仕組みで防ぐ。
**医療機関の患者の情報は、M2Office に入れない**（第 0.220.0 版、ADR-0063。患者の情報を扱う業務は別のシステム「M2Medical」で扱い、M2Office が受け取るのは抽象的な属性と集計だけ）。
2026-10-01 に三浦さんが「M2Office で患者情報を取り込んだときに、それを外部の AI などに食わせることを止める配慮が必要」と決めた。

| 項目 | 規定 |
|---|---|
| 会社の AI の方針 | 3 つから選ぶ。**クラウド**（いまの形。Gemini を使う）・**ローカルを既定**（ローカル LLM を既定にし、外部の AI は使ってよいと決めた業務だけ）・**ローカルだけ**（外部の AI を使わない）。ローカルを既定とローカルだけは、ローカルの形（第8.6節）でだけ選べる（クラウドの形からは社内のローカル LLM に届かないため） |
| 既定がローカルのもの | 秘書（会話・調べもの・記憶・学び）、渡されたファイルを読む業務（**録音は社内の AI で文字にできないため、ローカルの方針の会社では受け取らない**。第9.4.5節。第 0.369.0 版）、会社のデータ（名刺・人事・在庫・接続の答えなど）を読む業務、印の無い業務のすべて。**迷うものはローカル**にする |
| 外部の AI を使ってよい業務 | 業務の定義に「外部の AI を使ってよい」印を付けたものだけ（例: SNS の投稿・HP のコラム・広告の文案・Web の調べもの）。管理者は業務ごとに外せる |
| 印を付けられる条件 | **会社のデータを読むツールを持たない**こと。渡されたファイルの欄を持たないこと。印のある業務の定義を読み込むときに確かめ、満たさなければ印を無効にしてローカルで動かす |
| 秘書から頼むとき | 秘書（ローカル）が、印のある業務に渡す依頼の文から、個人を特定する情報を除いてから渡す（氏名・番号・生年月日・連絡先など） |
| Web の調べもの | 検索の言葉は外部（Google）に出る。ローカルを既定の会社では、検索の言葉をローカル LLM が作り、個人を特定する情報と社内の情報を入れない（第10.11.4節の決まりを、推論の置き場所でも守る） |
| 外部のサービスへの接続 | 接続（MCP）の相手も社外である。ローカルを既定・ローカルだけの会社では、接続ごとに「個人を特定する情報を除いてから送ってよい」か「送らない」かを管理者が決める。既定は送らない。医療の専門のサービス（EvidenceMD など）に匿名にした臨床の質問を送ってよいかは、会社の方針で決める（Q-158） |
| 途中で切り替えない | 1 つの実行の中で、外部に出してはならないデータを読んだ後に外部の AI へ切り替えることはしない。実行の始まりに使う AI を決め、最後まで変えない |
| 記録 | 実行ごとに、どの AI（ローカル・外部）を使ったかを実行の記録と監査ログに残す |
| 管理者の画面 | ローカルの形の会社だけ、「接続 › Gemini」に「AI の方針」（ローカルを既定・ローカルだけ・クラウド）と、ローカル AI に届くかの確かめを出す。ローカルの方針の会社だけ、コネクタごとに「この接続（社外）に送るもの」（送らない・個人を特定する情報を除いて送る）を出す。**業務ごとに外部の AI を外す画面は後の段** |
| ローカル LLM | 社内の機械で、外向きに口を開けない形で動かす（OpenAI 互換の口を持つものなど。設定は `LOCAL_LLM_URL`・`LOCAL_LLM_MODEL`）。画像を読めるモデルなら画像の読み取り（名刺など）にも使う。PDF は読めない。M2Office とは別のプロセスとして動かし、M2Office の中で他社のプログラムを動かさない（不変則 I-7）。使うモデルと、要る機械の性能は未決（Q-159） |

#### 16.3.8 実装上の含意

| # | 含意 |
|---|---|
| 1 | データに区画の属性を持たせる。文書・知識・記憶・会話ログのすべてが対象 |
| 2 | 検索とツール呼び出しに、区画による絞り込みを既定で適用する |
| 3 | 利用者と区画の割当を保持する |
| 4 | 区画内データへの参照を監査ログに記録する経路を用意する |

**第 1 項は Phase 1 から用意する。**
区画の属性を持たずに運用を始めると、後から機微情報と一般情報を分離することはできない。
個人記憶と組織知識を最初から分ける（第24.2節）のと同じ理由である。

### 16.4 エージェントの行動制約

| 区分 | 扱い |
|---|---|
| 実装しない | 送金・決済の実行、データの完全削除、認証情報の代理入力 |
| 必ず承認 | 対外送信、外部共有、会計データの確定、設定変更 |
| 承認不要 | 読取、下書き作成、社内向け要約、検索 |

**プロンプトインジェクション対策**: メール本文、外部文書、MCP サーバの応答、
第三者が提供したエージェント定義に含まれる指示文は、基盤の制約を上書きできない。
危険度による承認強制（第9.4節）は基盤側で判定する。

**音声経由でも同じ**（不変則 I-11、第10.6節）。

### 16.5 データ保護とプライバシー

| 項目 | 方針 |
|---|---|
| 通信 | TLS 必須。ワイルドカード証明書で全サブドメインを保護 |
| 保管 | 保存時暗号化。認証情報は専用のシークレット管理で別途保護 |
| テナント分離 | 単一データベース＋行レベルセキュリティ（RLS） |
| 個人記憶の分離 | 同一テナント内でも他者の個人記憶を参照できない |
| 個人情報 | 取得・利用目的を明示。委託先（LLM 提供者等）を公開 |
| モデルの学習 | 顧客データを LLM の重みの更新に用いない。外部提供者にも行わせない（第11.9.3節） |
| システムの蓄積 | テナント内にデータを蓄積し、応答の改善に用いる。**これは製品の中核機能である** |
| テナントを越える利用 | 既定では行わない。個別に同意を得た場合に限る |
| 拡張機能への露出 | 宣言・同意された範囲のデータにしか触れられない |
| LLM への送信範囲 | 必要最小限。TBD: マスキングの要否と対象項目 |
| 音声データ | 録音は破棄し、文字は会話ログに残す（Q-19） |
| 運営のアクセス | 顧客データに触れる場合は事前承諾と記録を必須とする |

調査で「情報漏洩のリスク」が懸念の 33.5% を占めることから、
**これらの方針を製品ページと管理者画面で平易に説明する**ことを要件とする。

### 16.6 監査

| 項目 | 内容 |
|---|---|
| 記録対象 | ログイン、権限変更、連携設定、拡張導入、全ステップ実行、承認判断、知識の昇華、API 呼び出し、不正の兆し（第16.8節） |
| 記録内容 | 主体（人・秘書・アプリ）、日時、対象、操作、根拠、結果 |
| 改変防止 | 追記のみ。削除・更新は不可 |
| 提出 | 期間・主体・操作の種類で検索し CSV 出力できる。画面と CSV は人の名前と業務の言葉で出す（第6.6.8.1節） |

誰の指示で何が行われたかが残ることが組織利用の前提になる。

### 16.7 グループと利用範囲

**この節で決めること**: 利用者をグループにまとめ、業務ごとに「誰が使えるか」（利用範囲）を決める方法。

#### 16.7.1 導入の理由

拡張機能で業務を足していくと、**全員が使う業務**と**一部の人だけが使う業務**が混ざる。

| 業務の例 | 使う人 |
|---|---|
| 社内ナレッジ Q&A、週次ブリーフ | 全員 |
| ローカル AI の市場調査を資料（PowerPoint）にまとめる | マーケティングと、経営層 |
| リポジトリの調査 | 開発部門と、特定の数名 |
| 採用・労務の業務 | 人事部だけ |

全員のメニューに全業務を並べると、使わない業務で画面が埋まり、使うべきでない人が起動できてしまう。
**これまでに作った仕組み（実行・承認・記録・拡張機能）は全社の共通基盤とし、その上に「誰が使えるか」を重ねる。**

#### 16.7.2 グループ

**グループは、利用者の組織上のまとまりである**（部署・役職・プロジェクトなど）。

| 性質 | 内容 |
|---|---|
| 作る人 | 会社の管理者 |
| 属性 | 名前（会社の中で重ならない）、説明 |
| 所属 | 1 人が複数のグループに入れる（例: 「開発」と「管理職」） |
| 範囲 | 会社（テナント）の中だけ。他の会社のグループとは無関係（不変則 I-2） |
| 例 | 管理職、マーケティング、開発、営業、人事 |
| 削除 | グループを消しても、利用者は消えない。利用範囲からそのグループが外れる。その結果、範囲に誰も残らない業務は**全員に戻さず誰も使えないままにし**、画面で知らせる（開く方向に倒さない） |

#### 16.7.3 利用範囲

**利用範囲は、業務を使える人の範囲である。** 業務の単位ごとに設定する。

| 対象 | 単位 |
|---|---|
| 公式の業務エージェント | 業務エージェントごと |
| 拡張機能 | **拡張機能ごと**（その拡張機能の業務エージェントすべてに同じ範囲が効く） |

| 範囲の指定 | 使える人 |
|---|---|
| **全員**（既定） | その会社の利用者全員 |
| **指定** | 指定したグループのいずれかに所属する人 **または** 個別に指定した人 |

「開発部門プラス誰か」は、グループ「開発」と個人「〇〇さん」を指定して表す。
指定を選んで、グループも人も 1 つも選ばない設定は保存できない（誰も使えない業務は「無効」（第6.6.5節）で表す）。

#### 16.7.4 範囲の外の人にとっての扱い

**範囲の外の人には、その業務は無いものとして扱う。**

| 経路 | 扱い |
|---|---|
| ワークスペースのメニュー | 出さない |
| 秘書の取次 | 取り次がない。秘書は範囲の外の業務を候補にしない |
| 定時実行 | 新しく作れない。範囲から外れた人の定時実行は、その回を起動せず記録を残す |
| API | 業務の一覧に出さない。起動の要求は「見つからない」（404）とする |
| ヘルプ | 業務の説明を出さない |
| 実行の途中 | ワーカーが実行を進める時点でも依頼者が範囲の中かを確かめ、外なら実行を止める |

**範囲の外の人にも、過去の自分の実行の記録と成果物は見せる。** 範囲は「これから使えるか」を決めるものであり、
すでに行った実行を消すものではない。
承認は、利用範囲ではなく承認の指定（第9.2.3節）に従う。範囲の外の承認者も、割り当てられた承認は判断できる。

#### 16.7.5 ロール・権限区画との関係

| 仕組み | 決めること | 例 |
|---|---|---|
| ロール（第16.2節） | 画面と操作の権限（管理・承認） | 管理者、承認者、一般 |
| **利用範囲（この節）** | **どの業務を使えるか** | 「市場調査」はマーケティングだけ |
| 権限区画（第16.3節） | **機微なデータ**を隔てる。参照も全件記録する | HR 区画の給与・評価 |

**利用範囲は権限区画の代わりにならない。** 利用範囲は業務の入口を絞るだけで、データを隔てない。
機微なデータを扱う業務は、権限区画に入れたうえで、利用範囲も区画の割当と揃える。
区画に属する業務エージェントは、利用範囲の中**かつ**区画に割り当てられた人だけが実行できる。

**人の割当は、すべてグループで行う（決定、Q-76）。** 利用範囲も権限区画も、「グループと、個別に指定した人」という
同じ形で割り当てる。特別な割当の仕組みを別に作らない。
例: 人事区画には「人事」グループと社長個人を、法務区画には「法務」と「管理職」を割り当てる。

区画の性質（区画外へ流出しない、参照も全件記録する。第16.3.2節）は変わらない。変わるのは「誰が入れるか」の指定の方法だけである。
グループに人を足すと区画に入れてしまうため、区画に割り当てたグループには次を守る。

| # | 規定 |
|---|---|
| 1 | 区画に割り当てたグループの所属の変更は、監査ログに**区画への出入り**としても記録する |
| 2 | そのとき、会社の管理者全員に通知する（誰が、どの区画に、入った・出たか） |
| 3 | グループの管理（作成・所属の変更）は M2Office の管理者だけが行う。グループごとの管理者は置かない |
| 4 | 管理者ページで、グループがどの区画・どの業務に割り当てられているかを示す。所属を変える前に影響が分かるようにする |

#### 16.7.6 管理者の扱い

**管理者も、業務を使う場面では利用範囲に従う**（最小権限。決定、Q-74）。
管理者ページでは、範囲に関係なくすべての業務と拡張機能を見て設定できる。
管理者が範囲の外の業務を試すには、自分を範囲に加える。

#### 16.7.7 画面

| 画面 | 内容 |
|---|---|
| 管理者ページ「ユーザーと権限」 | グループの作成・名前の変更・削除と、所属する人の割当。利用者ごとに所属するグループを示す |
| 管理者ページ「業務と承認」 | 公式の業務エージェントごとに「利用できる人」（全員／指定）を設定する |
| 管理者ページ「拡張機能」 | 導入の同意の画面で「利用できる人」を選ぶ（既定は全員）。導入後はカードに範囲を示し、変更できる |
| 個人設定「利用状況」 | 本人が所属するグループを示す |

範囲を示すときは「全員」「開発・マーケティング、ほか 2 人」のように短く書く。

**選び方（第 0.315.0 版）**: 範囲を示すボタンを押すと一覧が開き、「全員」・グループ・人を、その場で付け外しする。**付け外しのたびにすぐ保存する**（保存・キャンセルのボタンを置かない）。「全員」の状態でグループか人を選ぶとその人たちだけになり、「全員」を押すと全員に戻る。誰も使えない状態にはしない（最後の 1 つは外せない）。下に場所が無ければ、一覧は上に開く

#### 16.7.8 記録

| 操作 | 監査ログ |
|---|---|
| グループの作成・変更・削除 | `group.create`・`group.update`・`group.delete` |
| 所属の変更 | `group.members`（追加・削除した人） |
| 利用範囲の変更 | `settings.update`（区分 `access`） |
| 範囲の外で実行を止めた | `run.fail`（理由に「利用範囲の外」） |

#### 16.7.9 保存

| 対象 | 保存先 |
|---|---|
| グループ | `user_groups`（テナントごと。RLS） |
| 所属 | `user_group_members`（テナントごと。RLS） |
| 利用範囲 | 会社の設定の区分 `access`（`tenant_settings.access`）。対象（公式の業務エージェントの ID か拡張機能の ID）ごとに、グループと人の一覧を持つ。対象が無いものは全員 |

拡張機能を削除すると、その利用範囲の設定も消す。

|---|---|

| 検討中 | Google Workspace のグループとの関係（第16.7.11節、Q-75 保留） |

#### 16.7.11 Google Workspace のグループとの関係（検討中）

**結論は保留する（Q-75）。** ここでは判断の材料を残す。

**M2Office で別に管理した場合に起きること**

| # | 起きること | 重さ | 補足 |
|---|---|---|---|
| 1 | 異動のたびに、Workspace と M2Office の両方を直す必要がある | 中 | 10 名規模では管理者 1 人が両方を行うため、手間は小さい |
| 2 | **異動の反映漏れ**。異動した人が、元の部署の業務・区画を使い続ける | **高** | 最も重い問題。区画の出入りの通知（第16.7.5節）と、定期的な棚卸しで補う |
| 3 | 退職者 | 低 | ログインは Google アカウントで行うため、Workspace で停止すれば M2Office にも入れない |
| 4 | グループの名前や構成が、Workspace とずれる | 低 | 利用者が混乱する程度 |

**Workspace のグループと同期した場合に起きること**

| # | 起きること | 重さ | 補足 |
|---|---|---|---|
| 1 | **管理する人が違う**。Workspace ではグループのオーナー・管理者に一般の社員がなれる。その人が所属を変えると、M2Office の区画に人を入れられてしまう | **高** | 権限を広げる経路になる。「管理者が違うと厄介」の中身はこれ |
| 2 | Workspace のグループは、多くが**メールの配信用**に作られている。社外のアドレス、グループの入れ子、「全員」のような広いものが混ざる | **高** | そのまま権限に使うと、意図しない人が入る |
| 3 | 読み取りに Workspace の管理者の同意（Directory API の権限）が要る | 中 | Google 連携の準備（B-2）と審査に影響する |
| 4 | 同期のずれ・Google の障害 | 中 | 取得できないときの扱い（直前の状態を保つか、使えなくするか）を決める必要がある |
| 5 | 異動が自動で反映される | 利点 | 別管理の問題 2 が解消する |

**考えられる形**

| 案 | 内容 | 向いている会社 |
|---|---|---|
| A | M2Office で別に管理する（いまの実装） | 10 名規模。管理者が 1 人 |
| B | Workspace のグループをそのまま使う（完全な同期） | 権限用のグループを Workspace で厳密に運用している会社 |
| C | **M2Office のグループを正とし、Workspace のグループから所属を一方向に取り込む**。取り込むグループは管理者が選ぶ。区画に割り当てたグループは取り込みの対象にしない（または取り込んだ変更を管理者の承認制にする） | A の手間と、B の危うさの間 |

いまは A で運用し、Google 連携（B-2）が整った段階で C を検討する。

#### 16.7.12 Google Chat のスペースとの関係（Q-87。第 0.294.0 版で整理の案を書き、第 0.295.0 版で確定して実装した）

**M2Office のグループと、Google Chat のスペースは、つながっていない別々のものである。**
議事録の作成などの共有先に指定するのは Chat のスペースの名前（第14.3.4節「Chat」）であり、M2Office のグループではない。

| | M2Office のグループ | Google Chat のスペース |
|---|---|---|
| 決めること | 誰がどの業務を使えるか（利用範囲）、誰が権限区画に入れるか | 投稿がどこへ届き、誰が読めるか |
| 管理する人 | M2Office の管理者だけ | スペースの管理者（一般の社員もなれる） |
| M2Office での使い道 | メニューの出し分け、区画の出入り | 共有の投稿先としてだけ |

**起きていること**（2026-09-25 に三浦さんが提起）

| # | 事象 |
|---|---|
| 1 | 同じ「技術部」という名前でも、片方を変えても他方に効かない |
| 2 | M2Office の「技術部」グループに入っていても、Chat の「技術部」スペースに入っていなければ、共有先として見つからない |
| 3 | 共有の投稿は、M2Office のグループと関係なく、**Chat のスペースのメンバー全員**に届く。M2Office は投稿先のメンバーを確かめていない |
| 4 | 三浦さんも利用者も「グループで部署ごとに共有先をまとめられる」と思っていた |

**どう整理するかは、別の議題として後で扱う**（Q-87）。Workspace のグループとの関係（第16.7.11節、Q-75）と合わせて考える。
それまでは、結び付けの仕組みを作らない。

##### 16.7.12.1 グループを共有先に使える（第 0.294.0 版で案、第 0.295.0 版で確定して実装。ADR-0076）

2026-10-07 に三浦さんが「次に進んでください」で、この議題の整理を選び、方向を「**グループを共有先に使えるように**」と決めた
（ほかの案: M2Office がスペースを作って所属を合わせる・Google のグループを正にする・つながず言葉と見せ方だけ直す）。
**グループとスペースは別のものとして残し、共有を頼むときにグループの名前で頼めるようにする。** 届く先と、グループとの違いを承認の画面で見せる。

| 項目 | 規定（案） |
|---|---|
| 頼み方 | 「技術部に共有して」の「技術部」は、まず **Chat のスペースの名前**として探す（いまと同じ）。見つからなければ **M2Office のグループの名前**として扱い、そのグループに合う Chat のスペースを、依頼した人が入っているスペースの中から探す |
| 合わせ方 | 名前が同じ・ゆれ（「技術部」と「技術部（全体）」「技術チーム」）はプログラムで合わせ、それで決まらなければメンバーの重なりから選ぶ。**1 つに決まればそこへ**。決まらなければ候補を挙げて止める（承認に進まない。Q-203） |
| 対応表を作らせない | 人にグループとスペースの対応表を作らせない（ADR-0028）。秘書が見つけた組み合わせは会社で共有して覚え、次から使う。違えば会話で直す（「技術部の共有は〇〇のスペースにして」。Q-204） |
| 承認の画面 | 届く先のスペースの名前、**メンバーの数**、社外の人の数を出す。グループの名前で頼んだときは、**グループとスペースのメンバーの違い**を出す（「グループにいて、スペースにいない人（読めない）」「スペースにいて、グループにいない人（届く）」）。違いがあっても止めない。決めるのは承認する人（Q-203） |
| メンバーの照らし方 | Chat のメンバーは Google のアカウントの番号（`users/<番号>`）で返り、メールアドレスは返らない見込み。本人が Google と接続したときのアカウントの番号（OpenID の `sub`）と照らして M2Office の利用者に結び付ける。会社の外の人は、Workspace の番号（`domainId`）が会社と違う人とする。照らせない人は「確かめられない人」として数える。**実装の前に本物の Chat API で確かめる** |
| 社外 | いまと同じく、社外の人が入れるスペースは承認の後（分からなければ社外。第9.4.0節）。加えて、**メンバーに会社の外のアドレスの人がいれば社外**とする（いまより厳しくなる方向） |
| 管理者ページのグループ | グループごとに、合う Chat のスペースと、メンバーの違いの数を出す（見るだけ。直すのは Chat の側か会話）。合うスペースが無いグループは「Chat のスペースなし」 |
| スペースが無いとき | **M2Office はスペースを作らない**（作る権限を求めない。Q-205）。「技術部に合う Chat のスペースが見つかりません。Chat でスペースを作るか、スペースの名前で頼んでください」と答える |
| 権限 | Chat のメンバーを見る `chat.memberships.readonly`（Google の区分は sensitive）を足す。**共有を使う業務を使う人に、Google の再同意が要る**（リリース規定 第3.1節で MAJOR の扱い。`0.x` では MINOR を上げる運用か三浦さんに確かめる） |
| 変えないもの | M2Office のグループの役目（業務の利用範囲・権限区画）は変えない。Workspace のグループ（第16.7.11節、Q-75）は保留のまま |
| 実装（第 0.295.0 版） | 覚えた組み合わせはグループの記録（`user_groups.chat_space`。移行 104）に持つ（会社の知識の検索には混ぜない）。メンバーの重なりはプログラムが数える（グループの人のうち入っている割合が 6 割以上で、ほかより大きいもの。比べるスペースは 15 まで）。名前は全角と半角・括弧の中・「チーム」「グループ」などの言い添えを除いて比べる。メンバーの照らし方は、Chat API の `spaces.members.get` がメールアドレスを使えるため、グループの人の Google アカウント（接続していればそのアカウント、無ければ M2Office のメールアドレス）で 1 人ずつ確かめる（Google のアカウントの番号は持たない）。会社の外の人は本人と Workspace の番号（`domainId`）が違う人。Google のグループがメンバーに入っていれば中の人を数えられないため、社内だけとは言わない。すべての Chat の投稿で、社外の人が入れないスペースでも、メンバーを確かめて会社の外の人と Google のグループがいないと分かったときだけ社内とする。秘書は「技術部の共有は〇〇のスペースにして」「技術部の共有先を忘れて」で覚え直す（そのグループの人と管理者。監査ログ `group.chat_space`）。管理者ページのグループに「Chat のスペース」と「確かめる」（`GET /v1/admin/groups/:id/chat-space`） |
| 言葉 | 画面と秘書は「グループ」（M2Office の）と「Chat のスペース」を言い分ける。グループの画面に、共有はグループの名前で頼めることを、説明文ではなく合うスペースの表示で示す（原則 u11） |

#### 16.8.3 知らせと、防ぐ動き

| 項目 | 規定 |
|---|---|
| 受け取る人 | 利用中の管理者全員。**兆しの本人が管理者なら、その人を除いた管理者にも必ず届く**（乗っ取られた管理者のアカウントで知らせを握りつぶせないように）。管理者が本人だけの会社では本人に届ける |
| 本人への知らせ | 新しい端末でのログイン（兆し 5）は、本人のお知らせに届ける。覚えが無ければ、個人設定の「ログイン中の端末」でその端末をログアウトする（第6.5.8節） |
| 届け方 | 種類「セキュリティ」のお知らせ（本人が切れない）。重さ高は見つけたらすぐ（5 分ごとの見回り）、中は同じ型を 1 時間にまとめる。毎朝、前日の件数を 1 通にまとめる |
| 知らせの中身 | 何が・いつ・誰に起きたか、考えられること（乗っ取り・持ち出しなど）、勧める対応（「この人の端末をすべてログアウト」「アカウントを止める」）。業務の中身・開いた記録の中身・場所は入れない |
| 秘書での対応 | 管理者が秘書に「セキュリティの知らせは？」と聞ける。「〇〇さんの端末をすべてログアウトして」「これは大丈夫」で対応する（管理者だけ。どれも監査ログに残す）。アカウントを止めるのは、業務の中断と名刺の整理が連動する重い操作のため、管理者ページの「ユーザーと権限」で行い、秘書はそこへ案内する |
| 自動で防ぐこと | **既定は知らせるだけ。同じ人に 1 時間のうちに、まとまりの違う重さ高が 2 つ重なったとき（深夜の管理者の追加と大量の書き出しなど）だけ、その人の端末を自動ですべてログアウトする**（Q-218 で決定）。まとまりは、持ち出し（書き出し・一斉メール）・ログイン・権限・端末の 4 つ。1 つの行動から出た兆し（大きな書き出しと書き出しが続いた、など）は二重に数えない。アカウントは止めない（止めるのは管理者が決める）。ログアウトさせたことを管理者に知らせ、監査ログ `security.auto_signout` に残す |
| ログインの一時の締め出し | **同じアドレスの拒否が 10 分に 5 回に達したら、そのアドレスのログインを 30 分受けない**（Q-219 で決定）。締め出したことは監査ログ `auth.login.locked` に残す。締め出している間の試みも拒否として数える |
| 記録 | 見つけた兆しは監査ログ `security.signal`（兆しの型・重さ・対象の人・件数。中身は入れない）。監査ログの画面の種類に「セキュリティ」を足す |
| 画面 | 新しい画面は作らない。お知らせ・秘書・監査ログで扱う（原則 u11）。見張りが動いていることと兆しの数は、ダッシュボードの「業務の状態」に出す（第6.7.4.2.2節。第 0.333.0 版） |

#### 16.8.6 Google Workspace のログインの記録の取り込み（段 3。第 0.335.0 版で案、第 0.336.0 版で決定。ADR-0092）

2026-10-11 に三浦さんが、**Google Workspace のログインの記録（ログイン監査）も見張りに取り込む**ことを求めた（実装の時期は別に決める）。M2Office へのログインは Google のアカウントで行うため、**Google のアカウントが乗っ取られれば M2Office にも入られる**。段 1・段 2 の見張りは M2Office の中の記録しか見ないため、Google の側で起きた異変を取り込み、M2Office の中の兆しと重ねて判断する。2026-10-12 に三浦さんが、Q-222〜Q-226 を案のとおりに決めた。

##### 16.8.6.1 材料と読み方

Google の公式の文書（2026 年 10 月時点）で確かめた内容。

| 項目 | 規定 |
|---|---|
| 材料 | Admin SDK の Reports API のログインの記録（`activities.list`、`applicationName=login`。管理コンソールでは「ユーザーのログのイベント」。旧名「ログイン監査ログ」） |
| 権限 | `admin.reports.audit.readonly`（読み取りだけ）。許可できるのは、Google Workspace の特権管理者か、レポートを見る権限を持つ Google の管理者だけ。権限の段階（機密性の高い権限か）と、一般公開のときの審査（第14.3.1節）は TBD（実装の前に Google の文書で確かめる） |
| 誰の許可で読むか | **担当の管理者の Google の許可**で読む（Q-224）。Webの分析（第34章）と同じく、**本人の Google の接続とは別の許可**として預け、担当を替えると前の担当の許可では読まない。M2Office の管理者のうち Google の管理者である人が担当になる。担当がいなければ、秘書が「Google の管理者の人に接続してもらってください」と伝える（画面に説明を常に出さない。原則 u11） |
| 対象の会社 | Google Workspace を使い、会社のドメインでログインしている会社だけ。個人の Google アカウント（gmail.com）の会社では使えない |
| 読み方 | ワーカーが見張りの見回り（5 分ごと）で、前に読んだ時刻の続きから読む。Google への反映は数分の遅れ（Google の文書で「ほぼ即時」）があるため、読む範囲を 15 分重ね、同じ記録は Google の記録の番号で二重に数えない。Google から押して知らせる形（`activities.watch`）は使わない（受け口の公開が要り、ローカルの形（第8.6節）では受けられないため） |
| 持つ期間 | Google の記録そのものは M2Office に写さない。見つけた兆しだけを、ほかの兆しと同じく残す（`security_signals`）。Google は記録を 6 か月持つ |
| 読めないとき | 許可が切れた・担当が Google の管理者でなくなった・Google が答えない、は兆しにせず、ダッシュボードの見張りの囲み（第6.7.4.2.2節）に「Google のログイン: 読めていません」と出し、担当と管理者に 1 日 1 回まで知らせる。読めなかった間を推測で埋めない |

##### 16.8.6.2 取り込むできごと（Q-222）

**Google が「異変」と判断したものと、乗っ取りの後によく行われる操作だけ**を取り込む。ふだんのログインの成功・ログアウトは取り込まない（第6.7.10節。1 人ずつのログインの時刻を集めない）。

| できごと（Google の記録の名前） | M2Office での言い方 | 重さ |
|---|---|---|
| `account_disabled_hijacked` | Google が乗っ取りの疑いでアカウントを止めた | 高 |
| `account_disabled_password_leak` | パスワードが漏れたため、Google がアカウントを止めた | 高 |
| `login_success` のうち `is_suspicious` が真 | Google が不審と判断したログインが通った | 高 |
| `gov_attack_warning` | 政府の支援を受けた攻撃者に狙われている疑い | 高 |
| `email_forwarding_out_of_domain` | 社外へのメールの自動転送を入れた（持ち出しの手口） | 高 |
| `suspicious_login`・`suspicious_login_less_secure_app`・`suspicious_programmatic_login` | 不審なログインを Google が止めた | 中 |
| `user_signed_out_due_to_suspicious_session_cookie` | 盗まれた疑いのあるログイン状態を、Google がログアウトさせた | 中 |

### 16.10 システムログの保管・閲覧・証拠保全（第 0.370.0 版で案、第 0.371.0 版で確定して実装。ADR-0098）

2026-10-16 に三浦さんが、次の 4 つを求めた。

- ローカルの形（サブドメインを使わない）では、会社の管理者が管理者ページからシステムログを見て、ダウンロードできる。
- クラウドの形では、運営がマスター管理画面で、すべての会社（サブドメイン）のシステムログを見て、ダウンロードできる。
- ログのローテーション（入れ替え）ができていない問題を直す。
- サイバー攻撃などにあったときに、証拠を保全できる。

それまでのシステムログは、API とワーカーが標準出力へ書くだけだった。ローカルの形では launchd がファイルに書き足すだけで入れ替えず、
クラウドの形では置き場が決まっていなかった（開発規約 第7.6節）。

#### 16.10.1 置き方

**システムログを、アプリがデータベースにも書く。** 標準出力への書き出しは今までどおり続ける（データベースに書けないときの障害を追うため）。

| 項目 | 規定 |
|---|---|
| 置き場 | 表 `system_logs`（日ごとに区切った表。PostgreSQL の区切り）。1 行 1 件で、時刻・レベル・プロセス（`api`・`worker`・`ops`）・文・会社・利用者・要求 ID・実行 ID・項目（伏せ字の後の JSON） |
| なぜデータベースか | クラウドの形は API とワーカーが何台にもなりうる（第20.4.2節）ため、機械のファイルでは運営が全体を見られない。ローカルの形とクラウドの形で同じ作りにでき、会社・日時・レベルで絞れ、区切りごとに捨てるだけで入れ替えられる |
| 書く量 | `info` から上（本番の既定と同じ）。数秒ごとに読み直す要求のうまくいったものは、今までどおり書かない |
| 書き方 | まとめて 2 秒ごとに書く（1 件ずつ書いて要求を遅らせない）。データベースに書けないときは捨て、捨てた数を標準出力に書く（ログのためにアプリを止めない） |
| 書かないもの | 開発規約 第7.5節と同じ（認証情報・顧客データの中身・要求の本文）。ロガーの伏せ字を通した後のものだけを書く |
| テナント境界 | 会社の利用者のロールからは書くことだけができ、読むのは決まった関数を通す（ローカルの形の管理者と、運営のロールだけ） |

#### 16.10.2 入れ替え（ローテーション）

| 対象 | 規定 |
|---|---|
| データベースのシステムログ | **28 日（4 週）を過ぎた日の区切りを、ワーカーが毎日捨てる**（第11.9.6節の 4 週）。保全した期間（第16.10.5節）は捨てる前に写してあるので、そのまま捨ててよい |
| ローカルの形の標準出力のファイル（`api.log`・`worker.log`・`postgres.log`・`maintenance.log`・`update.log`） | **週に 1 回（日曜の 3 時 15 分）入れ替え、4 世代を圧縮して残す**（launchd の仕事 `jp.m2office.logrotate` が `logrotate.sh` を管理者の権限で呼ぶ）。launchd はこれらのファイルを追記で開いたままにしているため、名前を変えずに写して空にする（macOS の `newsyslog` には写して空にする指定が無く、名前を変えると書き込みが古いファイルに続く）。セットアップが入れ、更新でも無ければ入れる。ログの置き場（`M2O_LOG_DIR`）も更新が設定に足す |
| 入口のアクセスログ（`caddy.log`） | Caddy の入れ替えで、**28 日分を残す**（`roll_keep_for 672h`） |
| クラウドの形の標準出力 | 配備先の仕組みに任せる（読むのはデータベースのほう） |

#### 16.10.3 日ごとの改ざんの確かめ

日が変わったら、ワーカーが前の日のシステムログ（時刻順）から SHA-256 を作り、**前の日の値とつなげて**（鎖にして）表 `system_log_digests` に残す。
後からログの行を書き換えたり消したりすると、その日と、それより後の日の値が合わなくなる。この表は追記だけにする（監査ログと同じ。第16.6節）。
画面とダウンロードには、その日の値と、確かめた結果（合っている・合わない）を添える。

#### 16.10.4 見る・ダウンロードする

| 形 | 見られる人 | 場所 | 範囲 |
|---|---|---|---|
| **ローカルの形** | 会社の**管理者** | 管理者ページの「機械」に「システムログ」を足す（ローカルの形だけに出る。第8.6.7節） | その機械のすべて（会社は 1 つなので、会社の分と、会社に属さない仕組みの分）。標準出力のファイル（`api.log` ほか・入れ替えた世代）と入口のアクセスログも、ファイルのままダウンロードできる |
| **クラウドの形** | **運営者**（マスター管理画面に入れる人） | マスター管理画面に「システムログ」を足す（第23.8節） | すべての会社。会社（サブドメイン）で絞れる。どの会社にも属さない仕組みの分は「仕組み」で絞る |
| クラウドの形の会社の管理者 | 見られない（Q-236 で決定） | — | 会社の中で起きたことは、監査ログ（第16.6節）で見る |

| 項目 | 規定 |
|---|---|
| 絞り方 | 日時の範囲（既定は直近 1 時間）・レベル（`error`・`warn`・`info`）・プロセス・言葉（文と項目）・要求 ID・実行 ID・（クラウドの形）会社 |
| 並べ方 | 新しい順に 200 件ずつ続きを読む。行を押すと項目を開く |
| ダウンロード | 絞った結果を、1 行 1 件の JSON（`.jsonl`）か CSV で。1 回 100 万行・1 日分（クラウドの形の全社は 1 日、会社で絞れば 28 日）まで。日ごとの改ざんの確かめの値を添えた `manifest.json` と一緒に ZIP にする |
| 記録 | 見た・ダウンロードしたことを残す（ローカルの形は会社の監査ログ `log.view`・`log.download`、クラウドの形は運営の操作履歴。第23.8.10節）。絞った条件と件数だけを残す |
| 運営が会社のログを見ること | システムログは運営の運用のための記録で、顧客データの中身を持たない（第16.10.1節）ため、代理アクセス（第23.6.1節）の手続きは要らない。ただし見たことは運営の操作履歴に残し、会社で絞って見たときは会社の詳細（第23.8.4節）の運営の履歴にも出す。会社の管理者へのお知らせは送らない（Q-237 で決定） |

#### 16.10.5 証拠保全

**攻撃やその疑いがあったときに、その時点のログと記録を、消えない・書き換えられない形で写して残す。**

| 項目 | 規定 |
|---|---|
| 始め方 | ローカルの形は管理者ページの「機械」→「システムログ」の「証拠保全」。クラウドの形はマスター管理画面の「システムログ」の「証拠保全」（会社ごとか、全体）。理由（1〜300 字）を書いて押す。秘書にも「証拠を保全して」と頼める（管理者だけ。ローカルの形） |
| **自動で始める** | 不正の兆しの見張り（第16.8節）が、**自動でログアウトさせたとき**（種類の違う重い兆しが重なったとき）は、その会社の分を自動で保全する。理由は兆しの種類。攻撃が続いて何度もログアウトさせても膨れないよう、**自動の保全は同じ会社で 1 日に 1 回まで** |
| 写すもの | 範囲（既定は直近 28 日。始めた人が狭められる）の、システムログ・監査ログ・不正の兆しの記録・ログイン中の端末の一覧（その時点）・日ごとの改ざんの確かめの値。ローカルの形は、標準出力のファイルと入口のアクセスログ（接続元の IP を含む）も写す |
| 形 | 1 つの ZIP（中身ごとのファイルと、ファイルごとの SHA-256 を書いた `manifest.json`）。ZIP 全体の SHA-256 を、表 `evidence_packages` に残す（追記だけ）。ZIP はファイルの置き場の、ほかと分けた場所に置く |
| 消えないこと | 保全した ZIP は**入れ替えでも、4 週の決まりでも消さない。** 管理者も運営も、**保全してから 1 年は消せない**（Q-238 で決定。データベースの決まりでも止める）。1 年を過ぎたら、ローカルの形は管理者が、クラウドの形は運営が、理由を書いて消せる（消したことを残す） |
| ダウンロード | 保全した一覧から、ZIP をダウンロードできる。ダウンロードのたびに記録に残す。ダウンロードした ZIP は、`manifest.json` と `evidence_packages` の値で、写した後に変わっていないことを確かめられる |
| 知らせ | 保全したら（作れなかったときも）、その会社の管理者全員に「セキュリティ」のお知らせで知らせる。運営者には、マスター管理画面の「システムログ」の一覧に出す（全体の保全は会社に知らせない） |
| 持たないもの | 業務の入力・成果物・会話・ファイルの中身は写さない（システムログと監査ログが、もともと中身を持たない）。調べるのに中身が要るときは、第23.6節の手続きで別に扱う |

#### 16.11.2 「AI事業者ガイドライン（第 1.2 版）」の AI 提供者に関する事項

第 1.2 版は、AI エージェントが外への操作や大事な変更をする前に、人の判断を挟むことを求めている。M2Office の承認ゲート（不変則 I-3。人に判断を求めるのは社外に出るものとお金の確定。第9.4.0節）は、この考え方に沿う。

| 項目 | M2Office での対応 | 状態 |
|---|---|---|
| P-2）ⅰ. 人間の生命・身体・財産、精神及び環境に配慮したリスク対策 | 業務ごとに危険度を決め、社外への送信とお金の確定は承認の後（不変則 I-3）。送金・決済の実行とデータの完全な削除は作らない（第16.4節）。お金の機能は扱わない | 済 |
| P-2）ⅱ. 適正利用に資する提供 | 業務ごとのヘルプ（使い方・例・できないこと。第6.10節）。採用支援は合否と順位を付けない（第9.6.6節） | 済 |
| P-3）ⅰ. 構成及びデータに含まれるバイアスへの配慮 | 採用の文の点検で、性別・年齢・公正な採用選考で使ってはならない事柄を見つける（第9.6.6節）。金額は推論に計算させない | 一部（業務ごとに確かめる） |

別添 1 が挙げる AI エージェントの危険と、M2Office の対策は次のとおり。

| 危険（別添 1） | 対策 |
|---|---|
| 自律的な動作の中で、人の意図しない注文やファイルの削除をする | 社外への送信とお金の確定は承認の後（不変則 I-3）。送金と完全な削除は作らない（第16.4節）。本人の承認（`approver: requester`）を使う業務がある |

**G-11 の実装（第 0.387.0 版）**: `npm run security:check`（`scripts/check-security.mjs`）が `npm audit` で依存（開発の道具を含む）の既知の脆弱性を数え、「高」以上があれば失敗にする。npm の登録所に届かなければ「確かめられなかった」として失敗にする（通ったとは言わない）。GitHub Actions（`.github/workflows/security.yml`）が、main への push・pull request と週に 1 回（月曜の朝 9 時）、この点検と静的解析（CodeQL。`security-extended`）を回す。結果は GitHub の Security の画面に出る。リリース規定の事前の確認（第6.1節の 9）に足した。脆弱性の報告の窓口は `/.well-known/security.txt`（RFC 9116）で、入口（Caddy）が API の `/v1/security.txt` に渡す。連絡先は設定 `SECURITY_CONTACT`（運営主体が決める。無ければ出さない）、有効期限は 180 日後

**G-10 の実装（第 0.388.0 版）**: 前の鍵を設定 `M2OFFICE_SECRET_KEY_OLD`（カンマで複数）に置くと、読むときだけ使う（`SecretBox`。暗号化はいつも今の鍵。暗号文の形は変えない）。`npm run secrets:rotate`（`scripts/rotate-secrets.mjs`。配布物にも入れる）が、暗号化した値を持つ 7 つの列（`tenant_credentials.secret_enc`・`user_google_connections.refresh_token_enc`・`connection_secrets.client_secret_enc`・`connection_secrets.api_key_enc`・`user_connections.access_token_enc`・`user_connections.refresh_token_enc`・`canva_connections.refresh_token_enc`）を、データベースの所有者のつなぎで全社分読み、前の鍵で読めた値だけを今の鍵で暗号化し直す（`--check` は数えるだけ）。どの鍵でも読めない値は変えずに数えて示す。暗号化の列を移行で足したら、単体テストが対象の一覧との食い違いを見つける。手順: 新しい鍵を作る → `M2OFFICE_SECRET_KEY` を新しい鍵に、前の鍵を `M2OFFICE_SECRET_KEY_OLD` に → API とワーカーを動かし直す（止めずに続けられる。機械の管理者のログイン状態は同じ鍵で署名しているため入り直し）→ `npm run secrets:rotate`。**前の鍵は少なくとも 1 年残す**（名刺の一斉メールの配信停止のリンクと、入れ替えより前の控えが前の鍵で開くため）
