## 第 VI 部　安全性と品質

組織で使うために守ること。

## 16. 認証・セキュリティ・権限・プライバシー

### 16.1 認証

| 項目 | 方式 | 備考 |
|---|---|---|
| ログイン | **Google アカウント（OpenID Connect）** | 独自のパスワードは保持しない |
| テナント判定 | Workspace のドメインとテナントの対応を検証 | 招待されていないドメインは拒否する |
| **2 段階認証** | **Google アカウント側の 2 段階認証を利用。Phase 1 から必須とする** | 自前実装は行わない |
| セッション | API が発行する httpOnly Cookie | 第20.7節 |
| 失効 | Workspace 側でアカウントを停止すれば M2Office も使えなくなる | 退職処理が一元化される |
| 外部協力者 | Google アカウントを持たない相手の扱い | TBD（Q-34） |

**Google アカウントに一本化することで得られるもの**

| # | 内容 |
|---|---|
| 1 | パスワードの保管・リセット・漏洩対応といった責務を自社で負わない |
| 2 | 2 段階認証を Google の仕組みに委ねられ、自前実装が不要になる |
| 3 | ログインと Google 連携の同意が同じ事業者で完結し、初期設定の手数が減る |
| 4 | 退職者のアカウント停止が Workspace 側の操作だけで反映される |

**運用上の前提**

| # | 内容 |
|---|---|
| 1 | テナント管理者に対し、Workspace 側で 2 段階認証を必須にすることを導入時に確認する |
| 2 | Google アカウントが使えない状況ではログインできない。これは受け入れる前提とする |
| 3 | 管理者が 1 名しかいない状態を避けるため、管理者は 2 名以上の登録を推奨する |

#### 16.1.1 ログインに使う OAuth クライアント

**ログインと、Google のデータへのアクセスとで、OAuth クライアントを分ける。**

| 用途 | どのクライアントか | 求める権限 |
|---|---|---|
| **ログイン** | **運営のもの。全社で 1 つ** | `openid`・`email`・`profile` **だけ** |
| Google のデータ（メール・予定・ドライブ） | **会社のもの**。管理者ページの接続で登録する（第14.3.3節） | 使う業務が必要とする分だけ |

分ける理由は 2 つある。

| # | 理由 |
|---|---|
| 1 | **鶏と卵を避ける。** 会社の OAuth クライアントは管理者ページで登録する。そこへ入るにはログインが要る。ログインまで会社のクライアントに頼ると、最初の管理者が永久に入れない |
| 2 | **審査の重さが違う。** ログインが求めるのは基本の権限だけで、制限付きの権限を含まない。審査も CASA（第14.3.1節）も要らない。データへのアクセスと同じクライアントにすると、ログインまで審査に引きずられる |

**運営のクライアントが持つのは、誰がログインしたかを知るための権限だけである。**
メールも予定もドライブも読めない。会社のデータに触れるのは、会社のクライアントで得た許可だけである。

#### 16.1.2 ログインの経路

Google は、リダイレクト URI に **HTTPS を要求する**（例外は `localhost`）。
そのため**テナントごとのホストを、そのままリダイレクト先にはできない**。
開発の `http://<サブドメイン>.lvh.me` は、`localhost` ではないうえ HTTP であり、登録できない。

また、ログイン状態の Cookie は `Domain` を付けない（第20.7節）。
**受け取ったホストでしか有効にならない。**

この 2 つから、次の経路とする。

| 順 | 起きること | どのホストか |
|---|---|---|
| 1 | 利用者が「Google でログイン」を押す | 会社のホスト |
| 2 | どの会社かを `state` に入れて、Google の同意画面へ送る | 会社のホスト |
| 3 | Google が戻す | **運営のホスト 1 つ**（開発は `localhost`） |
| 4 | メールアドレスを取り、`state` の会社と照合する（下記） | 運営のホスト |
| 5 | **1 回限りの短命な引換券**を発行し、会社のホストへ戻す | 運営のホスト |
| 6 | 画面が引換券を差し出し、**そのホストで** Cookie を受け取る | 会社のホスト |

**リダイレクト URI を運営のホスト 1 本にできる。**
テナントが増えても、Google 側の設定を足す必要がない。

| 項目 | 規定 |
|---|---|
| 引換券 | **1 回だけ使える。** 使ったら消す。有効期間は 2 分 |
| 引換券に入れるもの | 会社と利用者の ID だけ。**利用者の名前もメールアドレスも入れない**（URL に個人の情報を載せない） |
| 照合 | メールアドレスのドメインが会社の Workspace のドメインと一致し、**かつその会社の利用者として登録されている**こと。どちらか一方でも欠ければ拒否する |
| 停止された利用者 | 拒否する |
| 失敗したとき | 会社のログイン画面へ戻し、理由を平易に示す。**どこまで合っていたかは示さない**（登録の有無を外から測らせない） |
| 記録 | 監査ログ `auth.login`（成功）と `auth.login.denied`（拒否。理由つき） |

#### 16.1.3 テナントの作成

セルフサインアップは Phase 3（Q-17）、マスター管理画面は第23章であり、どちらも未実装である。
**それまでの間、テナントの作成は運営の手元の道具（CLI）で行う。**

| 項目 | 規定 |
|---|---|
| 作るもの | 会社（サブドメイン・名前・Workspace のドメイン）と、**最初の管理者 1 名** |
| サブドメイン | 第20.4.3節の規則と予約語を守る。作る前に検査する |
| 最初の管理者 | メールアドレスは Workspace のドメインに属すること。ロールは `admin`・`approver`・`member` |
| 実行できる場所 | 運営の手元。画面からは行えない |
| 記録 | 監査ログに残す |

### 16.2 ロールと権限

| ロール | 権限範囲 |
|---|---|
| 運営管理者 | 全テナントの運用管理（顧客データの閲覧は原則不可、要記録の例外手続きのみ） |
| テナント管理者 | ユーザー、ペルソナ、LLM 設定、知識管理、拡張導入、課金、監査ログ |
| 承認者 | 割り当てられた領域の承認ゲートの判断 |
| 開発者 | サンドボックスでの定義作成・試験実行。本番データへの書込は不可 |
| 一般利用者 | 利用範囲（第16.7節）の中のエージェントの実行、自分の履歴と記憶の参照 |
| 外部協力者 | 限定されたエージェントと文書のみ |
| 外部アプリ | 付与されたスコープと最大危険度の範囲 |

### 16.3 権限区画

**この節で決めること**: 機微性の高いデータを、どう他から隔てるか。

#### 16.3.1 導入の理由

ロールと権限（第16.2節）だけでは足りない領域がある。
人事・労務が扱う給与額、評価、家族構成、健康診断の結果は、
他の業務データと同じ扱いにできない。特に健康に関する情報は
個人情報保護法の**要配慮個人情報**にあたる。

問題は、現在の設計が次の 2 つを許してしまう点にある。

| # | 問題 |
|---|---|
| 1 | 秘書は本人の権限内なら参照できる（不変則 I-9）。**人事担当者の秘書は全従業員の給与・評価を参照できてしまう** |
| 2 | 第11章の昇華をそのまま適用すると、**機微情報が全社の組織知識へ上がりうる** |

#### 16.3.2 権限区画とは

**権限区画（コンパートメント）は、データ・エージェント・知識をまとめて隔てる単位である。**

| 性質 | 内容 |
|---|---|
| 明示的な割当 | 区画に入れるのは、管理者が割り当てた**グループの所属者**と、個別に割り当てた者だけ（第16.7.5節、Q-76） |
| 既定は区画外 | ロールを持つだけでは入れない。職務として必要な者に限る |
| 流出しない | 区画内のデータは、区画外の知識・記憶・検索結果に現れない |
| 全件記録 | 区画内のデータへのアクセスは、**参照だけでも監査ログに残す** |

**HR を特別扱いするのではなく、区画という一般の仕組みを導入する。**
HR はその最初の適用例である。
将来、法務（係争案件）や経営（M&A、人事異動の検討）にも同じ仕組みを使える。

#### 16.3.3 HR 区画の範囲

| 区画に含む | 区画に含まない |
|---|---|
| 給与額、賞与、手当 | 就業規則・労務規程（全社に公開してよい） |
| 人事評価、面談記録 | 全社の集計値（総残業時間、有給取得率など個人が特定されないもの） |
| 家族構成、扶養情報 | 組織図、連絡先、所属 |
| 健康診断の結果、休職の記録 | 会議の出欠 |
| 勤怠の個人別明細 | 社内の福利厚生の案内 |
| 応募者の情報、面接の評価 | 求人原稿（公開する内容） |

**区画に含めるかどうかの基準**: その情報が漏れたとき、
本人の不利益になるか、社内の人間関係に影響するか。

#### 16.3.4 アクセスの 2 種類

**同じデータでも、誰がどの立場で見るかで扱いを分ける。**

| 種類 | 内容 | 秘書経由 | 記録 |
|---|---|---|---|
| **本人参照** | 自分に関するデータを本人が見る（自分の給与明細、自分の有給残日数） | **可** | 通常の監査ログ |
| **職務参照** | 他者のデータを職務として見る（人事担当者が全員分を確認する） | **不可** | **参照だけでも全件記録** |

この区別により、次が成立する。

- 従業員が秘書に「有給あと何日？」と聞くのは、本人参照なので問題なく答えられる。
- 人事担当者が秘書に「全員の残業時間を出して」と頼むことはできない。
  専用のエージェント（AG-11 ほか）から、記録が残る形で実行する。

**秘書は職務参照の経路にしない。** 秘書は常駐し文脈を保持するため、
機微情報が会話の流れに残りやすい。区画内の職務参照は、
目的が明確な業務エージェントに限定する。

#### 16.3.5 記憶と知識への制限

| 対象 | 扱い |
|---|---|
| 個人記憶（第11.1節） | **区画内のデータを残さない。** 本人参照で得た内容も記憶しない |
| チーム記憶 | 同上 |
| 組織知識（第11.1節） | **区画からの昇華を行わない**（第11.3節の経路を通さない） |
| 会話ログ（第11.9節） | 記録するが、区画の印を付け、学習の対象から除外する |
| 検索 | 区画外からの検索では、区画内の文書を候補にも出さない |

**「見つからない」と「権限がない」を区別しない。**
区画外の利用者に対しては、該当する情報の**存在そのものを示さない**。
「権限がありません」と返すと、情報の存在が推測できてしまう。

#### 16.3.6 エージェントとツールの扱い

| 項目 | 規定 |
|---|---|
| エージェント定義 | 区画に属するエージェントは、定義に区画を宣言する |
| 実行者 | 区画に割り当てられた者しか実行できない |
| ツール | 区画内のデータに触れるツールは、区画属性を持つ |
| 混在の禁止 | 1 つの実行の中で、区画内のデータを区画外の成果物へ書き出さない |
| 拡張機能 | 第三者の拡張機能を区画に入れる場合、審査の対象に加える（第12.5節） |

#### 16.3.6.1 区画の無効化と削除（第 0.62.0 版）

区画は、使わなくなったときに**無効にする**か、**削除する**ことができる。管理者だけが行う。

| 操作 | 規定 |
|---|---|
| 無効にする | 区画は残したまま、**その間は誰も区画に入れない**。割当の設定は消さず、有効に戻すと元の割当が効く |
| 無効の間の見え方 | 区画に属する知識・業務は、**誰にも見えない・実行できない**。区画の縛りが外れて全社に見えることはない（外す側に倒さない） |
| 無効の間の割当 | 入れるグループと人の変更はできない。先に有効へ戻す |
| 削除する | **その区画に属する知識・業務が 1 つでも残っていれば断る**。何がどれだけ残っているかを示し、先に消すか区画外へ移してもらう |
| 削除でできること | 残っていなければ、区画と割当をまとめて消す。監査ログは残る（第16.6節） |
| 記録 | 監査ログ `compartment.disable`・`compartment.enable`・`compartment.delete`。区画の出入りが変わるため、管理者へも知らせる（第16.7.5節） |

**「誰にも見えない」に倒す理由**は、区画の目的が隔離だからである。
無効にした拍子に機微な情報が全社に出るくらいなら、一時的に誰も見られないほうが害が小さい。

#### 16.3.7 LLM への送信

| 項目 | 方針 |
|---|---|
| 送信範囲 | 区画内のデータを送る場合、処理に必要な最小限に絞る |
| 識別子 | 氏名を識別子に置き換えられる処理では置き換える |
| 健康情報 | TBD: 送信の可否と範囲を個別に定める（Q-47）。**顧客の手元のシステムが持つ患者などの健康情報は、M2Office に入れない**（第 0.150.0 版で決定。個人が分からない集計だけを受け取る。第12.11.7節、ADR-0046） |
| 記録 | 何を送ったかを監査ログに残す |

#### 16.3.8 実装上の含意

| # | 含意 |
|---|---|
| 1 | データに区画の属性を持たせる。文書・知識・記憶・会話ログのすべてが対象 |
| 2 | 検索とツール呼び出しに、区画による絞り込みを既定で適用する |
| 3 | 利用者と区画の割当を保持する |
| 4 | 区画内データへの参照を監査ログに記録する経路を用意する |

**第 1 項は Phase 1 から用意する。**
区画の属性を持たずに運用を始めると、後から機微情報と一般情報を分離することはできない。
個人記憶と組織知識を最初から分ける（第24.2節）のと同じ理由である。

### 16.4 エージェントの行動制約

| 区分 | 扱い |
|---|---|
| 実装しない | 送金・決済の実行、データの完全削除、認証情報の代理入力 |
| 必ず承認 | 対外送信、外部共有、会計データの確定、設定変更 |
| 承認不要 | 読取、下書き作成、社内向け要約、検索 |

**プロンプトインジェクション対策**: メール本文、外部文書、MCP サーバの応答、
第三者が提供したエージェント定義に含まれる指示文は、基盤の制約を上書きできない。
危険度による承認強制（第9.4節）は基盤側で判定する。

**音声経由でも同じ**（不変則 I-11、第10.6節）。

### 16.5 データ保護とプライバシー

| 項目 | 方針 |
|---|---|
| 通信 | TLS 必須。ワイルドカード証明書で全サブドメインを保護 |
| 保管 | 保存時暗号化。認証情報は専用のシークレット管理で別途保護 |
| テナント分離 | 単一データベース＋行レベルセキュリティ（RLS） |
| 個人記憶の分離 | 同一テナント内でも他者の個人記憶を参照できない |
| 個人情報 | 取得・利用目的を明示。委託先（LLM 提供者等）を公開 |
| モデルの学習 | 顧客データを LLM の重みの更新に用いない。外部提供者にも行わせない（第11.9.3節） |
| システムの蓄積 | テナント内にデータを蓄積し、応答の改善に用いる。**これは製品の中核機能である** |
| テナントを越える利用 | 既定では行わない。個別に同意を得た場合に限る |
| 拡張機能への露出 | 宣言・同意された範囲のデータにしか触れられない |
| LLM への送信範囲 | 必要最小限。TBD: マスキングの要否と対象項目 |
| 音声データ | 録音は破棄し、文字は会話ログに残す（Q-19） |
| 運営のアクセス | 顧客データに触れる場合は事前承諾と記録を必須とする |

調査で「情報漏洩のリスク」が懸念の 33.5% を占めることから、
**これらの方針を製品ページと管理者画面で平易に説明する**ことを要件とする。

### 16.6 監査

| 項目 | 内容 |
|---|---|
| 記録対象 | ログイン、権限変更、連携設定、拡張導入、全ステップ実行、承認判断、知識の昇華、API 呼び出し |
| 記録内容 | 主体（人・秘書・アプリ）、日時、対象、操作、根拠、結果 |
| 改変防止 | 追記のみ。削除・更新は不可 |
| 提出 | 期間・主体・操作の種類で検索し CSV 出力できる。画面と CSV は人の名前と業務の言葉で出す（第6.6.8.1節） |

**秘書が代行した操作も、本人を主体として記録する。**
「秘書がやったから分からない」状態を作らない。
懸念として「トラブル時の責任所在」25.5% が挙がっている以上、
誰の指示で何が行われたかが残ることが組織利用の前提になる。

### 16.7 グループと利用範囲

**この節で決めること**: 利用者をグループにまとめ、業務ごとに「誰が使えるか」（利用範囲）を決める方法。

#### 16.7.1 導入の理由

拡張機能で業務を足していくと、**全員が使う業務**と**一部の人だけが使う業務**が混ざる。

| 業務の例 | 使う人 |
|---|---|
| 社内ナレッジ Q&A、週次ブリーフ | 全員 |
| ローカル AI の市場調査を資料（PowerPoint）にまとめる | マーケティングと、経営層 |
| リポジトリの調査 | 開発部門と、特定の数名 |
| 採用・労務の業務 | 人事部だけ |

全員のメニューに全業務を並べると、使わない業務で画面が埋まり、使うべきでない人が起動できてしまう。
**これまでに作った仕組み（実行・承認・記録・拡張機能）は全社の共通基盤とし、その上に「誰が使えるか」を重ねる。**

#### 16.7.2 グループ

**グループは、利用者の組織上のまとまりである**（部署・役職・プロジェクトなど）。

| 性質 | 内容 |
|---|---|
| 作る人 | 会社の管理者 |
| 属性 | 名前（会社の中で重ならない）、説明 |
| 所属 | 1 人が複数のグループに入れる（例: 「開発」と「管理職」） |
| 範囲 | 会社（テナント）の中だけ。他の会社のグループとは無関係（不変則 I-2） |
| 例 | 管理職、マーケティング、開発、営業、人事 |
| 削除 | グループを消しても、利用者は消えない。利用範囲からそのグループが外れる。その結果、範囲に誰も残らない業務は**全員に戻さず誰も使えないままにし**、画面で知らせる（開く方向に倒さない） |

#### 16.7.3 利用範囲

**利用範囲は、業務を使える人の範囲である。** 業務の単位ごとに設定する。

| 対象 | 単位 |
|---|---|
| 公式の業務エージェント | 業務エージェントごと |
| 拡張機能 | **拡張機能ごと**（その拡張機能の業務エージェントすべてに同じ範囲が効く） |

| 範囲の指定 | 使える人 |
|---|---|
| **全員**（既定） | その会社の利用者全員 |
| **指定** | 指定したグループのいずれかに所属する人 **または** 個別に指定した人 |

「開発部門プラス誰か」は、グループ「開発」と個人「〇〇さん」を指定して表す。
指定を選んで、グループも人も 1 つも選ばない設定は保存できない（誰も使えない業務は「無効」（第6.6.5節）で表す）。

#### 16.7.4 範囲の外の人にとっての扱い

**範囲の外の人には、その業務は無いものとして扱う。**

| 経路 | 扱い |
|---|---|
| ワークスペースのメニュー | 出さない |
| 秘書の取次 | 取り次がない。秘書は範囲の外の業務を候補にしない |
| 定時実行 | 新しく作れない。範囲から外れた人の定時実行は、その回を起動せず記録を残す |
| API | 業務の一覧に出さない。起動の要求は「見つからない」（404）とする |
| ヘルプ | 業務の説明を出さない |
| 実行の途中 | ワーカーが実行を進める時点でも依頼者が範囲の中かを確かめ、外なら実行を止める |

**範囲の外の人にも、過去の自分の実行の記録と成果物は見せる。** 範囲は「これから使えるか」を決めるものであり、
すでに行った実行を消すものではない。
承認は、利用範囲ではなく承認の指定（第9.2.3節）に従う。範囲の外の承認者も、割り当てられた承認は判断できる。

#### 16.7.5 ロール・権限区画との関係

| 仕組み | 決めること | 例 |
|---|---|---|
| ロール（第16.2節） | 画面と操作の権限（管理・承認） | 管理者、承認者、一般 |
| **利用範囲（この節）** | **どの業務を使えるか** | 「市場調査」はマーケティングだけ |
| 権限区画（第16.3節） | **機微なデータ**を隔てる。参照も全件記録する | HR 区画の給与・評価 |

**利用範囲は権限区画の代わりにならない。** 利用範囲は業務の入口を絞るだけで、データを隔てない。
機微なデータを扱う業務は、権限区画に入れたうえで、利用範囲も区画の割当と揃える。
区画に属する業務エージェントは、利用範囲の中**かつ**区画に割り当てられた人だけが実行できる。

**人の割当は、すべてグループで行う（決定、Q-76）。** 利用範囲も権限区画も、「グループと、個別に指定した人」という
同じ形で割り当てる。特別な割当の仕組みを別に作らない。
例: 人事区画には「人事」グループと社長個人を、法務区画には「法務」と「管理職」を割り当てる。

区画の性質（区画外へ流出しない、参照も全件記録する。第16.3.2節）は変わらない。変わるのは「誰が入れるか」の指定の方法だけである。
グループに人を足すと区画に入れてしまうため、区画に割り当てたグループには次を守る。

| # | 規定 |
|---|---|
| 1 | 区画に割り当てたグループの所属の変更は、監査ログに**区画への出入り**としても記録する |
| 2 | そのとき、会社の管理者全員に通知する（誰が、どの区画に、入った・出たか） |
| 3 | グループの管理（作成・所属の変更）は M2Office の管理者だけが行う。グループごとの管理者は置かない |
| 4 | 管理者ページで、グループがどの区画・どの業務に割り当てられているかを示す。所属を変える前に影響が分かるようにする |

#### 16.7.6 管理者の扱い

**管理者も、業務を使う場面では利用範囲に従う**（最小権限。決定、Q-74）。
管理者ページでは、範囲に関係なくすべての業務と拡張機能を見て設定できる。
管理者が範囲の外の業務を試すには、自分を範囲に加える。

#### 16.7.7 画面

| 画面 | 内容 |
|---|---|
| 管理者ページ「ユーザーと権限」 | グループの作成・名前の変更・削除と、所属する人の割当。利用者ごとに所属するグループを示す |
| 管理者ページ「業務と承認」 | 公式の業務エージェントごとに「利用できる人」（全員／指定）を設定する |
| 管理者ページ「拡張機能」 | 導入の同意の画面で「利用できる人」を選ぶ（既定は全員）。導入後はカードに範囲を示し、変更できる |
| 個人設定「利用状況」 | 本人が所属するグループを示す |

範囲を示すときは「全員」「開発・マーケティング、ほか 2 人」のように短く書く。

#### 16.7.8 記録

| 操作 | 監査ログ |
|---|---|
| グループの作成・変更・削除 | `group.create`・`group.update`・`group.delete` |
| 所属の変更 | `group.members`（追加・削除した人） |
| 利用範囲の変更 | `settings.update`（区分 `access`） |
| 範囲の外で実行を止めた | `run.fail`（理由に「利用範囲の外」） |

#### 16.7.9 保存

| 対象 | 保存先 |
|---|---|
| グループ | `user_groups`（テナントごと。RLS） |
| 所属 | `user_group_members`（テナントごと。RLS） |
| 利用範囲 | 会社の設定の区分 `access`（`tenant_settings.access`）。対象（公式の業務エージェントの ID か拡張機能の ID）ごとに、グループと人の一覧を持つ。対象が無いものは全員 |

拡張機能を削除すると、その利用範囲の設定も消す。

#### 16.7.10 段階

| 段階 | 内容 |
|---|---|
| いま実装する | グループ、利用範囲（公式の業務エージェント・拡張機能）、全経路での適用、画面、記録 |
| 次に | 権限区画の割当をグループで行う（第16.7.5節、Q-76 決定）、拡張機能の中の業務エージェントごとの範囲 |
| 検討中 | Google Workspace のグループとの関係（第16.7.11節、Q-75 保留） |
| そのあと | グループごとの承認者の指定（「営業の業務は営業部長が承認」） |

#### 16.7.11 Google Workspace のグループとの関係（検討中）

**結論は保留する（Q-75）。** ここでは判断の材料を残す。

**M2Office で別に管理した場合に起きること**

| # | 起きること | 重さ | 補足 |
|---|---|---|---|
| 1 | 異動のたびに、Workspace と M2Office の両方を直す必要がある | 中 | 10 名規模では管理者 1 人が両方を行うため、手間は小さい |
| 2 | **異動の反映漏れ**。異動した人が、元の部署の業務・区画を使い続ける | **高** | 最も重い問題。区画の出入りの通知（第16.7.5節）と、定期的な棚卸しで補う |
| 3 | 退職者 | 低 | ログインは Google アカウントで行うため、Workspace で停止すれば M2Office にも入れない |
| 4 | グループの名前や構成が、Workspace とずれる | 低 | 利用者が混乱する程度 |

**Workspace のグループと同期した場合に起きること**

| # | 起きること | 重さ | 補足 |
|---|---|---|---|
| 1 | **管理する人が違う**。Workspace ではグループのオーナー・管理者に一般の社員がなれる。その人が所属を変えると、M2Office の区画に人を入れられてしまう | **高** | 権限を広げる経路になる。「管理者が違うと厄介」の中身はこれ |
| 2 | Workspace のグループは、多くが**メールの配信用**に作られている。社外のアドレス、グループの入れ子、「全員」のような広いものが混ざる | **高** | そのまま権限に使うと、意図しない人が入る |
| 3 | 読み取りに Workspace の管理者の同意（Directory API の権限）が要る | 中 | Google 連携の準備（B-2）と審査に影響する |
| 4 | 同期のずれ・Google の障害 | 中 | 取得できないときの扱い（直前の状態を保つか、使えなくするか）を決める必要がある |
| 5 | 異動が自動で反映される | 利点 | 別管理の問題 2 が解消する |

**考えられる形**

| 案 | 内容 | 向いている会社 |
|---|---|---|
| A | M2Office で別に管理する（いまの実装） | 10 名規模。管理者が 1 人 |
| B | Workspace のグループをそのまま使う（完全な同期） | 権限用のグループを Workspace で厳密に運用している会社 |
| C | **M2Office のグループを正とし、Workspace のグループから所属を一方向に取り込む**。取り込むグループは管理者が選ぶ。区画に割り当てたグループは取り込みの対象にしない（または取り込んだ変更を管理者の承認制にする） | A の手間と、B の危うさの間 |

いまは A で運用し、Google 連携（B-2）が整った段階で C を検討する。

#### 16.7.12 Google Chat のスペースとの関係（未決。Q-87）

**M2Office のグループと、Google Chat のスペースは、つながっていない別々のものである。**
議事録作成などの共有先に指定するのは Chat のスペースの名前（第14.3.4節「Chat」）であり、M2Office のグループではない。

| | M2Office のグループ | Google Chat のスペース |
|---|---|---|
| 決めること | 誰がどの業務を使えるか（利用範囲）、誰が権限区画に入れるか | 投稿がどこへ届き、誰が読めるか |
| 管理する人 | M2Office の管理者だけ | スペースの管理者（一般の社員もなれる） |
| M2Office での使い道 | メニューの出し分け、区画の出入り | 共有の投稿先としてだけ |

**起きていること**（2026-09-25 に三浦さんが提起）

| # | 事象 |
|---|---|
| 1 | 同じ「技術部」という名前でも、片方を変えても他方に効かない |
| 2 | M2Office の「技術部」グループに入っていても、Chat の「技術部」スペースに入っていなければ、共有先として見つからない |
| 3 | 共有の投稿は、M2Office のグループと関係なく、**Chat のスペースのメンバー全員**に届く。M2Office は投稿先のメンバーを確かめていない |
| 4 | 三浦さんも利用者も「グループで部署ごとに共有先をまとめられる」と思っていた |

**どう整理するかは、別の議題として後で扱う**（Q-87）。Workspace のグループとの関係（第16.7.11節、Q-75）と合わせて考える。
それまでは、結び付けの仕組みを作らない。
