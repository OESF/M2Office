## 13. プラットフォーム API とエコシステム

**この章で決めること**: 外部から M2Office をどう使えるようにするか。

### 13.1 公開の方針

| # | 方針 |
|---|---|
| A-1 | 画面が使う API と外部公開 API は**同じ基盤の上に構築する** |
| A-2 | 自社が使う機能はすべて API として存在する。内部だけの抜け道を作らない |
| A-3 | 認証・スコープ・監査は内部利用と外部利用で共通とする |
| A-4 | 破壊的変更は版を分け、旧版を一定期間維持する |
| A-5 | 仕様は OpenAPI として公開し、実装から自動生成する |

**A-1 と A-2 は設計初期に決めておかないと後から実現できない。**
外部公開は Phase 2 以降だが、**この方針は Phase 1 から適用する**。

### 13.2 提供する API の種類

| 種類 | 用途 | フェーズ |
|---|---|---|
| REST API | ジョブ起動、状態取得、成果物取得、カタログ参照、知識登録 | 2 |
| Webhook | 実行完了、承認要求、失敗の通知 | 2 |
| MCP サーバとしての公開 | **M2Office 自体を MCP サーバとして公開し、外部の AI から呼べるようにする** | 3 |
| 管理 API | テナント設定、拡張機能の導入、権限付与 | 3 |
| 拡張機能配布 API | マーケットへの公開・更新 | 3 |

### 13.3 REST API の主要エンドポイント

**パスの体系は、現在の実装を正とする**（Q-67 で決定、ADR-0019）。
画面が使う API と、外部へ公開する API は**同じものである**。別系統を作らない（第24.2節）。

体系の決まりは 3 つである。

| # | 決まり | 理由 |
|---|---|---|
| 1 | **依頼（`/v1/jobs`）と実行（`/v1/runs`）を分ける** | 依頼は「何を頼んだか」（業務・入力・依頼者・起動経路）、実行は「1 回の走行」（状態・区切りの位置・費用・削減時間）であり、別の型である（第19章）。1 つの依頼が再試行で複数の実行になりうる |
| 2 | **管理者だけが使う口は `/v1/admin` の下に置く** | 権限の境界を URL に現す。取り付け点で 1 回だけ確かめられ、確認の抜けを作らない |
| 3 | **本人の設定・記憶・会話は `/v1/me` の下に置く** | 本人以外は触れない（不変則 I-10）。これも取り付け点で確かめる |

| 分類 | メソッド・パス | 内容 |
|---|---|---|
| カタログ | `GET /v1/agents` | 使える業務と入力の定義の一覧（利用範囲で絞る。第16.7節） |
| 依頼 | `POST /v1/jobs` | 業務を依頼する。待ち行列へ入れるだけで、呼び出し側を待たせない（第8.4節） |
| 依頼 | `GET /v1/jobs` | 本人が依頼したものの一覧 |
| 実行 | `GET /v1/runs/{id}` | 状態・進み具合・ステップ・成果物。見られる人は第6.2.3節 |
| 実行 | `POST /v1/runs/{id}/cancel` | 実行の中止（第9.3.1節）。依頼した本人だけ |
| 承認 | `GET /v1/approvals` | 承認待ちの一覧（本人が判断できるものだけ） |
| 承認 | `POST /v1/approvals/{id}` | 承認または却下。**外部からは既定で禁止**（下記） |
| ファイル | `GET /v1/files/{id}/content` | 実行が扱ったファイル。見られる人は第6.2.3節 |
| 秘書 | `POST /v1/secretary` | 秘書への問いかけ（第10.9節の 3 層） |
| 本人 | `GET /v1/me`、`PUT /v1/me/settings/{section}`、`POST /v1/me/voice-test` | 本人の情報と個人設定。声を試す（第10.5.8節） |
| 知識 | `POST /v1/admin/knowledge` | 組織知識への登録（ID を発行する） |
| 知識 | `PUT /v1/admin/knowledge/{id}` | 既存の知識の更新 |
| 監査 | `GET /v1/admin/audit-events` | 監査ログの取得 |
| 外部のアプリ | `GET /v1/company/profile`・`GET /v1/inventory/catalog`・`POST /v1/inventory/sales-events` ほか | 外部のアプリの鍵で呼ぶ機能（第13.4.1節）。機能ごとに呼べる道が決まる。案の機能は第13.4.2節 |

実装済みの API の全体は `packages/api/README.md` に一覧する。

**承認の API 化は慎重に扱う。**
既定では API 経由の承認を禁止し、管理者が危険度ごとに明示的に許可した場合のみ有効とする。
`external-send` と `financial` については API 承認を**恒久的に禁止**する。

### 13.4 認証と権限

| 項目 | 方式 |
|---|---|
| 方式 | OAuth 2.0（認可コード、およびサーバ間用のクライアント資格情報） |
| 発行 | 管理者が管理者ページからアプリを登録し、スコープを選んで発行 |
| スコープ | `agents:read` `jobs:write` `approvals:read` `knowledge:write` など機能単位 |
| 実行主体 | API 経由の実行にも「誰として実行するか」を必ず紐付ける |
| 危険度の上限 | アプリごとに扱える最大危険度を設定できる |
| 監査 | API 呼び出しはすべて監査ログに記録する |
| 失効 | 管理者はいつでもアプリの権限を失効できる |
| 流量制御 | アプリ単位のレート制限とコスト上限 |

#### 13.4.1 外部のアプリ（鍵の形。第 0.326.0 版、ADR-0090）

2026-10-10 に三浦さんが、販売管理（第29.20.1節）・M2Medical（第11.12節）と、外のシステムとつなぐ依頼が続くため、**用途ごとに口を作るのをやめ、汎用の API として定義し、販売管理やナレッジの提供は使い方の例として解説する**ことを求めた。
上の表の「管理者がアプリを登録し、スコープを選んで発行」を、まず**鍵の形**で作る。OAuth（認可コード・クライアント資格情報）は、あとで同じアプリに足す。三浦さんが、外部のアプリの登録の形・作った販売管理とのつなぎをいま移すこと・画面と同じ `/v1` の道で呼ぶこと、を選んだ。

| 項目 | 規定 |
|---|---|
| 登録 | 会社の管理者が、管理者ページの「接続」の「**外部のアプリ**」でアプリを登録する（販売管理・M2Medical など。1 社に 20 まで）。アプリごとに名前と鍵を持つ |
| 鍵 | 登録すると鍵（`m2oa_` で始まる 37 字）を**一度だけ見せ**、M2Office はハッシュだけを持つ。アプリは `Authorization: Bearer <鍵>` で呼ぶ。「鍵を出し直す」で前の鍵はすぐ使えなくなる。`m2oa_` の頭で、鍵が漏れたときに見つけやすくする |
| 機能（スコープ） | アプリごとに、使える**機能**を選ぶ（下の表）。機能は、外のシステムに許す操作のまとまりで、機能ごとに呼べる道が決まっている。選んでいない機能の道は 403 |
| 承認 | 機能と、機能ごとの設定（渡す品目など）を選び、「**この内容で許す**」を押すことが**管理者の承認**である（社外への送信・社外からの書き込みを、範囲で一度承認する。第9.4.0節）。承認するまでは、どの機能も使えない。機能や設定を変えたら承認し直す。承認した範囲の 1 回ずつの呼び出しは承認なしに受ける |
| 道 | **画面と同じ `/v1` の道**（第13.1節 A-1・A-2）。会社は呼んだ名前（サブドメイン。ローカルの形は機械の名前）で決まり、**鍵の会社と合わなければ断る**。機能ごとの道は下の表。管理者ページの道（`/v1/admin`）と本人の道（`/v1/me`）は、どの機能でも呼べない |
| 実行主体 | 「誰として実行するか」を必ず決める（上の表）。会社の情報や在庫を読み書きする機能は**アプリ自身**（記録した人は「外部のアプリ（名前）」）。本人の権限で行う機能は、**アカウントの結び付け**で結び付いた本人（第11.12節） |
| 答えの決まり | 鍵が違う・アプリを止めた・会社が止まっている（停止・緊急停止・解約）・会社が合わないは、どれも同じ 404（理由を分けない）。機能が許されていないは 403。形が違うは 400（どの項目か）。回数の上限は 429 と `Retry-After` |
| 回数の上限 | アプリごとに 1 分 120 回（機能ごとに、さらに絞ることがある） |
| 送られてきた中身 | データとして扱い、指示として読まない（不変則 I-6）。本文は 64 KB まで。書き込みの機能は、通知ごとの番号（`eventId`）で二重に数えない |
| 止める・削除 | 止めると、鍵ではどの道も 404。削除は止めてあるアプリだけ。入出庫の記録などの業務の記録は残る |
| 監査 | 登録・名前の変更・承認・鍵の出し直し・停止・再開・削除は監査ログ（`app.*`）。1 回ずつの呼び出しは、機能の決まりに従う（入出庫の記録そのもの・検索の記録など） |
| 様子 | アプリごとに、最後に呼ばれた時刻・この 7 日の呼び出しの数を「外部のアプリ」に出す |
| 定義 | すべての機能の道を、OpenAPI の 1 つの定義（`docs/api/m2office-apps.openapi.yaml`）に書き、管理者ページのヘルプの「開発者」で Swagger UI で見られる（第6.10.7.4節）。使い方の例（販売管理・M2Medical）は、ヘルプの記事で解説する |
| OAuth との関係 | 鍵の形は OAuth のクライアント資格情報の簡易版にあたる。OAuth を作るときは同じアプリに足し、機能をスコープとしてそのまま使う |

**機能の一覧**（足すときは、機能を 1 つ足し、道と定義と使い方の例を足す）

| 機能 | 呼べる道 | 実行主体 | 機能ごとの設定（承認の対象） | 状態 |
|---|---|---|---|---|
| 会社の基本情報を読む（`company.profile`） | `GET /v1/company/profile` | アプリ | なし。返すのは会社名・略称・郵便番号・所在地・電話・Web・適格請求書発行事業者の登録番号・会計年度の開始月・営業する曜日と祝日の扱い（第6.6.1節）。端数処理・締め日・支払サイトは返さない | 第 0.326.0 版で実装 |
| 商品の一覧を読む（`inventory.catalog`） | `GET /v1/inventory/catalog` | アプリ | 渡す品目・数か状態だけか・販売価格・社員価格（第29.20.1節） | 第 0.326.0 版で実装（販売管理とのつなぎから移した） |
| 販売を知らせる（`inventory.sales`） | `POST /v1/inventory/sales-events` | アプリ | なし（照らせない行は在庫管理で人が品目を選ぶ。第29.20.1節） | 第 0.326.0 版で実装（同上） |
| アカウントを結び付ける（`accounts.link`） | `POST /v1/accounts/link-requests`・`POST /v1/accounts/links`・`DELETE /v1/accounts/links/{bindingId}` | アプリ（結び付けの依頼・確定・削除） | なし（第11.12節） | 案 |
| ナレッジを検索する（`knowledge.search`） | `POST /v1/knowledge/search` | 結び付いた本人 | なし。`accounts.link` も要る（第11.12節） | 案 |

在庫管理の機能は、在庫管理を入れた会社でだけ選べる。案の機能は、合意のあとに作るまで選べない。
ほかに、問い合わせ・お知らせ・入庫・予約・会員のポイント・コラム・社内規程・業務の依頼の 8 つの機能を案として定めた（第13.4.2節）。

#### 13.4.2 外部のアプリの機能の案（第 0.327.0 版。案）

2026-10-10 に三浦さんが、外部のアプリとして公開すると便利な機能の提案を求め、次の 8 つを案にすることを選んだ（勤怠の打刻と監査ログを読む機能は外した）。どれも既にある機能（各章）を、外部のアプリの鍵で使えるようにするもので、**元の機能の決まり（権限・人の情報・承認・お金を扱わない）はそのまま守る**。作る順は合意のあとに決める。

**共通の決まり（案）**

| 項目 | 規定 |
|---|---|
| 元の機能の入り切り | 内蔵の拡張の機能（問い合わせ・予約・会員・コラム）は、その拡張を入れた会社でだけ選べ、切ると道は 404（在庫の機能と同じ） |
| 実行主体 | 会社として行うもの（問い合わせを受ける・お知らせを出す・入庫・ポイント・コラムを読む・規程を登録する）は**アプリ自身**（記録した人・出した人は「外部のアプリ（名前）」）。本人として行うもの（予約を入れる・業務を依頼する）は、**アカウントの結び付け**（`accounts.link`。第11.12節）で結び付いた本人で、本人の利用範囲と権限で行う |
| 道 | 画面に同じ操作の道があるもの（お知らせ・予約・業務の依頼）はその道を使い、アプリの鍵のときは下の決まりで動く。画面に無い形のもの（問い合わせの受け付け・入庫・ポイント・公開したコラム・規程の登録）は道を足す |
| 書き込み | どれも通知ごとの番号（`eventId`）で二重に数えない（第13.4.1節） |
| 承認 | 機能ごとの設定（下の表）を、アプリの「この内容で許す」で承認する。社外への送信とお金の確定は、どの機能でも外から行えない（外からの承認は第13.3節のとおり恒久的に禁止） |
| 利用範囲の判定 | アプリ自身として行う機能は、拡張の利用範囲（人やグループ）を使わず、機能の承認で決める。本人として行う機能は本人の利用範囲で決める |

| # | 機能（案） | 道（案） | 実行主体 | 機能ごとの設定（承認の対象） | 決まり（元の機能に合わせる） | 元の章 |
|---|---|---|---|---|---|---|

| 2 | 社内のお知らせを出す（`notices.post`） | `POST /v1/notices`・`POST /v1/notices/{id}/withdraw` | アプリ | 出してよい宛先（全員か、決めたグループ） | 画面と同じ形（題名・本文・リンク（https だけ）・宛先・締切・出す期限）。承認の範囲の外の宛先は 403。出したアプリだけが取り下げられる。Chat への投稿は、出した人の Google で行う仕組みのため、アプリからは投稿しない（お知らせだけ） | 第10.15節 |

### 13.6 エコシステムの成長戦略

| 段階 | 施策 | 狙い |
|---|---|---|
| 1 | 公式エージェントと秘書で製品として成立させる | 拡張の土台となる利用者を確保する |
| 2 | プライベート拡張を開放し、SIer が受託で作れるようにする | 顧客固有ニーズを外部の手で埋める |
| 3 | マーケットを開き、認定拡張を掲載する | 提供者が収益を得られる状態を作る |
| 4 | 業種特化の拡張が集まり、業種別の導入事例が生まれる | 「成功事例が不足」83.3% への回答となる |

**士業・業界団体との連携**が有効である。業務知識と販路の両方を持つためである。

### 13.7 パートナー制度

**この節で決めること**: 外部に拡張を作ってもらう仕組み。

#### 13.7.1 成り立つ理由

拡張が**画面から導入できる**ため、作る人と使う人を分けられる（第2.3.4節）。

| 役割 | 担う人 | 必要な能力 |
|---|---|---|
| 作る | パートナー | 業務知識、または API 開発 |
| 届ける | パートナー、マーケット | 販路 |
| **入れる** | **顧客の管理者** | **不要。画面の操作だけ** |
| 使う | 顧客の従業員 | 不要 |

既存の方式では「入れる」にも技術力が要り、
顧客側に扱える人がいなければ届かなかった。ここが外れることで、
**パートナーが作ったものが、そのまま顧客に届く**経路ができる。

#### 13.7.2 パートナーの類型

| 類型 | 作るもの | 収益の形 |
|---|---|---|
| システムインテグレーター | 個社固有の拡張（受託） | 受託費用。プライベート拡張は課金対象外 |
| 業種特化の事業者 | 業種向けの拡張（汎用） | マーケットでの販売 |
| 業務系 SaaS ベンダー | 自社サービスとの接続（MCP） | 自社製品の利用機会 |
| 士業・業界団体 | 業務手順と知識（L1） | 顧問先への付加価値、会員向けの提供 |

**士業と業界団体が鍵になる。**
業務知識と販路の両方を持ち、かつ L1（宣言的な定義）は
プログラミングなしで作れるため、参入の敷居が低い。

##### 先行例

Anthropic の公開リポジトリには `partner-built` という区画があり、
**SaaS ベンダー自身が自社製品向けのプラグインを提供している**
（Apollo、Slack、Zoom、Common Room ほか）。

この形は M2Office でもそのまま成立する。
会計・販売管理・勤怠などの国内 SaaS が、自社への接続を
拡張機能として提供すれば、**自社製品の利用機会が増える**。
運営が 1 社ずつ接続を作る必要がなくなる。

#### 13.7.3 段階

| 段階 | 内容 | フェーズ |
|---|---|---|
| 1 | プライベート拡張を開放する。受託で作れる状態にする | 2 |
| 2 | 認定制度を設け、審査を通ったものをマーケットへ掲載する | 3 |
| 3 | 収益分配を伴う販売を開始する | 3 |
| 4 | 業種別の事例が集まり、パートナー経由の導入が主になる | 4 |

#### 13.7.4 運営が用意するもの

| 提供物 | 内容 |
|---|---|
| 開発者ポータル | 仕様、手引き、サンプル（第13.5節） |
| サンドボックス | 本番に触れずに試せる環境 |
| 審査 | 権限・品質・制度適合の確認（第12.5節） |
| 掲載 | マーケットでの提示と、認定の表示 |
| 課金の代行 | 販売の受付と収益分配（第21.7節） |
| 事例の公開 | 導入実績の紹介 |
