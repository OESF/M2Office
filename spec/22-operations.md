## 22. 導入・運用

### 22.1 導入の流れ

| 段階 | 内容 | 目標時間 |
|---|---|---|
| 1 | サインアップ（Google アカウントで登録。第16.1節）、サブドメイン自動発行 | 3 分 |
| 2 | 会社情報の入力（社名・決算期・登録番号） | 5 分 |
| 3 | **Google Workspace への連携認可** | 3 分 |
| 4 | 使う業務エージェントの選択 | 5 分 |
| 5 | 労務規定など主要な規程の登録（任意） | 5 分 |
| 6 | **秘書に話しかけて 1 件試してみる** | 5 分 |
| 7 | 同僚を招待し、ペルソナを設定 | 4 分 |
| 8 | **従業員へ、ダッシュボードで表示される範囲を知らせる**（第6.7.10節）。案内文のひな形を用意する | 3 分 |

**サインアップから初回実行成功までを 30 分以内**とする（第17章）。
これは「推進人材の不足」40.0%、「業務がイメージできない」63.4% という
市場の実情への直接の回答である。

### 22.2 Google 連携ウィザード

段階 3 の「Google Workspace への連携認可」は、**放置すると最大の離脱点になる**。
OAuth の同意画面は利用者にとって馴染みがなく、
「なぜこの権限が必要なのか」が分からないまま許可を求められると、そこで手が止まる。

そのため、認可を**画面で案内するウィザード**として提供することを要件とする（FR-109）。

| 段階 | 画面の内容 |
|---|---|
| 1 | これから何を許可するのかを、業務の言葉で説明する（例:「メールの下書きを作るために、Gmail を読む許可が必要です」） |
| 2 | 許可する範囲を一覧で示す。**使う機能の分だけ**を求め、不要なものは求めない |
| 3 | Google の同意画面へ遷移する。戻ってくることを事前に伝える |
| 4 | 結果を確認し、失敗した場合は原因と対処を平易に示す |
| 5 | 許可が済んだ機能を「使えるようになったこと」として提示する |

ウィザードの設計方針は以下のとおり。

| 設計方針 | 内容 |
|---|---|
| 段階的に求める | 最初にすべての権限を求めない。機能を使う時点で必要な分だけ追加で求める |
| 目的を明示する | 権限ごとに「何のために使うか」を 1 行で示す |
| 後から確認できる | 管理者ページと個人設定で、現在の許可状態と取り消し方法を示す |
| 失敗を前提にする | 管理者によるアプリの制限、ブラウザの設定など、失敗要因ごとに対処を案内する |
| 管理者向けの案内 | Workspace 管理者がアプリを事前承認する場合の手順も用意する |

**認可は 1 回で終わる作業ではない。**
新しい機能を使うたび、従業員が増えるたびに発生する。
ウィザードは初期設定専用ではなく、**常設の仕組み**として設計する。

### 22.3 定着支援

| 項目 | 内容 |
|---|---|
| 業務テンプレート | 業種別・規模別の初期エージェント構成を用意する |
| 秘書による案内 | 使っていない機能を秘書がさりげなく提案する |
| 教育 | 画面内ガイド、実行例の提示。マニュアルは最小限。仕組みは第6.10節 |
| 定着フォロー | 最初の 2 週間の利用状況を運営側で確認し、必要なら連絡する |
| 知識の初期投入 | 規程・価格表・過去議事録の登録を導入時に支援する |

**知識の初期投入が定着を左右する。**
組織知識が空のままだと秘書は「分かりません」としか答えられず、
最初の体験が悪くなる。導入時に最低限の規程を入れることを標準手順とする。

| 項目 | 決まり |
|---|---|
| 公開するもの | 本体のソース・仕様書・ADR・開発者マニュアル・ヘルプ・テスト。リポジトリ直下に `LICENSE` と `NOTICE` を置く |
| 公開しないもの | お客様に合わせる特殊な部分（お客様のための Skill・接続の宣言・設定）と、出してはならない言葉の一覧。公開しないリポジトリに置く。**ソースはお客様ごとに分けない**（フォークを作らない） |
| データ | **お客様のデータは決して出さない。** 患者・社員・取引先の情報、本番のデータベース、画面の写し、デバッグの記録は、リポジトリに入れない |
| 開発のデータ | 開発に使う AI も外部の AI として扱う（第16.3.7.1節）。電子カルテなどのつなぎは、お客様が用意する**ダミーデータのトライアルのアカウント**で作り、確かめる。本番の不具合は、個人の情報を含まない形で再現してから調べる |
| 公開の形 | **開発用のリポジトリが公開のリポジトリである**（`OESF/M2Office`。履歴を含む）。push したものはすぐ誰でも読めるため、**push の前に公開の前の点検を通す**。パートナーもこのリポジトリを読む。過去の履歴の扱いは三浦さんが決め、責任を持つ（2026-10-01） |
| 履歴を含まない書き出し | 配布物などに履歴を含めたくないときだけ、いまのコミットの中身を空のフォルダに書き出す（`npm run publish:export -- <空のフォルダ>`。点検を通してから書き出す） |
| 公開の前の点検 | `npm run publish:check`。**push の前**と書き出しの中で通す。秘密の値と鍵のファイル、見本でないメールアドレス、出してはならない言葉、本番の依存のライセンス（GPL・AGPL・LGPL・SSPL・BUSL・非商用・不明）を確かめ、1 つでもあれば push・書き出しをしない。**見るのは、追跡しているファイルと、まだ追跡していない新しいファイル（`.gitignore` の対象を除く）**（第 0.226.1 版。コミットの前に点検したとき、そのコミットで足すファイルを見落とし、出してはならない言葉を 1 つ push した） |
| 出してはならない言葉 | 客先・個人の取引先・法人の名前など。**言葉そのものはどこにも書かない。** 公開しないリポジトリに「文字数・SHA-256・FNV」だけを置き（`node scripts/check-publish.mjs --hash` で作る）、点検は当たったファイルの名前だけを出す |
| 見本の値 | メールは予約済みの名前（`*.example`・`example.*`・`*.test`）、会社名は架空の名前にする。実在の会社・人・お客様を見本にしない |
