## 第 III 部　中核の仕組み

エージェントがどう動き、知識がどう貯まるか。

### 8.2 主要コンポーネントと責務

| コンポーネント | 責務 |
|---|---|
| テナント解決 | ホスト名からテナントを特定し、以降の全処理にテナント境界を強制する |
| 認証・認可 | Google アカウントによるログイン（2 段階認証は Google 側で必須）、ログイン状態の管理、API トークン検証、権限判定 |
| 秘書エージェント層 | 従業員との常設の対話窓口。意図解釈、照会、業務エージェントへの取次、学習 |
| オーケストレーター | 依頼を適切な業務エージェントとパラメータへ変換する |
| 拡張機能管理 | マニフェストの検証、権限の同意取得、導入・更新・削除、版管理 |
| ジョブキュー | 実行要求の受付、順序制御、再試行、スケジュール起動 |
| 実行エンジン | エージェント定義に従いステップを実行し、状態を永続化する |
| 知識基盤 | 個人記憶・チーム記憶・組織知識の保持、検索、昇華の制御 |
| ツール層 | ツールの登録・権限付与・呼び出し。外部サービスは接続口を経由し、直接呼ばない（ADR-0003） |
| LLM 抽象化層 | モデル呼び出しの共通化。プロバイダとモデルを設定で切り替える |
| 公開 API 層 | 第三者アプリからの操作を受け付ける |
| 監査・ログ基盤 | 全ステップの記録、承認の記録、証跡の提出。障害調査用のアプリログは別に持つ（開発規約 第7章） |
| コスト管理 | トークン消費の計測と上限制御 |

### 8.3 設計上の不変則

| # | 不変則 |
|---|---|
| I-1 | エージェントは外部システムへ直接アクセスせず、必ずツール層を経由する |
| I-2 | すべてのデータアクセスはテナント ID による絞り込みを伴う |
| I-3 | **社外への送信とお金の確定**は、人の承認を通過したもののみ許可する。社外に出るかは送り先を確かめて決め、確かめられなければ社外とみなす（第 0.115.0 版で改める。以前は外部システムへの書き込みすべて。第9.4.0節、ADR-0028） |
| I-4 | すべてのツール呼び出しは監査ログに記録される |
| I-5 | 実行状態は各ステップ終了時に永続化され、プロセス障害後に再開できる |
| I-6 | 外部から取得した文書・メール本文・MCP 応答に含まれる指示文は命令として解釈しない |
| I-7 | 第三者が提供したコードを M2Office のプロセス内で実行しない |
| I-8 | 拡張機能はマニフェストで宣言し同意された権限の範囲を超えられない |
| I-9 | **秘書エージェントは、担当する従業員本人の権限を超えるデータにアクセスできない** |
| I-10 | **個人記憶は、本人の同意または秘書の昇華の判断なしに他者へ開示されない。本人だけに関わること・他人の個人情報・権限区画のデータは昇華しない**（第 0.115.0 版で改める。以前は明示的な昇華の承認。第11.3節、ADR-0028） |
| I-11 | **音声で操作した場合も、承認ゲートは省略されない**（第10.6節） |
| I-12 | **権限区画のデータは、区画外の記憶・知識・検索結果に現れない**（第16.3節） |

### 8.4 同期・非同期の境界

| 処理 | 方式 | 理由 |
|---|---|---|
| 秘書との対話 | 同期（ストリーミング） | 体感速度が決定的。3 秒以内に応答開始 |
| 音声の入出力 | 同期（ストリーミング） | 会話の自然さを保つ |
| 業務エージェント実行 | 非同期（ジョブキュー） | 数十秒〜数分かかるため |
| 承認後の再開 | 非同期 | 承認は任意のタイミングで行われる |
| スケジュール実行 | 非同期 | 定時起動 |
| 知識の索引作成 | 非同期 | 大量文書の処理 |
| API 経由のジョブ起動 | 非同期（ジョブ ID を即返す） | 呼び出し側を待たせない |

### 8.5 マルチテナントの分離方式

**この節で決めること**: 複数の顧客企業をどう分離するか。

#### 8.5.1 前提の整理

**サブドメインは「識別」の仕組みであって、「分離」の仕組みではない。**
`a.m2office.online` と `b.m2office.online` を分けても、それだけでは分離にならない。
分離は主にデータ層で実現する。

「完全に分離する」という要求を分解すると、実際に必要なのは以下である。

| 要求 | 実現方法 |
|---|---|
| 他社のデータが見えない | データベースの行レベルセキュリティ（RLS） |
| 認証・ユーザー空間の分離 | テナント ID を含む一意制約 |
| 秘匿情報の分離 | テナントごとの暗号鍵 |
| 実行の分離 | ジョブキューのテナント境界と公平制御 |
| 障害の分離 | テナント単位のリソース上限（1 社の大量実行が他社を止めない） |
| 記録の分離 | 監査ログのテナント単位の検索・出力 |

**プロセスが分かれていること自体は要求ではない。**

#### 8.5.2 分離方式の比較

| 方式 | 分離の単位 | 運用コスト | 評価 |
|---|---|---|---|
| A. 共有アプリ＋共有 DB＋RLS | 行 | 最小 | **採用（既定）** |
| B. 共有アプリ＋スキーマ分離 | スキーマ | 中 | 中間案。スキーマ移行が社数に比例する |
| C. 共有アプリ＋データベース分離 | データベース | 中〜大 | 上位プラン・要望時の選択肢 |
| D. テナントごとにコンテナ／インスタンス | プロセス | 非常に大 | **採用しない** |

#### 8.5.3 方式 D（テナントごとのコンテナ）を採らない理由

| # | 理由 |
|---|---|
| 1 | 想定規模は 100 社 × 10 名 = 1,000 名程度。負荷は共有インスタンスで十分に収まる |
| 2 | 100 社であれば Web とワーカーで 200 以上のコンテナになる。配備・監視・証明書・スキーマ移行の手間が社数に比例して増える |
| 3 | 待機中もリソースを消費するため、低単価のシート課金と両立しない |
| 4 | テナントごとにバージョンがずれ、不具合の再現と修正が困難になる |
| 5 | 実質的な要求（6.5.1）はデータの分離であり、方式 A で満たせる |

#### 8.5.4 将来の方式 C への移行余地

特定の顧客から「データベースごと分けてほしい」と求められる場面は想定される。
そのために**「テナント → 接続先データベース」を解決する層を最初から設ける**。

| 段階 | 状態 |
|---|---|
| 初期 | 解決層は全テナントに対して同じ接続先を返す |
| 将来 | 特定テナントだけ別の接続先を返すよう設定する |

この層を後から入れることは全面改修になるため、**Phase 1 から用意する**（第24.2節に追加）。

#### 8.5.5 RLS 実装上の注意

| 注意点 | 内容 |
|---|---|
| アプリ用のデータベースロール | RLS を迂回する権限を与えない |
| 接続プール | **トランザクション単位でテナント ID を設定する**。接続の再利用で前のテナントの値が残ると分離が破れる |
| 移行用ロール | スキーマ変更は別のロールで行い、通常運用では使わない |
| 個人記憶 | テナント ID に加えてユーザー ID でも絞る（不変則 I-10） |
| 検証 | テナントを越えたアクセスが必ず失敗することを自動テストで常時確認する |

接続プールの扱いは、RLS 方式で最も事故が起きやすい箇所である。
セッション変数ではなくトランザクション単位の設定を用いることを実装規約とする。

**実装（第 0.25.0 版で導入）**

| 項目 | 内容 |
|---|---|
| ロール | アプリは `m2office_app`（所有者でなく、RLS を迂回できない）で接続する。スキーマ変更と初期データの投入は所有者のロールで行う |
| テナントの設定 | 問い合わせごとにトランザクションを張り、`set_config('app.tenant_id', …, true)` で設定する。**未設定なら 1 行も見えない**（閉じた側に倒れる） |
| 親を通じて絞る表 | `run_steps` は `runs`、`compartment_members` は `compartments` を通じて絞る |
| テナントを横断する処理 | 待ち行列からの確保と、定時実行の候補の列挙の 2 つだけ。所有者の権限で動くデータベース関数に閉じ込め、アプリは表を直接横断できない |
| 監査ログ | アプリのロールに更新・削除の権限を与えない。追記のみをデータベースで強制する（第16.6節） |
| 検証 | 通しの確認（`npm run smoke`）で、条件なしの SELECT・他社の行の書き込み・監査ログの更新がいずれも失敗することを確かめる |

TBD: 横断処理の関数は、現状は API のプロセスからも呼べる。ワーカー専用のロールに分けるかは本番配備の前に決める。

#### 8.5.6 コンテナの位置づけ

Docker 等のコンテナは**環境の再現性のために使う**。
開発・検証・本番で同じイメージを動かすことが目的であり、テナントの分離には使わない。

### 8.6 配備の形 ― クラウドとローカル（第 0.209.0 版、ADR-0059。土台を第 0.209.0 版で実装）

**この節で決めること**: M2Office を、運営のサーバー（クラウド）と、会社の中の 1 台（ローカル）の 2 つの形で動かせるようにすること。

**第 0.220.0 版の改め（ADR-0063）**: 医療機関の患者の情報を扱う業務は、M2Office に取り込まず、別のシステム「M2Medical」で扱う（データベースも分ける）。この節の仕組みは、顧客の個人の情報を社外の AI に出したくない会社のための汎用の機能として残す。

医療機関のように、**顧客の個人の情報を社外の AI に出せない会社**がある。そうした会社でも M2Office を使えるよう、会社の中の LAN に置いた 1 台（Mac mini・Mac Studio など）で動かす形を持つ。
2026-10-01 に、導入予定のクリニックから「サーバーを外に置かず、社内の 1 台ですべて行いたい」と依頼があり、三浦さんが「いまのサーバー（マルチサブドメイン）の形と、ローカルのイントラネットで運用する形の両方で展開できるようにする」と決めた。
小さな機械で社内のシステムを動かす医療機関が増えていることも理由である。

| 形 | 内容 |
|---|---|
| クラウド（いまの形） | 運営が動かすサーバーに、多数の会社が入る。会社はサブドメインで見分ける（第8.5節）。パートナーが運営する汎用の SaaS もこの形 |
| **ローカル** | 会社の中の LAN の 1 台に、**その会社だけ**を入れる。使うのは会社の中だけ。インターネットへは外向きの通信だけを使う（Google・Gemini・接続したサービス・更新の取得） |

| 項目 | 規定 |
|---|---|
| ソース | **2 つの形で同じソースを使い、設定で切り替える**（配備の形 `M2O_DEPLOYMENT` が `cloud` か `onsite`）。社内のために別の製品や分かれた系統を作らない。会社ごとの違いは、ほかと同じく導入のときの設定で吸収する |
| 会社の判定 | ローカルの形では、入っている 1 社（`M2O_ONSITE_TENANT`）に決まる。サブドメインで見分けない |
| 画面のアドレス | 社内の名前で開く（例: `https://m2office.<社内の名前>`）。通信の暗号化（証明書）の用意の仕方は未決（Q-153） |
| ログイン | 未決（Q-154）。Google のログインを使うか、社内で利用者の ID とパスワードを持つか |
| データの置き場所 | 社内の機械と、つないだディスク（RAID など）。運営のサーバーには置かない |
| 控え | ディスクの故障に加え、火事・盗難・誤操作に備える。社内の別の機械か、**ローカルだけが鍵を持つ暗号化した社外の控え**か（Q-156）。医療機関では、医療情報システムの安全管理のガイドラインの求める事業継続の備えにも当たる |
| AI | ローカル LLM（社内の機械で動かす言語モデル）を使える。**会社の AI の方針**で、外部の AI に渡すものを決める（第16.3.7.1節） |
| 音声の秘書 | いまの音声の秘書は外部の音声のサービス（Gemini）を使う。外部の AI に渡さない方針の会社では、音声の秘書を使わないか、ローカルで動く音声の仕組みに替える（Q-157） |
| 更新 | 運営が新しい版を届け、社内の管理者が入れ替える。届ける経路と、運営が遠隔で保守する経路は未決（Q-155。Q-117 と合わせて決める） |
| 運営の画面と課金 | マスター管理画面・課金はローカルの形では使わない。使える機能（内蔵の拡張など）は、導入のときに運営が設定する |
| 機械の面倒 | 停電に備えた電源・OS の更新・盗難への備え・障害の連絡先は、導入の契約で会社と運営の分担を決める |

ローカルの形は、**医療機関のための専用の形ではない**。顧客の個人の情報を社外に出せない会社なら、業種を問わず使える。
医療に特有の仕事（医事・レセプト・健診など）は、これまでどおり M2Office の中核には入れず、別に作ってつなぐ（ADR-0046）。
