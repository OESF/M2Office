### 8.2 主要コンポーネントと責務

| コンポーネント | 責務 |

| 実行エンジン | エージェント定義に従いステップを実行し、状態を永続化する |

| 公開 API 層 | 第三者アプリからの操作を受け付ける |
| 監査・ログ基盤 | 全ステップの記録、承認の記録、証跡の提出。障害調査用のアプリログは別に持つ（開発規約 第7章） |
| コスト管理 | トークン消費の計測と上限制御 |

### 8.3 設計上の不変則

| # | 不変則 |
|---|---|
| I-1 | エージェントは外部システムへ直接アクセスせず、必ずツール層を経由する |
| I-2 | すべてのデータアクセスはテナント ID による絞り込みを伴う |
| I-3 | **社外への送信とお金の確定**は、人の承認を通過したもののみ許可する。社外に出るかは送り先を確かめて決め、確かめられなければ社外とみなす（第 0.115.0 版で改める。以前は外部システムへの書き込みすべて。第9.4.0節、ADR-0028） |
| I-4 | すべてのツール呼び出しは監査ログに記録される |
| I-5 | 実行状態は各ステップ終了時に永続化され、プロセス障害後に再開できる |
| I-6 | 外部から取得した文書・メール本文・MCP 応答に含まれる指示文は命令として解釈しない |
| I-7 | 第三者が提供したコードを M2Office のプロセス内で実行しない |
| I-8 | 拡張機能はマニフェストで宣言し同意された権限の範囲を超えられない |
| I-9 | **秘書エージェントは、担当する従業員本人の権限を超えるデータにアクセスできない** |
| I-10 | **個人記憶は、本人の同意または秘書の昇華の判断なしに他者へ開示されない。本人だけに関わること・他人の個人情報・権限区画のデータは昇華しない**（第 0.115.0 版で改める。以前は明示的な昇華の承認。第11.3節、ADR-0028） |
| I-11 | **音声で操作した場合も、承認ゲートは省略されない**（第10.6節） |
| I-12 | **権限区画のデータは、区画外の記憶・知識・検索結果に現れない**（第16.3節） |

### 8.4 同期・非同期の境界

| 処理 | 方式 | 理由 |
|---|---|---|
| 秘書との対話 | 同期（ストリーミング） | 体感速度が決定的。3 秒以内に応答開始 |
| 音声の入出力 | 同期（ストリーミング） | 会話の自然さを保つ |
| 業務エージェント実行 | 非同期（ジョブキュー） | 数十秒〜数分かかるため |
| 承認後の再開 | 非同期 | 承認は任意のタイミングで行われる |
| スケジュール実行 | 非同期 | 定時起動 |
| 知識の索引作成 | 非同期 | 大量文書の処理 |
| API 経由のジョブ起動 | 非同期（ジョブ ID を即返す） | 呼び出し側を待たせない |

### 8.5 マルチテナントの分離方式

**この節で決めること**: 複数の顧客企業をどう分離するか。

#### 8.5.1 前提の整理

**サブドメインは「識別」の仕組みであって、「分離」の仕組みではない。**
`a.m2office.online` と `b.m2office.online` を分けても、それだけでは分離にならない。
分離は主にデータ層で実現する。

「完全に分離する」という要求を分解すると、実際に必要なのは以下である。

| 要求 | 実現方法 |
|---|---|
| 他社のデータが見えない | データベースの行レベルセキュリティ（RLS） |
| 認証・ユーザー空間の分離 | テナント ID を含む一意制約 |
| 秘匿情報の分離 | テナントごとの暗号鍵 |
| 実行の分離 | ジョブキューのテナント境界と公平制御 |
| 障害の分離 | テナント単位のリソース上限（1 社の大量実行が他社を止めない） |
| 記録の分離 | 監査ログのテナント単位の検索・出力 |

**プロセスが分かれていること自体は要求ではない。**

#### 8.5.2 分離方式の比較

| 方式 | 分離の単位 | 運用コスト | 評価 |
|---|---|---|---|
| A. 共有アプリ＋共有 DB＋RLS | 行 | 最小 | **採用（既定）** |
| B. 共有アプリ＋スキーマ分離 | スキーマ | 中 | 中間案。スキーマ移行が社数に比例する |
| C. 共有アプリ＋データベース分離 | データベース | 中〜大 | 上位プラン・要望時の選択肢 |
| D. テナントごとにコンテナ／インスタンス | プロセス | 非常に大 | **採用しない** |

#### 8.5.3 方式 D（テナントごとのコンテナ）を採らない理由

| # | 理由 |
|---|---|
| 1 | 想定規模は 100 社 × 10 名 = 1,000 名程度。負荷は共有インスタンスで十分に収まる |
| 2 | 100 社であれば Web とワーカーで 200 以上のコンテナになる。配備・監視・証明書・スキーマ移行の手間が社数に比例して増える |
| 3 | 待機中もリソースを消費するため、低単価のシート課金と両立しない |
| 4 | テナントごとにバージョンがずれ、不具合の再現と修正が困難になる |
| 5 | 実質的な要求（6.5.1）はデータの分離であり、方式 A で満たせる |

#### 8.5.4 将来の方式 C への移行余地

特定の顧客から「データベースごと分けてほしい」と求められる場面は想定される。
そのために**「テナント → 接続先データベース」を解決する層を最初から設ける**。

| 段階 | 状態 |
|---|---|
| 初期 | 解決層は全テナントに対して同じ接続先を返す |
| 将来 | 特定テナントだけ別の接続先を返すよう設定する |

この層を後から入れることは全面改修になるため、**Phase 1 から用意する**（第24.2節に追加）。

#### 8.5.5 RLS 実装上の注意

| 注意点 | 内容 |
|---|---|
| アプリ用のデータベースロール | RLS を迂回する権限を与えない |
| 接続プール | **トランザクション単位でテナント ID を設定する**。接続の再利用で前のテナントの値が残ると分離が破れる |
| 移行用ロール | スキーマ変更は別のロールで行い、通常運用では使わない |
| 個人記憶 | テナント ID に加えてユーザー ID でも絞る（不変則 I-10） |
| 検証 | テナントを越えたアクセスが必ず失敗することを自動テストで常時確認する |

接続プールの扱いは、RLS 方式で最も事故が起きやすい箇所である。
セッション変数ではなくトランザクション単位の設定を用いることを実装規約とする。

**実装（第 0.25.0 版で導入）**

| 項目 | 内容 |
|---|---|
| ロール | アプリは `m2office_app`（所有者でなく、RLS を迂回できない）で接続する。スキーマ変更と初期データの投入は所有者のロールで行う |
| テナントの設定 | 問い合わせごとにトランザクションを張り、`set_config('app.tenant_id', …, true)` で設定する。**未設定なら 1 行も見えない**（閉じた側に倒れる） |
| 親を通じて絞る表 | `run_steps` は `runs`、`compartment_members` は `compartments` を通じて絞る |
| テナントを横断する処理 | 待ち行列からの確保と、定時実行の候補の列挙の 2 つだけ。所有者の権限で動くデータベース関数に閉じ込め、アプリは表を直接横断できない |
| 監査ログ | アプリのロールに更新・削除の権限を与えない。追記のみをデータベースで強制する（第16.6節） |
| 検証 | 通しの確認（`npm run smoke`）で、条件なしの SELECT・他社の行の書き込み・監査ログの更新がいずれも失敗することを確かめる |

TBD: 横断処理の関数は、現状は API のプロセスからも呼べる。ワーカー専用のロールに分けるかは本番配備の前に決める。

#### 8.5.6 コンテナの位置づけ

Docker 等のコンテナは**環境の再現性のために使う**。
開発・検証・本番で同じイメージを動かすことが目的であり、テナントの分離には使わない。

### 8.6 配備の形 ― クラウドとローカル（第 0.209.0 版、ADR-0059。土台を第 0.209.0 版で実装）

**この節で決めること**: M2Office を、運営のサーバー（クラウド）と、会社の中の 1 台（ローカル）の 2 つの形で動かせるようにすること。

**第 0.220.0 版の改め（ADR-0063）**: 医療機関の患者の情報を扱う業務は、M2Office に取り込まず、別のシステム「M2Medical」で扱う（データベースも分ける）。この節の仕組みは、顧客の個人の情報を社外の AI に出したくない会社のための汎用の機能として残す。

医療機関のように、**顧客の個人の情報を社外の AI に出せない会社**がある。そうした会社でも M2Office を使えるよう、会社の中の LAN に置いた 1 台（Mac mini・Mac Studio など）で動かす形を持つ。
2026-10-01 に、導入予定のクリニックから「サーバーを外に置かず、社内の 1 台ですべて行いたい」と依頼があり、三浦さんが「いまのサーバー（マルチサブドメイン）の形と、ローカルのイントラネットで運用する形の両方で展開できるようにする」と決めた。
小さな機械で社内のシステムを動かす医療機関が増えていることも理由である。

| 形 | 内容 |
|---|---|
| クラウド（いまの形） | 運営が動かすサーバーに、多数の会社が入る。会社はサブドメインで見分ける（第8.5節）。パートナーが運営する汎用の SaaS もこの形 |
| **ローカル** | 会社の中の LAN の 1 台に、**その会社だけ**を入れる。使うのは会社の中だけ。インターネットへは外向きの通信だけを使う（Google・Gemini・接続したサービス・更新の取得） |

| 項目 | 規定 |
|---|---|
| ソース | **2 つの形で同じソースを使い、設定で切り替える**（配備の形 `M2O_DEPLOYMENT` が `cloud` か `onsite`）。社内のために別の製品や分かれた系統を作らない。会社ごとの違いは、ほかと同じく導入のときの設定で吸収する |
| 会社の判定 | ローカルの形では、入っている 1 社（`M2O_ONSITE_TENANT`）に決まる。サブドメインで見分けない |
| 画面のアドレス | 社内の名前で開く（例: `https://m2office.<社内の名前>`）。通信の暗号化（証明書）の用意の仕方は第8.6.2節（案。Q-153） |
| ログイン | 第8.6.3節（案。Q-154） |
| データの置き場所 | 社内の機械と、つないだディスク（RAID など）。運営のサーバーには置かない |
| 控え | ディスクの故障に加え、火事・盗難・誤操作に備える。社内の別の機械か、**ローカルだけが鍵を持つ暗号化した社外の控え**か（第8.6.5節に案。Q-156）。医療機関では、医療情報システムの安全管理のガイドラインの求める事業継続の備えにも当たる |
| AI | ローカル LLM（社内の機械で動かす言語モデル）を使える。**会社の AI の方針**で、外部の AI に渡すものを決める（第16.3.7.1節） |
| 音声の秘書 | いまの音声の秘書は外部の音声のサービス（Gemini）を使う。外部の AI に渡さない方針の会社では、音声の秘書を使わないか、ローカルで動く音声の仕組みに替える（Q-157） |
| 更新 | 機械が取りに行き、夜に自動で入れる。遠隔の保守は会社が時間を限って開ける（第8.6.4節に案。Q-155） |
| 運営の画面と課金 | マスター管理画面・課金はローカルの形では使わない。使える機能（内蔵の拡張など）は、導入のときに運営が設定する。機械の様子は管理者ページの「機械」で見る（第8.6.7節に案） |
| 機械の面倒 | 停電に備えた電源・OS の更新・盗難への備え・障害の連絡先は、導入の契約で会社と運営の分担を決める |

ローカルの形は、**医療機関のための専用の形ではない**。顧客の個人の情報を社外に出せない会社なら、業種を問わず使える。
医療に特有の仕事（医事・レセプト・健診など）は、これまでどおり M2Office の中核には入れず、別に作ってつなぐ（ADR-0046）。

#### 8.6.1 パッケージにして配る（第 0.296.0 版。案、ADR-0077）

2026-10-07 に三浦さんが、導入予定のクリニックで M2Office と M2Medical を同時に入れ、「データをすべて社内に置き、Mac Studio の 1 台で動かしたい」という希望を受けて、**Mac mini・Mac Studio に入れられるパッケージ**にすることを求めた。ソースは同じものを使い、パッケージとして組み立てて配る。

| 項目 | 規定（案） |
|---|---|
| 形 | **Mac のネイティブ**（launchd で動かす。コンテナは使わない。仮想の機械がメモリーを取り、ローカル AI と取り合うため。ADR-0077）。**署名つきの `.pkg` は作らない**（第 0.304.0 版で改めた。下の「入れ方」） |
| ソース | 1 つのまま。タグから本番の組み立て（第20.4.5節）を作り、それを Mac 用にまとめる（`npm run package:onsite`）。ローカルの形のための分岐はソースに書かず、配備の形（`M2O_DEPLOYMENT=onsite`）で切り替える |
| 動かし方 | 起動時に launchd が動かす（利用者がログインしていなくても動く）。専用の利用者（例 `_m2office`）で動かし、管理者の権限で動かさない |
| 置き場所 | プログラムは決まった場所（例 `/Library/M2Office`）。データ（データベース・ファイル・控え・証明書）は導入のときに選んだディスク（RAID など）に置く |
| 秘密の値 | データベースの合言葉・セッションの鍵・預かった鍵を暗号化する鍵は、導入のときに機械の上で作る。運営は知らない。控えに入れるときは暗号化する（第8.6.5節） |
| ローカル AI | Mac の上で直に動かす（GPU と統合メモリーを使う）。OpenAI 互換の口（`LOCAL_LLM_URL`）でつなぐ。何を使い、どれだけの機械が要るかは Q-159 |
| 導入 | 運営（またはパートナー）が、導入の道具で、会社の名前・アドレス・データの置き場所・AI の方針を入れる。会社は 1 つ（`M2O_ONSITE_TENANT`）で、サブドメインは使わない |
| 前提 | ~~Apple の開発者の登録（パッケージの署名と公証）~~（第 0.304.0 版で不要にした）、更新に使うタグの署名の鍵（第8.6.4節） |

**入れ方（第 0.304.0 版。案）**: 2026-10-07 に三浦さんが、署名つきの `.pkg` は要らないと決めた。サーバーの仕組みで、Google の設定なども要るため、導入には必ず技術者（SIer）が関わる。当面、利用者が自分で入れることは無い。画面はすべて Web なので、Mac のアプリの形にまとめる必要も無い。

| 項目 | 規定（案） |
|---|---|
| 入れる人 | 技術者（運営かパートナーの SIer）。手順は技術者向けに書き、利用者向けの導入の画面は作らない |
| 取ってくる | 管理する置き場（例 `/Library/M2Office/app`）を作り、公開のリポジトリ（GitHub）から**リリースのタグ**を `git clone`（会社ごとの手直しが要れば fork から）する。決まった版に固定し、開発中の枝は使わない |
| 前提のソフト | Homebrew で入れる Node.js（版を指定）・PostgreSQL 17 と pgvector・Caddy（会社の DNS の事業者のつなぎを足したもの）。セットアップのスクリプトが、足りないものを示し、入れてよいかを尋ねてから入れる。同梱はしない |
| セットアップ | **対話式のシェルスクリプト**（`deploy/onsite/setup.sh`）を走らせ、聞かれたことに答える。会社の名前・アドレス（名前）・データの置き場所（RAID など）・控えの置き場所・DNS の事業者と鍵・証明書の連絡先・AI の方針とローカル AI の口とモデル・Gemini の鍵（使う会社だけ）・Google の OAuth クライアント（後から管理者ページでも入れられる） |
| スクリプトが行うこと | 前提のソフトの確かめ → 秘密の値を機械の上で作る（運営は知らない）→ 専用の利用者（`_m2office`）を作る → `m2office.env`・`Caddyfile` を雛形から作る → データベースと利用者を作り pgvector を有効にする → 依存を入れて本番の組み立て（`npm ci`・`npm run build:release`）→ データベースの移行 → launchd の設定を入れて起動 → 動きを確かめる（API・ワーカー・入口・証明書・ローカル AI）→ 結果と、紙の「戻すための控え」に書くことを出す |
| やり直し | 何度走らせてもよい（すでにあるものは作り直さず、答えを変えたところだけを直す）。答えは `m2office.env` に残し、次に走らせたときの既定にする |
| 外さない | 管理者の権限（`sudo`）は、専用の利用者と launchd の設定を入れるときだけ使う。動かすのは専用の利用者 |

**実装の段（第 0.300.0 版）**: Q-206〜Q-210 を案のとおり決めた（名前の形・Mac のネイティブ・夜の自動の更新・稼働の知らせは導入のときに決める・M2Medical とは名前で分けて入口は 1 つ）。段 1 として、本番の組み立て（第20.4.5節）と、入口・起動・環境変数の雛形（`deploy/onsite/`。Caddy の設定・launchd の 4 つ・環境変数）を作った。第 0.301.0 版で、管理者ページの「機械」と控え（第8.6.5節・第8.6.7節）を作った。**残り**: セットアップのスクリプト（第 0.304.0 版で `.pkg` に代えた。雛形を埋める・秘密の値を作る・専用の利用者を作る・前提のソフトを確かめる）、更新、遠隔の保守、稼働の知らせ、社外の控え、M2Medical との入口の取り決め

#### 8.6.2 アドレスと証明書（第 0.296.0 版。案、Q-153・Q-206）

**社内でも HTTPS にする。** ブラウザは、マイク（音声の秘書）とカメラ（在庫・会員証のバーコードの読み取り）を HTTPS か `localhost` でしか使わせない（第20.4.1節）。

**Google は OAuth の戻り先に IP アドレスを使わせない**（ホストは公開の接尾辞の一覧にあるドメインであること）。そのため、IP アドレスだけのアドレスでは、Google のログインと Gmail などの接続が動かない。

| 形 | 内容 | 使える会社 |
|---|---|---|
| **名前の形（標準）** | 会社のドメインの名前（例 `office.<会社のドメイン>`）を、機械の固定の IP に向ける（公開の DNS に書くのを標準とする。下の表）。証明書は公的なもの（Let's Encrypt）を、**DNS で所有を確かめる方式（DNS-01）**で取り、入口が自動で更新する。機械は社外から見えなくてよい | すべての会社。端末に何も入れなくてよい |
| IP の形（代わり） | 機械が自分の認証局を持ち、IP アドレスの証明書を出す。端末ごとにルートの証明書を入れる（入れ方のページを用意する） | Google を使わない会社だけ（M2Office の Google の機能は動かない） |

| 項目 | 規定（案） |
|---|---|
| 1 つのアドレス | ローカルの形は 1 社だけなので、アドレスは 1 つ。サブドメインで見分けない |
| DNS の自動の更新 | 会社の DNS の事業者に API があればそれを使う。無ければ `_acme-challenge` の名前だけを、運営が用意する確かめ専用の DNS に委ねる（運営に渡るのは名前だけで、データは渡らない） |
| 名前の向け方 | 名前を引くと、機械の**社内の IP アドレス**（例 `192.168.1.10`）が返るように DNS を設定する |
| どこに書くか | **公開の DNS に A レコードを書くのを標準とする**（第 0.296.1 版）。どの端末も同じように名前を引け、端末とルーターの設定が要らないため。社内の DNS（ルーター）だけに書く形は、DNS を自分で選ぶ端末（スマホのプライベート DNS・ブラウザの DNS over HTTPS）が名前を引けないため、標準にしない |
| 公開の DNS に書くときの注意 | 社内の IP と名前は外から見える（中身は見えず、社外からはつながらない）。ルーターによっては、公開の DNS が社内の IP を返すと答えを捨てる（DNS リバインディングの対策）。導入の前に会社のルーターで確かめ、捨てるならその名前だけを例外にする |
| IP の固定 | ルーターの DHCP の予約で、機械にいつも同じ IP を割り当てる |
| 証明書との関係 | 証明書の確かめは、公開の DNS に一時的に置く TXT レコード（`_acme-challenge`）で行う。A レコードとは別で、機械を社外に見せなくてよい |
| 社外から | 名前は社内の IP を返すため、社外（スマホのモバイル回線など）からは開けない。データを社内に閉じる目的に合う |
| 暗号化しない形 | 用意しない |
| 証明書の期限 | 管理者ページの「機械」に出し、更新に失敗したら会社の管理者に知らせる |

#### 8.6.3 ログイン（第 0.296.0 版。案、Q-154）

| 対象 | 規定（案） |
|---|---|
| 利用者 | Google Workspace の会社は、これまでどおり Google のログイン。戻り先は第8.6.2節の名前。会社の OAuth クライアントは「内部」（その会社の Workspace の人だけ）にするため、Google の審査は要らない |
| Google を使わない人 | M2Office の中の ID とパスワードの利用者は、段 1 では作らない。Google のアカウントを持たないスタッフは M2Medical を使う（ADR-0063）。要るようになったら決める |
| 機械の管理者 | インターネットや Google が止まっても機械の様子を見られるよう、機械の管理だけに使う社内の管理者（ID・合言葉・2 段階の確かめ）を 1 つ持つ。業務の画面には入れない |

#### 8.6.4 更新と遠隔の保守（第 0.296.0 版。案、Q-155・Q-208）

**社外から機械へ入る口を開けない。** 更新は機械が取りに行き、遠隔の保守は会社が開けたときだけ外向きにつなぐ。

| 項目 | 規定（案） |
|---|---|
| 届け方 | 機械が、公開のリポジトリ（fork から入れた会社はその fork）の**リリースのタグ**を 1 日 1 回見に行く（`git fetch --tags`）。開発中の枝は入れない。運営はリリースのタグに署名し、機械は署名を確かめてから入れる（`git verify-tag`。第 0.304.0 版で、運営が配る署名つきの束から改めた。案） |
| 入れる時 | **夜の決まった時間に自動で入れる**（人に判断を求めない。ADR-0028）。会社の管理者は「機械」で止める・日を延ばすことができる。権限が増える版（再同意が要る）は、入れた後に知らせる |
| 入れ方 | 控えを取る → 止める → 新しいタグに切り替えて組み立て直す（`npm ci`・`npm run build:release`）→ データベースの移行 → 動きを確かめる。確かめに失敗したら、前のタグと更新の前の控えに自動で戻し、会社の管理者と運営に知らせる。技術者は同じことを `deploy/onsite/update.sh` で手で行える |
| OS の更新 | macOS の更新は会社の管理者が行う（機械の面倒の分担。第8.6節）。M2Office の更新とは別 |
| 遠隔の保守 | 外向きのトンネル（Tailscale など）を使う。**ふだんは切っておき、会社の管理者が「機械」で時間を限って開ける**（既定 4 時間）。運営は自分で開けられない。開けた時刻・つないだ人・閉じた時刻を監査ログに残す |
| 保守で触れるもの | 機械の様子と道具だけ。業務のデータは見ない（第23.6節の代理アクセスと同じ統制）。同じ機械に M2Medical があるときは、保守の取り決めを M2Medical の側でも決める |

#### 8.6.5 控え（第 0.296.0 版で案、第 0.301.0 版で実装。Q-156）

| 項目 | 規定 |
|---|---|
| 取るもの | データベース（論理の控え）と、ファイルの置き場 |
| 頻度と置き場所 | 毎晩。**RAID とは別のディスク**（つないだ外付けのディスクか、社内の別の機械）に置く。RAID は故障に備えるもので、誤操作・ランサムウェア・盗難の備えにならないため |
| 残す数 | 毎日 14 回・毎週 8 回・毎月 12 回（案） |
| 社外の控え | 会社が選んだときだけ。**鍵を社内だけが持つ暗号化**をしてから送る。鍵は導入のときに紙の「戻すための控え」に印刷して会社に渡す。運営は鍵を持たない |
| 戻せるかの確かめ | 毎月 1 回、控えを別のデータベースに自動で戻し、開けることを確かめる。結果を「機械」に出し、失敗したら知らせる |
| ディスクの暗号化 | FileVault を勧める。停電の後の起動で合言葉が要るため、無停電の電源と、停電のときに自動で止める設定を合わせて用意する |

**実装（第 0.301.0 版）**: ワーカーが毎晩 2 時（日本時間）すぎに 1 回と、管理者の「今すぐ控えを取る」で取る（`packages/core/src/machine/backup.ts`）。データベースは `pg_dump` の独自の形式、ファイルは `rsync`（前の控えと同じファイルは共有して場所を取らない）。うまくいった控えだけを数えて、毎日 14 回・毎週 8 回・毎月 12 回を残す（同じ日は新しいものだけ）。月が変わって初めての控えの後に、別のデータベースへ戻して表と会社があることを確かめ、別のデータベースは消す。結果は控えの置き場の `status.json` に持ち、失敗は会社の管理者に通知（種類 `machine`）で知らせる。設定は `M2O_BACKUP_DIR`（置き場）・`M2O_PG_BIN`（同梱した PostgreSQL の道具）。開発ではデータベースのコンテナの中の道具を `M2O_PG_DOCKER` で使う。**残り**: 社外の控え（鍵を社内だけが持つ暗号化）と、紙の「戻すための控え」

#### 8.6.6 本番の組み立てとの関係

ローカルの形は、クラウドと同じ**本番の組み立て**（第20.4.5節）を、機械の上で作って動かす。違うのは、動かし方（クラウドはコンテナ、ローカルの形は launchd）と設定だけ（第 0.304.0 版で `.pkg` をやめた）。

#### 8.6.7 管理者ページの「機械」（第 0.296.0 版で案、第 0.301.0 版で実装）

ローカルの形だけ、管理者ページに「機械」を出す。**マスター管理画面の簡易版**にあたる。会社の作成・課金・サブドメインは無い。

| 見るもの | 内容 |
|---|---|
| 版と更新 | いまの版・次に入る版と予定・止める／延ばす・直近の更新の結果 |
| 控え | 最後の控えの時刻と結果・置き場所の空き・戻せるかの確かめの結果 |
| ディスク | データの置き場所の使用量と空き・RAID の状態 |
| 証明書 | 名前・期限・直近の更新 |
| 各部の動き | データベース・API・ワーカー・入口・ローカル AI（モデルと応答の速さ） |
| 遠隔の保守 | 開ける（時間を選ぶ）・閉じる・記録 |
| 稼働の知らせ | 運営に送っているか（第23.8.15節） |

見られるのは会社の管理者と、機械の管理者（第8.6.3節）。

**実装（第 0.301.0 版）**: 管理者ページの記録の「機械」（ローカルの形だけ。`/v1/me` の `deployment`）。各部の動き（データベースに 1 回問い合わせた速さ・ワーカーが 30 秒ごとに書く知らせ・入口の 443 番の証明書の期限・ローカル AI の `/models`）・データと控えのディスクの空き・最後の控えと戻せるかの確かめを出し、「今すぐ控えを取る」を置く（`GET /v1/admin/machine`・`POST /v1/admin/machine/backup`。クラウドの形では 404）。どの確かめも数秒で打ち切り、確かめられなかったことを理由と一緒に出す。**残り**: 版と更新・遠隔の保守・稼働の知らせ（第8.6.4節・第8.6.8節の段）

#### 8.6.8 運営への稼働の知らせ（第 0.296.0 版。案、Q-209）

保守の契約で運営が機械を見守るために、機械が運営のマスター管理画面へ**稼働の知らせ**を送れる。

| 項目 | 規定（案） |
|---|---|
| 中身 | 機械の番号・版・各部の動き・最後の控えの結果・ディスクの空き・証明書の期限。**件数と状態だけ。人の名前・業務の中身・会社の利用の数は送らない** |
| 頻度 | 1 時間に 1 回 |
| 入り切り | 導入のときに保守の契約に合わせて決める。会社の管理者が「機械」で切れる |
| 受ける側 | マスター管理画面の「ローカルの形の機械」（第23.8.15節） |

#### 8.6.9 M2Medical と同じ機械に置く（第 0.296.0 版。案、Q-210）

M2Medical は別のシステムで、データベースも分ける（ADR-0063）。同じ機械に置くときの決まりを案として置く。**M2Medical の側の決まりは M2Medical の仕様書で決める**（M2Office の側からは直さない）。

| 項目 | 規定（案） |
|---|---|
| アドレス | **同じ IP に 2 つの名前**（例 `office.<会社のドメイン>` と `medical.<会社のドメイン>`）を向ける。**ポートで分けない**（Cookie はポートで分かれず、ログインの Cookie が混ざるため） |
| 入口 | 入口（Caddy）は機械に 1 つ。両方の名前を受け、それぞれの API と画面に振り分ける。どちらのパッケージが入口を持つかは、共通の部品として取り決める（案: 先に入れたほうが入口を入れ、もう一方は設定を足すだけ） |
| データベース | 別々の PostgreSQL（データの置き場所・ポート・OS の利用者を分ける）。同じデータベースの別のスキーマにしない |
| ローカル AI | 1 つを両方で使う。機械のメモリーは、両方の利用と AI のモデルを合わせて見積もる（Q-159） |
| 控え | それぞれが取り、鍵も分ける |
| 共通の部品 | 入口・更新・控え・「機械」の画面は、M2Office で作って M2Medical に写す候補（`M2Medical/docs/shared-from-m2office.md` に記録する） |
