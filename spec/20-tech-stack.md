## 20. 技術スタック

### 20.1 構成案

| 層 | 有力案 | 理由 |
|---|---|---|
| LLM | **Gemini（既定）** | Google プラットフォームへの一本化（原則 p8）。認証・契約・データ所在地を統一できる |
| LLM 呼び出し経路 | **Gemini API を直接利用** | 最新の機能に追随しやすい。抽象化層を挟むため経路の変更も可能 |
| 音声対話 | **Gemini Live（秘書のみ）** | 双方向音声を直接扱え、遅延が小さい（第10.5節） |
| エージェント実行 | 自製の実行エンジン | 承認による中断・再開が要件のため、状態の永続化を自前で持つ |
| 言語 | TypeScript（画面・API・ワーカー共通） | 小規模チームでの保守性。型をパッケージ間で共有できる |
| 実行環境 | Node.js（LTS 版） | |
| **画面** | **Vite + React（SPA）** | **画面が API を経由する以外に動けないため、第13.1節 A-2 を構造的に担保できる**（ADR-0001） |
| **API** | **Hono** | TypeScript の型推論が強く、画面との型共有が容易。概念が少なく学習コストが低い（ADR-0002） |
| API 仕様 | OpenAPI（実装から生成） | 外部公開を前提とするため |
| ワーカー | Node.js の常駐プロセス | Web と実行を分離する。承認による中断・再開のため常駐が必須 |
| ジョブキュー | PostgreSQL ベースのキュー | この規模ではミドルウェアを増やさない |
| データベース | PostgreSQL（RLS） + 全文検索 + ベクトル拡張 | テナント分離と検索を 1 つで賄う |
| ストレージ | オブジェクトストレージ（国内リージョン） | 成果物・証憑の保存。開発ではローカルのディレクトリで代用する |
| 文書形式 | exceljs・pdf.js・docx | Excel・PDF・Word の読み書き。解析を自作しない（ADR-0004） |
| 拡張機能のファイル | JSZip | `.m2ext`（ZIP）の作成と展開。記憶の上だけで展開する（ADR-0005） |
| MCP の接続 | 自作の最小のクライアント | ツールの一覧と呼び出しだけ。stdio を持たない（ADR-0005） |
| アプリログ | 自前の軽量なロガー（標準出力へ JSON） | 必要な機能が短く書けるため、パッケージを増やさない（開発規約 第7章） |
| インフラ | **案（第 0.427.0 版）: Xserver の VPS（Ubuntu）、入口に Cloudflare**（Q-10・第20.4.6節） | 日本国内に置けることを条件とする。運用は提携先の技術者が手順書に沿って受け持つ。使うサービスは第20.4.6節（Q-38） |
| DNS・ドメイン | **案（第 0.427.0 版）: ドメインの登録はお名前.com、DNS は Cloudflare** | 証明書も Cloudflare が持つ（第20.4.6節） |

### 20.2 LLM 抽象化層

**Gemini を既定としつつ、プロバイダを差し替えられる構造を必須とする。**

| 理由 | 内容 |
|---|---|
| 1 | モデルの性能・価格は短期間で変動する。特定モデルに固定すると追随できない |
| 2 | 管理画面から認証情報を設定する仕様（FR-403）は、そもそも切り替えを前提とする |
| 3 | 用途によって最適なモデルが異なる（音声対話と長文処理は要求が違う） |
| 4 | 顧客が自社の契約を使いたい場合に対応できる |

抽象化層が吸収するもの:

| 項目 | 内容 |
|---|---|
| 呼び出し形式 | プロバイダごとの API 差異 |
| モデル階層 | 「高速」「標準」「高性能」「調査」「音声」の 5 役割で扱い、実モデル名は設定値とする |
| ツール呼び出し | 関数呼び出しの形式差 |
| ストリーミング | 逐次応答の扱い |
| トークン計測 | 消費量とコストの算出 |
| 失敗時の切替 | 障害時に別モデルへ退避する（第 0.254.0 版で実装。第20.2.5節） |

**モデル名を仕様書と実装に直書きしない。**
「高速モデル」「標準モデル」という役割で参照し、実際のモデル名は管理画面の設定値として持つ。
モデルの更新に仕様書の改訂もコード変更も不要にする。

| 役割 | 用途 | 選定基準 |
|---|---|---|
| 高速モデル | 秘書の意図解釈、分類、振り分け | 低遅延・低コスト |
| 標準モデル | 業務エージェントの実行、文書生成 | 品質とコストの均衡 |
| 高性能モデル | 複雑な計画、長文の分析 | 必要な場面のみ |

#### 20.2.1 乗り換えの対象とする提供者

既定は Gemini とするが、以下への乗り換えが設定変更で済むことを設計目標とする。

| 提供者 | 備考 |
|---|---|
| Google Gemini | 既定 |
| Anthropic Claude | 独自のインターフェース。アダプタで吸収する |
| OpenAI | 多くの提供者が互換形式を採るため、共通形式の候補になる |
| xAI Grok | 同上 |
| Alibaba Qwen | 同上。自社環境での実行も選択肢になる |

**実装方針（決定）**: **共通形式は OpenAI 互換を土台とする。**

理由は、多くの提供者が OpenAI 互換の呼び出し形式を併せて提供しており、
互換形式に寄せておけば、乗り換えのたびにアダプタを書き下ろす必要がないためである。

| 層 | 内容 |
|---|---|
| M2Office の内部インターフェース | 自前で定義する。提供者に依存しない |
| 既定のアダプタ | OpenAI 互換形式。多くの提供者をこれ 1 つで扱う |
| 個別のアダプタ | 互換形式で表現できない提供者・機能のみ用意する |

**要確認**: 各提供者が互換形式でどこまで対応しているかは差がある。
特にツール呼び出し、構造化出力、ストリーミングの扱いは実装前に確認する。
Gemini を既定とするため、まず Gemini の互換対応の範囲を確認してから着手する。

#### 20.2.2 既定のモデルの選び方

**安いほうから選ぶ。難しくない仕事に高いモデルを使わない。**

モデル名は設定値であり（第20.2節）、会社ごとに管理者ページで上書きできる。
ここで決めるのは**上書きが無いときの既定**である。

| 役割 | 既定 | 入力/出力（$/100 万トークン） | 使うところ |
|---|---|---|---|
| 高速 | `gemini-3.5-flash-lite` | 0.30 / 2.50 | 秘書の層 2 の振り分け、記憶の要約と事実の取り出し、言い換え |
| 標準 | `gemini-3.5-flash-lite` | 0.30 / 2.50 | 業務のステップ、秘書の層 3 の対話、文字の読み取り |
| 高性能 | `gemini-3.8-flash` | 0.75 / 3.75 | SKILL.md の `effort` が `xhigh`・`max` の業務 |
| 調査 | 標準と同じ | — | Web の調査（`MODEL_RESEARCH` で変えられる） |
| 音声 | `gemini-3.1-flash-live-preview` | — | 秘書の音声（Gemini Live） |

**「そのときの最新」を指す別名（`…-latest`）を既定にしない。**
この別名は新しい版が出るたび中身が入れ替わり、**入れ替わった先が試験中の版や高い版である**
ことがある（Google の説明。2026-09-24 に確認）。費用も品質も、こちらが決めていない値に変わる。
設定されていたら、起動のときに知らせる。

| 判断 | 理由 |
|---|---|
| 版を固定する | 費用と品質を、こちらが決めた値に保つ。上げるのは確かめてから |
| まず軽いモデルで試す | 業務のステップも秘書の対話も、まず安いほうで動かす。**足りないと分かってから上げる** |
| 高性能は使うところを決めてから | 使っていない役割に高いモデルを既定で置かない |

**既定を変えるときは、実地の確認（`docs/acceptance-test.md`）を通すこと。**
安いモデルは、ツールの呼び出しの形を崩したり、根拠づけ（第10.9.4.1節）を守らなかったりしうる。
値段だけで決めない。

**`gemini-3.5-flash-lite` は、この確認を通している**（2026-09-24、20 問すべて）。
書いてあることを出典つきで答え、書いていない 3 問では作り話をしなかった。
**次に既定を変えるときも、同じ 20 問を通すこと。**

**値段の表は実装に持ち、出どころと確認日を書く**（`packages/core/src/llm/models.ts`）。
表に無いモデルは、費用を少なく見せないよう最も高い単価で見積もる。

#### 20.2.4 推論が使えない会社では動かさない（第 0.119.0 版。ADR-0030）

**M2Office は推論（Gemini）があって初めて成り立つ。推論が使えない会社では、秘書も業務も動かさない。**
以前は鍵が無いと見本の応答（スタブ）で動いたように見せていたが、評価も判断も誤らせるためやめた（2026-09-26 に三浦さんが指摘）。

| 項目 | 規定 |
|---|---|
| 推論が使える | 会社の鍵（BYOK）か、運営の鍵（`LLM_PROVIDER=gemini` と `GEMINI_API_KEY`）がある |
| 使えないときの秘書 | 何を聞かれても「Gemini の接続が設定されていません。管理者ページの『接続』で設定してください」とだけ答える |
| 使えないときの業務 | 始めない（依頼を受け付けず、同じ文を返す）。定時実行も同じ理由で失敗にする |
| 使えないときの音声・調べもの | 始めない・調べない。同じ文を返す |
| 見本の応答（スタブ） | **M2Office 自身の自動テストの中だけ**で使う（`LLM_PROVIDER=stub`）。利用者の画面・利用者向けの文書・拡張機能の書き方には出さない |
| 開発 | 開発の見本の会社も、開発者の鍵か会社の鍵で本物の推論を使う |

#### 20.2.5 失敗したときに別のモデルへ退避する（第 0.254.0 版）

**推論が一時的に失敗したら、同じ鍵のまま別のモデルで呼び直す。** Gemini はモデルごとに混み具合と障害が分かれており、
1 つのモデルが混んでいるだけで秘書も業務も止まるのを避ける（2026-10-04 に三浦さんが次の作業として選んだ）。

| 項目 | 規定 |
|---|---|
| 退避する失敗 | 混雑・上限（429）、時間切れ（408）、提供者の障害（500・502・503・504）、届かない（通信の失敗）、モデルが無い（404。廃止されたときなど） |
| 退避しない失敗 | 依頼の形の誤り（400）、鍵の誤り・権限が無い（401・403）。別のモデルでも同じく失敗するため |
| 退避先の順 | 会社の設定（または `MODEL_FALLBACK`）に退避先のモデルがあればそれを先に、次に設定にあるほかの役割のモデル（高性能・標準・高速の順。同じ名前は 1 度だけ）。**呼ぶのは最初を含めて 3 回まで** |
| 新しいモデル名を持ち込まない | 退避先は、設定にあるモデルだけから選ぶ（第20.2.2節。確かめていないモデルを黙って使わない） |
| 越えない境界 | **同じ提供者・同じ鍵の中だけで退避する。** 会社の鍵から運営の鍵へ、**ローカル AI から社外の AI へは退避しない**（第16.3.7.1節。社外に出さない約束を破らないため） |
| 費用 | 実際に答えたモデルの単価で数える（応答のモデル名を使う） |
| 記録 | 退避したことを、元のモデル・退避先・失敗の種類だけでアプリのログに残す（依頼の中身は残さない） |
| 範囲 | 文章の推論と、画像からの読み取り（文字の読み取り・名刺の項目）。音声（Gemini Live）と画像を作ることは退避しない |

#### 20.2.3 抽象化が及ばない範囲

| 範囲 | 扱い |
|---|---|
| テキストの生成・ツール呼び出し | 抽象化する。乗り換え可能 |
| **音声対話（Gemini Live）** | **抽象化しない。Gemini 固有とする**（第10.5.4節） |
| 埋め込み（ベクトル生成） | 抽象化する。ただし乗り換え時は索引の再作成が必要 |

**埋め込みの乗り換えには索引の作り直しが伴う。**
提供者を変えるとベクトルの空間が変わるため、既存の索引は使えなくなる。
テナントの知識量によっては時間のかかる処理になるので、移行手順を用意しておく。

### 20.4 環境構成

**この節で決めること**: ローカル開発から本番まで、どう構成するか。

#### 20.4.1 ローカル開発環境

| 要素 | 構成 |
|---|---|
| 実行 | コンテナで一式を起動（アプリ、ワーカー、PostgreSQL、オブジェクトストレージ互換） |
| サブドメイン | ワイルドカードで解決できる開発用ドメインを使う。任意のサブドメインが `127.0.0.1` に解決されるため、`a.<開発用ドメイン>:3000` のようにテナントを切り替えて検証できる |
| Google 連携 | 開発専用の OAuth クライアントを用意し、リダイレクト先をローカルに向ける |
| LLM | 開発用の鍵と低コストのモデル階層。上限を厳しく設定する |
| データ | 複数テナントの擬似データを投入するスクリプトを用意し、**テナント越えのアクセスが失敗することを日常的に確認できる状態にする** |

**開発の初期からテナントを 2 つ以上作って動かす。**
1 テナントだけで開発すると、分離の不備に気づけないまま進む。

**Google の準備が整う前も、全体を動かせるようにする**（ADR-0003）。**LLM（Gemini）は例外で、代わりを置かない**（第 0.119.0 版。第20.2.4節、ADR-0030）。

| 未準備のもの | 代わりに使うもの | 設定 |
|---|---|---|
| Google の OAuth クライアント（B-2） | ダミーデータを返す接続口 | `CONNECTOR_MODE=mock` |
| 同上（通しの確認の会社） | 本物の会社と同じサーバーで、決まった会社だけ見本の接続口を使う（第14.3.4節、ADR-0022） | `CONNECTOR_MODE=google` と `CONNECTOR_MOCK_TENANTS` |
| 同上（ログイン） | 利用者を選ぶだけの開発用ログイン | `AUTH_DEV_LOGIN=true` |
| Gemini の鍵（B-3） | **代わりは無い。** 開発者の鍵（`GEMINI_API_KEY`）か、会社の鍵で動かす（第20.2.4節、ADR-0030）。推論を行わないスタブは自動テスト専用 | `LLM_PROVIDER=gemini`（テストだけ `stub`） |

開発用ログインは `NODE_ENV=production` で有効にすると**起動を拒否する**。
ダミーの値は画面・秘書の応答・ツールの戻り値のすべてで、ダミーであることを示す。

##### 音声を試すには、開発でも HTTPS が要る

**ブラウザは、安全な文脈（HTTPS か `localhost`）でしかマイクを使わせない。**
`http://<サブドメイン>.lvh.me` は `localhost` ではないため、
マイクの口（`navigator.mediaDevices`）が**そもそも無い**。
許可を尋ねる画面も出ないため、**利用者がブラウザの設定で直すことはできない**。

| 項目 | 規定 |
|---|---|
| 開発での音声 | 開発用の証明書を作り、`https://<サブドメイン>.lvh.me` で開く |
| 証明書 | ブラウザが信頼するもの（`mkcert`）を優先する。無ければ自己署名とし、警告を 1 度だけ手で通す |
| 画面の伝え方 | **「ブラウザの設定で許可してください」と言わない。** 直せないことを指示することになる。`https` か `localhost` で開くよう伝える |
| 許可されなかったとき | そのときだけ「許可してください」と伝える。機器が無い・ほかのアプリが使っている場合は、それぞれの理由を伝える |

##### デバッグモード（第 0.167.0 版）

**開発のときに、何が起きたかを正確に追えるようにする。** 音声で頼んだ連絡先に未読メールの件数が出た（2026-09-29）とき、音声の対話は会話ログに残らず、秘書が何を受け取りどう振り分けたかを追えなかった。三浦さんが AI に正確に報告できるよう、`.env` の指定で記録を見られるようにした。

| 項目 | 規定 |
|---|---|
| 入れ方 | `M2O_DEBUG=true`。開発用の足場で、`NODE_ENV=production` で有効にすると**起動を拒否する**（開発用ログインと同じ） |
| 印 | どの画面（パソコン・管理者ページ・スマホ用のページ・掛け通しの画面）でも、上の帯の真ん中に赤い「Debug mode」を重ねる。押すと右から記録を開く。左のメニューの「自分の状況」にも「デバッグ」を出す |
| サーバーの記録 | **音声**: 聞き取った本人の文と秘書の発話（発話ごと）、音声の秘書がツール（`handle_request`・`show_on_canvas`）に渡した文と返した答え、音声の秘書へ伝えた指示（第一声・調べものの結果）、断り書き、対話の開始と終わり。**秘書**: 文字の依頼と答え（層・時間）、振り分けの経過（定型の答えの名前・業務への取次とその理由・在庫の答えなど）、画面へ渡した調べものの結果。**エラー**: 本人の呼び出しのうち失敗したもの（方法・パス・番号・応答の本文） |
| 画面の記録 | その画面から呼んだ API の直近 100 件（方法・パス・番号・時間・送った本文・応答の本文）。数秒ごとに読み直す口のうまくいった読み出しは残さない。スマホ用のページでは、読み取った値で品目を引いた呼び出しもここに出る |
| 持ち方 | サーバーの記録は API のプロセスのメモリーに、利用者ごとに直近 500 件。画面の記録はその画面のメモリーに。**データベースにも端末にも書かない**（音声の中身には人の名前が入りうるため、残す期間の決まりを新しく作らない）。再起動・再読み込みで消える |
| 見られる人 | 本人の記録だけ。管理者でもほかの人の記録は見られない |
| 写す | 「写す」で、見ている記録を時刻順の文字にして写す（AI への報告に貼るため） |

#### 20.4.2 本番環境

| 要素 | 構成 |
|---|---|
| DNS | `*.m2office.online` のワイルドカードレコード。**案（第 0.427.0 版）: Cloudflare**（第20.4.6節） |
| 証明書 | ワイルドカード証明書。**案（第 0.427.0 版）: Cloudflare の証明書**（自分で取る・更新する仕組みが要らない。第20.4.6節） |
| 配備 | 単一のアプリケーション。テナントが増えてもインスタンス数は負荷にのみ依存する |
| ワーカー | Web とは別に増減できるようにする |
| データベース | 単一の PostgreSQL。RLS でテナントを分離（第8.5節） |
| ストレージ | オブジェクトストレージ。テナントごとに保存先を分ける。**案（第 0.427.0 版）: 当面は機械のディスク**に置き、社外の控えを取る（第20.4.6節） |
| リージョン | 日本国内（**案（第 0.427.0 版）: Xserver の VPS の国内の拠点**。第20.4.6節） |

**テナントを追加しても配備作業は発生しない。**
テナントの追加はデータベースへのレコード作成とサブドメインの有効化のみで完了する。
これが方式 A を採る最大の実務上の利点である。

#### 20.4.3 サブドメインの運用

| 項目 | 方針 |
|---|---|
| 予約語 | `www` `api` `app` `admin` `ops` `signup` `mail` `docs` `status` `help` など運営が使う名前は払い出さない。`ops` は運営の画面、`signup` は申し込みの口が使う（第23.8.2節・第23.3.1節、Q-60） |
| 命名規則 | 英小文字・数字・ハイフン。先頭と末尾のハイフンは不可。最小 3 文字 |
| 重複 | 先着順 |
| 解約後 | 一定期間は再利用を禁止する。**別の会社に同じサブドメインを渡すと、旧 URL からの誤送信・誤アクセスが起きる** |
| 変更 | 原則不可。やむを得ない場合は旧サブドメインからの転送期間を設ける |
| 検証 | 申込時に予約語・規則・重複を検査する。申し込みのページで、入れるそばから空きを確かめる（第23.3.1節） |

#### 20.4.4 環境の分離

| 環境 | 用途 | 備考 |
|---|---|---|
| ローカル | 個々の開発 | 擬似データのみ。**当面はここで機能を進める** |
| 仮稼働 | 通しで動かして確かめる | 事業者を決める前の暫定。**エックスサーバーの VPS の空きを使うことを検討中**（第 0.68.0 版時点で未確定） |
| 検証 | 結合確認、拡張機能の審査 | 本番データは置かない |
| サンドボックス | 開発者向けの公開環境（第13.5節） | 本番と分離 |
| 本番 | 顧客利用 | **案（第 0.427.0 版）: Xserver の VPS と Cloudflare**（第20.4.6節） |

**検証環境と本番環境で同じイメージを使う。**
差異は設定値のみとし、環境固有のコードを書かない。

**仮稼働は本番ではない。**
顧客のデータを置かず、擬似データだけで動かす。
仮稼働の環境で動いたことは、本番の事業者で動くことを意味しない。
事業者ごとに使えるマネージドサービスと拡張機能が違うため、
本番の構成は事業者を決めてから（Q-10・Q-38）改めて確かめる。

#### 20.4.5 本番の組み立て（第 0.296.0 版で案、第 0.300.0 版で実装。ADR-0077）

第 0.295.0 版までは本番の組み立てが無かった。API とワーカーは開発用の実行（`tsx`）で動き、画面は開発サーバー（Vite）が出している。クラウドの本番とローカルの形のパッケージ（第8.6.1節）の両方に先立って、共通の本番の組み立てを作る。

| 項目 | 規定 |
|---|---|
| 組み立て | `npm run build:release` で、API・ワーカーを実行用の JavaScript に、画面を静的なファイルにする。開発用の道具（`tsx`・Vite の開発サーバー）を本番で動かさない |
| 入口 | 入口（Caddy）が画面の静的なファイルを出し、`/v1` を API に渡し、TLS を受け持つ。クラウドでは事業者の入口に置き換えてもよい |
| 包み方 | クラウドはコンテナのイメージ、ローカルの形は Mac の `.pkg`。中身は同じ組み立て |
| 版 | 組み立てに版を埋め込む（第6.1.1.1節）。リリースのタグからだけ作る |
| 設定 | 違いは設定（環境変数）だけ。開発用の足場（開発用ログイン・デバッグモード・見本の接続口）は `NODE_ENV=production` で起動を拒否する（第20.4.1節のとおり） |
| 確かめ | 組み立てたものを起動し、通しの確認（`npm run smoke`）を通してから出す |

**実装（第 0.300.0 版）**: `npm run build:release`（`scripts/build-release.mjs`）が `dist-release/` に組み立てる。API とワーカーは esbuild でそれぞれ 1 つのファイル（`server/api.js`・`server/worker.js`）にまとめ、社内のパッケージ（`@m2office/*`）は中に入れ、外のパッケージ（12 個）は入れずに、いま入っている版に固定した `package.json` を置く（`--install` で `node_modules` に入れる）。画面（`web/`）・ヘルプとマニュアル・フォント・拡張機能・データベースの移行・移行と会社の作成の道具を写す。実行中に読むファイルの置き場所の根は、ソースからの相対の道をやめ、環境変数 `M2O_APP_ROOT`（無ければリポジトリの根）で決める（`packages/core/src/app-root.ts`）。組み立てた API とワーカーで通しの確認を通した。入口（Caddy）は第8.6.2節の雛形（`deploy/onsite/`）

#### 20.4.6 クラウドの形の配備 ― Xserver の VPS と Cloudflare（第 0.427.0 版で案、第 0.428.0 版で機械の大きさと紹介のページを足し、第 0.430.0 版で 2 GB の機械に合わせた案。Q-10・Q-38・Q-255〜Q-257、ADR-0106・ADR-0107）

2026-10-23 に三浦さんが、クラウドの形を **Xserver の VPS（Ubuntu）に置き、入口に Cloudflare を置く**形で動かすと決め、仕様を求めた。
GCP（Cloud Run と Cloud SQL）と比べ、手元に使っていない VPS が 1 台あること、**運用は提携先の技術者が手順書に沿って 24 時間受け持つ**ことが理由である。
VPS は OS から上を自分たちで固めて守る必要があるため、この節は**手順に落とせるところまで決め、提携先が手順書どおりに動けば安全が保たれる**ことを目的にする。

**決めること**: 入口（Cloudflare）・機械の固め方・プロセスの動かし方・待ち受け先・更新・控え・見張り・役割の分担・提携先の権限。

##### 全体の形

```
見込みの客（紹介のページ）            利用者のブラウザ・外部のアプリ（M2Medical など）
   │ m2office.online・www                 │ *.m2office.online・signup・ops
Cloudflare（DNS・TLS・攻撃の防御（DDoS・WAF）・回数の制限・運営の画面の手前の確かめ）
   │ 紹介のページは Cloudflare の上の EmDash（VPS には来ない。第23.3.1節）
   │ Cloudflare Tunnel（機械から Cloudflare へ外向きにつなぐ。機械は受け口を開けない）
Xserver の VPS（Ubuntu 24.04 LTS）
   cloudflared ─▶ Caddy（127.0.0.1）─▶ API（127.0.0.1:3101）・運営の API（127.0.0.1:3102）
                                        画面の静的なファイル
   ワーカー（受け口なし）
   PostgreSQL 17 と pgvector（127.0.0.1 だけ）
   ファイルの置き場（機械のディスク）
   │ 外向きだけ: Google・Gemini・接続したサービス・GitHub（更新）・社外の控えの置き場・Tailscale（保守）
```

**機械は、インターネットからの受け口を 1 つも開けない。** 利用者の通信は Cloudflare Tunnel（機械から外向きにつなぐ）で、保守の SSH は Tailscale（同じく外向き）で入る。Xserver のパケットフィルターと機械のファイアウォールは、入ってくる通信をすべて断る。

##### 入口（Cloudflare）

| 項目 | 規定（案） |
|---|---|
| DNS | `m2office.online` のネームサーバーを Cloudflare に移す（お名前.com はドメインの登録だけに使う）。`*.m2office.online`（会社のサブドメインと `ops`）は Cloudflare Tunnel への CNAME（Cloudflare を通す）にする。機械の IP アドレスを DNS に書かない（IP を知られなければ、Cloudflare を回って直接攻撃されない） |
| 証明書 | 利用者との間は Cloudflare の証明書（無料の範囲で `m2office.online` と `*.m2office.online` を覆う）。Cloudflare と機械の間はトンネルの中で暗号化される。第20.4.2節の「DNS で所有を確かめてワイルドカードの証明書を取る」仕組みは、この形では要らない |
| トンネル | `cloudflared` を機械で常駐させ、`*.m2office.online` と `m2office.online` を `http://127.0.0.1:<Caddy のポート>` に送る（設定のファイルで管理する。ワイルドカードの規則を使う。最後に「どれにも当たらなければ 404」の規則を置く）。トンネルの鍵（資格情報のファイル）は機械の管理者だけが読める |
| TLS の設定 | 最低の版を TLS 1.2、HSTS を有効、HTTP は HTTPS へ転送。Cloudflare の「常に HTTPS」を入れる |
| 攻撃の防御 | DDoS の防御（どのプランにもある）。**WAF は有料のプラン（Pro）の管理された規則（OWASP など）を入れる**。回数の制限は Cloudflare（ログイン・外部のアプリの道に粗い上限）とアプリ（細かい上限。いまのまま）の二重にする |
| キャッシュ | 画面の静的なファイル（`/assets/*`。名前に版の印が入る）だけをキャッシュする。`/v1/*` と `index.html` はキャッシュしない（規則で明示する） |
| 長くつなぐ通信 | WebSocket（音声の秘書）と SSE（ダッシュボード・サイネージ）はトンネルと Cloudflare をそのまま通る。**Cloudflare は何も流れない接続を切ることがある**ため、SSE は 30 秒ごとに空のコメントを送り、WebSocket は 30 秒ごとに確かめの合図を送る（いまの作りを確かめ、足りなければ足す） |
| 送れる大きさ | **Cloudflare（Free・Pro）は 1 回の要求の本文を 100 MB までしか通さない**。いま 100 MB を超えて受けるのは、録音のファイル（200 MB まで）とサイネージの動画（200 MB まで）の 2 つ（Q-256） |
| 利用者のアドレス | API は回数の制限と不正の見張り（第16.8節）に相手のアドレスを使う。トンネルを通ると相手は `127.0.0.1` に見えるため、**Caddy が Cloudflare の見出し `CF-Connecting-IP` を相手のアドレスとして読み、`X-Forwarded-For` を置き換えて API に渡す**（Caddy の `trusted_proxies` は 127.0.0.1 だけ。受け口が無いので、ほかから偽った見出しは届かない） |
| 運営の画面 | `ops.m2office.online` の手前に **Cloudflare Access**（Zero Trust。50 人まで無料）を置き、運営主体の Google Workspace のアカウントでログインした人だけを通す。そのうえで、いまのとおり運営者の Google のログインとパスキーを求める（二重） |
| 止めているあいだ | 更新などで API が止まっている間は、Caddy が「ただいま更新中です」の静的なページを返す（502 の代わり） |
| 紹介のページ | `m2office.online` と `www` は、Cloudflare の上で動く EmDash に送る（VPS には来ない。第23.3.1節）。DNS は名前を決めた記録がワイルドカードより先に当たる。`signup` は申し込みの口（VPS）へ送る |
| プラン | **Pro**（WAF の管理された規則・独自のエラーのページ・規則の数のため）。立ち上げの間は Free でもよい |

##### 機械（Xserver の VPS）

| 項目 | 規定（案） |
|---|---|
| OS | Ubuntu 24.04 LTS（標準のサポートは 2029 年 4 月まで）。次の LTS への移行は、サポートの終わりの 1 年前までに計画する |
| 大きさ | **第 0.430.0 版の案: 3 vCPU・メモリ 2 GB・NVMe SSD 50 GB**（2026-10-24 に三浦さんが整理した VPS。Q-255）。**仮稼働はこのまま、顧客を入れる前にメモリ 4 GB 以上に上げる**。第 0.428.0 版では 4 vCPU・4 GB・150 GB で始める案だった。メモリが最も窮屈なので、下の「資源の配分」で上限を決め、目安を超えたらプランを上げる（Xserver の VPS はプランを上げられる。上げ方と止まる時間は導入のときに確かめる） |
| 入ってくる通信 | **すべて断る**（Xserver のパケットフィルターと `ufw` の両方。既定で拒否）。HTTP・HTTPS・SSH も開けない |
| 保守の入り口 | Tailscale（外向きにつなぐ）。提携先と運営の技術者の Tailscale のアカウントだけを、決めた機械だけに通す（Tailscale の ACL）。Tailscale の SSH を使い、パスワードは使わない。万一のときは Xserver の管理画面のコンソールで入る（手順書に書く） |
| 利用者 | 動かすのは専用の利用者 `m2office`（ログインできない）。保守の人は自分の名前の利用者で入り、`sudo` で上がる。`root` での直接のログインはしない |
| 自動の更新 | `unattended-upgrades` でセキュリティの更新を毎日入れる。再起動が要る更新は、決めた時間（夜中）に自動で再起動する |
| 固め | 使わないサービスを止める。`fail2ban` は受け口が無いので要らない。時刻の同期（`systemd-timesyncd`）。`auditd` で `sudo` と大事なファイルの変更を記録する |
| ソフト | Node.js 24 系（LTS。公式の配布の `.deb` を版を固定して入れる）、PostgreSQL 17 と pgvector（PostgreSQL の公式の apt の置き場）、Caddy（公式の apt）、`cloudflared`（公式の apt）、Tailscale、ffmpeg、restic、pgBackRest |
| 置き場所 | アプリ `/opt/m2office`（リリースのタグを取ってきて組み立てる）、データ `/var/lib/m2office`（ファイル・ログ・機械の様子）、設定 `/etc/m2office/m2office.env`（管理者と `m2office` だけが読める） |

##### 資源の配分（3 vCPU・メモリ 2 GB・NVMe SSD 50 GB。第 0.430.0 版の案）

| 項目 | 規定（案） |
|---|---|
| 使い道 | **仮稼働はこのスペックで動かす。顧客を入れる前にメモリ 4 GB 以上に上げる**（録音の文字起こし・PDF の組み立て・動画の書き出しが重なると 2 GB では足りない） |
| メモリの割り当て | PostgreSQL 約 512 MB（`shared_buffers` 256 MB・`work_mem` 4 MB・`maintenance_work_mem` 64 MB）、API 512 MB、ワーカー 768 MB、運営の API 192 MB（Node.js の `--max-old-space-size` で上限を決める）。申し込みの口は仮稼働では動かさない。Caddy・cloudflared・Tailscale・OS で残り |
| スワップ | **4 GB のスワップのファイルを必ず置く**（`vm.swappiness=10`。メモリが残っている間は使わない） |
| 重い処理 | 動画の書き出し（ffmpeg）と PDF の組み立ては、ワーカーで 1 つずつ行う（同時に走らせない） |
| データベースの接続 | 置き場（`pg.Pool`）がストアごとに分かれていて、合わせると API とワーカーで 100 を超えうる（使っていない接続は 10 秒で閉じる）。`max_connections` を 120 にし、仮稼働で山の数とメモリを測る。足りなければ置き場をまとめる |
| ディスクの割り当て | OS とアプリ約 15 GB、データベース、ファイル（サイネージの素材は 1 社 2 GB まで。第31章）、ログ（systemd の記録は 28 日・1 GB まで）。社外の控えは機械に溜めずに送る |
| プランを上げる目安 | メモリの使用が 1 週間の平均で 75% を超える、スワップを毎日使う、ディスクが 70% を超える、のどれか。**次はメモリ 4 GB**。提携先が見張りで見つけ、運営に知らせる |
| 会社の数の目安 | 仮稼働で測ってから決める（同時に使う人の数と、業務の実行の数で決まる） |
| OS の初期設定 | 運営のマニュアル 第 13 章（VPS の用意）の手順で、M2Office を入れる前に固める（SSH は鍵だけ・ufw・自動のセキュリティの更新と夜中 4 時半の再起動・スワップ・時刻と記録・Tailscale に移して 22 番を閉じる・auditd） |

##### プロセスと待ち受け先

| 項目 | 規定（案） |
|---|---|
| 動かし方 | systemd のサービス（`m2office-api`・`m2office-worker`・`m2office-ops`・`m2office-signup`・`caddy`・`cloudflared`）。落ちたら自動で起こし直す（`Restart=always`）。機械が起きたら順に起こす（データベース → API・ワーカー → Caddy → トンネル） |

| **待ち受け先** | **API・運営の API・申し込みの口は 127.0.0.1 だけで待ち受ける**。いまは待ち受け先を決めておらず、すべての口で待ち受けている（2026-10-23 に見つけた）。**どの配備の形でも、既定を 127.0.0.1 にし、変えるときだけ設定（`M2O_LISTEN_HOST`）で決める**。ローカルの形の Mac でも、院内の LAN から Caddy を通らずに API に届いてしまうため、同じ版で直す |
| データベース | 127.0.0.1 だけで待ち受ける。アプリのロール（`m2office_app`）・運営のロール（`m2office_ops`）・移行のロール（持ち主）の合言葉は、それぞれ長い乱数にする |
| 組み立て | 第20.4.5節の本番の組み立て（`npm run build:release`）を、機械の上で行う。コンテナは使わない |

##### 更新（GitHub のリリースのタグ）

| 項目 | 規定（案） |
|---|---|
| 届け方 | ローカルの形の更新（第8.6.4節・`deploy/onsite/update.sh`）と同じく、**機械が GitHub の公開のリポジトリのリリースのタグを取りに行く**。機械に入る鍵を GitHub に預けない |
| 署名 | **リリースのタグに三浦さんの SSH の鍵で署名する**（`git tag -s`。`/release` の手順に入れる）。機械は導入のときに固定した鍵の一覧（`allowed_signers`）で確かめてから入れる。**いまのタグには署名が無い**（2026-10-23 に確かめた）ため、この仕組みの前に署名を始める |
| 入れる時 | 既定は**夜の決まった時間（3 時）に自動で入れる**。提携先は、止める・日を延ばす・手で入れる（`update.sh --tag`）ことができる。権限が増える版（再同意が要る）や、巻き戻せない移行がある版は、自動では入れず、提携先が手順書に沿って入れる |

| 知らせ | 結果（入れた・戻した・止めた）を、提携先と三浦さんに知らせる（運営の画面の「稼働状況」と、メールか Chat） |
| 雛形 | Linux 用の雛形を `deploy/vps/` に作る（`setup.sh`・`update.sh`・systemd の設定・Caddy の設定・`cloudflared` の設定）。ローカルの形の雛形と、共通にできるところは共通にする |

##### 控え

| 項目 | 規定（案） |
|---|---|
| データベース | **pgBackRest** で、WAL（変更の記録）を絶えず社外の置き場へ送り、毎日 1 回まるごとの控えを取る。**どの時点にも戻せる**（失うのは直前の数分まで）。14 日分を残す |
| ファイル | restic で、ファイルの置き場を毎日社外の置き場へ送る。30 日分を残す |
| 社外の置き場 | **日本国内のリージョンを選べる S3 互換の置き場**（Wasabi の東京・さくらのオブジェクトストレージなど）。どちらも機械の上で暗号化してから送り、鍵は機械と、三浦さんが別に保管する控えだけが持つ（提携先には渡さない）。Cloudflare R2 は置き場所を日本に固定できないため使わない（第20.1節の条件） |
| 更新の前 | 更新の前に、そのときの WAL の位置を記録する（戻すときはその時点へ戻す） |
| 戻す練習 | **3 か月に 1 回、別の機械（使い捨ての VPS）に戻して動くことを確かめる**。提携先が行い、結果を記録する |

##### 見張りと知らせ

| 項目 | 規定（案） |
|---|---|
| 外から | 提携先の見張りの道具（または外部の死活の確かめのサービス）で、`https://<見張り用の会社>.m2office.online/v1/health` を 1 分ごとに確かめる。3 回続けて失敗したら提携先に知らせる |

| アプリ | 運営の画面の「稼働状況」と「動いている環境」（第8.6.7.1節）。Node.js のサポートの終わりとセキュリティの修正の知らせ（出たら提携先が更新の手順を行う） |
| ログ | アプリ・Caddy・systemd のログは機械に 28 日残す（第16.10.2節）。Caddy のアクセスのログは、いまの雛形のとおり鍵と問い合わせの部分を伏せる |

### 20.5 リポジトリ構成

単一リポジトリ（モノレポ）とし、役割ごとにパッケージを分ける。

```
m2office/
  packages/
    core/      ドメインロジック（エージェント定義・実行・承認・知識・接続口・文書形式・ロガー）
    api/       公開 API。画面も外部アプリも同じ API を使う
    web/       ワークスペース・管理者ページ・ダッシュボード（Vite + React）
    worker/    ジョブ実行と定時実行の見回り。承認による中断と再開
    shared/    型定義、定数、制度要件（第15.1節）
  db/
    migrations/  スキーマ（RLS を含む）
  scripts/     移行・初期データ・通しの確認・ファイルヘッダーの確認
  tools/       仕様書の PDF 化、説明資料の生成
  docs/
    adr/       設計判断記録
```

| パッケージ | 依存してよい先 | 依存してはならない先 |
|---|---|---|
| `core` | `shared` | HTTP、フレームワーク、画面 |
| `api` | `core`、`shared` | `web`、`worker` |
| `worker` | `core`、`shared` | `web`、`api` の内部実装 |
| `web` | `shared`（型のみ） | `core`、データベース |

**`core` を HTTP から独立させることが要点である。**
同じロジックを API とワーカーの双方から呼べるようにし、
画面専用の処理が生まれる余地をなくす。

### 20.6 配備上の制約

| # | 制約 | 理由 |
|---|---|---|
| 1 | **ワーカーは常駐プロセスとして動かす** | 承認による中断と再開は数分〜数十分にまたがる。リクエスト単位で終了する実行環境では実装できない（第9.3節） |
| 2 | 画面は静的ファイルとして配信できる | SPA のため、配信側に実行環境が要らない |
| 3 | API とワーカーは同じイメージから起動する | 起動引数で役割を切り替え、両者のロジックのずれを防ぐ |
| 4 | 長時間の接続（SSE）を許容する構成にする | 実行の進捗表示と音声のため |

### 20.7 認証の実装方針

SPA 構成のため、ログイン状態の保持方法を明確にしておく。

| 項目 | 方針 |
|---|---|
| セッション | API が発行する **httpOnly Cookie** で保持する。JavaScript から読めない形にする |
| 対象範囲 | テナントのサブドメインに限定する（`a.m2office.online` の Cookie が他社へ渡らない） |
| CSRF | SameSite 属性と、状態を変える操作でのトークン検証を併用する |
| 外部アプリ | Cookie ではなく OAuth 2.0 のトークンを用いる（第13.4節） |
| 2 段階認証 | ログイン処理に後から差し込めるよう、認証を独立した段として実装する（第16.1節） |
| 別オリジンからの呼び出し | テナントのサブドメインからのものだけを許す。任意のオリジンを許すと、Cookie を伴う要求を他のサイトから送られてしまう |
| ログイン状態の保存 | Cookie の値は保存せず、ハッシュだけを持つ。データベースが漏れても、そのままログインには使えない |
| 未ログイン | 誰でもないものとして扱い、ログインを求める。既定の利用者（管理者など）に倒さない |

**画面と外部アプリで認証方式は異なるが、その先の API と権限判定は同一である。**
これが第13.1節 A-3 の実装である。

### 20.8 依存パッケージの方針

顧客データを扱うため、外部パッケージは攻撃面のひとつとして扱う。

| # | 方針 |
|---|---|
| 1 | ロックファイルをリポジトリに含め、版を固定する |
| 2 | 自分で短く書けるものはパッケージを追加しない |
| 3 | 追加時は保守状況・利用実績・依存の深さを確認する |
| 4 | 既知の脆弱性を定期的に検査し、結果を記録する |
| 5 | 認証・暗号・決済に関わる処理は自作せず、実績のある実装を使う |

### 20.9 開発規約とリリース規定

コードの書き方とリリースの進め方は、本書とは別の文書で定める。

| 文書 | 内容 |
|---|---|
| `docs/coding-standards.md` | 言語とツール、命名、**JSDoc**、エラー処理、ログ、テスト、Git、**README**、セキュリティ上の遵守事項 |
| `docs/release-process.md` | **バージョンの付け方**、リリースの種類と手順、**リリースノート**、段階的配信、巻き戻し、非推奨と廃止 |
| `CLAUDE.md` | 上記の要点と参照先。開発エージェント向け |

本書と分ける理由は、更新の頻度と読み手が異なるためである。
仕様は合意のうえで変わるが、開発規約は運用しながら細かく直していく。

#### 20.9.1 特に守るべき点

| # | 内容 | 定義箇所 |
|---|---|---|
| 1 | 仕様にない機能を実装しない。先に本書を更新する | 開発規約 第12章 |
| 2 | JSDoc は `export` されるもの・公開 API・ツール関数に必須 | 開発規約 第5章 |
| 3 | ツール関数には危険度を明記する | 開発規約 第5.6節 |
| 3a | すべてのソースファイルはファイルヘッダー（`@file`）から始め、インポート文より前に置く | 開発規約 第5.3節 |
| 4 | README.md を必ず作り、変更と同じコミットで更新する | 開発規約 第11章 |
| 5 | テナント境界と承認ゲートを迂回しない | 開発規約 第9章 |
| 6 | バージョンは迷ったら大きいほうに倒す | リリース規定 第3.1節 |

#### 20.9.2 版を持つ対象の整理

**M2Office には版を持つものが複数あり、独立して動く。**

| 対象 | 版の付け方 |
|---|---|
| サービス本体 | セマンティックバージョニング |
| 公開 API | URL のパス（`/v1`）。破壊的変更は新版を追加し旧版を維持（第13.1節 A-4） |
| エージェント定義スキーマ | 整数（`schema_version`。第9.2節） |
| 拡張機能 | セマンティックバージョニング。`platform_schema` で互換を宣言（第12.6節） |
| 本書 | `0.x.y` |

サービス本体が更新されても、公開 API は `/v1` のまま提供され続けることがある。
