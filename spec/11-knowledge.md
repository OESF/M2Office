## 11. 知識基盤と組織学習

**この章で決めること**: 情報をどう蓄積し、個人の学習をどう会社の資産に変えるか。
**「会社としての情報が蓄積・統合されることが最大の武器になる」という前提の実装である。**

### 11.1 記憶の 3 層

| 層 | 内容 | 参照範囲 | 主な生成元 |
|---|---|---|---|
| **個人記憶** | その従業員の働き方 | 本人のみ | 秘書との対話、実行履歴 |
| **チーム記憶** | 部署・チームで共有される手順や文脈 | 所属メンバー | 昇華、チーム内の共有設定 |
| **組織知識** | 会社の正式な知識 | 全社（権限に応じて） | 規程の登録、議事録、昇華 |

```
   個人記憶               チーム記憶             組織知識
  （本人のみ）  ──昇華──→ （部署内）   ──昇華──→ （全社）
                     ▲                      ▲
                     │                      │
                秘書が判断             秘書が判断
```

**個人記憶から組織知識へは、秘書が、新しく覚えたときに、ほかの人にも役立つものを選んで登録する**（第 0.115.0 版、第11.3節、ADR-0028。第 0.135.0 版から 1 日 1 回ではなくその場で。第10.13節）。
管理者は秘書が加えたものを確かめ、違えば消す。チーム記憶は未実装。

**組織知識は、出どころで 3 つに分けて管理する**（第 0.193.0 版、第11.11節、ADR-0056）。**社内規程**（管理者が登録する会社の決まり。版を残し、消さずに廃止する）、
**議事録**（業務が登録する会議の記録）、**秘書が学んだこと**（秘書が会話から加えたもの。定期的に整理する）。検索は 3 つをまとめて行うが、根拠は社内規程を先にする。

### 11.2 記憶に入れるもの・入れないもの

**第 0.114.0 版で改めた。秘書は本人に関わることを、原則すべて覚える**（三浦さんの決定「全て記憶してください」。ADR-0027）。
覚えないのは、下の 3 つだけとする。

| 覚える | 覚えない（これだけ） |
|---|---|
| 要約された事実（誰が何の担当か、取引先との経緯、案件の状況） | **認証情報・パスワード・鍵**（漏れたときの害が大きい） |
| 本人の予定・約束・やりかけのこと（「来週までに見積を送る」） | **本人が「覚えないで」と指示した内容** |
| 作業の嗜好（文体、形式）・判断の傾向・繰り返しの手順 | **他人の要配慮個人情報**（病歴など。本人の同意なく取得できないため。個人情報保護法） |
| 社内用語・取引先の通称・人の呼び方 | |
| 本人が話した本人の事情（家族の予定など） | |
| メールや文書の要点と、どこにあるか（原文そのものではなく、要約と所在） | |

**原文は保持しない。要点と所在に圧縮して持つ。** 原文は Google Workspace 側に存在するため、
記憶には「どこに何があるか」と「そこから導かれた事実」だけを持つ。
これによりプライバシー面の露出と保管容量の双方を抑える。

### 11.3 昇華のフロー（第 0.115.0 版で改める。ADR-0028）

**個人の記憶を会社の知識にするか（昇華）は、秘書が判断して、そのまま登録する。** 本人の承認も、管理者の承認も求めない。
以前は、本人と管理者（または承認者）の二重の承認を必須としていた（Q-24、ADR-0016）。
三浦さんは、「これを会社の共通の知識にするかどうかの判断は、利用者に分かるわけがない。AI に任せる」と決めた（2026-09-26）。
少々の誤りは、使う人が会話で指摘して直すことで、知識として育つ。

```
[個人記憶に蓄積]（会話から秘書が自分で覚える。第11.5.2節）
      │
      │ 秘書が新しく覚えたときに、他の人にも役立つかを判断する
      ▼
[組織知識へ登録] ──→ 全従業員の秘書と業務エージェントが参照可能になる
      │
      │ 違っていたら、使った人が会話で指摘する（第11.5.3節）
      ▼
[秘書が直す・消す]
      │
      │ 手順性の高いものは
      ▼
[エージェント定義の草案] ──→ 第12章の拡張機構へ（プライベート拡張）
```

| 段階 | 実施者 | 見る観点 |
|---|---|---|
| 判断 | 秘書（自動） | 繰り返し性、汎用性、他の人の役に立つか。本人だけに関わることでないか。個人情報・権限区画のデータを含まないか。すでにある知識と重ならないか |
| 登録 | システム | 出典（秘書が会話から学んだもの）と、もとになった記憶の持ち主を記録する |
| 見直し | 使う人（会話で）・管理者（一覧で） | 違っていれば会話で直す。管理者は一覧で見て消せる |

**二重の承認をやめても、次の 3 つは会社の知識にしない。** 本人だけに関わること（好み・自分の予定の癖・個人的な事情）、
他人の個人情報（とくに健康・家族・評価などの立ち入った事情）、権限区画のデータ（不変則 I-12）。

#### 11.3.1 昇華の実装（第 0.115.0 版で改める）

| 項目 | 規定 |
|---|---|
| いつ | 秘書が新しく覚えたとき、その場で行う（第 0.135.0 版。第10.13節のイベントで学んだ直後）。推論が使えない環境では行わない |
| 何を見るか | 各人の記憶のうち、まだ判断していないもの。本人が「覚えることを許す」を切っている人の記憶は見ない |
| 判断 | 推論に、記憶の一文と、会社の知識の近いものを渡し、「会社の知識にする」「しない（本人だけに関わる・個人情報・重なる）」を選ばせる。**記憶の文は書き換えない**。重なるときは登録しない |
| 登録の中身 | 記憶の一文をそのまま登録する。題名は先頭の 30 字、出典は「秘書が会話から学んだこと」。区画は付けない（全社）。もとの記憶の持ち主は記録に残すが、**知識の本文と出典には名前を出さない** |
| 本人への知らせ | 行わない（本人の手間にしない）。本人は個人設定の「記憶とデータ」で、自分の記憶から会社の知識になったものを見られる |
| 管理者 | 管理者ページの「知識」の「秘書が学んだこと」に並べ、見て消せる（社内規程とは別の一覧。第11.11.1節）。承認の操作は無い |
| 本人が消した記憶 | 会社の知識にしたあとで本人が記憶を消しても、会社の知識は残る（会社の資産。第11.6節と同じ扱い）。会社の知識を消すのは、会話での訂正（第11.5.3節）か管理者 |
| 記録 | 監査ログ `knowledge.promote.auto`（件数と知識の ID）。**記憶の中身は入れない** |
| 以前の提案 | 判断待ちで残っている提案（第 0.114.0 版までの形）は、同じ判断にかけて登録するか見送る |

### 11.4 組織知識の供給源

| 供給源 | 内容 | 登録方法 | フェーズ |
|---|---|---|---|
| 社内規程 | 就業規則、労務規定、経費規程、稟議基準 | 管理者が登録 | 1 |
| 議事録 | 会議の決定事項・保留事項 | AG-02 が自動登録（承認②のあと。第9.5.2節） | 1 |
| 共有ドライブ | 提案書、報告書、マニュアル | フォルダを指定して同期 | 1 |
| 価格表・商品情報 | 単価、仕様、納期 | 管理者が登録、または連携 | 2 |
| 顧客情報 | 取引先の基本情報、履歴 | CRM 連携または手動 | 2 |
| 過去案件 | 見積・提案・結果 | 実行履歴から蓄積 | 2 |
| 昇華された知識 | 個人・チームから引き上げられたもの | 第11.3節のフロー | 2 |

**議事録が最も価値の高い供給源**である。
会議のたびに決定事項が自動で蓄積され、「あの件どうなったか」に答えられるようになる。
AG-02（議事録の作成）を Phase 1 に置く理由の一つはここにある。

### 11.5 本人による制御

原則 p10「情報は顧客のもの」を、個人レベルでも保証する。

| 機能 | 内容 | 優先度 |
|---|---|---|
| 記憶の一覧 | 秘書が自分について何を覚えているかを一覧できる | M |
| 個別削除 | 特定の記憶を削除できる | M |
| 記憶の停止 | 一時的に学習を止められる | S |
| 対象外の指定 | 「この件は覚えないで」と指示できる | M |
| 会話での訂正 | 「それは違う、〇〇だよ」と伝えれば、秘書が自分で記憶を直す。秘書が会社の知識にしたものも同じ（第11.5.3節。第 0.115.0 版。以前は「昇華の拒否」） | M |
| 全削除 | 自分の個人記憶をすべて消去できる | S |

**「何を覚えているか分からない AI」は組織では使えない。**
懸念として「情報漏洩のリスク」33.5%、「トラブル時の責任所在」25.5% が挙がっている以上、
記憶の可視化と制御は信頼の前提条件である。

#### 11.5.1 何をきっかけに覚えるか（Q-23 で決定）

**本人が「覚えておいて」と頼んだときは、その場で覚える。** それに加えて、**秘書は対話から自分で学び続ける**（第11.5.2節。第 0.114.0 版）。

| 規定 | 内容 |
|---|---|
| 覚えるきっかけ | 秘書への「〜を覚えておいて」という指示。本人の指示そのものが同意にあたるため、この形は**既定で有効**とする |
| 覚えないきっかけ | 秘書への「〜は覚えないで」という指示。対象外の言葉として残し、以後その言葉を含む指示では覚えない |
| 学習の停止 | 個人設定で止められる。止めている間は、頼まれても覚えない（そう答える） |
| 覚える中身 | 本人が指示した一文だけ。要約も推測もしない（推論を通さないため、覚えた内容が指示と食い違わない） |
| 覚えないもの | 第11.2節の「入れない」もの。とくに**認証情報らしき語**（パスワード・API キー・トークンなど）を含む指示は覚えず、理由を答える |
| 長さ | 1 件 200 字まで。超える指示は覚えず、短く言い直してもらう |
| 参照 | 本人のみ（第11.1節）。秘書は本人との対話でだけ使い、業務エージェントとほかの利用者には渡さない |
| 記録 | 監査ログ `memory.create`・`memory.delete`・`memory.clear`。**中身は監査ログに入れない**（本人のものであるため） |
| 退職・削除 | 利用者を消すと、その人の記憶も消える（第11.6節） |

#### 11.5.2 対話からの自動の学習（第 0.114.0 版で改める。ADR-0027）

**秘書は対話から事実を取り出し、そのまま覚える。本人は、覚えたことをいつでも見て、直して、消せる。**
以前は候補を示して本人が「覚える」を押したものだけを記憶にしていた（Q-23、ADR-0015）。
三浦さんは、秘書は本人と一心同体であり、可能な限り長く学び続けるべきと決めた（2026-09-25。ADR-0027）。
「何を覚えているか分からない AI」にしない（第11.5節）ことは、**覚えたことを見せ、止められる**ことで守る。

以下の表の「採否」「既定」の行は、第 0.114.0 版で改めた。

| 規定 | 内容 |
|---|---|
| いつ作るか | **会話を 1 往復残したとき、本人が直接使った業務が完了したとき、その場で学ぶ**（第 0.135.0 版、第10.13節、ADR-0039）。以前は 1 日 1 回、前日の会話をまとめて見ていた |
| 何を作るか | ①その日の**会話の要約**（長期に持つ。逐語が 4 週で消えた後もここに残る。出来事のたびに書き足す） ②**覚えた事実**（そのまま個人記憶にする。第 0.114.0 版） |
| 材料 | 残した**会話**の 1 往復と、本人が完了した**業務の依頼と答え**（メニュー・API・定時実行から直接使ったもの。第 0.134.0 版、ADR-0038）。どちらもその場で学ぶ（第10.13節）。秘書に頼んだ業務と秘書が伝えた結果（会話ログにある）、権限区画の業務、「会話を残す」を切っている人の業務は加えない。業務は最後の段の答えの文だけを使い、1 件 1,500 字までに切り詰める |
| 候補の中身 | 要約された事実だけ（第11.2節）。原文・他人の個人情報・機微情報・認証情報は入れない |
| 採否 | **本人の操作を待たずに覚える**（第 0.114.0 版）。**本人に確認は求めない**（第 0.115.0 版。「新しく覚えたこと」の印もやめる）。違っていれば、本人が会話で指摘し、秘書が直す（第11.5.3節）。個人設定の「記憶とデータ」は見たい人が見る場所で、そこでも直せ、消せる。消した事実は**同じ文を再び覚えない** |
| 既定 | **有効**。個人設定の「覚えることを許す」を切ると、自動では覚えない（頼まれたときも覚えない。第11.5.1節） |
| 対象外 | 対象外の言葉（第11.5.1節）を含む会話は、要約にも候補にも使わない |
| 権限区画 | 区画のデータを含む会話は、要約に区画の印を引き継ぐ（第11.9.6節 注意点 2） |
| 推論が使えないとき | 学ばない（見本の応答で作らない）。会話ログと要約の保存は続ける（第20.2.4節） |
| 記録 | 監査ログ `memory.learn`（覚えた件数と対象の日だけ。第 0.114.0 版）。本人が直すと `memory.update`、消すと `memory.delete`。**中身は入れない** |

#### 11.5.3 会話で直す（第 0.115.0 版。ADR-0028）

**覚えたことの間違いは、本人が会話で指摘し、秘書が自分で直す。** 本人が記憶の一覧を開いて 1 件ずつ直す作業にしない。
三浦さんのたとえでは、秘書は新人である。指摘はするが、直す作業は秘書が自ら行う（2026-09-26）。

| 言い方の例 | 秘書が行うこと |
|---|---|
| 「それは違う。見積は税込みで出す」 | 食い違う記憶を探して直す。無ければ新しく覚える |
| 「覚えたことを直しておいて。山田さんは経理じゃなくて総務」 | 同上 |
| 「〇〇のことは忘れて」 | 当たる記憶を消す |
| 「会社の知識の〇〇が違う」 | 秘書が会社の知識にしたもの（第11.3節）なら直す。**管理者が登録した規程や議事録は書き換えず**、管理者に伝えるよう案内する |

| 項目 | 規定 |
|---|---|
| 探し方 | 本人の記憶（と、秘書が会社の知識にしたもの）から、指摘に近いものを推論で選ぶ。1 つに絞れなければ、候補を示して聞き返す（推測で消さない） |
| 答え | 直した前と後を短く返す（「『山田さんは経理の担当』を『山田さんは総務の担当』に直しました」） |
| その場の学習との関係 | 会話のたびの学習（第11.5.2節・第10.13節）でも、会話の中の訂正を拾い、食い違う古い記憶を直す |
| 直したもとの文 | 秘書が覚えた文を直したときは、もとの文を再び覚えない（消したときと同じ） |
| 会社の知識を直したとき | 知識の本文を直し、出典に「会話での訂正」を添える。監査ログ `knowledge.correct`（知識の ID だけ） |
| 記録 | 監査ログ `memory.update`・`memory.delete`（中身は入れない） |

### 11.7 検索方式

知識を「蓄積する」だけでは使えない。**出典付きで正確に引けること**が要件である。

| 段階 | 方式 | フェーズ | 状態 |
|---|---|---|---|
| 1 | 構造で直接引く（規程を章・条に分けて登録し、条の単位で引く） | 1 | 実装済み（第11.7.2節） |
| 2 | 全文検索（キーワードによる文書横断と、関係の深い順の並べ替え） | 1 | 実装済み（第11.7.3節）。索引は未導入 |
| 3 | 意味的検索（ベクトル検索）の併用 | 2 | 第11.7.6節で規定。未実装 |
| 4 | 検索結果の統合と出典提示 | 1 | 実装済み（第11.7.4節） |

**段階を分ける理由**: いわゆる RAG（検索して生成に渡す方式）は有効だが、
規程のように構造が明確な文書は、章・条を直接引くほうが正確で説明もしやすい。
まず構造化と全文検索で確実に引ける状態を作り、
それで届かない領域に意味的検索を足す順序とする。設計の判断は ADR-0008 に残す。

| 要件 | 内容 |
|---|---|
| 出典の明示 | 回答には必ず参照元の文書名・該当箇所（章・条）・リンクを添える |
| 権限の反映 | 閲覧権限のある文書のみを検索対象とする |
| 鮮度 | 版が更新された場合、古い版を参照しない |
| 不在の明示 | 該当する知識がない場合、推測せず「見つからない」と答える |

#### 11.7.1 これまでの実装と、その問題

第 0.42 版までの実装は、文書 1 件を 1 行として保存し、質問の言葉が 1 つでも含まれる文書を
更新日の新しい順に 5 件返し、**本文をまるごと**推論に渡していた（仮の実装）。
文書の量が少ないうちは動くが、就業規則のような長い文書を 1 件で登録すると次の問題が起きる。

| 問題 | 起きること |
|---|---|
| 1 冊が 1 件になる | 何を聞いても 1 冊の全文が推論に渡る。費用が増え、答えの材料が薄まり、長いと入りきらない |
| 出典が粗い | 「就業規則」までしか示せず、該当する条を示せない（上の「出典の明示」を満たさない） |
| 関係の深い順でない | 新しい順に並べるだけ。言葉が 1 つでも入れば拾うため、長い文書ほど何にでも当たる |
| 言葉の区切りが粗い | 助詞の文字（か・ら・ま・よ・り など）でも区切るため、「取り扱い」が「取」と「扱い」に割れる |

**速さは問題にならない。** 中小企業の知識の量（数百の文書、数万の条）なら、索引がなくても検索は一瞬で終わる。
問題は正確さであり、以下の 4 つ（分割・検索・渡し方・鮮度）で解く。

#### 11.7.2 取り込み時の分割（段階 1）

知識を登録・更新したとき、本文を**節**（検索と出典の単位）に分けて保存する。
分け方は文書の書き方から機械的に決め、LLM は使わない（同じ文書は毎回同じに分かれる）。

| 優先 | 見出しとみなす行 | 例 | 節の単位 |
|---|---|---|---|
| 1 | 行頭の「第○条」 | `第23条（年次有給休暇）` | 条ごと。章・節は見出しの経路に入れる |
| 2 | 行頭の「第○章」「第○節」「附則」 | `第5章 休暇` | 条がない文書では章・節ごと |
| 3 | Markdown の見出し（`#`〜`###`） | `## 申請のしかた` | 見出しごと |
| 4 | 見出しがない | ― | 空行で区切った段落を、およそ 1,000 字ずつにまとめる |

| 規則 | 内容 |
|---|---|
| 番号の書き方 | 漢数字・算用数字・全角数字のいずれも見出しと認める（`第二十三条`・`第23条`・`第２３条`） |
| 見出しの経路 | 節ごとに、上位の見出しを含めた経路を持つ（例: `第5章 休暇 › 第23条（年次有給休暇）`） |
| 長すぎる節 | 2,000 字を超える節は段落の境で分け、見出しに「（続き）」を付ける |
| 見出しより前の文 | 「前文」という節にする（目的・適用範囲などが書かれることが多い） |
| 文書の大きさ | 1 件あたり 50 万字まで。超える場合は登録を断り、分けて登録するよう伝える |
| 権限区画 | 節は文書の区画を引き継ぐ。節ごとには指定しない |

**管理者は、保存した直後に分け方を確かめられる。**
管理者ページの知識（第6.6.6節）で、保存すると「23 の節に分けました」と表示し、節の見出しの一覧を開けるようにする。
思った単位で分かれていなければ、本文の見出しの書き方を直して保存し直す。

#### 11.7.3 検索と並べ替え（段階 2）

**質問の言葉の取り出し。**
質問の文から、次の 2 つを合わせて検索の言葉とする。

| 取り出し方 | 例（「育休の取り扱いを教えて」） |
|---|---|
| 漢字・カタカナ・英数字の連なり（ひらがなで区切る） | `育休` |
| 日本語の単語の区切り（実行環境の `Intl.Segmenter`）で得た、2 文字以上でひらがなだけではない語 | `育休`・`取り扱い` |

**候補の絞り込み。**
言葉を 2 文字ずつの組（バイグラム）に分け、そのどれかを見出しか本文に含む節を候補とする（最大 200 節）。
区画の外の利用者には、区画内の節を候補にも出さない（第16.3.5節）。

**点数の付け方。** 候補の節ごとに次の点を足し、高い順に並べる。

| 観点 | 点 | 理由 |
|---|---|---|
| 言葉が見出しに含まれる | 1 語につき 3 | 「年次有給休暇」を聞かれたら、その条が最も確か |
| 言葉が本文に含まれる | 1 語につき 1 ＋ 出現回数に応じた加点（上限あり） | 何度も出る節ほど関係が深い。ただし長い節が有利になりすぎないよう上限を置く |
| 言葉がそのままは無いが、2 文字の組の半分以上が含まれる | 1 語につき 0.5 | 「申請方法」に対する「申請の方法」のような言い回しの違いを拾う |
| 質問の言葉を多く満たす | 満たした語の割合 × 2 | 1 語だけ当たる節より、すべて当たる節を上にする |

同点なら更新日の新しい順とする。**点が一定に満たない節は返さない**（何にでも当たる節を出さない）。

**知識の種類による順（第 0.193.0 版、第11.11.1節）。** 点が一定を超えた節を、**社内規程 → 議事録 → 秘書が学んだこと**の順に並べ、同じ種類の中を点の順にする。
秘書が学んだことは、社内規程の節が見つかったときも根拠に添えてよいが、**規程と食い違えば規程を採る**（推論への指示に明記する）。
秘書が学んだ一文が、規程の条文より先に根拠に出ることを防ぐため（2026-09-29 に見つかった事例）。

**索引は速さのためだけに使う。**
上の絞り込みは PostgreSQL の部分一致（`ILIKE`）で書き、拡張機能がなくても同じ結果になるようにする。
量が増えたときは、日本語の 2 文字の部分一致を速くする拡張機能 pg_bigm の索引を足す。
**索引の有無で検索の結果は変わらない。** 本番のデータベースで pg_bigm を使えるかは Q-80 とする。

#### 11.7.4 推論への渡し方と出典

| 項目 | 規定 |
|---|---|
| 渡す単位 | 文書の全文ではなく、**上位の節**（最大 5 節） |
| 渡す量 | 合計 8,000 字まで。超える分は下位の節から落とす |
| 出典の書き方 | `文書名 › 見出しの経路`（例: 「就業規則 › 第5章 休暇 › 第23条（年次有給休暇）」）と、登録時の出典（リンク・ファイル名） |
| 見つからない場合 | 節を返さず、「見つからない」ことを返す。推論には推測させない（指示に明記する） |

秘書の使い方の答え（第6.10.6節）で社内の規程を示すときも、同じ出典の書き方を使う。

#### 11.7.5 鮮度と版

| 規則 | 内容 |
|---|---|
| 分け直し | 文書を保存するたびに、その文書の節を**すべて作り直す**。古い節と新しい節を 1 つの処理（トランザクション）で入れ替え、途中の状態を検索させない |
| 版 | 文書は保存のたびに版の番号を 1 つ上げる。出典には版を含めない（利用者には最新だけを見せる）。**社内規程は前の版の本文を残す**（第11.11.2節。第 0.193.0 版） |
| 削除 | 社内規程と議事録は消さずに**廃止**にし、検索から外す（第11.11.2節）。秘書が学んだことは、消すか**しまう**（第11.11.4節）。どれも検索から外すときに節を外す |
| 既存の知識 | この方式を入れる前に登録した知識は、移行のときに一度だけ分け直す |

古い版の本文は、社内規程について残す（Q-82 を第 0.193.0 版で決定。第11.11.2節）。「改定前の規程では何日だったか」には、版と施行日を添えて答える。

#### 11.7.6 意味的検索（段階 3。Phase 2）

段階 2 は、質問の言葉が規程の中にそのまま（またはほぼそのまま）出てくる節しか見つけられない。
利用者は規程の言葉で聞くとは限らない。**言い換えを結び付けることが、段階 3 の目的である。**

| 利用者の言い方 | 規程の言葉 | 段階 2 で見つかるか |
|---|---|---|
| 育休 | 育児休業 | 見つからない（2 文字の組が 1 つも重ならない） |
| 残業 | 時間外労働 | 見つからない |
| 休みは何日もらえる？ | 年次有給休暇を付与する | 「休」だけでは言葉にならず、見つからない |
| 出張の宿代 | 宿泊費 | 見つからない |

節ごとに、意味を表す数値の並び（埋め込み。ベクトル）を作っておく。
質問も同じように埋め込み、意味の近い節を探して、段階 2 の結果と合わせて並べる。
設計の判断は ADR-0009 に残す。

```
［知識を保存］─→［節に分ける（段階 1）］─→［節を埋め込む（ワーカーが後から）］

［質問］
  ├─→［言葉で探す（段階 2）］ ────────────→ 上位 20 節 ─┐
  └─→［質問を埋め込む］─→［意味で探す］ ──→ 上位 20 節 ─┤
                                                        ▼
                                        ［順位を合わせる］─→ 上位の節（最大 5 節）
```

##### 11.7.6.1 埋め込みの作成

| 項目 | 規定 |
|---|---|
| 提供者とモデル | Gemini の `gemini-embedding-2` とする（Q-81 で決定）。100 以上の言語に対応し、1 回に 8,192 トークンまで入る。節は最大 2,000 字（第11.7.2節）なので、1 節がそのまま入る |
| 次元 | 768 次元とする（Q-81 で決定）。モデルは 3,072 次元まで出せるが、規程の検索には 768 で足り、保存の大きさと計算が 4 分の 1 になる |
| 抽象化 | 埋め込みの提供者は LLM 抽象化層の一部とし、差し替えられるようにする（第20.2.2節）。鍵は推論と同じものを使う（会社が自社の鍵を登録していればその鍵。第14.3.3節） |
| 節と質問の書き方 | 節と質問を別の書き方にする（非対称の検索）。Gemini が検索のために推奨する書き方で、表の下に示す。節には見出しの経路を入れ、本文に章の名前が無くても意味が伝わるようにする |
| いつ作るか | 知識を保存した直後ではなく、**ワーカーが後から作る**。保存を待たせない。作り終わるまでの節は段階 2 だけで見つかる |
| 作り直しを減らす | 節ごとに本文のハッシュを持つ。保存し直しても、本文が変わらない節は前の埋め込みを使い回す。規程の 1 条を直しても、埋め込み直すのはその条だけになる |
| モデルの記録 | 節ごとに、どのモデル・何次元で作ったかを記録する。モデルを変えたら、古い埋め込みを段階 2 だけで扱いながら、ワーカーが順に作り直す（違うモデルの埋め込みどうしは比べられない） |
| 費用 | 埋め込みのトークンも会社の利用量に数える（第21.2.1節）。規程の登録は一度きりで、質問の埋め込みは短いため、推論に比べて小さい見込み。単価は採用時に確かめる |
| 失敗したとき | 数回まで間を空けてやり直す。それでも作れない節は段階 2 だけで見つかる。管理者ページの知識に「意味での検索の準備: ○ / ○ 節」を示す |

```
節:   title: 就業規則 › 第5章 休暇 › 第34条（育児休業） | text: 子を養育する従業員は、…
質問: task: search result | query: 育休はいつまで取れますか
```

##### 11.7.6.2 保存と検索

| 項目 | 規定 |
|---|---|
| 保存先 | 同じ PostgreSQL の拡張機能 **pgvector** を使い、節の表（`knowledge_sections`）に埋め込みの列を足す。別のベクトルデータベースは置かない |
| テナント境界 | 節の表と同じ行レベルセキュリティがそのまま効く（不変則 I-2）。検索は必ずテナントと権限区画で絞ってから距離を計算する |
| 探し方 | **近似の索引を使わず、そのテナントの節をすべて比べる**（厳密な検索）。中小企業 1 社の節は多くても数万で、768 次元なら十分に速い |
| 近似の索引を使わない理由 | pgvector の近似の索引（HNSW）は、全社の節から近いものを先に拾ってからテナントで絞る。節の少ない会社ほど、絞った後に何も残らないことがある。テナントで絞ってから比べれば、この問題が起きない |
| 距離 | コサイン距離（類似度 = 1 − 距離） |
| 候補 | 意味の近い上位 20 節。ただし類似度がしきい値に満たない節は候補にしない（第11.7.6.3節） |

量が増えて遅くなったときは、pgvector 0.8 以降の「絞り込みながら索引を読む」機能（iterative scan）とともに HNSW の索引を足す。
**索引を足しても、返す節は変えない**ことを、第11.7.6.5節の評価で確かめてから切り替える。

##### 11.7.6.3 順位の合わせ方

段階 2 と意味的検索の上位 20 節ずつを、**順位の融合**（Reciprocal Rank Fusion）で 1 つの並びにする。

| 項目 | 規定 |
|---|---|
| 計算 | 節ごとに、それぞれの並びでの順位 r について 1 ÷ (60 + r) を足す。片方にしか無い節は、その片方の分だけ |
| 点数そのものを足さない理由 | 段階 2 の点数と類似度は尺度が違い、足し方の重みを決められない。順位だけを使えば尺度をそろえる必要がない |
| 返す節 | 合わせた並びの上位から、段階 2 と同じ上限（最大 5 節、合計 8,000 字。第11.7.4節）で選ぶ |
| しきい値 | 意味的検索は「いちばん近いもの」を必ず返すため、関係のない節も出てくる。**類似度がしきい値に満たない節は、意味的検索の候補にしない**。しきい値の初期値は 0.6 とし、第11.7.6.5節の評価で決め直す |
| 不在の明示 | 段階 2 でも意味的検索でも候補が無ければ、これまでどおり「見つからない」と返す（第11.7節の要件） |
| 見つけ方の表示 | 節ごとに、言葉で見つけたか、意味で見つけたか、両方かを返す（`matchedBy`）。秘書と業務の答えの出典の横に「言い換えで見つけました」と示し、利用者が確かめる手がかりにする |

##### 11.7.6.4 権限・データの扱い

| 規則 | 内容 |
|---|---|
| 送る先 | 節の本文を埋め込みの API に送る。推論と同じ提供者・同じ契約の範囲であり、新しい送り先を増やさない |
| 権限区画 | 区画内の節も埋め込む。区画の外の利用者の検索では、距離を計算する前に区画内の節を除く（第16.3.5節）。ただし、健康情報を LLM へ送らないと決めた場合（Q-47）は、その区画の節は埋め込まない |
| 質問の文 | 質問の埋め込みは検索のたびに作り、保存しない |
| 消すとき | 埋め込みは節から作った値なので、節と一緒に消える。知識を削除すれば残らない |
| 持ち出し | OKF の書き出し（第11.10節）には含めない。モデルに依存する値で、持ち出した先では使えないため |
| 取り込んだ文書の指示 | 埋め込んでも、文書の中の指示に従わないことは変わらない（不変則 I-6） |

##### 11.7.6.5 評価と採用の条件

入れて良くなったかを、数えて確かめてから本番で有効にする（第18章）。

| 項目 | 規定 |
|---|---|
| 評価の問題 | 見本の規程（就業規則・経費規程・出張旅費規程など）に対する質問と、正解の節の組を 60 問用意する。規程の言葉のままの質問・言い換えの質問・規程に答えが無い質問を 20 問ずつ |
| 測るもの | 正解の節が上位 5 節に入る割合、答えが無い質問で何も返さない割合、1 回の検索にかかる時間 |
| 採用の条件 | 言い換えの質問で段階 2 だけより正解が増える。規程の言葉のままの質問で減らない。答えが無い質問で何も返さない割合が 9 割を下回らない |
| しきい値 | 上の条件を満たす範囲で、類似度のしきい値を決める |
| 回帰の確認 | 評価はテストとして残し、モデル・次元・しきい値を変えるたびに回す |

##### 11.7.6.6 使えないとき

| 状況 | 挙動 |
|---|---|
| Gemini が使えない会社 | 秘書も業務も動かない（第20.2.4節）。意味的検索だけが使えないときは、段階 2 だけで答える |
| 埋め込みの API に失敗した（質問の埋め込み） | その検索だけ段階 2 だけで答え、アプリログに警告を残す。利用者には止めずに答える |
| データベースに pgvector が無い | 埋め込みの列を作らず、段階 2 だけで動く。移行は pgvector があるときだけ列を足す |
| 開発環境 | pgvector を含むデータベースの像（`pgvector/pgvector`）を使う。テストには、決まった言い換えだけを近いとみなす見本の埋め込みを使う |

**意味的検索は、段階 2 を置き換えない。** 無くても同じように動き、あれば言い換えの分だけ見つかる範囲が広がる。

##### 11.7.6.7 言い換えの登録との関係

会社の中だけの呼び名は、意味的検索でも結び付かないことがある。
登録した言い換え（第11.7.7節）は、意味的検索を入れた後も段階 2 の側で使い続ける。

#### 11.7.7 言い換えの登録（段階 2 の補い）

##### 11.7.7.0 言い換えは秘書が考える（第 0.115.0 版。ADR-0028）

**「育休」が「育児休業」のことだと、人なら想像がつく。秘書も自分で考える。** 人に言い換えの表を作らせない（原則 u11）。
2026-09-26、三浦さんが「言い換えをわざわざリストに移すのは、AI を使っている意味がない」と指摘した。

| 項目 | 規定 |
|---|---|
| いつ | 組織知識を探すたび（`knowledge.search` と、秘書が社内の規程を示す答え） |
| 何をするか | 高速の推論に質問を渡し、質問の言葉ごとに、社内の規程や文書で使われそうな言い方（正式な名前・略さない形・言い換え）を挙げさせる。挙げた言葉は、下の表の「言葉の組」と同じように効かせる（点数・答えでの示し方も同じ） |
| 待ち時間 | 2 秒で打ち切る。間に合わなければ言い換えなしで探す（探すこと自体は止めない） |
| 推論が使えないとき | 標準の言い換え（下の表）だけで探す |
| 登録した組 | これまでに会社が登録した組は、そのまま効かせる。**新しく登録する画面は置かない**（管理者ページの知識から「言い換え」を外す） |
| 挙げさせない言葉 | 質問に無い意味を足さない。挙げた言葉は探す語を広げるだけで、答えの根拠にはならない（根拠は見つけた節だけ） |

以下は第 0.114.0 版までの規定である。「自社の組」を画面で登録すること以外は、推論が挙げた言葉にもそのまま当てはまる。

意味的検索（第11.7.6節）を待たずに、よく使う言い換えを**登録した言葉の組**で結び付ける。
埋め込みを使わないため、費用がかからず、Phase 1 で入れられる。
意味的検索を入れた後も使う。会社の中だけの呼び名（部署の略称、社内の制度の通称）は、一般の意味からは結び付かないためである。

| 項目 | 規定 |
|---|---|
| 登録の単位 | 同じ意味の言葉の組（例: `育休、育児休業`）。1 組に 2〜10 語、各語 2〜30 字。1 社あたり 300 組まで |
| 効き方 | 質問から取り出した言葉（第11.7.3節）が組の語を含むとき、組のほかの語も探す。例: 「育休中の給与は？」の「育休中」は「育休」を含むので、「育児休業」でも探す |
| 向き | 組の中は、どの語からでも、ほかの語を探す |
| 点数 | 組の語は**まとめて 1 つの言葉**として数える。どれかが当たれば、その言葉を満たしたとみなし、点はいちばん高い語のものを使う。言い換えを足しても「満たした語の割合」（第11.7.3節）は薄まらない |
| 標準の言い換え | M2Office が、労務と経費でよく使う言い換えを用意し、既定で有効にする（下の表）。会社の設定でまとめて無効にできる。一部だけ直したいときは、標準を無効にして、自社の組として登録し直す |
| 自社の組 | 管理者ページの知識（第6.6.6節）で、1 行に 1 組を書く。語は「、」「,」「=」のどれで区切ってもよい。同じ語を自社の 2 つの組に入れることはできない |
| 標準との重なり | 自社の組と標準の組に同じ語があれば、両方の組の語を探す |
| 答えでの示し方 | 言い換えで探した場合、答えに「「育休」を「育児休業」と読み替えて探しました」と示す。利用者が、なぜその条が出てきたかを確かめられるようにする |
| 使う範囲 | 組織知識の検索（`knowledge.search` と、秘書が社内の規程を示す答え）。ヘルプの記事の検索には使わない |
| 記録 | 登録と変更は監査ログに残す（`knowledge.synonyms.save`） |
| 保存先 | 会社の設定（`tenant_settings`）の区分 `knowledge`。テナント境界は会社の設定と同じ |

**標準の言い換え**（M2Office が用意する。版とともに見直す）

| 組 | 主な場面 |
|---|---|
| 育休、育児休業 | 休暇 |
| 産休、産前産後休業 | 休暇 |
| 介護休業、介護休み | 休暇 |
| 有休、有給、年休、年次有給休暇 | 休暇 |
| 忌引、忌引き、慶弔休暇 | 休暇 |
| 残業、時間外労働、時間外勤務 | 労働時間 |
| 休日出勤、休日労働 | 労働時間 |
| 在宅勤務、テレワーク、リモートワーク | 働き方 |
| 給料、給与、賃金 | 賃金 |
| ボーナス、賞与 | 賃金 |

言い換えは、**探すたびに秘書が考える**（第11.7.7.0節。第 0.115.0 版、ADR-0028）。管理者に提案して選ばせる形は採らない。
見つからなかった質問の扱い（Q-69）とあわせて決める（Q-83）。

### 11.8 成長ループ

第1.4節の優位 A-1〜A-3 は、以下のループとして実装される。

```
 ① 従業員が秘書に依頼する
        ↓
 ② 秘書が実行し、結果と文脈を個人記憶に蓄える
        ↓
 ③ 繰り返しを検知し、手順化を提案する（UC-08）
        ↓
 ④ 本人が承認 → 個人用エージェントとして登録
        ↓
 ⑤ 有用なら昇華 → チーム・全社のエージェントへ
        ↓
 ⑥ 会議・文書・実行履歴が組織知識として積み上がる
        ↓
 ⑦ 新しく入った従業員の秘書も、最初からその知識を使える
        ↓
      ①へ戻る（精度と範囲が上がった状態で）
```

**このループが回り始めると、使用期間そのものが競争優位になる。**
乗り換えれば、蓄積された組織知識と学習済みの秘書を失うことになるためである。

測定すべき指標（第18章に反映）:

| 指標 | 意味 |
|---|---|
| 組織知識の件数と参照回数 | 蓄積が実際に使われているか |
| 昇華の件数 | 個人の学習が組織に還元されているか |
| 手順化提案の受諾率 | 提案が的を射ているか |
| 新入社員の立ち上がり時間 | 知識が継承されているか |

### 11.9 会話ログと学習利用

**この節で決めること**: やり取りをどう残し、何に使うか。

#### 11.9.1 残すもの

| 対象 | 保存 | 用途 |
|---|---|---|
| 秘書との対話（音声・テキストとも、テキスト化した内容） | する | 参照、サポート、改善 |
| 業務エージェントの実行過程 | する | 監査、再現、改善 |
| 承認の判断とコメント | する | 監査、学習の評価信号 |
| **音声の録音そのもの** | **しない** | 第10.5.3節 |

#### 11.9.2 用途

| # | 用途 | 内容 |
|---|---|---|
| 1 | 本人の参照 | 「前に頼んだ件」を遡れる |
| 2 | 秘書の学習 | 個人記憶の材料になる（第10.7節） |
| 3 | カスタマーサポート | 問い合わせ時に状況を確認する |
| 4 | 品質改善 | 失敗・聞き返し・却下が多い箇所を特定する |
| 5 | 将来の学習 | 応答品質の改善に用いる |

#### 11.9.3 「学習」の意味を区別する

**本書で「学習」と書く場合、性質の異なる 2 つを指しうる。混同してはならない。**

| 区分 | 内容 | M2Office での扱い |
|---|---|---|
| **モデルの学習** | LLM の重みを更新すること（追加学習・ファインチューニング） | **行わない。外部提供者にも行わせない** |
| **システムの蓄積** | 蓄積した情報を参照して応答の精度を上げること | **行う。これが製品価値の中核である** |

整理すると次のようになる。

- **LLM そのものは賢くならない。** モデルは提供された状態のまま使う。
- **M2Office は企業ごとに賢くなる。** 過去のやり取り・成果物・知識が企業内に蓄積され、
  それを参照することで応答が的確になる。

この区別を誤ると、第16.5節の「顧客データをモデルの学習に用いない」という約束と、
第1.4節の「使うほど賢くなる」という製品価値が矛盾して見える。**両立する。**

##### データが渡る範囲

| 経路 | データが渡るか | 説明 |
|---|---|---|
| 外部 LLM 提供者の学習 | **渡らない** | 契約で明示的に除外する |
| 外部 LLM への推論リクエスト | その場限りで渡る | 応答生成のために送信される。学習には使われない |
| **テナント内の蓄積** | **渡る** | 会話ログ・個人記憶・組織知識として企業内に保存され、以後参照される |
| 他テナント | **渡らない** | 既定では行わない（下表 C） |

**企業内には必ずデータが渡り、システムとして成長する。** これが設計の前提である。
データが企業内に残らなければ、秘書は毎回はじめましての状態になり、
第10.7.1節の「いつものあれ」は成立しない。製品として成り立たない。

##### 蓄積したデータの利用範囲

| 区分 | 内容 | 方針 |
|---|---|---|
| A | 本人の秘書が参照する | 既定で行う |
| B | 同じテナント内で共有する | 秘書が判断して会社の知識にする（第11.3節） |
| C | **テナントを越えて利用する** | **既定では行わない**。個別に同意を得た場合に限る |

顧客が最も警戒するのは C である。
「自社の会話が他社のために使われる」と受け取られれば、
第1.1節の懸念（情報漏洩のリスク 33.5%）に直結する。
**B と C を混ぜて説明しない**ことを、規約と製品説明の両方の要件とする。

##### 将来のファインチューニング

テナント専用のモデルを追加学習する構想は、現時点では採らない。
第10.7.1節の到達点は蓄積と検索で実現できるため、
モデルを触らずに済むほうが乗り換え可能性（第20.2節）を保てる。
TBD: 将来的に検討するか（Q-41）。

#### 11.9.4 同意と統制

| 項目 | 方針 |
|---|---|
| 利用目的の明示 | 規約とプライバシーポリシーに、保存する対象と用途を具体的に記載する |
| 同意の取得 | 契約時にテナント管理者へ、初回ログイン時に各従業員へ提示する |
| 個人の制御 | 本人は自分の会話ログを参照・削除でき、学習対象から外せる（第11.5節） |
| 除外指定 | 「この会話は残さない」と指示できる |
| 運営の閲覧 | サポート目的の閲覧は第23.6節の統制に従う（顧客同意・期限・記録・通知） |
| 保持期間 | 逐語は 4 週でローテーション、要約と学習用データは長期保持（Q-36） |
| 退職時 | 個人記憶は削除する。会話ログは監査の範囲で保持する（第11.6節） |

**個人情報保護法との関係**: 会話ログには取引先の担当者名など第三者の個人情報が含まれうる。
利用目的を特定して明示することが必要になるため、規約文面は専門家の確認を受ける（Q-09）。

##### 11.9.4.1 会話ログの実装（第 0.55.0 版）

| 項目 | 規定 |
|---|---|
| 残す単位 | 秘書とのやり取り 1 往復を 1 件とする。本人の依頼・秘書の応答・応答の層・取り次いだ業務・結び付いた実行を組にする |
| 残さないもの | 音声の録音（第10.5.3節）。ヘルプの記事の全文と、知識の本文（出典だけを残す） |
| 見られる人 | **本人だけ**。管理者も運営も見られない（不変則 I-10）。運営の閲覧は第23.6節の手続きによる |
| 検索 | 本人が語句で検索できる。個人設定の「記憶とデータ」から開く |
| 削除 | 本人が 1 件ずつ、またはまとめて消せる |
| 残さない指定 | 個人設定で「会話を残す」を切ると、以後残さない。秘書に「この会話は残さないで」と言うと、**直近 1 時間の自分の会話を消す** |
| 保持 | 4 週。ワーカーが 1 日 1 回、過ぎたものを消す（第11.9.6節） |
| 退職・削除 | 利用者を消すと、その人の会話も消える |
| 記録 | 監査ログ `conversation.delete`・`conversation.clear`。**中身は監査ログに入れない** |

#### 11.9.5 設計上の含意

| # | 含意 |
|---|---|
| 1 | 会話ログは実行履歴・監査ログとは別に、検索できる形で保存する |
| 2 | テナント ID とユーザー ID で常に絞り込める構造にする（不変則 I-2、I-10） |
| 3 | 学習に使う際は、テナントを越えない処理であることを機械的に保証する |
| 4 | **入力・出力・評価を組にして残す**（承認されたか、修正されたか、却下されたか） |

**第 4 項が要点である。** 単に会話を残すだけでは学習の材料にならない。
「その応答が良かったか」を示す信号を同時に記録して、はじめて改善に使えるデータになる。
承認ゲート（第9.4節）は品質の門番であると同時に、**評価信号の供給源**でもある。

#### 11.9.6 保持とローテーション

**すべてを永久に残さない。層に分けて、それぞれ別の期間で持つ。**

| 層 | 内容 | 保持期間 | ローテーション |
|---|---|---|---|
| システムログ | 障害調査用のアプリログ。書き方は開発規約 第7章 | **4 週（週次で 4 世代）** | する |
| **会話ログ（逐語）** | やり取りの全文 | **4 週** | する |
| **会話の要約** | 会話ごとの要約と、そこから抽出した事実 | 長期 | しない |
| 学習用データ | 入力・出力・評価の組（第11.9.5節） | 長期 | しない |
| 個人記憶・組織知識 | 抽出され定着した知識 | 在籍中／恒久。社内規程の古い版と廃止した規程は 7 年（第11.11.2節） | **秘書が学んだこと（個人の記憶と会社の知識）は週 1 回整理し、まとめたもの・古くなったもの・半年使わなかったものをしまう。しまったものは 1 年で消す**（第11.11.4節） |
| 実行履歴・成果物 | ジョブ、実行、生成した文書 | 第19.3節による | しない |
| **監査ログ** | 誰が何をしたかの証跡 | **3 年以上。ローテーションしない** | **しない** |

##### 逐語ログを 4 週で消しても支障がない理由

第10.7.1節の「いつものあれ」に必要なのは、**逐語のやり取りではなく、
そこから抽出された事実と、成果物へのリンク**である。

| 依頼 | 参照するもの | 逐語ログが要るか |
|---|---|---|
| 「いつものレポート出して」 | 実行履歴と成果物 | 不要 |
| 「前と同じ形式で」 | 過去の成果物 | 不要 |
| 「B 社の担当者、変わったよね」 | 個人記憶に定着した事実 | 不要 |
| 「先週こう言ったはず」 | 会話の要約 | あれば望ましい |

逐語ログが要るのは最後の場面だけであり、多くは要約で足りる。
**4 週を過ぎた会話は、要約と抽出済みの事実に置き換える**（圧縮）。

##### 圧縮の処理

| 段階 | 内容 |
|---|---|
| 1 | 4 週を過ぎた会話を対象に、要約を生成する |
| 2 | 会話から事実を取り出し、そのまま個人記憶にする（第11.5.2節、ADR-0027） |
| 3 | 学習用の組（入力・出力・評価）を、個人を特定しない形に整えて保存する |
| 4 | 逐語ログを削除する |

**段階 3 が「自らの学習に使う」の実体である。**
逐語ログを消しても、応答の改善に必要な情報は残る。

##### 注意すべき点

| # | 内容 |
|---|---|
| 1 | **監査ログはローテーションしない。** 会話ログとは別系統として扱う（第16.6節） |
| 2 | 権限区画（第16.3節）のデータを含む会話は、要約にも区画の印を引き継ぐ |
| 3 | 本人が「残さない」と指定した会話は、圧縮の対象にもしない |
| 4 | 圧縮は非同期で行う。実行中の会話には触れない |
| 5 | 要約の生成にも推論コストがかかる。夜間など負荷の低い時間帯に実行する |

**保持期間は延ばせない**（Q-50 で決定）。逐語は 4 週で消し、会社の設定でも延ばせない。
預かる量を増やさず、説明を単純に保つためである。監査に要る証跡は監査ログ（3 年以上）が担う。

##### 実装（第 0.55.0 版）

| 段階 | 内容 | 状態 |
|---|---|---|
| 1 | 会話の要約を作る | **実装済み**。会話と業務の出来事のたびに、その日の要約に書き足して長期に持つ（第 0.135.0 版。逐語が消えた後も残すため） |
| 2 | 会話から事実を取り出し、個人記憶にする | **実装済み**（第11.5.2節）。会話のたびに、秘書がその場で自分で覚える（第 0.135.0 版、ADR-0039） |
| 3 | 学習用の組（入力・出力・評価）を保存する | **会話ごとに入力・出力・層・結び付いた実行を残す**。評価は、結び付いた実行の承認の結果から引く（第11.9.5節 第 4 項） |
| 4 | 逐語ログを消す | **実装済み**。ワーカーが 1 日 1 回、4 週を過ぎた会話を消す |

### 11.10 知識の可搬性 ― OKF への準拠

**この節で決めること**: 蓄積した知識を、どういう形で出し入れするか。

#### 11.10.1 OKF とは

OKF（Open Knowledge Format）は、AI エージェントに組織の知識を渡すための
ベンダー中立なオープン仕様である。Google Cloud が 2026 年 6 月に v0.1、
同年 7 月に v0.2 を公開した。

| 項目 | 内容 |
|---|---|
| 形式 | YAML フロントマターを持つ Markdown ファイルのディレクトリ |
| 必須フィールド | `type` のみ |
| 推奨フィールド | `title`、`description`、`resource`、`tags` |
| v0.2 の追加 | 来歴（`sources`）、信頼（`generated`、`verified`）、鮮度（`status`、`stale_after`）、計算（`runtime` ほか） |
| 予約ファイル名 | `index.md`（一覧）、`log.md`（更新履歴） |
| 配布 | tarball、git リポジトリ、ファイルシステム。専用の SDK やサーバーを要しない |
| 設計方針 | 最小限の規定、生産者と消費者の独立、プラットフォームではなくフォーマット |

#### 11.10.2 M2Office が準拠する理由

| # | 理由 |
|---|---|
| 1 | **顧客の知識を囲い込まない**。原則 p10「情報は顧客のもの」を、標準形式での持ち出しとして実装できる |
| 2 | **拡張機能に知識を同梱できる**。業種別の用語集・規程のひな形を OKF バンドルとして配布できる（第12.3節） |
| 3 | **士業・業界団体が知識を提供する経路になる**。第13.6節のエコシステム戦略と直接つながる |
| 4 | Git・Obsidian など既存のツールでそのまま扱える。顧客側の編集手段を選ばない |
| 5 | 特定のクラウド・モデル提供者に依存しない。第20.2節の乗り換え方針と整合する |

#### 11.10.3 準拠の範囲

**内部表現は OKF に合わせない。OKF は入出力の形式として扱う。**

| 層 | 形式 |
|---|---|
| 内部の保持 | データベース（第19.1節 `knowledge_item` ほか） |
| **取り込み・持ち出し** | **OKF バンドル** |
| 配布 | OKF バンドル（拡張機能への同梱、マーケット経由） |

OKF は v0.2 であり、仕様はまだ動く。
内部構造を仕様に合わせると、改版のたびに全体が揺れる。
**変換の層を 1 枚挟む**ことで、仕様変更の影響を入出力に閉じ込める。

#### 11.10.4 M2Office の概念との対応

OKF v0.2 のフィールドは、本書で既に規定した仕組みと素直に対応する。

| OKF のフィールド | M2Office での対応 |
|---|---|
| `type` | 知識の種別（規程、議事録、価格表、用語集など） |
| `title` / `description` / `tags` | 組織知識の属性（第19.1節） |
| `resource` | 元の Google ドライブ上のファイルへのリンク |
| `generated`（誰がいつ作ったか） | 登録者と登録日時 |
| **`verified`（誰がいつ検証したか）** | **会社の知識にした記録（秘書が加えたか、管理者が登録したか。第11.3節）** |
| `status`（draft / stable / deprecated） | 知識の版管理 |
| **`stale_after`（失効日）** | **鮮度の管理（第11.7節）** |
| `sources` | 出典（第11.7節の「出典の明示」） |

**`verified` と `stale_after` の対応は好都合である。**
第11.3節の二重承認（本人 → 管理者）は、そのまま OKF の検証記録として表現できる。
「誰が確認した知識か」を標準形式で持ち出せることは、
顧客が M2Office を離れた後もその知識を使い続けられることを意味する。

### 11.11 知識の種類と管理（第 0.193.0 版、ADR-0056。第 0.194.0 版で実装）

**会社の決まり（社内規程）と、秘書が学んだことを、同じ一覧・同じ扱いにしない。**
三浦さんの指摘（2026-09-30）: 社内規程・旅費規程のような会社のルールは管理の手段であり、人事・給与もそれをもとに設定を作る。
消されると会社の根幹が狂う。一方、秘書が会話から学んだことはどんどん増える。検索で一緒に探すのはよいが、画面で同列に並べ、同じ削除のボタンで消せるのは困る。
あわせて、秘書が学んだことが増え続けるだけで、まとめたり減らしたりする仕組みが無かった（第 0.192.0 版の本番の会社で、社内規程 3 件・議事録 4 件に対し、秘書が学んだこと 94 件、個人の記憶 628 件）。

#### 11.11.1 3 つの種類

| 種類 | 中身の例 | 登録 | 直す | 検索から外す | 根拠に出す順 |
|---|---|---|---|---|---|
| **社内規程** | 就業規則・賃金規程・育児介護休業規程・経費規程・旅費規程・稟議基準・36 協定などの労使協定 | 管理者が登録する | 管理者が改定する（前の版を残す）。秘書と業務は書き換えない（第11.5.3節） | 管理者が**廃止**する（1 年は戻せる） | 1 |
| **議事録** | 会議の決定事項・保留事項 | 議事録の業務が、承認②のあとに登録する（第9.5.2節） | 管理者が直す | 管理者が廃止する（1 年は戻せる） | 2 |
| **秘書が学んだこと** | 取引先の通称・担当の割り振り・社内のやり方 | 秘書が会話から加える（第11.3節） | 使う人が会話で直す（第11.5.3節）・管理者 | 管理者が消す。週 1 回の整理で**しまう**（第11.11.4節） | 3 |

区別は登録の経路で決まり、人に選ばせない。管理者が「知識」の画面から登録したものは社内規程、業務が登録したものは議事録、秘書が加えたものは秘書が学んだこととする。
これまでに登録したものは、移行のときに同じ決まりで分ける。

#### 11.11.2 社内規程の管理

| 項目 | 規定 |
|---|---|
| 版 | 改定して保存するたびに、前の版の本文を残す。版ごとに**施行日**を持つ（既定は保存した日。管理者が直せる。規程の附則に施行日があれば、AI が読んで案にする） |
| 改定前を尋ねられたとき | 「改定前の規程では何日だったか」には、古い版を引き、版と施行日を添えて答える。ふだんの答えは施行している版から作る |
| 施行前の版 | 施行日が先の版を保存したら、施行日までは前の版で答え、施行日から新しい版に切り替える。切り替えは検索の時点の日付で決める（夜中の処理を待たない） |
| 廃止 | 管理者が「廃止する」を押すと、検索から外し、「廃止した規程」の一覧に移す。**確認の画面は挟まない**。代わりに、廃止から 1 年は「戻す」で元に戻せる（戻せる形で守る。ADR-0028） |
| 残す期間 | 古い版と廃止した規程の本文は **7 年**残す（人事・給与の記録と同じ。第30.17節。給与の計算がどの版の規程にもとづいたかをたどるため）。1 年を過ぎた廃止の規程は「戻す」を出さないが、版の履歴としては読める |
| 書き換えない | 秘書・業務・会話の訂正は、社内規程を書き換えない・廃止しない。会話で「規程が違う」と言われたら、管理者に伝えるよう答える（第11.5.3節） |
| 人事・給与とのつながり | 人事・給与の「規程から設定の案」（第30.8.2節）は、ファイルを渡すほか、**登録した社内規程から選んで**読める。規程を登録・改定したら、人事・給与の会社の設定と食い違う項目（割増率・締め日・手当など）を、AI が管理者ページの人事・給与の設定の欄に示す（会社の設定を直せるのは管理者のため。直すかは管理者が決める。第30.8.1節）。AI の答えを版に残し、見るときにその時の設定と並べ直す（直した項目は出さない） |
| 記録 | 監査ログ `knowledge.rule.create`・`knowledge.rule.revise`（版と施行日）・`knowledge.rule.retire`・`knowledge.rule.restore`。本文は入れない |

#### 11.11.3 議事録

議事録は会社の記録であり、社内規程と同じく**消さずに廃止**にする（1 年は戻せる）。版は残さない（直した後の本文だけを持つ）。
廃止してから 1 年を過ぎたものは消す。

#### 11.11.4 秘書が学んだことの整理

**秘書が学んだこと（会社の知識と、各人の記憶）は、週 1 回、秘書が整理する。** 人に一件ずつ見直させない（ADR-0028）。

| 項目 | 規定 |
|---|---|
| いつ | 週 1 回、夜間（ワーカー。日本時間の日曜 23 時〜月曜 5 時に、前の整理から 6 日より経っていれば行う）。推論が使えない環境では整理しない（残す期間を過ぎたものを消すことだけは行う） |
| 対象 | 会社の知識のうち秘書が学んだこと（会社ごと）と、各人の記憶（本人ごと。本人の記憶は本人の処理の中だけで扱い、ほかの人の記憶と混ぜない。不変則 I-10） |
| まとめる | 同じ事柄についての文を 1 つの文にまとめる。まとめた文は新しく登録し、もとの文を**しまう**。まとめた文には、もとの文を記録として結び付ける |
| 古くなったもの | 同じ事柄で新しい事実があるもの（担当が変わった・取引先の名前が変わった）は、古いほうをしまう |
| 使われないもの | **半年**、答えの根拠にも会話の材料にも使われなかったものをしまう。使った日を、根拠や材料に選ばれたときに記録する |
| しまう | 検索と会話の材料から外し、「しまったもの」に移す。管理者（会社の知識）と本人（自分の記憶）が「しまったもの」を見て、戻せる。**しまってから 1 年で消す** |
| 書き換えないもの | 社内規程・議事録は整理の対象にしない。秘書が学んだことが社内規程と食い違うときは、秘書が学んだほうをしまう |
| 権限区画 | 区画の印の付いたものは、同じ区画のものとだけまとめる（第16.3節） |
| 推論に渡すもの | 同じ種類の中の文だけ。会社の知識と本人の記憶を同じ推論に渡さない |
| 量の見張り | 1 回に扱う数に上限を置き（案: 会社の知識 500 件・本人の記憶 300 件）、残りは次の回に回す。費用は利用量に含める（第21章） |
| 記録 | 監査ログ `knowledge.consolidate`・`memory.consolidate`（まとめた数・しまった数・消した数だけ。**中身は入れない**） |
| 見せ方 | 本人への知らせは行わない。本人は個人設定の「記憶とデータ」で、管理者は「知識」の「秘書が学んだこと」で、しまったものと理由（まとめた・古い・使われない）を見られる |

#### 11.11.5 管理者ページの「知識」（第6.6.6節）

| 小分け | 中身 |
|---|---|
| 社内規程 | 規程の一覧（題名・施行している版と施行日・次に施行する版・節の数）。登録・改定・版の履歴・廃止。廃止した規程の一覧と「戻す」 |
| 議事録 | 業務が登録した議事録の一覧（会議の日・由来）。直す・廃止。廃止したものと「戻す」 |
| 秘書が学んだこと | 秘書が加えたものの一覧（使った日・もとになった会話の日。名前は出さない。第11.3.1節）。消す。しまったもの（理由つき）と「戻す」。最後に整理した日と、まとめた数・しまった数 |

削除の操作は「秘書が学んだこと」にだけ置く。社内規程と議事録には「廃止」を置き、同じ見た目のボタンにしない。
