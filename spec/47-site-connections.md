## 47. 会社のサイトの接続（複数のサイト・MCP でのつなぎ・会話の中での承認。第 0.585.0 版で案、第 0.586.0 版で確定。Q-368〜Q-374、ADR-0148）

この章で決めること: **会社の Web サイトを、いまの REST API に加えて、サイトの運営会社が出す MCP でもつなげるようにする**こと。あわせて、**会社が複数のサイトを持ち、頼むたびに対象のサイトを選べる**ようにすること。**承認を会話の中で済ませ、一連の手順を画面を移らずに進められる**ようにすること。
サイトの持ち方、MCP の確定の手順の汎用の扱い、会話の中での承認、対象のサイトの選び方、接続の道具を使う汎用の業務、権限と記録、行わないこと、段階。

**この章は確定した**（2026-11-15 に三浦さんが、接続の道具を使う汎用の業務（第47.7節）を足したうえで、Q-368〜Q-374 をおすすめのとおりとした）。段 1 を第 0.586.0 版から実装する（第47.10節）。

### 47.1 目的と位置づけ

2026-11-15 に三浦さんが、WordPress でサイトを提供する会社が独自の MCP を出し始めていることを示した。導入先のクリニックのサイトも、運営会社が WordPress で作って運営しており、その運営会社の MCP でつなぐよう頼まれた。三浦さんは試しのサイトをその MCP でつなぎ、Claude Code から会話で問題なく使えることを確かめた。そのうえで、**各社の MCP で確認の手順が違うのを、M2Office がどう汎用に扱うかが命題だ**と述べた。続けて三浦さんは次の 3 つを求めた。

- 承認をすべて承認トレイで行うと、そのたびに画面を切り替えることになり手順が増えすぎる。一連の手順を滑らかに進められるようにする
- いまの REST API のつなぎを活かしたまま、MCP にも対応する
- 対象のサイトを選べるようにする

いまの M2Office のサイトとのつなぎは、次のとおりである。

| もの | いま |
|---|---|
| サイトの数 | 会社で 1 つ（「接続 › WordPress」。第6.6.2.1節） |
| つなぎ方 | REST API（`wp-json/wp/v2`）とアプリケーションパスワード（ADR-0140） |
| 使う機能 | コラムの作成・お知らせの作成・サイトの更新・Webの分析・サイトの見張り（コメントとプラグインの状態） |
| MCP | 汎用のコネクタ（第6.6.3節）でつなぎ、秘書と業務がツールを使える。ただしサイトの機能とはつながっていない |
| 承認 | 業務が承認の段で止まると、承認トレイとお知らせに届く。秘書は「承認を待っています」と伝えるだけ（第10.9.6節） |

### 47.2 各社の MCP の確認の手順（2026-11-15 に調べたこと）

試しのサイトの MCP（医院向けに WordPress のサイトを作って運営するサービスのもの。ツール 124 件）の説明を読むと、AI に向けた「確認」の指示が文で書かれている。性質の違う 5 種類が混ざっている。

| 種類 | 例 |
|---|---|
| ① 確定への了承 | 「見直しで示した内容に、利用者から明示的な了承を得られた場合にだけ確定を呼ぶ」 |
| ② 好みを聞く | 掲載の期限を提案する・ポップアップを出すかを提案する・検索エンジンに載せるかを利用者に確かめる・お知らせか固定ページかを相談する |
| ③ 必ず見せる注意 | パーマリンクを変えると URL が変わる注意・予定を作った後に別の経路で変わった（`baselineChanged`）・検索エンジンへの掲載の可否・公開の回数を 2 回分以上使う |
| ④ 終わった後の知らせ | 確かめのための一時公開の戻し忘れの注意・公開の残りの回数・使い切ったときに、人が WordPress にログインして追加を承認する URL |
| ⑤ 確認を飛ばしてよい | 「検索に出ないサイトでは、利用者の了承を待たずに確定してかまいません」 |

書き換えは、**準備（予定を保存して確認のトークンを返す。変更はしない）→ 見直し（予定の `current` と `proposed` を返す）→ 確定（トークンを使って適用する）**の 3 段である。戻す道具（`restore_*`）も持つ。

ほかの形もある。

| 形 | 例 | 確定の合図 |
|---|---|---|
| トークンの形 | 上のサービス | 準備で受け取ったトークンを確定に渡す |
| 目印の引数の形 | WordPress.com の MCP（第45.18.5節） | 書く操作の引数 `user_confirmed` を真にする |
| すぐ書く形 | Slack の投稿など | 呼べばすぐ書かれる（いまの承認ゲート） |
| 相手から問う形 | MCP の決まりの `elicitation`（サーバーが呼び出しの途中で利用者に入力を求める） | 応じた答えで続く |

Claude Code は会話をするので、この指示を読んでその場で人に聞き、了承を得てから確定を呼べる。M2Office の業務は、途中で人に聞かずに進み、社外に出る所だけを承認で止める（第9.4.0節、ADR-0028）。この違いを埋める決まりを第47.4節に置く。

### 47.3 サイトを複数持つ

**会社は、サイトを複数つなげる。** つなぎ方はサイトごとに、REST API か MCP かを選ぶ。

| 項目 | 規定 |
|---|---|
| 場所 | 管理者ページの「接続 › WordPress」を「接続 › 更新サイト」に改め（第 0.585.0 版で「サイト」とし、第 0.592.1 版で、意味が広すぎるとして三浦さんが「更新サイト」に改めた）、つないだサイトを並べる。1 件につき、名前・URL・つなぎ方・使える状態 |
| REST API のサイト | いまと同じ（URL・会社の利用者・アプリケーションパスワード。つながるかを確かめてから預ける）。一人ひとりの WordPress の利用者（第45.16節）は、サイトごとに持つ |
| MCP のサイト | 「接続 › コネクタ（MCP）」に登録した接続の中から選ぶ。サイトの名前と URL は、その接続の読むだけのツール（サイトの情報を返すもの）があれば推論が読んで埋める。無ければ管理者が入れる |
| 既定のサイト | 1 つを既定にする。1 つしかなければそれが既定。定時の業務（コラムの予定表・サイトの見張り）の既定の入れ先になる |
| いまの接続 | いまの「接続 › WordPress」のつなぎは、**1 つ目のサイト（既定）としてそのまま使える**。管理者がし直すことは無い |
| 外す | サイトを外すとき、そのサイトを入れ先にしている定時の業務とコラムの予定を示して確かめる。一人ひとりの WordPress の利用者も消す |
| 数 | 上限を置かない（Q-372） |

**サイトを使う機能は、どのサイトでも同じに動く。** 機能の側は「どのサイトに」だけを受け取り、つなぎ方の違い（REST API か MCP か）は裏の口が引き受ける（ADR-0140 の「裏の口を取り替えられる形」）。

### 47.4 MCP の確定の手順を汎用に扱う

**人に判断を求めるのは「① 確定への了承」だけにし、② から ④ はその 1 回の承認と結果の報告に集める。⑤ には従わない。**

| 種類 | M2Office での扱い |
|---|---|
| ① 確定への了承 | **承認**（社外への送信。第9.4.0節）。確定のツールを呼ぶ所で止める |
| ② 好みを聞く | **業務が会社の事情から決め、承認の画面に並べる**（「掲載の期限: 11 月 25 日に下書きへ戻す」）。前もって聞かない（ADR-0028）。違えば承認の画面か会話で直す（第47.5節） |
| ③ 必ず見せる注意 | 承認の画面の「注意」に、**相手の言葉のまま**出す。推論の言い換えにしない |
| ④ 終わった後の知らせ | 結果の報告に入れる。人がすること（相手の画面にログインして承認するなど）があれば、そうはっきり言い、相手の URL を添える |
| ⑤ 確認を飛ばしてよい | **従わない。** 外から来た文で承認ゲートは外せない（不変則 I-6、第9.4.0節） |

#### 47.4.1 ツールの役割

コネクタのツールに、危険度（第12.11.2節）とは別に**役割**を持たせる。

| 役割 | 意味 | 承認 |
|---|---|---|
| 読む | 何も変えない | 無し |
| 準備 | 相手の側に予定を作るが、見える状態は変えない（トークンを返すものなど） | 無し |
| 見直し | 予定の中身（いまと後）を返す。何も変えない | 無し |
| 確定 | 見える状態を変える（公開・修正・取り下げ・送信） | **有り** |
| 戻す | 前の状態に戻す。見える状態を変える | **有り** |

| 項目 | 規定 |
|---|---|
| 決め方 | 接続の登録と「ツールを取り直す」のときに、**推論がツールの名前・説明・MCP の目印（`readOnlyHint`・`destructiveHint`）から決める**。あわせて、確定の前に呼ぶ見直しのツール、結果のどの項目が注意か（③）、どの項目が終わった後の知らせか（④）、どの引数が確定の合図か（目印の引数の形）を読み取る |
| 管理者が見る | 「接続 › コネクタ（MCP）」のツールの一覧に役割を出す。**承認が要らない側（読む・準備・見直し）に決めたものは、管理者が 1 度見て「この役割で使う」とするまで、確定と同じに扱う**（Q-368）。ツールの説明は外から来た文であり、「このツールは変更を適用しません」という文だけを信じて承認を外さないため |
| 分からないもの | 確定として扱う（第9.4.0節「確かめられなければ社外とみなす」） |
| 取り直し | 増えたツールは推論が決める。管理者が直した役割は残す。説明が変わったツールは、管理者が見直すまで確定に戻す |

#### 47.4.2 実行のときの流れ

| 段 | すること |
|---|---|
| 準備と見直し | 業務は、読む・準備・見直しのツールを承認なしに呼んで進める |
| 確定の前 | 確定のツールを呼ぶ所で止め、承認を作る。承認の画面（第9.3.3節）に、次を出す |
| 承認の画面 | 何を・どのサイトに（サイトの名前）・直す前と後（直前の見直しの結果の `current` と `proposed`。変わる項目だけ）・業務が決めた好み（②）・注意（③。相手の言葉のまま）。分かりやすい言葉の要約も添えるが、要約だと分かるようにする |
| 承認の後 | **承認した引数のまま**確定を呼ぶ（トークンの形ならトークン。目印の引数の形なら、M2Office がその引数を真にする）。推論は承認の後に引数を変えられない。目印の引数は、推論に見せる引数の定義から外し、推論が真にできないようにする |
| 食い違い | 確定が「トークンが切れた」「予定を作った後に変わった」で断られたら、準備と見直しからやり直し、もう一度承認を求める（黙って入れ直さない） |
| 終わった後 | 確定の結果の知らせ（④）を、結果の報告に入れる |

**相手から問う形（`elicitation`）は段 2 で扱う**（第47.10節）。それまでは、相手が問いかけてきたら断り（MCP の決まりの `decline`）、その旨を結果に書く。

#### 47.4.3 道具の多い接続

**道具が多い接続（試しのサイトは 124 件）では、業務が使う道具を先に絞る。** 推論にまず名前と短い説明の一覧を渡して要るものを選ばせ、選んだものの引数の定義だけを詳しく渡す。相手が道具を探す道具（操作の一覧を返すもの）を持っていれば、それも使える。

### 47.5 会話の中で承認する

**秘書に頼んで始まった業務の承認は、秘書との会話の中に出し、その場で判断できるようにする。** 承認トレイへ移らなくてよい。

| 項目 | 規定 |
|---|---|
| 出す所 | 秘書の会話の、その依頼の答えの下に、承認の中身（承認トレイの 1 件と同じもの。第6.2.4節）を開いた形で出す。「承認」「却下」のボタンを置く |
| 対象 | 本人が操作して起こした業務（秘書に頼んだもの・画面で「承認へ進む」を押したもの）の承認で、**本人が判断できるもの**（`approver: requester`、または本人が承認者の役割を持ち権限区画に入っているもの。第9.2.3節） |
| 承認トレイ | **一連の流れの中の承認は、承認トレイに出さない**（第 0.589.0 版、第 0.590.0 版で広げた）。本人が操作して起こした業務（秘書に頼んだ・画面で「承認へ進む」を押した・そこから続けて起きた業務・秘書の段取りの段）の承認で、本人が判断でき、作られてから 12 時間の内のものは、秘書のキャンバスでだけ判断する。承認トレイ（と件数）に出すのは、時間的につながっていないもの: ほかの人の依頼の承認・システムが起こした業務（定時実行・会議の後の自動の議事録・先回りの準備・相手からの日程の返事・LINE の会員の見張り・外部のアプリからの送信）の承認・12 時間を過ぎたもの。業務を起こすときに、本人が操作して起こしたかシステムが起こしたかを記録する（`jobs.started_by`。移行 209）。2026-11-15 に三浦さんが、お知らせを出す・サイトに入れるといった一連の流れの中で、そのたびに承認トレイへ移って承認するのは使いにくく、件数も増えると決め、承認トレイは時間がかかるもの・外から頼まれたものにするよう求めた |
| 本人が判断できない承認 | 会話には出さない。秘書は「〇〇さんの承認を待っています」と伝える（いまと同じく承認トレイとお知らせに届く） |
| 管理者の承認が加わるとき | 本人の分は会話で判断する。管理者の分は承認トレイに届く（第9.2.3節） |
| 言葉での直し | 承認を待っている間に本人が「期限は来週にして」のように直しを頼んだら、その承認を却下し（直しの言葉を記録に残す）、直しを入れて業務をやり直す。新しい承認が会話に出る |
| 言葉での却下 | 「やめて」「出さないで」は、その承認を却下する |
| 言葉での承認 | **しない**（Q-369）。承認はボタンを押して行う。社外に出る操作の取り違えを防ぐため（不変則 I-11 と同じ考え） |
| 続きの報告 | 承認の後、業務は続きから進み、終わったら同じ会話で結果を伝える（第10.11.7節）。確定の後の知らせ（第47.4.2節）もここに入れる |
| 1 回にまとめる | 1 つの依頼で同じサイトに確定が何回も要るときは、業務がまとめて 1 回の承認にする（相手が 1 回の確定で受けられる形なら 1 回で確定する） |
| 音声・Google Chat | この版では会話の画面だけ。音声と Google Chat からの依頼の承認は、いまと同じく承認トレイ（Q-374） |

これはサイトに限らず、**本人が操作して起こしたすべての業務の承認**に当てはめる。画面で「承認へ進む」を押したとき（お知らせ・コラム・名刺のまとめてのメール・問い合わせの返事・発注のメール・会員への LINE・Web の依頼文など）も、承認トレイへ移さず、その画面のまま秘書のキャンバスを開いて判断する（第 0.590.0 版）（メールの送信・お知らせの作成なども、会話の中で判断できる。Q-373）。

### 47.6 対象のサイトを選ぶ

2026-11-15 に三浦さんが、2 つのサイトが「更新可能」に並んだサイトの更新の画面を見て、どうやって選ぶのかと尋ねた（第 0.588.0 版で、頼みの名前・サイトの更新の画面で選ぶ・聞き返すの形を作った）。続けて、コラムの作成とお知らせの作成の入れ先がどちらのサイトかを尋ね、秘書がお知らせを MCP のサイトの業務に取り替えると LINE やメールが抜けることを受けて、**入れる先は設定で決めるべきで、サイトの更新の画面で決めるのはよくない**と決めた（第 0.589.0 版）。

| 機能 | 対象のサイトの決め方 |
|---|---|
| コラムの作成 | **本人ごと**（第 0.592.0 版）。本人が使えるサイトが 1 つならそれ、2 つ以上なら個人設定の既定のサイト。既定が無ければ、承認へ進む前に「入れるサイトを決めてください」と出す（決まらないまま入れない） |
| お知らせの作成 | **本人ごと**（コラムと同じ）。秘書から頼んでも、お知らせの作成で進める（LINE・メール・サイネージも出す）。業務を取り替えない |
| サイトの更新（いまあるページを直す） | **① 頼みの中のサイトの名前（URL の名前・名前の終わりの「クリニック」などを外した言い方も。本人が使えないサイトなら、使えないと答える） → ② 本人が使えるサイトが 1 つならそれ → ③ 個人設定の既定のサイト → ④ その日の会話で聞き返して本人が答えたサイト → ⑤ 聞き返す**の順で決め、決まったサイトの業務に取り替える（REST API のサイトは「サイトの直し案」、MCP のサイトはその接続の業務。第 0.591.0 版で ②③ を足した） |

**誰がどのサイトを使えるかは、管理者が接続ごとに決める**（第 0.591.0 版）。2026-11-15 に三浦さんが、サイトの更新の既定のサイトを足すよう求め、管理画面で接続を管理してそこで使える人を決め、複数の接続を使える人は個人設定で選び、1 つしか使えない人はそれが選ばれる形がいちばん分かりやすいと決めた。

| 項目 | 規定 |
|---|---|
| 使える人 | 「接続 › 更新サイト」の各サイトの行に「利用できる人」を置く（業務の利用範囲と同じ部品。既定は全員。第16.7節）。利用範囲の対象は `site-rest`・`site-mcp-<接続の ID>`。MCP のサイトは、サイトの更新の利用範囲にも入っている人だけが使える |
| 既定のサイト | 本人が使えるサイトが 2 つ以上あるときだけ、個人設定の「サービスとの接続」に「既定のサイト」を出す（本人の設定 `secretary.site`）。「決めない」も選べる（秘書が聞き返す）。使えるサイトが 1 つの人には出さない |
| サイトの更新の画面 | 本人が使えるサイトだけを並べる |
| コラムとお知らせ | 入れるサイトも本人ごと（上）。管理画面で入れ先を固定しない（第 0.592.0 版。2026-11-15 に三浦さんが、コラムの作成の設定に入れるサイトと会社の WordPress の URL が出ているのを見て、入れるサイトは個人設定で決めるはずで、管理画面で固定するとワークスペースで選べなくなると指摘した） |

| 項目 | 規定 |
|---|---|
| 聞き返し | 取り違えると社外に出るので、1 度だけ聞き返し（「どちらのサイトですか: 1. 〇〇・2. △△」）、名前か番号で受ける。答えたサイトはその日の会話の続きで使う。10 分の内に答えが無ければ、聞き返した頼みは忘れる。決まらないまま既定のサイトに入れない（Q-370） |
| MCP のサイトに入れる | コラムとお知らせは、承認の後に、そのサイトの業務（「サイトの直し案（サイトの名前）」）に入れる中身を渡して頼む（`connectors/site-handoff.ts`）。頼んだ本人として、秘書が起こした業務と同じに起こす（秘書のキャンバスで承認でき、終わったら秘書が伝える） |
| コラム | 読み物の記事（ブログ・コラムなど）の**下書き**として頼む。公開はしない（公開は人があとで頼む）。カバー画像は渡さない |
| お知らせ | 設定が「公開まで」なら、そのサイトの業務が下書き・公開の予定・相手の見直しまで進め、**相手の見直しの結果を見せて、もう一度承認を求める**（承認は 2 回。案 A）。「下書きまで」なら下書きだけ。お知らせの作成の承認の画面にも、MCP のサイトに頼むこと（公開なら 2 回目の承認があること）を出す |
| 承認の画面 | どのサイトかを、承認の画面の 1 行目に必ず出す（MCP のサイトは「「サイトの名前」のサイトで…」、サイトの更新の REST API のサイトは、MCP のサイトもあるときに「「URL の名前」のサイト: …」） |
| 機能の画面 | サイトの更新の画面に、REST API のサイトと MCP のサイトを並べる（選ぶ印は出さない） |

### 47.7 接続の道具を使う汎用の業務（第 0.586.0 版）

**この節の実行のしかた（3 つの段・承認の前の組み立て・段の初めの道具の選択）は、第48章（案。1 本の会話で進め、見える状態を変える呼び出しの所でだけ止める）で置き換える。** 振り分け・業務の名前と ID・使える人・MCP のサイトでできることは、この節のまま。

2026-11-15 に三浦さんが、試しのサイトの MCP を Claude Code に入れたとき、何も指示しなくても「お知らせを書いて」「固定ページを作って」だけで、MCP の説明を正しく読んで動いたことを示した。そのうえで、M2Office では MCP を入れるたびに秘書の振り分けを指定しなければならないのか、それではソフトの修正が要り MCP の意味が無いと尋ねた。

それまでの M2Office では、会社の接続の**読むだけのツール**は秘書の調べものに自動で渡っていたが（第12.11.0節）、**書くツールは、業務の定義（拡張機能か SKILL.md）がツールを名前で指したときだけ**使えた。秘書は「お知らせを書いて」を内蔵のお知らせの作成（REST API のつなぎ）に振り分け、MCP の道具は使わなかった。

**会社の接続ごとに、その接続の道具を使う業務を M2Office が自動で用意する。** MCP を入れるたびに、振り分けの決まり・業務の定義・ソフトを足さない。

**会社のサイトを扱う接続は、サイトの更新の付属の業務にする**（第 0.587.0 版）。同じ日に三浦さんが、接続の名前の業務が別にできたのを見て、これは何か、サイトの更新でどのサイトを直すかを選び、それが REST API か MCP かで分ければよい、特別な業務を作る理由が分からないと指摘した。利用者に見える業務は「サイトの更新」1 つにし、MCP のサイトは、その中の対象のサイトの 1 つとして扱う（第47.6節）。業務は画面にもメニューにも出さず、利用範囲はサイトの更新と同じにする。サイトでない接続（業務システムなど）の業務も、メニューには出さず、秘書が取り次ぐだけにする。

| 段 | すること | 接続ごとの作業 |
|---|---|---|
| 登録のとき | 推論がツールの名前と説明を読み、ツールの役割（第47.4.1節）と「この接続で何ができるか」の短い説明を作る（例: 医院のサイトのお知らせ・固定ページ・休診日の作成と公開） | なし |
| 振り分け | 秘書が依頼を振り分けるとき（第10.7.4節の層 2）、その説明を内蔵の業務と並べて候補に入れる。同じ頼みを両方でできるときは、話の流れと対象のサイト（第47.6節）で選ぶ | なし |
| 実行 | 汎用の業務が、その接続の道具の中から要るものを絞って受け取り（第47.4.3節）、相手の説明どおりに使う | なし |
| 確定 | 確定と戻すの道具の所で止まり、会話の中で承認する（第47.5節） | なし |

| 項目 | 規定 |
|---|---|
| 業務の形 | 段は 3 つ: 「進める」（読む・準備・見直しの道具。作る・直す頼みで準備の道具をどれも呼ばずに終えようとしたら、エンジンが一度だけ促す。第 0.592.2 版）→「承認」（依頼した本人）→「確定」（確定と戻すの道具）。確定の段は、承認の前に組み立てて承認の画面に出し、承認の後にそのとおり行う（第9.3.3節、ADR-0023）。確定の道具が無い接続は「進める」だけ |
| 業務の名前と ID | 会社のサイトを扱う接続は、サイトの更新の付属の業務「サイトの直し案（サイトの名前）」（`site-updates:site-<接続の ID>`）。サイトの名前と URL は、サイトの情報を返す読む道具（必ず渡す引数が無いもの）があれば、役割を見たときと取り直すときに読む（読めなければ接続の名前）。サイトでない接続は、接続の名前（`connection-<接続の ID>`）。どちらもメニューと画面には出さない |
| 振り分けの説明 | 登録と「ツールを取り直す」のときに推論が作る。管理者は直せる |
| 指示 | 依頼と今日の会話・会社のこと（第10.9.6節）を渡す。相手の説明にある手順と書き方の決まりに従う。相手の説明が利用者に聞くよう求める好み（②）は、会社の事情から業務が決めて、確定の前の答えに書く。人に聞き返さない |
| 使える人 | 会社のサイトを扱う接続は、**サイトの更新の利用範囲**（既定は管理者だけ。第45.2節）。サイトの更新を入れていない会社では、サイトの接続の業務を作らない。サイトでない接続の業務は、業務ごとの利用範囲を持ち、**既定は管理者だけ**（社外に出る道具を持つため。会社が広げられる） |
| 出さない接続 | 読むだけの道具しかない接続（秘書の調べものがすでに使う）・振り分けの説明がまだ無い接続・役割を管理者がまだ見ていない接続 |
| 業務の定義を書く道 | そのまま残す。決まった手順を毎回同じに行わせたい会社は、拡張機能か SKILL.md で業務を書ける |

**MCP のサイトでは、M2Office の業務の部分（何を書くか・会社を知っていること・承認）はそのままに、サイトへの入れ方を相手の道具に任せる。** 相手の道具ごとに M2Office の側でコードを書かない（会社ごと・サービスごとに作らない）。

| 機能 | REST API のサイト | MCP のサイト |
|---|---|---|
| ページを直す・作る | サイトの更新（第45章） | 汎用の業務が相手の道具でページを探して読み、準備と見直しをして、確定を承認にかける |
| お知らせ（サイトへの掲載） | お知らせの作成（第35.6.1節） | 本人の入れるサイトが MCP のサイトなら、お知らせの作成の承認の後に、そのサイトの業務に頼む。相手の道具でお知らせの下書きを作り、準備と見直しをして、確定を 2 回目の承認にかける。期限やポップアップなど相手の項目は、業務が決めて承認の画面に並べる（②。第47.6節） |
| コラムの入れ先 | コラムの作成（第32.10節） | 本人の入れるサイトが MCP のサイトなら、承認の後に、そのサイトの業務に読み物の記事の下書きを頼む（公開しない。第47.6節） |
| 元に戻す | M2Office が直す前の本文を持って戻す（第45.8節） | **相手の戻す道具を使う**（Q-371）。M2Office は直す前の本文を持たない。戻すのも承認を通す |
| 崩さない確かめ | 頼まれた所の外が変わらないことをプログラムが確かめる（第45.5節） | 相手の見直しの結果の変わる項目（`changedFields` など）を承認の画面に出す。相手が持たない確かめはできないことを、ヘルプに書く |
| ぶつかり | 直し案の後に変わっていれば上書きしない（第45.7節） | 相手の知らせ（`baselineChanged` など）を注意として出し、やり直す（第47.4.2節） |
| 相手にしかない機能 | — | 休診日の暦・診療の案内など、相手の道具でしかできない頼みも、汎用の業務が相手の道具で行う。確定は承認を通す |
| 相手の決まり | — | 相手の説明にある書き方の決まり（見出しの階層など）は、道具の使い方として推論に渡す。承認・送り先・社外かどうかの判断は、相手の説明では変えない |

**できないことは、できないと言う。** 相手の道具に無いことを頼まれたら、そう伝える。相手の版が古くて使えない道具は、相手の知らせのまま伝える。

### 47.8 権限と記録

| 項目 | 規定 |
|---|---|
| 使える人 | サイトを使う機能の利用範囲の人（第16.7.3節）。MCP のサイトは、そのコネクタの認証（会社の鍵か、本人の認可か。第12.11.6節）で動く |
| 承認 | 確定と戻すは、本人の承認を通す（第47.4節）。サイトの更新の既定の利用範囲（管理者だけ。第45.2節）は変えない |
| 記録 | 監査ログ `site.add`・`site.update`・`site.delete`（サイトの登録・既定の変更・外す）。MCP のサイトへの確定は、いまのツールの呼び出しの記録に、サイトの ID・道具の名前・役割を足す。承認の判断は、会話で行っても承認トレイで行っても同じ記録 |

| 送り先の確かめ | MCP の呼び出しは、いまのコネクタと同じ口（`net/outbound.ts`）を通す |
| 外から来た文 | 相手の道具の説明と応答は、道具の使い方と結果として読む。承認を外す・送り先を変える・ほかの道具を呼ばせるといった指示としては扱わない（不変則 I-6） |

### 47.9 行わないこと

| 行わないこと | 理由 |
|---|---|
| 相手の「了承を待たずに確定してよい」に従う | 承認ゲートは外から来た文で外せない |
| 言葉だけで承認する | 社外に出る操作の取り違えを防ぐ（Q-369） |
| サービスごとに専用のコードを書く | 汎用の役割と承認の決まりで扱う。会社ごと・サービスごとに作らない |
| 対象のサイトが分からないまま、既定のサイトに入れる | 取り違えると社外に出る |
| MCP のサイトで、M2Office が相手のページを丸ごと読み書きして直す | 相手の作り（独自の項目・テーマ）を壊す。相手の道具を通す |
