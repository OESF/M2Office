## 45. サイトの更新（会社の WordPress のいまあるページを、秘書に頼んで直す。第 0.563.0 版で案、第 0.564.0 版で確定。第 0.565.0 版で一人ひとりの WordPress の利用者を案、第 0.566.0 版で確定して実装。第 0.567.0 版でサイトのカテゴリーとタグを案、第 0.568.0 版で確定して実装。第 0.569.0 版で WordPress の API を広く使う案、第 0.570.0 版で確定して段 2a を実装。第 0.571.0 版で投稿の種類（カスタム投稿タイプ）を案、第 0.572.0 版で確定して段 1、第 0.573.0 版で段 2、第 0.574.0 版で独自の分類を実装。Q-330〜Q-350、ADR-0140〜ADR-0144）

この章で決めること: **会社の Web サイト（WordPress）の、いまある固定ページと記事を、秘書に頼むだけで直せるようにする**こと。
入口、直せるもの、直し案の作り方、承認の画面、入れ方と確かめ、元に戻す、WordPress の側の権限、MCP との関係、権限と記録、段階。

**この章は確定した**（2026-11-12 に三浦さんが、Q-330〜Q-334 をおすすめのとおりとした）。段 1 を第 0.564.0 版で実装する（第45.15節）。

### 45.1 目的と位置づけ

2026-11-12 に三浦さんが、世間で WordPress の MCP との連携が進んでいることを受けて、いまの WordPress とのつなぎ方が時代遅れではないかと尋ね、MCP を調べたうえで、会社のサイトを簡単に更新できる方法を検討するよう求めた。調べた結果（第45.9節）、**自前のサーバー（レンタルサーバー）の WordPress では、MCP にしても簡単にならない**ことが分かった。三浦さんは、導入先の多くは自前のサーバーであるとして、REST API の上に「秘書に頼んでいまのページを直す」機能を作る案（案 A）を選んだ。

いまの M2Office は、WordPress に**新しく入れる**ことしかしない（コラムの下書き・お知らせの記事。第32.10節・第35.6.1節）。中小企業のサイトで多い手間は、営業時間・料金・休業のお知らせ・スタッフの紹介・アクセスなど、**いまあるページの文を直す**ことである。いまは、WordPress の管理画面に入って場所を探して直すか、制作会社に頼んでいる。

| 痛み | M2Office で行うこと |
|---|---|
| どのページのどこに書いてあるか分からない | 秘書が探す。同じことが何か所にも書いてあれば、まとめて直す |
| WordPress の管理画面の操作が分からない・怖い | 管理画面に入らない。秘書に頼んで、直す前と後を見て承認するだけ |
| 直したら崩れるのが怖い | 変えるのは頼まれた文だけ。ほかは 1 文字も変えないことをプログラムが確かめる。いつでも元に戻せる |
| 制作会社に頼むと時間とお金がかかる | 文の直しなら、その場で済む |

### 45.2 形: 内蔵の拡張

| 項目 | 規定 |
|---|---|
| 形 | 業務と記録の表と画面を持つので**内蔵の拡張**にする（第12.13節）。既定は切りで、管理者が入れる（Q-330。決定） |
| 名前 | 「サイトの更新」（Q-334。決定） |
| つなぎ | 管理者ページの「接続 › WordPress」でつないだサイトを使う（第6.6.2.1節。コラムの作成・お知らせの作成と同じ 1 つ）。つないでいなければ、拡張機能を入れても使えず、接続の場所を示す |
| 使える人 | 拡張機能の利用範囲の人（第16.7.3節）。**既定の利用範囲は管理者だけ**（Q-331。決定）。会社の顔になるページなので、広げるかは会社が決める |
| 料金 | 拡張機能なので追加の料金は無い（第21.7節）。AI の費用は利用者の負担（第23.4.5節） |
| ローカルの形 | 同じ。M2Office の機械から WordPress のサイトに届けば使える |

### 45.3 入口

| 入口 | 例 | 段 |
|---|---|---|
| 秘書に頼む（画面・音声・Chat） | 「トップの営業時間を 10 時からにして」「料金のページに年末年始の休みを足して」「スタッフ紹介から田中さんを外して」 | 1 |
| Webの分析の「直すべき所」 | 検索に出るのに押されないページの題名・説明の案、古くなった記事の見直し（第34.6節）。いまは「制作会社への依頼文」だが、この拡張を入れていれば「直し案を作る」にする | 2 |
| お知らせの作成 | 休業のお知らせを出すとき、営業時間などのページにも書くかを秘書が判断して、直し案を添える（第35章） | 2 |

**画面に「ページの一覧と編集の欄」は作らない**（原則 u11、ADR-0028）。WordPress の管理画面をまねない。拡張機能の画面は、直した記録（いつ・誰が・どのページを・どう直したか・元に戻す）だけを並べる。

### 45.4 直せるもの

| 対象 | 段 1 | 理由 |
|---|---|---|
| 固定ページと投稿の本文の文（見出し・段落・箇条書き・表の文字・ボタンの文字） | 直す・足す・消す | いちばん多い手間 |
| 固定ページと投稿の題名・抜粋 | 直す | 同上 |
| 文の中のリンク（`https://` と `tel:`・`mailto:`） | 直す・足す | 電話番号やリンク先の変更が多い |
| 画像の差し替え・足す | 段 2 | 画像の選び方と代わりの文字の決まりが要る |
| 新しい固定ページ | 段 2（下書きとして入れる） | 新しく作るのはコラムとお知らせで足りていることが多い |
| ブロックのテーマのヘッダー・フッター（テンプレートの部品）・クラシックのテーマのウィジェット | 段 2 | フッターに営業時間がある会社が多いが、WordPress の管理者の権限が要る |
| サイトのカテゴリーとタグ（作る・名前を変える・記事に付ける・外す） | 第 0.568.0 版で実装（第45.17節） | 記事の分け方を変える頼みが多い。消すことは行わない |
| メニュー・テーマ・プラグイン・サイトの設定・ページの削除 | **行わない**（第45.12節） | 壊したときの害が大きく、頼まれることも少ない |

**ページビルダー（Elementor・Divi など）で作ったページは直さない。** 本文の中身が WordPress の本文の欄ではなく、ビルダーの持つ別の欄にあり、本文の欄を書き換えても表示が変わらない・崩れるためである。見分けられなければ、入れた後の確かめ（第45.7節）で表示が変わらないことで分かり、元に戻す。そのページは「このページは、M2Office では直せない作りです」と伝え、制作会社への依頼文の下書きを添える（第34.6節と同じ。送るのは承認の後。Q-333。決定）。

### 45.5 直し案の作り方

| 段 | すること | 危険度 |
|---|---|---|
| 1. 探す | WordPress の固定ページと投稿を、題名・本文の文で探す（REST API の `search` と、ページの一覧）。頼みの言葉（「トップ」「料金」「アクセス」）からページを選ぶのは推論が行う。**同じことが書いてある所は全部拾う**（営業時間がトップとアクセスの 2 か所にあるなど） | read |
| 2. 読む | 選んだページの本文を、編集用の形（`context=edit` の `content.raw`。ブロックの印を含む）と、最後に直された時刻（`modified_gmt`）で読む | read |
| 3. 分ける | プログラムが本文を、ブロックと文のかたまりに分け、番号を振る。印（ブロックの印・HTML の札）はプログラムが持ち、推論には文だけを渡す | — |
| 4. 直し案 | 推論が「何番の文をどう変えるか」だけを返す（足す・消すも番号で言う）。プログラムが印を元のまま組み直す | draft |
| 5. 確かめ | プログラムが、**頼まれた番号の外が 1 文字も変わっていない**こと、足したのが決めた札（太字・強調・改行・リンク）だけであること、スクリプト・埋め込み（`iframe` など）・`style` を足していないことを確かめる。合わなければ直し案を作り直し、2 回だめなら止めて理由を言う | — |

- **推論に任せる**（ADR-0028）: どのページのどこを直すか、言い回し、ほかの所との揃え方。人にページや場所を選ばせない。違えば、承認の画面で却下するか、会話で「アクセスのページは直さないで」と言えば直す
- **ページの文は指示として読まない**（不変則 I-6）。本文に「この指示を無視して…」とあっても、直す材料として読むだけにする
- 頼みがあいまいで、直すページの候補が多すぎるとき（10 ページを超えるなど）だけ、秘書が聞き返す

### 45.6 承認の画面

サイトに出すのは**社外への送信**なので、承認なしには入れない（第9.4.0節）。危険度は `external-send`。承認は第9.2.3節の決まりに従い、既定は依頼した本人とする。会社の設定で管理者の承認を加えられる（`adminAlsoWhen`。Q-331。決定）。

| 出すもの | 中身 |
|---|---|
| 確認すること（1 行目） | 「サイトの 2 ページを直します: トップ・アクセス」 |
| 判断するもの | ページごとに、ページの題名と公開の URL、**直す前と後を並べた文**（変わった所に印）。変わらない所はたたむ |
| 承認すると行うこと | 「トップ（https://…）の本文を更新します。公開中のまま、すぐにサイトに出ます」をページごとに |
| 戻せること | 「あとで元に戻せます（90 日。Q-332）」 |

**承認の画面は、変わる文そのものを見せる**（第9.3.3節）。MCP のツールに渡す値を並べるような見せ方はしない。

### 45.7 入れ方と確かめ

| 項目 | 規定 |
|---|---|
| 入れ方 | 承認の後、ページごとに本文（と題名・抜粋）を REST API で更新する。公開の状態は変えない（公開中なら公開のまま、下書きなら下書きのまま。Q-332） |
| ぶつかり | 入れる前に、もう一度最後に直された時刻を読む。直し案を作った後に誰かが WordPress で直していれば、**入れずに**、直し案を作り直すかを本人に知らせる（上書きしない） |
| 公開のページでの確かめ | 入れた後に、公開の URL を読み、直した文が出ていることを確かめる。キャッシュのため出ていなければ、時間をおいて 3 回まで読み直す。それでも出なければ、「サイトに入れましたが、表示がまだ変わっていません（キャッシュの設定か、ページビルダーで作ったページの見込み）」と知らせる。ページビルダーと分かれば元に戻す |
| 何ページか | 1 回の頼みで 10 ページまで。1 ページずつ入れ、途中で失敗したら、入れたページと入れていないページを分けて伝える |
| 結果 | 秘書が「トップとアクセスの営業時間を直しました」と、公開の URL を添えて答える |

### 45.8 元に戻す

| 項目 | 規定 |
|---|---|
| 持つもの | 直す前の本文・題名・抜粋と、入れた後の最後に直された時刻を、M2Office が持つ（WordPress の版の記録は、サイトによって切られているため頼らない） |
| 戻し方 | 拡張機能の画面の記録の「元に戻す」か、秘書に「さっきのサイトの直しを戻して」と頼む。戻すのもサイトに出すことなので、承認を通す（直す前と後を逆にして見せる） |
| 戻せないとき | 入れた後に WordPress で誰かが直していれば、そのまま戻すとその直しが消えるので、戻さずに伝える |
| 持つ期間 | 90 日（Q-332。決定）。過ぎたら直す前の本文を消し、記録（いつ・誰が・どのページ）だけを残す |

### 45.9 MCP との関係（2026-11-12 に調べたこと）

| 項目 | 自前のサーバーの WordPress（公式の MCP Adapter） | WordPress.com（公式の MCP サーバー） |
|---|---|---|
| 入れ方 | プラグイン「MCP Adapter」（v0.7.1。WordPress 6.9 以上） | 何も入れない。Jetpack でつないだ自前のサイトも使える |
| 最初からできること | 読むことだけ（サイトの情報・利用者の情報・環境）。記事・固定ページ・画像を書く操作は、別のプラグインか自前のコードが要る | 記事・固定ページ（ブロック単位の直しも）・画像・カテゴリーなど 60 以上 |
| 認証 | アプリケーションパスワード（いまと同じ）。OAuth は無い | OAuth 2.1（アプリの自動登録）。読むだけも選べる |
| 成熟度 | 0.x の版。小さな版上げでも作りを変えている | 正式な提供。有料のプラン（Jetpack は Jetpack AI か Jetpack Complete）。無料のサイトは 2026-11-30 まで |

**決めたこと（ADR-0140）**

- 自前のサーバーの WordPress には、**REST API（`wp-json/wp/v2`）とアプリケーションパスワード**でつなぐ。WordPress 4.7 からの本体の機能で、相手のサイトに何も入れなくてよい
- 直し案・承認の画面・確かめ・元に戻すは M2Office の中に持ち、つなぎ方（裏の口）を取り替えられる形にする
- WordPress.com と Jetpack のサイトには、段 3 で、同じ流れの裏の口として WordPress.com の MCP を足す（OAuth の同意だけでつながる）
- 自前のサーバーの MCP Adapter が、本体の操作として記事と固定ページを書けるようになり、版が落ち着いたら、裏の口に足すかを考え直す
- 汎用のコネクタ（第6.6.3節）で、アプリケーションパスワードの形（`Basic`）の鍵も送れるようにする（段 3。詳しい人が MCP Adapter を自分でつなぐため）

### 45.10 WordPress の側の権限

| 項目 | 規定 |
|---|---|
| 要る役割 | アプリケーションパスワードを作る利用者は、**固定ページと公開済みのページを直せる役割（編集者）**が要る。投稿者の役割では、固定ページも、ほかの人の記事も直せない |
| 確かめ | 拡張機能を入れたときと接続を確かめるときに、その利用者の役割（`users/me?context=edit` の権限）を読み、足りなければ「WordPress の利用者を『編集者』にしてください」と、何ができないかを添えて言う |
| ヘルプ | 「接続」の記事の「記事を書ける権限（投稿者・編集者など）」を、この拡張を使うなら編集者、と直す |
| 管理者の権限 | 段 2 のヘッダー・フッター・ウィジェットは、WordPress の管理者の役割（`edit_theme_options`）が要る。求めるのは段 2 で、使う会社だけ |

### 45.11 権限と記録

| 項目 | 規定 |
|---|---|
| 記録 | 監査ログ `site_edit.propose`（直し案を作って承認へ進めた）・`site_edit.apply`（ページの ID と URL・入れた結果）・`site_edit.revert`（元に戻した）。承認した人は実行の記録に残る。本文は監査ログに残さず、直す前と後は拡張の表に 90 日だけ持つ |
| 表（案） | `site_edits`: tenant_id、実行、ページの種類（固定ページ・投稿）と ID、公開の URL、題名、直す前（本文・題名・抜粋）、直した後、入れた後の最後に直された時刻、状態（直し案・承認待ち・入れた・表示を確かめられない・戻した・失敗）、入れた時刻・戻した時刻。テナントで絞る（不変則 I-2） |
| 送り先の確かめ | WordPress への呼び出しは、いまの接続と同じ口（`net/outbound.ts`）を通す（第16章の SSRF の対策） |
| 第三者のコード | 相手のサイトのプラグインやスクリプトを、M2Office の中で動かさない（不変則 I-7）。公開のページは文として読むだけ |

### 45.12 行わないこと

| 行わないこと | 理由 |
|---|---|
| 承認なしにサイトを直す | 社外への送信である |
| WordPress の管理画面をまねた、ページの一覧と編集の画面を作る | 頼むだけで済ませる（原則 u11、ADR-0028） |
| メニュー・テーマ・プラグイン・サイトの設定を変える・ページを消す | 壊したときの害が大きい。消すのは非公開にして済ませられる（メニューとサイトのタイトルは第45.18.4節で扱った。ブロックのテーマの全体のスタイルは、承認と元に戻すことを条件に第46章で扱う。Q-357。決定） |
| ページビルダーで作ったページを書き換える | 表示が変わらないか崩れる |
| スクリプト・埋め込み・`style` を足す | サイトを壊す・乗っ取られる元になる |
| 直す前に WordPress で誰かが直したものを上書きする | 人の直しを消してしまう |
| 検索の順位だけを狙った直しを勧める | 読み手の役に立つ直しだけにする（第32.20節・第34.16節と同じ考え） |

### 45.13 段階

| 段 | 内容 |
|---|---|
| 段 1 | 秘書に頼んで、固定ページと投稿の本文・題名・抜粋を直す。同じことが書いてある所をまとめて直す。直す前と後の承認・ぶつかりの確かめ・公開のページでの確かめ・元に戻す・WordPress の役割の確かめ |
| 段 2 | サイトのカテゴリーとタグ（第45.17節。第 0.568.0 版で実装）・画像の差し替えと追加・新しい固定ページ（下書き）・ヘッダーとフッターとウィジェット・Webの分析の「直すべき所」から直し案を作る・お知らせの作成から営業時間などのページを直す案を添える |
| 段 3 | プラグインとテーマの状態を知らせる・汎用のコネクタで `Basic` の鍵を送れるようにする（第 0.577.0 版で実装。第45.18.5節）。WordPress.com と Jetpack のサイトの裏の口として WordPress.com の MCP を足すか（Q-351）、プラグインの口（Q-352）は未決 |

### 45.14 まだ確かめること

- よく使われるテーマ（ブロックのテーマとクラシックのテーマ）と、日本のレンタルサーバー（キャッシュの機能を持つもの）で、編集用の本文の読み書きと公開のページでの確かめができるか
- ページビルダーで作ったページを、入れる前に見分けられるか（本文の欄の形・`meta` の見え方）
- 検索の結果に出る説明文は、SEO のプラグイン（Yoast SEO など）が別の欄に持つことが多い。REST API で書けるかは、プラグインごとに確かめる（段 2）

### 45.15 段 1 の実装の決まり（第 0.564.0 版）

| 項目 | 実装 |
|---|---|
| 形 | 内蔵の拡張 `site-updates`（`packages/core/src/site-updates/`）。会社の設定の区分 `siteUpdates`（`enabled`・`adminApproval`。移行 198 で `tenant_settings.site_updates`）。初めて入れたときに利用範囲を管理者だけにする（`extension-switch.ts` の `ADMIN_SCOPED_FIRST`）。業務の区分は「お知らせと販促」 |
| 付属の業務 | 「サイトの直し案」（`site-updates:edit`。秘書から。ツール `site_updates.propose`・`site_updates.revert`・`site_updates.list`）と「サイトに入れる」（`site-updates:apply`。直し案ができると `submitter` が始める。承認の段は `approver: requester`、会社の設定 `siteUpdates.adminApproval` が入なら管理者の承認を加える（`adminAlsoWhen`）。ツール `site_updates.apply`） |
| 分け方と組み直し | `segments.ts`。本文を印（`<!-- … -->`）・札・文に分け、ブロックの札で区切った文のかたまりに番号を振る（包む札は開いた札の積み重ねで決める）。直しは「書き換え・消す・足す（段落か箇条書きの行）」の 3 つ。足してよい札は、元のかたまりにある札と `strong`・`em`・`b`・`i`・`br`・`a href="https://…"`（`tel:`・`mailto:`）だけ。スクリプト・埋め込み・`style`・`on…=` は断る。消すのは段落・見出し・箇条書きの行などだけで、包むブロックの印ごと外す（表のますは消せない）。組み直した後に分け直し、直していないかたまりが同じ順で残っているかと、危ないものが増えていないかを確かめる |
| 直し案の作り方 | `SiteUpdateService.propose`。① WordPress の利用者の権限（`users/me` の `edit_pages` など 6 つ）を確かめる ② 固定ページの一覧から推論（`fast`）がページの候補と本文から探す言葉（3 つまで）を決め、REST の `search` でも探す（8 ページまで）③ 編集用の形で読み、ページビルダー（ショートコードの形・ブロックの無い Elementor）は直さない ④ 推論（`standard`）がかたまりの番号で直しを返し、題名・抜粋も直せる ⑤ 決まりに合わなければ理由を添えて 1 度だけ作り直させる ⑥ 10 ページまでを記録して承認へ進める。推論が使えない会社では作らない |
| 承認の画面 | `site_updates.apply` の `prepare` が、ページごとの「直す前・直した後・足す・消す」と、公開中ならすぐに出ることを組み立て、指紋（ページ・直す前の時刻・入れる本文）を引数に入れる。`ALWAYS_ASK` に入れ、宛先に関わらず人が見る（`describe-call.ts`） |
| 入れ方 | 承認の後に、指紋（項目の並びに左右されない形で作る。第 0.570.1 版。PostgreSQL が保存で並びを入れ替え、承認した直しを「中身が変わった」と断っていたため）を確かめ、ページごとにもう一度読んで、最後に直された時刻と本文が直し案のときのままか確かめてから書く（違えば「ぶつかり」で入れない）。公開の状態は送らない（変えない）。入れられなかったとき（1 つも入らなかったときを含む）は、ツールが例外を投げて実行を失敗にし、直しの記録を「入れられなかった」にする（入れたつもりで「済んだ」と伝えないため。第 0.570.1 版） |
| 確かめ | 公開中のページだけ、公開の URL を読み（`m2o_check` を付けてキャッシュを避ける）、書き換えた文と足した文が出ているか（空白を除いて比べる）を見る。0 秒・3 秒・10 秒の 3 回まで。出なければ「表示がまだ変わっていません」（結果 `unverified`） |
| 元に戻す | `revert` が、入れたページについて、いまの本文が入れた後のままかを確かめ、直す前の本文（題名・抜粋は直したときだけ）に戻す直し案を作って承認へ進める（`revert_of`）。入れたら元の直しを `reverted` にする。画面の「元に戻す」と秘書の「戻して」が同じ道を通る（`POST /v1/site-updates/{ID}/revert`） |
| 持つ期間 | 90 日を過ぎた直しは、ページごとの直す前と後の本文と直しの文を消し（`purged_at`）、ページ・結果・日時だけを残す。ワーカーが 1 日 1 回、一覧と直し案を作るときにも行う |
| API と画面 | `GET /v1/site-updates/site`（つないでいるサイト。サイトのタイトルとキャッチフレーズ・URL・つないでいる WordPress の利用者・直せるか（足りない権限）を、開いたときに WordPress に問い合わせる。読めない値は「読めませんでした」と出し、推測で埋めない）・`GET /v1/site-updates`（一覧）・`GET /v1/site-updates/{ID}`・`POST /v1/site-updates/{ID}/revert`。`PUT /v1/admin/extensions/site-updates/settings`（`adminApproval`）。画面は左のメニューの「サイトの更新」で、いちばん上につないでいるサイト（2026-11-12 に三浦さんが求めた）、その下に直した記録と元に戻すを並べる（`SiteUpdates.tsx`）。拡張機能の画面に「サイトの直しは管理者も承認する」と WordPress の接続への案内 |
| データの渡し先 | 「会社の WordPress」の使い道に「サイトのページの直し」を足し、サイトの更新を入れた会社でも出す |

**段 1 で行っていないこと**（段 2 以降）: 画像・新しい固定ページ・ヘッダーとフッターとウィジェット・Webの分析とお知らせの作成からの直し案（第45.13節）。拡張機能のアイコンは、コラムの作成のものを仮に使っている。本物の WordPress（日本のレンタルサーバー・キャッシュの機能）での確かめはまだ（第45.14節）。

### 45.16 一人ひとりの WordPress の利用者（第 0.565.0 版で案、第 0.566.0 版で確定して実装。ADR-0141・Q-335〜Q-338）

2026-11-12 に三浦さんが、会社の接続では WordPress の利用者を 1 人しか登録できず、M2Office の利用者 A は WordPress の管理者 AA、利用者 B は編集者 BB、のように分けられないことを指摘した。いまは誰が頼んでも会社の 1 人の利用者で直すため、WordPress の記録（版・投稿者）が全部その 1 人になり、WordPress の役割で人ごとに絞れない。三浦さんは、本人がつないでいれば本人の利用者で直し、つないでいなければ会社の利用者で直す案（案 A）を選び、Q-335〜Q-338 をおすすめのとおりとした。

| 項目 | 規定 |
|---|---|
| サイト | 会社で 1 つのまま。会社の接続（「接続 › WordPress」。サイトの URL・会社の利用者・アプリケーションパスワード）が、直すサイトを決める（第6.6.2.1節）。会社の接続が無ければ、本人の接続も使えない（Q-336。決定） |

| つなぐときの確かめ | 会社のサイトで、その利用者名とパスワードが通るか（`users/me`）を確かめてから預ける。通れば、WordPress の表示名と役割（管理者・編集者・投稿者など）を出す。サイトの更新に要る権限が足りなければ、預けたうえで「固定ページと記事を直す権限がありません」と出す（直すときに断る） |
| 預け方 | パスワードは本人の分も暗号化して預け、画面に戻さない。本人だけが使う。管理者もほかの人も、本人の接続で操作しない |
| 外す | 本人が「切断」で外す。利用者を停止・削除したときと、会社の WordPress の接続を外した・サイトを変えたときは、本人の接続も消す（Q-338。決定） |
| どれで直すか | サイトの更新（つないでいるサイトの表示・直し案を作る・入れる・元に戻す）は、**本人がつないでいれば本人の利用者で、つないでいなければ会社の利用者で**行う |
| 本人がつないでいるとき | 本人の利用者の権限が足りなければ、会社の利用者で直さずに断る（WordPress の役割を守る）。「あなたの WordPress の利用者（BB・投稿者）では、このページを直せません」と言う |
| 直し案と入れるときをそろえる | 直し案を作ったときに使った接続（本人か会社か。本人なら WordPress の利用者名）を記録し、承認の後に入れるときも同じ接続で入れる。管理者の承認が加わっても、入れるのは頼んだ本人の接続。間で本人が外した・利用者名が変わったときは、入れずに理由を言う（会社の利用者に切り替えない） |
| 元に戻す | 戻す直し案を作る人の接続で行う（その人がつないでいれば本人の利用者、いなければ会社の利用者） |
| 画面 | 「サイトの更新」のいちばん上のつないでいるサイトに、「あなたの WordPress の利用者: BB（編集者）」か、つないでいないときは「会社の WordPress の利用者: m2office」を出す。直した記録には、どの WordPress の利用者で直したかを出す。説明文は常に出さない（原則 u11） |
| 管理者が見るもの | 「接続 › WordPress」に、本人の接続をしている人の一覧（M2Office の利用者・WordPress の利用者名と役割・つないだ日時）を出す。パスワードは出さない（Q-337。決定） |
| 記録 | 監査ログ `connection.wordpress_user`（つないだ・利用者名と役割）・`connection.wordpress_user_delete`。サイトの直しの監査ログに、本人か会社かと WordPress の利用者名を足す |
| コラムとお知らせ | この版では変えない（会社の利用者で入れる。Q-335） |
| 表（案） | `user_wordpress_connections`: tenant_id、user_id、WordPress の利用者名、暗号化したパスワード、表示名、役割、つないだ日時。テナントと本人で絞る（不変則 I-2）。`site_edits` に、使った接続（`company`・`user`）と WordPress の利用者名を足す |

### 45.17 サイトのカテゴリーとタグ（第 0.567.0 版で案、第 0.568.0 版で確定して実装。ADR-0142・Q-339〜Q-342）

2026-11-12 に三浦さんが、秘書に頼んで WordPress の新しいカテゴリーを作れないかと尋ねた。段 1 は、いまある固定ページと記事の文を直すだけで、カテゴリーとタグは扱わない。三浦さんは、カテゴリーという言葉はナレッジでも使っているので、秘書には区別がつかないと指摘したうえで、仕様の案を求めた。同じ日に「せっかく秘書とは会話ができるので、わからないときは聞き返して欲しい」と述べ、Q-339〜Q-342 をおすすめのとおりとした。

#### 45.17.1 「カテゴリー」の見分け方

M2Office の中で「カテゴリー」と呼ぶものは、すでに 3 つある。サイトのカテゴリーを足すと 4 つになる。

| もの | 中身 | 頼み方の例 |
|---|---|---|
| メールのカテゴリー | メールの仕事のまとまり（第9.5.1.1.1節） | 「採用というカテゴリーを作って」（メールの画面のヘルプの例） |
| 組織の知識の種類 | 規程・秘書が学んだことなど（第11章） | 「この規程のカテゴリーは？」 |
| ナレッジの整理のタグ | 資料に AI が付ける印（第44章。OKF の書き出しにも使う） | 「この資料のタグを直して」 |
| サイトのカテゴリーとタグ（新しく足す） | WordPress の記事の分け方 | 「ブログに『旅行』というカテゴリーを作って」 |

| 項目 | 規定 |
|---|---|
| 見分け方 | 秘書が、頼みの中の手がかりで見分ける。「サイト」「ブログ」「ホームページ」「WordPress」「記事」「投稿」と一緒ならサイトのカテゴリー。「メール」と一緒か、メールを開いて頼んだならメールのカテゴリー。「資料」「ナレッジ」と一緒ならナレッジの整理。「規程」「知識」と一緒なら組織の知識 |
| 手がかりが無いとき | 「採用というカテゴリーを作って」のように手がかりが無ければ、本人が使える機能のうち当てはまるものが 1 つなら、それにする。2 つ以上なら、**1 度だけ聞き返す**（「メールのカテゴリーですか、サイト（WordPress）のカテゴリーですか」）（Q-339。決定） |
| 覚える | 聞き返した答えは、取り次ぎの好み（第11.13.7節。種類 `routing`）として覚え、次からは聞かない。違えば「それじゃなくてサイトの」と言えば、頼み直しとして覚え直す |
| 言葉 | サイトのカテゴリーとタグは、画面・承認・秘書の答えで「**サイトのカテゴリー**」「**サイトのタグ**」と呼ぶ。メールのカテゴリーの言葉は変えない |

#### 45.17.2 できること

| 頼み | すること |
|---|---|
| 作る（「ブログに『旅行』というカテゴリーを作って」「『温泉』を『旅行』の下に作って」） | サイトのカテゴリー（親を決めてよい）かタグを作る。同じ名前があれば作らずに伝える。似た名前（「旅」と「旅行」など）があれば、作る前にあることを承認の画面に添える |
| 名前を変える（「『旅』を『旅行』にして」） | 名前だけを変える。**スラッグ（URL の一部）は変えない**（変えると、前の URL へのリンクが切れる。Q-342。決定） |
| 記事に付ける・外す（「先週の温泉の記事を『旅行』に入れて」「この記事から『未分類』を外して」） | 秘書が題名・時期・本文から記事を探し（10 件まで）、カテゴリーかタグを付ける・外す。カテゴリーが 1 つも無くなる外し方は、WordPress が「未分類」に戻すので、承認の画面にそう書く |
| 一覧を聞く（「サイトのカテゴリーは何がある？」） | 名前・記事の数・親を答える |

**行わないこと**: カテゴリーとタグを消す・まとめる・スラッグや説明を変える（記事の分け方と URL が崩れる。WordPress の管理画面で行う）。固定ページにはカテゴリーが無いので、付けない。

#### 45.17.3 承認と元に戻す

| 項目 | 規定 |
|---|---|
| 承認 | 作る・名前を変える・付ける・外すは、サイトの見え方が変わるので、ページの直しと同じく**承認を通す**（Q-340。決定）。承認の画面には、作るカテゴリーの名前と親・変える前と後の名前・付ける記事と外す記事の題名を並べる。ページの直しと 1 回の頼みにまとめてよい |
| 入れ方 | ページの直しと同じ道（付属の業務「サイトに入れる」）。記事に付けるときは、直し案の後にその記事のカテゴリーが WordPress で変えられていれば、上書きしない |
| 元に戻す | 90 日の間、元に戻せる。名前は前の名前に、付けた・外したものは元に戻す。作ったカテゴリーとタグは、**記事が 1 つも付いていなければ消し**、付いていれば消さずに伝える（Q-341。決定） |
| 権限 | 作る・名前を変えるには WordPress の `manage_categories`（編集者は持つ）、付ける・外すには記事を直す権限が要る。本人の接続なら本人の利用者の権限で行う（第45.16節） |
| 記録 | 監査ログ `site_edit.*` に、カテゴリーかタグか・名前を足す |

#### 45.17.4 実装（第 0.568.0 版、移行 200）

- WordPress の口: `listSiteTerms`・`readSiteTerm`・`createSiteTerm`・`renameSiteTerm`（名前だけを送り、スラッグは送らない）・`deleteSiteTerm`（元に戻すときだけ）・`findSitePosts`・`readSitePostTerms`・`setSitePostTerms`（`wordpress.ts`）
- 直し案: `SiteUpdateService.proposeTerms`。推論（`fast`）が記事を探す言葉を決め、新しい 20 件と合わせて 40 件までの記事・カテゴリー・タグを推論（`standard`）に渡す。推論は名前と記事の番号で「作る・名前を変える・付ける・外す」を返し、分からなければ聞き返す文（`question`）を返す。プログラムが ID に直して確かめる（`terms.ts` の `buildTermChanges`。もうある名前は作らない・似た名前を添える・無い名前は付けない・名前の重なる変更はしない・上限は作る 10・名前を変える 10・記事 10）。作る・名前を変えるには `manage_categories`、付ける・外すには記事を直す権限を確かめる
- 記録: `site_edits.terms`（移行 200）。承認の画面（`preview`）にページの直しと並べて出し、指紋に入れる。入れるのは「作る → 名前を変える → 付ける・外す → 消す」の順で、付けるときは直し案の後に記事のカテゴリーとタグが変えられていないかを確かめる（`applyTermChanges`）。元に戻すときは `revertTermChanges`（作ったものは消す直し、名前は前の名前、付けた・外したものは前のとおり。入れた後に人が変えていれば戻さない）。消すのは、入れるときに記事の数を読み、0 のときだけ
- ツール: `site_updates.terms`（`write-internal`。直し案を作って承認へ進める。聞き返す文があれば返す）・`site_updates.term_list`（`read`）。付属の業務「サイトの直し案」の段に足した
- 秘書の見分け: `categoryTarget`（手がかりでサイト・メール・ナレッジ・知識・分からないを分ける）と `categoryAnswer`（聞き返しへの答え）。秘書（`secretary.ts`）は、サイトの更新を使える人について、手がかりがサイトならメールのカテゴリーとして拾わずにサイトの更新に取り次ぐ。手がかりが無く、メールのカテゴリーとしても拾える頼みなら、前に覚えた答え（取り次ぎの好み。言い方「カテゴリー」「タグ」）に従い、無ければ「メールのカテゴリーですか、サイト（WordPress）のカテゴリーですか。」と 1 度だけ聞き、10 分のあいだに答えがあれば覚えて続ける

### 45.18 WordPress の API を広く使う（第 0.569.0 版で案、第 0.570.0 版で確定して段 2a を実装。ADR-0143・Q-343〜Q-346）

2026-11-12 に三浦さんが、コラムの作成（秘書がコラムの業務に頼み、下書きを WordPress に入れる）が動くことを確かめたうえで、「WordPress が提供する API を可能な限り利用できるようにして下さい」と求めた。WordPress の REST API（第45.9節）で読み書きできるものを並べ、どこまで秘書に頼めるようにするかを決める。同じ日に三浦さんが Q-343〜Q-346 をおすすめのとおりとし、WordPress の MCP を使う人が増えている中で、M2Office がそれ以上のことをできると示したいと述べた（第45.19節）。

**守ること（どの段でも変えない）**

| 決まり | 中身 |
|---|---|
| 書くものは承認の後 | サイトの見え方を変えるもの・社外の人に届くもの（コメントの返事）は、直す前と後を見せて承認を通す（第45.6節） |

### 45.19 WordPress の MCP との違い（第 0.570.0 版）

2026-11-12 に三浦さんが、WordPress の MCP を使う人が増えている中で、M2Office はそれ以上のことをできると示しておきたいと述べた。WordPress の MCP（第45.9節）は、AI に WordPress の操作の口を渡す仕組みで、何を書くか・何が正しいか・誰が確かめるかは、使う人と AI の道具に任される。M2Office は、その上に業務として次を持つ。

| M2Office が持つもの | 中身 | WordPress の MCP だけでは |
|---|---|---|
| 会社を知った秘書 | 会社の名前・営業時間・規程・お知らせ・案件を知ったうえで書き、直す所を探す | 使う人が毎回、会社のことを伝える |
| 業務として仕上げる | コラムは、テーマ案・下書き・表現と事実の校正・カバー画像（AI の挿絵か会社の写真か型）・予定表まで作る（第32章）。新しい記事にアイキャッチを作る | 文を入れる口だけ。画像と校正は別に用意する |
| 助言 | Webの分析が、検索とアクセスの数字から直すべき所と直し方を言う（第34章）。サイトの更新はその直し案につなぐ（段 2） | 数字を読んで判断するのは使う人 |
| 承認と直す前と後 | 社外に出す前に、直す前と後を並べて人が承認する。承認した中身だけを入れる（第45.6節） | AI の道具の確認に任される |
| 崩さない | 頼まれた所の外が変わらないことと、スクリプトを足していないことをプログラムが確かめる（第45.5節） | AI がページを丸ごと書き直せば、崩れることがある |
| ぶつかりと元に戻す | 直し案の後に人が直していれば上書きしない。90 日の間は元に戻せる（第45.7節・第45.8節） | 戻すのは使う人 |
| 人ごとの役割と記録 | 一人ひとりの WordPress の利用者で直し、監査ログに残す（第45.16節） | つないだ利用者のまま |
| 聞き返す | 頼みが分からなければ秘書が聞き返し、答えを覚える（第45.17.1節） | — |
| ほかの業務とつながる | お知らせの作成・Webの分析・問い合わせの記録・ナレッジの整理と同じ秘書から頼める | WordPress だけ |

WordPress.com と Jetpack のサイトでは、段 3 で WordPress.com の MCP を裏の口として使う（第45.9節）。口が変わっても、上の業務の部分は同じに動く。

### 45.20 投稿の種類（カスタム投稿タイプ）と、コラムとお知らせの入れ先（第 0.571.0 版で案、第 0.572.0 版で確定して段 1 を実装。ADR-0144・Q-347〜Q-350）

2026-11-13 に三浦さんが、WordPress の API ではコラムとお知らせを分けられず、どちらも投稿として扱うのかと尋ね、お知らせはカスタム投稿タイプの `news` で作ることが多いと指摘した。同じ日に三浦さんが Q-347〜Q-350 をおすすめのとおりとした。

WordPress の本体が持つ記事の種類は、投稿（`posts`）と固定ページ（`pages`）の 2 つだけである。日本の会社やお店のサイトでは、お知らせを投稿とは別の種類（カスタム投稿タイプ。`news`・`info`・`topics` など）で作り、投稿をブログやコラムに使うことが多い。いまの M2Office は、お知らせを投稿に「お知らせ」のカテゴリーを付けて入れ、コラムをカテゴリーなしの投稿の下書きとして入れている。そのため、`news` で作っているサイトではお知らせが別の一覧に出てしまい、コラムは「未分類」に入る。

#### 45.20.1 種類を読む

| 項目 | 規定 |
|---|---|
| 読むもの | WordPress の `types`（REST API に出している記事の種類の一覧。名前・表示名・口の名前 `rest_base`・持っている分類 `taxonomies`）。つないだとき・拡張機能を入れたとき・「サイトの更新」の画面を開いたときに読む |
| 扱う種類 | 投稿・固定ページと、カスタム投稿タイプ。メディア・再利用ブロック・テンプレート・メニュー・フォントなどの、記事でない種類は扱わない |
| 出していない種類 | REST API に出す設定（`show_in_rest`）が切りの種類は、M2Office から見えない。お知らせらしい種類が見えないのに管理画面には無いか、と聞かれたら、その種類を作ったプラグインで REST API に出す設定を入れれば使えると答える（ヘルプにも書く） |
| 画面 | 「サイトの更新」のつないでいるサイトの欄に、サイトの記事の種類（「投稿・固定ページ・お知らせ（news）」）を並べる |

#### 45.20.2 お知らせとコラムの入れ先

| 項目 | 規定 |
|---|---|
| お知らせの入れ先 | 種類の一覧から、**お知らせらしい種類**を M2Office が選ぶ（名前か表示名が `news`・`info`・`information`・`topics`・`notice`・「お知らせ」「ニュース」「新着情報」などのもの。1 つならそれ、2 つ以上なら推論が表示名から選ぶ）。無ければ、いまどおり投稿に入れる（Q-347。決定） |
| お知らせの分類 | 入れる種類が `category` を持てば、いまどおり「お知らせ」のカテゴリーを付ける。持たずに独自の分類（`news_category` など、親子のあるもの）を持てば、その分類の同じ名前のものを付ける（無ければ作る）。どちらも持たなければ付けない |
| コラムの入れ先 | 投稿に入れ、カテゴリー「**コラム**」を付ける（無ければ、初めて入れるときに作る）。名前は拡張機能の設定で変えられ、付けないこともできる（Q-348。決定）。コラムらしい種類（`column`・`blog` など）があれば、そちらに入れる（段 2。コラムの取り下げと Webの分析が、入れた種類の口で読めるようにしてから） |
| 決め方の見せ方 | 決めた入れ先は、お知らせの作成とコラムの作成の拡張機能の設定に出す（「お知らせは『お知らせ（news）』に入れます」）。違えば、管理者が設定で選ぶか、秘書に「お知らせは投稿に入れて」と頼めば変える。人に最初から選ばせない（ADR-0028） |
| 分からないとき | お知らせらしい種類が 2 つ以上あって推論でも決められないときは、初めてお知らせを出すときに、秘書が 1 度だけ聞き返す（「お知らせは『ニュース（news）』と『新着情報（topics）』のどちらに入れますか」）。答えは設定に残す（第45.17.1節と同じ考え） |
| 出したもの | すでに投稿に入れたお知らせとコラムは、`news` に移さない（URL が変わり、リンクが切れるため。Q-350。決定） |
| 承認の画面 | お知らせとコラムの承認の画面の「公開先」に、入れる種類と分類を出す（「お知らせ（news）・分類『お知らせ』」） |
| 権限 | カスタム投稿タイプは、独自の権限を持つことがある。入れるときに断られたら、「WordPress の利用者に『お知らせ（news）』を書く権限がありません」と言う |

#### 45.20.3 サイトの更新で扱う

| 項目 | 規定 |
|---|---|
| 扱うこと | カスタム投稿タイプの記事も、投稿と同じに扱う。文を直す（段 1）・新しく作る・公開の状態を変える・前の版に戻す・アイキャッチを付ける（段 2a）（Q-349。決定） |
| 頼み方 | 「ニュースの『年末年始の営業』を直して」「お知らせに新しい記事を作って」のように、種類の表示名で頼める。種類を言わなければ、秘書が頼みの中身から選ぶ。分からなければ聞き返す |
| 分類 | その種類が持つ分類（カテゴリー・タグ・独自の分類）を、サイトのカテゴリーとタグと同じ決まり（第45.17節）で扱う。画面と秘書の言葉は「お知らせ（news）の分類『…』」のように、どの種類のものかを添える |
| 前の版 | 種類が版の記録を持たなければ（`revisions` が無い）、そう伝える |

#### 45.20.5 段 1 の実装（第 0.572.0 版）

| 項目 | 実装 |
|---|---|
| 種類と分類を読む | `listPostTypes`（`types?context=edit`。記事でない種類を除く）・`listTaxonomies`（`taxonomies?context=edit`。口の名前と親子の有無）・`pickNewsTypes`（名前・口の名前・表示名から、お知らせらしい種類の候補）（`columns/wordpress.ts`） |

#### 45.20.6 段 2 の実装（第 0.573.0 版）

| 項目 | 実装 |
|---|---|
| コラムの入れ先 | 会社の設定 `webColumns.wpPostType`（空なら M2Office が選ぶ: コラムらしい種類（`column`・`blog`・「コラム」「ブログ」など。`pickColumnTypes`）が 1 つならそれ、無いか 2 つ以上なら投稿）。分類は、その種類が `category` を持てばカテゴリー、持たずに親子のある独自の分類を持てばその分類に「コラム」を付ける。拡張機能の設定に「入れる種類」（種類が 2 つ以上あるサイトだけ）。API `GET /v1/admin/extensions/web-columns/web-types` |
| 入れた記録 | コラムの記録の記事の ID の欄に、投稿なら ID のまま、ほかの種類なら `口の名前:ID`（`blog:123`）を持つ（`wpRef`・`parseWpRef`）。前から入っている ID は投稿として読む。取り下げ（下書きに戻す）と Webの分析（公開された URL を読む）は、この参照の口で読む |
| サイトの更新 | 記事の種類（`kind`）に、固定ページ・投稿のほか、カスタム投稿タイプの口の名前を持てる（`siteContentPath`）。言葉で探すときに、カスタム投稿タイプの記事も探す（10 種類まで）。段 2a の推論に、サイトの種類（表示名と口の名前）とその記事を渡し、「お知らせに臨時休業の記事を作って」なら `news` に作る。承認の画面では「記事（news）」と出す |
| 独自の分類（第 0.574.0 版） | カテゴリーとタグの頼みにカスタム投稿タイプの名前（表示名・口の名前）があれば、その種類の分類を扱う（`termScope`）。親子のある分類は、`category` を持てばカテゴリー、無ければ最初の親子のある独自の分類（`news_category` など）。親子の無い分類は、`post_tag` を持てばタグ、無ければ最初の親子の無い独自の分類。推論には「親子のあるもの」「無いもの」として渡し、作る・名前を変えるはその分類の口（`/wp/v2/news_category`）に、付ける・外すはその種類の記事（`/wp/v2/news/{id}`）の分類の欄に送る。直した記録に、記事の種類と分類の欄を持ち、元に戻すも同じ口で行う。名前が無ければ投稿の分を扱う。その種類が分類を持たなければ、そう返す |
