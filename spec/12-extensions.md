## 第 IV 部　拡張とエコシステム

提供側だけで作らないための仕組み。

## 12. 拡張機構

**この章で決めること**: 第三者・顧客自身がどうやって機能を追加するか。
**提供側だけでは全ニーズを埋められないという前提に対する回答である。**

### 12.1 拡張の 3 階層

| 階層 | 拡張点 | 作るもの | 実行場所 | 必要な技術力 | 主な提供者 |
|---|---|---|---|---|---|
| **L1** | スキル（業務エージェント） | **SKILL.md（スキルの形式＋α。第12.12節）**。上級者は宣言的な定義（手順・フォーム・承認）も書ける | M2Office 内 | 業務知識のみ | 士業、業務担当者、SIer |
| **L2** | ツール・コネクタ | MCP サーバ | **提供者側または顧客側** | API 開発 | SaaS ベンダー、SIer |
| **L3** | 外部アプリ | プラットフォーム API を使う独立アプリ | **完全に外部** | 一般的な Web 開発 | SIer、顧客内技術者 |

Google 以外のグループウェアやメールへの対応（第2.2節）、
および LINE などの対外チャネル（第14.6節）も、L2 の拡張として実現する。

#### 12.1.1 用語の統一

同じものが「プラグイン」「アドイン」「スキル」などと呼ばれがちなため、本書と開発者向けの文書では次に揃える。

| 使う言葉 | 指すもの | こう呼ばれがちなもの |
|---|---|---|
| **拡張機能** | 配布・導入の単位（パッケージ）。業務エージェント・コネクタの宣言・資源・ヘルプをまとめたもの | プラグイン、アドイン |
| **業務エージェント** | 1 つの業務の定義（エージェント定義）。拡張機能に 1 つ以上含まれる（L1） | — |
| **スキル** | SKILL.md で書いた業務エージェント（第12.12節）。取り込むとエージェント定義になる（第 0.118.0 版で技術用語にした） | — |
| **コネクタ** | 外部の業務システムへの接続。MCP サーバとして別のプロセスで動く（L2） | 連携、インテグレーション |
| **ツール** | エージェントが呼べる個々の操作。基盤の内蔵ツールと、コネクタが提供するツールがある | 関数、アクション |

**利用者向けの説明や販売資料でも、技術文書でも「スキル」を使ってよい**（第2.3節。第 0.118.0 版で改めた。以前は技術文書では使わなかった）。SKILL.md で書いたものを指す（Q-70）。

### 12.2 中核となる設計判断: 第三者コードを実行しない

**M2Office は、第三者が書いたコードを自らのプロセス内で実行しない。**

| 階層 | 第三者が持ち込むもの | 実行主体 | 安全性の担保 |
|---|---|---|---|
| L1 | 宣言的定義（チューリング完全ではない） | M2Office が解釈 | スキーマ検証とツール許可リスト |
| L2 | MCP サーバ（独立したプロセス／ホスト） | 提供者または顧客 | ネットワーク境界、応答は外部データとして扱う |
| L3 | 独立したアプリ | 外部 | API のスコープと権限境界 |

この判断により、**サンドボックス実行環境を自前で構築する必要がなくなる**。

#### 12.2.1 作る人と入れる人を分ける

3 階層はいずれも**作るには技術力が要る**。
しかし**入れるのは画面の操作だけ**である（第2.3.3節）。

| 階層 | 作る人 | 入れる人 |
|---|---|---|
| L1 エージェント定義 | 業務知識を持つ人（士業・業務担当者） | 顧客の管理者 |
| L2 MCP コネクタ | API を書ける人 | 顧客の管理者 |
| L3 外部アプリ | Web 開発ができる人 | 顧客の管理者 |

この分離が、第13.7節のパートナー制度の前提になる。

### 12.3 拡張機能パッケージ

```
建設業向け工事管理拡張/
  manifest.json          # メタデータ、必要権限、互換性
  agents/                # エージェント定義（L1）
  connectors/            # 接続する MCP サーバの宣言（L2）
  resources/             # 帳票テンプレート、業界用語集、指示文断片
  evals/                 # 品質検証用のテストケース
  locales/ja.json        # 表示文字列
  help/                  # 利用者向け・管理者向けのヘルプの記事（第6.10.8節）
  icon.png               # アイコン（第12.10.5節）
  README.md              # 管理者向けの説明
```

マニフェストで宣言する内容:

```json
{
  "id": "jp.example.construction",
  "name": "建設業向け工事管理",
  "version": "1.2.0",
  "publisher": { "name": "株式会社サンプル", "verified": true },
  "platform_schema": ">=1.0 <2.0",
  "permissions": {
    "tools": ["knowledge.search", "document.render", "gmail.create_draft"],
    "connectors": [{ "id": "kouji-system", "protocol": "mcp", "required": true }],
    "data_scopes": ["knowledge:read", "customer:read"],
    "max_risk_level": "draft"
  },
  "pricing": { "model": "monthly_per_seat", "amount": 800, "currency": "JPY" }
}
```

**権限は宣言され、同意され、強制される。**
管理者は導入時にこの一覧を平易な日本語で提示され、同意して初めて有効になる（不変則 I-8）。

### 12.4 配布区分と審査

| 区分 | 提供者 | 審査 | 配布範囲 | 表示 |
|---|---|---|---|---|
| 公式 | M2Office 運営 | 内部レビュー | 全テナント | 「公式」 |
| 認定 | 審査を通過した第三者 | 運営による審査 | マーケットで公開 | 「認定済み・提供者名」 |
| 未審査 | 第三者 | なし | 掲載するが警告を表示 | 「未審査。自己責任で導入」 |
| プライベート | 顧客自身／委託先 | なし | **そのテナント内のみ** | 「自社専用」 |

**プライベート拡張が重要である。** 顧客固有の業務は公開する必要がなく、
審査を待つ理由もない。第11.8節の成長ループで生まれた手順も、ここに登録される。

### 12.5 審査の観点

| 観点 | 確認内容 | 方法 |
|---|---|---|
| スキーマ適合 | 定義が仕様に適合しているか | 自動検証 |
| 権限の妥当性 | 宣言された権限が機能に対して過大でないか | 人的レビュー |
| 承認ゲート | 危険度に応じた承認ゲートが置かれているか | 自動検証 |
| 品質 | 同梱の評価セットが通るか | 自動実行 |
| 制度適合 | 会計・税務に関わる場合、日本の制度要件を満たすか | 人的レビュー |
| 業務範囲 | 士業の独占業務に踏み込んでいないか（第15.4節） | 人的レビュー |
| 指示の注入 | 定義文に基盤の制約を破る指示が含まれていないか | 自動検出＋人的レビュー |
| ヘルプ | `help` とヘルプの記事があり、実際の挙動（使うツール・承認の場所）と一致しているか（第6.10.8節） | 自動検証＋人的レビュー |

第三者の定義文に「承認を求めずに送信せよ」といった指示が含まれていても、
基盤側の制約（第9.4節）が優先され、定義からは上書きできない。

### 12.6 版管理と互換性

| 項目 | 方針 |
|---|---|
| 定義スキーマの版 | `schema_version` で管理。破壊的変更はメジャー版を上げる |
| 互換性宣言 | マニフェストの `platform_schema` で対応範囲を宣言 |
| 自動更新 | 既定は「軽微な更新のみ自動」。権限が増える更新は必ず再同意 |
| 廃止 | 提供者は廃止予定を宣言でき、利用中テナントへ通知される |
| 後方互換 | 基盤は 1 つ前のメジャー版の定義を動かし続ける |

### 12.7 GUI からの拡張作成

**方針: 利用者にエージェントを一から設計させない。**
GUI で行えるのは**既存エージェントの設定変更**までとし、
新規作成は開発者が拡張機能（第12.3節）として行う。

第 0.118.0 版で、「設計させない」は**手順・承認の置き方を設計させない**ことと読み替える。
業務を文で書くこと（スキルの形式。第12.12節）は、業務を知る人ができる。段と承認は取り込むときに組み立てる。

理由は 2 つある。第一に、業務手順を一から設計するには承認ゲートの置き方や
ツールの危険度の理解が要り、一般の利用者には負担が大きい。
第二に、自由に作れる仕組みは品質と安全性の管理が難しく、
「誰も保守しないエージェント」が増える原因になる。

#### 12.7.1 GUI で変更できる範囲

| 対象 | 変更できるか | 例 |
|---|---|---|
| 文面・定型句 | できる | メールの書き出し、署名、報告書の見出し |
| 入力フォームの既定値 | できる | 対象期間の初期値、よく使う取引先 |
| 承認者 | できる | このエージェントは誰が承認するか |
| スケジュール | できる | 毎月 25 日に実行する |
| 上限 | できる | 1 回の実行にかける時間・コストの上限 |
| 参照する知識の範囲 | できる | どのフォルダ・どの規程を見るか |
| **手順（ステップ）** | **できない** | 拡張機能として開発者が定義する |
| **利用するツール** | **できない** | 権限に直結するため |
| **承認ゲートの有無** | **できない** | 安全性の根幹（第9.4節） |

#### 12.7.2 提供する機能

| 機能 | 内容 | フェーズ |
|---|---|---|
| 設定の編集 | 上表の「できる」項目を画面から変更する | 2 |
| 複製して調整 | 公式エージェントを複製し、自社向けに設定を変える | 2 |
| 試し実行 | サンドボックスで結果を確認してから有効化する | 2 |
| 秘書からの手順化 | 繰り返しを検知し、定型化の草案を提示する（UC-08） | 2 |
| 開発者向けの定義作成 | 拡張機能として新規のエージェントを作る | 3 |

**秘書からの手順化（UC-08）は例外的に草案の生成まで行う。**
ただし生成されるのは「こういう手順にしてはどうか」という提案であり、
実際に動くエージェントにするには開発者による定義化を経る。
利用者が自分で設計する必要はない。

### 12.8 選択的な有効化

| 段階 | 制御 | 実施者 |
|---|---|---|
| 1 | 拡張機能を導入するか | 管理者 |
| 2 | 拡張機能内のどのエージェントを有効にするか | 管理者 |
| 3 | 誰がそのエージェントを使えるか（ペルソナで指定） | 管理者 |
| 4 | 自分のメニューに何を並べるか | 各従業員 |

**無効なエージェントは画面に一切表示しない**（原則 p5）。

### 12.9 拡張機能の読み込みと導入（第 0.31.0 版の実装）

**この節で決めること**: L1（業務エージェント）の拡張機能を、どう読み込み、どう検証し、どう会社に導入するか。
作り方の詳細は開発者マニュアル（`docs/developer/`）に書く。

#### 12.9.1 パッケージの形式

| 項目 | 規定 |
|---|---|
| 置き場所 | 開発ではリポジトリ直下の `extensions/<名前>/`。1 つのディレクトリが 1 つの拡張機能 |
| 構成 | `SKILL.md`（第12.12節）、`HELP.md`、`connectors/*.json`（コネクタの宣言。第12.11節）、`evals/*.json`（評価のケース）、`README.md`。**`manifest.json`・`agents/*.json` の形は第 0.131.0 版で廃止した**（第12.12.7節）。M2Office の中では、SKILL.md から組み立てた後の形として使う |
| 形式 | 業務は SKILL.md（Markdown と、頭の YAML の見出し）。コネクタの宣言と評価のケースは JSON |
| 業務エージェントの ID | **`<拡張機能の ID>:<定義の ID>`**。公式の業務エージェントや他の拡張機能と衝突しない。定義の ID は英小文字・数字・ハイフン |

#### 12.9.2 読み込み時の検証

API とワーカーは起動時に拡張機能を読み込み、**検証を通ったものだけを使える状態にする**。
通らないものは読み込まず、理由を記録する。同じ検証を `npm run ext:validate` で事前に行える。

| # | 検証 | 根拠 |
|---|---|---|
| 1 | SKILL.md の形（`name`・`description`・本文・入力の欄）を満たす。JSON の定義は受け付けない（第12.12.7節） | 第12.12節 |
| 2 | SKILL.md から組み立てた定義が、エージェント定義の検証（承認ゲート・ツールの登録・承認者の指定など）を通る | 第9.2節、第9.4節 |
| 3 | `allowed-tools` の道具がすべて登録されている（会社の接続の道具は仮の道具で確かめる。第12.11節） | 不変則 I-8 |
| 4 | 扱う最大の危険度を道具から決め、同梱したコネクタの道具がそれを超えない | 第12.3節 |
| 5 | 業務の説明（`description` と `HELP.md`）がある | 第9.2.5節、第6.10.8節 |
| 6 | ID が公式の業務エージェントや他の拡張機能と重ならない | 第12.9.1節 |

#### 12.9.3 会社への導入

**読み込まれた拡張機能は、どの会社でもまだ使えない。** 管理者が導入して初めて、その会社で使えるようになる。

| 段階 | 内容 |
|---|---|
| 1 | 管理者ページの「拡張機能」に、導入できる拡張機能を一覧する（提供者・版・説明） |
| 2 | 導入の前に、**必要な権限を平易な言葉で示す**（使うツールの「すること」と、扱う最大の危険度） |
| 3 | 管理者が同意して導入する。同意した権限の一覧を記録する（不変則 I-8） |
| 4 | 導入した会社でだけ、メニュー・秘書・定時実行・ヘルプに業務エージェントが現れる |
| 5 | 削除すると使えなくなる。実行の記録は残す |

導入していない会社から、その業務エージェントを実行しようとしても拒否する（API とワーカーの両方で確かめる）。

#### 12.9.4 評価のケース（第 0.119.0 版で改める）

**評価のケース（`evals/*.json`）は、業務の品質を確かめるための「入力と期待する結果」である。** 本物の推論で実行して確かめる（第12.5節の審査にも使う）。

以前は、LLM の鍵が無い開発環境のために、評価のケースに**見本の応答**（`stub`）を書かせていた。
第 0.119.0 版で、鍵が無い環境を想定しないことにした（第20.2.4節、ADR-0030）。**拡張機能を作る人は見本の応答を書かなくてよい。**
見本の応答の仕組みは、M2Office 自身の自動テスト（単体テストと通しの確認）の中でだけ使う。

#### 12.9.5 まだ実装していないもの

| 項目 | 状態 |
|---|---|
| L2 コネクタ（MCP サーバの接続） | 第12.11節で規定。`auth: none` は実装済み。`oauth`・`api_key` はこれから（Q-72） |
| 拡張機能の `help/` の記事 | 未実装（第6.10.11節の Phase 2）。業務の説明は定義から自動で作る |
| マーケット・審査・配布区分の表示 | 第12.10節で、公式の配布元とファイルからの取り込みを規定。審査と第三者の配布元は未実装 |
| 版の更新と再同意 | 未実装（第12.6節） |
| GUI からの作成 | 未実装（第12.7節） |

### 12.10 持ち運べる拡張機能 ― 取り込みと有効化

**この節で決めること**: 拡張機能を 1 つのファイルとして持ち運び、画面で取り込み、スイッチで有効にする方法。

**拡張機能は、ブラウザの拡張機能と同じ感覚で扱えるものにする。**
配布元から選ぶか、ファイルを受け取って取り込み、スイッチを入れれば使える。
これが第2.3.3節の「GUI で拡張できる」の実体であり、M2Office の最大の売りである。

#### 12.10.1 拡張機能に含められるもの

| 構成要素 | 置き場所 | 内容 | 階層 |
|---|---|---|---|
| **業務エージェント（スキル）** | `SKILL.md`（第12.12節。`agents/*.json` は第 0.131.0 版で廃止） | 業務の指示（プロンプト）。段と承認は取り込むときに組み立てる | L1 |
| スキルの補助のファイル | `reference.md`・`examples.md`・`references/*.md` など（Markdown・テキスト） | 本文から参照し、推論が必要なときに読む（第12.12.2節） | L1 |
| 利用者向けの説明 | `HELP.md` | 業務の説明（「？」）とヘルプセンターに出す（第12.12.4節） | L1 |
| **コネクタ** | `connectors/*.json` | 外部の MCP サーバへの接続の宣言（第12.11節） | L2 |
| **ツール** | コネクタが提供する | コネクタの MCP サーバが持つ操作。拡張機能はその一覧と推奨の危険度を宣言する | L2 |
| 評価のケース | `evals/*.json` | 第12.9.4節（入力と期待する結果。品質の確認に使う） | — |
| 説明 | `README.md`・`icon.png` | 管理者向けの説明とアイコン | — |

**ツールは、コネクタを通じてのみ持ち込める。** 第三者が書いた処理を M2Office の中で動かさないため
（不変則 I-7）、ツールの実体はコネクタの MCP サーバ（M2Office の外）に置く。
拡張機能には、業務エージェントだけのもの、コネクタだけのもの（ツールを提供する）、両方を含むものがある。

#### 12.10.2 ファイルの形式

| 項目 | 規定 |
|---|---|
| 形式 | **ZIP**。拡張子は `.m2ext`（`.zip`・`.skill` も受け付ける）。直下に `SKILL.md`（第12.12節）か `manifest.json` を置く。**SKILL.md 1 つだけのファイルも取り込める**（第 0.118.0 版） |
| 作り方 | `npm run ext:pack <ディレクトリ>` でディレクトリから作る |
| 大きさ | 5 MB まで |
| 入れてよいファイル | `SKILL.md` とその資料（Markdown・テキスト）、`connectors/*.json`、`evals/*.json`、`help/*.md`、`README.md`、`icon.png`（PNG、256 KB まで） |
| **入れてはならないファイル** | それ以外のすべて。**とくにプログラム（`.js`・`.py`・実行ファイルなど）は動かさない。** `manifest.json` の形では拒否する。SKILL.md の形では取り込むときに除き、除いたことを示す（スキルには `scripts/` が付いていることが多いため。第12.12.4節） |
| 検証 | 取り込みの時点で第12.9.2節の検証を行い、通らなければ取り込まない |

#### 12.10.3 取り込み元

| 取り込み元 | 扱い | 見える範囲 | 表示 |
|---|---|---|---|
| **配布元**（M2Office 公式） | 運営が検証して置いたもの。いまはリポジトリの `extensions/` | 全テナント | 「公式」 |
| **ファイル**（`.m2ext`） | 管理者が画面から取り込む。**プライベート拡張**（第12.4節） | **取り込んだテナントのみ** | 「自社専用」 |
| 配布元（第三者のリポジトリ） | 配布元の一覧（索引）の URL を登録し、そこから選ぶ | 登録したテナント | 「未審査」 |

第三者の配布元を認めるかどうかと、その審査は Q-71 で決める。
いまは公式の配布元とファイルの 2 つを実装する。

#### 12.10.4 状態の遷移

| 操作 | 前の状態 | 後の状態 | 同意 |
|---|---|---|---|
| ファイルから取り込む | — | 取り込み済み（そのテナントの配布元に並ぶ） | 不要（検証だけ） |
| 導入する | 配布元にある・取り込み済み | **導入済み・有効** | **権限に同意する** |
| スイッチを切る | 導入済み・有効 | 導入済み・無効 | 不要 |
| スイッチを入れる | 導入済み・無効 | 導入済み・有効 | 不要（権限が増えた版では再同意） |
| 削除する | 導入済み | 未導入 | 確認のみ |

| 状態 | 業務エージェント | コネクタ | データ |
|---|---|---|---|
| 導入済み・有効 | メニュー・秘書・定時実行に出る | 同梱の接続を会社の接続として登録する（無ければ） | — |
| **導入済み・無効** | **出ない。実行できない** | 会社の接続は残す（止めるのは「接続 › コネクタ（MCP）」） | 実行の記録と設定を残す |
| 削除 | 出ない | 同梱していた接続は会社の接続として残す（第12.11.0節） | 実行の記録は残す |

**スイッチは同意をやり直さずに切り替えられる。** 権限の同意は導入のときに 1 回だけ行う。
ただし、新しい版で権限が増えた場合は、スイッチを入れる前に再同意を求める（第12.6節）。

### 12.11 コネクタ（L2）の実装

**この節で決めること**: MCP サーバへの接続（コネクタ）を会社の資源として登録し、そのツールを秘書・業務が使えるようにする方法。

#### 12.11.0 位置付け（第 0.132.0 版、ADR-0037）

```
秘書・公式の業務・拡張機能（SKILL.md）   ← 道具を使う側。allowed-tools に名前を書くだけ
────────────────────────────────
内蔵の道具（Google Workspace など） ＋ 会社の接続（MCP）  ← 道具を供給する側。会社で一元管理
```

| 項目 | 規定 |
|---|---|
| 管理の単位 | **会社**。管理者ページ「接続 › コネクタ（MCP）」（第6.6.3節）で登録・危険度・入り切り・削除を行う |
| 使う側 | 秘書・公式の業務・拡張機能のどれからでも、**`<接続の ID>.<ツールの名前>`**（例: `deepwiki.ask_wiki_question`）で使う |
| 拡張機能に同梱したもの | 拡張機能は、使う接続の宣言（`connectors/*.json`。第12.11.1節）を**同梱して提案できる**。導入のとき、会社にその ID の接続が無ければ登録する。あれば使い回す（接続先が違えば置き換えず、そのことを知らせる） |
| 同梱していない接続を使う業務 | `allowed-tools` に `<接続の ID>.<道具>` を書けば使える。その会社にその接続が無ければ、**業務は使えず「接続が要ります」と示す**（メニュー・秘書・定時実行から外す） |
| 秘書 | 秘書の調べもの（第10.11.4節）は、会社の接続の**読むだけの道具**を使える。書き込み・送信の道具は、その道具を使う業務に頼む（第10.9.6節） |
| 外すとき | 接続を消すと、その道具を使う業務は使えなくなる。消す前に業務の名前を示して確かめる |
| 拡張機能を外したとき | 同梱していた接続は**消さない**（会社の資源として残す。ほかの業務が使っているかもしれない） |

#### 12.11.1 接続の宣言（`connectors/*.json`）

拡張機能に同梱するときの形。管理者が画面で登録するときは、URL を入れれば M2Office がこの形に組み立てる。

```json
{
  "id": "deepwiki",
  "name": "DeepWiki",
  "description": "GitHub のリポジトリの説明文書を調べます",
  "transport": "http",
  "url": "https://mcp.deepwiki.com/mcp",
  "auth": { "type": "none" },
  "tools": [
    { "name": "ask_wiki_question", "description": "リポジトリについて質問し、答えを得ます", "risk": "read" }
  ]
}
```

| 項目 | 規定 |
|---|---|
| `id` | 接続の ID。英小文字・数字・ハイフン。**会社の中で重ならないこと**。内蔵の道具の頭の部分（`gmail` など）とも重ならないこと |
| `transport` | `http`（MCP の Streamable HTTP）。M2Office の中でプロセスを起動する方式（stdio）は使わない（不変則 I-7） |
| `url` | MCP サーバの URL。`https` に限る（開発環境の `localhost` を除く） |
| `auth.type` | `none`（認証なし）・`oauth`（会社がアプリを登録し、利用者ごとに認可。Slack など）・`api_key`（管理者が登録する会社の鍵）。規定は第12.11.6節 |
| `tools` | 使うツールの一覧。`name` は MCP サーバでの名前、`risk` は推奨の危険度 |

#### 12.11.2 ツールの危険度

| 項目 | 規定 |
|---|---|
| 決める人 | **会社の管理者**。接続の画面で道具ごとに決める |
| 初期値 | 同梱の宣言にあればその推奨の危険度。管理者が URL で登録したときは、MCP の道具の目印（`readOnlyHint`）があれば `read`、無ければ **`external-send`**（承認が入る安全側。第14.4節の「既定は最も厳しい扱い」） |
| 宣言していないツール | MCP サーバが提供していても、接続の道具の一覧に無いものは使わない |
| 業務の組み立て | SKILL.md を組み立てるとき、会社の接続の道具の危険度はまだ分からない。**`external-send` として組み立て**（承認の段が入る）、実行のときは会社が決めた危険度で判断する。読むだけの道具なら承認は自動で通る（第9.4.0節）。**導入の同意に示す最大の危険度も `external-send` として数える**（第 0.140.5 版。それまでは仮の道具の危険度（読むだけ）で数え、投稿する業務でも同意の画面に「読むだけ」と出ていた） |

同意の画面で推奨の危険度を明示して同意を得ることは、管理者による割り当てにあたる（Q-73）。

#### 12.11.3 呼び出し

| 項目 | 規定 |
|---|---|
| 呼ぶ側 | ワーカーが MCP の `tools/call` を呼ぶ。承認・操作の確認・監査ログは内蔵ツールと同じ（第9.4節） |
| 引数の定義 | 道具の一覧（`tools/list`）の `inputSchema` を道具の宣言に写し、**推論に引数の名前と説明を渡し、呼ぶ前に確かめる**（第9.4.4節）。登録と「道具を取り直す」のたびに相手の最新のものにする（第 0.140.3 版。それまでは渡しておらず、推論が引数を知らずに呼んで検索の言葉が空のまま届いた。2026-09-27 に Slack で確認） |
| 承認の画面での見せ方 | 相手の道具の説明（英語で長いことがある）は推論にだけ渡し、**人には「Slack へ送ります（slack_send_message）」のように、接続の名前・危険度の言い方・相手の道具の名前と、送り先を含むすべての引数を出す**。型に言葉があれば引数の名前を直し（`channel_id` → 送り先、`message` → 本文）、型に問い合わせがあれば**承認の前に ID を名前に直す**（「送り先: #研究開発（C0C4WEH1TNY）」。読むだけ・依頼した本人の認可。直せなければ ID のまま。第 0.140.5 版）（第 0.140.4 版。引数の意味が分からない相手でも、どこへ何が行くかを承認する人が見て判断できるように。2026-09-27 に Slack への投稿で確認） |
| 応答 | テキストとして受け取り、**外部のデータとして扱う**（不変則 I-6）。長すぎる応答は切り詰める |
| 失敗 | 接続できない・時間切れ・MCP のエラーは「取得できませんでした」として返し、推測で続けない。相手が理由を返していれば、短く添える（第 0.140.3 版） |
| 時間の上限 | 1 回の呼び出しは 60 秒まで |
| 接続の確認 | 管理者ページから `tools/list` を呼び、登録した道具が提供されているかを確かめられる |

#### 12.11.4 自動テストとの関係

コネクタのツールは**本物の MCP サーバを呼ぶ**。M2Office の自動テストでは、見本の応答（第12.9.4節）で道具の呼び出しを決め、
その引数に前のステップの結果を差し込める（`{{ステップ ID}}`）。拡張機能を作る人が書くものではない（ADR-0030）。

#### 12.11.5 段階

| 段階 | 内容 |
|---|---|
| 実装済み | `auth: none` のコネクタ、道具と危険度、呼び出し、接続の確認。サンプル: DeepWiki。**会社の接続としての一元管理**（第 0.132.0 版）。**`auth: oauth`（会社が登録し、利用者ごとに認可）と `auth: api_key`（会社の鍵）、認証情報の暗号化、よく使うサービスの型（Slack）**（第 0.140.2 版。規定は第12.11.6節） |
| 本物で確かめたこと | **Slack の公式の MCP サーバ**（2026-09-27、`oesf`）。社内向けアプリの登録、利用者の許可、管理者の許可での道具の取り直し（10 の道具。読むもの 7・書くもの 3）、接続の確認、本人の許可でのユーザーの検索（読むだけ）、**承認を経た #研究開発 への投稿**（本人の名前で投稿され、Slack に「M2Office を使用して送信」と出た）と、その読み返し |
| そのあと | 第三者の配布元、ダッシュボードの「接続先」への表示 |

#### 12.11.6 認証の要る接続（第 0.140.0 版、ADR-0044）

**認証の要る MCP サーバにも、会社の接続としてつなげるようにする**（Q-72 で決定）。
最初の相手は **Slack の公式の MCP サーバ**（`https://mcp.slack.com/mcp`）とする。会社がアプリを登録し、利用者ごとに認可する形が、M2Office の決まり（本人の権限を超えない。不変則 I-9）とそのまま合うためである。

##### 12.11.6.1 認証の型

| 型 | 誰のものとして動くか | 認証情報を持つ人 | 使いどころ |
|---|---|---|---|
| `none` | 認証なし | なし | 公開の情報を返すサーバ（DeepWiki など。実装済み） |
| `oauth` | **利用者ごと**。業務は依頼した本人のものとして呼ぶ | 会社がアプリ（クライアント ID とシークレット）を登録し、**各利用者が自分のアカウントで認可する** | 本人のデータを扱うサービス（Slack など） |
| `api_key` | **会社**。誰が呼んでも会社の鍵で動く | 管理者が鍵を登録する | 会社で 1 つの口座を使うサービス（会計・販売管理など） |

**`oauth` を基本にする。** 本人ごとの権限がそのまま効くためである。
`api_key` は会社として動くため、本人ごとの権限の区別が無い。管理者は、道具の危険度（第12.11.2節）と、その接続を使う業務の利用範囲（第16.7.3節）で絞る。

##### 12.11.6.2 管理者が登録する（`oauth`）

登録の流れは、Google Workspace の接続（第14.3.3節）と同じ作りにする。

| 手順 | 管理者が行うこと |
|---|---|
| 1 | 管理者ページ「接続 › コネクタ（MCP）」で、接続先の URL を入れる。**よく使うサービスは型から選べる**（第12.11.6.7節。Slack など）。型を選ぶと、URL・認可の口・求める権限が入る |
| 2 | 画面に出る**戻り先の URL**（リダイレクト URI）を、相手のサービスで作ったアプリに登録する |
| 3 | アプリの**クライアント ID とシークレット**を登録する。シークレットは暗号化して持ち、**登録後は表示しない**（上書きと削除だけ） |
| 4 | 管理者が自分のアカウントで「接続して確かめる」を行う。認可できたら、**管理者の認可で道具の一覧（`tools/list`）を問い合わせて並べ**、危険度を決める（第12.11.2節） |
| 5 | 利用者がそれぞれ接続する（第12.11.6.3節） |

| 項目 | 規定 |
|---|---|
| 認可の口 | 相手のサーバの案内（保護されたリソースの情報と認可サーバの情報。MCP の認可の決まり）から自動で見つける。**見つからなければ、型に書いた口を使うか、管理者が入れる** |
| アプリの自動登録 | 行わない。会社が相手のサービスでアプリを作って登録する（Slack は自動登録に対応していない）。自動登録への対応は Q-99 |
| 求める権限 | 型、または相手のサーバの案内にある権限から、**会社で使う道具が要るものだけ**を求める（第14.3.2節と同じ考え方）。道具を足して権限が増えたら、利用者に接続し直しを促す |
| クライアント ID を替える・接続を消す | 前に「接続している○人の認可が使えなくなります」と示して確かめ、全員の認可を消す。**シークレットだけを替える場合は認可を消さない** |
| 拡張機能に同梱した `oauth` の接続 | 導入のときに接続を登録するが、クライアント ID とシークレットが入るまでは「設定が要ります」と示し、使えない |

##### 12.11.6.3 利用者が接続する（`oauth`）

| 項目 | 規定 |
|---|---|
| 場所 | 個人設定「サービスとの接続」（第6.5.9節）。会社に `oauth` の接続があるときだけ出す |
| 接続 | 「Slack と接続する」で相手のサービスの許可の画面へ進み、**本人のアカウントで許可する**。戻ってきたら、許可されたアカウント（ワークスペースと名前）を示す |
| 求められたときに接続する | **全員に先に接続させない。** 接続していない人がその接続の道具を使う業務を開く・秘書に頼むと、「Slack との接続が要ります」と接続のボタンを出す。定時実行は、接続するまで起動を飛ばし、一度だけ知らせる |
| 戻り先の検証 | 認可の要求には使い捨ての `state` と PKCE を付け、戻ってきた要求を照合する。照合できなければ何もしない（第14.3.3節と同じ） |
| 取り消し | 本人が個人設定で取り消せる。相手のサービスに取り消しの口があれば、そこでも取り消す。保存した認可を消す。取り消す前に、使えなくなる業務と止まる定時実行を示す |
| 言葉 | 「鍵」「トークン」という言葉を使わない（第6.5.2節と同じ。原則 u1） |
| 管理者に見せるもの | 利用者ごとの接続の有無と接続した日時。**認可の中身は見せない** |

##### 12.11.6.4 呼び出し

| 項目 | 規定 |
|---|---|
| 誰の認可で呼ぶか | **業務を依頼した本人の認可**で呼ぶ。定時実行はその持ち主、段取り（第10.14節）の各段は依頼した本人、秘書の調べもの（第10.11節）は頼んだ本人。**ほかの人の認可で代わりに呼ばない**（不変則 I-9） |
| 承認のあとに送る段 | 承認した人ではなく、**依頼した本人の認可で送る**（Gmail の送信と同じ。第14.3.4節） |
| 送り方 | 認可を `Authorization: Bearer` で付けて、これまでどおり `tools/call` を呼ぶ（第12.11.3節）。認可はワーカーの中だけで使い、推論にも画面にも渡さない |
| 期限の切れた認可 | 相手のサービスが更新の仕組みを持つなら、呼ぶ前か断られたときに更新して 1 回だけ呼び直す |
| 読んだデータ | 外部のデータとして扱い、中の指示に従わない（不変則 I-6）。相手のサービスの利用条件（学習に使わない等）に従う（Q-101） |

##### 12.11.6.5 認可が切れたとき

第6.5.2.1節（Google の許可がなくなったとき）と同じ考え方で扱う。

| 経路 | 扱い |
|---|---|
| 本人が個人設定で取り消す | 取り消す前に止まるものを示す。待ち行列と承認待ちのうち、その接続の道具を使う本人の業務を止め（`cancelled`）、理由を残して知らせる |
| 相手のサービスの側で許可が外れた（更新にも失敗した） | その時点で保存した認可を消し、その業務を「取得できませんでした: Slack との接続が切れました」で失敗にする。本人に「個人設定から接続し直してください」と知らせる |
| 管理者がクライアント ID を替える・接続を消す | 第12.11.6.2節のとおり、確かめてから全員の認可を消し、同じく後始末をする |
| 定時実行 | 設定は残し、接続し直すまで起動を飛ばす |

##### 12.11.6.6 会社の鍵で動く接続（`api_key`）

| 項目 | 規定 |
|---|---|
| 登録 | 管理者が鍵を登録する。暗号化して持ち、登録後は表示しない（上書きと削除だけ） |
| 送り方 | 既定は `Authorization: Bearer <鍵>`。相手が別の見出し（`X-API-Key` など）を求めるなら、登録のときに見出しの名前を選ぶ |
| 動く主体 | **会社**。誰が依頼しても同じ鍵で呼ぶ。監査ログには依頼した本人を残す |
| 絞り方 | 道具の危険度、道具の入り切り（第6.6.3.1節）、業務の利用範囲。接続そのものを使える人を絞るかは Q-100 |
| 最初に確かめる相手 | 鍵でつなぐ MCP サーバ（freee などの会計・販売管理の候補）。Slack の公式サーバは `oauth` だけのため使わない |

##### 12.11.6.7 よく使うサービスの型（最初は Slack）

中小企業の管理者が、相手のサービスの認可の細かい決まりを調べなくて済むように、**よく使うサービスの登録の型**を M2Office が持つ。型は宣言（第12.11.1節の形に認可の情報を足したもの）であり、プログラムは持たない。

| 項目 | Slack の型 |
|---|---|
| 接続先 | `https://mcp.slack.com/mcp`（Streamable HTTP） |
| 認証 | `oauth`。Slack のアプリのクライアント ID とシークレット。**利用者ごとのユーザートークン**を受け取る |
| 認可の口 | `https://slack.com/oauth/v2_user/authorize`（許可の画面）、`https://slack.com/api/oauth.v2.user.access`（受け取り） |
| 求める権限 | 会社で有効にした道具が要るものだけ（例: 検索と読み取りは `search:read.public`・`channels:history` など、投稿は `chat:write`） |
| 相手の側で要ること | ワークスペースに**社内向けのアプリ**を作る（非掲載のアプリは Slack の MCP を使えない）。戻り先の URL と権限をアプリに登録する。**アプリの設定の「Agents & AI Apps」で Slack の MCP サーバの利用をオンにする**（オフのままだと MCP サーバが「App is not enabled for Slack MCP server access」で断る。2026-09-27 に実機で確認）。ワークスペースの管理者がアプリを承認する運用なら、その承認 |
| 承認の画面の言葉 | 引数の名前を「送り先」「本文」「返信先のスレッド」などにし、送り先の ID をチャンネル名（`conversations.info`）か人の名前（`users.info`）に直して出す（第 0.140.5 版） |
| 道具の危険度の初期値 | 検索・読み取り（メッセージ・チャンネル・ファイル・ユーザー・キャンバスを読む）は `read`。**投稿・予約投稿・チャンネルの作成・リアクション・キャンバスの作成と更新は `external-send`**（社外の人がいる Slack コネクトのチャンネルがありうるため。確かめられなければ社外とみなす。第9.4.0節） |
| 確かめる順番 | 読む道具（検索・チャンネルを読む）で、利用者ごとの認可と呼び出しを確かめる。投稿は、承認を挟み、テスト用のチャンネルにだけ行う |

出典: Slack Developer Docs「Slack MCP server overview」（https://docs.slack.dev/ai/slack-mcp-server/ 、2026-09-27 に確認）。型は相手の変更に合わせて直し、確認日を型に書く。

### 12.12 スキルの形式で書く（第 0.118.0 版。第 0.120.0 版で書き直し。ADR-0029）

**業務エージェントは、エンジニアが知っているスキル（Claude Code の Skills・Agent Skills）の書き方のまま書く。**
M2Office で動かすために覚えることは、第12.12.1節の 4 つだけにする（2026-09-26 に三浦さんが指示）。
スキルの項目は、M2Office で意味のあるものはそのとおりに効かせ、意味の無いものは無視して知らせる（第12.12.2節）。
公開されている数多くのスキルを土台に、管理・監督・承認・監査のある M2Office の環境で業務として展開できるようにする（販売の売り）。
**JSON で書く形は第 0.131.0 版で廃止した**（第12.12.7節）。 中では SKILL.md をエージェント定義（第9.2節）に組み立てて動かす。

```
expense-check/                ← このフォルダを ZIP にして取り込む（SKILL.md 1 つだけでもよい）
  SKILL.md                    必須。スキルの書き方のまま
  HELP.md                     任意。利用者向けの説明（M2Office で足すもの）
  reference.md・examples.md など  任意。本文から参照する補助のファイル（Markdown・テキスト）
```

```markdown
---
name: expense-check
description: 経費の申請を社内の規程と照らし合わせ、足りない領収書や規程に合わない点を指摘する
when_to_use: 「経費を確認して」「この精算は通る？」と頼まれたとき
argument-hint: 申請の内容を貼り付けてください
allowed-tools: knowledge.search file.read_text
---

# 経費精算チェック

次の申請を、社内の規程（経費規程・出張旅費規程）と照らし合わせる。

$ARGUMENTS

- 領収書が無い、上限を超える、対象外の費目、を 1 つずつ挙げる
- 規程の条を出典として示す。規程に無いことは「規程に記載なし」と書き、推測で判断しない
- 費目の区分は [reference.md](reference.md) に従う
```

#### 12.12.1 M2Office で覚えること（これだけ）

| # | 覚えること | 内容 |
|---|---|---|
| 1 | **道具は `allowed-tools` に M2Office の道具を書く** | M2Office の道具の名前（`knowledge.search`・`gmail.create_draft` など。開発者マニュアル 第4章）を空白で区切る。会社の接続（第12.11節）の道具は `<接続の ID>.<道具>`（例: `deepwiki.ask_wiki_question`）で書く。同じフォルダの `connectors/*.json` で同梱もできる（第 0.131.0 版・第 0.132.0 版）。書かなければ読むだけの道具（社内の知識を探す・渡された書類を読む）。スキルの環境の道具（`Bash`・`Read`・`Write` など）は M2Office には無いため無視し、取り込みの画面で知らせる。**M2Office では、書いた道具しか使えない**（許可の一覧であり、同意の画面に出る。不変則 I-8） |
| 2 | **利用者向けの説明は `HELP.md` に書く** | SKILL.md の隣に置く。業務の説明（題名の「？」）とヘルプセンターに、書いたとおりに出す（第12.12.4節）。SKILL.md は推論が読む指示、HELP.md は人が読む説明として分ける |
| 3 | **プログラムは動かない** | `scripts/` のプログラム、本文の `` !`コマンド` ``、`${CLAUDE_SKILL_DIR}` を使った実行は行わない（不変則 I-7）。取り込むときに除き・消し、そのことを知らせる。処理が要るならコネクタ（MCP。第12.11節）にする |
| 4 | **承認は書かない** | 送る道具（`gmail.send`・`chat.post` など `external-send` 以上）を `allowed-tools` に書くと、M2Office が「作業 → 承認 → 送る」を組み立てる。承認は、社外にもお金にも関わらなければ自動で通る（第9.4.0節、ADR-0028） |

#### 12.12.2 スキルの項目の扱い

| スキルの項目 | M2Office での扱い |
|---|---|
| `name` | 業務の ID の一部（`<拡張機能の ID>:<name>`）。**省けばフォルダの名前**（スキルと同じ） |
| `description` | メニューの説明と、**秘書が業務へ取り次ぐときの手がかり**（スキルの自動の呼び出しと同じ役割）。省けば本文の最初の行 |
| `when_to_use` | `description` に添えて、秘書の取り次ぎの手がかりにする |
| 本文の最初の見出し（`# 〇〇`） | 画面に出す業務の名前。無ければ `name` |
| 本文 | **業務の指示そのもの**（推論が読む） |
| `argument-hint` | 依頼の欄に薄く置く例 |
| `arguments` | 入力の欄（1 つの名前が 1 つの欄）。書かなければ自由記入の「依頼」の欄 1 つ |
| `$ARGUMENTS`・`$ARGUMENTS[N]`・`$N`・`$名前` | **実行のときに入力で置き換える**（スキルと同じ）。`$ARGUMENTS` は入力のすべて。本文に無くても、入力は推論に渡す |
| `disable-model-invocation: true` | 秘書は取り次がない。メニューからだけ使う |
| `user-invocable: false` | メニューに出さない。秘書が取り次いだときだけ使う |
| `allowed-tools` | M2Office の道具の一覧（第12.12.1節 1） |
| `effort` | 推論の強さ。`low` は高速のモデル、`medium`・`high` は標準、`xhigh`・`max` は高性能のモデル（第20.2.2節） |
| `model` | 使わない（M2Office は会社の Gemini で動く）。知らせる |
| `context`・`agent`・`background` | 使わない（M2Office の業務は、もともと 1 件ずつ独立して動く） |
| `disallowed-tools`・`hooks`・`paths`・`shell` | 使わない。知らせる |
| `license`・`compatibility`・`metadata` | 保つ。`metadata.version`・`metadata.author` は拡張機能の版と提供者に使う |
| 補助のファイル（`reference.md`・`examples.md`・`template.md` など） | **スキルと同じく、本文から参照したファイルを、推論が必要なときに読む**（読むだけの道具 `skill.read`。Markdown・テキストのみ、合計 50 万字まで） |

#### 12.12.3 `metadata` の `m2office-*`（要るときだけ）

スキルの項目で言い表せないことだけを、`metadata` の中に置く（値はすべて文字。Agent Skills の決まり）。**ふつうは要らない。**

| 名前 | 使うとき | 書き方 |
|---|---|---|
| `m2office-id` | 他の会社に配るとき（逆ドメイン名の ID） | 例: `jp.example.expense`。無ければ `skill.<name>`（自社専用） |
| `m2office-inputs` | 欄に種類（長文・日付・ファイル）や任意の印を付けたいとき | 1 行に 1 つ「欄の名前: 種類」。種類は `短文`・`長文`・`日付`・`ファイル`、後ろに「（任意）」。`arguments` より優先する |
| `m2office-examples` | 業務の説明に実行例のボタンを出したいとき | 1 行に 1 つ（押すと最初の欄に入る） |
| `m2office-approver` | 社外に出すものを依頼した本人以外が承認するとき | `承認者`・`管理者`。無ければ依頼した本人 |
| `m2office-private` | 結果を秘書の記憶に入れたくないとき（契約書など機密の業務。第 0.139.0 版） | `true`。書いた業務の結果からは、秘書が学ばず（第10.13節）、秘書の答えに結果の要点を添えない（第10.7.3節）。秘書が結果を伝えた会話も、会話ログには残すが学ばない（本人が「さっきの契約書の第 6 条を詳しく」と続けられるように。第 0.146.0 版で実装）。例: 契約書チェック（第28章） |

#### 12.12.4 HELP.md（利用者向けの説明）

| 項目 | 規定 |

| 置き場所 | SKILL.md の隣。任意 |

#### 12.12.5 取り込むときに組み立てるもの

利用者には見せない。中では第9.2節の定義で動くため、承認の強制・監査・権限の同意（不変則 I-8）・権限区画は変わらない。

| 結果 | 最後の段の文を結果として出す（第6.2.2節） |

| 会社の名前 | 会社の正式名称と略称を指示に添える（第15.2.1節の「自社の書き方」と同じ経路。第 0.139.0 版。**第 0.146.0 版で実装。スキルに限らずすべての業務に添える**。会社情報の正式な会社名が無ければ、申し込みのときの会社名）。契約書の当事者のどちらが自社かを見分けるなどに使う（第28.4節） |

### 12.13 内蔵の拡張（第 0.139.0 版、ADR-0042）

**データの置き場（表）や専用の画面を要する業務は、拡張機能（第12.10.1節）では作れない。** 拡張機能は宣言的なファイルだけで、
第三者のコードを M2Office の中で動かさない（不変則 I-7）ためである。そうした業務のうち、中小企業が共通して使うものは、
**M2Office 運営が中核に組み込み、拡張機能と同じように会社ごとに入り切りできる「内蔵の拡張」**として作る。

| 項目 | 規定 |
|---|---|
| 作る人 | M2Office 運営だけ。第三者は作れない（第三者は L2 のコネクタか L3 の外部アプリで作る。第12.1節） |
| 持てるもの | 表（テナント ID で絞る。不変則 I-2）、画面、道具、付属の業務エージェント |
| 入り切り | 管理者ページの「拡張機能」の一覧に「公式・内蔵」として並べ、会社ごとに切れる（第12.10.5節）。切ると画面・道具・付属の業務を出さない。**データは消さない**（入れ直せば戻る） |
| 利用範囲 | 拡張機能と同じく、使える人を部署やグループで絞れる（第16.7.3節） |
| 仕様の置き場 | 第 X 部に 1 章ずつ置く（第0.3節 約束 7） |
| いまあるもの | 名刺管理（第27章。第 0.144.0 版で実装） |
| 管理者ページ（第 0.144.0 版） | 「拡張機能」の導入済みに「公式・内蔵」として並べる。導入と削除の操作は無く、スイッチで入り切りする（会社の設定に持つ）。拡張機能ごとの設定（名刺管理の既定の範囲）もここに置く |

**拡張機能で作れるものは、内蔵にしない。** 契約書チェック（第28章）は、表も画面も要らないため公式の拡張機能として作る。
