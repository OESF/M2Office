## 33. 問い合わせの記録（お客様の声。第 0.227.0 版。第 0.228.0 版で窓口と LINE を統合。案。第 0.230.0 版で段 1、第 0.232.0 版で段 2 を実装）

この章で決めること: 電話・メール・Web のフォーム・LINE・来店などで届いたお客様からの問い合わせを、**会社の対外の窓口に寄せて 1 つの会話の履歴にまとめ**（電話と来店は話すか書くだけで残し）、次の対応を取りこぼさず、集まった声を次の集客（Web の振り返り・コラムの作成）につなぐしくみ。

**この章は案である。** **汎用の記録のしくみとして作る。** 特定の導入先・業種の条件に合わせた作りにしない。
会社ごとの違いは、導入のときに会社が設定する項目（第33.4節）で吸収する。まだ確かめる事項（第33.16節）の答えで直してから実装する。
**「（案）」と書いた値は、会社（三浦さん）の判断を待つ値である。** 方針の判断の記録は [ADR-0067](../docs/adr/0067-inquiries-and-web-review.md)。

**2026-10-03 に三浦さんが示した狙い**

- 顧客からの問い合わせ（たとえば電話）に対して、**ある程度の履歴を残し、将来のマーケティングにつないでいく**サービスを提供したい。
- 同じ日に、メールの問い合わせも統合すべきとした。**info@ のような会社の窓口のアカウントを 1 つ作り、対外のすべての窓口にして、その会話の履歴を残し、マーケティングに使う**。LINE も統合する（第 0.228.0 版。最初の案では LINE は先でよいとしていた）。
- 三浦さんが、別々の内蔵の拡張にすること・既定で会社で共有すること・Web の振り返り（第34章）より先に作ることを、おすすめのとおりに選んだ（2026-10-03）。

### 33.1 目的と位置づけ

| 痛み | M2Office で行うこと |
|---|---|
| 電話の内容が、受けた人の頭とメモ用紙にしか残らない | 電話を切った後に**秘書へ話すか書くだけ**で、AI が用件・次にやること・どこで知ったかに分けて残す（第33.5節） |
| 誰が対応しているか、返事をしたか分からない | 次にやることと期限を持ち、近づけば担当に知らせる。朝のブリーフにも載せる（第33.7節） |
| 対外の窓口が人ごとにばらばらで、やり取りが個人の受信箱に埋もれる | **会社の窓口のアカウント**（info@ など）を 1 つ決め、Web のフォーム・名刺・Web サイトの連絡先をそこにそろえる。届いたメールと返事を、会話の履歴として残す（第33.6節） |
| 問い合わせがメール・LINE・電話・来店に散らばる | 入口を問わず、1 つの台帳にまとめる。LINE 公式アカウントのやり取りも入れる（第33.6.2節）。同じ人は名刺管理の連絡先とつなぐ（第33.6.1節） |
| 集客の判断の材料が無い | 「どこで知ったか」と分類が毎回残るので、月ごとの数と傾向が出る。よくある質問はコラムのテーマ案と、よくある質問のページの案になる（第33.9節） |

#### 33.1.1 想定する会社

| 項目 | 想定 |
|---|---|
| 会社 | 中小企業・店舗・士業など、お客様から電話やメールで問い合わせを受ける会社。Web サイトが無い会社でも使える |
| 件数 | 月に数件〜数百件 |
| 受ける人 | 専任の窓口がいない会社が多い。電話に出た人がそのまま受ける |
| 医療機関 | **患者さんの問い合わせは扱わない**（M2 Medical の範囲。ADR-0063）。医療機関でも、取引先・業者・採用などの問い合わせには使える |

### 33.2 形: 内蔵の拡張（既定は切り。案）

名刺管理・コラムの作成と同じく、**内蔵の拡張**（第12.13節）「問い合わせの記録」とする（ADR-0067）。Web の振り返り（第34章）とは**別の拡張**にする。Web サイトを持たない会社でも使えるようにするため。

| 項目 | 規定 |
|---|---|
| 入り切り | 管理者ページの「拡張機能」。**既定は切り** |
| 料金 | 無償で同梱する（Q-173。第 0.229.1 版で決定） |
| 左のメニュー | 業務の 1 つとして「問い合わせの記録」を出す |
| 業務（付属） | 「問い合わせを残す」「窓口のメールを読む」「問い合わせの返事」「問い合わせの振り返り」。秘書が取り次ぐ（第33.10節） |

### 33.3 用語

| 用語 | 意味 |
|---|---|
| 問い合わせ | お客様（見込みのお客様を含む）から届いた 1 つの用件。やり取りが続けば、同じ問い合わせに足していく |
| 経路 | 届いた入口。電話・メール・Web のフォーム・LINE・来店・そのほか |
| 窓口のアカウント | 会社の対外の窓口にする、Google Workspace の**専用のアカウント**（例: `info@会社のドメイン`）。人ではなく会社の窓口として、管理者が会社の接続に預ける（第33.6節） |
| 会話の履歴 | 1 つの問い合わせの中の、届いたものとこちらからの返事を時系列に並べたもの。経路をまたいでよい（メールで来て、電話で答えた、など） |
| どこで知ったか | お客様が会社を知ったきっかけ（検索・Web サイト・紹介・チラシ・看板・SNS・前からのお客様など）。**聞けたときだけ残す**。分からなければ「不明」にし、AI が推し量って埋めない |
| 次にやること | 担当・中身・期限。済んだら閉じる |
| 温度感 | 見込みの強さ（高い・ふつう・低い）。AI が話の中身から付け、人が直せる |

### 33.4 導入のときに会社が設定すること

| 項目 | 内容 | 既定 |
|---|---|---|
| 入り切り | 管理者ページの「拡張機能」 | 切り |
| 見られる人 | 利用範囲（第16.7節）。範囲の中の人は、問い合わせを**会社で共有**して見る | 会社で共有（三浦さんが選んだ） |
| 窓口のアカウント | 管理者が「拡張機能」の問い合わせの記録の設定で預ける（第33.6節・第33.18節）。Web のフォームの送り先・名刺・Web サイトの連絡先を、このアドレスにそろえることをヘルプで勧める | なし（預けるまで、メールは読まない） |
| LINE 公式アカウント | 管理者が「接続」で預ける（第33.6.2節） | なし |

**分類・言い換え・項目の表を会社に作らせない**（ADR-0028）。分類は AI が中身から付け、違っていれば画面か秘書で直す。

### 33.5 残し方

| 入口 | 動き |
|---|---|
| 秘書に話す・書く | 「いま田中さんから電話。来月の法人向けプランの見積もりがほしい。ホームページを見たって」と話す（音声でもよい。原則 u9）。AI が下の項目に分けて残し、「残しました。見積もりを金曜日までに、で合っていますか」のように一言で返す（確認を求めるのではなく、結果を伝える。違えばそのまま言い直せばよい） |
| 画面の 1 行の欄 | 「問い合わせの記録」の画面の上に、1 行の欄を置く。電話を受けながら書き、送ると同じように分ける。**項目ごとの入力の欄を並べない** |
| メール・Web のフォーム | 窓口のアカウントに届いたものを読む（第33.6節） |
| LINE | LINE 公式アカウントに届いたものを読む（第33.6.2節） |
| 続きのやり取り | 「田中さんに見積もりを送った」と話せば、同じ問い合わせに足し、次にやることを閉じる。どの問い合わせか 1 つに決まらなければ、候補を挙げて聞く |

**AI が分けて残す項目**

| 項目 | 規定 |
|---|---|
| 誰から | 名前・会社・電話・メール（分かるものだけ）。名刺管理の連絡先と同じ人ならつなぐ（第33.6.1節） |
| 経路 | 話の中身から決める（「電話で」「来店して」）。分からなければ「そのほか」 |
| 用件 | 1〜2 文の要約。話した文やメールの原文は、要約とは別に残す（第33.12節の期間） |
| 分類 | 見積もり・予約・質問・苦情・採用・営業の売り込み・そのほかなど。**AI が会社の扱う分野から付ける**。表は持たない |
| どこで知ったか | 話に出たときだけ。出なければ「不明」。**推し量って埋めない** |
| 次にやること | 担当（既定は受けた人）・中身・期限（「金曜日まで」は日付に直す）。無ければ空 |
| 温度感 | 高い・ふつう・低い |

**残さないもの**

| 残さないもの | 理由 |
|---|---|
| 健康の情報（症状・病名・服薬・障害など）、信条、犯罪の経歴などの**要配慮個人情報** | 本人の同意なしに取得してはならない情報（個人情報保護法）。話に出ても要約に入れず、「健康のことを話されていたため、記録には入れていません」と伝える。原文にも残さない（入口が秘書のときは、残す前に除く） |
| 患者さんとしての問い合わせ | M2 Medical の範囲（ADR-0063） |
| カードの番号・口座・パスワード | 問い合わせの記録に要らない。話に出ても除く |

### 33.6 窓口のアカウント（メールと Web のフォーム）

**会社の対外の窓口を、Google Workspace の専用のアカウント 1 つ（例: `info@会社のドメイン`）に寄せる**（第 0.228.0 版。三浦さんの指定。Q-171 決定）。
Web のフォームの送り先、名刺と Web サイトに載せるアドレス、取引の窓口のアドレスをこれにそろえ、届いたメールと返事をすべて会話の履歴にする。

**M2Office がつなぐ窓口は、会社ごとに指定した 1 本だけにする**（第 0.228.1 版。三浦さんの方針。お客様の会社の費用を、利用者のライセンス 1 つ分に抑えるため）。用途ごとのアドレス（contact@・sales@ など）が要る会社は、窓口のアカウントの**別名**か **Google グループ**で作る。どちらもライセンスが要らず、届いたメールは窓口のアカウントの受信箱に集まる。アカウントを増やす余裕のある会社が別のアカウントを作るのは妨げないが、M2Office が読むのは指定した 1 本だけである。

| 項目 | 規定 |
|---|---|
| アカウント | **専用のアカウント**（人が使うアカウントと同じく、Google Workspace の利用者のライセンスが 1 つ要る）。Google グループのアドレス（共同トレイ）そのものは、**API でメールを読めない**ため窓口にできない |
| 用途ごとのアドレス | 窓口のアカウントの**別名**（1 アカウントに 30 個まで。無料）か、宛先に窓口のアカウントを入れた **Google グループ**（無料）で作る。どちらも窓口のアカウントの受信箱に届くので、M2Office は 1 本を読むだけでよい。どのアドレスに届いたか（宛先）を会話の履歴に残し、月の振り返りで宛先ごとの数も出す。作り方はヘルプで示す |
| 預け方 | 管理者が、管理者ページの「拡張機能」の問い合わせの記録の設定で「つなぐ」を押し、**そのアカウントで Google にログインして許可を出す**（Gmail の読み取り・送信。第 0.232.0 版で、Gmail の下書きを使わないため下書きの権限を求めないことにした）。会社の接続として、リフレッシュ トークンを暗号化して預ける（第14.3.4節の保存と同じ）。人の接続ではないので、担当が辞めても止まらない |
| 不変則 I-9 との関係 | 窓口のアカウントは人ではなく会社の窓口であり、そのメールは利用範囲（第16.7節）の中で**会社で共有するもの**と、管理者が決めて預ける。**読むのは問い合わせの記録の業務だけ**で、秘書がほかの用（調べもの・ブリーフなど）に読まない。預けた・外したことは監査ログに残す |
| 読むもの | 窓口のアカウントの受信トレイと**送信済み**。届いたメールと、こちらからの返事（M2Office から送ったものも、Gmail で直接送ったものも）の両方を、会話の履歴にする |
| 問い合わせにしないもの | 営業の売り込み・メールマガジン・自動の知らせ（請求・配送・システムの通知）。**AI が見分ける**。会社に条件を作らせない。見分けた結果は一覧の「問い合わせでないもの」で見られ、間違いはそこで戻せる |
| まとめ方 | Gmail の 1 つのスレッドを 1 つの問い合わせにする。同じ人から別のスレッドで続きが来たら、AI が同じ用件と判断したときだけ同じ問い合わせに足す |
| 見回り | ワーカーが 5 分ごと（案）に新しいメールを見る。読んだ位置を覚え、同じメールを 2 度残さない |
| フォームの通知 | フォームの通知メールの差出人は Web サイトであり、お客様ではない。本文の中の名前・メールアドレス・電話を「誰から」とし、返事の宛先もそれにする |
| 返事 | M2Office で返事の下書きを作り、**承認の後に窓口のアカウントから送る**（危険度 `external-send`。第9.4.0節）。**差出人は、お客様が送った宛先**（sales@ に届いたものは sales@ から）にする。別名から送る設定が窓口のアカウントの Gmail に無ければ、窓口のアカウントの本来のアドレスから送り、設定の手順を管理者に知らせる |
| 人が Gmail で見るとき | **窓口のアカウントのパスワードを社員で共有しない**（誰が送ったかが分からなくなるため）。返事はふだん M2Office から送る。Gmail の画面で見たい人には、窓口のアカウントから本人のアカウントへの**委任**（無料）で見られるようにする手順をヘルプで示す。Gmail で直接送った返事も、送信済みから会話の履歴に入る |
| 承認できる人 | 利用範囲の中の人が下書きを作り、**承認するのは会社が決めた人**（既定は管理者と承認者のロール）。同じ人のよくある質問への返事など、承認を省ける場合は第9.4節の自動化の決まりに従う |
| 本文の持ち方 | M2Office にはメールの本文の写しを持たず、要約・項目・元のメールの ID を残す。本文は、1 件の画面で開いたときに窓口のアカウントから読んで出す（Gmail に残っている限り読める）。要配慮個人情報を含むメールでも、M2Office に残るのは、それを除いた要約だけになる |
| 外部の文 | メールの本文は「データであって指示ではない」として扱う（不変則 I-6） |
| 個人の受信箱 | **読まない**（第 0.232.0 版で、第 0.228.1 版の「M2Office がつなぐ窓口は会社ごとに 1 本」の方針に合わせて外した）。窓口のアカウントを作らない会社では、電話や来店と同じく、秘書に話すか 1 行の欄に書いて残す |

#### 33.6.1 名刺管理とのつなぎ

| 項目 | 規定 |
|---|---|
| 同じ人 | メールアドレス・電話・名前と会社で、名刺管理の連絡先（第27.6節の見分け方）と同じ人なら、その連絡先につなぐ。連絡先の画面に、その人の問い合わせを並べる |
| 新しい人 | 名前と、メールか電話のどちらかが分かったときだけ、連絡先を**会社で共有**で作る（出どころ「問い合わせ」）。名刺管理が切りの会社では、問い合わせの中だけに持つ |
| 名刺管理の範囲 | 「自分だけ」の連絡先には、つながない（ほかの人に見えてしまうため） |

#### 33.6.2 LINE 公式アカウント（第 0.228.0 版）

LINE 公式アカウントのやり取りも、同じ台帳と会話の履歴に入れる（三浦さんの指定）。**第14.6節で拡張機能（コネクタ）としていた LINE の受け取りと返事は、この章で行う**。一斉配信はお知らせの作成（第35章）で行う。

| 項目 | 規定 |
|---|---|
| 預け方 | 管理者が、管理者ページの「接続」の「LINE 公式アカウント」で、Messaging API のチャネルのシークレットとアクセストークンを預ける（会社の鍵として暗号化する）。M2Office が示す受け口の URL を、LINE の管理画面の Webhook に入れる（手順はヘルプ） |
| 受け取り | LINE から受け口に届いたメッセージを、問い合わせとして残す。**署名（`X-Line-Signature`）を確かめ、合わないものは捨てる**。受け口は会社ごとの URL にし、どの会社のものかを URL だけで決めない（署名をその会社のシークレットで確かめる） |
| まとめ方 | 相手（LINE の利用者）ごとに、最後のやり取りから 30 日（案）以内なら同じ問い合わせに足す。過ぎたら新しい問い合わせにする |
| 誰から | LINE の表示名だけが分かる。会話に名前・電話・メールが出たら、名刺管理の連絡先とつなぐ（第33.6.1節） |
| 画像・スタンプ | 文だけを残す。画像は「画像が届きました」と残し、LINE の画面で見る（案） |
| 返事 | 返事の下書きを作り、**承認の後に送る**（危険度 `external-send`）。LINE の無料で送れる数を超えると費用がかかるため、送る前に今月の残りの数を示す（第14.6.4節） |
| 自動の返事 | しない。営業時間の案内などの決まった返事は、LINE の管理画面の応答メッセージで行う。よくある質問への自動の答えは後で検討する |
| 一斉配信 | この章では扱わない。友だち全員へのお知らせは、お知らせの作成（第35.6.2節）で行い、この接続を使う |
| ローカルの形 | 社外から届く受け口を開けられないため、ローカルの形（第8.6節）の会社では使えない（Q-176。第 0.229.1 版で決定。要望があれば中継の口を別に検討する） |
| 同意 | 友だちに登録した人からのメッセージだけが届く。登録していない人に送らない（第14.6.4節） |

### 33.7 取りこぼさない

| 項目 | 規定 |
|---|---|
| 知らせ | 次にやることの期限の前の日（案）と、期限を過ぎたときに、担当に知らせる |
| 朝のブリーフ | 「今日が期限の問い合わせ」「返事を待たせている問い合わせ」を載せる |
| 手つかず | 次にやることが無く、3 営業日（案）動いていない問い合わせは、残した人に「閉じてよいか」ではなく「対応が済んだなら秘書に言ってください」と一度だけ知らせる |
| ToDo | Google の ToDo には入れない（M2Office の中で持つ。二重に持たない） |

### 33.8 画面

| 項目 | 規定 |
|---|---|
| 一覧 | 上に 1 行の欄。その下に、次にやることの期限が近い順、その後に新しい順で並べる。列は日時・誰から・経路・用件・次にやること・担当・状態 |
| 絞り込み | 「対応中」「すべて」と、経路・分類・担当。検索の欄 |
| 1 件 | **会話の履歴**を時系列に並べ（経路の印つき。メールの本文は開いたときに窓口のアカウントから読む）、次にやること・どこで知ったか・温度感を出す。項目はその場で直せる。下に「返事の下書き」（メール・LINE。承認の後に送る） |
| 問い合わせでないもの | 窓口のメールのうち、AI が問い合わせでないと見分けたものを、別の一覧で見られる。「問い合わせにする」で戻せる |
| 説明文 | 常に出さない（原則 u11） |
| 削除 | 1 件ずつ「削除」。会社の管理者は、人から求められたときにその人の問い合わせをまとめて削除できる（第33.12節） |

### 33.9 集客へのつなぎ

| 組織知識 | 答えた内容を、個人の情報を除いて組織知識の候補にする（第11.4節）。登録は人の判断（第11章の決まりのまま） |
| Web の振り返り | Web の振り返り（第34章）が入っていれば、月の便りで「Web から来た問い合わせ」と Web の数字を並べる（第34.9節） |

### 33.12 人の情報とデータの扱い

| 項目 | 規定 |
|---|---|
| 利用の目的 | お客様の問い合わせに答えるため、と、問い合わせの傾向を集計して自社の案内を良くするため。**広告の配信先に渡さない・ほかの会社に渡さない** |
| 見られる人 | 利用範囲の中の人（会社で共有）。範囲の外の人と、ほかの会社には見えない（不変則 I-2） |

| 本人から求められたとき | 管理者が、その人の問い合わせと、問い合わせから作った連絡先をまとめて削除できる。削除は監査ログに残す（中身は残さない） |

| 集計とテーマ案 | 月の振り返りの数と、よくある質問の話題には、個人を特定する情報を入れない。コラムの作成に渡すのは話題だけ |
| 窓口のアカウント | 預かったトークンは、問い合わせの記録の業務だけが使う。管理者が外せばすぐに読まなくなる |
| 監査ログ | 残した・直した・削除した・返事を送った（承認）・まとめて削除した・窓口のアカウントと LINE を預けた・外した |

### 33.15 行わないこと

| 行わないこと | 理由 |
|---|---|
| 承認なしに返事を送る | 社外への送信は承認が要る（第9.4.0節） |
| 「どこで知ったか」を推し量って埋める | 集客の判断を誤らせる。分からなければ「不明」と残す |
| 要配慮個人情報を残す | 本人の同意の無い取得になる |
| 患者さんの問い合わせを扱う | M2 Medical の範囲（ADR-0063） |
| お客様を広告の配信先として書き出す・ほかのサービスに渡す | 利用の目的の外。お客様の信頼を損なう |
| 電話を録音する・通話の中身を自動で聞き取る | 段 1〜3 では行わない。録音には相手への断りが要り、後の段でつなぐサービス（Q-172）の側で行う |
| 会社に分類や項目の表を作らせる | AI が中身から決める（ADR-0028） |
| 窓口のアカウントのメールを、問い合わせの記録のほかの用に読む | 会社で共有すると決めたのは、問い合わせのため。秘書の調べものやブリーフには使わない |
| LINE で一斉配信・自動の返事をする | 一斉配信は第14.6節で別に扱う。自動の返事は後で検討する |

### 33.17 段 1 の実装の決まり（第 0.230.0 版）

2026-10-03 に三浦さんが「問い合わせの記録の段 1 を実装してください」と依頼した。段 1（第33.14節）を、次の決まりで実装した。

| 項目 | 規定 |
|---|---|
| 形 | 内蔵の拡張「問い合わせの記録」（ID `inquiries`。既定は切り）。会社の設定の区分 `inquiries`（入り切りだけ）。移行 065（`inquiries`・`inquiry_events`・`inquiry_tasks`。行単位の制限つき）・066（次にやることが生まれた履歴） |

| 続き | 推論が対応中の問い合わせ（30 件まで）から選ぶ。**推論が選んでも、同じ人とはっきり分かる（名前・会社・電話・メールのどれかが同じ）ときだけ続きにする**（第 0.231.0 版。2026-10-03 に三浦さんが、名前の無い別の電話が、名前の無い前の問い合わせに続きとして入り、次にやることと誰からが書き足されたと指摘）。選べなければ、名前・会社で探し、**名前がそのまま同じものが 1 つならそれ**、ほかに似た名前がいくつもあれば候補を返して選んでもらう（画面は候補ごとに「この問い合わせに足す」）。お客様からまた届いたら対応中に戻す。「送った」などの報告なら、いちばん期限の近い次にやることを済みにする |
| 分ける | 続きとして入ったのが別の用件なら、1 件の画面の会話の履歴の「別の問い合わせに分ける」で、その履歴を新しい問い合わせにする（第 0.231.0 版）。原文が残っていれば読み直して誰から・経路などを作り、その履歴から生まれた次にやることも移す（移行 066 で、次にやることに生まれた履歴を持たせた。それより前の行は移らない）。最初の履歴は分けない |
| 名刺管理 | 名刺管理を使っている人なら、会社で共有の連絡先から、メールアドレス・電話番号（数字 9 桁以上で一致）・氏名と会社名（1 件だけ一致）で同じ人を探してつなぐ。見つからず、名前とメールか電話が分かれば、会社で共有の連絡先を作る（メモ「出どころ: 問い合わせの記録」）。名刺の詳細に「問い合わせ」を並べる |
| 推論 | 会社の推論（会社の AI の方針に従う。ローカルを既定の会社ではローカル AI） |
| 画面 | 左のメニューの「問い合わせの記録」。上に 1 行の欄と「残す」（結果はボタンの下に出す）。「対応中」「すべて」と検索。一覧は対応中を先に、次にやることの期限の近い順。**秘書が問い合わせを残し終えたら、開いている一覧と 1 件の画面を読み直す**。一覧と 1 件の画面に「更新」を置く（第 0.231.0 版。ページを読み直すと秘書との会話が切れるため。三浦さんの依頼）。1 件の画面は、項目をその場で直し（入力の欄を離れると保存）、次にやることを足して期限を変え「済み」にし、会話の履歴（書いた文は畳む）と「続きを足す」、名刺を開く、削除 |
| 削除 | 1 件ずつ。**残した本人と管理者だけ**（会社で共有のため、ほかの人の記録を消させない） |
| 知らせ | ワーカーが 15 分ごと（`INQUIRY_INTERVAL_MS`）に、次にやることの期限の前の日と期限を過ぎたときに担当へ 1 回ずつ、次にやることが無く 3 営業日（土日を除く。祝日は数える）動いていない問い合わせを残した人へ 1 回だけ知らせる。題は「明日が期限の問い合わせ: 田中さん」の形で、**用件の中身は入れない**。止めた人・利用範囲の外の人・個人設定の通知で「問い合わせ」を切った人には送らない。お知らせから開くと問い合わせの記録の一覧 |
| 原文 | 秘書に話した文・書いた文の原文は、見回りで 90 日を過ぎたものを消す（要約と項目は残す） |
| 秘書から聞く | 付属の業務「問い合わせを調べる」（ツール `inquiries.list`。危険度 `read`。対応中・最近何日・人や会社の言葉・次にやることが残っているもの）。結果はお客様の言葉なのでデータとして扱う（`untrusted`） |
| 会社の自動化ポリシー | 社内への書き込みに確認を求める会社（第9.4節）では、秘書から頼んだ記録は本人の確認の後に残る |

### 33.18 段 2 の実装の決まり（第 0.232.0 版）

2026-10-03 に三浦さんが「問い合わせの記録の段 2 を実装してください」と依頼した。段 2（第33.14節）を、次の決まりで実装した。個人の受信箱から拾う形は、第 0.228.1 版の「M2Office がつなぐ窓口は会社ごとに 1 本」の方針に合わせて外した（第33.6節）。

| 項目 | 規定 |
|---|---|
| つなぐ | 管理者が「拡張機能」の問い合わせの記録の設定で「つなぐ」を押す。Google の認可の画面で**アカウントを選ばせ**（本人ではなく窓口のアカウントを選ぶため）、Gmail の読み取り（`gmail.readonly`）と送信（`gmail.send`）を求める。両方が許されていなければ預けない。**会社の利用者と同じドメインのアカウントだけ**を預ける（個人の Gmail などを窓口にしない）。リフレッシュ トークンは会社の鍵の置き場に暗号化して預け、アドレスとつないだ人を会社の設定に置く。外すと Google の許可も取り消す。つなぐ・外すは監査ログに残す |
| 窓口の担当 | つないだ管理者を**窓口の担当**とし、メールから生まれた次にやること（ふつうは「返事をする」）の担当と、手つかずの知らせの相手にする |
| 読む | ワーカーが 5 分ごと（`INQUIRY_MAIL_INTERVAL_MS`）に、受信トレイと送信済みの新しいメールを読む（はじめは 3 日さかのぼる。読んだ位置から 10 分重ねて読み、見たメールの ID で 2 度読まない）。画面の「更新」でもすぐ読む（会社ごとに 30 秒に 1 回まで） |
| 見分け | 推論（高速）に、問い合わせか・Web のフォームの通知か・誰から・分類・用件・どこで知ったか・温度感・次にやることを JSON で答えさせる。メールマガジンの見出し（`List-Unsubscribe`・`Precedence: bulk`・`Auto-Submitted`）があるものは、推論が問い合わせとしても問い合わせにしない。推論が使えなければ決まった言葉で見分ける（送り元の無い自動の知らせ・営業の言葉・請求や配送の知らせ） |
| まとめ方 | 同じスレッドのメールは同じ問い合わせに足す。新しいスレッドでも、**メールアドレスが同じ**対応中の問い合わせがあれば足す（名前だけでは足さない）。お客様からまた届いたら対応中に戻し、次にやることが無ければ「返事をする」を足す |
| 送信済み | 問い合わせのスレッドの送信済み（Gmail で直接送った返事を含む）は「こちらから」として足し、「返事をする」などの次にやることを済みにする。問い合わせのスレッドでない送信は扱わない |
| 宛先（別名） | お客様が送った宛先のうち、窓口のアカウントの送信元に使えるアドレス（別名）を「届いた宛先」として残す。無ければ会社のドメインの宛先、無ければ窓口のアドレス |
| 本文 | メールの本文は写さない。1 件の画面の「メールを開く」で、そのときに窓口のアカウントから読む |
| 問い合わせでないもの | 一覧の「問い合わせでないもの」に、差出人・件名・見分けた理由を並べ、「問い合わせにする」で戻せる |

### 33.19 段 3 の実装の決まり（第 0.234.0 版）

2026-10-03 に三浦さんが「問い合わせの記録の段 3 の実装をお願いします」と依頼した。段 3（第33.14節）のうち、LINE 公式アカウントとよくある質問を、次の決まりで実装した。

| 項目 | 規定 |
|---|---|
| つなぐ場所 | 管理者が「拡張機能」の問い合わせの記録の設定で、チャネルのシークレットとアクセストークン（長期）を入れて「つなぐ」を押す（第33.6.2節の「接続」ではなく、窓口のアカウントと同じ場所にまとめた）。M2Office は公式アカウントの情報を引いて鍵を確かめてから預ける。**受け口の URL は、つないだときに 1 度だけ出す**。管理者はそれを LINE の管理画面の Webhook に入れる。つなぎ直すと URL も変わる。外すと受け口も止まる（問い合わせは消さない）。つなぐ・外すは監査ログに残す |
| 受け口 | `POST /v1/hooks/line/:key`（ログインの無い口。会社の判定より前）。URL の鍵（ランダムな 24 バイト）のハッシュから会社を引き、**その会社のシークレットで署名を確かめる**。知らない鍵・問い合わせの記録か LINE を切っている会社は 404、署名が違えば 401。確かめたらすぐに 200 を返し、取り込みは後ろで行う（LINE は応答の遅い受け口に送り直すため）。本文は 1 MB まで |
| 取り込み | 1 対 1 のトーク（`source.type = user`）のメッセージだけを扱う。グループ・複数人のトークは扱わない。出来事の ID で 2 度残さない。同じ相手の続けて届いたメッセージは会社ごとに順に処理する（2 通目が別の問い合わせにならないように）。友だちの追加・ブロックは相手の記録にだけ残す |
| まとめ方 | 相手ごとに、最後のやり取りから 30 日以内なら同じ問い合わせに足す（対応中に戻し、次にやることが無ければ足す）。過ぎたら新しい問い合わせにする |
| 読み方 | 推論（高速）に分類・用件・温度感・次にやること（ふつうは「返事をする」）を答えさせる。使えなければ決まった言葉で読む。誰からは LINE の表示名。**健康などの要配慮個人情報が書かれていれば本文を残さない**（用件にも入れない）。画像・スタンプは「届きました」とだけ残す |
| 担当 | LINE をつないだ管理者を、LINE から生まれた次にやることの担当にする |
| 返事 | LINE から来た問い合わせの「返事の下書き」は LINE で返す形にする（宛先はその相手で変えられない。差出人は公式アカウント。件名なし。短く、絵文字を使わない）。送り方は段 2 と同じで、承認の画面に**相手の表示名と今月の残りの通数**を出し、承認した中身が同じときだけプッシュのメッセージで送る。残りが 0 のときは送らない |
| よくある質問 | 一覧の「振り返り」に、最近 90 日の問い合わせから何度も聞かれた話題（2 件以上。5 つまで）を出す。推論が使えなければ分類で数える。**誰が聞いたかは入れない**。コラムの作成を使える人には「コラムにする」を出し、話題をテーマにしてコラムを書き始める。秘書に「よく聞かれる質問は？」と聞いても答える（ツール `inquiries.faq`、危険度 `read`） |
| 開発の環境 | 見本の会社では鍵を確かめず、見本の口（表示名は「LINE の見本」、今月の上限は 200 通）を使う。送ったものはプロセスの記憶に置くだけで、外には何も送らない |
| ローカルの形 | 使えない（社外から届く受け口が要るため。Q-176） |
| 付属の業務 | 「問い合わせを調べる」がよくある質問も答える。拡張の版 1.2.0 |
| API | `PUT`／`DELETE /v1/admin/extensions/inquiries/line`、`POST /v1/hooks/line/:key`、`GET /v1/inquiries/faq` |

**段 3 で行っていないこと**（後で行う）: 本物の LINE 公式アカウントでの確かめ（開発の環境は見本の口と、署名を付けた受け口の呼び出しで確かめた）、組織知識の候補（候補を確かめる流れがまだ無い）、Web の振り返りとの突き合わせ（第34章が未実装）、LINE の会話に出た名前・電話・メールから名刺管理の連絡先につなぐこと。
