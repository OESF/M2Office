## 25. リスク

| ID | リスク | 影響 | 対策 |
|---|---|---|---|
| R-01 | 生成内容の誤りによる業務事故 | 高 | 承認ゲート、根拠提示、影響の大きい操作の制限 |
| R-02 | 顧客データの漏洩 | 高 | テナント分離（RLS）、暗号化、最小権限、監査 |
| R-03 | 個人記憶の意図しない共有 | 高 | 秘書がほかの人にも役立つものだけを選んで会社の知識にし（第11.3節）、本人は記憶を確認・削除でき、管理者は秘書が加えた知識を消せる |
| R-04 | プロンプトインジェクション | 高 | 外部データを命令として扱わない。危険度による承認強制 |
| R-05 | 音声誤認識による誤送信 | 高 | 音声でも承認ゲートを省略しない（I-11）、認識結果の画面表示 |
| R-06 | Google API の制限付きスコープ対応の遅延 | 高 | 一般公開の前に CASA が要ると判明（第14.3.1節）。制限付きの権限を Gmail に限り、CASA に備えた作り（第14.3.2節）にしておく。公開の時期から逆算して評価機関の選定・見積もりを始める |
| R-07 | Google プラットフォームへの依存 | 中 | ツール層を非依存インターフェースに保つ。LLM は抽象化層で差し替え可能 |
| R-08 | 秘書の応答が遅く使われなくなる | 高 | 照会系は LLM を介さない経路を用意。3 秒以内を必達要件とする |
| R-09 | 組織知識が空で価値を感じられない | 高 | 導入時の知識初期投入を標準手順とする（第22.2節） |
| R-10 | 第三者拡張による品質・信頼の毀損 | 高 | 第三者コードを実行しない設計、権限宣言と同意、審査、区分の明示 |
| R-11 | API 化を後回しにして作り直しが発生 | 高 | Phase 1 から API 優先で設計する（第24.2節） |
| R-12 | 拡張機能が集まらずエコシステムが成立しない | 高 | まず公式と秘書で製品を成立させる。士業・業界団体との連携を先行 |
| R-13 | Google アカウントの乗っ取りに起因する事故 | 中 | Workspace 側で 2 段階認証を必須にすることを導入時に確認（第16.1節）、ログイン中の端末の個別ログアウト（第6.5.8節）、緊急停止（第23.8.6節） |
| R-14 | 推論コストの想定超過 | 中 | モデルの使い分け、上限制御、照会系の LLM 回避 |
| R-15 | 制度改正への追随漏れ | 中 | 制度要件をエージェント定義から分離し共通ルール化（第15.1節） |
| R-16 | 士業の独占業務への抵触 | 高 | 業務範囲の境界を明示（15.4）、拡張機能の審査でも確認。契約書チェックは論点の提示にとどめ、表示と規約を弁護士に確認する（第28.2節、Q-97） |
| R-17 | 現場に定着しない | 高 | 30 分以内の初回実行、既定値で動く設計、効果の可視化 |
| R-18 | 大手 SaaS ベンダーの参入 | 中 | 日本の制度対応、蓄積された組織知識、エコシステムを参入障壁とする |
| R-19 | テナント分離の実装不備による情報漏洩 | 高 | RLS を基盤で強制。接続プールはトランザクション単位で設定。テナント越えの失敗を自動テストで常時検証（第8.5.5節） |
| R-20 | AI の価格改定で採算が崩れる | 中 | クレジット換算レートを設定値として持ち、価格表を変えずに吸収する（第21.2節） |
| R-21 | Google 連携の認可で離脱する | 高 | 連携ウィザードを常設の仕組みとして提供する（第22.2節） |
| R-22 | 請求漏れ・二重請求 | 中 | 利用実績の集計を自動化し、締め処理を冪等にする。差異は人が確認する（第23.4節） |
| R-23 | 運営による顧客データの不適切な閲覧 | 高 | 原則禁止。例外は顧客同意・期限付き・全記録・事後通知（第23.6節） |
| R-24 | 誤った利用停止による顧客業務の中断 | 高 | 停止処理は人の承認を必須とし、停止後も閲覧とエクスポートは残す（第23.3節） |
| R-25 | 会話ログの学習利用が顧客の不信を招く | 高 | 学習の範囲を A・B・C に分け、テナントを越える利用は個別同意に限る。規約に具体的に記載する（第11.9.3節） |
| R-26 | Google アカウント障害時にログインできない | 中 | 受け入れる前提とする。管理者を 2 名以上登録し、障害時の連絡手段を定める（第16.1節） |
| R-27 | 音声が Gemini に依存し乗り換えできない | 中 | 非対称性を許容する。テキスト側の抽象化は妥協しない（第10.5.4節） |
| R-28 | 選んだ事業者で必要なマネージドサービスが揃わず運用負荷が増す | 中 | 利用サービスを早期に確認する（Q-38）。データベースの運用体制を決めてから Phase 1 に入る |
| R-29 | Gemini API の仕様変更に追随できない | 中 | 抽象化層で吸収する。音声部分は影響を受けるため変更情報を継続的に確認する |
| R-30 | OKF の後方互換のない改版で入出力が壊れる | 低 | 内部表現を OKF に合わせず、変換層で吸収する（第11.10.3節） |
| R-31 | LINE の一斉配信の誤送信 | 高 | `external-send` として承認必須。配信対象・件数・概算費用を提示してから実行する（第14.6.4節） |
| R-32 | 権限区画のデータが記憶・知識へ流出する | 高 | 不変則 I-12。区画の属性を Phase 1 から持たせ、検索・記憶・昇華の各経路で絞り込む（第16.3.5節） |
| R-33 | 区画の存在自体から機微情報が推測される | 中 | 区画外の利用者には「権限がない」ではなく、存在を示さない応答とする（第16.3.5節） |
