## 6. ユーザー体験（UI/UX）

### 6.1 ワークスペースの画面構造

従業員の主作業画面は、左・中央・右の 3 領域と、常駐する秘書バーで構成する。

```
┌──────────────┬────────────────────────────────┬───────────────────┐
│ 左ペイン     │ 中央: キャンバス               │ 右: 秘書のキャンバス │
│              │                                │ （いちばん新しい    │
│ 業務         │  ・業務の入力                  │   結果を 1 つ出す。 │
│ □ メール整理 │  ・実行の詳細（結果・根拠）    │   折りたたむ）      │
│ □ 議事録     │  ・承認トレイ                  │                     │
│ □ 規程Q&A    │  ・実行履歴・お知らせ          │  ご依頼: 会議費の…  │
│ ほかの業務(7)│  ・定時実行・ヘルプ            │  5,000 円です       │
│ ──────       │                                │  （出典…）          │
│ 自分の状況   │                                │ ←─ 開く／たたむ     │
│ 承認トレイ(3)│                                │                     │
│ 実行履歴 …   │                                │                     │
├──────────────┴────────────────────────────────┴───────────────────┤
│ 秘書バー  「何かお手伝いしましょうか」      [音声入力] [テキスト] │
└───────────────────────────────────────────────────────────────────┘
```

左ペインの最下部には、**利用者の情報と個人設定への入口**を置く。
一般的な業務アプリと同じく、**名前と属性（ロール）を並べ、右端の歯車のボタンで個人設定を開く**。

```
│ 業務                     │
│  ・メール整理            │
│  ・議事録                │
│ ──────                   │
│ 自分の状況               │
│  承認トレイ (3)          │
│  実行履歴                │
│                          │
│ （下部に固定）           │
│ ［顔］ 山田 太郎 ［歯車］│
│        管理者            │
```

| 領域 | 役割 | 振る舞い |
|---|---|---|
| 左ペイン | 利用できる業務への入口 | 有効なエージェントのみ表示。折りたためる。**画面の下端まで伸ばす**。業務の名前と押すキー（第6.11節）が並ぶため、**名前を切らない幅を取る** |
| 左ペイン下部 | 利用者の情報と個人設定への入口 | 常に見える位置に固定する。名前・属性（管理者・承認者・一般）・歯車のボタン |
| キャンバス | 主作業領域 | 1 つの作業に集中する（タブで並べることはしない） |
| 秘書のキャンバス | **秘書が結果を見せる場所** | 折りたたんでおき、結果を出したら開く。いちばん新しい結果だけを出し、会話の履歴は並べない（第6.2節） |
| 秘書バー | 常駐の窓口 | どの画面でも表示。音声・テキストの両方で呼び出せる。**左ペインの右側（キャンバスと秘書のキャンバスの下）に置く**。音声で話している間は、直近の 1 往復を字幕で出す（第6.2.0節） |

**上の帯**には、左から「M2Office」（会社のロゴがあればロゴ）と版（第6.1.1.1節）、会社名、見本のデータで動いているときの「予定・メールはダミー」の印、
Google のアプリの一覧（第6.1.1.2節）、管理者ページへの入口（管理者だけ）、明るさの切り替え、利用者の名前、ログアウトを置く。
管理者ページの上の帯には「ワークスペースへ戻る」を置く。

**文字の大きさ**は、ブラウザの表示の倍率が 100% のときに読みやすい大きさにする。画面の文字の大きさ・行間・余白は 1 か所の倍率（`--font-scale`・`--line-scale`・`--space-scale`）で持つ。**第 0.136.2 版で、文字は 0.875（16px を 14px、12px を 10.5px）、行間は 0.9（既定の 1.5 を 1.35）にし、第 0.136.3 版で余白（padding・margin・gap）も 0.9 にした**（2026-09-27、三浦さんの指定）。高さの決まった枠の中の行間（px で指定したもの）と 1px の線の余白は変えない。眺めるための画面（第6.7.2.1節）は、別の倍率で決める。

#### 6.1.1 左ペインの表示

業務が増えても左ペインを見渡せるよう、**項目は名前とアイコンだけ**にし、説明は必要なときに出す。
管理者ページの左ペインも同じ決まりに従う。

| 項目 | 規定 |
|---|---|
| アイコン | 各項目の頭に**モノクロのアイコン**を付ける。アイコンは 1 つの SVG ファイルにまとめ、文字の色を引き継ぐ（ダークでも自動で見やすい色になる） |
| 業務のアイコン | 業務の分類（`category`）から決める。分類に対応が無ければ共通のアイコン |
| 説明 | 業務の説明（`description`）は項目に並べず、**マウスを重ねたときに出す**（画面の読み上げにも名前と説明を渡す） |
| 折りたたみ | 左ペインを狭くすると**アイコンだけ**が並び、広げると名前も見える。折りたたんだときは、マウスを重ねると名前と説明が出る |
| 件数 | 承認待ち・未読の件数は、折りたたんだときもアイコンの右上に小さく示す |
| **業務の並び**（第 0.128.0 版、第 0.129.0 版でピン止めに改めた。第 0.166.0 版でカテゴリーを加えた） | **本人がピン止めした業務だけを上に出し、ほかは本人が作ったカテゴリーごとにたたみ、どのカテゴリーにも入れていない業務は最後の「ほかの業務（件数）」にたたむ。** 業務は増え続けるため、全部を並べると見渡せない（2026-09-26 に三浦さんが依頼。この時点で 16 ほど。2026-09-29 に、増えた業務をまとめて見られるようカテゴリーを依頼） |
| 並びの順 | ① ピン止めした業務 → ② カテゴリー（作った順。1 つずつたためる見出し） → ③ 「ほかの業務」（カテゴリーに入れていない業務）。中身の無いカテゴリーは左ペインに出さない |
| 項目の操作 | 項目にマウスを重ねると、右端に**縦の三点（︙）のボタン**が出る。押すと、その業務の操作の一覧を出す。上から「ピン止めする」か「ピン止めを外す」（いまの状態に合わせてどちらか一方）、作ったカテゴリーの一覧（いま入っているものに印）、「カテゴリーに入れない」、「カテゴリーを作る」。外を押すか Esc で閉じる。ピン止めした項目に印は出さない（上に並んでいることで分かるため。三浦さんの判断） |
| ピン止め | ピン止めすると、カテゴリーに入っていても上に出る（**ピン止めが優先**）。外すと、入っているカテゴリーに戻る（入っていなければ「ほかの業務」） |
| カテゴリー（第 0.166.0 版） | 業務をまとめる、**本人だけの見出し**（「ブリーフ」「経理」など）。1 つの業務は 1 つのカテゴリーにだけ入る。「カテゴリーを作る」で名前を入れると作り、その業務をそこに入れる。作ったカテゴリーは、中身が無くても操作の一覧に常に出す。名前は 20 字まで、1 人 20 個まで。**利用者のグループ（部署など。第16.7.3節）とは別のもの**で、使える業務は変わらない（混同を避けるため、画面では「グループ」と呼ばない） |
| カテゴリーの見出し | 見出しにマウスを重ねると、右端に縦の三点のボタンが出る。押すと「名前を変える」「カテゴリーを消す」。消すと、中の業務は「カテゴリーに入れない」に戻る（業務は消えない） |
| 自動で変えない | **使った回数で並びや表示を変えない。** 使う回数は少なくても常に見ておきたい業務があるため、ピン止めは本人だけが変える（三浦さんの判断。第 0.128.0 版の利用回数で決める形はやめた） |
| はじめの状態 | まだ一度もピン止めを変えていない人は、標準の組（議事録作成・メール整理・社内ナレッジ Q&A・日程調整・スライド作成・文書の作成・名刺管理）がピン止めされている（名刺管理は第 0.147.0 版で加えた） |
| ピン止めとカテゴリーの中の並び | メニューの順（第6.5.6節）のまま |
| 覚える場所 | ピン止めとカテゴリーは個人設定（メニュー）。端末をまたいで同じになる |
| たたみ方 | カテゴリーと「ほかの業務」は、見出しを押すと開き、もう一度押すとたたむ。はじめはたたんでいる。開いたかどうかは見出しごと・端末ごとに覚える。**いま開いている業務がたたんだ中にあれば開いておく** |
| 押すキー | 1〜9 は見えている順に割り当てる（たたんだ中の業務には割り当てない） |
| 画面を持つ内蔵の拡張（第 0.147.0 版） | **名刺管理（第27章）と在庫管理（第29章。第 0.149.0 版）も業務の 1 つとして「業務」の並びに置く（項目の名前は「名刺管理」。第 0.147.2 版）。** ピン止め・「ほかの業務」へのたたみ・メニューの並びと表示（第6.5.6節）・押すキーは、ほかの業務と同じ。押すと名刺の画面を開く。「自分の状況」には置かない（自分宛てのものや自分の依頼の状況を並べる見出しのため。三浦さんの指摘） |
| 利用者のカード | 最下部に固定する。名前と属性（ロールのうち最も強いもの）を示し、右端の歯車のボタンで個人設定を開く。折りたたんだときは歯車のボタンだけを示す |
| 覚えておく | 折りたたんだかどうかは、端末（ブラウザ）ごとに覚えておく |
| 狭い画面 | 第6.9節のとおり、上部の横並びに変える（折りたたみは使わない） |

##### 6.1.1.1 版の表示（第 0.104.0 版）

**いま使っている M2Office の版が、いつでもすぐ分かるようにする。** 機能が増え、版が上がっていくと、
「いまの画面はどの版か」「更新は届いているか」を確かめたくなる（2026-09-25 に三浦さんが依頼）。

| 項目 | 規定 |
|---|---|
| 置き場所 | 画面の上の帯の「M2Office」の右に**小さく常に出す**（例: `M2Office v0.5.0`）。ワークスペースも管理者ページも同じ |
| 押したとき | 「このアプリについて」を開く。**画面の版とサーバーの版**、更新情報（ヘルプの「更新情報」）への入口を出す |
| 版の食い違い | 画面の版とサーバーの版が違えば、**「新しい版があります。再読み込みしてください」**と出し、再読み込みのボタンを置く（開いたままのタブが古い版の画面のままになるため） |
| 版の出どころ | 画面は**ビルドのときに埋め込む**（ルートの `package.json` の版）。サーバーは起動のときに読む。リリースのあとは画面を作り直し、埋め込まれた版を確かめる（リリース規定） |

##### 6.1.1.2 Google のサービスへのリンク（第 0.104.0 版）

**M2Office から、連携している Google のサービスをすぐ開けるようにする。** 連携先の実物（メール・予定・ToDo・Chat）を
見に行くことは多い。管理者も利用者も同じである（2026-09-25 に三浦さんが依頼）。

| 項目 | 規定 |
|---|---|
| 形 | **Google のアプリの一覧と同じ形**にする（三浦さんが Gmail の画面の、右上の格子のボタンのメニューを示して依頼）。画面の上の帯の右側に格子のボタンを置き、押すとサービスが**格子状に**並ぶ |
| 置き場所 | ワークスペースの上の帯（管理者ページには置かない。管理者もワークスペースから開く） |
| 並べるもの | M2Office が連携する（または連携する予定の）サービス: Gmail・カレンダー・ToDo・Chat・ドライブ・ドキュメント・スプレッドシート・スライド・Meet・フォーム。**管理者には Google の管理コンソール**も並べる |
| アイコン | **M2Office のモノクロの線画**を使う（第6.1.1節）。Google の色付きのアイコンは商標で、使うにはブランドの決まりに従う必要があるため、確かめるまで使わない |
| 開き方 | **新しいタブで開く**。M2Office の画面は残す。外の画面へ開くことを、メニューの見出しで示す |
| 閉じ方 | 外を押す・`Esc`（第6.11.1節） |
| アカウント | 本人の Google アカウント（ログインに使ったメールアドレス）を指定して開く。ブラウザで複数の Google アカウントを使っていても、仕事のアカウントで開くようにするため |
| 出す条件 | **会社が Google につないでいるとき**（値の出どころが `google`）だけ出す。見本のデータで動いている会社では出さない（見本の中身と、開いた先の本物が食い違うため） |
| 送るもの | **何も送らない。** 開くのは各サービスのトップページで、M2Office のデータを URL に載せない |

#### 6.1.2 画面の明るさ（ライト・ダーク）

| 項目 | 規定 |
|---|---|
| 選べるもの | **ライト**・**ダーク**・**端末の設定に合わせる**（既定） |
| 切り替える場所 | 上部のボタン（押すたびにライトとダークを切り替える）と、個人設定の「表示」 |
| 覚えておく | 端末（ブラウザ）ごとに覚えておく。ほかの端末の表示は変えない |
| 色の持ち方 | 画面の色はすべて名前の付いた色（トークン）で持ち、ライトとダークの 2 組を用意する。画面ごとに色を直書きしない |
| 読みやすさ | 本文の文字と背景の明るさの差は、どちらの組でも十分に取る（目安: WCAG の AA、4.5:1 以上） |

**根拠を示す場所の設計意図**: 原則 p3「説明可能」を画面で実装する。
「なぜこの金額になったのか」「どの文書を参照したのか」を、
作業の流れを中断せずに確認できることが、AI への信頼（懸念の 50.4% が正確性）を支える。
**秘書の答えの根拠はその応答に添え、業務の実行の根拠は実行の詳細の画面に置く**（第6.2節）。

#### 6.1.3 秘書バーの作り

秘書バーは**どの画面にも常に出ている**。狭い帯の中に、呼びかけと入力と応答を
すべて詰め込むと、どれも使えなくなる。**役割ごとに置き場所を分ける。**

| 置き場所 | 何を置くか |
|---|---|
| 秘書バー（帯） | **呼びかけの口だけ**。アバター・入力欄・操作のボタン・状態の知らせ |
| 秘書のキャンバス（右） | **秘書の結果**。いちばん新しい答えと、その根拠（第6.2節）。聞こえた内容と秘書の言葉は秘書バーの字幕 |

**やり取りの中身を帯の中に出さない。** 会話が続くほど帯が膨らみ、入力欄が潰れる。

##### 帯の高さは変わらない

**音声での対話は製品の要である。** 帯は狭く詰めず、落ち着いて話しかけられる高さを取る。

| 項目 | 規定 |
|---|---|
| 入力欄 | **最初から 2 行ぶん見える**。書くほど伸び、上限を超えたら中で送る |
| アバター | 入力欄の高さに見合う大きさにする。小さく置かない |
| 状態の知らせ | 「聞いています」「お調べしています」などは、**高さの決まった場所**に出す |
| 変えないこと | **知らせの長さで帯の高さを変えない。** 変わると、書いている最中に入力欄が動く |

##### アバター（帯の左端）

| 項目 | 規定 |
|---|---|
| 置くもの | **秘書のアバター**。本人が個人設定で登録する（第6.5.3節）。未登録なら人の形のアイコン |
| 大きさ | 入力欄と知らせの場所に**見合う大きさ**。音声での対話が製品の要であり、小さく添えるものではない。ただし帯を占領しない |
| ふだんの見え方 | **控えめに見せる**（色を落とす）。会話していないことが一目で分かる |
| 話しているとき | はっきり見せる。**いま秘書が聞いている**ことを示す |
| 押したとき | **音声の対話を始める・終える。** 名前の文字ではなく、アバターが音声の入口になる |
| 読み上げ | 画像には代替の文を付ける（「秘書と音声で話す」） |

##### 操作はアイコンにする

文字のボタンを並べると、幅を食ううえに読み取りに時間がかかる。
**操作はアイコンにし、言葉は重ねたときに出す**（第6.1.1節の左ペインと同じ決まり）。

| 操作 | 形 |
|---|---|
| 音声で話す・終える | マイク |
| 書類を渡す（第10.10節） | クリップ |
| 送る | 紙飛行機 |

##### 入力欄

| 項目 | 規定 |
|---|---|
| 行数 | **複数行を書ける。** 入力に合わせて高さが伸び、上限を超えたら中で送る |
| 送る | `Enter` で送る。**`Shift+Enter` で改行する** |
| 日本語の入力 | 変換の確定の `Enter` では送らない |

#### 6.1.4 音声を始めたときの第一声

**押したら、秘書から先に声をかける。** 押した人が「何を言えばよいか」を考えずに済む。

| 項目 | 規定 |
|---|---|
| 呼びかけ | 本人の設定に従う。呼ばれ方（第6.5.3節）と、秘書の名前を使う |
| 名乗り | 秘書の名前が設定されていれば名乗る。無ければ名乗らない（勝手な名前を作らない） |
| 添えること | **その時点で分かっている事実だけ。** 今日の予定、承認待ちの件数など |
| 取れなかったもの | **触れない。** 「予定は取得できませんでした」と言わせない。第一声で詫びさせない |
| 作らないこと | **予定の中身を推測で作らない**（不変則 I-6 と同じ考え方）。数と題名は取れたものだけ |
| 長さ | ひと息で終わる長さ。最後に用件を尋ねて、相手に返す |
| 渡し方 | 読み上げる原稿ではなく**材料**を渡す（第10.11.7節と同じ）。秘書が自分の言葉で言う |

#### 6.1.5 最初の画面の呼びかけ

**業務の一覧ではなく、呼びかけから始める。**

最初の画面は、**その日はじめて秘書に会う場所**である。機能の説明や件数の表を並べる場所ではない。
名前を呼び、時候に合った一言を添える。**生きた相手と話している感じを作る。**

| 項目 | 規定 |
|---|---|
| 呼び方 | 本人の設定の呼ばれ方（第6.5.3節）。無ければ表示名に「さん」 |
| 時候の一言 | **いまの時刻と曜日から選ぶ**（下表）。朝・昼・夜・深夜・休日 |
| 続ける言葉 | 「何かお手伝いしましょうか」。ひと息で終わる長さにする |
| 出さないもの | **件数の表・機能の説明。** 使える業務は左のメニューに、承認待ちは承認トレイに出ている。同じことを二度出さない |
| 作らないこと | **分からないことに触れない**（不変則 I-6 と同じ考え方）。祝日の判定は暦を持っていないため行わない |

| いつ | 一言 |
|---|---|
| 5:00〜10:59 | おはようございます |
| 11:00〜17:59 | こんにちは |
| 18:00〜21:59 | お疲れさまです |
| 22:00〜4:59 | 遅くまでお疲れさまです |
| 土曜・日曜 | 休日にお疲れさまです（時刻より優先する） |

**祝日は判定しない。** 日本の祝日は暦を持たないと分からず、年ごとに変わる。
**間違えて「休日ですね」と言うくらいなら、言わない。** 暦を持つときが来たら足す（第26章）。

#### 6.1.6 画面の URL（第 0.112.0 版）

**画面ごとに URL を持たせる。** 再読み込みしても同じ画面に戻り、ブラウザの「戻る」「進む」で画面を行き来でき、
お知らせのリンクから目的の画面へ直接入れるようにする。
これまでは画面を切り替えても URL が変わらず、再読み込みで最初の画面に戻り、お知らせのリンクは最初の画面止まりだった。
Chat への実際の送信が動いたため、先送りしていたこの改修を行う（2026-09-25 に三浦さんが依頼）。

| 画面 | URL |
|---|---|
| 最初の画面 | `/` |
| 業務の入力 | `/agents/{業務の ID}` |
| 実行の詳細 | `/runs/{実行の ID}` |
| 承認トレイ | `/approvals` |
| 実行履歴・お知らせ・定時実行 | `/history`・`/notifications`・`/schedules` |
| 個人設定 | `/settings/{区分}`（例: `/settings/google`） |
| ヘルプ | `/help`、記事は `/help/{記事の ID}` |
| 管理者ページ | `/admin`、区分は `/admin/{区分}`、小分けは `/admin/{区分}/{小分け}`（例: `/admin/connectors/mcp`）。管理者向けのヘルプは `/admin/help/{記事の ID}` |
| 眺めるための画面 | `/board`（第6.7.2.1節） |

| 項目 | 規定 |
|---|---|
| URL に載せるもの | **画面の種類と、意味を持たない ID だけ**（業務・実行・記事・区分）。**入力した内容・名前・メールアドレスなどは載せない**（ブラウザの履歴や共有したリンクから漏れるため） |
| 戻る・進む | 画面を切り替えるたびに履歴に積み、「戻る」「進む」で行き来できる |
| 再読み込み | 同じ画面を開き直す |
| 見られない・無い画面 | 業務・実行・記事が無い、または使えない・見られないときは、**「見つかりません」と出して最初の画面に戻す**。使えない業務があることは示さない（第16.7.4節と同じ） |
| 知らない URL | 最初の画面に戻す |
| お知らせのリンク | 承認の依頼は承認トレイ（`/approvals`）へ、完了・失敗など実行に結び付くものは実行の詳細（`/runs/{実行の ID}`）へ、ほかは `/` へ。Chat への控え（第6.5.5.2節）にも同じリンクを載せる |
| 配信 | 画面は静的なファイルとして配信する（第20章）。**知らない道には `index.html` を返す**設定が要る（`/v1` と静的なファイルを除く）。開発の Vite は既定でそう動く |
| 権限 | URL は開く画面を選ぶだけで、**見てよいかは API が決める**（第13.1節）。URL を知っていても、見られないものは見られない |

#### 6.1.7 定時実行の画面（第 0.133.0 版）

**定時実行は、画面で登録・編集・削除・制御する。** 左のメニューの「定時実行」（`/schedules`）で行う。
これまでは一覧と「停止する」「今すぐ実行」しかなく、新しく作るには API を呼ぶしかなかった（2026-09-26 に三浦さんが依頼）。
秘書からは、状態の確認・停止・再開・今すぐ実行ができる（第10.9.8節）。登録・編集・削除は秘書からは行わない。

| 操作 | 規定 |
|---|---|
| 登録 | 「追加」で、業務・繰り返し・時刻・業務の入力を選んで保存する。繰り返しは**毎日・毎平日（月〜金）・毎週（曜日を選ぶ）**。時刻は時と分 |
| 選べる業務 | 本人が使える業務（利用範囲・無効にした業務の決まりはそのまま効く。第16.7節）。**ファイルを受け取る業務**（第10.10.3節）と秘書の調べものは選べない（毎回違うものを渡すため） |
| 業務の入力 | 業務の実行の画面と同じ欄を出す（第6.10.4.1節）。必須の欄が空なら保存しない |
| 編集 | 繰り返し・時刻・業務の入力を変える。**業務は変えない**（変えたいときは削除して登録し直す）。保存すると次回の時刻を求め直す |
| 削除 | その場で消す。確かめの画面は出さない（社外にもお金にも関わらない。ADR-0028）。動いている実行は止めない |
| 停止・再開 | 停止すると次の回から起動しない。再開すると次の回から起動する（止めていた間の回は起動しない） |
| 今すぐ実行 | 次の回を今にする。ワーカーの次の見回りで起動し、そのあとは元の繰り返しに戻る |
| 時刻の基準 | 本人の個人設定のタイムゾーン（第6.5.1節） |
| 見られる人 | 本人の定時実行だけを見て、操作できる（管理者はほかの人の定時実行を管理者ページの「定時実行の一覧」で見られるが、操作はしない。第6.6.8.2節） |
| 朝のブリーフ | 秘書が自動で用意したもの（第9.5.5.1節）も、ほかと同じく編集・停止・削除できる。**消したものを秘書が作り直すことはない** |

### 6.2 秘書のキャンバス（第 0.114.0 版。以前の「会話ペイン」）

**画面右の領域は、秘書が結果を見せるための場所（秘書のキャンバス）とする。やり取りの記録（会話の履歴）は並べない**（ADR-0026。ADR-0020 の「会話専用」を改める）。

秘書とのやり取りは、**会話そのものは声か入力欄の中で行い、見せる必要のある結果だけを秘書のキャンバスに出す**。
これまでの会話ペインは、音声の細切れの文字と応答が履歴として積み上がり、読みたい結果が流れに埋もれた。
メールの一覧や予定の表のように「見る」ものと、「話す」ものを分ける（2026-09-25 に三浦さんが決定）。

##### 6.2.0 どこに返すか（第 0.114.0 版）

| 依頼の入り方 | 返し方 |
|---|---|
| **文字（入力欄）** | **答えを秘書のキャンバスに出す。音声は一切使わない**（読み上げない。音声で話している最中でも、入力欄から書いた依頼には文字で返す） |
| **音声** | **基本は音声で返す**（秘書のキャンバスには出さない）。ただし次のときは秘書のキャンバスにも出し、音声では要点と「画面に出しました」だけを話す |
| 　音声で「画面（キャンバス）に出して」と言われた | 直前の答え、または頼まれたものを秘書のキャンバスに出す |
| 　**秘書が「大きい」と判断した** | 次のどれかに当たる答え。**4 件以上の一覧**（予定・メール・ToDo など）、**メールや文書の本文**、**表**、**読み上げると 30 秒を超える長さ**（目安 200 字）、**押すボタンが付くもの**（業務を開く・ヘルプの記事）、**出典・根拠が付くもの**（社内の規程に基づく答え） |
| 後ろへ回した調べもの（第10.11節）の結果 | 音声で話している間は音声で伝え、大きければ秘書のキャンバスにも出す。音声で話していなければ秘書のキャンバスに出す |

| 項目 | 規定 |
|---|---|
| 出すもの | **いちばん新しい結果 1 つ**。新しい結果が来たら置き換える。前の結果は並べない（会話の履歴を作らない） |
| 結果の形 | 見出しに**依頼の言葉**（「明日の予定は？」など）を小さく出し、その下に答え。答えは書式として読む（第6.2.2.1節）。出典・根拠・業務を開くボタン・ヘルプの記事は、その結果に添える |
| 音声の文字（聞こえた言葉と秘書の言葉） | **秘書のキャンバスには並べない。** 秘書バーに、**直近の 1 往復だけ**を字幕として出す（聞き間違いに気づけるように。第10.5.2節）。次の発話で置き換え、残さない |
| 会話ログ | これまでどおりサーバーに残す（4 週。第11.9.4.1節）。記憶の候補（第11.5.2節）もそこから作る。**画面には並べない** |
| 画面を移ったとき | 秘書のキャンバスの結果は残る（業務の画面へ移っても消えない）。再読み込みでは消える |

##### 6.2.0.1 画面に履歴が無くても、秘書は覚えている（第 0.114.0 版）

画面にやり取りの記録を並べなくても、**秘書は本人とのやり取りをずっと覚えていて、答えるたびに使う**（第10.7.3節）。
「それを詳しく」「あれ、どうなった」は、画面の履歴ではなく秘書の記憶で通じるようにする。

以下のうち「本人の発言と秘書の応答」は、第 0.114.0 版で「秘書の結果（いちばん新しいもの）」に改めた。ほかの住み分けは変えない。

| ここに置くもの | ここに置かないもの | 置く場所 |
|---|---|---|
| 秘書の結果（いちばん新しいもの） | 業務の実行の結果と根拠 | 実行の詳細の画面（第6.2.2節） |
| その応答に添えた根拠・出典 | 承認の差分 | 承認トレイ |
| 取次の提案、ヘルプの案内 | 知識の検索結果の一覧 | キャンバス |

**秘書の答えの根拠は、秘書のキャンバスのその結果に添える**（第6.2.0節）。結果から離れた場所へ出さない。

**出典の見せ方**（第 0.103.0 版）

2026-09-25 の受け入れテストで、同じ議事録の節が 5 つ、書式の記号（`**`・`-`）のまま、右の細い欄に押し込まれて並び、読めなかった。

| 項目 | 規定 |
|---|---|
| 形 | 出典は**題名の行（文書名 › 見出しの経路）と、抜き出した本文の 2 段**で出す。「ラベル｜値」の 2 列にしない |
| 本文 | 書式の記号を外して読める文にし、**3 行まで**に収める。全文は出典の文書で読む |
| 並び | **答えで根拠にした出典を先に出す。** それ以外に調べた箇所は「ほかに調べた箇所（〇件）」として畳む |
| そのほかの根拠 | 予定の時刻と題名、未読メールの差出人と件名などの短い根拠は、これまでどおり 2 列で出す |

**会話の画面には答えだけを出す**（第 0.160.0 版）

2026-09-29 に、「トナーまだ足りてる？」への答えの下に、本文に書き込まれた出典の括弧、聞いていない経費精算規程の本文、
「参照した記憶（覚えている事実 35 件・…）」、「ほかに調べた箇所」、「対話 / 2826ms / 4687 トークン」が並び、
一文で済む答えが重くなった（三浦さんの指摘）。

| 項目 | 規定 |
|---|---|
| 出すもの | 秘書の答えの文、取次の提案（業務を開くボタン）、ヘルプの案内 |
| 根拠 | 出典・そのほかの根拠・参照した記憶は、**答えの下の「根拠」にまとめて畳む**（既定は閉じる）。押すと開き、上の「出典の見せ方」のとおりに出す。信頼は、押せばいつでも出典を確かめられることで保つ |
| 答えの本文 | **出典の括弧（【…】）を書かない。** 根拠にした出典は「根拠」の先頭に出す（第10.9.4.1節） |
| 処理の情報 | 応答の層・かかった時間・トークンの数は、**会話の画面に出さない**。管理者は実行の一覧・利用状況で見る（第6.6節） |

**開き方と幅**

結果は読むものである。**狭いと読めない。** かといって、使っていない間まで場所を取るのもよくない。
左ペインと同じく、**折りたためる**ようにする。

| 項目 | 規定 |
|---|---|
| 既定 | **折りたたむ。** 結果を出していないときは、細い帯だけを残す |
| 自動で開く | **秘書のキャンバスに結果を出したら開く**（第 0.114.0 版）。音声だけで返したときは開かない |
| 自動で閉じない | **一度開いたら、閉じるのは本人だけ。** 画面を移っても閉じない |
| たたんだとき | 細い帯に、開くボタンと、**まだ見ていない結果がある印**を出す。中身は出さない |
| 幅 | **開いたときの既定は、中央のキャンバスと同じ幅にする。** 左ペインを除いた残りを半分ずつに分ける |
| 幅を変える | **左端の境目をつかんで、狭くできる**（第 0.138.0 版）。**広げられるのは既定の幅（残りの半分）まで**。中央のキャンバスより広くすると、業務の画面が読めなくなるため。狭くできるのは 280px まで。境目をダブルクリックすると既定の幅に戻る。キーボードでも境目に移って左右の矢印で変えられる |
| 題 | 「秘書のキャンバス」の題は、**開け閉めのボタンと同じ行の中央**に出す（第 0.138.0 版）。題のために 1 行を使わず、結果を縦に広く見せる |
| 覚えておく | たたんでいるかどうかと、**変えた幅**を、端末ごとに覚えておく（左ペインと同じ扱い）。たたんで開き直すと、覚えた幅で開く。画面が狭くなって覚えた幅が既定の幅を超えるときは、既定の幅で出す |
| 狭い画面 | 折りたたみも幅の変更も使わず、キャンバスの下に積む（第6.1.1節と同じ考え方） |

**幅を、補助情報のときのまま（320px）にしない。** 見出しと箇条書きを含む答え（第6.2.2.1節）が
1 行 10 数文字に折り返され、読めなくなる。**決め打ちの幅も置かない。**
画面の広さは人によって違う。広い画面で会話だけが細いままになる。

#### 6.2.1 やり取りの記録の並べ方（第 0.114.0 版で廃止）

**第 0.114.0 版で、画面にやり取りの記録を並べるのをやめた**（第6.2.0節、ADR-0026）。以下は以前の規定として残す。
書式の扱い（秘書の応答は書式として読み、本人が書いた文は書いたとおりに出す）は、秘書のキャンバスの結果にも引き継ぐ。

秘書とのやり取り（文字・音声の両方）は、**1 本の流れとして時間の順に並べる**。

| 項目 | 規定 |
|---|---|
| 並び | **古いものが上、新しいものが下。** 上から差し込まない |
| 開いたとき | **一番下（いちばん新しいところ）を見せる** |
| 新しく届いたとき | 一番下へ足し、そこまで送る |
| 話し手 | 1 件ごとに、本人か秘書かを示す |
| 音声の途中 | 文字は細かく届く。**同じ話し手が続く間は 1 件にまとめる。** 話し手が変わったら次の 1 件にする |
| 根拠・提案 | その応答の 1 件に添える。別の場所へ離さない |
| 書式 | **秘書の応答は**見出し・箇条書き・表として読む（第6.2.2.1節）。**本人が書いた文は、書いたとおりに出す** |

**新しいものを上に積まない。** 上に積むと、どちらが先の発言か分からなくなる。

#### 6.2.2 実行の結果の示し方

**終わった実行の答えは、必ず画面に出す。**

業務には、文書を作るもの（成果物が残る）と、**答えるだけのもの**（AG-04 社内ナレッジ Q&A など）がある。
後者は成果物を作らないため、成果物の欄だけを見ていると**結果がどこにも出ない**（2026-09-23 に実機で確認）。

利用者から見れば、段が並んでいて「完了」と出ているのに、何が分かったのかが読めない。

| 項目 | 規定 |
|---|---|
| 出すもの | **最後の段の応答の文**。成果物があればそれも出す。**同じことを 2 度出さない**: 応答の文が成果物と同じ（片方がもう片方をそのまま含む）なら成果物だけを出す（第 0.116.1 版） |
| 見出し | **「結果」「成果物: 〇〇」のような仕組みの見出しを付けない**（第 0.116.1 版）。成果物の題名は、成果物が 2 つ以上あって見分けが要るときだけ出す。2026-09-26 に、挨拶の拡張機能の実行の詳細に「結果」と「成果物: 返事」で同じ一文が 2 回並び、三浦さんが「堅苦しい。ロジックを見せないで」と指摘した |
| 置き場所 | 実行の詳細の**いちばん上**。ほかのものより先に読めること |
| ツールの呼び出し | 途中の段の文にはツールの呼び出しが混じる。**それは出さない**（第10.11 節の調べものと同じ） |
| 失敗したとき | 理由を出す。**そこまでに分かったことがあれば、それも出す** |
| 何も無いとき | 「結果がありません」と明示する。黙って空にしない |
| 書式 | 推論が返す文は**見出し・箇条書き・表として読む**（第6.2.2.1節） |
| 途中の見せ方 | 動いていることだけを示し、終わったら消す（第6.2.2.2節） |

##### 6.2.2.1 推論が返した文の書き方の扱い

推論は、見出し・箇条書き・表を使って答える。**これを文字のまま出すと `###` や `**` が画面に並び、読めない。**
実行の結果・秘書の応答・通知の本文は、いずれも推論が書いた文であり、同じ扱いにする。

| 項目 | 規定 |
|---|---|
| 読むもの | 見出し・段落・箇条書き・番号付きの箇条書き・表・コードの囲み・行の中のコード・太字・リンク |
| HTML | **解釈しない。** 書かれたタグは文字のまま出す |
| リンク | **`http(s)://` と `mailto:` だけを押せるようにする。** それ以外は文字だけを出す。**文の中にそのまま書かれた `http(s)://` の URL も押せるようにする**（第 0.110.3 版。空白・括弧・日本語の句読点と閉じ括弧で終わりとし、文末の「.」「,」は含めない。コードの中は押せるようにしない） |
| 本人が書いた文 | **書いたとおりに出す。** 書式として読み替えない |
| 内部の ID | 実行の結果と承認の画面では、推論の文から成果物・ファイル・実行などの ID を取り除いて出す（URL の中は残す。第 0.110.2 版）。推論にも ID を書かないよう指示している（第9.3.2節）。実行の記録（確認用）の実行 ID は、問い合わせに使うため残す |

**HTML を解釈しない理由は不変則 I-6 である。** 実行の結果には、外から取得した文書やメールの
中身が入りうる。そこに書かれたものを画面の仕組みとして動かしてはならない。
リンクを絞るのも同じ理由による。

##### 6.2.2.2 実行の途中と、出さないもの

**実行の詳細に出すのは、本人が読むもの・本人が決めることだけにする。**

利用者は、実行 ID も、消費したトークン数も、段の一覧も**変えられない**。
変えられないものを並べても、読むべきものが埋もれるだけである（2026-09-24 に実機で確認）。

**動いている間**

| 項目 | 規定 |
|---|---|
| 出すもの | **回っている印**（歯車など）と、**いま何をしているか**を 1 行。ツールを呼んでいる間はツールの言葉（「evidencemd に問い合わせています」「資料を作成しています」）、それ以外はステップの表示名（第9.2.4節）を使う |
| 経過した時間 | 1 行の後ろに、**その動きを始めてからの時間**を添える（「（28 秒）」「（1 分 20 秒）」）。画面で 1 秒ごとに数える（第 0.208.0 版。2026-10-01 に三浦さんが、EvidenceMD の答えを 30 秒待つ間に「動いているのか心配になる」と指摘して依頼） |
| 進み具合 | 段が 2 つ以上の業務では、1 行の下に段の並びを短く出す（済んだ段は ✓、いまの段は ●、これからの段は ○ と表示名）。**動いている間だけ出し、終わったら消す**（第 0.208.0 版。それまでは段の一覧を出さないとしていたが、どこまで進んだかが分からず待つ不安が大きいため、動いている間に限って改めた） |
| 見込み | **残りの時間の見込みは出さない**（当たらない見込みは不安を増やす。第10.11.5節） |
| 目的 | **だんまりにしない。** 動いていること、どこまで進んだか、どれだけ待ったかが分かればよい（第10.11.6節と同じ考え方） |
| 残さない | **考えている途中の文（思考の経過）は残さない。** 終わったら消す |
| 本人が決めること | 中止のボタン（第9.3.1節）。承認待ちなら、承認トレイへの案内 |

**終わったあと**

| 項目 | 規定 |
|---|---|
| 消すもの | 途中の表示は**すべて消す** |
| 残すもの | **結果**（第6.2.2節）と**成果物**だけ。失敗したときは理由 |

**本人の画面に出さないもの**

| 出さないもの | どこにあるか |
|---|---|
| 実行 ID | 実行の記録（第19.1節）。問い合わせのときは要求の ID を使う（開発規約 第7.4節） |
| 消費トークン・費用 | 管理者ダッシュボード（第6.7節、FR-413）と利用量の画面（第21章） |
| 段（ステップ）の一覧 | 実行の記録。ダッシュボードの「業務の流れ」（第6.7.5節） |
| 使ったツールの一覧 | 実行の記録とアプリログ（第19.3節） |

**これらを消しても、調べられなくなるわけではない。** 場所を変えるだけである。
不具合の追跡はアプリログで行う（開発規約 第7章）。実行の中身は API（`GET /v1/runs/{id}`）に残り、
見られる人の範囲も変わらない（第6.2.3節）。

**ただし、承認する人は判断の前に中身を確かめる必要がある**（原則 u2）。
このため、実行の詳細の最後に**閉じた状態の「実行の記録」**を置き、開いたときだけ
段・ツール・ID を出す。既定では閉じている。

#### 6.2.3 実行の中身を見られる人

実行の中身（ステップの入力と出力、根拠、成果物、業務が扱ったファイル）には、
業務が Google から取得したメールや文書が入る。**見られる人を、その実行に関わる人に限る。**

| 見られる人 | 範囲 | 理由 |
|---|---|---|
| 依頼した本人 | 自分が依頼した実行（定時実行を含む）のすべて | 本人の業務である |
| 承認する人 | **自分が判断できる承認（第9.2.3節）がある実行だけ**。判断を終えた後も同じ | 判断のために中身を見る必要がある |
| 承認者の役割を持つほかの人 | 見られない | 承認者の役割は「その業務の承認を判断する」ためのもので、会社の中のすべての実行を見る権限ではない |
| 管理者 | 状態・費用・起動経路だけ（第6.6.8節）。中身は見られない | 内容ではなく状態を見る |
| 運営 | 見られない。調査が必要なときは第23章の例外の手続きだけ | Google の Limited Use（第14.3.2節） |

**見られない実行は、存在自体を示さない**（「見つかりません」と返す）。
業務が作ったファイル（`file.run_id` がある）は、その実行を見られる人だけが開ける。
利用者が上げたファイルは、上げた本人と、そのファイルを使った実行を見られる人だけが開ける。

#### 6.2.4 一覧から中身を開く

**一覧から詳細へ移るとき、画面を切り替えない。その場で開く。**

実行履歴の 1 件ごとに「詳細を見る」を置き、押すと実行の詳細の画面へ移していた。
**そこから一覧へ戻る道が無く、見比べるたびにメニューから入り直すことになる**
（2026-09-25 に実機で確認）。

| 項目 | 規定 |
|---|---|
| 開き方 | 行を押すと**その場で開く**。もう一度押すと閉じる |
| 何を出すか | 実行の詳細と同じもの（結果・成果物・実行の記録。第6.2.2節） |
| 取りに行く時機 | **開いたときに初めて**取りに行く。一覧を出すために全件の中身を読まない |
| 行に出すもの | 業務の名前・状態・始めた日時。**押す前に、どれを開くかが分かること** |
| 複数 | いくつでも開いたままにできる。**見比べるための画面である** |

**これは一覧の画面すべてに当てはまる。**

| 一覧 | 行に出すもの | 開いたときに出すもの |
|---|---|---|
| 実行履歴 | 業務の名前・状態・始めた日時 | 結果・成果物・実行の記録 |
| 承認トレイ | **業務の名前**・何の承認か・待たせている時間 | 判断するものと、**承認・却下のボタン** |
| 承認トレイの「判断したもの」 | **業務の名前**・承認か却下か・判断した日時・依頼した人 | 判断したときの承認の画面（何を承認したか）、承認のあとに実際に行ったことと結果、コメント、実行の詳細への道（第6.2.5節） |
| お知らせ | 題名・未読の印・届いた日時 | 本文 |
| 実行の一覧（管理者） | 業務の名前・状態・依頼者・起動経路・始めた日時 | **状態だけ**（段の進み・失敗の理由・費用・削減時間。下記） |

**管理者の一覧で開いても、中身は出さない。**
段の入力と出力、成果物、業務の入力は返さない。出すのは**段の表示名と状態**、失敗の理由、
時刻、費用、削減時間までである（第6.6.8節、不変則 I-10）。
**画面で隠すのではなく、API がそもそも返さない。** 画面の側だけで隠すと、いつか漏れる。

**承認・却下のボタンは、開いたときにだけ出す。** 中身を見ずに押せてしまうと、
承認が形だけのものになる（不変則 I-11 と同じ考え方）。

**お知らせは、開いた時点で読んだことにする。** 閉じても未読へ戻さない。

#### 6.2.5 判断したもの（承認の履歴。第 0.141.0 版）

**承認した人が、あとから「何を・どのように承認したか」を見返せるようにする。**
承認トレイは判断を待つものだけを出し、判断すると消えていた。社外への送信とお金の確定を承認するのに、
自分がいつ何を承認したかを見返す場所が無かった（2026-09-27、三浦さんの指摘）。
ほかの人が依頼した業務を承認したときは、自分の実行履歴にも出ないため、まったく見返せなかった。

| 項目 | 規定 |
|---|---|
| 場所 | 承認トレイの中の「**判断したもの**」。判断を待つものの下に並べる |
| 並べるもの | **自分が判断した**承認と却下。新しい順に 100 件まで。**自動で通過した承認**（社外にもお金にも関わらないもの。第9.3.3節）・期限切れ・取り消しは、人が判断していないため並べない |
| 行に出すもの | 業務の名前・**承認か却下か**・判断した日時・依頼した人（自分以外のとき） |
| 開いたときに出すもの | 下の表 |
| 見られる人 | 判断した本人だけ。管理者は監査ログ（第6.6.8節）で見る |

| 開いたときに出すもの | 内容 |
|---|---|
| **何を承認したか** | 判断したときの承認の画面を、**そのときのまま**出す（判断するもの・承認すると行うこと）。あとから書き換えない |
| **どのように承認したか** | 承認か却下か、判断した人と日時、コメント（却下の理由など） |
| **実際に行ったこと** | 承認のあとに行った操作を 1 つずつ、業務の言葉（第9.3.3節の言い方）と結果で出す。結果に相手のリンク（投稿・文書・予定など）があれば押せるように出す。失敗したものは理由を出す。却下したものは「行っていません」 |
| 実行の詳細へ | その実行の詳細（第6.2.2節）を開く道。承認する人はその実行を見られる（第6.2.3節） |
| 消した中身 | Google から取得したデータを含む実行は、保存期間（第14.3.2節）を過ぎると中身を消す。そのときは「保存期間を過ぎたため、中身を消しました」と出し、承認か却下か・日時・業務の名前は残す |

**実行の詳細にも、誰がいつ判断したかを出す。** 承認の段に「三浦雅孝さんが 9月27日 22:00 に承認」「自動で通過」「却下（理由）」を、
閉じた実行の記録の中ではなく、結果の近くに出す。依頼した人が、自分の業務を誰が承認したかを確かめられるようにする。

### 6.4 設定の分担

**この節で決めること**: 何を管理者が決め、何を本人が決めるか。

#### 6.4.1 分担の原則

| # | 原則 | 対象 |
|---|---|---|
| d1 | **安全性・費用・権限に関わるものは管理者が決める** | LLM の鍵、コネクタ、ロール、承認者、上限 |
| d2 | **本人の働き方と本人のデータは本人が決める** | 表示名、応対スタイル、音声、個人記憶 |
| d3 | **本人が選べるのは、管理者が決めた枠の中だけ** | 使えるエージェントの中から並べ替える、など |
| d4 | **本人にしかできないことがある** | Google の認可（第6.4.2節） |

d3 が要点である。たとえば管理者が「経理エージェントは経理担当のみ」と決めたら、
本人がメニューに並べることはできない。本人が調整できるのは、
**与えられた範囲の中での見せ方と好み**に限る。

#### 6.4.2 Google の認可は本人にしかできない

| 決めること | 決める人 |
|---|---|
| どのスコープを要求するか | **管理者**（機能の有効化を通じて） |
| 実際に許可するか | **本人**（OAuth の同意画面で） |
| 許可を取り消すか | **本人**（および Workspace 管理者） |

これは製品の方針ではなく、**OAuth の仕組み上そうなる**。
管理者が本人に代わって同意することはできない。

したがって、機能を有効にしただけでは動かず、
本人が認可して初めて使える状態になる。この段差を埋めるのが
連携ウィザード（第22.2節）である。

#### 6.4.3 分担の一覧

| 設定項目 | 管理者 | 本人 |
|---|---|---|
| LLM の提供者・モデル階層・鍵 | **決める** | 見えない |
| コネクタ（Google、MCP） | **決める** | 状態を見る |
| Google の個別の認可 | 要求する範囲を決める | **許可・取消を行う** |
| 利用できるエージェント | **決める** | 与えられた中から並べる |
| 承認者・承認権限 | **決める** | 見る |
| 権限区画への所属 | **決める** | 見る |
| 利用量の上限・自動課金 | **決める** | 自分の消費を見る |
| 組織知識の登録 | **決める** | 見る（会社の知識にするかは秘書が判断する。第11.3節） |
| 表示名・アバター | 初期値を設定 | **変える** |
| 秘書の応対スタイル・音声 | 既定を設定 | **変える** |
| 個人記憶 | 見えない | **確認・削除する** |
| 通知の受け取り方 | 既定を設定 | **変える** |

**管理者は個人記憶を見られない**（不変則 I-10）。
部下の秘書が何を覚えているかを管理者が閲覧できる状態は、信頼を損なう。

#### 6.5.0 設定は分けて出す

**目的の項目までたどり着くのに画面を延々と送ることになる**（2026-09-24 に実機で確認）。

| キーボード | 一覧は矢印で選び、Enter で決める（第6.11節） |

| 区分 | 中身 |
|---|---|
| プロフィール | 名前、利用状況（第6.5.1節・第6.5.7節） |

#### 6.5.1 プロフィール

| 項目 | 内容 | 備考 |
|---|---|---|
| 表示名 | 画面と成果物に出る名前 | 初期値は Google アカウントから取得 |
| ふりがな | 並び順と読み上げに使う | |
| アバター | 画像。**Google のプロフィール写真を取り込む**（第6.5.1.1節）。取り込めていなければ人の形のアイコン | 左ペインの下の、本人の表示に出す |
| 役職・所属 | 文書の署名に使う | 初期値は管理者が設定 |
| メールアドレス | ログインに使う | **変更不可**（Google 側で管理） |
| タイムゾーン | 予定と定時実行の基準 | 既定は Asia/Tokyo |
| **自宅**（第 0.125.0 版） | 地域か最寄り駅（例: 横浜市港北区・日吉駅）。出張・外出の行程の出発地と、朝のブリーフの天気の地域に使う | **本人の秘書と、本人の依頼で動く業務だけが使う**。管理者・ほかの利用者には見せない。番地までは書かなくてよい（Google 検索に渡るため） |
| **いつもの勤務地**（第 0.125.0 版） | 「会社から行く場合」の出発地 | 空なら会社情報の住所（第6.6.1節） |

**自宅と勤務地のほかは、人に表を書かせない**（ADR-0028）。「新幹線は窓側」「月・金は在宅」のような好みは、秘書が会話から覚える（第11.5節）。

##### 6.5.1.1 Google のプロフィール写真（第 0.99.0 版）

**本人のアバターには、Google アカウントのプロフィール写真を使う。** 本人が設定しなくても、見慣れた自分の顔が出る。
ログインで求める許可（`openid`・`email`・`profile`。第16.1.1節）の範囲で受け取れるため、**許可を増やさない**。

| 項目 | 規定 |
|---|---|
| いつ取り込むか | **Google でログインしたとき**。あわせて、Google 連携で接続したときと、許可の状況を確かめたとき（その許可で受け取れる場合だけ）。**どれも本人の操作の中で行い、裏で定期的に取りに行かない** |
| どこから | Google の利用者情報（userinfo）の `picture`。**`https` で、Google の画像の置き場（`*.googleusercontent.com`）からだけ取る**。受け取った URL をそのまま取りに行くと、サーバーから任意の場所へ要求を出させられる |
| 保存 | サーバーに取り込み、**画面へは M2Office から出す**。画面から Google の置き場を直接読ませない（写真の URL が変わっても出続け、画面を開くたびに Google へ要求が飛ばない） |
| 形式・大きさ | PNG と JPEG だけ。1 MB まで。1 人 1 枚 |
| 置き換え | 取り込み直すたびに上書きする。古い写真は残らない |
| 取れないとき | **前の写真のまま**にする。ログインや接続は止めない（写真のためにログインできなくなるのは本末転倒） |
| 見られる人 | 本人だけ（いまは左ペインの下の、本人の表示にだけ出す） |
| Google のデータの保持 | **対象外**（第14.3.2節）。表示名と同じく、ログインで受け取る本人の情報であり、Workspace の中身ではない。利用者を消すと一緒に消える |

#### 6.5.2 Google 連携

**本人が許可し、本人が取り消す**（第6.4.2節）。

| 項目 | 内容 |
|---|---|
| 許可の状態 | 用途ごとに、許可済みか未許可かを一覧表示する |
| 用途の説明 | 「メールの下書きを作るために Gmail を読みます」のように**業務の言葉で**書く |
| 接続 | 「Google と接続する」で Google の同意の画面へ進み、本人のアカウントで許可する（第14.3.3節） |
| 追加の許可 | 未許可の用途を、その場で許可できる |
| 取り消し | **許可はまとめて取り消す**（Google の取り消しはトークン単位で、用途ごとには外せないため）。用途を減らしたいときは、取り消してから、必要な用途だけで接続し直す。取り消す前に、使えなくなる業務と止まる業務を示す（第6.5.2.1節） |
| 有効期限 | 再認可が必要な時期を表示する |
| 最終確認 | いつ許可したかを表示する |

**「鍵」という言葉を使わない。** 利用者から見れば「Gmail を読む許可」であり、
トークンの存在を意識させない（原則 u1）。

##### 6.5.2.1 許可がなくなったときの業務の扱い（Q-54 で決定）

許可は、M2Office の外でもなくなる。どの経路でも、**ほかの人のトークンや見本の接続口で代わりに動かさない**（不変則 I-9）。

| # | 経路 | 気づく時点 | 扱い |
|---|---|---|---|
| 1 | 本人が個人設定で取り消す | すぐ | 取り消す前に「止まる業務が○件あります」と示し、確かめてから取り消す。下の「後始末」を行う |
| 2 | 本人が Google アカウントの画面で M2Office へのアクセスを外す | 次に Google を呼び、トークンの取り直しに失敗したとき | その時点で、保存しているトークンを消し、経路 1 と同じ後始末を自動で行う。本人に「Google との接続が切れました。個人設定から接続し直してください」と知らせる |
| 3 | Google Workspace の管理者がアプリの許可を外す、または本人のアカウントを停止する | 同上 | 経路 2 と同じ |
| 4 | 会社の管理者が OAuth クライアントを削除する、またはクライアント ID を替える | すぐ | 削除（変更）の前に「接続している○人の許可が使えなくなり、動いている業務○件が止まります」と示して確かめる。そのあと全員について後始末を行う。**シークレットだけを替える場合は影響しない**（トークンはクライアント ID に結び付くため） |
| 5 | 接続し直したとき、前より少ない権限しか許可しない | 次に Google を呼んだとき | その業務だけを止め、足りない許可を業務の言葉で示して追加の許可へ案内する。トークンは消さない |

**後始末**（経路 1〜4）

| 対象 | 扱い |
|---|---|
| 待ち行列・実行中・承認待ちの業務のうち、Google のツールを使うもの | 止めて「中止」（`cancelled`）とし、理由を「Google との連携を解除したため止めました」とする。承認待ちの承認は承認トレイから外す。依頼した本人（承認待ちなら承認する人にも）に知らせる |
| Google のツールを使わない業務 | 止めない |
| 実行中の業務の止め方 | エンジンは手順の区切りごとに、止められていないかを確かめ、止められていれば続きを行わない。呼び出し中の Google の操作は途中では切れない |
| 途中で作られた Google 側の文書 | 許可がないため M2Office からは消せない。止めたことを知らせるときに、作りかけの文書へのリンクを添える |
| 終わった実行の中身 | 直ちに消す（第14.3.2節） |
| 定時実行 | 設定は消さずに残し、許可がない間は起動を飛ばす。本人に一度だけ知らせる。接続し直せば、次から自動で起動する |

**承認された送信でも、許可がなければ送らずに止める。** 依頼した人と承認した人の両方に、業務の言葉で理由を知らせる（第9.4節の承認ゲートの意味を保つ）。
失敗の理由に技術的な誤りの文をそのまま出さない（原則 u1）。

M2Office で利用者を停止したとき（第6.6.4節）も、同じ後始末を行う。停止された利用者の定時実行は起動しない。

##### 6.5.5.1 通知の種類と、誰に届くか（Q-86 で決定）

| 種類 | いつ | 届く人 |

| 承認依頼（`approval`） | 実行が承認待ちになったとき | その承認を判断できる人（ロール、または依頼した本人。第9.2.3節） |

### 6.6 管理者ページ（`/admin`）

**この節で決めること**: 管理者が設定する項目。

テナントのサブドメイン配下の `/admin` に置く。管理者ロールを持つ者だけが開ける。

**管理者ページには秘書のキャンバス（第6.2節。以前の会話ペイン）を置かない。** 中央の作業の場所は、左のメニューの右から画面の右端まで使う。ワークスペースと同じ配置のまま右の列を残すと、右端に何も無い帯ができる（2026-09-25 に三浦さんが指摘）。

#### 6.6.0 1 つの画面に、1 つの保存

**1 画面 1 保存とする。** 1 つの画面にいくつも保存のボタンを置かない。

いくつも置くと、**どのボタンがどこまでを保存するのかが分からない**。
書き換えたのに別のボタンを押し、保存できていないことに気づかない
（2026-09-24 に実機で確認。「会社情報」に保存が 5 つ、「業務と承認」に 4 つあった）。

| 項目 | 規定 |
|---|---|
| 分け方 | 大きな区分（会社情報・接続など）の下に**小分け**を作り、**小分け 1 つを 1 画面**にする |
| 保存 | **1 画面に 1 つ。** その画面で書き換えたものだけを保存する |
| 選び方 | 左のメニューの区分に**開く印**を付ける。押すと小分けが出て、選ぶとその画面へ入る |
| 覚えておく | 開いている区分を覚える。設定を続けて触るときに、毎回開き直さない |
| 保存を持たない画面 | **混ぜない。** 一覧・状況の確認だけの画面は、小分けとして別に置く |

**「設定」と「状況の確認」を同じ画面に混ぜない。**
接続の画面には、設定（鍵・クライアント）と、確認（従業員の接続状況・求める許可）が
混ざっていた。読む人の目的が違う。

##### 6.6.0.1 区分と小分け

| 区分 | 小分け | 保存 |
|---|---|---|
| 会社情報 | 基本情報／自社の書き方／帳票の体裁／スライドの見本／ダッシュボードの見せ方 | 各 1 つ |
| 接続 | Gemini／Google Workspace／データを残す日数／求める許可（確認）／従業員の接続状況（確認）／コネクタ（MCP） | 各 1 つ、確認は 0。コネクタは操作ごとにすぐ反映 |

##### 6.6.3.1 ツールを 1 つずつ有効・無効にする

**接続を登録したあとで、ツールを 1 つだけ止めたいことがある。**
「調べるのはよいが、書き込みは止めたい」のように、危険度の高いツールだけを外す場合である。

| 項目 | 規定 |
|---|---|
| 対象 | **コネクタ（MCP）のツールだけ**。内蔵のツールは業務の定義が決めるもので、ここでは扱わない |
| 既定 | 接続のツールは、すべて有効である。**無効にしたものだけを記録する** |
| 決める人 | 管理者。場所は管理者ページの「接続 › コネクタ（MCP）」（第 0.132.0 版） |
| 危険度との関係 | 無効化は、危険度を強くすることの一番強い形である（第12.11.2節）。危険度を決めるのも止めるのも管理者である |
| 無効にしたツール | テナントのツールの一覧から外す。業務エージェントからも、接続の確認からも見えない |

**無効にすると、そのツールを使う業務が使えなくなる。**
業務の定義はツールを名前で指しており、1 つ欠けると最後まで進めないためである。

| 項目 | 規定 |
|---|---|
| 無効にする前 | **止まる業務を一覧で示して確かめる。** 数だけでなく、業務の名前を挙げる |
| 無効にしたあと | その業務は**メニュー・秘書・定時実行・API から消える**。存在自体を示さない（第12.10.4節・第16.7.4節と同じ） |
| 動いている実行 | **止めない。最後まで進める。** 同意のある範囲で始まった実行であり、途中で止めると成果物が中途半端に残る。Google の許可の取り消し（第6.5.2.1節）は本人の権限が消えるため止めるが、ここは管理者の運用の判断であり、急いで止める理由がない |
| 定時実行 | 次の回から飛ばす。業務が使えないことを、定時実行を持つ人に一度だけ知らせる（第6.5.2.1節と同じ扱い） |
| 元に戻す | いつでも有効に戻せる。戻せば業務も戻る |
| 記録 | 監査ログ `extension.tool.toggle`（拡張機能・コネクタ・ツール・有効か） |

##### 6.6.8.1 監査ログの画面（第 0.142.0 版）

**監査ログは「いつ・誰の指示で・何が行われたか」を、管理者が業務の言葉で確かめる画面である**（第16.6節）。
トラブルのとき（このメールは誰が承認して送られたか）、設定の変更を追うとき（誰が権限や接続を変えたか）、
社外に説明を求められたときに使う。

以前は、主体を内部の番号（`user: u-…`）、操作を開発者向けの名前（`connection.oauth.connect`）で直近 200 件並べるだけで、
**誰が何をしたのかが分からなかった**（2026-09-27、三浦さんの指摘）。記録そのものは残っており、足りなかったのは見せ方である。

| 列 | 出すもの |
|---|---|
| 日時 | 日本時間 |
| **誰が** | 人の名前。秘書が代わりに行ったものは「秘書（〇〇さんの依頼）」、業務が行ったものは「業務「〇〇」（〇〇さんの依頼）」、定時実行や保持期間の処理は「システム（定時実行）」のように、**指示した人か、仕組みの名前**を出す（第16.6節「秘書が代行した操作も、本人を主体として記録する」）。人を引けなければ記録の値のまま出す（推測で名前を作らない） |
| **何をしたか** | 業務の言葉（「Slack と接続した」「承認・却下した」「接続の鍵を登録した」など）。言葉を持たない操作は、記録の名前のまま出す |
| **何に対して** | 分かるものは名前で出す（業務・接続・利用者・拡張機能など）。分からないものは記録の値 |
| 詳細 | 行を押すとその場で開き、記録に残した根拠（コメント、承認か却下か、変えた項目など）と、記録の名前・値をそのまま出す。**会話や成果物の中身は元から記録しない**ため出ない |

| 機能 | 規定 |
|---|---|
| 絞り込み | **期間**（既定は直近 7 日）・**人**（その人が行ったもの・その人の依頼で秘書や業務が行ったもの）・**操作の種類**（ログイン・承認・業務の実行・秘書・接続・拡張機能・ユーザーと権限・設定・知識と記憶・定時実行・名刺） |
| 件数 | 新しい順。1 回に 200 件ずつ、「さらに読む」で続きを出す |
| CSV 出力 | 絞った結果をそのまま出力する（Excel で開けるよう BOM 付きの UTF-8）。列は日時・誰が・何をしたか・何に対して・記録の名前・記録の値・詳細。**出力したことも監査ログに残す**（`audit.export`） |
| 見られる人 | 管理者だけ（これまでどおり） |
| 改変 | 追記のみ。画面から消したり直したりできない（第16.6節） |

##### 6.6.8.2 定時実行の一覧（第 0.143.0 版）

**管理者が、会社の全員の定時実行を見渡す画面である。** 左のメニューの記録の「定時実行の一覧」（`/admin/schedules`）に置く。
使う場面は、「毎朝のブリーフが届かない」と相談されたとき、業務や接続を止める前にだれの定時実行に響くかを見るとき、
辞めた人の定時実行が残っていないかを確かめるときである。
これまでは API（`GET /v1/schedules?scope=tenant`）だけがあり、画面が無かった（第24.4.4節）。

| 列 | 出すもの |
|---|---|
| 人 | 定時実行の持ち主の名前（引けなければ記録の値のまま） |
| 業務 | 業務の名前 |
| 繰り返し | 「毎平日 7:30」のような言葉（本人の画面と同じ） |
| 次回・前回 | 日時（日本時間） |
| 状態 | **動く**・**止めている**（本人が止めた）・**動かない**（次の回に起動を飛ばすもの。理由を添える） |

| 項目 | 規定 |
|---|---|
| 動かない理由 | 定時実行の起動役が起動を飛ばすときと**同じ判定**で、いま見たときの理由を出す（利用者が停止中・業務が無効・止めたツールを使う・利用範囲の外・権限区画の外・Google と未接続・サービスと未接続など。第6.5.2.1節・第6.6.3.1節・第12.11.6.3節・第16.7.4節）。判定を画面のために別に作らない（食い違うと、動かないものを「動く」と見せてしまう） |
| 並び | 動かないものを先に、次に人・次回の順 |
| 出さないもの | **業務の入力**（本人が業務に渡す中身。第6.6.8節と同じく、管理者は状態を見て中身は見ない。不変則 I-10） |
| 操作 | **しない。** 追加・編集・停止・削除・今すぐ実行は本人の画面だけで行う（本人の権限で動くものを他人が仕掛けたり変えたりしないため。第6.1.7節）。動かないものは、理由に応じて管理者が業務・ツール・利用者の設定を直すか、本人に接続を頼む |
| 見られる人 | 管理者だけ |

#### 6.6.9 外部アプリ

| 項目 | 内容 |
|---|---|
| アプリの登録 | 名称、用途、スコープ、扱える最大危険度 |
| 失効 | いつでも権限を取り消せる |
| 利用状況 | 呼び出し回数、直近のエラー |

`external-send` と `financial` の承認は、外部アプリからは
**恒久的に行えない**（第13.3節）。

### 6.7 ダッシュボード

**この節で決めること**: 会社の管理者が、M2Office がいま社内でどう動いているかを
**リアルタイムかつ視覚的に**把握する画面。

**用語の区別**: 本書で「ダッシュボード」と言うときは、この節の画面（テナントごと、会社の管理者向け）を指す。
M2Office 運営が全契約企業を見る画面は「マスター管理画面」（第23.8節）であり、別のものである。

#### 6.7.1 目的

管理者ページ（第6.6節）で設定はできても、**実際にどう動いているかが見えなければ、
管理者は安心して任せられない**。ダッシュボードは次の問いにその場で答える。

| 問い | 答える部分 |
|---|---|
| いま誰が使っているか。何をしているか | 人の状態（第6.7.4節） |
| どの業務が動いていて、どこまで進み、どこで止まっているか | 業務の流れ（第6.7.5節） |
| 外部のサービスとの接続は健全か | 接続先（第6.7.6節） |
| 今日はどれだけ動き、どれだけ時間が浮いたか | 上部の数値と集計（第6.7.8節） |

「導入したが効果が測れない」という調査上の課題（第1.5節）への回答でもある。
**動いている様子が見えること自体が、定着と追加導入の説得材料になる。**

#### 6.7.2 置き場所と対象者

| 項目 | 方針 |
|---|---|
| 置き場所 | 管理者ページ（`/admin`）の最初の画面と、**掛け通しの画面**（`/board`。第6.7.2.1節） |
| 見られる者 | テナントの管理者 |
| 一般の利用者 | 自分の状態と、自分の業務の流れだけを見られる（ワークスペースの「実行履歴」） |
| 更新 | **自動で更新する**。画面を開いている間、状態の変化を数秒以内に反映する（第6.7.9節） |

##### 6.7.2.1 掛け通しの画面（`/board`）

**この画面は、操作する画面ではない。眺める画面である。**

管理者はダッシュボードをほとんど操作しない。**開いたまま置いておき、ときどき目をやる。**
壁に掛けたモニターに映しておく使い方も想定する。
操作するための飾り（メニュー・タブ・設定）は、眺めるときには邪魔になる。

| 項目 | 規定 |
|---|---|
| 置き場所 | `/board`。管理者ページとは**別の道**にする |
| 開き方 | ダッシュボードから「**別の画面で開く**」。新しいタブで開く |
| 出さないもの | 左のメニュー、上の帯、「集計」への切り替え、ヘルプの「？」。**押すところを置かない** |
| 出すもの | 会社の名前、いまの時刻、上部の数値、人の状態、業務の状態、業務の流れ、承認の滞留 |
| 文字の大きさ | **離れて読める大きさ**にする。画面の幅に応じて変える |
| 更新 | 自動（第6.7.9節）。**更新が途切れたら、そのことを画面に出す**。古い値を黙って映し続けない |
| 見える範囲 | 管理者ページと同じ（第6.7.10節）。**壁に映る以上、個人名の扱いは会社の設定に従う**（第6.7.4.1節） |
| 権限 | 管理者だけ。判定は API で行う（画面の出し分けは利便のため） |

**壁に映すなら、個人名の設定を見直す機会になる。** 会社の設定が「個人名で表示」のままだと、
通りかかった人にも誰が何をしているかが見える。
**この注意は、設定を変える場所（管理者ページの会社情報）に書く。**
ダッシュボードの上には書かない。毎日眺める画面に、めったに読まない注意を残さない。

#### 6.7.3 画面構成

```
│ ログイン中 6 人   実行中の業務 3 件   承認待ち 2 件   失敗 0 件            │

├──────────────────────────────────────┬─────────────────────────────────────┤

```

| 区画 | 内容 |
|---|---|
| 上部の数値 | ログイン中の人数、実行中の業務、承認待ち、失敗、今日の実行件数・費用・推計の削減時間 |
| 人の状態 | 利用者ごとの現在の状態（第6.7.4節） |
| 承認の滞留 | 誰の判断を待っているかと、待っている時間 |
| **業務の状態** | **業務エージェントの、いまの受け持ち**（第6.7.4.2節）。拡張機能と業務の分野ごとの**まとまり**で並べ、まとまりごとに絵を添える（第6.7.4.2.1節・第6.7.4.3節） |
| 業務の流れ | 実行中の業務と、その段階の進み具合（第6.7.5節） |
| 接続先 | Google の各サービスと、MCP で接続した外部システムの状態（第6.7.6節） |
| 出来事 | 直近の出来事を新しい順に流す（開始・完了・承認・失敗など）。**既定では畳む**（第6.7.3.1節） |
| 集計 | 期間を指定した推移のグラフ（第6.7.8節）。別のタブに置く |

##### 6.7.3.1 縦を使いすぎない

**この画面は「いまどうなっているか」を一目で見るための画面である。**
下まで送らないと全体が分からないなら、役目を果たしていない。

| 項目 | 規定 |
|---|---|
| 一目で見えること | **上部の数値・人の状態・業務の状態**は、開いた時点で見えていること |
| 更新の知らせ | **最終更新の時刻だけ**を片隅に小さく出す。「自動で更新します」といった説明は書かない。**更新が途切れたときだけ目立たせる** |
| 設定 | **めったに触らない設定を、毎日眺める画面に置かない**（見せ方の選択は会社の設定へ。第6.7.4.1節） |
| 畳むもの | **出来事**は既定で畳み、直近の数件だけを出す。押すと伸びる |
| 失敗 | 今日の失敗は**業務の流れとは別の囲み**にし、既定で畳む（第6.7.5.1節） |
| 空のとき | 「ありません」の 1 行で済ませる。空の囲みで場所を取らない |

#### 6.7.4 人の状態

利用者ごとに、**いま何をしているか**を 1 つの状態で示す。色と短い言葉で表す。

| 状態 | 判定 | 表示の例 |
|---|---|---|
| オフライン | ログイン状態が無い、または一定時間操作が無い | 灰色 |
| ログイン中（待機） | ログインしているが、下のいずれにも当たらない | 淡い色 |
| 秘書と会話中 | 直近に秘書へ依頼し、応答を待っているか、やり取りを続けている | 「秘書と会話中」 |
| 音声で会話中 | 音声の秘書（第10.5節）と接続している | 「音声で会話中」 |
| 業務を実行中 | 本人が依頼した業務が実行中である | 「議事録作成を実行中」 |
| 活動中 | 実行中の業務が、いまツールを呼んでいる | 「リサーチ中」「メールを確認中」など（第6.7.7節） |
| 承認の依頼あり | 本人が判断すべき承認・操作の確認が待っている | 「承認の依頼 2 件」 |

**あわせて表示するもの**

| 項目 | 内容 |
|---|---|
| 接続の経路 | 画面・音声・LINE（第14.6節）・外部アプリ（API）のどれから使っているか |
| 端末の種類 | パソコン・スマートフォン |
| 使っている業務 | いま実行中の業務の名前 |

**表示しないもの**（第6.7.10節）

| 項目 | 理由 |
|---|---|
| 秘書との会話の中身 | 不変則 I-10。管理者でも見られない |
| 業務の入力と成果物の中身 | 状態を見る画面であり、中身を見る画面ではない（第6.6.8節） |
| 接続元の場所（住所・IP から推定した地域） | 業務の把握に不要であり、働く場所の監視になる |

##### 6.7.4.1 実装の範囲と、状態の決め方（第 0.54.0 版）

**状態は既存の記録から組み立てる。** 人の状態のための新しい記録は持たない（第6.7.9節）。

| 状態 | 決め方 | 状態 |
|---|---|---|
| 承認の依頼あり | その人が判断できる承認・操作の確認がある（第9.2.3節の `canDecide`） | 実装する |
| 活動中 | その人の実行中の業務が、いまツールを呼んでいる。ツールの活動の表示名を出す（第6.7.7節） | 実装する |
| 業務を実行中 | その人が依頼した業務が待機・実行中 | 実装する |
| 秘書と会話中 | 直近 2 分に秘書へ依頼している（監査ログ `secretary.*`） | 実装する |
| ログイン中（待機） | 上に当たらず、直近 15 分に操作がある | 実装する |
| オフライン | ログイン状態が無いか、15 分より前から操作が無い | 実装する |
| 音声で会話中 | 音声の秘書との対話が開いている。監査ログ `secretary.voice` の始まり（`start`）があり、終わり（`end`）が無い。**60 分より前の始まりは数えない**（異常終了で終わりが残らなかった対話を、開いたままと見なさないため） | **実装する**（第 0.105.0 版） |

**あわせて表示するもの**のうち、接続の経路は**画面と外部アプリ（API）**を示す。音声と LINE は Phase 2 とする。
端末の種類は、ログイン状態に残る利用者エージェントから「パソコン」「スマートフォン」を判別する。

**表示の粒度（Q-64 で決定）**

| 設定 | 表示 | 既定 |
|---|---|---|
| 個人名 | 名前と状態、使っている業務 | **こちらを既定とする** |
| 人数と業務だけ | 状態ごとの人数と、動いている業務の名前。誰かは示さない | |

既定を個人名とするのは、この画面の最大の役割が**承認の滞留が誰の判断待ちかを示すこと**にあるためである（第6.7.5節）。

**選ぶ場所は、管理者ページの「会社情報」に置く。ダッシュボードの上には置かない。**
めったに触らない設定であり、毎日眺める画面の場所を取る理由がない（第6.7.3.1節）。
壁のモニターに映すときに見直すものなので、**注意書きも設定のそばに置く**（第6.7.2.1節）。

##### 6.7.4.2 業務の状態

**人だけでなく、業務エージェントの受け持ちも見せる。**

人の状態は「誰が動いているか」を示すが、**どの業務にどれだけ仕事が溜まっているか**は分からない。
管理者が知りたいのは「社内ナレッジ Q&A は空いているのか、議事録作成に詰まっているのか」である。

| 表示 | 内容 |
|---|---|
| 対象 | **その会社で使えるすべての業務**。動いていないものも出す（空いていることが分かる） |
| いまの受け持ち | 実行中・承認待ち・待ち行列の件数 |
| 待機 | いずれも 0 なら「待機」と示す |
| 今日 | 今日の実行の件数と、失敗の件数 |
| 並び | **忙しい順**（実行中 → 承認待ち → 待ち行列の合計）。同じなら今日の件数の多い順。まとまりの間も、まとまりの中も同じ |
| まとまり | 業務を 1 つずつ並べず、**拡張機能と業務の分野ごとのまとまり**で並べる（第6.7.4.2.1節。第 0.212.0 版） |
| 出さないもの | 依頼者・入力・成果物の中身（第6.7.10節） |

**「待機」を出すことに意味がある。** 動いているものだけを並べると、
使われていない業務があることに気づけない。導入した業務が誰にも使われていないのは、
管理者が知るべきことである（第22.3節）。

###### 6.7.4.2.1 業務のまとまり（第 0.212.0 版、ADR-0061）

**業務の数が増えても、並ぶ数を増やさない。** 名刺の取り込み・名刺の修正・まとめてのメールは、どれも「名刺管理」の仕事である。
管理者が一瞥で知りたいのは「名刺管理は動いているか」であり、中のどの業務かは、動いているときにだけ要る。

| 項目 | 規定 |
|---|---|
| まとまりの決め方 | **拡張機能の業務は、その拡張機能で 1 つ**（名刺管理・在庫管理・取り込んだスキルなど）。**公式の業務は分野（エージェント定義の `category`）で 1 つ**: メール・予定・会議・ブリーフ・資料・知識と調べもの |
| 人に決めさせない | まとまりは定義から決まる。**管理者に組み分けを作らせない**（ADR-0028。左のメニューのカテゴリーは本人の並べ方であり、ここには使わない） |
| 業務が 1 つだけのまとまり | まとまりにせず、これまでどおり業務 1 つの囲みで出す（「EvidenceMD の中に EvidenceMD」のような二重の名前を出さない） |
| まとまりの囲み | 名前・中の業務の数・まとめた受け持ち（実行中・承認待ち・待ち行列の合計。どれも 0 なら「待機」）・今日の件数と失敗の件数。絵は 1 つ（第6.7.4.3節） |
| 動いている業務 | **受け持ちのある業務と、今日失敗した業務だけを、囲みの中に名前と受け持ちで出す。** どこが動いているかを開かずに分かる |
| 中の業務をすべて見る | 囲みを開くと、待機のものを含めて中の業務がすべて並ぶ。**既定は閉じる**。掛け通しの画面（第6.7.2.1節）では開く操作を出さない |
| 分野の名前が無い業務 | 定義の `category` が上の分野に無い公式の業務は、業務 1 つの囲みで出す |

##### 6.7.4.3 業務エージェントの絵

**業務ごとに、ロボットの絵を添える。** 受け持ちがあるあいだだけ動かす。

数字と言葉だけを並べた一覧は、目で追わないと状態が分からない。
壁に掛けたモニター（第6.7.2.1節）では、**離れた場所から一瞥して「いま動いている」と分かる**必要がある。
動きは、そのための手がかりである。

| 項目 | 規定 |
|---|---|
| 絵 | 同梱の 50 枚（`packages/web/public/agents/agent01.png`〜`agent50.png`。第 0.140.1 版で 25 枚から増やした）。**同じ画風でそろえ、色だけを変える** |
| 割り当て | エージェント定義の `face`（1〜50）。**業務を 1 つ足すたびに、未使用の番号を 1 つ割り当てる** |
| まとまりの絵 | まとまり（第6.7.4.2.1節）は、中の業務のうち定義の順で最初の業務の絵を使う。受け持ちがあれば輪で囲む |
| 割り当てを書かない定義 | 拡張機能で入った業務は、ID から機械的に決める。絵は必ず出るが、他の業務と重なりうる。**絵の枚数を増やすと、決まる番号が一度だけ変わる**（第 0.140.1 版で 50 枚にしたとき、拡張機能の業務の絵が入れ替わった） |
| 色 | **待機でも色を落とさない。** 絵は色が身上であり、灰色にすると誰の絵かも分からなくなる |
| 受け持ちがあるとき | **絵を輪で囲む**（囲みの中を淡く塗る）。あわせて、絵をゆるやかに揺らし、輪の外側をもう 1 本が広がっていく |
| 待機のとき | **輪を出さず、動かさない**。絵はそのまま出す |
| 動きを減らす設定 | `prefers-reduced-motion` のときは動かさない。**輪は残す**（第6.9節） |
| 読み上げ | **絵は読み上げに渡さない。** 絵が伝えることは、すぐ横の文字がすべて書いている |
| 絵が無いとき | 絵の場所ごと詰め、文字だけを出す。**代わりの記号を置かない** |

**動いていることは、輪で示す。色の濃さでは示さない。**
色を落とす表し方も試したが、待機の業務が何の絵なのか分からなくなった。
絵は色で見分けるものであり、色は状態を表す場所ではない。
状態はすでに、囲みの左端の帯と、その横の「実行中」「待機」の文字が示している。
輪はそこへ、離れた場所からでも見える三つ目の手がかりを足す。

**動かしてよいのは、実際に動いているものだけである。**
何も起きていないのに動き続ける絵は、画面のどこを見ればよいかを分からなくする。
動きが状態を表すからこそ、状態が無いときは止める。

##### 6.7.4.4 人と秘書の組（第 0.105.0 版）

**人の状態は、本人と、その人に付く秘書を 1 組にして示す。**
M2Office では、利用者 1 人に専属の秘書が 1 人付き、業務は秘書が中で進める（第10章）。
本人がオフラインでも、秘書は定時実行や頼まれた業務を進めている。
本人と秘書の状態を 1 つにまとめると、「本人は席を外しているが、秘書は議事録を作っている」が読み取れない
（2026-09-25 に三浦さんが依頼）。

| 項目 | 規定 |
|---|---|
| 1 組の並び | 左に**本人**（プロフィール写真・名前・本人の状態）、右に**秘書**（秘書のアバター・秘書の名前・秘書の状態） |
| 本人の写真 | Google のプロフィール写真（第6.5.1.1節）。無ければ人の形のアイコン |
| 秘書のアバター | 本人が個人設定で選んだもの（第6.1.3節。同梱の絵か、上げた画像）。無ければ人の形のアイコン |
| 秘書の名前 | 本人が付けた名前（第6.5.3節）。付けていなければ「秘書」 |
| 秘書が動いているとき | **秘書のアバターを輪で囲む**（業務の絵と同じ手がかり。第6.7.4.3節）。動きを減らす設定では動かさず、輪は残す |
| 左端の帯の色 | 1 組全体の状態（第6.7.4節の強い順）で決める |
| 出す条件 | **個人名で表示する会社だけ**（第6.7.4.1節）。人数と業務だけの会社には、写真も秘書の名前も出さない |

**本人の状態**（強い順に見て、先に当たったものを採る）

| 状態 | 決め方 |
|---|---|
| 承認の依頼あり | 本人が判断できる承認・操作の確認がある（「承認の依頼 2 件」） |
| 音声で会話中 | 音声の秘書との対話が開いている（第6.7.4.1節） |
| 秘書と会話中 | 直近 2 分に秘書へ依頼し、ログインしている |
| ログイン中 | 直近 15 分に操作がある |
| オフライン | 上のいずれにも当たらない |

**秘書の状態**（強い順。秘書の状態は、本人がオフラインでも出す）

| 状態 | 決め方 | 表示の例 |
|---|---|---|
| 活動中 | 本人の業務が、いまツールを呼んでいる。活動の表示名を出す（第6.7.7節） | 「メールを確認中」 |
| 業務を実行中 | 本人が依頼した業務（画面・秘書・定時実行・外部アプリのどれからでも）が実行中 | 「議事録作成・共有を実行中（ほか 1 件）」 |
| 承認待ち | 本人の業務が、承認・操作の確認を待っている（誰の判断かは問わない） | 「議事録作成・共有の承認を待っています」 |
| 順番待ち | 本人の業務が、実行の順番を待っている | 「議事録作成・共有の順番待ち」 |
| 音声で応対中 | 音声の対話が開いている | 「音声で応対中」 |
| 応対中 | 直近 2 分に本人から依頼を受けている | 「応対中」 |
| 待機 | いずれにも当たらない | 「待機」 |

**写真とアバターを取り出す口**: 管理者のダッシュボードの中に、利用者ごとの写真と秘書のアバターを返す口を置く。
**その会社の、停止していない利用者のものだけ**を返し、個人名で表示する会社でなければ返さない。
秘書のアバターは、**本人が個人設定に登録した画像だけ**を返す（ファイルの ID を受け取らない）。
種類を推測させず、何も読み込ませない（第6.5.1.1節と同じ）。

**新しい記録は持たない**（第6.7.9節）。秘書の状態も、実行・承認・監査ログから、そのつど組み立てる。
本人の見え方（第6.7.10節 規定 4）には、写真・秘書の名前・秘書の状態が示されることを加える。

#### 6.7.5 業務の流れ

実行中の業務を、**定義の段階を並べた流れ**として表示し、いまどこにいるかを示す。

| 表示 | 内容 |
|---|---|
| 段階 | エージェント定義のステップを順に並べる（例: 取得 → 作成 → 承認 → 共有） |
| 現在地 | 実行中の段階を強調し、その段階で行っている活動（第6.7.7節）を添える |
| 止まっている所 | 承認待ち・操作の確認待ちは目立つ色にし、**誰の判断を待っているか**と経過時間を示す |
| 起動の経路 | メニュー・秘書・定時実行・API |
| 依頼者 | 誰の依頼か |


承認の滞留が一目で分かることが、この区画の最大の役割である。
業務が止まる原因の多くは、システムではなく**人の判断待ち**だからである。

##### 6.7.5.1 失敗は、流れと混ぜない

**失敗した業務を「業務の流れ」の中に並べない。別の囲みにする。**

「業務の流れ」は**いま動いているもの**を見る区画である。そこに終わったもの（失敗）が混ざると、
何時間も前のものが並び続け、**いま動いているのかどうかが読み取れない**
（2026-09-24 に実機で確認。21 時間前の失敗が「業務の流れ」に残っていた）。

| 項目 | 規定 |
|---|---|
| 置き場所 | 「今日、失敗した業務」として**別の囲み**に出す |
| 既定 | **畳む。** 件数だけを出し、押すと開く |
| 中身 | 業務の名前・依頼者・失敗した時刻・**理由の要約** |
| 範囲 | **今日（日本時間の 0 時以降）の分だけ。** 日が変わると消える。この旨を画面に書く |
| 消せること | 管理者が確認したら消せる（**未実装**。第24.4.3節） |

**「日が変わると消える」と画面に書く。** 書かないと、いつまで残るのかが分からない。

#### 6.7.6 接続先

M2Office を中心に、接続している外部のサービスを並べ、状態を示す。

| 対象 | 状態の判定 |
|---|---|
| Google の各サービス（Gmail・カレンダー・Tasks・Chat・ドライブ・Meet） | 直近の呼び出しの成否と応答時間、認可の有効期限 |
| MCP で接続した外部システム（freee など。第14.4節） | 同上。切断を検知したら異常とする |
| LLM | 応答時間と失敗率 |

いま呼び出しが行われている接続は、**動いていることが分かる表示**（線が流れるなど）にする。
状態は「正常」「遅延」「失敗」「未接続」の 4 つとする。

#### 6.7.7 活動の表し方

ツールの名前（`knowledge.search` など）をそのまま見せず、**業務の言葉**で表す。
各ツールに「活動の表示名」を持たせ、ダッシュボードはそれを表示する。

| ツール | 活動の表示名 |
|---|---|
| `knowledge.search` | 社内の知識を調べています（リサーチ中） |
| `gmail.list`・`gmail.get` | メールを確認しています |
| `gmail.create_draft` | 返信の下書きを作っています |
| `calendar.freebusy` | 予定の空きを調べています |
| `calendar.create` | 予定を登録しています |
| `document.create`・`docx.render`・`sheet.render` | 資料を作成しています |
| `web.research` | Web で調べています（リサーチ中） |
| `slides.template` | スライドのテンプレートを確かめています |
| `slides.create` | スライドを作成しています |
| `pdf.extract`・`sheet.read` | 書類を読んでいます |
| `tasks.create` | ToDo を登録しています |
| `chat.post` | チャットへ投稿しています |
| `notification.send` | お知らせを届けています |

**活動の表示名はツールの定義に含める。** 拡張機能（第12章）が追加するツールも、
表示名を持たなければ審査を通さない（第12.5節）。表示名が無い場合は「処理しています」と表示する。

#### 6.7.8 集計

期間を指定して推移を見るためのタブ。リアルタイムの画面とは分ける。

| 区分 | 項目 |
|---|---|
| 稼働 | 本日／今月の実行件数、成功率、平均所要時間、エージェント別の利用状況、時間帯別の利用 |
| 秘書 | よく使われる依頼の種類、層 1〜3 の比率（第10.9節） |
| 滞留 | 承認待ちの件数と最長待ち時間、失敗して未対応の実行 |
| 効果 | 削減時間の推計、処理件数の推移、エージェント別の貢献 |
| 知識 | 組織知識の件数と増加、参照回数、秘書が加えた件数 |
| コスト | トークン消費と費用、上限に対する消化率、上位消費エージェント |
| 健全性 | Google 連携の状態、直近のエラー、知識同期の状態 |

**集計は業務と会社全体の単位で示し、個人ごとの勤務時間の集計には使わない**（第6.7.10節）。

#### 6.7.9 リアルタイム性の実現

| 項目 | 方針 |
|---|---|
| 更新の目標 | 状態の変化から**数秒以内**に画面へ反映する |
| 方式 | API からの**サーバー送信イベント（SSE）**で変化を送る。画面は受け取った差分で表示を更新する（第8.4節） |
| 状態の出どころ | ログイン状態の最終操作時刻、秘書への依頼、実行とステップの状態、ツールの呼び出し、接続の成否。**いずれも既存の記録から組み立てる**（監査ログ・実行の記録） |
| 状態の保持 | 「いまの状態」は記憶上に持ち、長期には保存しない。後から遡るのは監査ログと実行の記録である |
| 負荷 | 1 テナント 10 名程度を想定する（第2.1節）。変化の通知はテナント単位にまとめる |
| テナント境界 | 送る内容はそのテナントのものだけ。接続時に利用者とロールを確かめる（不変則 I-2） |
| 接続が切れた場合 | 自動で接続し直し、そのあいだに起きた変化は最新の状態で置き換える |

**実装（第 0.54.0 版、ADR-0013）**

| 項目 | 内容 |
|---|---|
| 経路 | `GET /v1/admin/dashboard/stream`（`text/event-stream`）。管理者だけが開ける |
| 送る内容 | 「いま」の画面（第6.7.3節）と同じ中身。**変わったときだけ**送る |
| 変化の見つけ方 | API が 2 秒ごとに状態を組み立て、前回と違えば送る。状態は記憶上で比べるだけで、保存しない |
| 心拍 | 15 秒ごとにコメント行を送り、経路の途中で切られることを防ぐ |
| 画面の受け方 | `fetch` の読み取りで受ける（`EventSource` は認証のヘッダーを付けられないため）。切れたら少し待って開き直し、そのあいだの変化は次に届く全体で置き換える |
| 受けられないとき | 一定間隔の取り直し（5 秒）に戻す。画面には更新の仕方を示す |
| 停止中の会社 | 開けない（第23.8.6節。閲覧のうち、続けて開き続ける経路は止める） |

#### 6.7.10 見える範囲と、働く人への配慮

**このダッシュボードは、業務の流れを管理するためのものであり、従業員を監視するためのものではない。**
リアルタイムに人の状態が見える仕組みは、使い方を誤れば監視のツールになる。

| # | 規定 |
|---|---|
| 1 | **中身は見せない。** 表示は状態・業務の名前・活動の表示名までとする（不変則 I-10）。個人名で表示する会社では、あわせてプロフィール写真と、秘書の名前・アバター・状態を出す（第6.7.4.4節） |
| 2 | **働く場所を推定しない。** 接続元の住所や地域は表示しない |
| 3 | **個人の勤務時間の集計に使わない。** 「誰が何時間ログインしていたか」のような個人別の集計・出力は設けない |
| 4 | **本人に知らせる。** 個人設定（第6.5節）に「管理者のダッシュボードで、あなたはこう表示されています」を示す。いまの自分の状態と、示される項目・示されない項目を並べる（第 0.54.0 版で実装） |
| 5 | **会社として告知する。** 導入時に、表示される範囲を従業員へ知らせることを管理者の手順に含める（第22.1節）。**本人の同意の取得までは求めない**（Q-65 で決定）。中身を見せず、履歴も残さず、本人が自分の見え方を確かめられるため |
| 6 | 表示の粒度を会社ごとに選べるようにする。個人名で表示するか、人数と業務だけを表示するか（Q-64） |

**個人の状態の履歴を保存しない。** いまの状態は記憶上に持ち、
後から遡れるのは監査ログ（誰が何を実行したか）と実行の記録だけである。

#### 6.7.11 段階的な構築

| フェーズ | 作るもの |
|---|---|
| Phase 1 | 上部の数値、業務の流れ、承認の滞留、出来事、集計（削減時間を含む。第24.1節の完了条件 5）。更新は一定間隔（5 秒）の取り直しで行う |
| Phase 1 後半 | 人の状態（ログイン中・秘書と会話中・業務を実行中・活動中）、SSE による自動更新、活動の表示名 ― **第 0.54.0 版で実装**（音声・LINE の経路を除く） |
| Phase 1 後半（第 0.105.0 版） | 本人と秘書の 1 組（写真・アバター・秘書の状態）と、音声の経路の表示（第6.7.4.4節） |
| Phase 2 | 接続先（MCP を含む）、LINE の経路の表示 |

#### 6.7.12 削減時間の推計

**削減時間 = 完了した実行の件数 × その業務を手作業で行った場合の標準所要時間**

| 項目 | 規定 |
|---|---|
| 標準所要時間 | エージェントごとに持つ「手作業なら 1 件に何分かかるか」の値。公式エージェントには既定値を付け、**会社ごとに管理者が変えられる**（第6.6.5節） |
| 数える実行 | **最後まで完了したものだけ**。失敗・却下・途中で終了（対象が 0 件だったなど）は 0 分とする |
| 記録 | 実行が完了した時点の値を実行の記録に残す（第19.1節 `run` の削減時間推計）。後から標準所要時間を変えても、過去の実行の値は変わらない |
| 表示 | 必ず「推計」と明記する。実測ではないため |

**公式エージェントの既定値（推奨。要確認 Q-66）**

| エージェント | 標準所要時間 | 想定している手作業 |
|---|---|---|
| AG-01 メール整理・下書き作成 | 15 分 | 未読メールを読み分け、返信が要るものに下書きを書く |
| AG-02 議事録作成・共有 | 30 分 | 記録を読み返して議事録にまとめ、ToDo を起票して共有する |
| AG-03 日程調整 | 15 分 | 参加者の空きを確かめ、候補を出して招待を送る |
| AG-04 社内ナレッジ Q&A | 10 分 | 規程を探して該当箇所を読み、答える（または担当者に聞く） |
| AG-05 週次ブリーフ | 20 分 | 予定・ToDo・承認待ち・受信箱を見て、今週の優先を整理する |

**過大に見せない。** 推計を大きく見せたくなる誘惑はあるが、実態と離れた数字は
導入企業の信頼を損なう。既定値は控えめに置き、実態に合わせて会社が調整する前提とする。

### 6.8 UX 原則

| # | 原則 |
|---|---|
| u1 | 専門用語を出さない。「プロンプト」「トークン」「RAG」を一般利用者向け画面に表示しない |
| u2 | 提案には必ず根拠と変更差分を添える（秘書の答えは秘書のキャンバス、業務の実行は実行の詳細） |
| u3 | 承認は 1 画面・数クリックで完了できる |
| u4 | 失敗時は「何が起きて、次に何をすべきか」を平易な日本語で伝える |
| u5 | 実行中も待たせない。進捗を可視化し、他の作業へ移れる |
| u6 | 既定値のままで動く。設定は任意項目として後から詰められる |
| u7 | **使える業務を先に見せる**。空の画面や自由入力欄から始めない |
| u8 | **困ったら秘書に聞けばよい**状態にする。マニュアルを読ませない |
| u9 | 音声は任意。音声でしかできない操作を作らない |
| u11 | **画面に説明文を常に出さない**（第 0.115.0 版）。1 回見れば分かる案内、空の欄の説明、画面の使い方の段落は置かない。場所は中身に使う。分からなければ秘書に聞けばよい（u8）。**人に一覧や規則を作らせない**（言い換えの表など）。人なら想像がつくことは秘書が考える |
| u10 | **よく使う操作は、キーボードから手を離さずに終えられる**（第6.11節）。マウスでしかできない操作を、よく使う位置に置かない |

u7 は調査データに基づく。活用していない理由の最多が
「活用する業務がイメージできていない」63.4% であるため、
**初回ログイン時に空のチャット画面を見せることは設計上の誤り**である。
左ペインに業務名の付いたカードが並び、秘書が「何かお手伝いしましょうか」と待っている状態から始める。

### 6.10 ヘルプと案内

**この節で決めること**: 初めて使う人が迷わずに使い始め、困ったときにその場で解決できる仕組み。
業務（エージェント）や拡張機能が増えても、ヘルプが追いつく作り方。

#### 6.10.1 方針

**読ませるマニュアルを作るのではなく、その場で・その業務について・秘書が答える。**
原則 u8（困ったら秘書に聞けばよい）と第22.3節（マニュアルは最小限）を、仕組みとして実現する。

| # | 方針 | 理由 |
|---|---|---|
| h1 | **いま見ている画面・いま使おうとしている業務の説明を、その場に出す** | 別の画面のマニュアルを探させると、そこで離脱する |
| h2 | **秘書に聞けば答えが返る**。答えにはヘルプの出典を添える | 利用者は「どこに書いてあるか」を知らなくてよい |
| h3 | **業務のヘルプはエージェント定義から自動で作る** | 業務が増えても、書き忘れ・書き遅れが起きない |
| h4 | **拡張機能にはヘルプを必須とする** | 第三者の業務だけ説明が無い、という状態を作らない |
| h5 | **システムの使い方と、会社の決まりを混ぜない** | 「承認のしかた」（使い方）と「経費は部長承認」（社内規程）は出どころが違う |
| h6 | **一覧して読める場所も用意する**。ただし読まなくても使えることを前提とする | 管理者や、じっくり知りたい人のため |

#### 6.10.2 ヘルプの 5 つの層

| 層 | いつ | 何を | 誰に |
|---|---|---|---|
| **1. 初回の案内** | 最初のログイン、管理者の初期設定 | 画面の見方の短い案内、初期設定の手順 | 全員／管理者 |
| **2. その場の説明** | 各画面・各入力項目・各業務のカード | その場所で何ができるか、何が起きるか | 全員 |
| **3. 秘書に聞く** | 「どうやって〜？」「これは何をする？」と聞いたとき | ヘルプの記事から答える。できる業務ならその場で実行を提案する | 全員 |
| **4. ヘルプセンター** | 自分で調べたいとき | 記事の一覧と検索 | 全員（役割で出し分け） |
| **5. 問い合わせ** | 上で解決しないとき | 社内の管理者へ。管理者から運営のサポートへ | 全員／管理者 |

#### 6.10.3 初回の案内

**従業員の初回ログイン**

| 段階 | 見せるもの |
|---|---|
| 1 | 「左に使える業務が並んでいます」。業務のカードを 1 つ示す |
| 2 | 「下の秘書に話しかければ、何でも取り次ぎます」。試しの一言の例を示す（「今日の予定は？」） |
| 3 | 「社外に出るものだけ、承認トレイに届きます」 |

- 3 段階まで、1 分以内で終わる長さにする。**いつでも飛ばせて、いつでも見直せる**（ヘルプセンターから）
- 案内を見たかどうかは本人の設定として記録し、次回からは出さない

**管理者の初期設定**

第22.1節の導入の流れを、管理者ページの**チェックリスト**として示す。すべて済むと出さない。

| # | 項目 | 済んだことの判定 |
|---|---|---|
| 1 | 会社情報を入力する | 正式な会社名が入っている |
| 2 | Google Workspace を接続する | 接続口が Google につながっている |
| 3 | 使う業務を選ぶ | 業務と承認の画面を一度保存した |
| 4 | 就業規則などの規程を登録する | 組織知識が 1 件以上ある |
| 5 | 同僚を招待する | 利用者が 2 人以上いる |
| 6 | 従業員へ、ダッシュボードで表示される範囲を知らせる（第6.7.10節） | 管理者が「知らせた」と記録した |

**知識が空のまま使い始めると、秘書は「分かりません」としか答えられない**（第22.3節）。
項目 4 を目立たせる。

##### 6.10.3.1 チェックリストの置き場所

**ダッシュボードの上には置かない。設定の 1 項目として置く。**

初期設定は**一度きり**の作業である。ダッシュボードは**毎日見る画面**である。
一度きりのものを毎日の画面の先頭に広げると、**毎日見たいもの（いまの状況）が下へ押し下げられる**
（2026-09-24 に実機で確認）。

| 項目 | 規定 |
|---|---|
| 置き場所 | 左ペインの「設定」の区分の**いちばん下**。ダッシュボードには出さない |
| 進み具合 | **左ペインの項目に「2 / 6」を出す。** 開かなくても、残りがあることが分かる |
| 済んだら | 項目ごと**出さない**。左ペインから消える |
| 順番 | 設定の項目は上から順に済ませれば使い始められる並びである（第6.6節）。チェックリストは**その並びをたどる案内**なので、設定の最後に置く |

**進み具合を左ペインに出すのが要である。** 画面から追い出しただけでは、
初期設定が途中であることに気づけなくなる。

#### 6.10.4 その場の説明

| 場所 | 出すもの |
|---|---|
| 業務の画面 | **この業務でできること・できないこと、承認が入る場所と誰が承認するか、実行例**（第6.10.5節）。**題名の「？」から出す。画面には広げない**（第6.10.5.1節） |
| 入力項目 | 項目の意味と、入力の例。入力欄のそばに短く |
| 承認の画面 | 何を確認すべきか。承認すると次に何が起きるか |
| 空の画面 | 「まだありません」で終わらせず、**次にすべきこと**を示す（例: 「規程を登録すると、秘書が答えられるようになります」） |
| エラー | 何が起きて、次に何をすればよいか（原則 u4）。解決しなければ問い合わせへの道を示し、**要求の ID を添える**（開発規約 第7.4節） |
| 管理者ページの設定 | その設定を変えると何が変わるか。とくに承認・停止・無効化のように業務に影響するもの |

説明は短くし、詳しくはヘルプセンターの記事へつなぐ。

##### 6.10.4.1 説明より、例を置く

**読ませるより、見せる。**

説明の文を足すほど画面は重くなり、読まれなくなる。**入力欄に例を薄く置けば、
何を書けばよいかは一目で伝わる。** 文を 1 行足す前に、例で示せないかを考える。

| やめること | 代わりに |
|---|---|
| 「必要な項目を入力して実行します」のような、**見れば分かることを書く** | 何も書かない |
| ボタンに「〜する」と付ける（「実行する」「保存する」） | **動詞だけ**（「実行」「保存」） |
| 入力欄の下に、書き方の説明を長く添える | **入力欄の中に例を薄く置く**（`例: 夏季休暇は何日ありますか`） |
| 見出しと同じことを、その下の行でもう一度言う | 見出しだけにする |

| 項目 | 規定 |
|---|---|
| 例の出どころ | **エージェント定義の `inputs` の各項目**（JSON Schema の `examples`）。画面に直書きしない |
| 例の書き方 | **実際に使えるものを書く。** 「例: テキスト」のような中身の無い例を置かない |
| 例が無い項目 | 何も出さない。**それらしい例を作らない**（不変則 I-6 と同じ考え方） |
| 補足が要るとき | 短い注記を 1 行だけ。長くなるならヘルプの記事へ送る |

**任意の日付の入力は、チェックボックスとカレンダーで出す（第 0.117.1 版）。** 定義の `inputs` の項目が `format: date` で必須でないとき、
画面は項目の題名（例:「対象期間を指定」）のチェックボックスを出し、**既定ではチェックしない**（日付は渡さない）。
チェックすると日付を選ぶカレンダーが開き、選んだ日付（`YYYY-MM-DD`）を渡す。チェックを外すと日付は渡さない。
業務ごとに画面を作らず、定義から組み立てる決まりのまま行う。必須の日付は、チェックボックスを付けずにカレンダーだけを出す。
AG-01 メール整理・下書き作成の「対象期間を指定」（その日以降の未読に絞る。第9.5.1節）がこれに当たる（2026-09-26 に三浦さんが指定）。

**ファイルの入力は、ファイルを選ぶ欄で出す（第 0.147.1 版）。** 定義の `inputs` の項目が `format: file` のとき（公式の業務の `fileId`、スキルの「ファイル」の欄。第12.12.3節）、
画面は文字の欄ではなく、ファイルを選ぶ欄を出す。以前は文字の欄のままで、ファイルの ID を打ち込むしかなく、メニューから開いた契約書チェック・議事録作成・文書の作成にファイルを渡せなかった（2026-09-28 に三浦さんが指摘）。

| 項目 | 規定 |
|---|---|
| 渡し方 | 「ファイルを選ぶ」で選ぶか、欄にドラッグする |
| 上げる時 | 選んだらすぐに上げる（第9.4.1節の受け取り）。欄にはファイルの名前と「外す」を出し、業務にはファイルの ID を渡す |
| 形式と大きさ | 秘書に渡すときと同じ（PDF・Word・Excel・CSV・画像、10 MB まで。拡張子と中身の先頭で確かめる）。合わないときは、その場で理由を出す |
| 必須 | 必須のファイルの欄が空なら「実行」を押せない |
| 秘書から開いたとき | 秘書に渡したファイル（第10.10.3節）は、はじめから入っている（名前を出す） |

**例は「入力の見本」であって、「実行の見本」ではない。**
実行の見本（`help.examples`。第9.2.5節）は、押すと全項目が埋まるものである。両者を混同しない。

##### 6.10.4.2 操作の結果を知らせる

**押したら、どうなったかを必ず返す。**

保存のボタンと、結果の文が離れていると、押した人は保存できたのかが分からない
（2026-09-24 に実機で確認。個人設定の「秘書」で、保存しても何も起きていないように見えた）。

| 項目 | 規定 |
|---|---|
| 出す場所 | **押したボタンのすぐ横。** 画面の隅に出さない。目線がボタンから離れると気づけない |
| うまくいったとき | 「保存しました」のように**言い切る**。数秒で消える |
| 失敗したとき | **自分では消えない。** 読んで、直してもらう必要がある |
| 押している間 | ボタンを止め、「保存しています…」にする。二重に保存させない |
| 文言 | 何が起きたかを書く。「処理が完了しました」のような中身の無い文にしない |
| 読み上げ | 読み上げの対象にする（`aria-live`）。画面を見ていない人にも届く |

**「押したが何も起きない」を作らない。** 変化が画面に出ない操作ほど、知らせが要る。

**画面の隅に出す方式（トースト）は採らない。** 一度作って試したが、
保存のボタンから目線が遠く、気づけなかった（2026-09-24）。
**押した場所で返すのが、いちばん確かである。**

##### 6.10.4.3 社内の文書への参照を、画面に出さない

**「仕様書 第6.1.3節」のような書き方を、利用者に見せない。**

コードの説明には要るが、**画面に出ても利用者には何のことか分からない**
（2026-09-24 に実機で確認。個人設定のアバターの説明に出ていた）。

| 対象 | 扱い |
|---|---|
| 画面に出る文・`title`・`placeholder`・読み上げの文言 | **仕様書・開発規約・不変則・ADR への参照を書かない** |
| コードのコメント・JSDoc | これまでどおり書く。**根拠をたどれることが大事である** |
| 確かめ方 | `npm test`（`scripts/check-web-components.mjs`）が機械的に見つける |

##### 6.10.4.4 「？」の置き方（第 0.106.0 版）

**1 つの画面に「？」は 1 つ。題名の横に置き、その画面のことを説明する。**

管理者ページで、題名の「？」が区分全体の説明（例: 「知識」の画面で規程の登録の説明）を出し、
囲みの中に見出しの無い「？」がもう 1 つあって、そちらが画面そのもの（例: 言い換え）を説明していた。
どちらを押せばよいか分からず、題名の「？」は開いている画面と合わない（2026-09-25 に三浦さんが指摘）。

| 項目 | 規定 |
|---|---|
| 数 | **1 画面に 1 つ**。題名（`区分 › 小分け`）の横に置く |
| 中身 | **開いている小分けの説明**。区分全体の説明を、すべての小分けで使い回さない |
| 開く記事 | その小分けを扱う記事。無ければ区分の記事 |
| 囲みの中 | **見出しの無い「？」を置かない**。囲みに見出しがあり、その囲みだけの説明が要るときに限り、見出しの横に置く（例: ダッシュボードの「人の状態」） |
| 文の途中 | 文の途中に「？」を挟まない。説明は題名の「？」へまとめる |
| 記事の無い画面 | 「？」を置かない。関係の薄い記事へつながない |

#### 6.10.5 業務のヘルプは定義から作る

**業務ごとのヘルプの大部分は、エージェント定義から自動で組み立てる。**
人が書く説明は、定義から読み取れない補足だけにする。

| ヘルプの項目 | 出どころ |
|---|---|
| 業務の名前と概要 | 定義の `name`・`description` |
| 入力するもの | 定義の `inputs`（各項目の `title`） |
| 進み方 | 定義の各ステップの表示名（第9.2.4節）。例: 取得 → 作成 → 承認 → 共有 |
| 承認が入る場所と承認者 | 承認ステップと `approver`（第9.2.3節）。社内への書き込みの確認は会社の自動化ポリシー（第9.4節）から |
| **この業務がすること** | 定義が使うツールの「すること」の説明から作る（例: 「メールの下書きを作ります。送信はしません」） |
| 定時実行できるか | 定時実行の設定の有無 |
| 実行例 | 定義の `help.examples`。無ければ `evals` の入力から作る |
| 補足・よくある質問 | 定義の `help`（第9.2.5節） |
| 会社の補足 | 管理者が書いた社内向けの補足（第6.10.7節） |

**「すること」はツールの説明から載せる。** 送るかどうかは、ツールの説明（「送信はしません」など）と「承認が入る場所」で分かる。
**どの業務にも同じになる決まり文句（「社外へ送ることはありません」「あなたの権限を超えません」など）は、業務ごとに並べない**（第 0.130.0 版。三浦さんの指摘: すべての説明に同じ文が入り冗長）。
M2Office 全体で守ることは、ヘルプの「承認のしかた」などに一度だけ書く。
各ツールは、活動の表示名（第6.7.7節）に加えて、**すること**の説明を定義に持つ。

| ツール | すること（ヘルプの文言） |
|---|---|
| `gmail.create_draft` | 返信の下書きを作ります。**送信はしません** |
| `chat.post` | チャットへ投稿します。**必ず承認のあとに行います** |
| `calendar.create` | 予定を登録し、参加者を招待します。**必ず承認のあとに行います** |
| `tasks.create` | ToDo を登録します。会社の設定により、登録の前に確認を求めます |
| `knowledge.search` | 社内の知識を調べます。区画の外の人には区画内の文書を見せません |

##### 6.10.5.1 説明の出し方

**説明は、画面に広げたままにしない。題名の「？」を押したときだけ出す。**

説明は**一度読めば済む**。毎回、入力欄の上に置くと、繰り返し使う人にとっては
ただ入力欄を下へ押し下げるだけのものになる。

| 項目 | 規定 |
|---|---|
| 既定 | **出さない。** 業務の題名の右に「？」だけを置く |
| 押したとき | 説明をポップアップで出す（第6.10.4節の「その場の説明」と同じ作り） |
| 閉じ方 | もう一度「？」を押す、外を押す、Esc を押す。**どれでも閉じる** |
| 中身 | すること・しないこと、進み方、承認、実行例、注意点、よくある質問。**拡張機能の業務なら、最後に拡張機能の名前と提供者**（第 0.118.1 版。入力の画面には出さない。三浦さんの指摘）。**スキルの業務は、書き手の `HELP.md` を本文にし、「すること」と「進み方」は出さない**（第12.12.4節。第 0.120.0 版） |
| 実行例 | 押すと入力欄に入り、**ポップアップは閉じる**。すぐ実行に移れる |
| 高さ | 画面に収まる高さに抑え、あふれる分は中で送る |

**入力欄は、画面を開いたらすぐそこにあること。** これが業務の画面の本題である。

#### 6.10.6 秘書に聞く（使い方の質問）

| 項目 | 方針 |
|---|---|
| 対象の質問 | 「どうやって〜？」「〜はできる？」「この業務は何をする？」「承認はどこで？」のような使い方の質問 |
| 答えの材料 | **ヘルプの記事**（公式・拡張機能・会社の補足）。組織知識（社内規程）とは別に検索する（方針 h5） |
| 出典 | 答えには参照した記事を添え、押せばその記事を開ける |
| 実行への橋渡し | 質問の対象が使える業務なら、「実行してみますか」と提案する（第10.8節） |
| 記事の探し方 | 言葉の取り出しと点数は組織知識の検索（第11.7.3節）と同じものを使い、題名に当たる言葉を重く数える。長い言葉に含まれる短い言葉（「定時実行」の「定時」）は 1 つにまとめて数える。**題名に言葉が 1 つも当たらない記事は、2 つ以上の言葉をすべて本文で満たすときだけ返す**。本文の例に「有給」とあるだけの記事を、社内規程の質問に返さないため。言い換え（第11.7.7節）は使わない |
| 分からない場合 | 推測で答えない。「ヘルプに見当たりません」と伝え、問い合わせへの道を示す |
| 権限 | 本人の役割で見られる記事だけを材料にする。管理者向けの記事を一般の利用者に答えない |

**使い方の質問と社内規程の質問を取り違えない。**
「経費はどう申請する？」は、M2Office の使い方ではなく社内規程の質問である。
秘書は両方を検索し、どちらの答えかを明示する（「社内の経費規程によると…」「M2Office では…」）。

#### 6.10.7 ヘルプセンター

左のメニューの「ヘルプ」から開く（ワークスペース・管理者ページとも）。

**ワークスペースのヘルプと管理者ページのヘルプで、出す記事を分ける**（第 0.188.0 版。三浦さんの指摘: 管理者向けは管理者ページだけでよい）。
業務が増えても探せるよう、**左に区分の木（開け閉めできる目次）、右に本文**を置く。

| 区分 | 内容 | 出す所 |
|---|---|---|
| はじめに | 画面の見方、秘書の使い方、承認の流れ、初回の案内の見直し | ワークスペース |
| 業務 | 業務の区分（名刺管理・在庫管理・人事・給与・店頭サイネージなど）ごとに、使い方の要点の記事と**業務のマニュアルの章**をまとめる（第6.10.7.3節）。**会社で入れていない・利用範囲の外の業務（内蔵の拡張）の要点の記事とマニュアルは出さない**（第 0.190.0 版）。続けて、使える業務エージェントごとのページ（第6.10.5節。**有効な業務だけを出す**） | ワークスペース |
| よくある質問 | 「勝手に送られない？」「間違えたら？」「誰に見られる？」など | ワークスペース |
| 更新情報 | 新しくできるようになったこと、変わったこと。平易な言葉で。新しい順。はじめは閉じておく | ワークスペース（全員向け）・管理者ページ（管理者向け） |
| 管理者向け | はじめに行う設定・設定（業務と承認・ユーザー・接続・拡張機能・知識など）・記録（ダッシュボード・利用状況・実行・監査ログ）に分ける | **管理者ページだけ** |
| 用語・問い合わせ | 画面に出てくる言葉の説明と、社内の管理者（管理者には運営のサポート）の窓口。**区分の木の下に小さな入口として置き、場所を取らない** | 両方 |

| 項目 | 規定 |
|---|---|
| 区分の木 | 区分を開け閉めできる。開いている記事を含む区分は開いておく。狭い画面では、木と本文を切り替える（記事から「目次」で木へ戻る） |
| すべて開く・すべて閉じる | 木の上に、**すべての区分を開く**・**すべて閉じる**の 2 つの小さなボタンを置く（第 0.215.0 版。三浦さんの依頼）。閉じても、開いている記事は本文に出したまま |
| 前の状態に戻す | **開いた区分と、開いていた記事を端末に覚えておき、ヘルプを開き直すと前の状態で開く**（第 0.215.0 版。ほかの作業をしてから戻っても、同じ所から続けられる）。ワークスペースと管理者ページで別々に覚える。記事を指定して開いたとき（画面の「？」・記事の URL）はその記事を開き、木はその記事を含む区分を開き足す。「目次」で戻ったら、次は目次から開く。覚えるのはこの端末のブラウザだけで、サーバーには送らない（端末を替えたら既定の形で開く）。覚えた記事が無くなっていたら目次を開く |
| はじめの形 | 覚えたものが無いときは、「はじめに」「業務」「よくある質問」と管理者向けの区分を開き、業務の区分ごとの枝と「更新情報」は閉じておく |
| 探す | 木の上の検索は、その画面で出す記事の中から探す（ワークスペースで管理者向けの記事を出さない） |
| 画面の「？」 | 記事の ID で開く。出す所の違いに関わらず、本人の役割で見られる記事なら開ける |
| 何も開いていないとき | 本文の側に「はじめに」（管理者ページでは管理者向け）の記事を並べる。説明の文は常には出さない（原則 u11） |

**会社の補足**: 管理者は業務ごとに、社内向けの補足を書ける（例: 「当社では議事録の共有先は必ず部署のスペースにする」）。
業務のページと、秘書の答えに添えて表示する。
**自社の書き方（第15.2.1節）とは別物である。** 自社の書き方は業務の文面に反映され、
会社の補足は人が読む説明にとどまる。

##### 6.10.7.1 更新情報は、使い方の案内より下に出す

**更新情報は「いつ何が変わったか」の記録であり、使い方の案内ではない。**

更新情報の題名には業務の言葉が入る（例:「秘書と会話できるようになりました」）。
そのまま同じ重みで並べると、**「秘書の使い方を教えて」で使い方の記事に勝ってしまう**
（2026-09-24 に、v0.3.0 の記事を足した時点で実際に起きた）。
**版を重ねるほど更新情報は増えるため、放っておくと案内が押し出される。**

| 項目 | 規定 |
|---|---|
| 並べ方 | 更新情報は**重みを下げて**並べる。消しはしない |
| 下げ方 | **版の数によらず一定**にする。増えるほど下げる、といった仕組みにしない |
| 探せること | 更新情報の中身で探せば出る（「会話できるようになりました」など） |
| 一覧 | ヘルプセンターの区分「更新情報」から、いつでも新しい順に読める |

##### 6.10.7.2 ヘルプから、元の画面へ戻れる

**調べ終えたら、調べる前にいた場所へ戻せる。**

画面の「？」から「詳しく見る」を押すと、ヘルプセンターへ移る。
そこから**元いた画面へ戻る道が無いと、やり方を調べたあとに迷子になる**
（2026-09-24 に実機で確認）。

| 項目 | 規定 |
|---|---|
| 戻り先 | **ヘルプを開く直前にいた画面。** その画面の中で見ていた場所（区分・小分け）も含む |
| 出し方 | ヘルプの題名の上に「← ○○へ戻る」。**どこへ戻るのかを名前で書く** |
| 記事から一覧へ | 左の区分の木がいつも見えるので、木から別の記事へ移る。狭い画面では、記事から「目次」でまず木へ戻る（二段階） |
| ヘルプから入ったとき | 左のメニューの「ヘルプ」から入ったときは、戻り先が無いので出さない |
| ブラウザの戻る | ブラウザの戻る・進むでも行き来できる（第6.1.6節）。画面の中の戻る道は、それに加えて置く |

##### 6.10.7.3 業務のマニュアルをヘルプで読む

業務ごとのユーザーマニュアル（`docs/manual/<業務>/`。PDF にもする）を、**ヘルプの中でも章ごとに読めるようにする**（第 0.188.0 版）。

| 項目 | 規定 |
|---|---|
| 置き場 | `docs/manual/<業務>/` の `README.md`（はじめに）と、番号で始まる章のファイル（`01-….md`）。章の順は番号の順。**PDF とヘルプで同じ文を使う**（別に書かない） |
| 業務との結び付け | 各マニュアルの `manual.json` に、名前と、どの内蔵の拡張のものかを書く。ヘルプの木の「業務」の、その業務の区分の下に章を並べる。区分の名前はマニュアルの名前 |
| 見られる人 | **その業務を使える人だけ**（会社で入れていて、利用範囲・区画に入っている人。第16.7.3節・第29.2節・第30.2節）。使えない人の木と検索には出さない |
| 読みやすさ | 章の題は章の最初の見出しから取る。章の終わりに「前の章」「次の章」を置く |
| 秘書 | 秘書の使い方の答え（第6.10.6節）の材料には、今は入れない（長い章が要点の記事より先に当たるのを避ける。入れるかは様子を見て決める） |
| 業務の要点の記事 | `docs/help/` の記事に `business:`（マニュアルと同じ名前）を書くと、同じ業務の区分に入る。`extension:`（内蔵の拡張の ID。本人の「給与・勤怠」は `hr-self`）を書くと、その業務を使える人にだけ出す |

#### 6.10.8 拡張機能のヘルプ

| 項目 | 規定 |
|---|---|
| 必須 | 拡張機能のエージェント定義は `help`（第9.2.5節）を持つ。ツールは「すること」の説明を持つ |
| 置き場所 | 拡張機能パッケージの `help/`（第12.3節）。利用者向けの記事と、管理者向けの導入・設定の記事 |
| 審査 | ヘルプの有無と、実際の挙動との一致を審査する（第12.5節） |
| 表示 | 公式の記事と同じ場所に出し、**提供者の名前を明示する** |
| 版 | 拡張機能の版と一緒に更新する。版が上がって挙動が変わったのにヘルプが古い、を審査で止める |
| 問い合わせ | 拡張機能に固有の質問は提供者へ。基盤の不具合は運営へ。窓口を記事に書く |

**第三者の業務だけ説明が薄い、という状態が、マーケット全体の信頼を損なう。**
「すること・しないこと」を定義から自動で作るのは、この差を小さくするためでもある。

#### 6.10.9 ヘルプの内容の管理

| 項目 | 方針 |
|---|---|
| 公式の記事 | リポジトリの `docs/help/` に Markdown で置き、サービスの版と一緒に更新する |
| 記事の属性 | ID、題名、読み手（全員・承認者・管理者）、区分、関係する記事。業務の要点の記事は業務の名前（`business`）、管理者向けの記事は木の中の小分け（`group`: はじめに・設定・記録）を持つ |
| 画面との結び付け | 画面の「？」は記事の ID で記事を開く。画面の文言を変えたら記事も直す |
| **更新の義務** | **利用者に見える変更は、同じリリースでヘルプを更新する**（リリース規定）。README と同じ扱い |
| 検証 | 公式エージェントがすべて `help` を持つこと、記事の ID の参照が切れていないことを、テストで確かめる |
| **書く人と点検する人**（Q-68 で決定） | **利用者に見える変更を入れた人が、同じリリースで記事を直す**。点検はリリースの手順（第6.1節・リリース規定）に含め、実際の問い合わせ（第6.10.10節）から記事を足す。専任の担当は置かない |
| 保存の単位 | 公式と拡張機能の記事はテナントをまたいで共通（読み取り専用）。会社の補足はテナントごと（RLS） |

#### 6.10.10 ヘルプを育てる

| 項目 | 方針 |
|---|---|
| 見つからなかった質問 | 秘書が「ヘルプに見当たりません」と答えた質問を、そのテナントの管理者に件数と質問の文で示す。**質問した人の名前は出さない** |
| 運営への共有 | テナントの外へは出さない。運営がヘルプの改善に使う場合は、学習利用の同意（第11.9節）と同じ扱いとする（Q-69） |
| 役に立ったか | 記事と秘書の答えに「役に立った／立たなかった」を付け、件数だけを見る |

#### 6.10.11 段階的な構築

| フェーズ | 作るもの |
|---|---|
| Phase 1 | 初回の案内、管理者の初期設定チェックリスト、業務のカードの説明（定義から自動）、画面の「？」、ヘルプセンター（公式の記事）、秘書が使い方に答える、エラーに要求 ID を出す、更新情報（実装済み）、拡張機能のヘルプ（HELP.md。実装済み） |

### 6.11 キーボードから手を離さない

**この節で決めること**: 画面の操作を、どこまでキーボードだけで終えられるようにするか。

#### 6.11.1 方針

**入力してから実行するまで、キーボードから手を離させない。**

業務の入力欄に文字を打ち、そこからマウスへ手を移し、離れた場所の「実行する」を探して押す。
この往復が、1 日に何十回も起きる。**速さは、慣れた人ほど効いてくる。**

| 原則 | 内容 |
|---|---|
| k1 | **よく使う操作には、必ずキーボードの道がある。** マウスでしかできない操作を、よく使う位置に置かない |
| k2 | **入力欄から実行まで、手を移さずに終えられる。** 送信は `Mod+Enter` に揃える |
| k3 | **閉じるのは常に `Esc`。** ポップアップ・引き出し・確認は、例外なく `Esc` で閉じる |
| k4 | **道があることを画面に示す。** 隠れたショートカットにしない（メニューに併記し、一覧を出せる） |
| k5 | **音声も同じ目的を果たす。** 手が使えない・使いたくない場面では、話しかけて済ませられる（第10.5節） |

**すべてをキーボードで行えるようにする、とは約束しない。**
まれにしか使わない操作（管理者の初期設定など）まで割り当てると、覚えきれず、衝突も増える。
**よく使う操作に絞る。**

#### 6.11.2 修飾キーの扱い

**使う端末で押すキーが違う。画面には、その端末のキーで示す。**

| 端末 | `Mod` が指すキー | 画面の表示 |
|---|---|---|
| Mac・iPad・iPhone | Command | `⌘K` |
| Windows・Linux・Android | Control | `Ctrl+K` |

| 項目 | 規定 |
|---|---|
| 判定 | 利用者の環境から求める。**設定させない** |
| 触る端末 | 外付けのキーボードが無い端末では、**ショートカットを画面に出さない**（第6.9節） |
| 文字を打っている最中 | **単独のキーは効かせない。** `Mod` を伴う組み合わせと `Esc` だけを効かせる |
| 衝突 | ブラウザや OS が使うものを避ける（`Mod+1`〜`9` はブラウザのタブの切り替え、`Mod+W` は閉じる、など） |
| 読み上げ | ショートカットは追加の道である。**Tab での移動と読み上げを妨げない** |

#### 6.11.3 割り当て

| キー | 何をするか |
|---|---|
| `Mod+J` | 秘書の入力欄へ移る。どの画面からでも |
| `Mod+Enter` | いまの画面の主な操作を行う（業務を実行する、秘書に送る） |
| `Mod+Shift+1`〜`9` | 左メニューの 1〜9 番目の業務を開く |
| `Mod+B` | 左メニューを広げる・狭くする |
| `Mod+I` | 秘書のキャンバスを開く・閉じる（第6.2節） |
| `Mod+,` | 個人設定を開く |
| `Mod+/` | **ショートカットの一覧**を出す |
| `Esc` | 開いているポップアップ・一覧を閉じる |

`Mod+Shift+1`〜`9` に `Shift` を入れるのは、**`Mod+1`〜`9` がブラウザのタブの切り替えだから**である。

**割り当ては 1 か所にまとめて持ち、画面と一覧はそこから作る。**
コードの中に散らすと、一覧と実際がずれる。

#### 6.11.4 これから

| 項目 | 状態 |
|---|---|
| 業務を名前で探して開く（コマンドパレット、`Mod+K`） | Phase 2。業務が増えると、番号での割り当ては足りなくなる |
| 承認トレイをキーボードだけでさばく | Phase 2 |
| 割り当ての変更 | 予定しない。覚える対象を増やさない |
