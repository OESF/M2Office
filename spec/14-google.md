## 第 V 部　連携と制度

外部と何をつなぎ、日本の制度にどう合わせるか。

## 14. Google プラットフォーム連携

**この章で決めること**: Google の各サービスをどう使い、どう繋ぐか。

### 14.1 対象サービスと用途

| サービス | 用途 | 主な操作 | 危険度 |
|---|---|---|---|
| Gmail | メール | 読取、下書き作成、送信（ラベルの付け替えは作らない。第9.4.4節） | read / draft / external-send |
| Google ドライブ | ファイル保管・ナレッジ | 検索、読取、成果物の保存 | read / write-internal |
| Google ドキュメント | 文書作成 | 議事録・報告書・提案書の生成と編集 | draft / write-internal |
| Google スプレッドシート | 表計算 | 集計表、一覧の生成 | draft / write-internal |
| Google カレンダー | 予定 | 空き確認、予定作成、招待 | read / external-send |
| Google Tasks | ToDo | 一覧、起票、完了 | read / write-internal |
| Google Chat | 社内連絡・通知 | 投稿（通知の控えの送信口は見本。読取は未実装） | external-send |
| Google Meet | 会議 | 録画・文字起こしの取得 | read |

### 14.2 有機的な連携の形

Google の各サービスを個別に繋ぐのではなく、**業務の流れとして一本に通す**。
第1.4節の優位 A-1「組織知識の蓄積」は、この連携によって実現される。

```
     Meet で会議       Gmail に依頼が届く        ドライブに資料
          │                     │                       │
          ▼                     ▼                       ▼
   文字起こし取得       受信箱整理・要約            横断検索
          │                     │                       │
          └─────────────────────┴───────────────────────┘
                                ▼
                   議事録・回答・報告書を生成
                                │
          ┌─────────────────────┼───────────┬─────────────┐
          ▼                     ▼           ▼             ▼
    ドキュメント            Tasks に     Chat で   組織知識として
     として保存               起票        共有       登録・索引
                                                          │
                                                          ▼
                                            以後、全員の秘書が参照できる
```

**この流れが回ることで、会議をするだけ・メールを処理するだけで
会社の知識が厚くなっていく**。これが「有機的に回す」ことの具体的な意味である。

### 14.3 認可の方式

**ログインと Google データへの認可を、同じ Google アカウントで一体化する。**

| 段階 | 方式 | 内容 |
|---|---|---|
| ログイン | Google アカウント（OpenID Connect） | M2Office へのログイン。独自のパスワードは持たない |
| テナント判定 | Workspace のドメインとテナントの対応を検証 | 他社のサブドメインへは入れない |
| データ認可 | OAuth 2.0 による各従業員の同意 | Gmail・カレンダー等へのアクセス許可 |

ログインと認可が同じ事業者のアカウントで完結するため、
利用者から見れば「Google でログインし、必要な許可を出す」という 1 つの流れになる。

**ただし、ログインできることと Gmail が読めることは別である。**
ログインの同意だけでは Gmail やカレンダーにはアクセスできず、
用途ごとの権限（スコープ）に対する同意が別途必要になる。
したがって初期設定ウィザード（第22.2節）では、この 2 つを区別して案内する。

スコープは段階的に要求し、**使う機能の分だけ**許可を求める。
最初にすべての権限を求めることはしない。

#### 14.3.1 Google の審査と CASA

Google の公式の説明（2026 年 9 月時点）で確かめた内容。**審査が要るのは一般公開（外販）のときであり、
開発と社内での運用試験は審査なしで進められる。**

| 権限の段階 | 例 | 一般公開のときに必要なこと |
|---|---|---|
| 機密性の高くない権限 | ログイン、`drive.file`（M2Office が作った・利用者が選んだファイルだけ） | ブランドの確認（アプリ名・ホームページ・プライバシーポリシー） |
| 機密性の高い権限 | カレンダー、ToDo、Chat、ドキュメント・スプレッドシート・スライド（見込み） | 上に加えて Google の審査（使い道の説明、デモ動画） |
| **制限付きの権限** | **Gmail の読み取り・下書き**、**ドライブ全体** | 上に加えて、**Google が認定した第三者の評価機関によるセキュリティ評価（CASA）** |

| CASA の項目 | 内容 |
|---|---|
| 対象 | 制限付きのデータを、自社のサーバーから、またはサーバー経由で扱うアプリ。M2Office はあたる |
| 評価する者 | Google が認定した独立の評価機関（App Defense Alliance の枠組み） |
| 見るもの | データを安全に扱うこと、利用者の求めに応じてデータを削除できること |
| 期間 | 審査全体で数週間 |
| 受け直し | 評価文書（LOA）の承認日から **12 か月ごと**。新しい制限付きの権限を足すと再評価が要ることがある |
| 費用 | 評価機関と評価の段階による。見積もりを取って確かめる（Q-08） |
| 業務の自動化の基盤 | デモ動画で、複数の API をまたぐ処理をどう作って自動化し、データがどちらへ流れるかを示す |

| 審査が要らない場合 | M2Office での扱い |
|---|---|
| 開発・テスト（同意画面を「テスト」のまま。登録した人だけ、人数の上限、警告の画面、短いログインの有効期間） | **開発の段階** |
| 社内専用（1 つの Google Workspace 組織の中だけ。同意画面を「内部」にする） | **社内での運用試験の段階**（自社だけで使う）。**会社の OAuth クライアントを使う形（第14.3.3節）では、各社が社内専用として動かせる** |
| 個人的な利用 | 当てはまらない |
| ドメイン全体のインストール | ブランドの確認は不要になるが、機密性の高い権限・制限付きの権限の審査は要る |

**段階**: 開発（テスト）→ 社内での運用試験（社内専用）→ **一般公開の前に** ブランドの確認・データアクセスの審査・CASA を受ける。

#### 14.3.2 CASA に備えた作り

公開の段階で作り直さないよう、**いまから次の作りにしておく。**

| # | 規定 | 理由 |
|---|---|---|
| 1 | **ツールごとに、必要な権限（スコープ）と段階を宣言する**（第9.4.4節） | どのツールがどの審査を招くかを、コードから一覧できるようにする |
| 2 | **会社で使う業務の分だけ権限を求める**（段階的な認可） | 最小の権限。使わない制限付きの権限を求めない |
| 3 | **制限付きの権限を使うツールを最小にする**。ドライブは `drive.file` で作る。例外はスライド作成の会社のテンプレート（`drive`。第 0.123.0 版、Q-88） | CASA の対象は Gmail と、スライド作成を使う会社のドライブになる |
| 4 | 制限付きの権限で得たデータを、**学習（第11.9節の学習利用）・広告・人による閲覧に使わない**（Google の Limited Use） | 審査の条件。運営の閲覧は第23章の例外の手続きだけ |
| 5 | 取得したメールの本文を長く持たない。実行の記録に残す範囲と期間は下の表のとおり（Q-78 で決定） | 保存が少ないほど、評価と漏えいの影響が小さい |
| 6 | **利用者・会社の求めに応じて、Google から得たデータと認可（トークン）を削除できる**。退会のときにも消す | CASA が確かめる項目 |
| 7 | 認可のトークンは暗号化して保存し、推論に渡さない（第14.4節と同じ） | 漏えいの防止 |
| 8 | 依存の脆弱性の点検と静的解析を、継続的に回す | CASA の評価（OWASP ASVS 相当）に備える |

**Google から取得したデータの保持**（規定 5。Q-78 で決定）

| 項目 | 規定 |
|---|---|
| 対象 | Google から取得したものすべて（メール・予定・ToDo・ドライブ・文書・スプレッドシート・会議の文字起こし・フォームの回答・ディレクトリ）。制限付きの権限かどうかで分けない |
| 由来のデータ | 取得したものから LLM が作った要約・分類・下書きの文（ステップの出力）も対象に含める。Google の Limited Use は、取得したデータから作ったものにも及ぶため |
| 残す期間 | **実行が終わってから 7 日**。承認待ちの間は残す（判断と再開に要るため） |
| 期間の後 | ステップの入力と出力から中身を消し、目印だけを残す。残すのはツール名・メッセージやファイルの ID・日時・件数だけで、**件名と差出人は残さない** |
| 承認待ちの放置 | 承認待ちのまま 30 日たった実行は期限切れとして止め、同じく中身を消す。依頼者に通知する |
| 成果物 | 利用者が求めた成果（下書き・議事録など）は、実行の記録と同じ期間（第19.3節）残す。本人が消せる |
| 名刺の更新 | メールの署名から新しくした名刺の値（会社名・部署・役職・電話・住所など。第27.6.1節）は、連絡先の値として連絡先がある間残す（Q-152 を第 0.205.0 版で決定）。メールの ID は 7 日で消し、件名・本文は残さない。連携の解除では戻さず、削除の求めでは前の値に戻して変更の記録を消す |
| 通知の本文 | 実行に結び付いた通知（朝のブリーフ・週次ブリーフの本文、承認の依頼など）は、**その実行の中身を消すときに本文も消す**（第 0.153.0 版。ブリーフの本文に予定の題名やメールの件名が入るようになったため）。題名と日時は残る |
| 組織知識へ登録した議事録 | 対象外。承認を経て会社の知識になったものは、会社の資産として残す。管理者が消せる。由来（Google から読んだデータで作ったか）を記録する（第9.5.2節、Q-85） |
| 会社の設定 | 7 日を短くできる（0 日 = 実行が終わったら消す）。長くはできない |
| 削除の求め | 利用者が Google の連携を解除したとき、その人の実行から Google 由来の中身を消す（期間を待たない）。退会・解約のときも同じ |
| 監査ログ・アプリログ | もともと中身を入れない（ツール名・危険度・実行 ID だけ）。この規定の対象外 |
| 秘書の会話の記録 | **対象外。会話の記録の決まり（4 週。第11.9.6節）に従う**（2026-09-25 に三浦さんが決定）。秘書が予定やメールについて答えた文（例:「次の予定は 10 時からの『朝会』です」）は、Google から取得した値を含むが、本人の会話として 4 週残す。根拠の欄（件名の一覧など）はもともと記録に残さない。本人が「会話を残す」を切っていれば、はじめから残らない。**会話の要約と抽出した事実も第11.9.6節のとおり長期で残す。Google の連携を解除しても、会話の記録と要約は消さない**（いずれも 2026-09-25 に三浦さんが決定。解除で消すのは業務の実行の中身だけ） |
| 見られる人 | 期間の中でも、その実行に関わる人だけ（第6.2.3節） |

実行中・承認待ちの間に連携がなくなったときの扱いは、第6.5.2.1節（Q-54 で決定）。

#### 14.3.3 接続の設定（会社が自分で行う）

**Gemini と Google Workspace への接続は、会社の管理者が管理者ページ「接続」で自分で設定する。**
設定の流れと見せ方は、AI Radio の「システム接続設定」で実績のある作りを引き継ぐ（ADR-0007）。

##### Gemini（業務の推論・秘書・Web の調査・音声）

| 項目 | 規定 |
|---|---|
| 契約の形態 | **運営一括**（既定。運営の鍵を使う）か、**自社の鍵**（BYOK。第21.3節） |
| 自社の鍵 | Gemini の API キーを登録する。**登録後は表示しない**。上書きと削除だけができる（第6.6.2節） |
| モデル | 高速・標準・高性能・調査・音声に使うモデル名。空欄なら既定 |
| 接続の確認 | 文章（モデルを 1 回呼ぶ）と音声（Gemini Live の接続を開いて閉じる）を、その場で試せる |
| 効く範囲 | 自社の鍵を登録すると、その会社の業務の推論・秘書・`web.research`・音声がその鍵を使う |
| 音声（Gemini Live） | **鍵をブラウザに渡さない。** ブラウザはサーバーにつなぎ、サーバーが Gemini Live へ中継する（AI Radio と同じ。第10.5節） |

##### Google Workspace（Gmail・カレンダー・ToDo・Chat・ドライブほか）

**会社の Google Cloud で作った OAuth クライアント（同意画面を「内部」にしたもの）を登録する。**
1 つの組織の中だけで使う社内専用のアプリとして動くため、一般公開のための Google の審査と CASA が要らない（第14.3.1節）。

| 手順 | 管理者が行うこと |
|---|---|
| 1 | 会社の Google Cloud でプロジェクトを作り、使う API（Gmail・カレンダー・Tasks ほか）を有効にする |
| 2 | OAuth の同意画面を**「内部」**で作る |
| 3 | OAuth クライアント（種類は「ウェブ アプリケーション」）を作り、**管理者ページに表示されるリダイレクト URI** を登録する |
| 4 | クライアント ID とクライアント シークレットを管理者ページに登録する（シークレットは登録後に表示しない） |
| 5 | 管理者が自分で「Google と接続する」を試し、許可の状況を確かめる |
| 6 | 従業員が、個人設定の「Google 連携」でそれぞれ接続する（第6.5.2節） |

| 項目 | 規定 |
|---|---|
| 接続の単位 | **利用者ごと**。各自が本人の Google アカウントで許可し、本人のメール・予定だけを扱う（不変則 I-9） |
| 求める権限 | ログインに要るもの（`openid`・`email`）と、**会社で使える業務のツールが求める権限だけ**（第14.3.2節 規定 2）。業務を足して権限が増えたら、画面で再接続を促す |
| 許可の確認 | 保存の有無ではなく、Google に**実際に許可された範囲**を問い合わせて示す（一部だけ拒否された場合も分かる。AI Radio と同じ） |
| 管理者に見せるもの | 利用者ごとの接続の有無・接続した日時・足りない許可。**トークンは見せない** |
| 取り消し | 利用者は個人設定で接続を取り消せる。取り消すと Google 側の許可も取り消し、保存したトークンを消す |
| 戻り先の検証 | 認可の要求には使い捨ての `state` と PKCE を付け、戻ってきた要求を照合する。照合できなければ何もしない |

###### 登録の確認（第 0.97.0 版）

**クライアント ID とシークレットを保存するとき、組になっているかを Google に確かめる。誤っていれば保存しない。**

2026-09-25 に、組にならないシークレットが**そのまま保存され**、利用者が「Google と接続する」を押して
初めて失敗した。利用者の画面には「管理者に設定を確かめてもらってください」としか出ず、
何が誤っているかは、サーバーの記録を読むまで分からなかった。

| 項目 | 規定 |
|---|---|
| 確かめ方 | Google のトークンの窓口へ、**使えない認可コード**を付けて鍵の受け取りを 1 回求める。Google は先にクライアントを確かめるため、返し方でクライアントの正否が分かる。利用者の許可も、実際の鍵も要らない |
| 判定 | `invalid_grant`（コードが無効）→ **組は正しい** ／ `invalid_client` と「client secret is invalid」→ **シークレットの誤り** ／ `invalid_client` と「client was not found」→ **クライアント ID が無い** ／ 届かない・5xx → **確かめられない** ／ それ以外 → **想定外の返事**（返事をそのまま示す） |
| 誤りのとき | **保存しない。** いまの登録はそのまま残る。**正しいシークレットを誤った値で上書きすると、接続済みの全員がトークンを取り直せなくなる**ためである。何が誤っているかを、保存のボタンの横に出す（第6.10.4.2節） |
| 確かめられないとき | 保存する。**確かめられなかったことを、確かめたように見せない。**「保存しましたが、Google に届かず確かめられませんでした」と出す |
| いつ確かめるか | 保存のたび（シークレットを替えたとき、クライアント ID を替えたとき、どちらも替えずに保存し直したとき） |
| 登録済みの確認 | 「**Google で確かめる**」で、保存し直さずにいつでも試せる（Gemini の「接続を確認する」と同じ位置づけ） |
| 記録 | 監査ログの登録の記録に、判定の結果を残す。**シークレットの値は残さない** |
| 利用者の接続で分かったとき | 利用者が接続を押し、Google がクライアントの誤りを返したときは、「**会社の Google 接続の設定に誤りがあるため接続できませんでした。管理者に伝えてください**」と出す。もう一度押しても直らないため、「もう一度試す」を勧めない |

**確かめるのはクライアントの正否だけである。** リダイレクト URI の登録漏れ、API の有効化漏れ、
同意画面の設定は、この方法では分からない。利用者の接続（手順 5）で確かめる。

##### 保存

| 対象 | 扱い |
|---|---|
| Gemini の鍵、OAuth のクライアント シークレット、利用者のリフレッシュ トークン | **暗号化して保存する**（AES-256-GCM。暗号の鍵はサーバーの設定 `M2OFFICE_SECRET_KEY` に置き、データベースには置かない） |
| API の応答 | 秘密の値を返さない。「登録済み」かどうかと、登録した日時だけを返す |
| 推論 | 秘密の値を推論に渡さない |
| 監査ログ | 登録・削除・接続・取り消しを記録する。**値は記録しない** |

**運営の OAuth クライアント（公開アプリ）を用意する形**は、会社が Google Cloud を扱えない場合の選択肢として残す。
その場合は一般公開の審査と CASA が要る（Q-79）。

#### 14.3.4 Google の接続口（Gmail・カレンダー。第 0.98.0 版）

**接続口の `google` 実装を、Gmail とカレンダーから作る。** 残りのサービスは順に足す（ADR-0022）。
ツール・エージェント・画面は変えない。接続口（ADR-0003）の後ろだけを差し替える。

##### 範囲

| サービス | この版 | 操作 |
|---|---|---|
| Gmail | **本物** | 受信箱の一覧・1 通の本文・検索・下書きの作成・送信 |
| カレンダー | **本物** | 期間の予定・空き時間（freeBusy）・予定の作成・変更・取り消し |
| ToDo | **本物**（第 0.100.0 版） | 一覧・起票・完了 |
| Chat | **本物**（第 0.101.0 版） | スペースへの投稿 |
| スライド | **本物**（第 0.122.0 版） | 構成からの作成（標準の見た目）と、会社のテンプレートを読んで組み立てる（第 0.123.0 版。第9.4.2節） |
| ディレクトリ・Meet・フォーム | **準備中** | 呼ばれたら「まだ Google につないでいません（準備中）」と断る |

**準備中のサービスを、見本のデータで代わりに動かさない。**
本物のメールと見本の ToDo が 1 つの週次ブリーフに混ざると、どれが本物か利用者に見分けられない。
取得できなかったことを「取得できませんでした」と示すほうがよい（開発規約「取得に失敗した値を推測で埋めない」、ADR-0003「黙ってダミーに切り替えない」）。

##### 誰の権限で呼ぶか

| 項目 | 規定 |
|---|---|
| 権限 | **依頼した本人の** Google の許可（第14.3.3節の利用者ごとの接続）。ほかの人のトークンで代わりに呼ばない（不変則 I-9） |
| アクセス トークン | 保存したリフレッシュ トークンから取り直す。**プロセスのメモリにだけ**、期限の 1 分前まで持つ。データベースにもログにも書かない |
| 会社のクライアント | 会社が登録した OAuth クライアント（第14.3.3節）で取り直す |

##### 断るときの言葉

接続口は、呼べないときに次の理由で断る。**断りの文にはメールや予定の中身を入れない**（実行の失敗の理由は、管理者の「実行の一覧」にも出るため。第6.6.8節）。

| 理由 | 利用者に見せる文の要点 |
|---|---|
| 接続していない | 「Google と接続していません。個人設定の『Google 連携』で接続してください」 |
| 許可が取り消された・切れた | 「Google の許可が取り消されたか、期限が切れています。接続し直してください」 |
| 権限が足りない | 「この操作に要る Google の許可がありません。接続し直して、許可を追加してください」 |
| 準備中 | 「〈サービス〉はまだ Google につないでいません（準備中）」 |
| 会社のクライアントが無い・誤り | 「会社の Google 接続の設定がありません（または誤りがあります）。管理者に伝えてください」 |

**読むだけのツール（危険度 `read`）で断られたときは、実行を止めずに「取得できませんでした」と理由つきで返す。**
エージェントは、ほかの手がかりで続けられる（週次ブリーフが ToDo だけ欠けても、予定とメールはまとめられる）。
**書くツールで断られたときは、そのステップを失敗にする。** 書いたつもりで先へ進ませない。

##### ToDo（第 0.100.0 版）

| 項目 | 規定 |
|---|---|
| 対象 | 本人の**既定の ToDo リスト**（`@default`）。ほかのリストは見ない・書かない |
| 誰のリストか | **依頼した本人のリスト。** Google の ToDo の API には、他人に割り当てる機能が無い。議事録の担当者は、題名に書いて残す（例:「資料を作る（山田）」） |
| 期限 | Google の ToDo の期限は**日付だけ**で、時刻は捨てられる。M2Office では**その日の終わり（日本時間 23:59:59）**として扱い、その日のうちは「期限切れ」にしない。登録するときは日付だけを渡す（時刻つきで渡されたら、日本時間の日付にする） |
| 一覧 | 未完了のものだけ（完了も含めるよう求められたときは含める）。100 件まで |
| 完了 | 状態を「完了」にする。無い ToDo なら「見つかりません」と返す（例外にしない）。**Google は形の違う ID に 404 でなく 400 を返す**ため、完了に限り 400 も「見つからない」とみなす（送る中身は決まっており、不正になりうるのは ID だけ） |
| 危険度 | 起票と完了は `write-internal`（本人のリストへの書き込み。会社の設定により、実行の前に本人の確認を求める。第9.4節） |

##### Chat（第 0.101.0 版）

| 項目 | 規定 |
|---|---|
| 投稿する人 | **依頼した本人として**投稿する（本人の許可。Chat には本人の名前で出る） |
| 投稿先の指定 | スペースの**名前**（例:「営業部」）か、スペースの**リンク・ID**（`spaces/…`）。名前のときは、**本人が入っているスペース**から名前が一致するものを探す（2026-09-25 に三浦さんが決定） |
| 名前の一致 | 前後の空白・全角と半角・英字の大小は区別しない。**ちょうど 1 つ**のときだけ投稿する。無ければ「見つかりません」、2 つ以上なら「同じ名前のスペースが複数あります。リンクを貼ってください」と断る。**似た名前のスペースに、推測で投稿しない** |
| 探す範囲 | 名前のあるスペースだけ。1 対 1 の会話とグループの会話は、名前で探さない |
| 本文 | Chat の書式に直す（見出しは太字に、`**太字**` は `*太字*` に）。4,000 字を超えたら切り、続きは M2Office で見られる旨を添える |
| 会社の準備 | 会社の Google Cloud で **Chat アプリを設定**しておく。本人の権限で投稿する場合も Google が求める（2026-09-25 に確認。設定が無いと「Google Chat app not found」と返る）。無ければ「会社の Google Cloud で Chat アプリが設定されていません。管理者に伝えてください」と断る |
| 許可 | 投稿（`chat.messages.create`）に加え、スペースの一覧を見る許可（`chat.spaces.readonly`。機密）を求める。**許可が増えるため、接続済みの利用者は接続し直しが要る**。足りない間は「許可を追加してください」と断る |
| 危険度 | `external-send`。**承認の後でしか呼ばれない**（第9.4節） |
| 承認の前の確かめ | **承認の前（組み立てのとき）に投稿先を探す**（第9.3.3節「承認の前に、行えるかを確かめる」。第 0.108.0 版）。名前ならスペースを探し、リンクなら本人が見られるかを確かめる。見つかれば、承認の画面にスペースの名前を出し、**承認のあとはそのスペースへ投稿する（探し直さない）**。見つからない・複数ある・許可が無い・Chat アプリの設定が無いときは、投稿を記録せず、承認の画面に「行えません」と理由を出す。Google に届かず確かめられなければ、投稿は記録し、承認のあとで改めて探す |

| 項目 | 規定 |
|---|---|
| 権限 | `drive.file`（機密でない）。**見えるのは M2Office が作ったファイルと、利用者が選んだファイルだけ**。ドライブ全体は見ない（第9.4.4節「作らないもの」） |
| 利用者が選ぶ画面 | Google の「ファイルを選ぶ画面」（Picker）は**次の段階**。それまでは、M2Office が作ったファイルだけが見える |

| フォルダを作る | 本人のドライブに作る。共有はしない |
| 共有 | 指定した人（メールアドレス）に、閲覧・コメント・編集のいずれかで共有する。**「リンクを知っている全員」への公開は作らない**。Google から相手に共有の知らせのメールが届く。会社の設定で社外への共有が禁じられていれば、Google が断り、その旨を返す |
| 会社の全員への共有 | 本人の Google アカウントの会社のドメインの全員が、**閲覧だけ**できるようにする（第 0.110.0 版）。検索には出さず、リンクを知っている社内の人だけが開ける。**個人向けの Google アカウント（`gmail.com` など）では行わない**（ドメインが会社でなく、一般公開と同じになるため） |
| 見つからないファイル | 読む・共有で見つからなければ（見えない範囲のものを含む）、「見つかりません」と返す。例外にしない |

##### スプレッドシート（第 0.111.0 版）

| 項目 | 規定 |
|---|---|
| 権限 | `drive.file`（機密でない）。M2Office が作った表（と利用者が選んだ表）だけを扱う |
| 作る | 本人のドライブに作り、**共有しない**。1 行目に列名、2 行目から値を入れる。フォルダを指定すれば、そこに入れる。開くリンクを添える |

### 14.5 Google 以外のグループウェアへの対応

第2.2節の方針により、標準機能は Google に限定する。
Microsoft 365 等への対応は以下の扱いとする。

| 段階 | 扱い |
|---|---|
| Phase 1〜2 | 対応しない。Google Workspace 利用企業のみを対象とする |
| Phase 3 以降 | L2 拡張（MCP コネクタ）として対応を検討する |
| 設計上の準備 | ツール層のインターフェースをサービス非依存に保ち、後から差し替えられる形にする |

**「後から対応できる形にしておく」ことと「今すぐ対応する」ことは別である。**
インターフェースの抽象化だけ行い、実装は Google に集中する。

### 14.6 対外チャネル ― LINE 連携（将来）

**この節で決めること**: 顧客企業が対外的に使う LINE と、どう繋ぐか。

#### 14.6.1 位置づけ

国内の中小企業では、顧客や取引先とのやり取りに LINE を使う例が多いことが指摘されている。
Google Workspace は**社内**の基盤であり、LINE は**社外**との接点という役割の違いがある。
両者は競合せず、補完の関係にある。

| 領域 | 基盤 |
|---|---|
| 社内の業務・情報共有 | Google Workspace（第2.2節） |
| **社外との接点（顧客・見込み客）** | **LINE 公式アカウント** |

TBD: 利用率の出典となる調査の特定（Q-44）。

#### 14.6.2 できること・できないこと

**個人どうしの LINE のやり取りには関与しない。** 扱うのは企業の公式アカウントである。

| できること | できないこと |
|---|---|
| 公式アカウント宛の問い合わせを受け取る | 従業員個人の LINE を読む・代理で送る |
| 友だち登録した相手へ配信する | 登録していない相手へ送る |
| 応答メッセージを下書きし、承認後に返信する | グループトークへ無断で参加する |
| 定型の案内（営業時間、予約手順）を返す | 相手の同意なく情報を収集する |

#### 14.6.3 想定するユースケース

| # | 内容 | 関連エージェント |
|---|---|---|
| 1 | 問い合わせの一次対応。回答を下書きし、担当者が承認して返信する | AG-10 |
| 2 | よくある質問に、組織知識を参照して自動で答える | AG-04 |
| 3 | 予約・注文の受付内容を整理し、社内のタスクに起票する | AG-02 系 |
| 4 | 友だち登録者へのお知らせ配信（承認必須） | — |
| 5 | 問い合わせ内容を組織知識として蓄積し、FAQ を育てる | 第11.4節 |

**第 5 項が最も価値が高い。**
顧客からの問い合わせは社内に散らばりやすく、形式知になりにくい情報である。
これを蓄積して FAQ に育てる流れは、第11.8節の成長ループと同じ構造になる。

#### 14.6.4 設計上の扱い

| 項目 | 方針 |
|---|---|
| 実装形態 | **標準機能ではなく拡張機能（L2 コネクタ）として実装する**（第12.1節） |
| 理由 | 第2.2節の「Google に一本化」方針を崩さず、必要な顧客だけが導入できる形にする |
| 危険度 | LINE への送信は `external-send`。**承認を省略できない**（第9.4節） |
| 一斉配信 | 影響が大きいため、通常の承認に加えて配信対象と件数を明示して確認する |
| 費用 | 配信数に応じた費用が発生するため、送信前に件数と概算を提示する |
| 同意 | 友だち登録が相手の同意にあたる。登録していない相手への送信は行わない |
| 記録 | やり取りは会話ログとして保存し、組織知識の供給源とする（第11.9節） |

| 2 | 問い合わせ対応エージェント（AG-10）を、チャネルに依存しない形で定義する |
| 3 | 外部からの受信を起点にジョブを起動できる経路（Webhook）を用意する（第13.2節） |

第 3 項は第13章の公開 API と同じ仕組みで実現できる。
**外部からの入力でエージェントが動き出す構造を一度作れば、LINE に限らず適用できる。**
