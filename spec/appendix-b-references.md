## 付録 B. 参考にした外部資料

`anthropics/knowledge-work-plugins` は、業務手順を宣言的に記述して
AI に実行させる方式の公開実装である。M2Office はこの考え方を継承しつつ、
定義をファイルではなくデータとして扱い、GUI から操作できるようにする（第2.3.3節）。

### B.1 リポジトリの構成

| 区分 | 内容 |
|---|---|
| 職種別プラグイン | productivity、sales、customer-support、product-management、marketing、legal、finance、data、enterprise-search、engineering、design、operations |
| 規模・領域別 | small-business（44 スキル）、human-resources、bio-research |
| 仕組み | cowork-plugin-management（プラグインの作成支援） |
| **パートナー製** | **partner-built（Apollo、Slack、Zoom、Common Room ほか）** |
| その他 | pdf-viewer |

構造はいずれも共通である。

```
plugin-name/
├── .claude-plugin/plugin.json   マニフェスト
├── .mcp.json                    外部ツールへの接続
├── commands/                    明示的に呼び出す操作
└── skills/                      必要なときに引き出される知識と手順
```

### B.2 M2Office での扱い

| プラグイン | M2Office での扱い | 理由 |
|---|---|---|
| **cowork-plugin-management** | **考え方を採用** | スキルを作る支援そのもの。第12.7節の設計に対応する |
| **partner-built** | **制度の先行例** | SaaS ベンダーが自社向けに作る類型（第13.7.2節） |
| **productivity** | **考え方を採用** | 2 層のメモリ（作業記憶と深層保存）は第11.1節と同じ発想 |
| **enterprise-search** | **考え方を採用** | 横断検索は AG-04 と組織知識に対応。範囲は Google 内に絞る |
| **customer-support** | **骨格を流用** | チケットのトリアージは AG-10 に使える。LINE 連携とも接続する |
| small-business | 大半を再設計 | 財務・税務が米国制度。営業・提案・ブリーフは構造を流用 |
| human-resources | 一部を再設計 | 第9.6.1節に対応表 |
| legal | 限定して採用 | 契約の論点抽出まで。判断は行わない（第15.4節） |
| finance | 全面再設計 | 日本の会計制度に合わせて作り直す |
| pdf-viewer | 参考にする | 証憑の読み取り（AG-08）に関係する |
| sales | Phase 2 以降 | CRM の前提が強い。国内 SaaS に合わせる必要がある |
| operations | 要調査 | 在庫・発注など、業種によっては有用 |
| marketing | Phase 3 以降 | 米国のプラットフォーム前提のものが多い |
| product-management | 対象外 | 中小企業の非 IT 部門には需要が薄い |
| data | 対象外 | データウェアハウスの前提が中小企業にない |
| engineering / design | 対象外 | 対象とする業務領域の外 |
| bio-research | 対象外 | 同上 |

### B.3 考え方として取り込むもの

| # | 取り込む考え方 | M2Office での対応 |
|---|---|---|
| 1 | **宣言的な記述だけで業務が形になる**。コードもインフラも要らない | エージェント定義（第9.2節）。任意のコードを含まない |
| 2 | **自動で引き出される知識と、明示的に呼ぶ操作を分ける** | 秘書の取次（第10.9節）とメニューからの実行 |
| 3 | **2 層のメモリ**（作業記憶と深層保存） | 個人記憶・チーム記憶・組織知識の 3 層（第11.1節） |
| 4 | **外部接続は MCP に寄せる** | 第14.4節。コネクタ層で吸収する |
| 5 | **カスタマイズの手段を 4 つに分ける**（接続の置換／社内文脈の追加／手順の調整／新規作成） | 第12.7.1節の変更範囲。ただし M2Office は画面から行う |
| 6 | **パートナーが自社向けに作る区画を設ける** | 第13.7節 |

**第 3 項は独立に同じ結論へ至った点である。**
記憶を層に分ける設計は、別々に検討して同じ形になった。
この方式の妥当性を補強するものとして記録しておく。

### B.4 取り込まない点

| # | 取り込まない | 理由 |
|---|---|---|
| 1 | ファイルとコマンドによる操作 | 中小企業に届かない。本書の出発点（第2.3.3節） |
| 2 | 米国の制度を前提とした財務・税務・労務 | 日本の制度で作り直す（第15章） |
| 3 | 環境の権限に従う実行 | 組織利用には権限の割当と監査が要る（第16章） |
| 4 | 承認の扱いを会話の中で済ませる | 危険度に応じた承認ゲートを基盤が強制する（第9.4節） |

#### B.5.1 取り込むもの

##### doc-coauthoring から取り込む発想

文脈を集める → 節ごとに詰める → **文脈を持たない別の推論に読者として検証させる**、
という 3 段階の手順である。

第 3 段階が目を引く。**生成した文書を、経緯を知らない側から読み直させて
曖昧さを指摘させる**という方法である。

M2Office では承認ゲートの手前に置ける。
人が確認する前に機械が一度読み直せば、承認者の負担が減る。

#### B.5.3 ライセンス上の注意

**文書形式を扱うスキル（docx・pdf・pptx・xlsx）は
「source-available であり、オープンソースではない」と明記されている。**

| してよいこと | してはならないこと |
|---|---|
| 設計の考え方を参考にする | 実装をそのまま取り込む |
| 同じ機能を自前で実装する | ライセンスを確認せずに流用する |

第9.4.3節に実装上の注意として記載した。
**他のスキルの多くは Apache 2.0 だが、形式ごとに確認すること。**
