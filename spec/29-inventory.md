## 29. 在庫管理（第 0.149.0 版、ADR-0045。第 0.156.0 版で汎用の前提と導入時の設定に改めた。第 0.157.0 版で Phase 1 の土台を実装）

この章で決めること: 品目・場所・在庫の数（ロットと使用期限を含む）を持ち、入庫・使用・移動を記録し、スマホでバーコードを読んで棚卸しをし、
在庫を Web に公開し、AI が欠品を防ぐしくみ。形（内蔵の拡張）、汎用にするための入り切り、最初の範囲と後の段階、秘書と業務からの使い方、お金と社外への境界、人の情報と業種の決まりとの線引き。

**この章は案である。** **汎用の在庫管理として作る。** 特定の導入先・業種の条件に合わせた作りにしない（三浦さんの方針）。
会社ごとの違いは、**機能の入り切り**（第29.4節）と、**導入のときに会社が設定する項目**（第29.4.1節）で吸収する。残りの確かめる事項（第29.22節）の答えで直してから実装する。

### 29.1 目的と位置づけ

物販・製造・サービス業などの中小企業では、在庫を Excel や紙で持ち、**実際の数と帳簿の数が合わない**。
棚卸しは紙に書いて数え、Excel に打ち直す。欠品に気づくのは、無くなってからである。

| 痛み | M2Office で行うこと |
|---|---|
| 棚卸しに時間がかかる | スマホで棚と品目のバーコードを読むだけで数える。数えた端から帳簿との差が分かる |
| 入庫の入力の手間 | バーコード（使用期限とロットを含む GS1 のバーコードなら、それも一緒に）を読むか、**納品書の写真から AI が読み取って**入庫にする |
| 在庫をお客様に伝えられない | **在庫を Web ページにそのまま公開する**。入出庫のたびに、すぐ変わる |
| 欠品に気づくのが遅い | **AI が常に在庫を見張り**、残りわずか・無くなる見込みの日・使用期限の近いものを知らせ、発注の案を作る |

#### 29.1.1 想定する会社（第 0.156.0 版）

**導入先の業種や、使っている製品の名前は仕様書に書かない。** 特定の導入先の値を決まりにしない（経緯は ADR-0045）。

| 項目 | 想定 |
|---|---|
| 業種 | 物販・製造・サービス業（予約を受けて物を使う・渡す業種を含む） |
| 規模 | 品目は**数十〜数千**、場所は倉庫と棚で**数十まで**、使う人は**100 人まで**。一覧・検索・棚卸しはこの規模で待たせない作りにする |
| 今の方法 | 表計算か紙。在庫の管理のソフトを使っていない |
| 品目の性質 | **使用期限とロットのある品**・**1 つを数回に分けて使う品**・バーコードの付いていない品（輸入品など）がありうる |
| 違い | 機能の要否・残りわずかの目安・仕入先と発注の方法・公開の形・予約のサービスとのつなぎ・棚卸しの頻度は**会社ごとに違う**。すべて導入のときに会社が設定する（第29.4.1節） |

### 29.2 形: 内蔵の拡張（既定は切り）

在庫管理は、表とスキャン・棚卸し・公開の画面を持つ。拡張機能（第12.10.1節）では作れないため、名刺管理（第27章）と同じく**内蔵の拡張**（第12.13節）として作る。

| 項目 | 規定 |
|---|---|
| 入り切り | 管理者ページの「拡張機能」に「公式・内蔵」として並べ、会社ごとに入り切りする。**既定は切り**（物を扱う会社には要るが、どの会社にも要るわけではない） |
| 利用範囲 | ほかの拡張機能と同じく、使える人をグループや人で絞れる（第16.7.3節） |
| 画面 | 左ペインの「業務」の並びに「在庫管理」を置く（第6.1.1節）。切っている会社と利用範囲の外の人には出さない |
| 範囲 | 在庫は**会社で共有**する |
| 課金 | **無償で同梱する**（基本の料金に含め、在庫管理だけの料金は取らない。2026-10-02 に三浦さんが決めた。Q-112） |

### 29.3 用語

| 用語 | 意味 |
|---|---|
| 品目 | 管理する物の 1 種類。名前・バーコード・単位を持つ |
| 場所 | 物を置く所。「倉庫」とその中の「棚」の 2 段 |
| ロット | 同じ品目の、製造の単位。使用期限を持つ |
| 在庫 | 場所・ロットごとの数（帳簿の数）。入出庫の記録から求める |
| 使える数 | 在庫から、**予約で取り置いた数（引き当て）**と使用期限の切れた数を引いたもの。公開と欠品の判断はこの数で行う |
| 入り数 | 仕入れの単位と使う単位の換算（「1 本 = 5 回分」「1 箱 = 10 本」） |
| 入出庫の記録 | 入庫・使用・移動・調整の 1 件ずつの記録。**消さない**。取り消しは逆の記録を足す |
| 棚卸し | 実際の数を数え、帳簿の数との差を合わせる作業 |
| 公開 | 在庫を Web ページに出すこと（第29.12節） |

### 29.4 汎用にするための入り切り

業種ごとの違いは、**会社ごとの機能の入り切り**と品目ごとの項目で吸収する。お客様ごとの作り分けはしない。

| 機能 | 入れると | 既定 |
|---|---|---|
| ロットと使用期限 | 入庫でロットと使用期限を記録し、期限の近いものから使う。期限切れは使える数から外す（第29.8節） | 切り |
| 単位の換算 | 品目に入り数を持たせ、仕入れの単位で入れて使う単位で減らす（第29.9節） | 切り |
| 公開 | 在庫を Web に出す（第29.12節） | 切り |
| 予約との引き当て | 予約で使える数を減らす（第29.13節） | 切り |
| 発注の案 | 残りわずか・無くなる見込みで、発注の案とメールの下書きを作る（第29.14節） | 入 |

| 項目 | 規定 |
|---|---|
| 置き場所 | 管理者ページの「拡張機能」の在庫管理の欄（名刺管理の既定の範囲と同じ所。第12.13節） |
| AI の提案 | 品目を取り込んだとき、中身から入れたほうがよい機能を**秘書が提案する**（「使用期限のある品があります。ロットと使用期限を使いますか」）。入れるのは管理者。人に一から考えさせない（ADR-0028） |
| 切ったとき | 記録は消さない。入れ直せば戻る |

#### 29.4.1 導入のときに会社が設定すること（第 0.156.0 版）

**導入のときに、会社が次を設定する。** 設定の案は AI が今の表計算・納品書・品目の写真から作り、**決めて保存するのは会社**である。後からいつでも変えられる。

| 区分 | 設定する項目 |
|---|---|
| 機能 | ロットと使用期限・単位の換算・公開・予約との引き当て・発注の案の入り切り（第29.4節） |
| 場所 | 倉庫と棚（1 か所だけなら設定しなくてよい）・棚のラベルを使うか |
| 分類 | 品目の分類（公開の区分にも使う） |
| 残りわずか | 残りわずかの目安の**既定の数**（**品目ごとに変えられる**）。会社が目安を決めていない品目は、需要の予測（第29.14節）の目安を使う |
| 仕入先 | 仕入先ごとの発注の方法（メール・Web・電話）・連絡先・仕入れにかかる日数（分からなければ 7 日） |
| 公開 | 出し方（埋め込みのページか JSON か）・出す品目と項目・数を出すか状態だけか・色分けの境目（多い・残りわずか・終了）。承認は第29.12節 |
| 予約 | 予約のサービスとのつなぎ方（口があれば接続・無ければ画面と秘書・手元の自動操作。第29.13節） |
| 棚卸し | 棚卸しの頻度（知らせの予定）・対象（全体か棚ごとか） |
| 在庫の正 | M2Office を在庫の正とするか、ほかのソフト（販売管理など）を正とするか（ほかのソフトとのつなぎは Phase 2） |
| 知らせ | 残りわずか・無くなる見込み・使用期限を知らせる相手（最近使った人。いなければ管理者。人の一覧は作らせない。第29.14節） |
| 仕入先の画面 | パソコンの在庫管理の「仕入先」で、名前・発注の方法（メール・Web・電話）・連絡先・仕入れにかかる日数を足し、直す。品目の詳細で仕入先と仕入れにかかる日数を選ぶ（第 0.163.0 版） |

| 項目 | 規定 |
|---|---|
| 足りない設定 | 止めずに、何が足りないかを画面と秘書で示す |
| 画面 | 管理者ページの「拡張機能」の在庫管理の欄。説明文を常に出さない（原則 u11）。分からなければ秘書に聞く |

### 29.6 品目

| 項目 | 規定 |
|---|---|
| 持つもの | 名前、公開する名前（例: 「ハンドクリーム」と商品名「〇〇 ハンドクリーム 50g」を分けて出すため）、自社のコード（任意）、バーコード（1 つの品目にいくつでも）、分類（例: 消耗品・販売品・材料、国産・輸入）、単位、入り数、販売価格（任意。税込か税抜か）、**社員価格**（任意。第 0.324.0 版）、写真（任意）、**残りわずかの目安**（既定は会社の設定。第29.4.1節）、メモ、使うか止めたか |
| 作り方 | 画面で 1 件ずつ、**CSV・Excel で取り込み**（今の Excel から。列の見出しを AI が読む。人に対応表を作らせない。ADR-0028）、知らないバーコードを読んだときにその場で作る |
| はじめの数 | 画面で品目を作るとき、**いまの数**を単位と並べて入れられる。入れれば入庫（理由「はじめの数」）として記録する。入れなければ 0 で作る（第 0.158.0 版） |
| 単位の欄の数 | 単位は数え方の呼び名（個・本・冊）である。**作るときに単位の欄に数（「3」「3本」）が入っていたら、尋ねずに数として読み**、単位は呼び名（無ければ「個」）にし、そう読んだことを一度だけ示す（ADR-0028）。直すときに数を入れたら断り、数は記録の欄で入れるよう示す（第 0.158.0 版） |
| 取り込みで直す | 同じバーコード・自社のコード・名前の品目があれば直し、無ければ作る。**在庫の数は新しく作った品目にだけ入れる**（今ある品目の数を取り込みで上書きしない。数を合わせるのは棚卸し）。取り込めなかった行は、行の番号と理由を返す |
| 名前を埋める | 写真のパッケージの文字から名前を読み取って埋める。**読めなければ空にし、推測で埋めない**。JAN の外部の台帳は Q-111 |
| JAN から名前を引く | 知らないバーコード（JAN・GTIN）から品目を作るとき、**Gemini に Google 検索を使わせて、そのコードの商品名・メーカー・分類を調べ、品目を作る欄に入れておく**（第 0.216.0 版、Q-111 を決定）。人はいつもどおり、名前を見て保存する（確かめの手順を足さない。ADR-0028） |
| 引き方の決まり | 検索で見つけた商品の JAN が、読んだコードと**一致すると確かめられたときだけ**埋める。確かめられなければ空のままにし、「見つかりませんでした」とだけ示す（推測で埋めない）。検索の結果は外部のデータとして扱い、指示として読まない（不変則 I-6）。送るのはコードだけで、会社のデータは送らない |
| 引くとき | パソコンの画面で知らないバーコードを読み（USB のリーダー、または探す欄に数字を入れて Enter）、「新しい品目にする」を選んだとき。名前と分類をもう入れていれば上書きしない。調べている間も入力できる |
| 費用と回数 | 会社の Gemini の利用料に含める（1 件あたりわずか）。同じ会社で同じコードを 24 時間以内にもう一度引くときは、前の結果を使う |
| 引かないとき | 会社の AI の方針が「ローカルだけ」のとき（外部の AI を使わない。第16.3.7.1節）、Gemini の鍵が無い開発の環境のとき。どちらも、いつもどおり空の欄で作る |
| 販売価格 | **公開の表に出すための値**で、在庫の金額（評価）ではない（第29.18節） |
| 社員価格 | 社員に売るときの値段（第 0.324.0 版で三浦さんの依頼で足した）。品目の詳細で入れ、CSV・Excel で取り込み・書き出しできる（見出しの「社員価格」「社販」などを読み、販売価格と取り違えない）。税込か税抜かは販売価格と同じ。**Web への公開には出さない**（社内の値段のため）。販売管理とのつなぎには、渡すと承認したときだけ渡す（第29.20.1節）。在庫の金額（評価）ではない |
| 止める | しばらく使わない品目は止める（記録は残す。また使うに戻せる）。在庫が残っていれば止められない。もう扱わない品目は削除する（第29.6.3節） |

#### 29.6.1 区分・消費税率・一覧の絞り込み・販売品の在庫額（第 0.391.0 版で案、第 0.392.0 版で確定して実装。Q-242）

2026-10-19 に三浦さんが、品目の一覧を分類などで絞り込めるようにし、販売品と消耗品を列で分け、販売品の在庫額の合計が分かるようにし、販売品に消費税率を設定できるようにするよう依頼し、区分を 4 つに固定して案のとおりに確定した。

| 項目 | 規定 |
|---|---|
| 区分 | 品目に**区分**を持つ。**販売品・消耗品・原材料・その他の 4 つに固定する**（2026-10-19 に三浦さんが決めた）。分類（自由な名前。例: 化粧品・飲料）とは別に持つ。一覧では区分と分類をそれぞれの列に出す |
| 区分の決め方 | 品目の追加と詳細で選ぶ。追加のときの既定は消耗品で、**販売価格を入れると販売品にする**（選び直せる）。CSV・Excel の取り込みは「区分」の列を読み（4 つのどれでもない値はその他。列が無ければ同じ決め方）、書き出しにも出す。詳細で販売価格を入れはじめたとき、消耗品のままの品目は販売品にする（選び直せる） |
| いまの品目 | 移行のとき、分類の名前に「販売」を含むか、販売価格の入っている品目を販売品に、分類の名前に「原材料」「材料」を含む品目を原材料に、ほかを消耗品にする |
| 消費税率 | **販売品だけ**に持つ。10%（既定）か 8%（軽減税率。飲食料品など）。品目の詳細・取り込み・書き出しで扱う。消耗品には出さない |
| 一覧の絞り込み | 一覧の上に、**区分**（すべて・販売品・消耗品・原材料・その他）・**分類**（いまある分類から選ぶ）・**状態**（すべて・残りわずか・無くなる見込み・期限が近い・期限切れ）の絞り込みを置く。今の探す欄（品名・コード・バーコード）と「止めた品目も出す」と組み合わせて効く。選んだ絞り込みは、その端末で覚えておく |
| 販売品の在庫額 | 一覧の上に、**絞り込んだ販売品の在庫額の合計**を出す（例: 「販売品の在庫額（売価）: 税込 123,400 円（税抜 112,182 円）・28 品目」）。品目ごとに「在庫（帳簿の数）− 期限切れ」×販売価格で出し、税込と税抜は品目の消費税率で直す（端数は合計で 1 回、会社の端数の扱い）。**販売価格の無い販売品は数えず、その数を添える**（推測で埋めない） |
| 在庫額の位置付け | **売価で見た目安**であり、在庫の評価（仕入れ値による決算の棚卸資産。Q-108）ではない。会計に渡さず、承認も求めない（お金の確定ではない）。社員価格は使わない |
| 見られる人 | 在庫管理を使える人（販売価格をいま見られる人と同じ） |
| ほかへの効き | Web への公開の「品目を選ぶ」の既定（いまは分類の名前に「販売」を含むもの）を、区分が販売品の品目にする（第29.12.2節）。外部のアプリの「商品の一覧を読む」で販売価格を渡すと承認していれば、消費税率も渡す（第13.4.2節） |
| 行わないこと | 在庫の評価の方法の選択（Q-108 のまま）、区分を会社が自由に増やすこと（4 つに固定）、販売品のほかの区分の在庫額（仕入価格と利益率は第 0.399.0 版で第29.6.2節に移した） |

**実装（第 0.392.0 版）**: 品目の表 `inventory_items` の `kind`（`sale`・`supply`・`material`・`other`）と `tax_rate`（10・8）（移行 147。いまの品目を上の決め方で埋めた）。取り込みは見出し「区分」「品目区分」「在庫区分」「種別」を区分として読み（分類より先に見る）、「消費税率」「税率」を読む。書き出しの列に「区分」「消費税率」を足した。一覧の API は、絞り込みの「無くなる見込み」の品目（見張りと同じ計算）と会社の端数の扱いも返す。在庫額は画面で絞り込んだ品目から出す（`inventorySaleValue`。`packages/shared`）。外部のアプリの「商品の一覧」の `price` に `taxRate` を足した（後方互換）。Web への公開と外部のアプリの「品目を選ぶ」の既定は区分が販売品の品目にした。

**画面の上の段の並べ方**（第 0.392.0 版。2026-10-19 に三浦さんが、ボタンが多く見にくいと求めた）: 1 段目に探す欄とよく使う操作（品目を追加・棚卸し・納品書から入庫）を置き、たまに使う操作（取り込み・書き出し・棚ラベルの印刷・スマホで開く）は「その他」のメニューにまとめる。2 段目に、欄を開くもの（場所・発注の案・仕入先・取り置き・Web へ公開・照らせなかった販売）をタブの並びで置く。3 段目に絞り込みと販売品の在庫額を置く

#### 29.6.2 仕入価格・利益率・仕入価格の比較（第 0.399.0 版で案、第 0.400.0 版〜で確定して実装。Q-244）

2026-10-19 に三浦さんが、仕入価格を入れられるようにし、販売価格と同じように仕入価格の比較を行い、販売価格のある品目は利益率の列を出すよう依頼した。
第29.21.1節の「仕入れの単価の記録」（7）と「原価と粗利の目安」（10）にあたる。**決算の在庫の評価（評価の方法の選択・棚卸資産の確定。Q-108）は、引き続き行わない**（ここで出すのは目安）。案のとおりに確定した（2026-10-19）。

| 項目 | 規定 |
|---|---|
| 仕入価格 | 品目に**仕入価格**（使う単位 1 つあたり）を持つ。税込か税抜かを持つ（既定は税抜。仕入れは税抜で扱うことが多いため）。品目の詳細・追加・取り込み（見出し「仕入価格」「仕入値」「原価」「仕入単価」など）・書き出しで扱う。区分を問わず入れられる（消耗品・原材料の費用の目安にもなる） |

| 利益率 | 販売価格と仕入価格のある品目に、**利益**（販売価格 − 仕入価格。1 つあたり）と**利益率**（利益 ÷ 販売価格）を出す。どちらも品目の消費税率で税抜にそろえて計算する。一覧の「列」（はじめは隠す列）と品目の詳細に出す |

| 仕入価格の比較 | 販売品の相場（第29.24節）と同じ形で、**仕入れの相場**を調べる。Web の調べもので、同じ商品の卸・業務用・ケース売りの価格を探し、入り数で割って 1 つあたりにそろえ（同じ商品と確かめられたものだけ。推測しない）、自社の仕入価格と比べる。位置は「安く仕入れている・相場並み・高く仕入れている」（中央値から ±10%）。出典（店・URL・ケースの価格と入り数）を並べる |

| 見られる人 | **仕入価格・利益・利益率・在庫額（仕入価格）・仕入れの相場は、在庫管理の利用範囲の管理者だけ**が見て直せる（第29.21.1節の 10 と同じ）。ほかの人には API も画面も出さない。秘書も、管理者にだけ答える |

| 行わないこと | 決算の在庫の評価（評価の方法の選択・棚卸資産の確定・会計への連携。Q-108）、価格を自動で変えること、仕入先ごとの価格の一覧を人に作らせること |

**実装（第 0.400.0 版。仕入価格・利益率）**: 品目の表の `purchase_price`・`purchase_tax_included`（移行 149）。利益と利益率は `inventoryMargin`、在庫額（仕入価格）は `inventoryCostValue`（`packages/shared`）。在庫の API は、利用範囲の管理者でない人への**どの口の答えからも** `purchasePrice`・`purchaseTaxIncluded` を取り除き（`withoutPurchase`。口ごとに直す抜けを無くすため、出口でまとめて行う）、管理者でない人が仕入価格を送れば 403 で断る。取り込み・書き出しの仕入価格の列も管理者だけ。納品書の読み取りは、行の単価（と税込か）も読むようにし（行の金額・合計・税額は読まない）、入庫のときに仕入価格を直す。直した金額は入庫の結果の `purchasePrice` に入れ、文（`text`）には入れない（秘書の答えや管理者でない人の画面に出さないため）。画面は、品目の詳細の仕入価格（管理者だけ）と利益・利益率、一覧の「列」のはじめは隠す列（仕入価格・利益・利益率・在庫額（仕入価格）。管理者だけ）

**実装（第 0.401.0 版。仕入価格の比較）**: `researchItemPurchase`（`packages/core/src/inventory/market.ts`）。Web の調べもので同じ商品の卸・業務用・ケース売りの価格を探し、出典の番号と入り数（`pack`）の付いた価格だけを取り出して、1 つあたりの税抜にそろえる（入り数の無い価格・番号の合わない価格は捨てる）。自社の仕入価格も 1 つあたりの税抜にそろえて比べる（`purchaseExTax`）。結果は相場の表に種類 `purchase` で残す（移行 149 の `kind`）。API は `GET /v1/inventory/market?kind=purchase`・`POST /v1/inventory/market/check`（`kind: purchase`）で、どちらも利用範囲の管理者でなければ 403。品目の相場の履歴（`GET /v1/inventory/items/:id/market`）は、管理者でない人には仕入れの相場を除いて返す。秘書のツール `inventory.market`・`inventory.check_market` は `kind: purchase` を受け、頼んだ人が管理者でなければ「見られません」と返す。月の見回りは仕入価格のある品目の仕入れの相場も調べ、相場より 20% を超えて高く仕入れている品目を知らせる。画面は「価格の比較」のタブの「販売価格・仕入価格」の切り替え（管理者だけ）と、品目の詳細の「仕入れの相場」（出典ごとにケースの価格と入り数を添える）

#### 29.6.3 品目の削除（第 0.417.0 版で案、第 0.418.0 版で確定して実装。Q-252）

2026-10-20 に三浦さんが、製造中止になった商品などは「止める」ではなく削除したいと求めた。
それまでは「止める」しかなく、止めた品目は「止めた品目も出す」で一覧に戻り、バーコードも付いたまま残った（同じバーコードの新しい商品を登録できない）。案のとおりに確定した（2026-10-20）。

| 項目 | 規定 |
|---|---|
| 止めると削除の違い | **止める**は、しばらく使わないが、また使うかもしれない品目（一覧の「止めた品目も出す」で見え、使うに戻せる）。**削除**は、もう扱わない品目（製造中止・間違えて作った・重なった品目）。どこにも出さない |
| 削除できる人 | 在庫管理の利用範囲の管理者（止めると同じ） |
| 削除できるとき | 在庫が 0 で、取り置き中の引き当て・入荷待ちの発注が無いとき。残っていれば「在庫が 3 個残っています」のように理由を出して断る（数を 0 にするのは出庫か調整。黙って捨てない） |
| 記録の無い品目 | 入出庫・棚卸し・発注の記録が 1 つも無い品目（作っただけ・間違えて作った）は、**品目ごと跡形なく消す** |
| 記録のある品目 | 入出庫の記録は追記のみで消さない（第29.16節）。品目は「削除した」状態にし、**一覧・探す・スマホ・秘書・Web への公開・外部のアプリ・予約のメニューの対応・見張り・需要の予測・発注の案のどこにも出さない**（「止めた品目も出す」にも出さない）。過去の入出庫の記録・発注書・棚卸しの記録には品名をそのまま出す（記録を読めるようにするため） |
| バーコード | 削除した品目のバーコードは外す。同じバーコードを新しい品目に付け直せる（同じ JAN で中身の変わった新しい商品のため） |
| 押す場所 | パソコンの品目の詳細の「止める」の隣に「**削除**」。止めた品目の詳細にも出す。確かめの画面は挟まず、削除の直後に「〇〇を削除しました」と「**取り消す**」を出す（取り消すと、品目とバーコードを元に戻す。バーコードがほかの品目に付いていれば、それだけを戻さず、そう伝える） |
| スマホの登録の「取り消す」 | 登録した直後の「取り消す」（第29.11.2節）は、止めるのではなく**削除**にする（バーコードが残って、読み直すと「登録済み」と出るのを避ける） |
| 終売の品目 | 終売の印（第29.24.1節）が付き、在庫が 0 になった品目は、品目の詳細に「削除」を目立たせて出す。自動では削除しない（会社の台帳から品目を消すのは人の判断） |
| 監査ログ | 品目の削除と、削除の取り消しを残す（品名・バーコード・記録があったか） |
| 行わないこと | 入出庫の記録・発注・棚卸しの記録を消すこと、削除した品目の一覧を見せる画面（削除した品目は監査ログで追える）、在庫が残る品目の削除 |

**実装（第 0.418.0 版）**: 品目の表 `inventory_items` の `deleted_at`・`deleted_by`（移行 154）。置き場の `listItems`・`getItem`・`findItemByCode` は削除した品目を返さない（一覧・探す・スマホ・秘書・公開・外部のアプリ・見張り・需要の予測はどれもここを通る）。`InventoryService.deleteItem` は在庫・取り置き・入荷待ちの発注を確かめ、記録（入出庫・棚卸しの行・発注の行・引き当て）が無ければ `purgeItem`（相場の記録も消し、バーコード・ロット・いまの数・メニューの対応は外部キーで消える）、あれば `setItemDeleted`（バーコードとメニューの対応を外す）。監査ログは `inventory.item.delete`・`inventory.item.restore`。API は `DELETE /v1/inventory/items/:id`（管理者）と `POST /v1/inventory/items/:id/restore`（削除した本人が 1 時間のうち。削除する前の品目は API のプロセスが覚える）。スマホの登録の取り消し（`POST /v1/inventory/register/:id/undo`）も、入れた数を戻したあとに削除する。画面は、品目の詳細の「止める」の隣の「削除」（終売の印があり在庫が 0 なら枠のある赤いボタン）と、一覧の上の「〇〇を削除しました」「取り消す」

### 29.9 在庫の増減と単位の換算

**在庫の数は、入出庫の記録の合計で決まる。** 記録は足していくだけで、取り消しは逆の記録を足す。誰がいつ何をしたかが残る。

| 記録の種類 | 内容 |
|---|---|
| 入庫 | 数を足す（仕入・返品の戻りなど） |
| 出庫（第 0.406.0 版で「使用」から呼び方を改めた） | 数を引く。用途（販売・社内消費・廃棄・その他）を選ぶ（第 0.408.0 版。第29.9.1節） |
| 移動 | 場所から場所へ |
| 調整 | 棚卸しの確定と数の直し。理由を必ず残す |

| 項目 | 規定 |
|---|---|
| 単位の換算（入り切り） | 在庫は**いちばん小さい使う単位**（例: 回）で持つ。入庫は仕入れの単位（箱・本）で入れ、入り数で換算する（「2 本」→「10 回」）。画面は両方で出す（「10 回（2 本）」） |
| 入れ方 | 画面で品目と数を選ぶ、バーコードを読む、**納品書の写真**（AI が行ごとに品名・品番・数・ロット・使用期限を読み、品目に照らして入庫にする。確認を挟まず、照らせない行だけを残す。ADR-0028。金額は使わない） |

#### 29.9.1 出庫を速く ― 用途を選ぶだけにする（第 0.407.0 版で案、第 0.408.0 版で確定して実装。Q-247）

2026-10-19 に三浦さんが、出庫がいちばん多い操作なので手順をできる限り減らし、理由を文で打つ手間をなくし、社内消費や販売を簡単に指定できるようにするよう依頼し、案のとおりに確定した。

**それまでの手順**: パソコンは、一覧で品目を開く → 「出庫」を選ぶ（開くと「入庫」が選ばれている）→ 数を打つ → 理由を文で打つ（任意）→ 「記録する」の 4〜5 手。
スマホは、「出庫」→ 読む → 数を合わせる → 「記録する」で、品目ごとに 2 手（読む・記録する）かかる。

| 項目 | 規定 |
|---|---|
| 用途 | 出庫に**用途**を持つ。**販売・社内消費・廃棄・その他の 4 つに固定**する（会社が増やさない。区分と同じ考え。第29.6.1節）。ボタンで選び、文は打たない。理由の文の欄は出さず、パソコンだけ「メモ」を押すと開く（任意） |
| 用途の既定 | **その品目で前に選んだ用途**（会社の中で最後の出庫）。前が無ければ、区分が販売品なら販売、ほかは社内消費。たいていは選び直さずに済む |
| パソコン: 一覧から出庫 | 一覧の**先頭に「出庫」の列**を置き、各行にカートの印（🛒）を置く（2026-10-19 に三浦さんが、行の中のボタンでは見た目が良くないとして求めた）。押すと、その場に小さな欄（数は 1・用途は既定）が開き、**Enter か「決定」で記録**する（2 手。品目の詳細へ移らない）。数を変えるときだけ打つ |
| パソコン: バーコード | 一覧の探す欄で USB のリーダーで読むと、その品目の出庫の欄が開く（数 1）。同じ品目を続けて読むと 1 つずつ増え、別の品目を読むと選び直す（前の品目は記録しない。第 0.414.2 版）。手元は探す欄に置いたままにし、探す欄が空のときの Enter で記録、Esc で閉じる（数を打つ欄に手元を移すと、続けて読んだバーコードの数字が入るため。数は − ＋ で変える） |
| パソコン: 品目の詳細 | 記録の欄は、はじめから「出庫」を選び、数に 1 を入れて置く（入庫・移動・調整は選び直す） |
| スマホ | 「出庫」→ 読む → 「決定」のまま、カードに用途のボタンを足す（既定を選んだ状態）。**記録するのは「決定」を押したときだけ**（ボタンの言葉は第 0.414.3 版で「記録する」から「決定」に改めた。利用者になじむ言葉にするため。2026-10-20 に三浦さんが求めた）。別の品目を読む・選ぶと選び直し、前の品目は記録しない（第 0.414.2 版。2026-10-20 に三浦さんが、選び直すと記録を押していないのに出庫されるのは問題と指摘した。それまでは別の品目を読むと前の品目を記録していた） |

| 秘書 | 「ハンドクリームを 2 個売った」「手袋を 1 箱使った」「期限切れの乳液を 3 本捨てた」の言葉から、用途を推論して記録する（確認は求めない） |
| 外部のアプリの販売 | 販売の通知からの出庫（第29.20.1節）は販売。予約で使ったもの（第29.13節）は社内消費 |
| 見え方 | 記録の一覧と書き出しに用途を出す |
| 需要の予測 | **廃棄は「使う速さ」に入れない**（売れた・使った数ではないため）。減り具合（第29.14.1節）・見張り・需要の予測は、販売・社内消費・その他の出庫から数える |

| 行わないこと | 用途を会社が増やすこと、用途ごとの金額（売上・原価。お金の機能は扱わない）、記録のたびの確認 |

**実装（第 0.408.0 版）**: 入出庫の記録 `inventory_moves` に `purpose`（`sale`・`internal`・`disposal`・`other`。出庫のほかは null）を足し、いまの記録を上の決め方で埋めた（移行 151）。用途を省いた出庫は、販売の通知は販売・予約は社内消費・ほかはその品目の既定（`InventoryService.recordMove`）。品目の一覧は既定の用途 `outPurpose` を返す。取り消しの記録は元の用途を引き継ぐ。減り具合・需要の予測・見張りの使う速さは廃棄を除いて数える。API `POST /v1/inventory/moves` の `purpose`、秘書の道具 `inventory.move` の `purpose`（言葉から推論）、記録の書き出しの「用途」の列。画面は一覧の出庫の欄（`QuickOut`）・品目の詳細の記録の欄・スマホの出庫（`packages/web/src/inventory-out.tsx` の用途のボタンと「取り消す」）。

### 29.10 棚卸し

#### 29.11.2 スマホでバーコードを読んで品目を登録する（第 0.413.0 版で案、第 0.414.0 版で確定して実装。Q-250）

2026-10-20 に三浦さんが、スマホのページにバーコードを読んで登録するメニューが無いので分からなかった、
新しい商品をスマホでバーコードを読んで自動で登録できないか、と求め、案のとおりに確定した。それまではスマホで知らないバーコードを読むと「知らないバーコードです」と出るだけで、
品目を作る・バーコードを結び付けるのはパソコンの画面でしかできない。

| 項目 | 規定 |
|---|---|
| メニュー | スマホのページのはじめの画面に「**登録**」のボタンを足す（入庫・出庫・棚卸し・探すと同じ大きさ・色とアイコンつき。5 つ目は横いっぱい） |
| 読む | カメラで読む（読めなければ数字を打つ）。棚のラベルを読んだら棚を選ぶだけ（いまと同じ） |
| 知っているバーコード | 「〇〇のバーコードです」と、その品目の使える数と置き場所を出す（何も登録しない） |
| 知らないバーコード | AI が JAN で商品名・メーカー・分類を Web で調べ（第29.6節の「JAN から名前を引く」）、見つかった名前を入れた**登録のカード**を出す。カードでは名前・区分（既定は消耗品）・単位（既定は「個」）・いまの数（＋・−。既定 1。0 にもできる）を指で整えられる（区分を販売品にすると販売価格の欄を出す）。**「決定」を押したときに品目を作り**、バーコードを付け、いまの数を入庫として記録する。**読んだだけでは作らない**（2026-10-20 に、読んだだけで作られてしまう件。人の決めた品目の台帳に、押さずに品目が増えるのを避ける） |
| 同じ名前の品目 | 作る前に、同じ名前（または名前を含み合う）でバーコードの無い品目があれば、作らずに「**〇〇に結び付ける**」と「別の品目として作る」を出す（同じ品目を二重に作らないため。2026-10-19 に同じ名前の品目が重なった件）。名前を打って「決定」したときも同じに確かめる。「別の品目として登録する」で登録のカードに進む |
| 見つからないとき | 名前の欄を空にした登録のカードを出し、打って「決定」。名前で探して「既にある品目に結び付ける」もできる。どちらも「スキップして次を読む」で次の商品に進める |
| 取り消し | 作った直後に「〇〇を登録しました」と「取り消す」を出す（入れた数を戻し、作った品目を削除する。第29.6.3節。第 0.418.0 版までは止めていた）。間違えて作っても戻せる |
| 入庫・出庫・棚卸しで知らないバーコードを読んだとき | 「知らないバーコードです」に「**登録する**」を添え、押すと上と同じ流れで作り、終わったら元の作業に戻る（作った品目をそのまま入庫・出庫できる） |
| 権限 | 在庫管理を使える人なら誰でも登録できる（パソコンの「品目を追加」と同じ） |
| 外へ渡すもの | バーコードの数字だけ（いまの「JAN から名前を引く」と同じ） |
| 行わないこと | 販売価格・仕入価格を Web から推して入れること（相場の調べもの（第29.24節）は別）、品目の写真を自動で撮ること |
| 見つからないとき（第 0.414.5 版） | 「**スキップして次を読む**」で閉じて次の商品を読める（2026-10-20 に三浦さんが求めた）。カメラが同じコードを読み続けても、表示中のコードは調べ直さない |

**実装（第 0.414.0 版）**: API `POST /v1/inventory/register`（`code`・`name`・`force`。答えは `known`・`location`・`notFound`・`similar`・`created`。商品名は `JanLookupService` で調べ、同じ名前は空白と全角・半角の違いを無くして比べる）と `POST /v1/inventory/register/:id/undo`（作った本人が 1 時間のうち。API の中に覚えるため、API を起こし直すと取り消せなくなり、そのときは管理者が品目を止める）。画面は `MobileInventory.tsx` の「登録」（`RegisterFlow`・`CreatedCard`）と、入庫・出庫・棚卸し・探すの読み取り（`Picker`）で知らないバーコードを読んだときの「登録する」（終わったら「〇〇に戻る」で元の作業へ）。

#### 29.11.3 JAN から商品名を引く方法を増やす（第 0.415.0 版で案。第 0.416.0 版で Yahoo!ショッピングを先に実装。Q-251）

2026-10-20 に三浦さんが、JAN コードから商品を探すもっと良い方法は無いかと尋ねた。
いまは Gemini に Google 検索をさせて JAN と商品を結び付けている（第29.6節。Q-111）。Web のページに JAN が載っていない商品は見つからず、
開発の環境のように Web の調べものが使えないところでは、いつも「見つかりませんでした」になる。

| 項目 | 規定（案） |
|---|---|

### 29.12 公開（Web への反映。入り切り）

**在庫を Web ページにそのまま出す。** Web サイトには**一度貼るだけ**で、あとは入出庫のたびにすぐ変わる。

| 項目 | 規定 |
|---|---|
| 出し方 | **① 埋め込みのページ**: M2Office が会社ごとの公開用のページ（表）を出し、Web サイトに iframe で貼る（サイトの作りは問わない。貼るのは会社か、サイトの制作を頼んでいる会社）。**② 公開のデータ**: 同じ中身を JSON で出し、サイトの側で好きな見た目に組める。どちらもログインは要らない。Web サイトの管理の鍵を M2Office に預からない |
| 出すもの | 公開すると決めた品目だけ。分類ごとに、公開する名前・商品名・**使える数か状態**・販売価格・最終更新の日時。**数を出すか、状態（在庫あり・残りわずか・終了）だけを出すかは会社が決める** |
| 色と状態 | 使える数が残りわずかの目安（会社の設定。品目ごとに変えられる。第29.4.1節）以下なら「残りわずか」、0 なら「終了」。最終更新の日時を出す |
| すぐ反映 | 入出庫・引き当て・期限切れのたびに、公開の中身を作り直す。ページは開くたびに最新を読む |
| **承認** | 公開は**社外に出るもの**である（第9.4.0節）。**何を公開するか（品目・出す項目・数か状態か）を、管理者が一度承認する**。承認した範囲での数の変化は、承認なしに自動で流す（1 件ずつ承認させると、すぐ反映できないため）。公開する品目・項目を変えたときは承認し直す。承認と変更は監査ログに残す |
| 出さないもの | 仕入れ値、**社員価格**、ロット、場所、記録した人、内部のコード、**予約した人**。公開のデータに入る項目は、承認した項目だけ |
| 止める | 公開を止めると、埋め込みのページは「表示できません」になる。止めたことを監査ログに残す |
| 負荷 | 公開のページとデータは作り直したものを置いて配り、見る人が多くても在庫の表を直接読まない |

#### 29.12.1 公開の作り（第 0.213.0 版で実装。段 5）

| 項目 | 規定 |
|---|---|
| 置き場所 | 在庫の画面の「Web へ公開」（ボタンの名前は第 0.215.2 版で改めた）。**管理者だけ**が開く。会社の設定で「Web への公開」を入にした会社にだけ出す |
| 選ぶもの | 公開する品目（止めた品目は選べない）・分類で分けて出すか・販売価格を出すか・**数を出すか状態だけか**。既定は、品目はすべて・分類あり・価格あり・状態だけ |
| 承認 | 選んだ中身を見本の表で確かめ、「この内容で公開する」を押すことが承認である（**押した管理者が承認者**）。承認した人・日時・中身を残し、監査ログに `inventory.publication.approve` で残す。中身を変えたら押し直す。押し直すまで、前に承認した中身のまま出る |
| 新しい品目 | 承認のあとに足した品目は、**承認し直すまで出さない** |
| 状態 | 使える数が 0 以下なら「終了」、残りわずかの目安以下なら「残りわずか」、ほかは「在庫あり」。数を出す会社は、あわせて使える数と単位を出す |
| 作り直すとき | 入出庫・取り消し・棚卸しの確定・品目の修正と止め・取り置きの出し入れのあと（続けて起きたものはまとめて 1 回）と、日本時間の日付が変わったとき（使用期限を過ぎた数を外すため）。公開を承認・再開したとき |
| 公開の URL | 埋め込みのページ `/v1/public/inventory/<鍵>`、公開のデータ `/v1/public/inventory/<鍵>.json`。鍵は推測されにくい 32 字で、最初の承認のときに作る。ログインは要らず、会社の判定より前に受ける |
| 貼り方 | 管理者に、埋め込みのページを貼る `iframe` の 1 行と、データの URL を出す（写して制作会社に渡せる） |
| 埋め込みとデータの決まり | ページは他のサイトの `iframe` に入れてよい（`frame-ancestors *`）。スクリプトを持たず、外のものを読まない。データはどのサイトからも読める（`Access-Control-Allow-Origin: *`。ログインの情報は使わない）。どちらも作り直した中身だけを返す |

| 再開 | 止めたあとは、もう一度「この内容で公開する」を押す（承認し直す）。鍵は変えない |

#### 29.12.2 公開を分ける（第 0.219.0 版。三浦さんの依頼）

**1 社で公開をいくつも持てる。** Web サイトのページごとに違う品目を出したい（あるページには販売品、別のページには別の分類の品目など）ため、
公開を **1 社で 8 つまで**（案。三浦さんは「少なくとも 4 つ」と依頼）作り、それぞれに別の URL を持たせる。

| 項目 | 規定 |
|---|---|
| まとまり | 公開 1 つ（名前・品目・出し方・URL の鍵・状態・承認）を 1 つのまとまりとし、**まとまりごとに別々に承認・止める・削除する**。ほかのまとまりには影響しない |
| 名前 | 管理の画面のタブに出す名前（例: 「店頭の販売品」「化粧品」）。公開のページには出さない。名前を変えても承認し直さない |
| 画面 | 「Web へ公開」の欄の上にまとまりのタブを並べ、切り替えて選ぶ・確かめる・承認する（第29.12.1節と同じ欄）。「＋」で新しいまとまりを足す（名前は「公開 2」のように自動で付け、あとで変えられる） |
| 品目を選ぶ | 区分と分類のボタンで選ぶ（第 0.404.0 版。それまでは分類ごとの「この分類をすべて選ぶ」。第29.12.3節）。**承認のあとに足した品目は、そのまとまりでも承認し直すまで出さない**（第29.12.1節） |
| URL | まとまりごとに別の鍵（`/v1/public/inventory/<鍵>` と `.json`）。最初の承認のときに作り、変えない |
| 削除 | **止めてあるまとまりだけ**を削除できる（公開中のページを誤って消さないため）。削除すると URL は 404 になり、元に戻せない。監査ログに `inventory.publication.delete` で残す |
| 作り直し | 在庫が変わったら、公開中のまとまりをすべて作り直す |
| 移行 | 第 0.218.0 版までの公開は、名前「公開 1」のまとまりとして引き継ぐ（URL の鍵は変わらない。移行 061） |

#### 29.12.3 区分と分類で選ぶ（第 0.403.0 版で案、第 0.404.0 版で確定して実装。Q-245）

2026-10-19 に三浦さんが、Web への公開で区分でも絞り込めるようにし、「販売品のうち化粧品と日用品」のように指定したいと依頼し、案のとおりに確定した。

| 項目 | 規定 |
|---|---|
| 絞り込み | 「品目を選ぶ」の欄の上に、**区分**（販売品・消耗品・原材料・その他。いくつでも選べる）と**分類**（いまある分類。いくつでも選べる）のボタンを置く。区分と分類の両方を選べば「かつ」で絞る（例: 販売品 × 化粧品・日用品）。分類のボタンは、選んだ区分に品目のある分類だけを出す。どちらも選ばなければ、使っている品目すべてを出す |
| 選び方 | 区分・分類を選ぶと、**当たる品目をすべて選び、当たらない品目を外す**（条件で選ぶ）。そのあと品目を 1 つずつ外す・足すこともできる。「すべて」「外す」は、いま並んでいる品目に効く。それまでの「この分類をすべて選ぶ」は、この分類のボタンに置き換える |
| 条件を覚える | 選んだ区分・分類を、まとまりの中身として覚える。**あとで条件に当たる品目を足すと、欄では選んだ状態で並び**、「承認のあとに足した品目 N 件は、まだ出ていません」と出る。**出すのは承認し直したときだけ**（第29.12.1節。社外への送信の境界は変えない）。1 つずつ外した品目は、条件に当たっても外したままにする |
| 既定 | 新しいまとまりは、区分が販売品の条件で始める（第29.6.1節のいまの既定と同じ。販売品が無ければ条件なしで、使っている品目すべて） |
| 外部のアプリ | 「商品の一覧を読む」の渡す品目の選び方（第29.20.1節）も同じ欄にする（区分と分類で選び、条件を覚え、足した品目は承認し直すまで渡さない） |
| 見本 | 見本の表は、いままでどおり選んだ品目だけを出す（区分は公開のページに出さない） |
| 行わないこと | 区分と分類のほかの条件（価格の幅・在庫の有無など）、条件に当たる新しい品目を承認なしに出すこと |

**実装（第 0.404.0 版）**: 公開の中身 `InventoryPublicationScope` と外部のアプリの `InventoryCatalogScope` に条件 `rule`（`kinds`・`categories`・`excluded`）を足した（後方互換。無ければ 1 つずつ選んだもの）。条件の当たり方と本文の整え方は `packages/shared` の `inventoryRuleMatches`・`inventoryRuleItemIds`・`inventoryRuleOf`。出す・渡すのは今までどおり承認した `itemIds` だけで、条件は画面で選び直すのに使う。承認の監査ログに区分と分類を残す。画面は両方の欄で同じ部品（`InventoryItemPicker`）を使う。移行は無い（中身は JSON の列にある）。

### 29.13 予約との引き当て（入り切り）

予約を受けてから物を使う・渡す業種では、予約が入った時点で使える数を減らしたい。予約で取り置いた数を、使える数から引く。

**形**（第 0.164.0 版）: **予約そのものは外部の予約のシステムが持ち、M2Office は「どの予約に何をいくつ取り置いたか」（引き当ての台帳）だけを持つ。**
外部とは**入口の部品**でつなぎ、どの入口も同じ共通の形（出どころ・予約番号・日時・メニュー・状態）に直してから台帳に入れる。在庫の中核は外部のシステムを知らない。

```
 予約のシステム ─①通知（Webhook）─▶ 通知の受け口 ─┐
 予約のシステム ◀─②読みに行く─── 会社の接続    ─┤  共通の形に直す
 予約のシステム ◀─③画面の操作─── 手元の自動操作 ─┤  （氏名などは捨てる）─▶ 引き当ての台帳 ─▶ 使える数・公開
 受付の人・秘書 ─────────────────── 画面・秘書 ───┘
```

| 項目 | 規定 |
|---|---|
| 引き当て | 予約 1 件ごとに、品目と数（例: 体験用のセット 1 つ）を取り置く。在庫は減らさず、**使える数だけを減らす**（公開もこの数） |
| 使える数より多いとき | 断らずに取り置き、使える数がマイナスになることで知らせる（マイナスの在庫と同じ。第29.9節）。予約は予約のシステムの側で決まっており、在庫の都合で断れないため。足りない分は見張り（第29.14節）が発注の案に入れる |
| 使ったとき | 予約の人が来て使ったら、引き当てを消して使用の記録を足す（引き当てた品目を選ぶだけで済む）。予約のシステムが「来店済み」を知らせてくれれば、そのとき使用にする |
| 取り消し・来なかった | 予約の取り消しで引き当てを消す。予約の日を過ぎた引き当ては、翌朝に「使った・取り消し」を尋ねる（在庫の見張りの知らせと画面） |
| **予約のシステムとのつなぎ** | **予約の出し入れを受け取れる口（API・通知）があるかを確かめ（Q-113）、あれば会社の接続（第12.11節）としてつなぐ**。無ければ、受付が画面か秘書（「明日 10 時の予約の体験セット 1 つを取り置いて」）で引き当てる |
| 個人の情報 | 引き当てに**予約した人の氏名などを持たない**。予約の番号・日時・メニューの名前だけを持つ（第29.17節）。通知に氏名などが入っていても、共通の形に直すときに捨て、保存しない |
| 書き戻し | 予約のシステムへは**書き戻さない**（読むだけ）。社外への書き込みが生まれないため、承認の対象も増えない |

#### 29.13.1 入口（第 0.164.0 版）

| 入口 | 規定 | 段 4 |
|---|---|---|
| 画面・秘書 | パソコンの在庫管理の「取り置き」で、日時・予約番号（任意）・品目・数を入れる。取り置いた数は、一覧の「状態」の列に「取り置き 2 個」のように出す（第 0.419.0 版。2026-10-20 に三浦さんが求めた。品目の詳細では数の並びに出す。画面の言い方は「取り置き」にそろえる）。秘書に「明日 10 時の予約の体験セット 1 つを取り置いて」と頼む（付属の業務「在庫の記録」がツール `inventory.reserve` で引き当てる） | 作る |
| ① 通知の受け口 | 会社ごとに**予約の受け口**を作り（管理者。管理者ページの拡張機能の在庫管理の欄）、その URL を予約のシステムの通知の送り先に登録する。URL の鍵は推測されにくい値で、**作ったときに一度だけ見せ、M2Office はハッシュだけを持つ**。受け口は会社の判定より前に置き、鍵から会社を引く。本文は 64 KB まで。中身はデータとして扱い、指示として読まない（不変則 I-6）。**使わなくなった受け口は削除できる**（第 0.419.0 版。2026-10-20 に三浦さんが求めた。管理者。確かめの画面は挟まず、直後の「取り消す」で同じ URL のまま戻せる。削除した URL への通知は受け取らない。受け口から届いた予約と取り置きは残し、取り置きの欄で片付けられる。監査ログに残す） | 作る |
| ② 読みに行く | 通知は無いが API がある予約のシステムを、会社の接続でつなぎ、ワーカーが決まった間隔で予約の一覧を読んで差分を取る | 後の段（導入する会社の予約のシステムに合わせて） |
| ③ 手元の自動操作 | API も通知も無い予約のシステムを、お客様の側の機械の決まった操作（MCP のツール）で読む（第12.11.7.1節）。相手のパスワードを M2Office に預けない | 後の段 |

**受け口の「型」**: 予約のシステムごとに通知の項目の名前が違う。M2Office の標準の形（`id`・`startsAt`・`menu`・`status`: booked・cancelled・visited）ならそのまま読む。
違う形の通知が初めて届いたら、**AI が項目の対応（予約番号・日時・メニュー・状態と、取り消し・来店済みを表す値）を推測して受け口に覚える**（人に対応表を作らせない。ADR-0028）。日付と時刻が別の項目になっている通知は、2 つを合わせて日時にする。取り消し・来店済みの値は、推測した値に加えて、よく使われる言い方（cancel・no show・キャンセル・取消／visited・checked in・来店・完了）も読む（最初の通知に取り消しが無くても働くように）。推測には項目の名前と値の種類だけを渡し、氏名などの値は渡さない。直すときは管理者が受け口の対応を直す。

| 受け取り | 規定 |
|---|---|
| 同じ予約が何度届く | 「出どころ＋予約番号」で 1 件にまとめる。届く順番が前後しても、最後の状態にそろえる |
| 予約が入った・変わった | メニューから品目と数を決めて引き当てる（下の「メニューと品目」）。日時が変われば引き当ての日時も直す |
| 取り消された | 引き当てを消す |
| 来店済み | 引き当てを使用の記録にする |

#### 29.13.2 メニューと品目（第 0.164.0 版）

予約のシステムが持つのは「体験コース」のようなメニューの名前で、品目ではない。

| 項目 | 規定 |
|---|---|
| 推測 | **AI がメニューの名前と品目の名前から、使う品目と数を推測する**（例: 「体験コース」→ 体験セット 1 つ）。人に対応表を作らせない（ADR-0028） |

| 推論が使えないとき | 推論が一時的に使えなくても予約は受け取り（受け口は 200 を返す）、品目の分からない予約として残す。同じメニューの予約が届いたときと毎朝の見張りの前に推測し直す |

### 29.14 AI の見張り（欠品を防ぐ）

| 会社が決めた目安 | 品目ごとに会社が目安を決めて「固定」にした品目は変えない |

| 費用 | AI の利用の上限に数える（品目をまとめて 1 回に聞く） |
| 行わないこと | 在庫の金額・利益の判断（お金の機能を扱わない方針。Q-108）、自動の発注（発注は承認の後） |

**実装（第 0.383.0 版）**: `packages/core/src/inventory/demand.ts`。ワーカーが 1 時間ごとに見て、月曜の朝 6 時（日本時間）から、前の予測から 5 日たった会社だけ回す（`runDemandForecasts`）。土台は在庫の記録の使用（`usageByItem`）から決まった計算で出す（直近 4 週の 1 日あたりの使用と、去年の「今日からの 4 週」÷「今日までの 4 週」の伸び。0.5〜3 倍に収める）。AI には品目の名前・分類・使う速さ・去年の伸びだけを 100 品目ずつまとめて渡し、季節と行事を加味した倍率と理由を受け取る（読めない品目と、AI を使えない会社は去年の伸びのまま）。予測の目安は「使う速さ × 倍率 × 仕入れにかかる日数」（1 以上。使っていない品目は目安を出さない）。品目の表 `inventory_items` の `forecast_low`・`forecast_factor`・`forecast_note`・`forecast_at`（移行 145）に書く。残りわずかの目安は「会社が品目に決めた目安 → 予測の目安 → 会社の既定」の順に使い（`effectiveLow`）、使う速さと発注の数には倍率を掛け、発注の案の理由に予測の理由を添える。在庫の画面の品目に「多めに使う見込み（2 倍。年末の需要）」のように出し、朝のブリーフと秘書の在庫の答えにも理由を載せる。会社の在庫の設定の「需要の予測」で切れる（既定は入り）。**まだ使っていないもの**: 会社のカレンダーの行事と Web の調べもの（季節の流行）は見ていない（AI は季節と一般の行事だけを加味する）。先の予約は、いまは使える数から引くだけで、無くなる日の前倒し（第29.21.1節の 3）はしない


**AI が常に在庫を見張る。** 入出庫・引き当てのたびと、毎朝に見直す。

| 見張ること | 動き |

| 残りわずか | 使える数が目安以下になった品目を、**その場で**在庫管理を使う人に知らせる（お知らせ）。朝のブリーフにもまとめる |

| 発注のメール | 仕入先がメールで受けるなら、発注のメールの**下書き**を作る（Gmail）。**送るのは承認のあと**（社外への送信。第9.4.0節）。Web で発注する仕入先には、発注の案と仕入先のページへのリンクを出す。電話の仕入先には、伝える内容をまとめて出す |

**実装の決まり**（第 0.163.0 版）

#### 29.14.1 減り具合と需要の予測を見る（第 0.393.0 版で案、第 0.394.0 版で確定して実装。Q-243）

2026-10-19 に三浦さんが、在庫の減り具合を管理して需要を予測するよう依頼した。需要の予測（上の「需要の予測」）はすでに週に 1 回回っているが、画面では「多めに使う見込み」の印と発注の案にしか出ていない。**減り具合と次の見込みを、数で見られるようにする。** 案のとおりに確定した（2026-10-19）。

| 項目 | 規定 |
|---|---|
| 減り具合のタブ | 在庫の画面の 2 段目のタブに「**減り具合**」を足す。品目ごとに、直近 4 週の 1 日あたりの使用（販売品は売れた数）・その前の 4 週と比べた増減（↑↓ と割合）・あと何日で無くなるか・**次の 4 週の見込み**（1 日の使用 × 予測の倍率 × 28 日。単位つき）・予測の倍率と理由を並べる。並びは「あと何日」の短い順。上の段の絞り込み（区分・分類・状態）がそのまま効く |
| 品目の詳細 | 直近 12 週の週ごとの使用の棒グラフと、**来週の見込み**（点線の 1 本。次の 4 週の見込み ÷ 4。上に数を出す）を出す。使用の記録が無い週は 0。第 0.419.4 版で、4 週とも同じ高さの点線を 4 本並べていたのを 1 本にした（2026-10-20 に三浦さんが、同じものを 4 本出す意味がないとした）。次の 4 週の見込みの合計は、グラフの上の文に出す |
| 数え方 | 使用は「使用」の記録（販売の通知と取り置きの引き渡しを含む）から取り消しを差し引いたもの。調整（棚卸しの差）は数えない（いまの使う速さと同じ） |
| 需要の予測の残り | 販売品の予測に、**Web の調べもの（季節の流行・話題）**を加える（会社の AI の方針が許すときだけ。第32章と同じ調べもの）。会社のカレンダーの行事は、会社の予定の置き場が決まっていないため、引き続き残す |
| 行わないこと | 人に目安や予測の数を入れさせること（会社が決めた目安はいままでどおり先に効く）、予測を理由にした自動の発注 |

#### 29.14.2 予約の分を分けて数える（第 0.409.0 版で案、第 0.410.0 版で確定して実装。Q-248）

2026-10-19 に三浦さんが、Phase 2 の候補（第29.21.1節の 1〜3）を見直し、いまできることを案にするよう依頼し、案のとおりに確定した。その 1 つ目。

**いまの数え方の問題**: 先の予約の分は、取り置きとして「使える数」から引いている（第29.13節）。一方で「使う速さ」は、予約で使った過去の出庫も含めて出している。
このため、予約の多い会社では、**先の予約の分を 2 回見込み**、無くなる日を早く・発注の案を多く出しすぎる。

| 項目 | 規定 |
|---|---|
| 使う速さ | **予約の外の出庫**（予約で使った出庫 `source = reservation` を除く。廃棄も除く。第29.9.1節）だけから出す。先の予約の分は、いままでどおり取り置きとして使える数から引く |
| あと何日・発注の案 | 使える数（取り置きを引いた数）÷ 予約の外の使う速さ。発注の案の「届くまでに使う分」も予約の外の使う速さで出す |
| 減り具合の見込み | 次の 4 週の見込みは、**予約の外の見込み（使う速さ × 予測の倍率 × 28 日）＋ この先 4 週の取り置きの数**にする。品目の詳細のグラフの見込みも同じ |
| 予約の無い会社 | 予約で使った出庫が無いので、数は何も変わらない |
| 需要の予測 | 週に 1 回の予測の土台（直近 4 週・去年の同じ時期）も、予約の外の出庫で出す（予約の数は予約のほうで分かるため） |
| 行わないこと | 品目の決まらない予約を推し量って数えること、予約の入り方（先の予約の伸び）を見ること。どちらも予約のデータがたまってから（第29.21.1節の 3） |

**実装（第 0.410.0 版）**: 置き場の `usageByItem` と見張り（`InventoryService.forecast`）が予約で使った出庫（`source = reservation`）を除く。減り具合の次の 4 週の見込みに `heldUntil`（この先 4 週の取り置き。販売管理の注文の取り置きは除く）を足し、`booked` として返す。週ごとの出庫のグラフの棒は、いままでどおり実際の出庫（予約の分を含む。廃棄を除く）を出す。

#### 29.14.3 曜日の波（第 0.409.0 版で案、第 0.410.0 版で確定して実装。Q-248）

Phase 2 の候補の見直しの 2 つ目。いまは 1 日の使う量を直近 4 週の平均で出し、曜日による差を見ていない。土日に多く出る品目や、曜日で客足の違う店では、無くなる日がずれる。**推論を使わず、記録から決まった計算で出す。**

| 項目 | 規定 |
|---|---|
| 曜日の重み | 品目ごとに、直近 12 週の予約の外の出庫（廃棄を除く。第29.14.2節）を曜日ごとに合計し、営業日 1 日あたりの平均に対する比を重みとする（例: 土曜 1.8・火曜 0.6）。**営業日でない日**（会社情報の営業する曜日・祝日・お知らせで出した休業の期間。第6.6.1節）は 0 |
| 使う品目 | 8 週より前から使っていて、出庫のあった日が 20 日以上ある品目だけ。足りない品目は重みを持たず、いままでどおり平らに数える |
| あと何日 | 明日から日ごとに「1 日の量 × その曜日の重み × 予測の倍率」を引き、使える数が尽きる日までを数える（90 日まで）。曜日の重みが無い品目はいままでの割り算と同じ |
| 発注の案 | 「届くまでに使う分」を、届くまでの日ごとの量の合計にする（届いてから 2 週間分はいままでどおり平均で）。理由に曜日の波を一言添える（例: 「土日に多い」） |
| 見せ方 | 減り具合のタブの品目に、重みがいちばん大きい曜日が 1.5 以上なら「土日に多い」「月曜に多い」のような短い印を出す（曜日 2 つまで）。品目の詳細に曜日ごとの棒（7 本）を出す |
| いつ出す | 週に 1 回の需要の予測と一緒に計算し、品目に置く（毎回の画面で数え直さない） |
| 行わないこと | 時間帯の波、人に曜日ごとの数を入れさせること |

**実装（第 0.410.0 版）**: 重みは `weekdayWeights`（`packages/core/src/inventory/forecast.ts`。置き場の `weekdayUsage` が品目と曜日ごとの量・出庫のあった日の数・最初の出庫を返す）。週に 1 回の需要の予測（`forecastDemand`）が品目の `forecast_weekdays` に置く（移行 152。営業する曜日はワーカーが会社情報から渡す）。あと何日と届くまでに使う分は `forecastItem` が明日から 90 日まで日ごとに数える（営業日は会社情報の営業する曜日と祝日。お知らせで出した休業の期間は見ない）。言い方は `weekdayNote`。減り具合の行は `weekdays`・`weekdayNote` を返し、品目の詳細に曜日ごとの棒（`WeekdayBars`）を出す。

#### 29.14.4 発注の記録（第 0.411.0 版で案、第 0.412.0 版で確定して実装。Q-249）

2026-10-19 に三浦さんが、Phase 2 の候補（第29.21.1節の 4・5）の発注の記録と発注書を進めるよう依頼し、案のとおりに確定した。
いまは発注したことを記録しないため、発注してから届くまでの間も、見張りが「足りなくなりそう」と知らせ続け、発注の案も出し続ける。届かなくても誰も気づかない。

| 項目 | 規定 |
|---|---|
| 発注 | 仕入先ごとに 1 件。品目と数・発注の方法（メール・Web・電話）・発注した日・**届く予定の日**（発注した日 ＋ 仕入れにかかる日数。品目 → 仕入先 → 会社の既定の順）・状態・発注番号・発注書（第29.14.5節）・発注した人を持つ |
| 状態 | **入荷待ち**（発注した）→ **一部入荷**（一部の品目・数が届いた）→ **入荷済み**。ほかに、まだ発注していない **発注待ち**（Web・電話。メールの発注は **承認待ち**）と **取り消し** |
| 記録する時 | **メールの発注**: 発注のメールを作りはじめたら承認待ちとして記録し、**承認されて送ったら入荷待ち**にする。却下・失敗なら取り消し。**Web・電話の発注**: 発注の内容を出したあと「**発注完了**」を押すと入荷待ちにする（実際に発注したかは M2Office には分からないため、押す 1 手だけ求める）。秘書に「トナーを 2 箱発注した」と話しても記録する |
| 入荷待ちの間 | 見張りは、**使える数に入荷待ちの数を足して**残りわずか・無くなる見込みを判断する（届くまで「足りなくなりそう」を知らせない）。発注の案の数からも入荷待ちの数を引き、全部まかなえていれば案を出さない。一覧の「状態」の列と品目の詳細・発注の案に「入荷待ち 2 箱（10/24 予定）」を出す |
| 届いたとき | 入庫（画面・スマホ・納品書・秘書）のとき、その品目の入荷待ちの発注があれば、**古い発注から数を消し込む**（確認を挟まない。ADR-0028）。全部届けば入荷済み、一部なら一部入荷。納品書から入庫したときは、納品書の仕入先の発注を先に消し込む |
| 遅れ | 届く予定の日を過ぎても入荷済みにならない発注は、毎朝の在庫の知らせ（第29.14節）に「届いていない発注」として出す（発注番号・仕入先・品目・何日遅れか）。届くか取り消すまで毎朝出す。相手は発注した人と、在庫の知らせの相手 |
| 重ねない | 同じ仕入先に発注待ちがあれば、「発注の内容を出す」を押し直しても新しく作らず、その発注の品目と数・発注書を出し直す（発注番号は同じ）。メールの発注は、同じ仕入先の承認待ちがあれば作らず、承認トレイを案内する（第 0.412.2 版。2026-10-20 に三浦さんが、押すたびに発注が積み重なり同じ発注をしてしまう危険があると指摘した） |
| 画面 | 在庫の画面の「発注の案」の欄に「**発注待ち**」（発注待ち・承認待ち）と「**入荷待ち**」（入荷待ち・一部入荷）の段を分けて足し（第 0.412.2 版。それまでは 1 つの段に並べていた）、発注ごとに状態・予定の日（遅れは赤）・品目と届いた数・発注書を出す。「キャンセル」（社内の記録だけ。仕入先への連絡はしない）と「残りを入庫する」（届いていない数をそのまま入庫する）。Web・電話の発注前には「発注完了」（第 0.412.1 版で「発注した」から改め、操作は右にそろえて間を空けて並べる。2026-10-19 に三浦さんが求めた） |
| 秘書 | 「トナーは発注済み？」「届いていない発注は？」に答え、「〇〇を発注した」「〇〇の発注を取り消して」で記録する |
| 行わないこと | 仕入先へ催促のメールを自動で送ること（送るなら発注のメールと同じく承認の後。秘書に頼めば下書きを作る）、仕入先のシステムから出荷の状態を読むこと（Q-115） |

**実装（第 0.412.0 版）**: 表 `inventory_orders`・`inventory_order_lines`・`inventory_order_receipts`（移行 153）。`InventoryService` の `createOrder`・`orders`（遅れた日数 `overdueDays`）・`markOrdered`・`cancelOrder`・`reconcileOrders`（メールの発注の実行が `completed` なら入荷待ち、`failed`・`cancelled`・`expired` なら取り消し。一覧・見張りを読むときに合わせる）。入庫（`recordMove` の入庫のうち、出どころが画面・納品書・秘書のもの）で古い発注から消し込み（納品書は仕入先の名前が合う発注を先に）、入庫の取り消しで消し込みを戻す。品目の `onOrder`・`onOrderDue` を一覧に返し、残りわずか・あと何日・発注の案は使える数に入荷待ちを足して出す。発注前・承認待ちにも、今日から見た届く予定の日を置く（発注書の希望納期。発注したときに出し直す）。Web・電話は「発注前」として記録し、「発注完了」で入荷待ちにする。毎朝の在庫の知らせに「届いていない発注」の段を足し、発注した人にも届ける。API は `POST /v1/inventory/orders`（記録と発注書を作る）・`GET /v1/inventory/orders`・`POST …/:id/ordered`・`POST …/:id/cancel`。秘書の道具は `inventory.orders`（読む）と `inventory.record_order`（「発注した」の記録と取り消し。危険度 `write-internal`）。画面は発注の案の欄の「入荷待ち」の段（`OpenOrders`）と一覧の「入荷待ち」の印。

#### 29.14.5 発注書（第 0.411.0 版で案、第 0.412.0 版で確定して実装。Q-249）

| 項目 | 規定 |
|---|---|
| 作るもの | 会社の帳票の体裁（第15.2.2節・第15.2.3節。見積書と同じ型と印影）で**発注書の PDF** を作る。載せるのは、発注番号・発注日・宛先（仕入先の名前「御中」）・自社の会社名と住所と連絡先・印影・品目（品名・品番・数・単位。入り数があれば仕入れの単位）・希望の納期（届く予定の日）・備考 |
| 金額 | **載せない**（いまの発注のメールと同じ。仕入価格は目安であり、お金の確定は仕入先の請求と会計で行う。第29.18節） |
| 発注番号 | 会社ごとの連番（例: `PO-202610-001`）。発注の記録と同じ番号 |
| メールの発注 | 発注のメールに発注書の PDF を添える。**送るのは承認の後**（いままでどおり。承認の画面で PDF も開ける） |
| Web・電話・FAX | 発注の内容を出すときに発注書も作り、画面から開いて印刷できる（FAX で送る会社向け） |
| 残すもの | 発注書は会社のファイルとして残し、発注の記録から開ける |
| 行わないこと | 金額・合計・消費税を載せること、FAX を M2Office から送ること |

**実装（第 0.412.0 版）**: `renderPurchaseOrder`（`packages/core/src/files/pdf-render.ts`。見積書と同じロゴ・差出人・印影、No・品名・品番・数量の表、備考の枠）と `createOrderSheet`（`packages/core/src/inventory/order-sheet.ts`。会社のファイルとして残す）。発注の業務「発注の下書き」は入力の `attachment`（発注書）を `gmail.send` の添付に渡し、件名に発注番号を入れる。発注書は `GET /v1/inventory/orders/:id/sheet` で、在庫管理を使える人が開ける。

### 29.15 秘書と業務から使う

| 依頼の例 | 秘書の動き |
|---|---|
| 「ハンドクリームの在庫は？」 | 使える数・在庫・引き当て・期限切れを、**在庫の表を引いてその場で答える**（推論を使わない。第 0.159.0 版） |
| 「先週のコピー用紙の使用を教えて」 | 入出庫の記録から一覧にする（`inventory.history`） |
| 「A4 用紙を 2 箱入庫して」「トナーを 1 本使った」 | 記録する（`inventory.move`、write-internal）。品目が決められなければ候補を挙げて尋ねる |
| 「明日 10 時の予約の体験セット 1 つを取り置いて」 | 引き当てる（`inventory.reserve`、write-internal） |
| 納品書の写真を渡す | 付属の業務「納品書から入庫」に取り次ぐ |
| 「足りなくなりそうなものは？」 | 無くなる見込みの早い順に答え、発注の案を添える。見込みを出す見張り（第29.14節）ができるまでは、残りわずかの品目を使える数の少ない順に、その場で答える |
| 「〇〇を発注して」 | 付属の業務「発注の下書き」に取り次ぐ（メールの下書きまで。送るのは承認のあと） |

| 項目 | 規定 |
|---|---|
| 振り分け | 在庫管理を使える人の在庫の依頼は、**推論に選ばせずに見分ける**（第 0.159.0 版）。数の問いと「足りなくなりそうなものは？」はその場で答え、期間の記録の問い（「今月のコピー用紙の使用」）は秘書の調べもの、入庫・使用・移動の依頼（数と数え方がある）は付属の業務「在庫の記録」へ回す。推論に任せると、在庫の問いを組織知識の問いと取り違えて「社内の規程には書かれていません」と答えたり、ただの問いを記録の業務に回して待たせたりしたため |
| 見つからないとき | 「〇〇という品目は、在庫管理にありません」と答え、推測で数を作らない。語順が違う言い方（「A4 のコピー用紙」）は言葉を分けて探す |
| 場所を言われたとき | 問いに場所（倉庫・棚）の名前があれば、**その場所の数**で答える（「店頭在庫はいくつ？」はその場所にある品目の一覧、「店頭のハンドクリームは何個？」はその品目のその場所の数。無ければ全体の数を添える）。取り置きは品目の単位で持つため場所の数に含めない |
| 短い問い | 「店頭のコピー用紙は？」「トナーは？」「トナーまだ足りてる？」「店頭にハンドクリームある？」のように、**品目と場所の名前に、在庫を尋ねる言い回し（足りてる・ある・残ってる・もうない）だけが付いた問い**も在庫の問いとする。名前を除いてほかの言葉が残る問い（「トナーの交換方法は？」）はしない |
| 答えの長さ | 在庫の問いには**数だけを短く答える**（「トナー（黒）: 使える数 1 本。残りわずかです。」）。記憶や社内の規程を添えない |

| ツール | 危険度 | 内容 |
|---|---|---|
| `inventory.search` | read | 品目と使える数・在庫・引き当て・ロットを探す |
| `inventory.history` | read | 入出庫の記録を期間で探す |
| `inventory.forecast` | read | 無くなる見込みの日と発注の案 |
| `inventory.move` | write-internal | 入庫・使用・移動を記録する |
| `inventory.reserve` | write-internal | 引き当てを足す（品目・数・予約の日時・予約番号）・取り消す・使ったにする。メニューで使う品目を覚える（第29.13節） |
| `inventory.read_slip` | read | 納品書の画像から、行ごとの品名・品番・数・ロット・使用期限を取り出す |
| `inventory.receive_slip` | write-internal | 納品書の画像を読み取り、品目に照らせた行を入庫にする。照らせない行は理由と候補を返す（第 0.163.0 版。読み取りと入庫を 1 つのツールにし、推論が行を書き写す誤りを避ける） |

| 業務 | 内容 |
|---|---|
| 在庫の記録（公式・付属） | 秘書に頼まれた入庫・使用・移動を `inventory.search` と `inventory.move` で記録する。品目が 1 つに決まらなければ記録せず候補を挙げる。メニューには出さない（第 0.157.0 版） |
| 納品書から入庫（公式・付属） | `inventory.receive_slip` で読み取って入庫にし、結果を伝える。照らせない行は残す。メニューには出さない。秘書に納品書の写真を渡すとこの業務に取り次ぐ |
| 発注の下書き（公式・付属） | 発注の案（`inventory.forecast`）か画面で選んだ品目と数から、仕入先への発注のメールを作り、**本人の承認のあとに `gmail.send` で送る**（作る段 → 承認 → 送る段）。メールで受ける仕入先だけが対象。秘書に「〇〇を発注して」と頼むとこの業務に取り次ぐ（推論に選ばせない） |

### 29.16 権限と記録

| 項目 | 規定 |
|---|---|
| 見られる人・記録できる人 | 在庫管理の利用範囲の全員 |
| 品目・場所の作成と変更 | 利用範囲の全員（直した人と日時を残す）。品目の止め・品目の削除（第29.6.3節）・場所の削除は管理者 |
| 棚卸しの確定 | 始めた人と管理者 |
| 公開の承認・機能の入り切り | 管理者 |
| 監査ログ | 品目の取り込み、棚卸しの確定、調整、品目の止め、品目の削除と削除の取り消し、場所の削除、公開の承認・変更・停止、機能の入り切り、書き出し。**入出庫の 1 件ずつは監査ログに入れない**（入出庫の記録そのものが誰がいつを持ち、消せないため） |
| テナント境界 | すべての表をテナント ID で絞る（不変則 I-2）。公開のページとデータは会社ごとの推測されにくい URL で出し、承認した項目だけを入れる |

### 29.17 人の情報と業種の決まりとの線引き

| 項目 | 規定 |
|---|---|
| 記憶と知識 | 在庫の数・残りわずか・使用期限は、**秘書の記憶にも会社の知識にもしない**。すぐ変わるため、要るたびに在庫管理を引く（第10.13節。第 0.159.0 版） |
| 人の情報 | **持たない。** 誰にどの品・どのロットを使ったか・渡したかは、その業種の顧客の記録の役割である。業種によっては要配慮個人情報に当たる。使用の記録と引き当てには、日時・数・ロット・予約の番号だけを持つ |
| 法令 | 業種ごとの保管や記録の義務に合っているかの判断はしない。記録を出せる（CSV）ようにするまでにする |
| 公開の言葉 | 在庫の表に効能・効果を書かない（業種ごとの広告の決まりに関わるため）。出すのは名前・数か状態・価格・更新の日時だけ。説明の文はサイトの側で書く |

### 29.18 お金と社外への境界

| 項目 | 規定 |
|---|---|
| 数の記録 | 入出庫・引き当て・棚卸しの確定は**数だけ**を扱い、お金の確定に当たらない。承認を挟まない |
| 販売価格 | 公開の表に出す値。在庫の評価ではない。公開は第29.12節の承認の範囲で出す |
| 社員価格 | 社内の値段。在庫の評価ではなく、お金の確定に当たらない。公開には出さず、販売管理には承認した範囲でだけ渡す |
| 在庫の金額 | 将来計画（Q-108。第24.5節）。扱うときは、棚卸しと評価の確定を「お金の確定」として承認の対象にする |
| 発注 | 発注のメールを仕入先へ送るのは社外への送信。承認のあと |
| 公開 | 社外に出るもの。何を出すかを一度承認し、その範囲の数の変化は自動で流す（第29.12節） |

### 29.20 ほかのシステムとの関係

#### 29.20.1 販売管理とのつなぎ ― 外部のアプリの在庫の機能（第 0.321.0 版で案、第 0.325.0 版で実装、第 0.326.0 版で外部のアプリに移した。ADR-0087・ADR-0090）

2026-10-09 に三浦さんが、**販売管理（レジ・POS・EC を含む）から、販売できる商品の一覧を取りに来る要求と、販売の通知を受け取る API** を求めた。
M2Office を在庫の正とする会社（第29.4.1節）で、販売管理が売る品目と数を M2Office から読み、売れたことを M2Office に知らせる。
三浦さんが、認証はつなぎごとの鍵・渡す範囲は一度承認・注文で取り置き販売で減らす・数の変化は販売管理が読みに来る、と決めた。第29.21.1節の 11 にあたる。

**第 0.326.0 版で、外部のアプリ（第13.4.1節）の 2 つの機能に移した**（三浦さんの依頼。つなぐ依頼が続くため汎用にした）。販売管理は「外部のアプリ」として登録し、機能「**商品の一覧を読む**」（`inventory.catalog`）と「**販売を知らせる**」（`inventory.sales`）を選ぶ。鍵・承認・止める・回数の上限・答えの決まりは第13.4.1節に従い、ここには在庫の機能の決まりだけを書く。

```
 販売管理（外部のアプリ）─① GET /v1/inventory/catalog ────▶ 承認した品目と項目だけを返す
 販売管理（外部のアプリ）─② POST /v1/inventory/sales-events ─▶ 取り置き・使用・戻し・入庫 ─▶ 使える数・公開・見張り
```

**外部のアプリの設定**（第13.4.1節。販売の経路ごとに、レジと EC などを別のアプリにできる）

| 項目 | 規定 |
|---|---|
| 選べる会社 | 在庫管理を入れた会社だけ、在庫の 2 つの機能を選べる |
| 渡す範囲の承認 | 商品の一覧を販売管理に渡すのは**社外への送信**である（第9.4.0節）。Web への公開（第29.12節）と同じく、機能「商品の一覧を読む」の設定として、**渡す品目と項目（使える数か状態だけか・販売価格を渡すか・社員価格を渡すか。社員価格の既定は渡さない）を選び、見本の表で確かめて**、アプリの「この内容で許す」で承認する。その範囲の数の変化は承認なしに渡す。中身を変えたら承認し直す。**承認のあとに足した品目は、承認し直すまで渡さない** |
| 品目を選ぶ | 区分と分類のボタンで選び、条件を覚える（第 0.404.0 版。第29.12.3節と同じ。あとで条件に当たる品目は、承認し直すまで渡さない）。既定は区分が販売品の条件（第 0.392.0 版。第29.6.1節。それまでは「販売品」に当たる分類）。販売品が無ければ何も選ばない（何を渡すかは人が承認する） |
| 在庫管理を切ったとき | 在庫の 2 つの機能の道は 404（会社が止まっているときと同じ） |

**① 商品の一覧**（機能 `inventory.catalog`）: `GET /v1/inventory/catalog`

| 項目 | 規定 |
|---|---|
| 絞り込み | `updatedSince`（その時刻より後に変わった品目だけ。読みに来るたびに、前回の答えの `asOf` を渡す）・`categories`（分類の名前。カンマ区切りで 20 まで。名前が同じ分類の品目だけ。販売品の一覧を作るときに使う。第 0.323.0 版で三浦さんの依頼で足した）・`ids`・`codes`・`barcodes`（それぞれ 100 件まで。売る直前に数を確かめる用）・`limit`（既定 200、500 まで）・`cursor`（続き） |
| 1 品目の中身 | `id`（M2Office の品目の ID）・`name`（品目の名前）・`publicName`（公開する名前。無ければ `null`）・`code`（自社のコード）・`barcodes`・`category`・`unit`（使う単位）・`status`（`in_stock`・`low`・`out`。第29.12.1節と同じ判定）・`available`（使える数。**数を渡すと承認したときだけ**）・`price`（`{ amount, taxIncluded }`。**販売価格を渡すと承認したときだけ**）・`employeePrice`（社員価格の数。**社員価格を渡すと承認したときだけ**。税込か税抜かは `price` と同じ）・`active`・`updatedAt` |
| 外れた品目 | 範囲から外した・止めた品目は、`updatedSince` の答えに `active: false` として 1 度入れる（販売管理が売るのを止められるように）。中身は `id` と `active` だけ。`categories` で絞ったときは、**その時刻より後に変わり、いまは絞った分類に当たらない品目**も `active: false` として入れる（分類を変えた品目を、販売管理の販売品の一覧から外せるように。前にその分類だったかは問わないので、販売管理は知らない `id` を読み捨てる） |
| 分類の名前 | 会社が在庫管理で付けた分類の名前（第29.4.1節）をそのまま使う。前後の空白は無視し、大文字と小文字・全角と半角は区別する。無い分類を指定しても誤りにせず、当たる品目が無いだけ。分類の名前を変えたら、販売管理の指定も直してもらう |
| 答え | `{ items, nextCursor, asOf }`。`asOf` はその答えを作った時刻 |
| 渡さないもの | 仕入れ値・在庫の金額・ロット・場所・仕入先・記録した人・引き当てた予約・メモ。承認していない項目 |

**② 販売の通知**（機能 `inventory.sales`）: `POST /v1/inventory/sales-events`

```json
{ "eventId": "evt-20261009-0001", "saleId": "ORD-1001", "status": "sold",
  "occurredAt": "2026-10-09T15:04:05+09:00",
  "lines": [ { "itemId": "…", "quantity": 2 }, { "barcode": "4901234567894", "quantity": 1 } ] }
```

| 状態（`status`） | 在庫で行うこと |
|---|---|
| `ordered`（注文を受けた） | 行の品目と数を**取り置く**（在庫は減らさず使える数だけを減らす。予約の引き当てと同じ。第29.13節）。同じ販売番号で行が変われば、取り置きを直す |
| `sold`（販売した・出荷した） | 取り置きがあればそれを**使用**に変え、無ければそのまま使用を記録する（理由「販売」）。店頭のようにその場で売れるものは、いきなり `sold` を送ればよい |
| `cancelled`（取り消し） | 販売番号の全体を取り消す（行は要らない）。取り置きを消し、販売のあとなら使用の記録を取り消す（逆の記録を足す。第29.9節） |
| `returned`（返品） | 行の品目と数を**入庫**する（理由「返品」）。一部の返品は行で分けて送る。何度でも送れる（`eventId` を変える） |

| 項目 | 規定 |
|---|---|
| 1 件にまとめる | 「アプリ＋販売番号（`saleId`）」で 1 件の販売にまとめる。状態は `ordered` → `sold` → `cancelled` の順にだけ進み、遅れて届いた前の状態は記録だけして在庫は動かさない |
| 二重に数えない | `eventId` は通知ごとに一意。同じ `eventId` がもう一度届いたら、前と同じ答えを返し、在庫は動かさない（届いたかが分からず送り直したとき用）。同じ `eventId` で中身が違えば 409 |
| 品目の照らし方 | 行ごとに `itemId` → `code`（自社のコード）→ `barcode` の順に、推論を使わず決まった規則で照らす（納品書と同じ。第29.9節）。照らすのは止めていない品目すべて（渡す範囲の外の品目が売れても数は合わせる） |
| 照らせない行 | 通知は受け付け（販売は済んでいるため）、その行だけを「照らせなかった販売」として残す。在庫の画面と見張りの知らせ（第29.14節）で示し、パソコンで品目を選べばその時点で記録する |
| 数 | 品目の使う単位（一覧の `unit`）で、正の整数。ロットと場所は尋ねず、決まりで選ぶ（使用期限の近いロットから。入庫は既定の場所。第29.7節・第29.8節） |
| 足りないとき | 断らずに受け付け、マイナスの在庫として知らせる（第29.9節）。売れたことは販売管理の側で決まっているため |
| 答え | 200。`{ eventId, saleId, applied: true, lines: [ { index, itemId, result, available } ] }`。`result` は `held`・`used`・`released`・`returned`・`unmatched`・`ignored`（遅れて届いた前の状態）。`available` は数を渡すと承認した品目だけ |
| 持たないもの | 金額・支払い・お客様の氏名や連絡先・住所。本文に入っていても読まずに捨てる（第29.17節）。**金額は受け取らない**（お金は扱わない。第29.18節） |
| 書かれた指示 | 通知の中身はデータとして扱い、指示として読まない（不変則 I-6） |

**共通の決まり**

| 項目 | 規定 |
|---|---|
| 形 | JSON（UTF-8）だけ。本文は 64 KB まで、通知の行は 200 まで |
| 流量 | アプリごとに 1 分 120 回まで（第13.4.1節）。超えたら 429（`Retry-After` を付ける） |
| 失敗の答え | 第13.4.1節の決まり（404・403・400・429）に加えて、409（`eventId` の中身が違う・処理の途中）・413・415。500 のときは販売管理が同じ `eventId` で送り直せばよい |
| 記録 | 入出庫の記録の「元になったもの」に販売番号を残し、記録した人は「外部のアプリ（アプリの名前）」と出す。1 件ずつは監査ログに入れない（第29.16節）。アプリの登録・承認などの監査ログは第13.4.1節 |
| 様子 | 最後に呼ばれた時刻・この 7 日の呼び出しの数は「外部のアプリ」に出す（第13.4.1節）。照らせなかった行の数は在庫の画面に出す |
| すぐ反映 | 通知で在庫が動いたら、ほかと同じく公開と見張りに反映する（第29.12.1節） |
| ローカルの形 | 販売管理が社内の機械の名前（第8.6.2節）に届く所にあることが要る。届かないときは使えない |
| 定義 | 外部のアプリの定義（`docs/api/m2office-apps.openapi.yaml`。第13.4.1節）に書き、管理者ページのヘルプの「開発者」で Swagger UI で見られる。使い方は、ヘルプの記事「使い方の例: 販売管理」で解説する |
| 行わないこと | M2Office から販売管理へ送ること（数の変化の知らせ・Webhook）は、この段では作らない（社外への送信の口を増やさない。要るようになったら後の段で、承認の範囲を決めて足す）。販売管理を在庫の正にする形（第29.21.1節の 13）もこの段ではない |

### 29.24 販売品の相場と競合の比較（第 0.393.0 版で案、第 0.395.0 版で確定して実装。Q-243）

2026-10-19 に三浦さんが、販売品について市場での価格を調べ、競合と比べられるようにするよう依頼した。
競合の分析（第36章）は競合の**会社**の動きを見る。こちらは**品目ごと**に、同じ商品がほかでいくらで売られているかを見る。**値付けを決めるのは会社で、AI は材料を出す。** 案のとおりに確定した（2026-10-19）。

| 項目 | 規定 |
|---|---|
| 対象 | 区分が販売品の品目（第29.6.1節）。名前と、あればバーコード（JAN）で探す |
| 調べ方 | Gemini に Google 検索を使わせ、同じ商品の販売価格を探す。**同じ商品と確かめられたもの（JAN が一致するか、商品名と容量・入り数が一致するもの）だけ**を使い、店の名前・URL・価格・税込か・見た日を出典として持つ。確かめられなければ「見つかりませんでした」とし、推測で埋めない（第29.6節の「JAN から名前を引く」と同じ決まり） |
| 競合の店 | 競合の分析（第36章）を入れていて、競合のサイトから取り出した事実に同じ商品の値段があれば、それも出典つきで並べる |
| 結果 | 相場（見つかった価格の中央値・最安・最高・件数）、**自社の販売価格との差**（%）、**位置**（安め・相場並み・高め。中央値から ±10% の内を相場並み）、出典の一覧、調べた日。ひとこと（例: 「相場（1,980 円）より 12% 高い。最安は 1,650 円（〇〇店）」。数から決まった言い方で作る）を添える。税込と税抜は品目の消費税率でそろえて比べる |
| 画面 | 在庫の画面の 2 段目のタブに「**価格の比較**」を足し、販売品を位置ごと（高め・安め を先に）に並べる。品目の詳細に出典の一覧と「相場を調べる」を置く |
| いつ調べる | 品目の詳細の「相場を調べる」と、タブの「まとめて調べる」（1 回 50 品目まで）。加えて**月に 1 回**、ワーカーが販売価格のある販売品を見回り（1 社 50 品目まで。前に調べた日の古い順）、相場が自社の価格から ±20% を超えて離れた品目を、在庫管理の利用範囲の管理者にお知らせで知らせる |
| 入り切り | 在庫の設定の機能「相場の比較」（既定は入り）。会社の AI の方針が「ローカルだけ」なら使えない（外部の検索を使うため。第16.3.7.1節） |
| 外へ渡すもの | 検索に渡すのは**商品の名前とバーコードだけ**。会社の名前・自社の価格・在庫の数は渡さない。読んだページはデータで、中の指示には従わない（不変則 I-6） |
| 持つもの | 品目ごとの最新の結果と、月ごとの相場の履歴（12 か月）。相手のページの文章は持たない（出典の URL と取り出した価格だけ） |
| 秘書 | 「ハンドクリームの相場は？」「高めの販売品は？」に、覚えている結果から答える。「相場を調べて」で調べる |
| 費用 | AI の利用の上限に数える（第6.6.2節） |
| 行わないこと | 価格を自動で変えること（値付けは会社が決める）、仕入れ値・利益の計算（Q-108）、ログインの要るページや会員価格を見ること、他社と価格をそろえるための使い方 |

**実装（第 0.395.0 版）**: `packages/core/src/inventory/market.ts`（`InventoryMarketService`・`researchItemPrice`・`marketSummary`）。調べ方は、Web の調べもの（Gemini の Google 検索）で調べた文と出典に番号を振り、推論に「同じ商品の価格だけ、出典の番号つき」で取り出させ、**番号の合わない価格と、同じ商品と確かめられない価格は捨てる**。税抜の価格は品目の消費税率で税込にそろえて比べる。ひとことは推論に書かせず、相場と差の数から決まった言い方で作る。実際に調べていない結果（見本の調べもの・推論の見本）では「調べられなかった」と残し、推測で埋めない。競合の分析を入れていれば、見ている競合のいちばん新しい回の「サービスと値段」の事実のうち、品目の名前の主な語に触れたものを出典に加える（`competitorPriceFacts`）。結果は表 `inventory_market_checks`（移行 148。1 回 1 行、12 か月で消す）。API は `GET /v1/inventory/market`・`POST /v1/inventory/market/check`（1 品目は待って結果を返し、ほかは待たずに始めて 202。画面は読み直す）・`GET /v1/inventory/items/:id/market`。月の見回りはワーカーが 1 時間ごとに見て、前の見回りから 30 日たった会社だけ回す（`runMarketWatch`。在庫の設定の機能 `market`。既定は入り）。秘書のツールは `inventory.market`（覚えている結果から答える）と `inventory.check_market`（いま調べる。1 品目）で、秘書の調べもの（`secretary-lookup`）が使う

#### 29.24.1 メーカーの終売（第 0.409.0 版で案、第 0.410.0 版で確定して実装。Q-248）

Phase 2 の候補の見直しの 3 つ目。終売になる品目を知らずに多めに発注すると、売れ残りや使い切れない在庫が出る。**相場の調べものに相乗りして、終売を出典つきで見つける。**

| 項目 | 規定 |
|---|---|
| 調べ方 | 販売価格の相場（上）と仕入れの相場（第29.6.2節）の調べもので、同じ商品の価格と一緒に「**終売・販売終了・生産終了・後継品**」を尋ねる。追加の調べものはしない（費用はほとんど増えない）。**出典の番号で確かめられたもの（メーカー・販売店・仕入先のページ）だけ**を採り、推測で埋めない（価格と同じ決まり） |
| 対象 | 相場を調べる品目（販売品と、管理者が仕入れの相場を見る品目） |
| 持つもの | 品目ごとに、終売の見込み（「終売予定」か「終売済み」・分かれば日付・後継品の名前・出典の URL・確かめた日） |
| 見せ方 | 一覧の「状態」の列に短い印「終売」を出し、マウスを重ねる・押すと日付・後継品・出典を出す（需要の予測の印と同じ出し方。第29.14節）。品目の詳細にも出す |
| 知らせ | 新しく終売の見込みが分かったら、在庫管理の利用範囲の管理者にお知らせで知らせる（月の見回りの知らせと一緒に） |
| 発注の案 | 終売の品目は、**終売の日までに使う見込みの分を上限**にする（「最後の発注」）。日付が分からなければ、届いてから 2 週間分を足さない。理由に「終売の見込み（出典）」と後継品の名前を添える。発注は承認のあとだけ（いままでどおり） |
| 外す | 管理者が「終売ではない」を押すか、秘書に「〇〇は終売じゃない」と言えば外す。同じ出典では付け直さない |
| 秘書に渡す | 仕入先から届いた終売の知らせを秘書に転送するか写真で渡すと、品目を照らして印を付ける（出典はその文書）。照らせなければ候補を尋ねる |
| 外へ渡すもの | 相場と同じく、商品の名前とバーコードだけ |
| 行わないこと | 仕入先のメールを自動で読むこと（Gmail の権限を広げないため）、品目を自動で止めること、後継品に自動で切り替えること、自動の発注 |

**実装（第 0.410.0 版）**: 品目の `discontinued`（`{current, dismissed}`。移行 152）。相場の調べもの（`researchItemPrice`・`researchItemPurchase`）が同じ推論で終売を取り出し、`pickDiscontinued` が出典の番号の合うものだけを採る。`InventoryMarketService.check` が `InventoryService.markDiscontinued` で付け（外した出典は付けない）、月の見回りが新しく付いた品目を知らせる。発注の案は `forecastItem`（終売済みは出さない・終売予定は終売の日までの分。日付が無ければ届いてから 2 週間分を足さない）。API は `POST /v1/inventory/items/:id/discontinued/dismiss`（管理者だけ）。秘書の道具は `inventory.mark_discontinued`（危険度 `write-internal`。付ける・外す。外すのは管理者だけ）で、付属の業務「在庫の記録」が使う。画面は一覧の「状態」の列の「終売」の印（押すと日付・後継品・出典）と、品目の詳細の欄と「終売ではない」。
