# @m2office/worker

ジョブ実行の常駐プロセス。承認による中断と再開を担います。

## 前提

Node.js 22 以上、PostgreSQL。

## 起動

```bash
npm run dev     # 監視付き
npm run start   # 単発
```

## なぜ常駐なのか

承認による中断と再開は数分から数十分にまたがります。
リクエスト単位で終了する実行環境では実装できません（仕様書 第20.6節）。

配備先を選ぶときの前提条件になります。

## 動き

```
1. 待ち行列から実行を 1 件確保する（for update skip locked）
2. 完了するか承認待ちになるまで進める
3. 各ステップの終了時に状態を永続化する
4. 承認待ちになったら、その実行を手放す
```

あわせて `SCHEDULE_INTERVAL_MS`（既定 15 秒）ごとに定時実行を見回り、
時刻を過ぎたものを待ち行列へ入れます。定時実行は対象者の権限で動き、
停止された利用者の分は起動しません。

`RETENTION_INTERVAL_MS`（既定 本番 10 分・開発 15 秒）ごとに、Google から取得したデータの保持期間を見回ります（仕様書 第14.3.2節）。
会社の設定の日数（既定 7 日）を過ぎた終わった実行から、Google 由来の中身を消して目印だけを残し、
承認待ちのまま 30 日たった実行を期限切れにします。

`NOTIFY_INTERVAL_MS`（既定 10 秒）ごとに、通知の控えを Chat とメールへ届けます（仕様書 第6.5.5.2節）。
本人が控えを受け取る設定のときだけ送り、通知しない時間帯の間は送らずに次の見回りへ回します。
送るのは種類・題名と画面へのリンク（`APP_BASE_URL`）だけです。送信口はいまは見本で、実際には届きません。

承認されると実行は待ち行列へ戻り、**次に空いたワーカーが続きを担当します**。
中断したワーカーが再開するとは限りません。この経路が動くことが、
プロトタイプで確認すべき最重要の項目です（仕様書 第24.3.2節 段階 5 と 7）。

## 拡張機能とコネクタ

起動時に `extensions/`（公式の配布元）を読み込みます。会社がファイルから取り込んだ拡張機能は、
実行のたびにデータベースから読むため、取り込んだあとに再起動は要りません（仕様書 第12.10.6節）。
コネクタのツールは、このワーカーから MCP サーバを呼びます（1 回 60 秒まで。第12.11.3節）。
外部の MCP サーバへ出ていける通信経路が必要です。

## 複数起動

`for update skip locked` により、同時に何個動かしても同じ実行を二重に処理しません。

```bash
npm run start & npm run start &
```
