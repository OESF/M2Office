# 第 11 章 運営の側の準備（配備する技術者）

マスター管理画面を動かすための準備です。クラウドの形の配備でだけ行います（ローカルの形には運営の画面を入れません）。

## 1. 仕組み

- 運営の API は、会社の利用者向けの API とは**別のプロセス**で動きます（`server/ops.js`、`npm run start:ops`）。名前が `ops.` で始まる要求だけを受けます
- データベースには、運営の**専用のロール** `m2office_ops` で接続します。このロールは、会社のデータの表に届きません。会社の数を数える・会社を作る・状態を変えるといった操作は、決めた関数だけで行います
- 画面は利用者の画面と同じ組み立てで、名前が `ops.` のときだけ運営の画面を出します

## 2. 環境変数

| 変数 | 内容 |
|---|---|
| `OPS_DATABASE_URL` | 運営の専用のロールの接続（`postgres://m2office_ops:<合言葉>@…/m2office`）。**本番では必須**。`npm run db:migrate` を走らせるとき、この合言葉でロールにログインできるようにする |
| `OPS_PORT` | 運営の API のポート（既定 3102） |
| `OPS_GOOGLE_REDIRECT_URI` | 運営者の Google のログインの戻り先（`https://ops.<本番のドメイン>/v1/ops/auth/callback`）。運営の OAuth クライアント（`GOOGLE_LOGIN_CLIENT_ID`）の承認済みのリダイレクト URI に足す |
| `OPS_GOOGLE_DOMAIN` | 運営主体の Google Workspace のドメイン。入れると、このドメインの人だけを運営者にできる |
| `OPS_SESSION_TTL_HOURS` | 運営のログイン状態の時間（既定 12） |

## 3. 入口と名前

- `ops.<本番のドメイン>` を、入口（逆プロキシ）に向けます。ワイルドカードの証明書があれば、そのまま使えます
- 入口では、`ops.<本番のドメイン>` の `/v1/ops` を運営の API のプロセスへ、それ以外を画面へ送ります
- `ops` は会社のサブドメインとしては払い出しません

## 4. 最初の運営管理者

```bash
npm run db:migrate
npm run ops:operator -- --email <運営管理者のメールアドレス> --name "名前" --role admin
```

出た**登録の合言葉**を本人に渡します（第 1 章）。本人は Google でログインし、合言葉でパスキーを登録します。2 人目からは、マスター管理画面の「運営者」で足します。

## 5. 最後の運営管理者がパスキーをなくしたとき

運営管理者がほかにいないときは、画面ではやり直せません。手元のツールで戻します。

```bash
npm run ops:operator -- --email <その人のメールアドレス> --reset-passkeys
```

その人のパスキーを削除し、ログインの状態を切り、新しい登録の合言葉を出します。**本人であることを対面などで確かめてから**行います。
合言葉だけを出し直すときは `--code` を付けます。

## 6. 開発の環境

- 開発では、運営の API は `npm run dev` で一緒に動きます（3102 番）。画面の開発サーバーが `/v1/ops` を運営の API に送ります
- `https://ops.lvh.me:3100` で開きます
- 開発用ログイン（`AUTH_DEV_LOGIN=true`。本番では起動を拒否します）では、運営者を選ぶだけで入れて、パスキーを求めません
