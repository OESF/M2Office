# 第 18 章 全体の構成

クラウドの形の M2Office が、どの部品でできていて、それぞれがどこで何をしているかをまとめた章です（仕様書 第20.4.6節・第23.8.16節「全体の構成」）。
VPS の用意（第 12 章）・セットアップ（第 13 章）・バックアップと復旧（第 17 章）の手順が、全体のどこに当たる作業なのかを分かってから手を動かせるように、はじめに読んでください。

この章はクラウドの形（運営が動かす VPS）だけを扱います。会社が自分のサーバーで動かすローカルの形には運営の画面が無く、構成は `deploy/onsite/README.md` にあります。

![クラウドの形の全体の構成。外から順に、Xserver のパケットフィルター、サーバーのファイアウォール（ufw・国の遮断・CrowdSec の止める役）、入口の Caddy（証明書と WAF）と WireGuard を通る。奥に API・ワーカー・運営の API・SSH と update.sh があり、PostgreSQL とファイルを毎晩 m2office-backup が Google Cloud Storage へ送る。入口の守りと VPN の数は m2office-edge-status が 5 分ごとに集める。土台は Ubuntu 26.04 LTS。外部に Google・Gemini・Let's Encrypt・Cloud Storage・GitHub・地域の登録機関・CrowdSec の中央がある](images/cloud-architecture.svg)

| 色 | 意味 |
|---|---|
| 赤茶 | 入口（インターネットから来た通信を受ける Caddy） |
| 赤紫 | 守り（通信を止める仕組み） |

| 緑 | M2Office のプログラム |
| 紫 | データ |

| 灰 | VPS の外の守り・OS の土台・外の事業者 |

上から下へ、外から来た通信が通る順に並べています。点線の枠の中が VPS 1 台です。

## 2. 守りの重なり

外から来た通信は、次の順に関門を通ります。1 つが破られても、次の関門で止められるようにしています。

| 順 | 関門 | 何をするか | 設定のありか |
|---|---|---|---|
| 1 | Xserver のパケットフィルター | VPS の外で、TCP 80・443 と UDP 51820 だけを通す | Xserver の管理画面（第 12 章） |
| 2 | サーバーのファイアウォール（nftables） | ufw が開けるポートを絞り、SSH は VPN の網からだけ通す。国の遮断（中国・ロシア・北朝鮮）は入る通信も出る通信も止める。CrowdSec が決めた相手もここで止める | ufw（第 12 章）、`deploy/vps/geo/`、CrowdSec の止める役 |
| 3 | CrowdSec | 入口と SSH の記録を読み、総当たり・道の探り・WAF に当たった相手を決めた時間だけ止める。世界中の利用者が見つけた攻撃元の一覧も使う | `deploy/vps/crowdsec/acquis-m2office.yaml`（`/etc/crowdsec/acquis.d/m2office.yaml`） |
| 4 | WAF | Caddy に組み込んだ Coraza が、OWASP の規則（CRS）でよくある攻撃の型を見つける。はじめは記録だけにし、誤って止める道を外してから止める形にする | `deploy/vps/Caddyfile.template` の `(waf)`（第 13 章 手順 7） |
| 5 | サーバーの中だけで待ち受ける | M2Office のプログラムは `127.0.0.1` でしか待ち受けないので、Caddy を通らずには届かない | `deploy/vps/m2office.env.template` |

それぞれの考え方と、この形で受け入れていること（大量の通信の攻撃など）は、第 13 章の「1. 入口の守りの考え方」にあります。

## 3. 入口（Caddy）

Caddy は、インターネットからの通信を受けて、名前で行き先を分けます。

| 名前 | 行き先 |
|---|---|
| `会社名.m2office.net` | 会社の画面と API |
| `m2office.net`・`www.m2office.net` | 紹介のページ（`/var/www/m2office-site/`）。問い合わせのフォーム（`/api/contact`）だけは、紹介のサイトの受け口（`127.0.0.1:4330`）へ渡す |
| `ops.m2office.net` | マスター管理画面と運営の API。VPN の網から来た通信だけを通し、網の外には「見つかりません」を返す |

- 証明書は Let's Encrypt から自動で取ります。会社の名前の証明書は、初めて開かれたときに、M2Office に「払い出した会社か」を尋ねてから取ります。
- 画面のファイル（組み立てたもの）は、Caddy が直接配ります。
- アクセスの記録と WAF の記録は `/var/log/caddy/` に残り、CrowdSec が読みます。

## 4. VPN の道（運営と保守）

運営と保守の道は、WireGuard の VPN の中にしかありません。

| 道 | 中身 |
|---|---|
| マスター管理画面 | 運営者の端末で `ops.m2office.net` を VPN の中の VPS（`10.66.0.1`）に向け、VPN を通して開く。ここでも Google のログインとパスキーを求める（第 1 章） |
| SSH | VPN の網からだけ入れる。M2Office の更新（`update.sh`）、セットアップ（`setup.sh`）、紹介のページの入れ替えに使う |

VPN を通らずに入れる管理の道はありません。運営者の端末の WireGuard の鍵はバックアップを持ち、2 台目の端末も登録しておきます（第 12 章 手順 8）。どうしても入れないときは、Xserver の管理画面のコンソールから入ります。

## 5. 中で動くもの

| 部品 | systemd の名前 | 待ち受け | 役目 |
|---|---|---|---|
| API | `m2office-api` | `127.0.0.1:3101` | 会社の画面と、外部のアプリからの窓口 |
| ワーカー | `m2office-worker` | なし | 毎朝の見回り・定期の処理・AI の仕事など、画面の裏で動く仕事 |
| 運営の API | `m2office-ops` | `127.0.0.1:3102` | マスター管理画面の裏側（会社の管理・稼働状況・体験版など） |
| 申し込みの口 | `m2office-signup` | `127.0.0.1:3103` | 申し込みのページの API とカードの課金（第 19 章）。専用のロールで接続し、業務の表にも運営の表にも届かない |
| Caddy | `caddy` | 80・443 | 入口 |
| WireGuard | `wg-quick@wg0` | UDP 51820 | VPN |
| PostgreSQL 17 | `postgresql` | サーバーの中だけ | データベース |
| CrowdSec | `crowdsec`・`crowdsec-firewall-bouncer` | なし | 攻撃する相手を決めて、ファイアウォールで止める |
| 国の遮断 | `m2office-geo`・`m2office-geo-update.timer` | なし | 起動のときに国の表を入れ、毎週月曜の朝 5 時に一覧を取り直す |
| 社外バックアップ | `m2office-backup.timer` | なし | 毎晩 2 時に社外バックアップを取る |
| 入口の守りと VPN の様子 | `m2office-edge-status.timer` | なし | 5 分ごとに、CrowdSec・国の遮断・WAF・証明書・WireGuard の数と、攻撃の種類・国だけを集め、「稼働状況」の「セキュリティ」に出す（第 7 章） |

M2Office の 3 つのプログラムは、専用の利用者 `m2office` で動き、Node.js のメモリの上限を付けています。動いているかどうかは、マスター管理画面の「稼働状況」（第 7 章）で見られます。

## 6. データと置き場所

- **データベース**: PostgreSQL 17 に、会社（テナント）ごとに分けて入れています。意味の検索のため pgvector を使います。画面・移行・運営で、データベースに入る権限を分けています。
- **ファイル**: 会社が入れたファイルは、VPS のディスク（`/var/lib/m2office/files/`）に置いています。
- **秘密の値**: 環境変数のファイル（`/etc/m2office/m2office.env`）にあり、root と `m2office` だけが読めます。

置き場所の一覧は `deploy/vps/README.md` の「置き場所」にあります。

## 7. バックアップ

バックアップは 3 種類あります。

| バックアップ | いつ | どこへ | 残す長さ |
|---|---|---|---|
| 社外バックアップ（データベース） | 毎晩 2 時すぎ（pgBackRest） | Google Cloud Storage の東京 | まるごとのバックアップを 14 日分 |
| 変更の記録（WAL） | 少なくとも 5 分ごと | 同上 | 14 日の範囲なら、好きな時刻の状態に戻せる |
| 社外バックアップ（ファイル） | 毎晩 2 時すぎ（restic） | 同上 | 30 日分 |
| 更新の前のバックアップ | `update.sh` で更新するたび（`pg_dump`） | VPS の中（`/var/backups/m2office/pre-update/`） | 直近の 3 回 |

- 社外バックアップは暗号化して送ります。戻すための合言葉は紙に書き写して保管します。
- 月に 1 回、バックアップが壊れていないかを確かめます。結果と戻せる範囲は、マスター管理画面の「稼働状況」の「バックアップ」と、VPS の上の `sudo m2office-backup --status` で見られます。
- VPS に置いたバックアップ用の鍵は、読み書きだけができ、置き場の設定は変えられません。乗っ取られてバックアップを消されても、30 日のうちなら管理者が戻せます。

バックアップの見方と戻し方は第 17 章にあります。

## 8. OS の土台

| 項目 | 中身 |
|---|---|
| OS | Ubuntu 26.04 LTS |
| セキュリティの更新 | 自動で入る。再起動が要るときは夜中の 4 時半に起動し直す（第 12 章 手順 5） |
| 作業の記録 | auditd が管理者の作業を記録する（第 12 章 手順 9） |
| systemd の記録 | 起動し直しても消さず、28 日分・1 GB まで残す（第 12 章 手順 7） |
| スワップ | 4 GB（第 12 章 手順 6） |
| Node.js | 24 系（`setup.sh` が入れる） |

## 9. 外とのつながり

| 相手 | 何のため | 止まったとき |
|---|---|---|
| Google | 利用者と運営者のログイン、Gmail・カレンダー・ドライブなど Workspace の利用 | ログインと Workspace を使う仕事ができない |
| Gemini | 秘書や業務の AI の推論 | AI を使う仕事ができない。ほかの画面は使える |
| Let's Encrypt | 入口の証明書 | 新しい会社の名前の証明書が取れない。取ってある証明書は期限まで使える |
| Google Cloud Storage | 社外バックアップの置き場 | バックアップが送れない（「稼働状況」に出る）。M2Office は動き続ける |
| GitHub | 更新のときに、リリースのタグを取る | 更新できない。動いている版はそのまま |
| 地域の登録機関 | 国の遮断に使う、国ごとのアドレスの一覧 | 前の一覧を使い続ける |
| CrowdSec の中央 | 世界中の利用者が見つけた攻撃元の一覧 | 自分のサーバーで見つけた相手は、これまでどおり止める |
| Google Chat か Slack（入れたときだけ） | 稼働状況が警戒になったときの知らせ（運営の API が送る。第 7 章「0.1 警戒のときの知らせ」） | 知らせが届かない。マスター管理画面の警戒の帯は出る |

## 11. この章を直すとき

構成を変えたら（`deploy/vps/` の雛形・入れるソフト・開けるポート・バックアップの仕組み・外とのつながり）、同じ変更でこの章と図（`docs/ops-manual/images/cloud-architecture.svg`）を直します。この章が変わった版では、バックアップと復旧の手順書（印刷）を刷り直します（仕様書 第23.8.16節「構成の章の保ち方」）。
