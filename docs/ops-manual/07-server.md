# 第 7 章 稼働状況

左のメニューの「**稼働状況**」で、サーバー全体が健全に動いているかを見ます。1 分ごとに読み直します。

## 1. 動いている環境

いちばん上に、M2Office の版・API とワーカーの Node.js（系・段階・サポートの終わる日）・PostgreSQL・OS と CPU・メモリー・動いている形・推論・起動してからの時間が出ます。クラウドの形では、これらは運営の機械の情報なので、各社の管理者には出しません（運営だけが見ます）。

- Node.js のサポートの終わりまで 6 か月を切ると「Node.js の更新が要ります」と出ます。終わった後は赤く出ます。配備した技術者に、新しい LTS の版への更新を頼みます
- Node.js がセキュリティの修正の下限より古いと「セキュリティの修正があります（v24.22.1 以上に更新してください）」と赤く出て、古い部分（API・ワーカー）も出ます。**できるだけ早く**、配備した技術者に Node.js の更新を頼みます（M2Office は止まりません）
- ワーカーの版が API と違う・ワーカーの知らせが 12 分より古いときは印が付きます
- 画面は外（nodejs.org など）へ最新の版を見に行きません。サポートの終わりの日付は、リリースのたびに公式の予定と見比べて直しています

## 1.0 機械の資源

「動いている環境」のすぐ下に、機械の資源が棒と図で出ます。棒は **80% 以上で黄色、90% 以上で赤**です。

| 項目 | 内容 | 気にする目安 |
|---|---|---|
| CPU の負荷 | 1 分の平均の負荷 ÷ コアの数（5 分・15 分の値も出る）。100% を超えうる | 100% を超える状態が 15 分の平均でも続くなら、機械の大きさが足りない |
| メモリー | 使っている量 ／ 全体（使える量は、すぐに空けられる分を含む） | 90% を超える状態が続き、Swap も増えるなら、メモリーが足りない |
| Swap | 使っている量 ／ 全体。Swap が無い機械は「なし」 | 増え続けるなら、メモリーが足りない |
| ディスク | ファイルの置き場があるディスクの使っている量 ／ 全体。うちデータベースとファイルの置き場の量 | 80% を超えたら、技術者と容量を足す相談を始める |
| データベースの接続 | 接続の数 ／ 上限 | 80% を超えたら、技術者に知らせる |

「推移」は、CPU の負荷・メモリー・Swap・ディスクの直近 24 時間の折れ線です（「7 日」に切り替えられます）。API が 5 分ごとに標本を取り、7 日より古いものは消します。止まっていた間は線が切れます。図の上でマウスを動かすと、その時刻の値が出ます。

## 1.1 項目と見方

| 項目 | 内容 | 気にする目安 |
|---|---|---|
| 待ち行列 | 始まりを待っている業務の数と、最も古い待ちの日時。動いている数・承認待ちの数 | 待ちが増え続ける・最も古い待ちが数分より前なら、ワーカーが止まっていないかを見る |
| 実行（1 時間 ／ 今日） | 業務の実行の件数と失敗の割合 | 失敗の割合がふだんより急に上がったら、AI や Google の障害を疑う |
| ワーカー | 業務を動かすワーカーが動いているか（最後の応答）。いま動いているワーカーが 2 台以上のときは台数を出し、下に「ワーカー」の表（名前・最後の応答・版）を出す。起動し直して止めた前のワーカーは数えない | 「応答がありません」なら、ワーカーが止まっている。配備した技術者に連絡する |
| 遅れている定時実行 | 予定の時刻を 5 分過ぎても動いていない定時実行の数 | 0 でなければ、ワーカーの止まりか、待ち行列の詰まり |
| 社外の控え | 毎晩の控え（データベースとファイル）の最後の結果・変更の記録を最後に送った日時・月に 1 回の確かめ。失敗・26 時間より古い（止まっている）・変更の記録を送れていない・確かめの失敗のときは、理由と一緒に目立たせる。入れていなければ「入れていません」 | 「取れています」以外なら、配備した技術者に連絡する（[第 17 章](17-backup-recovery.md) の「1. まず見る表」）。変更の記録を送れていないままだと、機械のディスクが埋まる |
| AI の費用（今日 ／ 今月） | 全社の AI の費用と、前の月の同じ時期の費用 | 前の月より大きく増えていたら、会社一覧の「今月の AI」で、どの会社が増えたかを見る |
| 外部の接続（24 時間） | AI・Google・会社の接続（MCP）ごとの成功・失敗・失敗の割合・平均の速さ。呼び出しが 1 件も無ければ「まだありません」 | 失敗の割合が高い・速さが急に遅いなら、相手のサービスの障害を疑う |

## 1.2 社外の控え（表）

要約の欄の下に「社外の控え」の表が出ます（クラウドの形で控えを入れているときだけ）。いざというときに「どこまで戻せるか」「どの名前で戻すか」を、ここで確かめます。題名の横の「？」から [第 17 章](17-backup-recovery.md) を開けます。

| 行 | 内容 |
|---|---|
| 毎晩の控え | 最後に取った日時と、データベース・ファイルのそれぞれが済んだか |
| 次の控え | 次の予定（日本時間の 2 時。最大 20 分遅れる） |
| データベースを戻せる範囲 | いちばん古いまるごとの控えの終わりから、変更の記録を最後に送った時刻まで。この中のどの時刻にも戻せる |
| データベースの控え | まるごとの控えの数・いちばん新しい日時・大きさ |
| 変更の記録 | 最後に送った日時。いま送れていなければ印が付く |
| ファイルの控え | 回の数・いちばん古い回と新しい回・置き場の中の大きさ |
| 壊れていないかの確かめ | 月に 1 回の確かめの結果と日時 |
| 更新の前の戻す点 | 更新のたびに記録した名前と日時（新しい 5 件）。戻せる範囲より前になったものは「戻せる範囲の外」 |
| 置き場 | Google Cloud Storage のバケットの名前とプロジェクトの ID |

画面は VPS の上の結果のファイルを読むだけで、Google Cloud へは見に行きません。合言葉と鍵は出しません。

## 2. 異常に気づいたら

1. 1 社だけの問題か、全社の問題かを見分けます。会社一覧の「失敗」「注意」の印で、1 社に偏っていないかを見ます
2. 全社の問題なら、AI・Google のサービスの障害の情報を確かめ、配備した技術者に連絡します
3. 1 社だけなら、その会社の詳細の「稼働」で、どの業務・どの接続先かを見ます
