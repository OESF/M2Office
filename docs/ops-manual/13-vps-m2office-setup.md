# 第 13 章 M2Office のセットアップ（VPS）

第 12 章で固めた VPS に、M2Office 本体（Node.js・PostgreSQL・Caddy・CrowdSec と置き場所）を入れ、利用者に見せるところまでの手順です。配備する技術者（提携先の技術者を含む）が行います。
仕組みの考え方は仕様書 第20.4.6節にあります。

入れる前に「1. 入口の守りの考え方」を読み、「2. 手順」でセットアップの命令（`deploy/vps/setup.sh`）を走らせます。

## 1. 入口の守りの考え方

### VPS だけで守る形（第 1 弾）

M2Office の第 1 弾は、**VPS の上だけで守ります**（仕様書 第20.4.6節、ADR-0113）。Cloudflare のような外の事業者を入口に置かず、契約を Xserver（VPS・ドメイン・DNS）の 1 つにまとめます。運営の会社に引き継ぐときに、移す契約が少なくて済むためです。多くの VPS の利用者も、この形で守っています。

VPS が開ける口は 3 つだけです。

| 口 | 使う人 | 使い道 |
|---|---|---|
| TCP 443（HTTPS） | 利用者・外部のアプリ・紹介のページを見る人 | M2Office の画面と API |
| TCP 80（HTTP） | 同上 | HTTPS への転送と、証明書を取るときの確かめだけ |
| UDP 51820（WireGuard） | 保守の人と運営者 | SSH とマスター管理画面（第 12 章の手順 8） |

データベース・API・SSH は、インターネットから直接は届きません。API は VPS の中（`127.0.0.1`）でだけ待ち受け、Caddy を通して受けます。

### Caddy（入口の Web サーバー）

**Caddy** は、nginx や Apache と同じ役割の Web サーバーです。インターネットからの通信を受けて、VPS の中の M2Office に渡します。

| 特徴 | 内容 |
|---|---|
| HTTPS が自動 | **Let's Encrypt** の証明書を自動で取り、期限（90 日）の 30 日前から自動で更新する。証明書の契約も費用も要らない |
| 会社のサブドメインの証明書 | 会社のサブドメイン（`<会社>.m2office.net`）は、**初めて開かれたときに、その名前の証明書を取る**（On-Demand TLS）。取る前に M2Office に「払い出した会社か」を尋ね、払い出した名前だけ取る。でたらめな名前で証明書を取らせ、Let's Encrypt の回数の上限を使い切らせる攻撃を防ぐため |
| 安全な既定 | TLS 1.2 以上・HSTS・HTTP から HTTPS への転送が最初から効く |
| 止めているあいだ | 更新などで M2Office が止まっている間は、「ただいま更新中です」のページを返す |

### 攻撃を止める仕組み

| 仕組み | 内容 |
|---|---|
| WAF（Coraza と OWASP の規則） | Caddy に組み込む。SQL の差し込み・スクリプトの差し込みなど、よくある攻撃の型を見つけて止める。**はじめは記録だけの形で動かし**、文書の本文・ファイルの送信・外部のアプリの配信などを誤って止めないことを確かめてから、止める形にする |
| CrowdSec | Caddy と SSH のログを読み、総当たり・道の探り・WAF に当たった相手を、決めた時間だけ機械のファイアウォールで断る。世界中の利用者が見つけた攻撃元の一覧（無料の範囲）も使う |
| 国で通信を止める | 中国・ロシア・北朝鮮（既定）との通信を、入ってくるものも出ていくものも、機械のファイアウォール（nftables の表 `m2office_geo`）で断る。国のアドレスは 5 つの地域インターネットレジストリの公開の一覧から作り、週に 1 回（月曜の朝）取り直す。取れない・壊れているときは前の一覧を使い続ける。WireGuard の網と機械の中は見ない |
| 回数の制限 | Caddy が粗い上限（ログイン・外部のアプリの道）、M2Office が細かい上限を持つ（二重） |
| 自動の更新 | OS のセキュリティの更新（第 12 章の手順 5）と M2Office の夜の更新で、弱点を早くふさぐ |

### 運営の画面（マスター管理画面）

`ops.m2office.net` は、**WireGuard の網から来た通信だけを通します**。網の外から開くと「見つかりません」になります。網に入った運営者にも、これまでどおり Google のログインとパスキーを求めます（第 1 章。二重の守り）。運営者の端末にも WireGuard を入れます（第 12 章の手順 8「人を足す・外す」）。

公開の DNS では、`ops` も VPS の IP のままにします（Caddy が Let's Encrypt の証明書を取るため）。そのため、運営者の端末で **`ops` だけを網の中の VPS（`10.66.0.1`）に向けます**。Mac なら、次の 1 行を `/etc/hosts` に足します（`sudo nano /etc/hosts`）。

```
10.66.0.1 ops.m2office.net
```

この行が無いと、運営者の通信がインターネットを通って VPS に届き、網の外とみなされて開けません。

### 大量の通信の攻撃（DDoS）を受けたとき

回線を埋めるほどの大量の通信は、VPS だけでは防ぎきれません。第 1 弾では、受けたら止まることを受け入れ、**その日のうちに Cloudflare（無料のプラン。カードは要らない）を前に置いて**守ります。

| 前に置くときに行うこと | 内容 |
|---|---|
| DNS を移す | ドメインの DNS を Cloudflare に移し、記録を「Cloudflare を通す」にする |
| Caddy を切り替える | Caddy の設定の「Cloudflare を前に置く」を入れる（Cloudflare からの通信だけを受け、利用者のアドレスを `CF-Connecting-IP` から取る） |
| IP を替える | 攻撃者に VPS の IP を知られているので、Xserver で IP を替えられるなら替える |
| 気をつけること | 1 回の送信が 100 MB までになる（録音・動画）。Cloudflare が通信の中身を見られるようになるので、会社に知らせる |

手順は「大量の通信の攻撃を受けたとき」の章（これから作る）に書き、年に 1 回、使い捨ての VPS で練習します。

Cloudflare を前に置くと、入ってくる通信は Cloudflare のアドレスからしか来なくなり、VPS では国で止められません。Cloudflare の「セキュリティ › WAF › カスタムルール」（無料の範囲）に、`(ip.src.country in {"CN" "RU" "KP"})` を「ブロック」にする規則を足します。出ていく通信は、いままでどおり VPS で止めます。

### この形で受け入れること

| 項目 | 内容 |
|---|---|
| 口が開いている | Caddy・Node.js・M2Office の弱点が直接狙われる。弱点の知らせが出たら、その日のうちに手当てする |
| VPS の IP が知られている | DNS に IP を書くので、知られる前提で守る |
| Let's Encrypt に頼る | 証明書が更新できないと期限で開けなくなる。見張りで期限を確かめる。会社が一度に多く増えるときは、Let's Encrypt の回数の上限（同じドメインで週に 50 枚ほど）を前もって確かめる |

### 保守で見るところ

| 見るところ | 内容 |
|---|---|
| 証明書 | 期限が 30 日を切っても更新されていなければ、Caddy のログを見る |
| CrowdSec | 止めた相手の数（`sudo cscli decisions list`・`sudo cscli alerts list`）。急に増えたら攻撃の兆しとして運営に知らせる |
| WAF | 記録だけの間は、当たった記録を週に 1 回見て、誤りを外す |
| 回線 | 使用量が急に増えたら、大量の通信の攻撃を疑う |
| 画面が開けないとき | 証明書 → Caddy が動いているか → M2Office が動いているか（第 7 章）→ 回線（大量の通信）の順に確かめる |

## 2. 手順

第 12 章を終えてから行います（SSH は WireGuard の網から・ufw・自動の更新・スワップ）。命令は VPS の上で、自分の名前の利用者で打ちます。

### 手順 1. Xserver で用意する

| 用意すること | 内容 |
|---|---|
| ドメイン | `m2office.net` を Xserver で取る（または移す）。DNS も Xserver で持つ |
| DNS の記録 | `m2office.net`・`www`・`*`（ワイルドカード）の A の記録を、VPS の IP にする。`ops` も `*` に含まれるので、別に作らなくてよい |
| パケットフィルター | TCP 80・443 を開ける規則を足す（UDP 51820 は第 12 章で開けてある。SSH の 22 番は開けない） |

DNS が引けるまで、数分から数時間かかることがあります。手元で `dig +short m2office.net` が VPS の IP を返せば引けています。

### 手順 2. リリースのタグを取ってくる

```bash
sudo mkdir -p /opt/m2office && sudo chown "$USER" /opt/m2office
```

```bash
git clone --branch <リリースのタグ> https://github.com/OESF/M2Office.git /opt/m2office/app
```

`<リリースのタグ>` は、運営が知らせた版（`v` で始まる。例 `v0.20.0`）です。

顧客を入れる前に、本物の VPS で初めて確かめるときだけは、タグを付けずに取ってきて（`--branch` を外す）、手順 3 で `setup.sh --allow-untagged` と走らせます。確かめが済んだら、リリースのタグに切り替えます。

### 手順 3. セットアップの命令を走らせる

```bash
/opt/m2office/app/deploy/vps/setup.sh
```

聞かれること:

| 問い | 答え |
|---|---|
| 会社のサブドメインの親のドメイン | `m2office.net` |
| 証明書の連絡先のメールアドレス | 運営の連絡先（Let's Encrypt から期限の知らせが来る） |
| マスター管理画面に入れる Google Workspace のドメイン | 運営主体の Google Workspace のドメイン。提携会社の人も運営者にするなら、提携会社のドメインもカンマで並べる（例 `ops.example.co.jp,partner.example.co.jp`。第 2 章「提携会社の人を運営者にする」） |
| WireGuard の網 | 既定（`10.66.0.0/24`）のまま |
| WAF の動き | 初めは `DetectionOnly`（記録だけ） |
| Cloudflare を前に置くか | `no` |
| 通信を止める国 | 既定（`CN,RU,KP`）のまま。止めないときは `none` |
| 国で止めずに通す相手 | 空のまま（どうしても通す相手がいるときだけ、アドレスか範囲を入れる） |
| 体験版の入口の名前 | 体験版を使うなら `demo`。使わないなら空のまま（第 16 章 6 節） |
| 紹介のページの公開前の確認の利用者の名前・ハッシュ | 紹介のページを公開する前だけ入れる（下の「紹介のページを公開する」）。公開しているなら空のまま |
| Gemini の API の鍵・Google のログインのクライアント | あれば入れる（後で走らせ直して入れてもよい）。Gemini の鍵は、マスター管理画面の「設定 › AI」でも入れられる（第 8 章。画面で入れた鍵が優先） |

命令が行うこと: ソフトを公式の置き場から入れる（Node.js 24・PostgreSQL 17 と pgvector・Caddy と WAF・CrowdSec）→ 専用の利用者 `m2office` と置き場を作る → 秘密の値を機械の上で作る → 設定のファイル（`/etc/m2office/m2office.env`）を作る → データベースを作る → 本番の組み立てと移行 → systemd で動かす → Caddy と CrowdSec の設定を置く → 80・443 を開ける → 動きを確かめる。初めては 10〜20 分ほどかかります。

最後に「残りの作業」が出ます。何度走らせてもかまいません（秘密の値とデータベースは作り直しません）。

2 回目からは、前の答えが既定になります（Enter でそのまま）。入れた答えを外すときは `-` を入れます。

#### 紹介のページを公開する

紹介のページ（`m2office.net`・`www`）は、公開の前に本物の名前で中身を確かめるあいだ、**BASIC 認証**で守れます。守っているあいだは、検索に出さない見出し（`X-Robots-Tag: noindex, nofollow`）も付きます。Google からの戻り（`/v1/oauth/`）は守りません。

| すること | 手順 |
|---|---|
| 守る | 紹介のサイトの側（M2Office-site の `scripts/basic-auth-hash.sh`）でパスワードとハッシュを作り、`setup.sh` を走らせ直して、利用者の名前とハッシュ（`$2a$` で始まるもの）を入れる。**パスワードは VPS に入れない** |
| 公開する | `setup.sh` を走らせ直し、利用者の名前とハッシュの両方に `-` を入れる。紹介のサイトの側の `scripts/verify-live.sh --expect public` で、認証が外れたことを外から確かめる |

### 手順 4. 確かめる

| # | 確かめること | 命令・操作 | よい結果 |
|---|---|---|---|
| 1 | 動いている | `systemctl is-active m2office-api m2office-worker m2office-ops caddy crowdsec` | すべて `active` |
| 2 | API は機械の中だけ | `sudo ss -tlnp \| grep -E ':310[12]'` | `127.0.0.1:3101` と `127.0.0.1:3102` だけ |
| 3 | 開いている口 | `sudo ufw status verbose` | `80/tcp`・`443/tcp`・`51820/udp`・`22/tcp on wg0` だけ |
| 4 | 紹介のページ | 手元のブラウザで `https://m2office.net` | 鍵のマークが出て開ける |
| 5 | 運営の画面 | WireGuard を入れ、hosts に `10.66.0.1 ops.m2office.net` を足して `https://ops.m2office.net` | ログインの画面が出る。WireGuard を切ると開けない |
| 6 | 外から機械の中の口に届かない | 手元で `curl -s -o /dev/null -w '%{http_code}' https://m2office.net/internal/tls-allowed?domain=x` | `404` |
| 7 | CrowdSec が読んでいる | `sudo cscli metrics` | `Acquisition Metrics` に `/var/log/caddy/access.log` が出る |
| 8 | CrowdSec が止めている | `sudo cscli bouncers list` と `systemctl is-active crowdsec-firewall-bouncer` | `crowdsec-firewall-bouncer` が並び、`active`。無ければ見つけた相手を止められないので、`setup.sh` を走らせ直す |
| 9 | 国で通信を止めている | `sudo m2office-geo-update --status` と `systemctl list-timers m2office-geo-update.timer` | 止める国・範囲の数（2 万を超える）・止めた数が出て、次の取り直しの日時が出る。取り直しの記録は `journalctl -u m2office-geo-update` |

自分の手元のアドレスが止められて WireGuard でつながらなくなったときは、Xserver の管理画面のコンソールで入り、`sudo cscli decisions delete --ip <手元のアドレス>` で外します。

### 手順 5. 最初の運営者を作る

できたばかりのデータベースには、運営者がいません。Google でログインしても「このアカウントは運営者として登録されていません」と出ます。最初の運営管理者だけは、VPS の上で作ります（2 人目からはマスター管理画面で足します）。

```bash
cd / && sudo -u m2office node --env-file=/etc/m2office/m2office.env /opt/m2office/app/scripts/create-operator.mjs --email <運営管理者の Google のアドレス> --name "<名前>" --role admin
```

パスキーの登録の合言葉（24 時間・1 回だけ）が出ます。運営の画面で Google でログインしたあと、この合言葉を入れてパスキーを登録します。合言葉は人に見せず、作業の記録にも残しません。

### 手順 6. 最初の会社を作る

マスター管理画面（`https://ops.m2office.net`）で会社を作ります（第 3 章）。会社のサブドメインを初めて開いたときに、その名前の証明書を取ります（数秒かかります）。

### 手順 7. WAF を止める形にする（1〜2 週間後）

WAF は記録だけで始めます。週に 1 回、記録（`/var/log/caddy/waf-audit.log`）を見て、ふだんの使い方で当たっているものが無いか確かめます。当たっているものがあれば運営に知らせ、外す規則を決めてから、`setup.sh` を走らせ直して「WAF の動き」を `On` にします。

### 手順 8. 更新する

運営が新しい版を知らせたら、VPS の上で入れます。止まるのは数分で、その間は「ただいま M2Office を更新しています」と出ます。

```bash
sudo /opt/m2office/app/deploy/vps/update.sh --tag <リリースのタグ> --allow-unsigned
```

- 入れる前に、データベースの控えを `/var/backups/m2office/pre-update/` に取ります（直近の 3 回）。組み立て・移行・動きの確かめのどれかで失敗したら、前の版と控えに戻します
- `--allow-unsigned` は、タグへの署名を始める v1.0 までの間だけ付けます
- 最後に「deploy/vps の雛形が変わっています」と出たら、`setup.sh` を走らせ直します（前の答えのまま Enter で進めます）
- 記録は `/var/log/m2office/update.log` に残ります

### まだこの章に無いもの

社外の控え（pgBackRest・restic）は、置き場の事業者を運用を始めるときに決めてから足します（仕様書 第20.4.6節「控え」）。顧客を入れる前に入れます。夜の自動の更新は、タグへの署名を始める v1.0 から入れます。
