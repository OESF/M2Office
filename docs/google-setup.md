# Google 環境のセットアップ手順

開発と自社検証のために、Google Workspace と Google Cloud に用意するものをまとめます。

> **注記**: 管理コンソールの項目名は変わることがあります。
> 本書は「どこを探すか」の見当をつけるためのものです。実際の画面でご確認ください。
> 判断の根拠は仕様書の [第14章](../spec/14-google.md)・[第16章](../spec/16-security.md) にあります。

## 1. 全体像

| 用意するもの | 数 | 用途 |
|---|---|---|
| Google Cloud プロジェクト | 1 | Gemini の鍵と OAuth クライアント。**利用額を分けるため専用にする** |
| Workspace のテストユーザー | 2 | 管理者役と一般利用者役 |
| 組織部門（OU） | 1 | テストユーザーを入れ、設定の影響範囲を限る |
| OAuth クライアント | 1 | `http://localhost:3101` 向け |

**既存の Workspace の中にテストユーザーを作る**方針とする。
新規に Workspace を契約する必要はない。

### 役割の分離

| 用途 | 使うアカウント |
|---|---|
| Google Cloud プロジェクトの所有、鍵の発行 | **普段のアカウントでよい** |
| **OAuth でデータを渡す相手** | **テストユーザーに限る** |

普段使いのアカウントに OAuth でアクセス権を渡さないこと。
AG-01（メールの整理）は下書きを作るエージェントであり、
開発中の不具合で実際のメールに下書きが大量にできる事故を避ける。

## 2. 事前に確認すること

着手前に、次の 4 点を確認する。

| # | 確認事項 | 影響 |
|---|---|---|
| 1 | ユーザーを 2 人追加したときの月額 | プランにより異なる |
| 2 | **Meet の文字起こしが使えるか** | **使えないと AG-02 の検証が限定される** |
| 3 | Chat のスペース作成が許可されているか | AG-02 の共有部分で使う |
| 4 | ディレクトリからユーザーを隠す設定の有無 | 手順 3-3 で使う |

**第 2 項が最も重要である。** Meet の文字起こしはエディションによって
使えないことがある。使えない場合でも、テキストを貼り付ける形で AG-02 は動くため、
開発は止まらない（`packages/core/src/agents/ag-02-minutes.ts`）。

## 3. Workspace にテストユーザーを作る

### 3-1. 組織部門（OU）を作る

```
組織のルート
├── 通常の社員        ← 既存の設定のまま
└── M2Office テスト   ← テストユーザーを入れる
```

**OU を先に作ること。** OAuth アプリのアクセス許可を設定する際、
ドメイン全体に適用すると全社員に影響する。OU 単位に絞れば本番の社員に影響しない。

### 3-2. ユーザーを 2 人作る

| 役割 | アドレスの例 | 表示名の例 |
|---|---|---|
| 管理者・承認者 | `m2o-admin@<自社ドメイン>` | M2Office テスト（管理者） |
| 一般利用者 | `m2o-employee@<自社ドメイン>` | M2Office テスト（一般） |

**テストと分かる名前にする。** 同僚が見て本物の社員でないと分かることが目的である。

作成したら、手順 3-1 の OU へ移す。

### 3-3. ディレクトリから隠す

作ったユーザーは社内のアドレス帳に載る。
同僚が誤ってメールを送ることを避けるため、ディレクトリから隠す設定を探して有効にする。

## 4. Google Cloud プロジェクトを作る

### 4-1. プロジェクトを作る

| 項目 | 値の例 |
|---|---|
| プロジェクト名 | `m2office-dev` |
| 所有者 | 普段のアカウント |

**専用のプロジェクトにする。** Google Cloud の利用額はプロジェクト単位で集計されるため、
分けておけば M2Office の推論コストだけを取り出せる。
本番用は別のプロジェクトとして後で作る。

### 4-2. 予算アラートを設定する

**必ず設定する。** 想定を超えた利用に気づけるようにする。

仕様書 第21.2節で変動原価の管理を設計しているが、その実測値を取る土台がここにある。
Phase 1 で AG-01〜05 の実コストを測ることが、そのまま価格設計（Q-05、Q-49）の材料になる。

### 4-3. Gemini の鍵を取得する

取得した鍵は `.env` の `GEMINI_API_KEY` に設定する。

```bash
LLM_PROVIDER=gemini
GEMINI_API_KEY=<取得した鍵>
```

鍵が無い（または `LLM_PROVIDER=stub` の）ままでは、秘書も業務も動かない。`stub` は自動テスト専用である（仕様書 第20.2.4節、ADR-0030）。
会社ごとの鍵は、管理者ページの「接続」でも登録できる。

## 5. OAuth を設定する

### 5-1. 同意画面

| 項目 | 内容 |
|---|---|
| 公開ステータス | **テスト**のままにする |
| テストユーザー | **手順 3-2 で作った 2 つを登録する** |

**テスト状態の性質**（要確認）:

| 項目 | 内容 |
|---|---|
| 利用できる人 | 登録したテストユーザーのみ（100 人程度まで） |
| **更新トークンの期限** | **1 週間程度で失効する。開発中は定期的な再認可が必要** |
| **制限付きスコープ** | **審査なしで使える** |

最後の項目は重要である。Gmail の制限付きスコープに伴う審査（仕様書 Q-08）は
**一般公開するときの話**であり、開発と自社検証は審査を待たずに進められる。
ただし外販の前には必要になるため、時期の見通しは早めに立てる。

### 5-2. クライアントを作る

| 項目 | 値 |
|---|---|
| 種類 | ウェブアプリケーション |
| リダイレクト URI | `http://localhost:3101/v1/auth/google/callback` |

**ポートは 3101（API）である。** 画面（3100）ではない。
認証は API が処理し、画面は API を経由する（仕様書 第13.1節 A-2）。

既存の個人用エージェントが `localhost:3000` を使っていても、
別のクライアントとして登録されるため共存する。

取得した値を `.env` に設定する。

```bash
GOOGLE_CLIENT_ID=<クライアント ID>
GOOGLE_CLIENT_SECRET=<クライアントシークレット>
```

### 5-3. スコープは段階的に追加する

**最初からすべてを要求しない**（仕様書 第14.3節）。使う機能の分だけ追加する。

| 段階 | スコープ | 必要になる機能 |
|---|---|---|
| 1 | `openid` `email` `profile` | ログインとテナント判定 |
| 2 | カレンダーの読取 | AG-03、AG-05 |
| 3 | ドライブの読取（範囲を絞る） | AG-04 の知識取り込み |
| 4 | Tasks、Chat | AG-02 |
| 5 | **Gmail の読取・下書き作成** | AG-01。**制限付きスコープ** |

段階 5 を後回しにすれば、Phase 1 の大部分は審査の見通しが立つ前に進められる。

### 5-4. 業務の接続を管理者ページで登録する

メール・予定などを業務で扱うための接続は、**管理者ページ「接続」で登録する**（仕様書 第14.3.3節、ADR-0007）。
`.env` には書かない。お客さまの会社も同じ画面で、自社の OAuth クライアントを登録する。

1. 5-2 のクライアントの「承認済みのリダイレクト URI」に、管理者ページに表示される URI を**一字一句同じに**追加する。
   開発での値は、画面を HTTPS で動かしているかで変わる。`.env` の `GOOGLE_OAUTH_REDIRECT_URI` を同じ値にする

   | 開発サーバーの起動 | 戻り先 |
   |---|---|
   | `WEB_HTTPS=true npm run dev`（マイクを `*.lvh.me` で使うとき。ふだんはこちら） | `https://localhost:3100/v1/oauth/google/callback` |
   | `npm run dev`（HTTP） | `http://localhost:3100/v1/oauth/google/callback`（既定値） |

   **HTTPS で動かしているのに `http` を登録すると、許可を押した直後に「接続できません」となり、何も保存されない**
   HTTPS で動く開発サーバーは `http` の要求を受けないためである（2026-09-25 に、`http` の戻り先がつながらないことを確認）。
   Google は `http` の戻り先を `localhost` にしか認めないが、`https` の `localhost` は認める。
   開発用の証明書は `localhost` も含めて作ってある（`npm run dev:cert`）
2. 使う API（Gmail・Calendar・Tasks・Chat・Drive・Docs・Sheets・Slides・People・Meet・Forms）を有効にする
   - **Chat は、API を有効にするだけでは使えない。** Google Chat API の構成（Configuration）の画面で、
     アプリの名前・アバターの画像の URL・説明を入れて保存する（対話の機能は使わないので、切ったままでよい）。
     本人の権限で投稿する場合も Google が求める。設定が無いと、投稿のときに
     「Google Chat app not found」と返る（2026-09-25 に確認。仕様書 第14.3.4節「Chat」）
3. 管理者ページ「接続」の「Google Workspace」に、クライアント ID とシークレットを登録する
4. 個人設定の「Google 連携」で「Google と接続する」を押し、許可の状況を確かめる

同意画面が「内部」なら、社内の利用者は審査なしで接続できる（仕様書 第14.3.1節）。
Gemini の鍵も、`.env` の代わりに管理者ページ「接続」の「Gemini」で会社ごとに登録できる（自社の鍵）。

## 6. M2Office 側の設定

### 6-1. 初期データのドメインを合わせる

現在の初期データはテナントの Workspace ドメインを `alpha.example.jp` としている。
実際のドメインへ差し替える。

```
scripts/seed.mjs の workspace_domain と、ユーザーのメールアドレス
```

差し替え後に再投入する。

```bash
npm run db:reset
```

### 6-2. 動作を確認する

```bash
npm run dev
npm run smoke
```

## 7. 2 ユーザーで検証すること

| 検証できる | 検証できない |
|---|---|
| 管理者と一般利用者の権限の違い | **2 テナント間の分離** |
| 承認の流れ（依頼者と承認者が別人） | |
| 個人記憶が他人に漏れないこと | |
| Chat・共有ドライブ・Meet | |

**依頼者と承認者を分けて試すこと。**
別々のブラウザ（または別プロファイル）で開き、
`m2o-employee` が実行して `m2o-admin` が承認する流れを再現する。
これが本来の使われ方であり、1 人で試すと見落とす問題がある。

あわせて、**employee の秘書が admin のデータを参照しないこと**を確認する
（仕様書 不変則 I-9、I-10）。2 人いないと確認できない項目である。

テナント分離は Google を使わずに `npm run smoke` で検証済みである。
実際の Google と組み合わせた 2 テナント検証は Phase 2 で行う。

## 8. つまずきやすい点

| 症状 | 原因と対処 |
|---|---|
| 認可のあとエラーになる | リダイレクト URI の不一致。ログインは **3101**（手順 4）、業務の接続は **3100** の URI であるか確認する |
| 業務の接続で、許可のあと「接続できません」 | 開発サーバーを HTTPS で動かしているのに、戻り先が `http` になっている。手順 5-4 の表を見る |
| 数日後に認可が切れる | テスト状態の仕様。再認可する |
| テストユーザー以外で入れない | 同意画面のテストユーザーに登録されていない |
| 同僚からテストユーザーに連絡が来る | ディレクトリから隠す設定（手順 3-3） |
| Meet の文字起こしが取得できない | エディションの確認（手順 2 の第 2 項） |
| 利用額が把握できない | プロジェクトが分かれていない（手順 4-1） |

## 9. 後片付け

検証が終わったら、次のいずれかで費用を止める。

| 対象 | 方法 |
|---|---|
| テストユーザー | **停止**する（削除しなくてよい） |
| Google Cloud プロジェクト | 不要になれば削除する。まとめて片付く |
