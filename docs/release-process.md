# M2Office リリース規定

> 本書はバージョンの付け方と、リリースの進め方を定めます。
> コードの書き方は [coding-standards.md](coding-standards.md)、
> 設計上の決定は [specification.md](../specification.md) を参照してください。

## 1. 前提

M2Office は SaaS であり、**利用者はいつでも最新版を使っている**。
利用者が版を選んで留まることはできない。この前提が、以下すべての規定の理由になる。

| # | 前提から導かれること |
|---|---|
| 1 | 破壊的変更は、利用者に事前に知らせる以外に回避手段がない |
| 2 | 巻き戻しができる状態を常に保つ必要がある |
| 3 | 一部のテナントに先に配って様子を見る手段が要る（仕様書 FR-606） |
| 4 | 「気づいたら変わっていた」を避けるため、リリースノートが必須になる |

## 2. バージョンを持つ対象

**M2Office には版を持つものが複数ある。混同しないこと。**

| 対象 | 版の付け方 | 例 |
|---|---|---|
| サービス本体 | セマンティックバージョニング | `1.4.2` |
| 公開 API | URL のパスに含める。破壊的変更は新しい版を追加し旧版を維持 | `/v1`、`/v2` |
| エージェント定義スキーマ | 整数。破壊的変更のたびに増やす | `schema_version: 2` |
| 拡張機能 | セマンティックバージョニング。`platform_schema` で互換を宣言 | `1.2.0` |
| 仕様書 | `0.x.y`。確定前は `0` 系のまま | `0.10.0` |
| 本規定・開発規約 | セマンティックバージョニング | `1.0.0` |

公開 API とエージェント定義スキーマは、サービス本体の版とは独立して動く。
サービスが `2.0.0` になっても、API が `/v1` のまま提供され続けることはある。

## 3. セマンティックバージョニングの解釈

`MAJOR.MINOR.PATCH` とする。M2Office では以下のように判断する。

| 区分 | 該当する変更 |
|---|---|
| **MAJOR** | 公開 API の破壊的変更 / エージェント定義スキーマのメジャー更新 / 巻き戻せないデータ移行 / 既存の操作手順が変わる画面の改変 |
| **MINOR** | 機能の追加 / 新しいエージェントの追加 / 後方互換のある API の追加 / 既定値の追加（既存の挙動を変えないもの） |
| **PATCH** | 不具合の修正 / 文言の修正 / 性能の改善 / 依存パッケージの更新（挙動が変わらないもの） |

### 3.1 判断に迷う場合

| 状況 | 判断 |
|---|---|
| 既定値を変えた | 既存テナントの挙動が変わるなら MAJOR。新規テナントのみなら MINOR |
| 権限の要求が増えた | MAJOR 扱いとする。再同意が必要になるため（仕様書 第12.6節） |
| エージェントの出力の形式が変わった | 利用者が手順を変える必要があればMAJOR、そうでなければMINOR |
| 上限値を厳しくした | MAJOR。今まで通っていた処理が通らなくなる |
| 上限値を緩めた | MINOR |

**迷ったら大きいほうに倒す。** 小さく見積もって利用者を驚かせるより、
大きく告知して何も起きないほうがよい（開発規約 原則 c4）。

## 4. リリースの種類

| 種類 | 内容 | 手順 |
|---|---|---|
| 通常リリース | 計画された機能追加・修正 | 第6章の手順をすべて実施 |
| 緊急修正 | 障害・セキュリティ上の問題への対処 | 第8章の短縮手順 |
| 設定変更 | 価格・上限・モデル階層など設定値のみの変更 | 配備を伴わない。記録は残す |

## 5. リリースノート

### 5.1 2 種類を書く

**読み手が違うので、同じ文章を使い回さない。**

| 種類 | 読み手 | 置き場所 | 書き方 |
|---|---|---|---|
| **利用者向け** | 顧客企業の管理者・従業員 | 管理者ページの「お知らせ」。**お知らせの画面ができるまでは、ヘルプセンターの「更新情報」（`docs/help/updates-vX-Y-Z.md`）** | 業務の言葉。専門用語を使わない（仕様書 原則 u1） |
| **開発者向け** | 開発者、拡張機能の提供者 | `CHANGELOG.md` | 技術的な内容。API の変更点を省略しない |

### 5.2 書き分けの例

同じ変更でも、次のように書き分ける。

| 開発者向け | 利用者向け |
|---|---|
| `POST /v1/jobs` に `idempotency_key` を追加。省略時は従来どおり | 同じ依頼を二重に実行してしまう問題を防げるようになりました |
| 承認ゲートの再開処理でトランザクション境界を修正 | 承認後に処理が止まってしまう不具合を直しました |
| Gemini の高速モデル階層を更新 | 秘書の返答が速くなりました |

### 5.3 変更の分類

両方のリリースノートで以下の分類を使う。

| 分類 | 内容 |
|---|---|
| 追加 | 新しい機能・エージェント |
| 変更 | 既存の挙動の変更 |
| 非推奨 | 将来なくなるもの。**代替を必ず示す** |
| 削除 | なくなったもの |
| 修正 | 不具合の修正 |
| セキュリティ | 安全性に関わる修正 |

### 5.4 必ず書くこと

| # | 内容 |
|---|---|
| 1 | 利用者が**何かをしなければならない**場合、それを冒頭に書く |
| 2 | 権限の再同意が必要な場合、対象と理由を明記する |
| 3 | 既存の操作手順が変わる場合、変更前と変更後を並べて示す |
| 4 | 停止を伴う場合、時間帯と影響範囲を事前に告知する |

## 6. リリース手順

リリースの作業（変更の把握・版の決定・事前の確認・リリースノート・コミットとタグ）は、
Claude Code の `/release` スキル（[.claude/skills/release/SKILL.md](../.claude/skills/release/SKILL.md)）で行う。
スキルはこの章と第5章・第10章を手順にしたもので、版の番号とリリースノートを提示して了承を得てからコミットとタグを作る。push は行わない。

| 項目 | 規定 |
|---|---|
| 版を持つファイル | ルートと各ワークスペース（`packages/*`）の `package.json`、`package-lock.json`。**すべて同じ番号にそろえる** |
| コミット | 1 行目を `release: Version X.Y.Z — <概要>` とする |
| タグ | 注釈付きタグ `vX.Y.Z` |
| 画面の版 | 画面はビルドのときにルートの `package.json` の版を埋め込み、上の帯に出す（仕様書 第6.1.1.1節）。**リリースのコミットの後に `npm run build -w packages/web` で作り直し、埋め込まれた版を確かめる**。作り直しを省くと、画面の版が古いまま残る |

### 6.1 事前の確認

| # | 確認事項 | 根拠 |
|---|---|---|
| 1 | 仕様書が更新済みである | 開発規約 第12章 |
| 2 | エージェントの評価セットが通る | 仕様書 第18.2節 |
| 3 | テナント境界のテストが通る | 仕様書 第8.5.5節 |
| 4 | データ移行の手順と、**巻き戻しの手順**が用意されている | 第7章 |
| 5 | リリースノート（利用者向け・開発者向け）が書けている | 第5章 |
| 6 | 権限が増える変更の場合、再同意の導線が用意されている | 仕様書 第12.6節 |
| 7 | 影響するテナントへの事前告知が済んでいる（MAJOR の場合） | 第5.4節 |
| 8 | **利用者に見える変更について、ヘルプの記事を更新した**（業務の追加・画面や文言の変更・挙動の変更） | 仕様書 第6.10.9節 |

### 6.2 配備

| 順序 | 内容 |
|---|---|
| 1 | データベースの移行を適用する（後方互換のある形で） |
| 2 | API とワーカーを更新する |
| 3 | 画面を更新する |
| 4 | 動作を確認する |
| 5 | リリースノートを公開する |

**移行は後方互換のある形で適用する。**
列の削除・改名は、旧版のコードが動かなくなった後の別リリースで行う。
1 つのリリースで「移行＋旧コードの削除」を同時に行わない。

### 6.3 段階的配信

MAJOR および影響の大きい MINOR は、段階的に配る（仕様書 FR-606）。

| 段階 | 対象 |
|---|---|
| 1 | 自社テナント |
| 2 | 合意した一部のテナント |
| 3 | 全テナント |

各段階で、失敗率・遅延・却下率（仕様書 第18.1節）を確認してから次へ進む。

## 7. 巻き戻し

| # | 規定 |
|---|---|
| 1 | すべてのリリースについて、巻き戻す手順を事前に用意する |
| 2 | 巻き戻せない変更（不可逆なデータ移行）は、**別リリースに分ける** |
| 3 | 巻き戻した場合、理由と影響を記録し、利用者へ通知する |
| 4 | 実行中のジョブがある状態での巻き戻しを想定し、再開可能性を確認する |

## 8. 緊急修正

障害やセキュリティ上の問題に対処する場合、手順を短縮する。

| 短縮できること | 短縮できないこと |
|---|---|
| 事前告知 | 巻き戻し手順の用意 |
| 段階的配信 | テナント境界のテスト |
| 利用者向けリリースノートの事前作成 | 監査ログへの記録 |

**事後 24 時間以内に、利用者向けリリースノートを公開する。**
何が起きて、影響があったか、何をしたかを書く。

## 9. 非推奨と廃止

| 段階 | 内容 | 期間 |
|---|---|---|
| 1 | 非推奨を宣言する。代替手段を示す | — |
| 2 | 利用しているテナント・アプリへ個別に通知する | — |
| 3 | 猶予期間を置く | TBD: 公開 API は最低 6 か月 |
| 4 | 削除する | — |

公開 API の旧版は、新版の提供開始から一定期間維持する（仕様書 第13.1節 A-4）。
拡張機能の廃止は、提供者が予告を宣言し、利用中テナントへ通知される（仕様書 第12.6節）。

## 10. 記録

| 対象 | 保存先 |
|---|---|
| 開発者向けリリースノート | `CHANGELOG.md`（リポジトリ直下） |
| 利用者向けリリースノート | 管理者ページの「お知らせ」。運営側にも履歴を残す |
| 配備の記録 | 監査ログ（誰が、いつ、どの版を配備したか） |
| 巻き戻しの記録 | 監査ログ。理由を含める |
