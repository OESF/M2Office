# M2Office 開発規約

> 本書は M2Office のコードを書くときに従う規約です。
> 設計上の決定は [specification.md](../specification.md) を正とし、本書は「どう書くか」を定めます。
> リリースとバージョンについては [release-process.md](release-process.md) を参照してください。

## 1. 適用範囲と原則

### 1.1 適用範囲

本書はリポジトリ内のすべてのコードに適用する。
第三者が提供する拡張機能（仕様書 第12章）には強制しないが、公式が作るものは本書に従う。

### 1.2 原則

| # | 原則 | 意味 |
|---|---|---|
| c1 | 仕様書が先 | 実装が仕様書と食い違う場合、コードではなく仕様書を先に直す |
| c2 | 読む人を想定する | 半年後の自分と、はじめて読む人が対象。短さより明瞭さ |
| c3 | 暗黙を残さない | 「分かっている人には分かる」書き方をしない |
| c4 | 安全側に倒す | 判断に迷う場面では、制限が強いほう・確認を求めるほうを選ぶ |
| c5 | 境界を守る | テナント境界と承認ゲートは、どんな事情があっても迂回しない |

## 2. 言語とツール

| 項目 | 規定 |
|---|---|
| 言語 | TypeScript。`strict` を有効にする |
| 実行環境 | Node.js の LTS 版 |
| `any` | 原則禁止。やむを得ない場合は理由をコメントで残す |
| `as` による型断定 | 原則禁止。型ガードを書く |
| 整形 | Prettier。設定はリポジトリのものを使い、個人設定で上書きしない |
| 静的解析 | ESLint。警告を残したままコミットしない |
| パッケージ管理 | ロックファイルを必ずコミットする（仕様書 第20.8節） |

## 3. ディレクトリとパッケージ

仕様書 第20.5節のパッケージ構成に従う。依存の向きを破らないこと。

| パッケージ | 依存してよい | 依存してはならない |
|---|---|---|
| `core` | `shared` | HTTP、フレームワーク、画面 |
| `api` | `core`、`shared` | `web`、`worker` |
| `worker` | `core`、`shared` | `web`、`api` の内部実装 |
| `web` | `shared`（型のみ） | `core`、データベース |

**`core` に HTTP やフレームワークを持ち込まないこと。**
ここが崩れると、同じロジックを API とワーカーから呼べなくなる。

## 4. 命名

| 対象 | 規則 | 例 |
|---|---|---|
| 識別子 | 英語。ローマ字は使わない | `approveRun`（`shouninSuru` は不可） |
| 変数・関数 | キャメルケース | `tenantId`、`resumeRun` |
| 型・クラス | パスカルケース | `AgentDefinition`、`RunState` |
| 定数 | 大文字スネークケース | `MAX_RUN_STEPS` |
| ファイル | ケバブケース | `resume-run.ts` |
| 真偽値 | `is` / `has` / `can` で始める | `isApproved`、`canExecute` |
| 非同期関数 | 動詞から始める。`Async` は付けない | `fetchRun`（`fetchRunAsync` は不可） |

**業務用語は仕様書 第3章の用語定義に合わせる。**
同じものを別の名前で呼ばない（例: 実行は `run`。`execution` や `task` と混在させない）。

## 5. JSDoc

### 5.1 基本方針

**型は TypeScript に書き、JSDoc には「なぜ」と「どう使うか」を書く。**

TypeScript が表現できる情報（型、必須か任意か）を JSDoc で繰り返さない。
重複した記述は、片方だけ更新されて嘘になる。

| 書く | 書かない |
|---|---|
| 何をする関数か | 引数の型（`@param {string}` のような型注記） |
| なぜその処理が必要か | コードを読めば分かる手続きの説明 |
| 呼び出し側が守るべき前提 | `@typedef`、`@type`（TypeScript で書く） |
| 例外が起きる条件 | 自明な getter/setter の説明 |
| 業務上の制約（危険度、テナント境界） | |

### 5.2 記述する対象

| 対象 | JSDoc |
|---|---|
| `export` される関数・クラス・型 | **必須** |
| 公開 API のハンドラ | **必須** |
| エージェント定義スキーマの各フィールド | **必須** |
| ツール関数（仕様書 第9.4節） | **必須。危険度を明記する** |
| パッケージ内部のみの補助関数 | 任意。意図が自明でない場合は書く |
| 画面のコンポーネント | 用途と前提を書く |

### 5.3 ファイルの先頭（ファイルヘッダー）

**すべてのソースファイルは、ファイルヘッダーから始める。** インポート文より前に置く。
ファイルを開いた人が、最初の数行で「このファイルが何をするか」を分かるようにするためである。

```ts
/**
 * @file 実行エンジン。承認ゲートでの中断と、別のワーカーからの再開を担う。
 *
 * 状態はすべて永続化層から読み直し、メモリ上の文脈に依存しない。
 * 承認後は、中断したワーカーとは別のワーカーが続きを実行する。
 *
 * @see 仕様書 第9.3節 実行ライフサイクル
 */

import { randomUUID } from 'node:crypto';
```

| 規則 | 内容 |
|---|---|
| 位置 | ファイルの 1 行目から。インポート文・コードより前。ヘッダーの後ろには空行を 1 つ置く |
| 1 行目 | `@file` に続けて、**このファイルが何をするか**を 1 文で書く |
| 補足 | 役割・使われ方・守るべき前提を、必要なら 2〜5 行で書く |
| 参照 | 関連する仕様書の節を `@see` で示す |
| 宣言の JSDoc との関係 | ファイルヘッダーはファイル全体の説明、宣言の JSDoc は個々の関数・クラスの説明。**混ぜない**。ヘッダーを書いたことを理由に、`export` の JSDoc を省かない |
| 禁止 | インポート文の後ろに、どの宣言にも付かない説明のコメントを置くこと。ファイルの説明はヘッダーに書く |

対象は `.ts`・`.tsx`・`.mjs`・`.js` のすべて（テスト・設定ファイル・スクリプトを含む）。
Python のスクリプトは、同じ内容をモジュールの docstring として先頭に置く
（`# -*- coding: utf-8 -*-` の行がある場合はその直後）。
SQL のマイグレーションは、先頭の `--` のコメントで同じ内容を書く。

### 5.4 使用するタグ

| タグ | 用途 |
|---|---|
| `@file` | ファイルヘッダーの 1 行目。ファイルが何をするか（第5.3節） |
| `@param` | 引数の意味。**型は書かない** |
| `@returns` | 戻り値の意味。`void` の場合は省略 |
| `@throws` | 例外の型と、それが起きる条件 |
| `@remarks` | 前提・制約・注意点。業務上の決まりはここに書く |
| `@example` | 使い方。引数の組み合わせが自明でない場合に付ける |
| `@see` | 関連する仕様書の節、関連する関数 |
| `@deprecated` | 非推奨。**代替手段を必ず書く** |

### 5.5 言語

**JSDoc とコメントは日本語で書く。** 識別子は英語のままとする。
1 つの記述の中で日本語と英語を混在させない（技術用語の原語表記は除く）。

### 5.6 記述例

```ts
/**
 * 承認ゲートで中断した実行を、保存した文脈から再開する。
 *
 * 承認操作を受けたワーカーが呼び出す。中断時とは別のプロセスで動くため、
 * 状態はすべて永続化層から読み直す。メモリ上の文脈に依存してはならない。
 *
 * @param runId 再開する実行の識別子
 * @param approval 承認の記録。却下の場合は実行を打ち切る
 * @returns 再開後の実行状態
 * @throws {RunNotResumableError} 実行が承認待ち以外の状態にある場合
 *
 * @remarks
 * テナント境界: `runId` からテナントを解決し、呼び出し元のテナントと
 * 一致することを必ず検証する（仕様書 不変則 I-2）。
 *
 * @see 仕様書 第9.3節 実行ライフサイクル
 */
export async function resumeRun(
  runId: RunId,
  approval: Approval,
): Promise<RunState> {
  // ...
}
```

ツール関数では、**危険度を `@remarks` に必ず書く**。

```ts
/**
 * Gmail の下書きを作成する。送信は行わない。
 *
 * @param userId 下書きを作成する利用者
 * @param draft 宛先・件名・本文・添付
 * @returns 作成された下書きの識別子
 *
 * @remarks
 * 危険度: `draft`（承認不要）。
 * 送信は {@link sendMail} が担い、そちらは `external-send` のため承認が必須である。
 * この関数で送信処理を行ってはならない。
 *
 * @see 仕様書 第9.4節 ツールと承認の対応
 */
export async function createGmailDraft(
  userId: UserId,
  draft: MailDraft,
): Promise<DraftId> {
  // ...
}
```

### 5.7 コメント

| 種類 | 方針 |
|---|---|
| 意図のコメント | 書く。「なぜこうしたか」は code に残らない |
| 手続きのコメント | 書かない。コードを読めば分かることは繰り返さない |
| `TODO` | 書いてよい。ただし**担当と期限、または課題番号を添える** |
| コメントアウトしたコード | 残さない。履歴は Git にある |

## 6. エラー処理

| 項目 | 規定 |
|---|---|
| 例外の型 | 独自のエラー型を定義し、`Error` をそのまま投げない |
| 握りつぶし | 禁止。`catch` して何もしない処理を書かない |
| 利用者への表示 | 「何が起きて、次に何をすべきか」を平易な日本語で返す（仕様書 原則 u4） |
| 内部情報 | スタックトレースや SQL を利用者に見せない |
| 取得失敗 | **推測値で処理を続けない。** 「取得できなかった」と明示する（仕様書 第9.2節） |
| 再試行 | 外部連携は再試行の回数と間隔を定義する。無限に再試行しない |

## 7. ログ

3 種類を混ぜないこと。

| 種類 | 目的 | 保存先 | 注意 |
|---|---|---|---|
| 監査ログ | 誰が何をしたかの証跡 | データベース（追記のみ） | 仕様書 第16.6節。削除・更新は不可 |
| アプリログ | 障害調査 | ログ基盤 | 個人情報・認証情報を書かない |
| 会話ログ | 利用者の参照と改善 | データベース | 仕様書 第11.9節 |

**アプリログに顧客データの中身を書かない。** 識別子までとする。

以下はアプリログ（システムログ）の決まりである。

### 7.1 出力の方法

**`console.log` を直接使わない。** `@m2office/core` のロガー（`createLogger`）を使う。
ロガーを通すことで、レベルによる絞り込み・形式・付加情報・伏せ字の処理が一か所で効く。

例外: 画面（`packages/web`）と、単発のスクリプト（`scripts/`・`tools/`）は対象外とする。

### 7.2 レベル

| レベル | 使う場面 | 例 |
|---|---|---|
| `error` | 処理が失敗し、人の対応が要るかもしれない | 想定外の例外、データベースに接続できない、API の 500 |
| `warn` | 失敗ではないが、注意して見るべき | 承認ゲートがツールの実行を止めた、実行が業務上の理由で失敗した、定時実行を見送った |
| `info` | 運用上の主な出来事 | 起動と停止、API の要求 1 件ごと、実行の開始・完了・承認待ち、定時実行の起動 |
| `debug` | 開発時の追跡 | ステップの開始と終了、ツールの呼び出し |

**迷ったら 1 つ下げる。** `error` が多すぎると本当の異常が埋もれる。
利用者の入力の誤り（400・401・403・404）は `error` にしない。

### 7.3 切り替え

| 変数 | 値 | 既定 |
|---|---|---|
| `LOG_LEVEL` | `error`・`warn`・`info`・`debug` | 開発は `debug`、本番（`NODE_ENV=production`）は `info` |
| `LOG_FORMAT` | `json`・`pretty` | 開発は `pretty`（人が読む形）、本番は `json` |

指定したレベルより下は出力しない（`info` なら `debug` は出ない）。

### 7.4 形式

本番は **1 行 1 件の JSON** とする。ログ基盤で検索・集計できるようにするため。

```json
{"time":"2026-09-22T09:12:03.418Z","level":"info","service":"api","msg":"要求","requestId":"4f1c…","tenantId":"t-alpha","userId":"u-a-admin","method":"POST","path":"/v1/jobs","status":201,"ms":12}
```

| 項目 | 内容 | 必須 |
|---|---|---|
| `time` | ISO 形式の時刻（UTC） | 必須 |
| `level` | レベル | 必須 |
| `service` | どのプロセスか（`api`・`worker`） | 必須 |
| `msg` | 何が起きたか。日本語の短い文 | 必須 |
| `requestId` | API の要求ごとの ID。応答の `X-Request-Id` と同じ値 | API の処理中 |
| `tenantId`・`userId` | 会社と利用者の ID | 分かる場合 |
| `runId` | 実行の ID | 実行の処理中 |
| `err` | 例外の名前・メッセージ（`error` では呼び出し履歴も） | 例外のとき |

### 7.5 書いてはならないもの

| 対象 | 扱い |
|---|---|
| 認証情報（パスワード、トークン、API 鍵、Cookie、CSRF トークン） | 書かない |
| 顧客データの中身（メール・文書・議事録・会話・業務の入力と成果物） | 書かない。ID までとする |
| 要求の本文と、URL の問い合わせ文字列 | 書かない。経路（`path`）だけを書く |

ロガーは、名前が `password`・`token`・`secret`・`authorization`・`cookie`・`body`・`text`・`content`・
`transcript`・`input` などの項目を自動で伏せ字にし、長い文字列は切り詰める。
**これは書き漏らしへの備えであり、中身を渡してよい理由にはならない。**

### 7.6 保存と入れ替え

システムログは 4 週分（週ごとに 4 世代）を残して入れ替える（仕様書 第11.9.6節）。
開発では標準出力に出すだけとし、保存と入れ替えは本番の出力先（仕様書 第20.4.2節）を決める時点で
その基盤の機能で行う。アプリは標準出力へ書くことだけに責任を持つ。

## 8. テスト

| 対象 | 必須 |
|---|---|
| `core` のドメインロジック | 必須 |
| 公開 API の各エンドポイント | 必須 |
| テナント境界（越境が失敗すること） | **必須。仕様書 第8.5.5節** |
| 承認ゲートが省略されないこと | **必須** |
| エージェント定義の評価セット | 必須（仕様書 第18.2節） |
| 画面 | 主要な操作の流れ |

**テナント越えのアクセスが必ず失敗することを、自動テストで常時確認する。**
これは機能テストではなく、安全性の回帰テストとして扱う。

## 9. セキュリティ上の遵守事項

仕様書 第16章の規定をコードとして守るための決まり。

| # | 規定 |
|---|---|
| s1 | データベースアクセスは必ずテナント ID による絞り込みを伴う。RLS を迂回する接続を作らない |
| s2 | テナント ID はトランザクション単位で設定する。セッション変数に置かない（第8.5.5節） |
| s3 | 認証情報・トークンを LLM へのプロンプトに含めない |
| s4 | 外部から取得した文書・メール・MCP 応答を、指示として解釈する処理を書かない（不変則 I-6） |
| s5 | 危険度 `external-send` 以上の操作は、承認済みであることをコード上で検証してから実行する |
| s6 | 秘匿情報はシークレット管理から取得する。ソースにも環境変数の既定値にも書かない |
| s7 | 個人記憶へのアクセスは、テナント ID に加えてユーザー ID でも絞る（不変則 I-10） |

## 10. Git

| 項目 | 規定 |
|---|---|
| 既定ブランチ | `main`。直接コミットしない |
| 作業ブランチ | `feature/<内容>`、`fix/<内容>`、`docs/<内容>` |
| コミット粒度 | 1 つの意図につき 1 コミット |
| コミットメッセージ | 「種別: 要約」の形式（下表）。日本語で書く |
| プルリクエスト | 変更の意図、影響範囲、確認方法を書く |

コミットメッセージの種別は以下から選ぶ。

| 種別 | 用途 |
|---|---|
| `feat` | 機能の追加 |
| `fix` | 不具合の修正 |
| `docs` | 文書のみの変更 |
| `refactor` | 挙動を変えない整理 |
| `test` | テストの追加・修正 |
| `chore` | 依存更新、設定変更 |

例: `feat: 承認ゲートからの実行再開を実装`

コミットの種別は、リリースノートの分類（[release-process.md](release-process.md)）に対応させる。

## 11. README

### 11.1 作成の義務

**README.md は必ず作成する。**

| 場所 | 内容 |
|---|---|
| リポジトリ直下 | プロジェクト全体の説明、開発環境の立ち上げ方 |
| 各パッケージ（`core`・`api`・`web`・`worker`・`shared`） | そのパッケージの責務と使い方 |
| 拡張機能 | 管理者向けの説明（仕様書 第12.3節） |

### 11.2 構成

以下の見出しを基本とする。不要な項目は省いてよいが、順序は変えない。

```markdown
# パッケージ名

<何をするものかを 2〜3 行で。読み手が「自分に関係あるか」を判断できること>

## 前提
<Node.js の版、必要な外部サービス、権限>

## セットアップ
<手順をコマンドで。上から順に実行すれば動く状態にする>

## 起動
<開発時の起動方法。複数プロセスがある場合はそれぞれ>

## テスト
<実行方法と、何を検証しているか>

## 構成
<ディレクトリの役割。図が有効なら図で>

## 設定
<環境変数の一覧と意味。既定値と必須かどうか>

## 関連文書
<仕様書の該当章へのリンク>
```

### 11.3 書き方

| # | 規定 |
|---|---|
| r1 | **最初の 3 行で「何をするものか」が分かること。** 背景説明から始めない |
| r2 | コマンドはコピーして実行できる形で書く。省略や `...` を使わない |
| r3 | 前提（版、権限、外部サービス）を省かない |
| r4 | 設計の理由は書かない。仕様書または ADR へリンクする |
| r5 | 更新を伴う変更をしたら、同じコミットで README も直す |

**r5 を守ること。** 古い README は、無い README より有害である。

## 12. 仕様書との関係

| 状況 | 対応 |
|---|---|
| 仕様にない機能を実装したくなった | 先に仕様書を更新し、合意を得てから実装する |
| 実装して初めて仕様の不備に気づいた | 実装を止めて仕様書を直す。コードを先に進めない |
| 設計上の判断をした | ADR（`docs/adr/`）に残し、仕様書からリンクする |
| 仕様書の `TBD` を解消した | 該当箇所と未決事項一覧（第26章）の両方を更新する |
