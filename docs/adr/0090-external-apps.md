# ADR-0090 外部のアプリ（汎用の API と鍵の形）

| 項目 | 内容 |
|---|---|
| 状態 | 採用（2026-10-10。三浦さんが、つなぐ依頼が続くため汎用の API として定義することを求め、外部のアプリの登録の形・作った販売管理とのつなぎをいま移すこと・画面と同じ `/v1` の道で呼ぶことを選んだ。会社の基本情報を読む機能も求めた。仕様書 第 0.326.0 版で実装） |
| 決定日 | 2026-10-10 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第13.1節・第13.4節・第13.4.1節・第29.20.1節・第11.12節・第6.10.7.4節・第9.4.0節。ADR-0087（販売管理とのつなぎ）・ADR-0089（M2Medical とのつなぎ）・ADR-0088（ヘルプの開発者の項目） |

## 背景

- 販売管理とのつなぎ（ADR-0087）を、つなぎごとの鍵と専用の口（`/v1/hooks/inventory/sales/…`）で作った。続けて M2Medical から、ナレッジを検索する口の依頼が来た（ADR-0089）。
- 用途ごとに口・画面・鍵の管理を作ると、依頼のたびに同じものが増える。第13.4節には「管理者がアプリを登録し、スコープを選んで発行」があるが、まだ作っていなかった。
- 第13.1節は、画面の API と外部公開の API を同じ基盤にし、内部だけの抜け道を作らない方針を置いている。
- 販売管理とのつなぎは、まだ push もリリースもしておらず、外で使っている人はいない。

## 検討した案

| 論点 | 採った案 | 採らなかった案 |
|---|---|---|
| 形 | **外部のアプリの登録**（アプリごとに鍵と機能を選んで承認する。第13.4節を鍵の形で先に作る） | 用途ごとのつなぎを共通の部品で作る（依頼のたびに画面と口が増える） |
| 販売管理 | **いま移す**（道・表・画面を作り直し、在庫の処理はそのまま使う） | いまの形を残す（形が 2 つ並ぶ） |
| 道 | **画面と同じ `/v1` の道**（`/v1/inventory/catalog` など。鍵の会社と呼んだ名前の会社が合わなければ断る） | `/v1/ext/…` に分ける（境界は分かりやすいが第13.1節とずれる） |

## 決定

1. 管理者ページの「接続」の「外部のアプリ」で、アプリを 1 社に 20 まで登録できる。鍵（`m2oa_` で始まる）は一度だけ見せ、ハッシュだけを持つ。
2. アプリごとに機能を選び、機能ごとの設定と一緒に「この内容で許す」で承認する。承認するまで、どの機能も使えない。選んでいない機能の道は 403。
3. 機能は `company.profile`（会社の基本情報を読む）・`inventory.catalog`（商品の一覧を読む）・`inventory.sales`（販売を知らせる）を作る。`accounts.link`・`knowledge.search` は案（ADR-0089）。
4. 道は画面と同じ `/v1`。認証の段で鍵を見て、機能の道だけを通す。管理者ページと本人の道は、どの機能でも呼べない。
5. 鍵が違う・止めた・会社が止まっている・会社が合わないは同じ 404。回数の上限はアプリごとに 1 分 120 回。書き込みは `eventId` で二重に数えない。
6. すべての機能の道を 1 つの OpenAPI の定義に書き、販売管理・M2Medical は使い方の例としてヘルプの記事で解説する。
7. OAuth は、あとで同じアプリに足し、機能をスコープとして使う。

## 結果

- 良い点: 新しいつなぐ依頼は、機能を 1 つ足すだけで済む。鍵・承認・上限・監査・止める操作が 1 か所にまとまる。第13.1節の方針に合う。
- 悪い点: 販売管理とのつなぎの道が変わった（まだ使っている人はいない）。機能ごとの設定の画面は、機能が増えるほど「外部のアプリ」の画面に増える。

## 追記（仕様書 第 0.327.0 版。2026-10-10）

三浦さんが、外部のアプリとして公開すると便利な機能の提案を求め、次の 8 つを案にすることを選んだ（勤怠の打刻と監査ログを読む機能は外した）。詳細は仕様書 第13.4.2節。

| 機能（案） | 実行主体 |
|---|---|
| 問い合わせを受ける（`inquiries.intake`） | アプリ |
| 社内のお知らせを出す（`notices.post`） | アプリ（宛先は承認した範囲だけ） |
| 入庫を知らせる（`inventory.receipts`） | アプリ |
| 予約の空きを読む・予約を入れる（`reservations.book`） | 空きはアプリ、予約は結び付いた本人 |
| 会員のポイントを付ける・使う（`members.points`） | アプリ（金額は残さない） |
| 公開したコラムを読む（`columns.read`） | アプリ |
| 社内規程を登録・改定する（`knowledge.rules`） | アプリ（書ける権限区画は承認した範囲だけ） |
| 業務を依頼して結果を受け取る（`jobs.run`） | 結び付いた本人（外から承認できない） |

決めたこと:

1. どれも既にある機能を外部のアプリの鍵で使えるようにするもので、元の機能の決まり（権限・人の情報・承認・お金を扱わない）をそのまま守る。
2. 会社として行うものはアプリ自身、本人として行うもの（予約・業務の依頼）は `accounts.link` で結び付いた本人で行う。今の拡張の利用範囲の確かめは、人やグループを前提にしているため、アプリ自身の機能では機能の承認で決める。
3. 画面に同じ操作の道があるもの（お知らせ・予約・業務の依頼）はその道を使い、無い形のものは道を足す。
4. 作る順は合意のあとに決める。
