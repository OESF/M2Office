# ADR-0022 Google の接続口は Gmail とカレンダーから本物にし、残りは見本で代えずに断る

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-25 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第14.3.4節、第14.3.3節、不変則 I-9、ADR-0003 |

## 背景

会社の OAuth クライアントの登録と、利用者ごとの接続が、本物の Google（`oesf.jp`）で通った（2026-09-25）。
接続口（ADR-0003）の `google` 実装は、まだ 1 つも無い。

接続口は 11 のサービス（Gmail・カレンダー・ToDo・Chat・ドライブ・ドキュメント・スプレッドシート・スライド・
ディレクトリ・Meet・フォーム）を持つ。一度に全部を本物にすると、確かめる範囲が広すぎる。

## 決定

**1. Gmail とカレンダーから本物にする。**

秘書の即答（予定・未読メール）、AG-01 受信箱整理、AG-03 日程調整がこの 2 つで動く。
利用者が毎日触る部分であり、本物のデータで確かめる価値が最も大きい。

**2. 準備中のサービスは、見本で代えずに断る。**

`CONNECTOR_MODE=google` のとき、まだ作っていないサービスが呼ばれたら「準備中」と断る。
見本の接続口に回さない。

**3. 読むツールは断られても実行を止めず、書くツールはステップを失敗にする。**

断りは例外（`ConnectorUnavailableError`）で伝え、エンジンがツールを呼ぶ 1 か所で受ける。
危険度 `read` のツールなら「取得できませんでした」と理由つきの結果にし、推論に渡す。
それ以外はそのまま例外にし、ステップを失敗にする。

**4. 開発では、会社ごとに見本と本物を分けられるようにする。**

`CONNECTOR_MOCK_TENANTS` に挙げた会社だけ見本の接続口を使う。
値の出どころ（`source`）は接続口全体ではなく会社ごとに決まるため、`WorkspaceConnector.sourceFor(tenantId)` で引く。
**本番で設定したら起動を拒否する。**

## 理由

| 観点 | 内容 |
|---|---|
| 見分けられること | 本物のメールと見本の ToDo が 1 つの週次ブリーフに混ざると、利用者はどれが本物か分からない。「取得できませんでした」のほうが正直である |
| 不変則 I-9 | 許可がないときに見本や他人のトークンで代わりに動かさない、という規定と同じ考え方を、準備中のサービスにも当てはめる |
| 読むものは続けられる | ToDo が取れないだけで週次ブリーフ全体を失敗にすると、本物の予定とメールのまとめまで失う |
| 書くものは止める | 書いたつもりで先へ進むと、後の段（共有・通知）が、無い ToDo を前提に動く |
| 通しの確認を保つ | smoke の会社（`a`・`b`）は決まった見本のデータを前提にしている。本物の会社（`oesf`）と同じサーバーで両方を動かす必要がある |
| 1 か所で受ける | ツールごとに受けると、30 近いツールに同じ処理が散らばる |

## 却下した案

| 案 | 却下した理由 |
|---|---|
| 準備中のサービスは見本に回す | 本物と見本が 1 つの結果に混ざる。出どころの印は推論を通ると消えうる |
| 全サービスを作り終えてから切り替える | 確かめる範囲が広すぎ、どこで壊れたか分からなくなる |
| 開発用に API を 2 つ立てる（見本用と本物用） | ポートと設定が倍になり、画面をどちらにつなぐかで迷う |
| 会社ごとの切り替えを「OAuth クライアントを登録したか」で決める | smoke が架空のクライアントを登録する間だけ会社が本物に切り替わり、確認が不安定になる。明示の設定のほうが読みやすい |

## 影響

- `CONNECTOR_MODE=google` の会社では、AG-02 議事録（ToDo・Chat を使う）が、ToDo の起票の段で失敗する。
  ToDo と Chat を本物にするまでは、見本の会社で確かめる
- AG-05 週次ブリーフは、ToDo の部分が「取得できませんでした」になる
- `WorkspaceConnector.source` を `sourceFor(tenantId)` に置き換えた。出どころを見る場所はすべて会社を渡す
