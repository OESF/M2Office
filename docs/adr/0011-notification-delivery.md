# ADR-0011 通知を Chat とメールへ届ける方式（控えとして題名とリンクだけを送る）

| 項目 | 内容 |
|---|---|
| 状態 | 採用（Q-86 の一部を決定。メールの送信サービスの選定は Q-86 に残す） |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第6.5.5節、第9.2.3節、第14.3.2節、第23.8.6節、ADR-0003 |

## 背景

通知は画面内のお知らせだけで、仕様書の「受け取り方: 画面内／Chat／メール」（第6.5.5節）が実装されていなかった。
承認依頼に気づかず、承認待ちのまま業務が止まることが起きうる。

Google への実接続（B-2）とメールの送信サービスの選定は、どちらもまだ終わっていない。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | **画面内のお知らせを正とし、Chat とメールはその控え**とする | 届け先が増えても、読む場所と既読の管理を 1 か所に保てる。届かなくても画面で気づける |
| 2 | 送り元は**会社の Google Chat アプリ**（本人への個別メッセージ）と**運営の送信用アドレス**（メール） | 本人が Google の許可を与えていなくても届く。承認依頼は、許可の有無によらず届かないと意味がない。本人の権限では、本人宛ての個別メッセージを送れない |
| 3 | 載せるのは**種類・題名・画面へのリンクだけ**。本文は載せない | 業務の中身（Google から読んだデータと、そこから作った文）を M2Office の外へ出さない。第14.3.2節の保持の規定は M2Office の中の話であり、外へ出したものには及ばない |
| 4 | 既定は**画面内のみ**。本人が個人設定で Chat とメールを入り切りする | 通知の好みは人によって違う。既定で会社のメールに流れ込むと、まず嫌われる |
| 5 | 通知しない時間帯の間は、**画面内には作り、Chat とメールへは時間帯が明けてから送る** | 夜間に鳴らさず、朝に見落とさない。まとめず 1 件ずつ送り、順序と既読の対応を保つ |
| 6 | 届ける役はワーカーの見回りとし、送信済みの時刻を通知ごとに記録する | 失敗しても次の見回りで再び試せる。二重に送らない |
| 7 | 送信口は接続口（インターフェース）の後ろに置き、**まず見本の実装**で全体を通す | ADR-0003 と同じ進め方。B-2 とメールの送信サービスの選定を待たずに、設定・時間帯・重複の除き方まで確かめられる |
| 8 | 承認依頼・完了・失敗の通知そのものも、あわせて作る | Chat とメールで届けたいものの中心がこれらである。届ける仕組みだけ作っても、届けるものが無い |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| 本人の Google の許可でメールを送る（本人の Gmail から本人宛て） | 許可を与えていない人に届かない。Chat の個別メッセージは本人の権限では送れず、Chat とメールで仕組みが分かれる |
| 本文も載せる | 決定 3 の理由。とくに受信箱整理や議事録の本文は、社外の転送で漏れたときの影響が大きい |
| 既定で Chat とメールを入れる | 既定で鳴ると通知そのものを切られる。まず画面内で慣れてもらう |
| 時間帯の間の通知を、明けたときにまとめて 1 通にする | まとめる単位（どこまで束ねるか）を決める必要があり、既読との対応も崩れる。件数が増えたときに改めて考える |
| 通知ごとに送信の待ち行列（別の表）を作る | いまは通知 1 件につき最大 1 回送るだけで足りる。表を増やすより、通知に送信済みの時刻を持たせるほうが単純 |
