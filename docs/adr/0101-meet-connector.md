# ADR-0101: Meet の文字起こしを本物にし、題名はカレンダーの予定から引く

- 状態: 採用（第 0.375.0 版で実装）
- 日付: 2026-10-16
- 関係: 仕様書 第14.3.4節「Meet」・第9.4.4節・第9.5.2節・第9.5.2.1節・第9.2.1節（第 0.375.0 版）、ADR-0022、ADR-0081

## 背景

会議が終わったら議事録を作り始める仕組み（ADR-0081）と、ツール `meet.transcript` は見本の接続口だけで動いていた。
本物の Google の Meet の接続口が無いため、Phase 1 の完了条件 3（議事録が自動でできる）が本物の会社では動かなかった。
三浦さんが Meet の接続口を進めるよう決めた（2026-10-16）。

作る中で、次の 3 つが分かった。

1. Meet REST API の会議の記録には**題名が無い**。会議の場所の会議のコード（`abc-defg-hij`）だけがある。
2. 会議の記録の一覧には、**本人が主催した会議だけ**が返る（Google の説明）。文字起こしの項目は、主催者と参加者が読める。
3. 議事録の作成（AG-02）の取得の段は、貼り付けた記録を返すだけの `meeting.get_transcript` しか持たず、自動の議事録（題名だけを渡す）は、本物の Meet があっても記録を取れなかった。
   さらに、ツールが「取得できなかった」と返しても段は空とみなされず、次の段が記録の無いまま議事録を書きうる作りだった。

## 決定

1. **題名は、同じ会議のコードを持つカレンダーの予定から引く**（`calendar.readonly` は ほかの業務ですでに求めている）。同じコードの繰り返しの予定は、始まりがいちばん近い回。予定の無い会議は「Meet の会議（会議のコード）」と呼ぶ。
2. **参加しただけの会議**は、本人のカレンダーの予定（本人が主催でないもの）の会議のコードで記録を探す。読めなければ飛ばす（作り話で埋めない）。
3. AG-02 に `meet.transcript` を持たせ、取得の段の順を「ファイル → 貼り付け → Meet」にする。自動の議事録は会議の記録の ID を入力に入れ、AG-02 はその会議を読む。題名の後ろの「（10/16）」は会議の日付として扱う。
   これで AG-02 を使う会社の利用者には権限 `meetings.space.readonly` が増え、接続し直しが要る（リリースの区分では大きいほう）。
4. **`on_empty` の「空」に、呼んだツールがすべて「取得できなかった」と返したときを足す**（エンジン全体）。`on_empty: stop` を持つ段は、どれも記録を取ってくる段（メール・予定・Meet・ファイル）で、取れなかったときに次の段へ進むと、中身を推論で作ってしまう。
   特に自動の議事録は、社内のスペースなら承認が自動で通るため、記録の無い議事録が共有されうる。
5. 推論に渡す文字起こしを 3 万字から 12 万字にする（3 時間の会議でもおおむね収まる。録音の文字起こしと同じ上限）。

## 考えた別の案

- **題名を会議のコードのままにする**: 作りは単純だが、自動の議事録の題名と共有先の引き継ぎ（同じ題名の会議で前に共有したスペース）が使えなくなる。
- **Meet の文字起こしのドキュメント（ドライブの主催者のファイル）を読む**: 題名を含むが、`drive` の権限が要り、項目に話した人と時刻が付かない。Meet REST API の項目のほうが構造がある。
- **`on_empty` を変えず、AG-02 の作成の段の指示で止める**: 推論の行儀に頼ることになり、見本の推論では止まらない（2026-10-16 に smoke で確かめた）。

## 結果

- 本物の会社で、Meet の会議が終わると、主催した人の議事録が文字起こしから作られるようになる（本物の Google での確かめは、会社の利用者の接続し直しと Meet REST API の有効化の後）。
- 記録の取れない議事録の依頼は、取得の段で止まる。これまで記録が無いまま承認まで進んでいた smoke の確かめ（第 43 節）は、記録を渡す形に直した。
