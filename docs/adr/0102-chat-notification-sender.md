# ADR-0102: 通知の控えは、会社の Chat アプリがアプリとして本人への個別メッセージに送る

- 状態: 採用（第 0.377.0 版で実装）
- 日付: 2026-10-16
- 関係: 仕様書 第6.5.5.2節・第6.5.5.2.1節・第6.6.3節・第27.15節（第 0.376.0 版）、ADR-0011、ADR-0003、Q-86

## 背景

通知の控えを Chat へ届ける仕組み（第6.5.5.2節）は、届ける見回り・本人の入り切り・通知しない時間帯・送り直しまで実装し、
実際の送信だけを見本の送信口のままにしていた（会社の Chat アプリの登録（B-2）のあと）。
三浦さんが本物の送信口を進めるよう決めた（2026-10-16）。決めることは、どの認証で送るかと、個別メッセージの場所をどう用意するかだった。

Google の説明（2026-10-16 に確かめた）:

- Chat アプリがアプリとして送るには、サービスアカウントで認証する。権限 `chat.bot` は Workspace の管理者の承認が要らない。`chat.app.*` の権限は管理者の 1 回の承認が要る。
- アプリは自分が入っている場所にしか送れない。アプリの権限だけで、本人とアプリの既存の個別メッセージは探せる（`spaces.findDirectMessage`）。
- 本人とアプリの個別メッセージの場所は、**本人の許可**（`chat.spaces.create`）で作れる（`spaces.setup` の `singleUserBotDm`）。アプリの権限では作れない。

## 決定

1. **アプリとして送る**（サービスアカウントの鍵。`chat.bot`）。本人の名前で送ると、本人が自分に送った形になり通知として目に留まらず、本人の許可が切れると届かなくなるため。
2. 鍵は会社が自分の Google Cloud で作り、管理者ページの「接続」で預ける（会社の OAuth クライアントと同じ考え方。運営の鍵で各社の Workspace に送らない）。
3. 個別メッセージの場所は、**本人が「Chat」を入れて保存したとき**に用意する。既存の場所を探し、無ければ本人の許可で作る。その許可は Chat の控えを使う人だけに使うときに求める（連絡先と同じ。ADR-0084）。
   Workspace の管理者の承認（`chat.app.spaces.create`）で、本人の操作なしに場所を作る形は採らない（会社の管理者の手続きが増え、承認の無い会社では使えないため）。
4. 鍵の無い会社では「Chat」を入れられないようにする（届かないのに入っている状態を作らない）。

## 結果

- 会社の準備は、Chat アプリを設定したプロジェクトでサービスアカウントと鍵を作り、管理者ページで登録することだけになる。Workspace の管理者の承認は要らない。
- 本人は個人設定で「Chat」を入れ、初めてなら Google の許可を 1 つ足す。
