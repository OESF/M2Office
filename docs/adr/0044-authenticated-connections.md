# ADR-0044 認証の要る接続は、会社がアプリを登録し利用者ごとに認可する形を基本にし、最初に Slack で確かめる

## 背景

会社の接続（MCP）は、認証の要らないもの（`none`）だけを実装していた。`oauth` と `api_key` は宣言の形だけあり、登録すると「まだ使えません」と断っていた（Q-72 は、サンプルに使うアカウントと認可の画面が未決だった）。

三浦さんの手元には Slack の環境がある。Slack の公式の MCP サーバ（`https://mcp.slack.com/mcp`）は、Streamable HTTP で、**会社が登録したアプリ（クライアント ID とシークレット）による OAuth で、利用者ごとのユーザートークンを発行する**。アプリの自動登録には対応せず、社内向けアプリかディレクトリに公開したアプリだけが使える。

## 決定

1. 認証の型は 3 つ。`none`（認証なし）、`oauth`（会社がアプリを登録し、利用者ごとに認可する。**基本**）、`api_key`（会社の鍵で会社として動く）。
2. `oauth` の管理者の登録は、Google Workspace の接続（第14.3.3節）と同じ流れにする。戻り先の URL を示し、クライアント ID とシークレットを登録する（シークレットは暗号化し、登録後は表示しない）。管理者が自分の認可で接続を確かめ、その認可で道具の一覧を問い合わせる。
3. 利用者は個人設定「サービスとの接続」で、本人のアカウントで許可し、本人が取り消す。**全員に先に接続させず、要る業務を使うときに接続を促す。**
4. 業務は**依頼した本人の認可で呼ぶ**。定時実行は持ち主、段取りの各段と秘書の調べものは頼んだ本人。承認のあとに送る段も依頼した本人の認可で送る。ほかの人の認可で代わりに呼ばない（I-9）。
5. 認可が切れたとき（本人の取り消し、相手の側で外れた、管理者がクライアント ID を替えた）は、Google の許可がなくなったとき（第6.5.2.1節）と同じ考え方で後始末する。
6. `api_key` は会社として動く。本人ごとの権限の区別が無いため、道具の危険度・入り切り・業務の利用範囲で絞る（接続ごとに使える人を絞るかは Q-100）。
7. よく使うサービスの**登録の型**を M2Office が持ち、最初に Slack の型を置く。Slack の投稿などの書く道具は、社外の人がいる Slack コネクトのチャンネルがありうるため、既定を `external-send`（承認が要る）にする。
8. 最初の確認は oesf で、読む道具（検索・チャンネルを読む）から行い、投稿は承認を挟んでテスト用のチャンネルにだけ行う。

## 理由

- 利用者ごとの認可なら、相手のサービスでの本人の権限がそのまま効き、M2Office が本人の権限を超えない（I-9）。会社の鍵 1 つで全員が動く形より安全である。
- Slack は中小企業でも多く使われ、公式の MCP サーバの認証の形が決定 1〜4 とそのまま合う。三浦さんの環境で本物を相手に確かめられる。
- 管理者の登録を Google Workspace の接続と同じ流れにすれば、管理者が覚えることが増えない。
- 登録の型を持てば、中小企業の管理者が相手のサービスの認可の細かい決まり（認可の口・権限の名前）を調べなくて済む。

## 影響

- 会社の接続の認証情報と、利用者ごとの認可を、暗号化して持つ表が要る（第19.1節）。
- ワーカーが道具を呼ぶとき、依頼した本人の認可を引いて付ける。接続していなければ「接続が要ります」で止める。
- 管理者ページの「接続 › コネクタ（MCP）」に認証の設定が、個人設定に「サービスとの接続」が加わる。
- Slack 側で、社内向けアプリの作成と、ワークスペースの管理者の承認が要る場合がある。クライアント シークレットは本物の認証情報のため、登録は管理者本人が行う。
