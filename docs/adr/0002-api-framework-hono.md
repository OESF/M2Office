# ADR-0002 API フレームワークに Hono を採用する

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-21 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第20.1節、第13.1節、ADR-0001 |

## 背景

ADR-0001 で画面を SPA とし、API を独立したサーバーとして実装することを決めた。
その API を構築するフレームワークとして、Fastify と Hono を比較した。

いずれも Node.js で動作し、OpenAPI の生成、長時間接続（SSE）、
TypeScript での開発に対応している。決定的な機能差はない。

## 決定

**Hono を採用する。**

## 比較

| 観点 | Fastify | Hono |
|---|---|---|
| 成熟度 | 長く使われており実績が多い | 比較的新しい |
| エコシステム | プラグインが豊富 | 発展途上。必要なものは揃う |
| 設計の土台 | Node.js 固有の API | Web 標準（Request / Response） |
| TypeScript | 対応するが、型付けに独自の作法がある | 型推論が中心。クライアントへ型を渡せる |
| 動作環境 | Node.js | Node.js のほか Bun、Deno、エッジ環境 |
| 学習コスト | 概念が多い | 概念が少ない |
| 日本語の情報 | 一般的な量 | 多い（作者が日本人、国内の利用例が多い） |

## 理由

### 1. 画面との型の共有が容易

SPA 構成では、API の型を画面側でも使いたい。
Hono は API の定義から型を導出してクライアントへ渡せるため、
`shared` パッケージに型を手書きして二重管理する手間が減る。

仕様書 第20.5節で `web` は `shared`（型のみ）にしか依存しない設計としており、
この型が自動で導出できることの価値は大きい。

### 2. 概念が少なく、学習コストが低い

開発チームは Node.js の経験が浅い（ADR-0001 と同じ前提）。
Hono は Web 標準の `Request` / `Response` をそのまま扱うため、
フレームワーク固有の作法を覚える量が少ない。

### 3. 日本語の情報が多い

作者が日本人であり、国内での利用例と日本語の解説が多い。
詰まったときに調べる時間が短くて済む。

### 4. 動作環境を選ばない

現時点ではさくらインターネット上の Node.js で動かす（仕様書 第20.1節）。
将来、配信の一部をエッジ環境へ移す選択肢が残る。
**これは決定の主な理由ではない**。現時点で必要な要件ではないため、副次的な利点として記録する。

## 却下した案の利点（記録として）

| # | Fastify の利点 |
|---|---|
| 1 | 実績が長く、大規模な運用事例が多い |
| 2 | プラグインが豊富。レート制限、認証、監視などで選択肢が多い |
| 3 | JSON Schema による検証とシリアライズが組み込まれており、OpenAPI と素直に対応する |

**エコシステムの規模は Fastify のほうが大きい。**
必要なプラグインが Hono 側に見つからない場面はありうる。
ただし M2Office の規模（1 テナント 10 名、テナント数 100 程度）では、
その差が問題になる場面は限られると判断した。

## 結果

### 守ること

| # | 内容 |
|---|---|
| 1 | ドメインロジックは `core` に置き、Hono に依存させない（仕様書 第20.5節） |
| 2 | フレームワークの機能に寄りかかった実装をしない。乗り換えの余地を残す |
| 3 | OpenAPI の生成を実装から行う（仕様書 第13.1節 A-5） |

### 想定されるリスク

- 必要なプラグインが不足した場合、自作するか別の手段を探す必要がある。
- 第 1 項を守っていれば、API 層の置き換えは局所的な作業に留まる。
