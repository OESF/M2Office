# ADR-0023 承認の直後の段を承認の前に組み立て、承認されたら記録した操作をそのまま実行する

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-25 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第9.3.3節、第9.4節、第9.2.7節、不変則 I-11 |

## 背景

受け入れテストで、議事録作成を本物の Google（`oesf`）で最後まで流した（2026-09-25）。
承認トレイには「議事録の内容と、抽出した決定事項」「共有先のスペースと、投稿する本文」の 1 行しか出ず、
承認した三浦さんは「何に対して何を承認するのか全く分からなかった」。

加えて、Chat に投稿する本文は、共有の承認の**あとで**推論が書いていた。
承認した人は、実際に投稿される文を一度も見ていない。
「送る前に人が確かめる」という承認ゲートの意味が失われていた。

## 決定

**1. 承認の段に来たら、その直後の段を先に組み立てる。**

読むだけの道具はその場で実行し、書く・送る道具は**記録だけして実行しない**。
記録した操作を、承認の画面に「承認すると行うこと」として業務の言葉で出す。

**2. 承認されたら、記録した操作をそのまま実行する。推論をやり直さない。**

いまの「操作の確認」（社内への書き込みを止めて本人に確かめる仕組み）と同じ作りを、承認の段にも広げる。
記録は承認の段の記録に持たせ、承認のあとの最初の進行で実行する。組み立てた段は済んだものとして進める。

**3. 承認の画面には、確認すること・判断するもの・承認すると行うことの 3 つを出す。**

確認すること（定義の `present`）は 1 行目に置き、一覧やダッシュボードは 1 行目だけを出す。

## 理由

| 観点 | 内容 |
|---|---|
| 承認の意味 | 承認した人が見た中身と、実行される中身が同じであることを、仕組みで保証する |
| 推論のゆらぎ | 承認のあとで推論し直すと、同じ入力でも違う文になりうる。見た文と送られる文が変わる |
| 既存の仕組みの再利用 | 操作の確認で「記録した操作をそのまま実行する」作りがすでにあり、試験も通っている |
| 定義を書き換えない | 公式のカタログも拡張機能も、定義の形を変えずに効く |

## 却下した案

| 案 | 却下した理由 |
|---|---|
| 定義の側で「下書きの段」を承認の前に足す | すべての定義（拡張機能を含む）の書き換えが要り、書き忘れれば元に戻る。基盤で保証するほうが確か |
| 承認の画面に、前の段の出力だけを出す | 送る中身は承認のあとで作られるので、承認の画面に出せない |
| 承認のあとに、もう一度確認を求める | 確認が 2 回になり、2 回目も読まれなくなる |

## 影響

- 承認の直後の段の推論は、承認の**前**に行われる。承認を待つ間に状況が変わっても（新しいメールが届くなど）、承認された時点の記録を実行する。これは意図した動きである（見たものを実行する）
- この変更の前に承認待ちになった実行は、承認のあとに従来どおり推論してから実行する（記録が無いため）
- 承認の画面の本文が長くなる。一覧・ダッシュボード・通知は 1 行目だけを出すので、中身がそこへ漏れることはない
