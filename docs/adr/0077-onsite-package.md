# ADR-0077 ローカルの形を、Mac に入れるパッケージとして配る

| 決定日 | 2026-10-07 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第8.6節・第8.6.1節〜第8.6.9節・第20.4.5節・第23.8.15節、Q-153〜Q-159・Q-206〜Q-210。ADR-0059（ローカルの形と外部の AI に渡さない決まり）・ADR-0063（医療は M2Medical に分ける）・ADR-0028（AI に任せる） |

## 背景

- 導入予定のクリニックが、M2Office と M2Medical を同時に入れ、**データをすべて社内に置き、Mac Studio の 1 台で動かしたい**と希望している（2026-10-07 に三浦さんが報告）。
- ローカルの形の土台（配備の形 `M2O_DEPLOYMENT=onsite`・入っている 1 社の固定・ローカル AI の口・会社の AI の方針）は、第 0.209.0 版で実装した。未決のまま残っているのは、証明書（Q-153）・ログイン（Q-154）・更新と遠隔の保守（Q-155）・控え（Q-156）。
- **本番の組み立てが、クラウドにもまだ無い。** API とワーカーは開発用の実行（`tsx`）で動き、画面は開発サーバー（Vite）が出している。ローカルの形のパッケージより先に、どちらの形でも使う本番の組み立てが要る。
- 三浦さんの希望: ソースは同じものを使う。サブドメインは要らず、社内の IP アドレスで開く 1 つのアドレスにする。社内の LAN でも HTTPS にしたい。

## 調べたこと

- **Google は、OAuth の戻り先に IP アドレスを使わせない**（`localhost` を除く。ホストは公開の接尾辞の一覧にあるドメインであること）。Google のログインと、Gmail などの接続は、**IP アドレスだけのアドレスでは動かない**。
- ブラウザは、**マイク（音声の秘書）とカメラ（在庫・会員証のバーコードの読み取り）を HTTPS か `localhost` でしか使わせない**。社内でも HTTPS は「できれば」ではなく必要。
- 社内の IP アドレスには、公的な証明書は出ない。会社のドメインの名前があれば、**DNS で所有を確かめる方式（DNS-01）**で公的な証明書を取れ、機械が社外から見えなくてよい（Let's Encrypt と Caddy の公式の説明）。
- **Cookie はポートで分かれない。** 同じ名前（IP）でポートだけを変えて M2Office と M2Medical を並べると、ログインの Cookie が混ざる。
- Mac でコンテナを動かすと、Linux の仮想の機械がメモリーを取り、GPU（Metal）を使えない。ローカル AI は GPU と統合メモリーを使うため、どのみち Mac の上で直に動かす。

## 検討した案

### パッケージの形

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. Mac のネイティブのパッケージ** | Node.js・PostgreSQL・入口（Caddy）を同梱した署名つきの `.pkg`。launchd で起動時に動かす | ログインしなくても起動で動く。メモリーをローカル AI に回せる。追加の契約が要らない | Mac 用の組み立てと署名（Apple の開発者の登録）が要る |
| B. コンテナ（Docker Desktop・OrbStack・Colima） | クラウドと同じイメージを Mac で動かす | クラウドと同じ物 | 仮想の機械がメモリーを取り合う。起動に利用者のログインが要るもの・会社の規模で有償になるものがある。ローカル AI は結局 Mac で直に動かす |
| C. ソースを置いて手で動かす | いまの開発の形 | 作る物が少ない | 導入と更新が人の手順になり、間違える |

### アドレスと証明書（Q-153）

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 会社のドメインの名前（例 `office.<会社のドメイン>`）を社内の IP に向け、公的な証明書を DNS-01 で取る** | 名前は社内の DNS か公開の DNS で、機械の固定の IP に向ける | 端末に何も入れなくてよい（スマホも）。Google の戻り先に使える | 会社のドメインが要る。DNS の自動の更新に、DNS の API か `_acme-challenge` の委任が要る |
| B. 機械が自分の認証局を持ち、IP アドレスの証明書を出す | 端末ごとにルートの証明書を入れる | ドメインが要らない | **M2Office の Google の機能が動かない**。端末（とくにスマホ）ごとの手間 |
| C. 暗号化しない | — | 簡単 | マイクとカメラが使えない。勧めない |

## 決定

1. **パッケージは案 A（Mac のネイティブ）**。ソースは 1 つのまま、タグから組み立てる。クラウドは同じ本番の組み立てをコンテナに入れる（第20.4.5節）。
2. **アドレスは案 A（会社のドメインの名前）を標準とする。** IP アドレスだけの形（案 B）は、Google を使わない会社のための代わりとして残す。三浦さんの「IP アドレスで開く」は、名前を社内の IP に向けることで満たす。
3. M2Medical と同じ機械に置くときは、**同じ IP に 2 つの名前**（例 `office.` と `medical.`）を向け、入口（Caddy）を 1 つにする。ポートで分けない（Cookie が混ざるため）。
4. 更新は**取りに行くだけ**（社外から機械へ入る口を開けない）。夜に自動で入れ、失敗したら自動で戻す。会社の管理者が止められる。
5. 遠隔の保守は、**会社の管理者がその都度、時間を限って開ける**外向きのトンネル。運営は自分で開けられない。
6. 控えは、毎晩の控えを RAID と別のディスクに置き、毎月自動で戻せるかを試す。社外の控えは、鍵を社内だけが持つ暗号化を条件に、会社が選んだときだけ。
7. 管理者ページに「機械」を足す（ローカルの形だけ）。版・更新・控え・ディスク・証明書・各部の動き・ローカル AI・遠隔の保守を見る。マスター管理画面の簡易版にあたり、運営への**稼働の知らせ**（数だけ）を送れる（第23.8.15節）。

## 結果

- 良い点: 1 つのソースでクラウドとローカルの両方を出せる。社内の機械でも、更新・控え・保守が人の手順に頼らない。
- 悪い点・残る作業: Apple の開発者の登録（署名と公証）、更新の署名の鍵の管理、M2Medical との共通の部品（入口・更新・控え）の取り決め。M2Medical のファイルは M2Office の側から直さない。

## 改め（2026-10-07、第 0.304.0 版。案）

三浦さんが、**署名つきの `.pkg` は要らない**と決めた。理由は次のとおり。
- サーバーの仕組みで、Google の設定なども要るため、導入には必ず技術者（SIer）が関わる。当面、利用者が自分で入れることは無い
- 画面はすべて Web で、Mac のアプリの形にまとめる必要が無い
- Apple の開発者の登録には、毎年の費用がかかる

代わりに、技術者が公開のリポジトリ（GitHub）からリリースのタグを取ってきて（会社ごとの手直しが要れば fork から）、対話式のセットアップのスクリプトで入れる。前提のソフト（Node.js・PostgreSQL と pgvector・Caddy）は同梱せず Homebrew で入れる。更新は、機械がリリースのタグを見に行き、運営の署名を確かめてから組み立て直す。Mac のネイティブ（launchd）で動かすこと、コンテナを使わないこと、夜に自動で更新することは変えない（仕様書 第8.6.1節・第8.6.4節）。
