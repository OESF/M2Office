# ADR-0148 会社のサイトを MCP でもつなぎ、各社の確認の手順を承認で汎用に扱う

| 項目 | 内容 |

| 決定者 | 三浦 |
| 関連 | 仕様書 第47章・第45.9節・第6.6.2.1節・第6.6.3節・第9.4.0節・第10.9.6節・第12.11.2節。Q-368〜Q-374。ADR-0028（AI に任せる）・ADR-0037（コネクタは会社の接続）・ADR-0140（サイトの更新は REST API で、裏の口を取り替えられる形に） |

## 背景

2026-11-15 に三浦さんが、WordPress でサイトを提供する会社が独自の MCP を出し始めていると示した。導入先のサイトの運営会社からも、その MCP でつなぐよう頼まれた。三浦さんは試しのサイトをその MCP でつなぎ、Claude Code では会話で問題なく使えることを確かめた。そのうえで、各社の MCP で確認の手順が違うのを M2Office がどう汎用に扱うかが命題だと述べた。

試しのサイトの MCP（ツール 124 件）の説明を読むと、書き換えは準備・見直し・確定の 3 段で、AI に向けた「確認」の指示が文で書かれていた。その指示は性質の違う 5 種類に分かれた: 確定への了承・好みを聞く・必ず見せる注意・終わった後の知らせ・確認を飛ばしてよい。WordPress.com の MCP は、書く操作の引数で了承を示す別の形である。

三浦さんは続けて、承認をすべて承認トレイで行うとそのたびに画面を切り替えることになり手順が増えすぎると指摘し、一連の手順を滑らかに進めるよう求めた。あわせて、いまの REST API のつなぎを活かしたまま MCP にも対応し、対象のサイトを選べるようにするよう求めた。

## 決定

1. **会社はサイトを複数持つ。** サイトごとに、REST API か MCP（会社の接続のコネクタ）かを選ぶ。いまの接続は 1 つ目のサイトとしてそのまま使う。サイトを使う機能は「どのサイトに」だけを受け取り、つなぎ方の違いは裏の口が引き受ける。
2. **コネクタのツールに役割を持たせる**（読む・準備・見直し・確定・戻す）。推論が説明と目印から決める。承認が要らない側に決めたものは、管理者が 1 度見るまで確定と同じに扱う。
3. **人に判断を求めるのは、確定と戻すの承認だけにする。** 好みは業務が決めて承認の画面に並べる。相手の注意は相手の言葉のまま出す。終わった後の知らせは結果の報告に入れる。「了承を待たずに確定してよい」には従わない。
4. **承認した引数のまま確定する。** 確定の合図の引数は推論に見せず、承認の後に M2Office が付ける。断られたら、準備からやり直して承認を求め直す。
5. **秘書に頼んだ業務の承認を、会話の中で判断できるようにする。** 本人が判断できる承認だけを、その依頼の答えの下に開いた形で出す。承認はボタンで行い、直しと却下は言葉でもできる。
6. **対象のサイトは、秘書が頼みと話の流れから決める。** 分からなければ 1 度聞き返して覚える。分からないまま既定のサイトに入れない。
7. **サービスごとに専用のコードを書かない。** 会社の接続ごとに、その接続の道具を使う汎用の業務を M2Office が自動で用意し、推論が作った説明で秘書の振り分けの候補に入れる（第 0.586.0 版。Claude Code では MCP の説明を読んで指示なしに動いたのに、M2Office では書くツールを業務の定義が名前で指さなければ使えなかったため）。
8. **会社のサイトを扱う接続は、サイトの更新の付属の業務にする**（第 0.587.0 版）。利用者に見える業務は「サイトの更新」1 つで、MCP のサイトはその中の対象のサイトの 1 つ。三浦さんが、接続の名前の業務が別にできるのは理由が分からないと指摘したため。
9. **コラムの作成とお知らせの作成の入れるサイトは、会社の設定で決める**（第 0.589.0 版）。サイトの更新の画面で選ぶ形はやめた。MCP のサイトには、承認の後にそのサイトの業務へ頼む。お知らせを MCP のサイトに公開するときは、相手の見直しの結果を見せてもう一度承認する（承認は 2 回）。
10. **一連の流れの中の承認は承認トレイに出さない**（第 0.589.0 版）。本人が秘書に頼んで起こした業務で本人が判断する 12 時間の内の承認は、秘書のキャンバスでだけ判断する。承認トレイは、時間的につながっていないもの（ほかの人の依頼・定時実行・時間がたったもの）のためにする。

## 理由

- 各社の確認の手順は、会話をする AI に向けた文である。M2Office の業務は途中で人に聞かずに進み、社外に出る所だけを承認で止める。5 種類を承認・業務の判断・注意・報告・従わないに振り分ければ、どの会社の形にも当てはまる
- ツールの説明は外から来た文である（不変則 I-6）。説明だけを信じて承認を外すと、説明の書き換えで承認なしに公開されうる。そのため、承認を外す向きだけは人が 1 度見る
- 承認トレイへ移らずに判断できれば、頼む・見る・判断する・結果を聞くが 1 つの会話で終わる。承認をボタンに限れば、言葉の取り違えで社外に出ることは無い
- REST API のつなぎ（直す前の本文を持つ・崩さない確かめ・ぶつかりの確かめ）は、自前のサーバーの WordPress では MCP より確かである（ADR-0140）。捨てずに、サイトごとに選べる形にする
- サービスごとにコードを書くと、導入先が増えるたびに作ることになる（個別の案件に特化しない）

## 影響

- 「接続 › WordPress」は「接続 › サイト」に改める。いまの接続は 1 つ目のサイトに移る（管理者がし直すことは無い）
- 一人ひとりの WordPress の利用者（第45.16節）はサイトごとに持つ
- コネクタのツールの一覧に役割が加わり、管理者が 1 度見る手間がある（接続の登録のときだけ）
- MCP のサイトの元に戻すは相手の道具に任せる。崩さない確かめは、相手の見直しの結果を見せることに留まる
- 承認トレイと会話の両方から同じ承認を判断できる。判断の記録は同じ
