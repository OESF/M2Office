# ADR-0106: クラウドの形を Xserver の VPS と Cloudflare で動かす

- 状態: 提案（第 0.427.0 版）
- 日付: 2026-10-23
- 関係: 仕様書 第20.4.6節・第20.4.2節・第8.6.4節・第16.8節、Q-10・Q-38・Q-255〜Q-257、ADR-0077

## 背景

クラウドの形（多数の会社が入る運営のサーバー）の置き場所は、さくらインターネット・エックスサーバー・Google Cloud から選ぶことになっていた（Q-10）。
2026-10-23 に三浦さんが比べ、次のように判断した。

- さくらインターネット・エックスサーバーは、事業者が用意する運用の環境とセキュリティの仕組みが乏しく、整える手間が大きい。
- GCP（Cloud Run と Cloud SQL）は手間が少ないが、月に約 3 万円（冗長化して約 7 万円）かかる。
- 使っていない Xserver の VPS が 1 台ある。運用は提携先の技術者が、手順書が整っていれば 24 時間受け持てる。

そのうえで、**入口に Cloudflare を置き、Xserver の VPS（Ubuntu）で動かす**形の仕様を求めた。

## 決定（案）

1. **機械はインターネットからの受け口を開けない。** 利用者の通信は Cloudflare Tunnel（機械から外向きにつなぐ）、保守は Tailscale（同じく外向き）で通す。DNS に機械の IP を書かない。
2. **Cloudflare に入口の守りを任せる。** DNS・証明書・DDoS の防御・WAF（Pro の管理された規則）・粗い回数の制限・運営の画面の手前の確かめ（Cloudflare Access）。
3. **API は 127.0.0.1 だけで待ち受ける（すべての配備の形）。** いまは待ち受け先を決めておらず、Caddy を通らずに届いてしまう。ローカルの形でも同じ版で直す。
4. **相手のアドレスは `CF-Connecting-IP` から取る。** トンネルを通ると相手が `127.0.0.1` に見え、回数の制限と不正の見張りが働かなくなるため、Caddy が置き換えて API に渡す。
5. **更新は、署名したリリースのタグを機械が取りに行く**（ローカルの形と同じ仕組みを Linux に写す）。リリースのタグへの署名を始める。
6. **控えは、どの時点にも戻せる形にする**（pgBackRest で WAL を絶えず送る。ファイルは restic）。置き場は日本国内のリージョンの S3 互換の置き場で、機械の上で暗号化してから送る。3 か月に 1 回、別の機械に戻して確かめる。
7. **提携先の役割・権限・記録を決め、手順書を運営のマニュアルに置く。** 提携先は障害の対応のほかは会社のデータを見ず、見たら記録して報告する。
8. **Cloudflare の 100 MB の上限に合わせ、大きなファイルは分けて送る**（録音・サイネージの動画）。

## 理由

- 受け口を開けなければ、VPS でいちばん手間のかかる「外からの攻撃への備え」の多くを Cloudflare に任せられる。OS とソフトの手当ては、自動の更新と手順書で提携先が受け持てる量になる。
- 署名つきのタグを取りに行く更新なら、機械に入る鍵を GitHub に預けずに済み、提携先が署名の無いコードを入れることもない。
- 機械が 1 台でも、どの時点にも戻せる控えと戻す練習があれば、壊れたときに数時間で戻せる。

## 採らなかった案

- **GCP（Cloud Run と Cloud SQL）**: 運用の手間は最も少ないが、月の費用がかかる。会社が増え、冗長化が要るときに改めて考える（コンテナの組み立ては第20.4.5節のまま使える）。
- **Cloudflare Workers に作り直す**: 常駐のワーカー・ネイティブの部品・PostgreSQL の RLS がそのまま動かず、作り直しが大きい。
- **443 番を開けて Cloudflare の IP だけを通す**: 受け口が残り、Cloudflare の IP の一覧を保守する手間がある。トンネルのほうが簡単で強い。
- **Cloudflare R2 を社外の控えに使う**: 置き場所を日本に固定できない。

## 残る危険

- 機械が 1 台のため、壊れると戻すまで止まる。
- Cloudflare は TLS をほどくため、通信の中身が Cloudflare の機械を通る（保存はしない）。医療機関への説明を決める（Q-257）。
- 安全は手順書と提携先の運用に頼る。手順書を版で管理する。
