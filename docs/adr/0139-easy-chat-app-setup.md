## 背景

2026-11-12 に、本物の Chat アプリ（ローカルの開発の環境・Cloud Pub/Sub）で、通知と Chat から秘書に頼むことの両方を通した。通すまでに、次の所でつまずいた。

- アプリの権限で人を探すとき、メールアドレスを Google に断られた（M2Office の誤り。第 0.559.1 版で直した）
- 許可を足して接続し直しても、古いトークンを使い回していた（M2Office の誤り。同じ版で直した）
- 「Developer permission settings do not support this action」。Chat アプリの構成を入れ直したら消えた（インタラクティブ機能が切れていたと見ている）
- Pub/Sub の待ちの打ち切りを失敗と扱い、警告を出し続けた（M2Office の誤り。同じ版で直した）
- Chat がトピックに書かなかった。アドオンの形のアプリは、案内した `chat-api-push@system.gserviceaccount.com` ではなく、構成の画面に出るプロジェクトごとのアカウントで書く
- アドオンの形のアプリの出来事を、M2Office が読めずに捨てていた（M2Office の誤り。同じ版で直した）

多くは理由がどこにも出ず、開発者が Google の記録（Cloud Monitoring の指標）を読んで見つけた。三浦さんは「かなり複雑。動いたら、ヘルプなどをしっかりとさせないとエンドユーザーには大変」と述べた。

## 決定（案）

1. **2 段に分ける。** 段 A「Chat に通知を届ける」、段 B「Chat から秘書に頼む」。画面・ヘルプ・点検をこの 2 段で組む。
2. **M2Office がつながりを順に確かめ、最初に止まっている所と直し方を言う。** 鍵 → 構成 → 個別メッセージ → 受け口 → 届くか。届くかは、管理者に Chat アプリへ 1 行書いてもらって確かめる。秘書に聞いても同じ点検をする。
3. **コマンドでできる作業は、会社の値を埋めたコマンドにする。** 管理者が Cloud Shell で動かす。M2Office は会社の Google Cloud を作り変える権限を預からない。
4. **購読の名前を決めておく。** 管理者が入れなくてよい。
5. **クラウド版の HTTP の受け口で、アドオンの形の送り主も受ける。** その会社のプロジェクトのアカウントだけを受ける。
6. **ヘルプを 2 段に分けて書き直す。** いまの画面の名前で書き、図を入れる。読み手は、Google Cloud コンソールと Cloud Shell にある程度慣れた人とする（2026-11-12、三浦さん。エンドユーザーがひとりで行うのは難しい）。手順の記事と、つながらないときの記事に分ける（第 0.561.0 版）

## 理由

- **止まっている所を言う:** 今回のつまずきは、どれも「何が足りないか」が分かれば数分で直せた。分からないことが難しさの正体だった。
- **人に 1 行書いてもらう:** Chat から M2Office への出来事は、人が書かないと生まれない。M2Office だけでは、受け口まで通るかを確かめられない。
- **権限を預からない:** 会社の Google Cloud を作り変える権限を M2Office が持てば、作業は減るが、漏れたときの害が大きい。コマンドを出すだけなら、何をするかを管理者が見てから動かせる。Cloud Shell なら手元に何も入れなくてよい。
- **構成の画面は残る:** Chat アプリの構成はコマンドや API では入れられない。ここだけは画面の作業として、ヘルプで手厚く書く。

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| M2Office が管理者の Google Cloud の許可を預かり、トピック・購読・権限を作る | 預かる権限が大きすぎる。管理者が何をされたか分からない |
| ヘルプを直すだけにする | 画面の名前が変わるたびに古くなる。つまずいた所を言う仕組みが無いと、今回と同じく原因が分からない |
| 手元の機械向けのスクリプトで Google Cloud の作業もする | 手元に gcloud を入れてログインする手間が増える。Cloud Shell で足りる |

## 影響

- 管理者ページの Chat アプリの欄に「確かめる」と、コマンドを出す口が増える
- 点検のために、管理者本人の個別メッセージに確かめの文を 1 通送る
- HTTP の受け口が、署名の送り主を 2 つ受けるようになる
