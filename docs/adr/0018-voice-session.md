# ADR-0018 音声の対話の接続口と、中継の作り

| 項目 | 内容 |
|---|---|
| 状態 | 採用（Q-35 を決定） |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第10.5節、第10.5.4節、第10.5.5節、第11.9.4.1節、第20.2節、ADR-0007、不変則 I-11 |

## 背景

音声（Gemini Live）は Phase 1 後半の機能で、未実装だった。
接続の確認（管理者ページ）だけが実装されており、対話そのものは無かった。

音声は Gemini 固有の機能に依存する（第10.5.4節）。テキスト側の抽象化（第20.2節）を崩さずに、
どこまで切り離すかが決まっていなかった（Q-35）。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 「音声の対話」の接続口を 1 つ定め、**Gemini Live 固有の形はその実装の中だけに置く**（Q-35） | 乗り換えのときに書き直すのが 1 か所で済む。画面と中継は提供者を知らない |
| 2 | 接続口でやり取りするのは**音のかたまり（PCM）と文字**だけ | どの提供者でも表せる最小の形。認識と合成を別々に抽象化すると、双方向で遅延が小さいという Gemini Live の利点が失われる |
| 3 | ブラウザ → M2Office のサーバー → Gemini Live と**中継する**。鍵はブラウザに渡さない | ADR-0007 決定 7 と同じ。会社の鍵でも運営の鍵でも同じ経路にする |
| 4 | **録音は残さない。** 音のかたまりは通したら捨て、サーバーにも画面にも書き出さない | 第10.5.3節。声は生体情報に近く、持つ利益より管理の負担が大きい |
| 5 | 聞こえた文字と応答の文字は、**終わったときに会話ログへ 1 往復として残す** | テキストの秘書と同じ扱いにそろえる（第11.9.4.1節）。本人が切っていれば残さない |
| 6 | 音声からは**業務を起動しない**。秘書の応答だけを返す | 第10.5.1節。承認は音声でも省略しない（不変則 I-11）。実行は画面で確かめてから行う |
| 7 | 鍵が無い環境では**見本の実装**に切り替え、音声を返さずに文字だけを返す | それらしい音声を作らない（第12.9.4節と同じ考え方）。画面と中継は鍵が無くても通しで動かせる |
| 8 | 監査ログには開始と終了だけを残す | 話した中身は会話ログ（本人だけが読める）に置く。ADR-0014 と同じ |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| Gemini Live を画面から直接呼ぶ | 鍵をブラウザに渡すことになる。会社の鍵なら漏えいの影響が大きい |
| 認識（音声→文字）と合成（文字→音声）を別々の接続口にする | 差し替えの幅は広がるが、往復の遅延が増える。秘書の 3 秒以内（第17章）に効く |
| 音声から業務を起動する | 入力項目が多く、フォームのほうが速く正確である（第10.5.1節）。承認の確認も画面で行う |
| 録音を一時的に残して、聞き取りの改善に使う | 第10.5.3節の判断を覆すことになる。改善には文字で足りる |
