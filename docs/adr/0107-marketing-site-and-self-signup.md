# ADR-0107: 紹介のページは Cloudflare の上の EmDash、申し込みと払い出しは M2Office の別のプロセス

- 状態: 提案（第 0.428.0 版）
- 日付: 2026-10-23
- 関係: 仕様書 第23.3.1節・第20.4.6節・第20.4.3節・第23.4節・第23.8.8節・第23.8.15節、Q-29・Q-30・Q-40・Q-258、ADR-0078・ADR-0106

## 背景

2026-10-23 に三浦さんが、サービスを紹介する Web のページを同じ仕組みに置き、そこで申し込み・サブドメインの決定・支払いの設定を行って、サブドメインを払い出す形を求めた。
紹介のページは WordPress（PHP）ではなく、Node.js の CMS の EmDash（Cloudflare が 2026 年 4 月に公開。WordPress に近い管理画面、MCP の口を内蔵）で作る予定である。
これまでの仕様では、申し込みは運営が審査してから払い出す形で、セルフの申し込みは後の段（Phase 4）だった。

## 決定（案）

1. **EmDash は Cloudflare の上に置き、VPS には置かない。** 顧客のデータがある機械から、CMS の管理画面とプラグインという攻撃を受けやすい面を離す。EmDash はもともと Cloudflare の上で動かすことを前提にしている。
2. **紹介のページには紹介の中身だけを置く。** 申し込み・支払い・払い出しは M2Office の側で行う。サブドメインの正はマスター管理画面であり、会社を作る権限を CMS に持たせない。問い合わせは、運営の会社の M2Office の `inquiries.intake` に送り、EmDash に個人の情報を溜めない。
3. **申し込みの口は、顧客向けの API・運営の API と別のプロセス**にし、業務のデータも運営の表も読めない専用のロールで、決めた関数だけを使う。誰でも開けるページから、運営の画面の権限に届かないようにする。
4. **申し込む人は Google でログインして始める**（Google Workspace のアカウントだけ）。メールの確かめを別に作らずに、会社のドメインとメールアドレスを確かめられ、その人が最初の管理者になる。
5. **カードは Stripe の支払いのページで登録し、M2Office はカードの番号を持たない。** 登録が済んだ知らせ（署名を確かめ、Stripe の API で引き直す）で自動で払い出す。請求書払いは運営が確かめてから払い出す。
6. **試用は 14 日**。申し込みのときにカードを登録し、試用の終わりに課金を始める。
7. **停止と返金は自動にしない**（第23.4.4節のまま）。

## 理由

- 申し込みから使い始めるまでを人の手を介さずに済ませられ、運営と提携先の手間が増えない（ADR-0028 の考え方）。
- 公開のページ（CMS）と、会社を作る力と、顧客のデータを、それぞれ別の場所と権限に分けることで、どこか 1 つが破られても被害が広がらない。
- Google でのログインとカードの登録が、なりすましといたずらの申し込みへの十分な備えになる。

## 採らなかった案

- **EmDash を同じ VPS に置く**: 受け口を開けない VPS の守りの設計に、管理画面とプラグインを持つ CMS を持ち込むことになる。Node.js の上では、プラグインを隔てる仕組みが Cloudflare の上と同じに働くかも確かめられていない。
- **EmDash のプラグインで申し込みと支払いを行う**: 会社を作る権限と支払いの記録が CMS に入る。
- **申し込みを運営の API（`ops.`）で受ける**: 誰でも開けるページを、運営の画面と同じプロセスと権限で受けることになる。
- **すべての申し込みを運営が審査する**: カードの登録と Google のログインで足り、払い出しが遅れる。おかしな申し込みは払い出した後でも止められる。

## 残ること

- Stripe の請求書が適格請求書の要件を満たすか（Q-258）。満たせなければ M2Office が作る。
- 請求書払いの入金の確かめ方（Q-40）。
- 人数の数え方（Q-30）。
- EmDash はまだ若い。紹介の中身を書き出せる形で持ち、困れば静的なページに替える。
