# ADR-0087 在庫管理と販売管理のつなぎ

| 項目 | 内容 |
|---|---|
| 状態 | 提案（2026-10-09。三浦さんが、販売管理から商品の一覧を取り、販売の通知を受け取る API を求め、認証・承認・販売の扱い・数の変化の伝え方を推奨のとおりに決めた。仕様書 第 0.321.0 版で案として書いた。実装は合意のあと） |
| 決定日 | 2026-10-09 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第29.12節・第29.13節・第29.20.1節・第29.21.1節（11）・第9.4.0節・第13.4節。ADR-0045（在庫管理）・ADR-0028（AI に任せる） |

## 背景

- 在庫管理は Phase 1 で、品目・入出庫・棚卸し・Web への公開・予約との引き当てを持つ。販売管理・EC とのつなぎは Phase 2（第29.21.1節の 11）として残していた。
- M2Office を在庫の正とする会社では、販売管理（レジ・POS・EC）が、売れる品目と数を M2Office から読み、売れたことを M2Office に伝えたい。
- すでに、予約の受け口（`/v1/hooks/inventory/:key`）とサイネージの呼び出しの受け口（`Authorization: Bearer`）が、ログインの無い外のシステムから鍵で呼ばれる形で動いている。
- 第13.4節の OAuth（アプリの登録とスコープ）は、まだ作っていない。

## 検討した案

| 論点 | 採った案 | 採らなかった案 |
|---|---|---|
| 認証 | **つなぎごとの鍵**（一度だけ見せ、ハッシュだけを持つ。Bearer）。受け口と同じ作りで、すぐ作れる | 第13.4節の OAuth を先に作る（ほかの連携にも使えるが、作る量が大きい） |
| 商品の一覧を渡す承認 | **渡す品目と項目を管理者が一度承認し、その範囲の数の変化は自動で渡す**（Web への公開と同じ） | 公開のまとまりをそのまま使う（画面は増えないが、Web には出さず販売管理にだけ渡す品目を分けにくい） |
| 販売の扱い | **注文で取り置き、販売で使用、取り消しで戻し、返品で入庫**（予約の引き当てと同じ仕組み） | 売れた数だけを減らす（作りは小さいが、注文から出荷までの間、ほかの経路に売れた分が残って見える） |
| 数の変化の伝え方 | **販売管理が読みに来る**（`updatedSince` で変わった品目だけ） | M2Office から知らせる（Webhook。社外への送信の口と再送の扱いが増える） |

## 決定（案）

1. 会社ごとに「販売管理とのつなぎ」を 8 つまで作れる。鍵はつなぎごとで、出し直せる。
2. 口は `GET /v1/hooks/inventory/sales/items`（商品の一覧）と `POST /v1/hooks/inventory/sales/events`（販売の通知）の 2 つ。
3. 一覧は承認した品目と項目だけを渡す。範囲から外れた品目は `active: false` として 1 度渡す。分類の名前で絞れる（`categories`。販売品の一覧を作るため。第 0.323.0 版）。
4. 通知は「つなぎ＋販売番号」で 1 件にまとめ、`eventId` で二重に数えない。品目は ID → 自社のコード → バーコードの順に決まった規則で照らし、照らせない行は残して人が選べるようにする。
5. 足りなくても受け付け、マイナスの在庫として知らせる。金額とお客様の情報は受け取らない。

## 結果

- 良い点: 予約の引き当て・公開の承認・納品書の照らし方という、すでにある仕組みの組み合わせで作れる。社外への送信は「渡す範囲の一度の承認」に閉じる。金額とお客様の情報を持たない。
- 悪い点: 数の変化はすぐには伝わらない（販売管理が読みに来る間隔による）。鍵の管理は会社と販売管理の側に任される。OAuth ができるまでは、スコープで細かく絞れない。
