# ADR-0017 帳票の PDF の書体と、OCR の実現方式

| 項目 | 内容 |
|---|---|
| 状態 | 採用（Q-59・Q-56 を決定。実装はこれから） |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第9.4.1節、第14.3.2節、第20.2節、ADR-0004 |

## 背景

ADR-0004 で、`pdf.render`（帳票の PDF 出力）を見送った。日本語の PDF には書体の埋め込みが要り、
どの書体をどう同梱するかが決まっていなかった（Q-59）。OCR の方式も決まっていなかった（Q-56）。

この 2 つが決まらないと、AG-06 請求書・AG-07 見積書・AG-08 証憑整理に着手できない。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 帳票の書体は **Noto Sans JP**（SIL OFL 1.1）の通常と太字。**TrueType 版**を使う | 再配布と埋め込みの条件が明確で、派生物の名称の制約が無い。Google に一本化した画面と見た目をそろえやすい |
| 2 | 書体は**リポジトリに同梱**する | 配備の手順を増やさない。開発と見本の環境でも、そのまま帳票を出せる |
| 3 | 埋め込みは**使った文字だけを抜き出す**（サブセット） | 日本語の書体は 1 つ数 MB ある。全部入れると帳票 1 通が重くなる。実測で請求書 1 通が 13〜20 KB になった |
| 3-b | OTF（CFF）ではなく **TrueType** を同梱する | OTF を抜き出すと pdf.js が字の形の警告を出した。TrueType では警告が出ず、抜き出した後も小さい |
| 4 | OCR は **Gemini に画像を渡して読み取る**（Q-56） | すでに使う推論で足りる。Cloud Vision は API の有効化・課金・鍵の管理が増え、Drive の変換は利用者のドライブに一時ファイルを作る |
| 5 | OCR も**接続口の後ろに置く** | 座標が要る用途（帳票の位置あわせなど）が出たら、Cloud Vision などへ差し替えられるようにする（第20.2節と同じ考え方） |
| 6 | 読み取った文は「読み取り結果」として示し、**確かなものとして扱わない** | OCR は推論である。第9.2節の「取得できなかった値を推測で埋めない」と同じ扱いにする |
| 7 | 鍵が無い環境では OCR を行わず、**取り出せなかったと明示する** | いまの `pdf.extract`（画像だけのページ）と同じ扱いにそろえる |
| 8 | まず**画像のファイル**（PNG・JPEG）を読み取る。**PDF の画像だけのページ**は次の段階 | ページを画像にする処理（描画の部品）が要る。先に画像の読み取りを通し、必要になってから足す |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| IPAex（明朝・ゴシック） | 国内の帳票で実績はあるが、IPA フォントライセンスの表示義務と派生物の名称の制約があり、同梱と配布の説明が増える |
| 2 つの書体を同梱して会社ごとに選ばせる | 同梱する量と、確かめる組み合わせが増える。要望が出てから足す |
| 書体を配備のときに取得する | 配備の手順と、取得先が落ちているときの扱いを決める必要がある。数 MB のために増やす手間に見合わない |
| Cloud Vision API | 精度と座標では最も良いが、契約・鍵・課金の設定が増える。差し替えられる形にしておき、必要になってから |
| Google ドライブの変換 | 新しい API は要らないが、利用者のドライブに一時ファイルができる。B-2 の完了も待つ |
| 端末内の Tesseract | 外へ画像を出さない利点はあるが、日本語の精度が実務に足りず、処理も重い |
