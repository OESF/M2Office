# ADR-0013 ダッシュボードの人の状態と、SSE による更新の方式

| 項目 | 内容 |
|---|---|
| 状態 | 採用（Q-64・Q-65 を決定） |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第6.7.4節、第6.7.4.1節、第6.7.9節、第6.7.10節、第8.4節、第23.8.6節 |

## 背景

ダッシュボードの Phase 1 後半（人の状態、SSE による自動更新）が未実装だった。
画面は 5 秒ごとの取り直しで更新しており、承認の滞留に気づくまでに間があった。

人の状態は、使い方を誤れば従業員の監視になる。表示の粒度（Q-64）と、従業員への告知の程度（Q-65）も決まっていなかった。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 人の状態は**既存の記録から組み立てる**（ログイン状態・実行とステップ・承認・監査ログ）。状態のための表を作らない | 個人の状態の履歴を残さないという規定（第6.7.10節）と、実装が一致する。残らないものは漏れない |
| 2 | 表示の粒度は会社ごとに選べる形とし、**既定は個人名**（Q-64） | この画面の最大の役割は、承認の滞留が誰の判断待ちかを示すことである。人数だけでは、止まっている業務を動かせない |
| 3 | 従業員への**告知にとどめ、同意の取得は求めない**（Q-65） | 中身を見せず、履歴も残さず、本人が自分の見え方を個人設定で確かめられる。同意を求めると、同意しない人の扱い（表示しないのか、使えないのか）を決める必要があり、運用が重くなる |
| 4 | 更新は **SSE**（`text/event-stream`）とし、API が 2 秒ごとに状態を組み立てて**変わったときだけ**送る | 変化を配る仕組み（イベントの配信基盤）を持たずに、数秒以内の反映という目標を満たせる。1 テナント 10 名程度の規模では、組み立て直しの負荷が小さい |
| 5 | 画面は `EventSource` ではなく **`fetch` の読み取り**で受ける | `EventSource` は認証のヘッダーを付けられない。ログイン状態の Cookie でも開発用ヘッダーでも同じ経路で受けられるようにする。トークンを URL に置く案は採らない |
| 6 | SSE が使えないときは、**一定間隔の取り直し（5 秒）に戻す** | 経路の途中に串がある環境でも、画面が止まらない |
| 7 | 「活動中」は、**ツールを呼ぶ直前にそのステップへ活動の表示名を書き、呼び終えたら消す** | 実行中のステップの中身は、終わるまで記録に現れない。表示名はツールの定義（`activityLabel`）にすでにある |
| 8 | 本人は個人設定で、**いまの自分の見え方**を確かめられる（第6.7.10節 規定 4） | 「見られているかもしれない」という不安に、実物で答える |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| 状態を表に持ち、変化のたびに書き込む | 個人の状態の履歴が残る。第6.7.10節の規定と食い違う |
| 変化の配信基盤（Redis の購読など）を入れる | 1 テナント 10 名の規模に対して重い。さくらインターネットで使う部品も増える（Q-38） |
| WebSocket | 双方向は要らない。SSE のほうが串と再接続の扱いが単純である |
| `EventSource` を使い、トークンを URL に載せる | 秘密の値が URL に残る（記録・履歴・参照元）。決定 5 の理由 |
| 活動の表示名を、ツールの呼び出しごとに監査ログから拾う | 監査ログは呼び終えてから書かれるため、「いま呼んでいる」を示せない |
| 既定を「人数と業務だけ」にする | 承認待ちが誰で止まっているかを見るのに、別の区画を突き合わせることになる。既定で役に立たない画面になる |
