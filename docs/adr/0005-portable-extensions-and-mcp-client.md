# ADR-0005 持ち運べる拡張機能の保存と、MCP サーバへの接続の方式

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-22 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第12.10節、第12.11節、第20.5節、不変則 I-2・I-6・I-7 |

## 背景

仕様書 第12.10節で、拡張機能を 1 つのファイル（`.m2ext`）として持ち運び、管理者ページで取り込み、
スイッチで有効にすることを定めた。第12.11節で、拡張機能が宣言したコネクタ（MCP サーバ）に接続することを定めた。
実装にあたり、次の 3 点を決める必要があった。

1. 取り込んだファイルをどこに置き、API とワーカーでどう共有するか
2. `.m2ext` の形式を扱うライブラリ
3. MCP サーバへの接続に、公式の SDK を使うか

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 取り込んだ拡張機能は、**展開した中身（パス → Base64）をデータベースに保存する**（`tenant_extension_packages`、RLS）。API とワーカーは要求・実行のたびに読み、**毎回検証し直す** | 再起動なしで両方のプロセスに届く。テナント境界を RLS で守れる。検証の規則が厳しくなったとき、古い取り込みを使わずに済む。大きさは 5 MB までで、読み直しの負荷は小さい |
| 2 | ZIP の扱いに **JSZip**（3.10、MIT/GPLv3 の二重ライセンスから MIT を選ぶ）を使う。展開は記憶の上だけで行い、ディスクに書かない | すでに依存関係（docx・exceljs）に含まれ、実績がある。ディスクに書かないため、パスの細工による上書きが起きない |
| 3 | MCP サーバへの接続は、**ツールの一覧と呼び出しだけを行う最小のクライアントを自作する**（`HttpMcpClient`、約 150 行） | 使うのは `initialize`・`tools/list`・`tools/call` の 3 つだけである。公式の SDK は多くの機能（サーバ・stdio・OAuth など）と依存を持ち込む。stdio を使えないこと（不変則 I-7）を、コードに無いことで担保できる |
| 4 | 業務エージェントが使えるコネクタは、**同じ拡張機能の中のものに限る** | 拡張機能どうしの依存関係（導入の順序・版・片方だけ無効にした場合）を決めていないため |
| 5 | コネクタの ID は、内蔵のツールの名前の頭の部分（`gmail` など）とも重ならないようにする | `gmail.send` のような名前の偽装で、内蔵のツールと取り違えさせないため |

## 検討した点

| 項目 | 内容 |
|---|---|
| ファイルをディスク（オブジェクトストレージ）に置く案 | 配備の構成が増え、API とワーカーの間で置き場所を揃える必要がある。いまの規模ではデータベースで足りる |
| 取り込み時に一度だけ検証する案 | 基盤の検証規則を強めたとき、古い取り込みが素通りする。毎回の検証の負荷は小さい |
| 公式の SDK（`@modelcontextprotocol/sdk`） | 認証（OAuth）を実装する段階（Q-72）で、クライアントの機能が足りなくなれば採用を見直す |

## 影響

- 取り込んだ拡張機能の数が増え、読み直しが負荷になったら、版ごとの記憶上のキャッシュを足す
- MCP の仕様の改訂（プロトコルの版）への追随は自前で行う。いまは `2025-06-18` で接続する
