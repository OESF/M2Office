# ADR-0010 議事録の組織知識への登録（承認②に含め、承認した成果物だけを登録する）

| 項目 | 内容 |
|---|---|
| 状態 | 採用（Q-85 で決定） |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第9.5.2節、第9.4節、第11.4節、第14.3.2節、第19.3節、不変則 I-6 |

## 背景

AG-02 議事録作成・共有の手順 7「組織知識として登録」は、仕様書にあるものの実装されていなかった。
Phase 1 の完了条件 3（議事録が自動生成され、組織知識として検索できる）が満たせない原因になっていた。

登録を足すにあたって、次の 3 つが決まっていなかった。

1. どの承認で登録を認めるか
2. 知識に入れる本文を、誰が（何が）決めるか
3. Meet の文字起こしのように Google から読んだデータで作った議事録を、登録したあとどう扱うか（第14.3.2節の 7 日の保持期間との関係）

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 登録は**承認②（共有範囲と本文）に含め**、承認の回数は 2 回のままとする。Chat への共有と登録は、承認②の直後の手順でまとめて行う | 組織知識への登録は、全従業員の秘書と業務から引けるようにすること、すなわち社内全体への共有である。共有の範囲を判断する承認②の役目にあたる。承認者（管理者・承認者の役割）が判断するのが妥当 |
| 2 | 新しいツール `knowledge.register`（危険度 `write-internal`）は**成果物の ID だけ**を受け取り、成果物の本文をそのまま登録する | 本文を引数で受け取ると、記録に紛れ込んだ指示（不変則 I-6）で、承認した人が見ていない文を知識に入れられてしまう |
| 3 | 登録できるのは、同じ実行が作り、**最初の承認ステップで止めた時点にあった**成果物に限る。承認で止めるときに、その時点の成果物の ID を承認ステップの記録に残す（時刻の前後では比べない。同じ時刻に起きうるため） | 承認①の後の手順で推論が作り直した成果物は、内容を承認した人が見ていない。承認②より前に作られていても、承認②は共有の範囲を判断するもので、内容を確かめ直すものではない |
| 4 | **定義の承認ステップをすべて通ったあと**でなければ登録しない | 承認①の直後の手順（ToDo の起票）でも `write-internal` は呼べる。そこで登録されると、承認②を却下しても知識に残ってしまう |
| 5 | 知識の ID を実行から決め、1 回の実行につき 1 件とする | ワーカーが落ちて手順をやり直しても、同じ知識を上書きするだけで増えない |
| 6 | Google から読んだデータで作った議事録も、登録したあとは**会社の知識**として扱う。7 日の保持期間と連携の解除では消さない。管理者が消せ、解約のときに消す | 2 回の承認を経た会社の記録であり、規程と同じく会社の資産である。消えるなら「あの件どうなった」に答えるという AG-02 の目的が成り立たない |
| 7 | 知識に**登録した実行**と、**Google から読んだデータで作ったか**を記録し、管理者ページに示す | 会社の求めに応じて Google 由来のものを探して消せるようにする（第14.3.2節 規定 6） |

「Google から読んだデータで作ったか」は、その実行で Google の権限を持つ**読み取り**（危険度 `read`）のツールを呼んだかで決める。
ToDo の起票や Chat への投稿は Google への書き込みであり、議事録の中身の出どころではないため数えない。

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| 登録を独立した手順にする | 承認の直後ではないため、既定では依頼した本人に 3 回目の確認（操作の確認）を求めることになる。全社への共有を依頼者だけが判断する形にもなる |
| 登録を承認①に含める | 共有（承認②）を却下しても知識に入ってしまう。共有の範囲の判断と食い違う |
| 本文を引数で受け取り、推論に整えさせる | 決定 2 の理由。整えたければ、承認①の前の手順で成果物を整える |
| 連携の解除で、その人の実行から登録した議事録も消す | 会社の記録が、個人の操作で消えることになる。会社の求めには管理者の削除で応えられる |
| エンジンに「登録」の手順の種類を足す | 手順の種類を増やすと、定義のスキーマ（第9.2節）と検証に波及する。ツールで足りる |
