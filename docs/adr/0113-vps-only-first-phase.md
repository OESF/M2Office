# ADR-0113: クラウドの形の第 1 弾は VPS だけで守る（Caddy・CrowdSec・WireGuard）

- 状態: 採用（第 0.471.0 版で提案、第 0.472.0 版で採用。M2Office の側の実装はまだ）
- 日付: 2026-10-26
- 関係: 仕様書 第20.4.6節・第20.4.2節・第20.1節・第23.3.1節、Q-10・Q-38・Q-256・Q-257・Q-279、ADR-0106（一部を置き換える）・ADR-0107

## 背景

ADR-0106（第 0.427.0 版）では、クラウドの形を Xserver の VPS に置き、入口に Cloudflare（Tunnel・WAF・Access）、保守の入り口に Tailscale を置く案にした。機械はインターネットからの受け口を 1 つも開けない形である。

2026-10-26 に VPS（4 vCPU・4 GB・150 GB）の用意を進める中で、三浦さんが次のことを示した。

- この形では、VPS・Cloudflare・Tailscale の 3 つの契約（商用の提供の開始後はどれもカードの支払い）が要る。いずれ運営の会社に引き継ぐときに、契約をそれぞれ移すのは手間である。
- Tailscale の無料のプランは商用で使えない。Cloudflare の WAF も有料のプラン（Pro）が要る。
- 多くの VPS の利用者は、Cloudflare も Tailscale も使わずに、VPS の上だけで守りを固めている。
- ドメインも Xserver で取る予定で、VPS・ドメイン・DNS を 1 つの契約でまとめて移せる。
- 事業が大きくなり機械 1 台で足りなくなったら、機械を上げるか負荷を分ける形に、構造ごと改める必要がある。

## 決定（案）

1. **第 1 弾は VPS だけで守る。** 開ける口は TCP 80・443 と WireGuard の UDP の 1 つだけ。
2. **入口は Caddy。** 証明書は Let's Encrypt から自動で取る。会社のサブドメインは、初めて開かれたときに、払い出したものだけ取る（On-Demand TLS。API の内部の口に尋ねる）。
3. **攻撃の防御は VPS の上で行う。** WAF は Caddy に入れる Coraza と OWASP の規則（はじめは記録だけ）。攻撃する相手は CrowdSec が止める。回数の制限は Caddy とアプリの二重。
4. **保守の入り口は VPS に立てた WireGuard。** SSH は WireGuard の網の中でだけ待ち受ける。鍵は人ごと。運営の画面（`ops`）も WireGuard の網からだけ開ける（Cloudflare Access の代わり）。
5. **ドメインと DNS も Xserver。** 引き継ぐ契約は Xserver（VPS・ドメイン・DNS）にまとまる。
6. **Cloudflare は、大量の通信の攻撃（DDoS）を受けたときに、あとから前に置ける作りにしておく。** Caddy の設定の切り替えと手順書を用意し、その日のうちに前に置けるようにする。
7. ADR-0106 のうち、API を 127.0.0.1 だけで待ち受けること（3）・署名したタグを取りに行く更新（5）・どの時点にも戻せる控え（6）・提携先の役割と手順書（7）はそのまま使う。入口の Cloudflare（1・2）・`CF-Connecting-IP`（4）・100 MB の上限への合わせ（8）は、Cloudflare を前に置くときまで使わない。

## 理由

- 契約と支払いが Xserver の 1 つにまとまり、引き継ぎが簡単になる。
- 通信の中身を第三者（Cloudflare）が見ない。医療機関を含む会社に、データの通り道を説明しやすい（Q-257 が第 1 弾では要らない）。
- 送れる大きさの上限（100 MB）が無く、利用者のアドレスもそのまま見えるので、作り直し（Q-256）が要らない。
- Caddy・CrowdSec・WireGuard は無料で、広く使われ、手順書に落としやすい。
- いちばん VPS で守りにくい大量の通信の攻撃は、受けたときに Cloudflare を前に置く道を用意して補う。

## 採らなかった案

- **ADR-0106 のまま（Cloudflare と Tailscale）**: 守りはいちばん厚いが、契約が 3 つになり、商用の提供の開始後は月 50 ドル前後かかる。
- **Cloudflare の無料のプランと自前の WireGuard**: DDoS の守りは得られるが、Cloudflare の契約（アカウント）が残り、通信の中身が Cloudflare を通る。攻撃を受けたときに切り替える形で足りると判断した。
- **SSH を 22 番で開け、鍵と CrowdSec だけで守る**: 保守の人の接続元の IP が決まらず、SSH の口が見える。WireGuard なら口があることも分からない。

## 残る危険

- 大量の通信の攻撃を受けると、Cloudflare を前に置くまで止まる。
- 口が開いているので、Caddy・Node.js・M2Office の弱点が直接狙われる。自動の更新・WAF・CrowdSec・待ち受け先の直しで守る。
- WireGuard の鍵の足し・外しを手で行う。人が増えたら管理の仕組み（Tailscale など）に移すことを考える。
- 機械が 1 台であること（ADR-0106 と同じ）。
