# ADR-0008 組織知識の検索（節への分割、点数による並べ替え、ベクトル検索は後から）

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-22 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第11.7節、第6.6.6節、第16.3.5節、第19章、第20.2.2節 |

## 背景

組織知識は、文書 1 件を 1 行として保存し、質問の言葉が 1 つでも含まれる文書を新しい順に 5 件返して、
本文をまるごと推論に渡していた（仮の実装）。
就業規則のような長い文書を 1 件で登録すると、何を聞いても全文が渡り、出典も「就業規則」までしか示せない。
並べ方も関係の深さによらない。

一般に言われる RAG（文書を細かく切り、ベクトルにして意味の近さで引く）をすぐ入れる案もあった。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | 保存時に、本文を**章・条・見出しで節に分けて**保存する。分け方は機械的に決め、LLM を使わない | 規程は構造が明確で、条の単位で引くのが最も正確で説明しやすい。同じ文書が毎回同じに分かれ、管理者が結果を確かめられる |
| 2 | 検索は、質問から取り出した言葉の**部分一致と点数**で並べる（見出しの一致を重く、満たした語の割合を加点） | 規程の質問は「有給」「育児休業」のように本文の言葉をそのまま使うことが多い。点数の理由を説明できる |
| 3 | 絞り込みは `ILIKE` で書き、拡張機能がなくても同じ結果にする。pg_bigm の索引は速さのためだけに足す | 本番のデータベース（さくらインターネット。Q-38）で使える拡張機能がまだ分からない。中小企業の量なら索引なしで足りる |
| 4 | 推論には上位の節だけ（最大 5 節、合計 8,000 字）を、`文書名 › 見出しの経路` の出典とともに渡す | 費用と正確さ。出典の明示（第11.7節の要件）を条の単位で満たす |
| 5 | ベクトル検索は Phase 2 で、**同じ PostgreSQL に pgvector を足して**併用する。節の単位は変えない | 別のベクトルデータベースを置くと、テナント境界（RLS）を二重に守る必要が出る。言い換えへの対応は、まず全文検索で確実に引ける状態を作ってから |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| いまベクトル検索（RAG）を入れる | 規程の質問は本文の言葉で引けることが多く、効果に比べて仕組みが重い。埋め込みの提供者の乗り換えに索引の作り直しが伴う（第20.2.2節）。条の単位で出典を示すには、どのみち分割が要る |
| PostgreSQL の標準の全文検索（`tsvector`） | 日本語の単語の区切りを持たず、日本語では使えない |
| PGroonga | 日本語の全文検索には強いが、クラウドの管理されたデータベースで使えないことが多い |
| pg_trgm | 3 文字の組で索引を作るため、日本語で多い 2 文字の言葉（「休暇」「育休」）に索引が効かない |
| 決まった文字数で機械的に切る（一般的な RAG の分割） | 条の途中で切れ、出典を条で示せない。規程では見出しで切るほうが正確 |

## 影響

- 知識を保存するたびに、その文書の節をすべて作り直す。1 件 50 万字までとする
- 既存の知識は、移行のときに一度だけ分け直す
- 検索の結果（`knowledge.search` の戻り値）に、節の見出しの経路が加わる
