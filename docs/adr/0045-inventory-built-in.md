## 背景

最初のお客様は、数十から百ほどの品目を表計算のファイルで管理している。1 つを数回分に分けて使う品目があり、ロットと使用期限がある。
お手本にしている同業のページは、在庫の数と価格の表を埋め込みのページとして自社の Web サイトに貼り、予約と納品のたびに数が変わる。
お客様は Web サイトの制作と管理を制作会社に任せ、予約はクラウドの予約サービス、仕入れはいま問屋へ電話で行っている。

三浦さんの方針: **このお客様の専用のシステムは作らない。** 汎用の在庫管理を用意し、設定だけでいろいろな業種に使えるようにする。
AI が常に在庫を見張って欠品を防ぎ、在庫が変わったら Web にデータを渡す。

在庫管理には表と画面が要り、拡張機能（第12.10.1節）では作れない（不変則 I-7）。

## 決定

1. 在庫管理は名刺管理（ADR-0042）と同じく**内蔵の拡張**として作る。**既定は切り**にし、使う会社が入れる。
2. **汎用にする。** 業種の違いは、会社ごとの機能の入り切り（ロットと使用期限・単位の換算・公開・予約との引き当て・発注の案）と品目の項目で吸収する。お客様ごとの作り分けはしない。品目を取り込んだとき、入れたほうがよい機能を秘書が提案する。
3. 在庫の数は**入出庫の記録の合計**で決め、記録は追記のみにする。在庫はいちばん小さい使う単位で持つ。
4. **Web への公開**は、M2Office が会社ごとの埋め込みのページと JSON を出し、Web サイトに一度貼る形にする。WordPress の管理の鍵を預からない。
5. 公開は社外に出るものなので、**何を公開するか（品目・項目・数か状態か）を管理者が一度承認し、その範囲の数の変化は承認なしに自動で流す**。範囲を変えたら承認し直す（Q-114。2026-10-01 に三浦さんがこの形で決めた）。
6. **AI の見張り**: 入出庫・引き当てのたびと毎朝、残りわずか・無くなる見込み・使用期限を見て知らせ、発注の案を作る。発注のメールは下書きまでで、送るのは承認のあと。
7. Phase 1 は**数だけ**を扱い、入出庫・引き当て・棚卸しの確定はお金の確定に当たらないため承認を挟まない。公開の表の販売価格は在庫の評価とは別の値として扱う。在庫の金額は Phase 2 で、確定を承認の対象にする。
8. バーコードはブラウザで読む（アプリを入れない）。医薬品の GS1 から使用期限とロットを取り出す。iPhone のために読み取りの部品を画面に同梱する（利用者のブラウザで動く部品であり I-7 に当たらない）。
9. **患者の情報を持たない。** 使用の記録と引き当てには日時・数・ロット・予約の番号だけを持つ。
10. 棚卸しで数えていない品目は 0 にしない。期限切れのロットは自動で消さない。
11. **導入先の値を決まりにしない**（第 0.156.0 版で追加。三浦さんの方針「個別のディールに特化した設計にしない。導入時にユーザー側が設定する」）。残りわずかの目安・仕入先と発注の方法・公開の形・予約のサービスとのつなぎ・棚卸しの頻度・在庫の正は、導入のときに会社が設定する（第29.4.1節）。想定は品目 数十〜数千・使う人 100 人まで。

## 理由

- 表と画面が要り、名刺管理で作った内蔵の拡張の仕組み（入り切り・利用範囲・業務の並び）をそのまま使える。
- 入り切りで吸収すれば、クリニック・物販・製造を同じ作りで扱え、お客様ごとの保守を抱えない。
- 埋め込みのページと JSON なら、制作会社は一度貼るだけで、M2Office は Web サイトの鍵を預からずに済む。お手本のページと同じ形なので、制作会社にとっても慣れた形である。
- 公開のたびに承認させると「すぐ反映」ができない。出す範囲を一度承認する形なら、社外に出るものの境界（第9.4.0節）を保ったまま自動で流せる。

## 影響

- 表（品目・バーコード・場所・ロット・入出庫の記録・いまの数・引き当て・棚卸し・棚卸しの行・公開）と、在庫管理の画面、道具 6 つ、付属の業務 2 つ（納品書から入庫・発注の下書き）、公開のページと JSON を作る。
- 画面にバーコードの読み取りの部品が加わる（ライセンスの表示）。
- 未決: バーコードの有無（Q-105）、予約システムの口（Q-113）、発注の方法（Q-115）、在庫の金額（Q-108）、端末（Q-110）、需要の予測（Q-116）。
- 決定（2026-10-02、三浦さん）: JAN の台帳は使わず Gemini の Google 検索で引く（Q-111）、料金は無償で同梱する（Q-112）、電波の無い所での棚卸しは対応しない（Q-109）。
