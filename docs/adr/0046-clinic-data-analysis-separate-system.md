## 背景

お客様は皮膚科のクリニックで、保険診療と自費診療（にきび跡・しみ取りなど）を行っている。これまで患者の傾向を分析していない。
次のような分析をマーケティングに使いたいという依頼である。

- 尋常性ざ瘡（にきび）の患者から、にきび跡の治療や重症のにきびの内服（自費）につなげる
- 子どもが受診している世帯の親を、しみ・ほくろ取りの潜在層として数える。院内のサイネージで知らせる価値があるかを見る
- 60 代女性の患者の数（母数）をつかむ
- どの病気でどの治療を受け、どれだけ続けているか（継続率）から、広告の的を決める
- 急性の病気が多いのか、かかりつけが多いのかで戦略を変える

データは、毎月の請求でレセコンが出す **UKE ファイル**（`RECEIPTC.UKE`。記録条件仕様（医科用）令和 8 年 8 月版）である。
病名・診療行為・薬・算定日・氏名・生年月日・性別・保険の記号と番号を含み、**要配慮個人情報（病歴）**にあたる。
お客様は、**データベースも LLM も院内のサーバー（Mac Studio）で動かす**と決めている。

三浦さんの懸念: **M2Office が 1 つのクリニックのための専用のシステムになってはならない。**

## 検討した案

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| A. M2Office に内蔵の拡張として組み込む | 在庫管理と同じく、M2Office の中に表と画面を作る | 画面・秘書・承認をそのまま使える | **患者のデータがクラウドの M2Office と Gemini に入る**（お客様の条件に反する）。M2Office 全体が医療情報の安全管理の規制の対象になる。医科の診療所にしか要らない機能で、共通の業務ではない（第12.13節に合わない） |
| B. M2Office をオンプレミスにしてクリニックに置く | M2Office ごと Mac Studio で動かす | データが外に出ない | Google Workspace と Gemini を前提にした作りを崩す。Phase 3 の課題を、1 つのお客様のために前倒しする。保守が 2 系統になる |
| **C. 別のシステムにし、集計だけを M2Office につなぐ** | Mac Studio で動く分析のシステムを別に作る。M2Office とは、**集計だけを返す読むだけの MCP の道具**でつなぐ | 患者のデータが院外に出ない。M2Office は汎用のまま。**「顧客の手元のシステムを接続（L2）でつなぐ」という汎用の仕組みの最初の例になる**。分析のシステムは UKE（全国共通の形式）を読むので、ほかの医科の診療所にも売れる | システムが 2 つになる。クラウドから院内へ届く道（トンネルなど）が要る |
| D. 別のシステムにし、つながない | C から接続を除いたもの | いちばん簡単で安全 | 秘書から聞けない。M2Office との相乗効果が無い |

## 決定

1. **案 C をとる。** 診療データの分析は、M2Office の外の別のシステム（仮称「クリニック診療データ分析」）として作る。
   M2Office の仕様書には、このシステムの中身を書かない。書くのは、手元のシステムを接続でつなぐ**汎用の決まり**（第12.11.7節）だけにする。
2. **進め方は D から C へ。** まず分析のシステムを単独で動かし（院内の LAN の画面とローカルの LLM）、分析の価値を確かめてから M2Office とつなぐ。
3. **M2Office は患者の個人のデータを受け取らない。** つなぐとき、分析のシステムが M2Office に返すのは**集計だけ**にする。
   - 名前・番号・自由記述は返さない。
   - **少ない数は伏せる**（NDB オープンデータにならい、10 未満を「10 未満」とする。値は Q-119 で決める）。
   - 道具は決めた集計に限り、任意の問い合わせ（SQL）を外から受けない（差を取って個人を割り出されないように）。
4. **個人を特定する分析と、個人に宛てた案内は、院内の分析のシステムの中だけで行う。** 患者の一覧を M2Office へ渡さない。
   個人への案内に使うかどうかは、利用目的の掲示と同意の要否を専門家に確かめて決める（Q-121）。
5. **M2Office とのつなぎは 2 つの口で行う。**
   - **接続（L2、MCP）**: 分析のシステムが、集計を返す読むだけの道具を持つ。会社の接続として登録し、秘書の調べもの（第10.11.4節）からそのまま使える。
   - **スキル（L1、拡張機能）**: 分析のシステムの提供者が、道具を使う業務（月ごとの患者の動きのまとめ、サイネージの企画の下書きなど）を SKILL.md で書き、接続の宣言（`connectors/*.json`）と一緒に 1 つの拡張機能にして配る（第12.11.0節）。管理者は画面から入れるだけでよい。
6. 分析のシステムは M2 ホールディングスが作るが、**位置付けは業種特化のパートナーの製品**（第13.7.2節）とする。
   M2Office の運営が、パートナーと同じ口（L2 の接続）だけを使って業種の製品をつなぐ最初の例にする。

## 理由

- お客様の条件（データと LLM は院内）を満たせるのは、B か C か D だけである。B は M2Office の前提（Google・Gemini・クラウド）を崩す。
- M2Office の方針は「業種特化は第三者が作る」「運営は共通の業務だけを作る」である。案 A は、この方針に反して M2Office を医科の診療所の専用の機能に寄せる。
- 案 C なら、M2Office に足すのは「手元のシステムを安全につなぐ」という**どの業種にも使える仕組み**だけになる。
  製造業の生産管理や、会計事務所の手元のデータにも同じ形が使える。Q-102（手元のツールへつなぐ）の答えにもなる。
- 集計だけなら、個人の健康情報を M2Office と Gemini に送らずに済む。Q-47 を、個人の健康情報を送らない形で閉じられる。
- 分析のシステムは、全国共通の UKE を入力にするため、ほかの医科の診療所にもそのまま使える。
  既存のサービスがクラウドに UKE を上げる形であるのに対し、**院内で完結し、AI に聞ける、自費の記録と結び付ける**点で違いを出せる。

## 影響

- M2Office の仕様書: 第12.11.7節（手元のシステムにつなぐ。案）を足す。第16.3.7節の健康情報の行と、第2.5節の業種特化の行を直す。未決事項 Q-117〜Q-122 を足す。
- 在庫管理の章（第29.1.1節）のお客様の記述を「保険診療と自費の皮膚科」に直す（これまで「自由診療」と誤って書いていた）。
- 分析のシステムの仕様は、M2Office とは別の文書として書く（仮の置き場: `~/project/clinic-insight/specification.md`）。
- M2Office のコードは、この決定では変えない。接続の仕組み（第12.11.7節）を作るのは、分析のシステムが単独で動き、つなぐ段になってからにする。
