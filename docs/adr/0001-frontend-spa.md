# ADR-0001 画面を Vite + React の SPA として実装する

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-20 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第11.1節、第21.1節、第24.2節 |

## 背景

M2Office の画面（従業員のワークスペース、管理者ページ）をどの構成で実装するかを決める必要がある。
候補は次の 2 つであった。

| 案 | 構成 |
|---|---|
| A | Vite + React による SPA ＋ 独立した API サーバー |
| B | Next.js（画面とサーバー処理を 1 つのプロジェクトに統合） |

前提として、いずれの案でも実行環境は Node.js、言語は TypeScript であり、
利用できるライブラリ（npm）に差はない。
また、エージェント実行を担うワーカーは、承認による中断と再開のため
どちらの案でも独立した常駐プロセスとして分離する。

## 決定

**A 案（Vite + React の SPA ＋ 独立した API サーバー）を採用する。**

## 理由

### 1. プラットフォーム API の要件を構造的に担保できる

仕様書 第11.1節で、次の 2 点を方針として定めている。

- A-1: 画面が使う API と外部公開 API は同じ基盤の上に構築する
- A-2: 自社が使う機能はすべて API として存在する。内部だけの抜け道を作らない

第1.3節のとおり、第三者がエージェントを追加できることが事業の前提であり、
API を公開できるかどうかがプロジェクトの成否を左右する。

B 案では、画面から直接データベースを操作する経路を作れてしまうため、
A-2 は「規律」として守る対象になる。開発が進むほど画面専用の処理が積み上がり、
後から API を公開しようとすると作り直しが発生する（第24.2節、リスク R-11）。

A 案では画面はブラウザ上で動作するため、**API を経由する以外に手段がない**。
A-2 が規律ではなく構造として保証される。

### 2. 役割の分離が理解しやすい

開発チームは Node.js の経験が浅い。
A 案は「ブラウザのアプリ」と「API サーバー」という独立した 2 つを作る構図であり、
どのコードがどちらで動くかが常に明確である。
API は画面がなくても単体で動作確認でき、学習対象がフレームワーク固有の作法に偏らない。

### 3. 後戻りしやすい

| 移行方向 | 難度 |
|---|---|
| A → B | API が独立しているため、画面を作り直せば移行できる |
| B → A | 画面とサーバー処理が結合しており、分離作業が発生する |

判断を誤った場合の回復コストが A 案のほうが小さい。

### 4. SSR の必要性が低い

M2Office はログインして使う業務システムであり、検索エンジン対策は不要である。
B 案の主要な利点であるサーバーサイドレンダリングの恩恵が小さい。

## 却下した案の利点（記録として）

B 案にも次の利点があり、将来状況が変われば再検討の余地がある。

| # | 利点 |
|---|---|
| 1 | 配備先が 1 つで済み、運用が単純になる |
| 2 | 日本の開発市場で経験者が多く、外注・採用がしやすい可能性がある（統計で確認したものではない） |
| 3 | 認証をサーバー側で扱えるため、Cookie の設計で悩む場面が少ない |

## 結果

### 守るべきこと

| # | 内容 | 対応箇所 |
|---|---|---|
| 1 | ドメインロジックは `core` パッケージに置き、HTTP に依存させない | 第21.5節 |
| 2 | セッションは API が発行する httpOnly Cookie で保持する | 第21.7節 |
| 3 | CSRF 対策（SameSite 属性と状態変更時のトークン検証）を実装する | 第21.7節 |
| 4 | ワーカーは常駐プロセスとして動かす | 第21.6節 |

### 増える作業

- ログイン状態の保持、画面遷移、読み込み中の表示を自前で実装する必要がある。
- 配備先が画面・API・ワーカーの 3 つになる。

### 未決事項

- API フレームワークの選定（Fastify / Hono）は別途決定する（仕様書 Q-33）。
