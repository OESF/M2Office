## 背景

- サーバーの側は、これまでどおり SaaS として出す。運営を担うパートナーと話を進めており、正式に決まり次第、展開したい（2026-10-07 に三浦さんが報告）。
- マスター管理画面は第 0.26.0 版で規定した（第23.8節）が、**未実装**。会社はいま、運営の手元のツール（`npm run tenant:create`）で作り、状態はデータベースを直接変えている。
- パートナーが運営するには、手元のツールとデータベースの操作に頼らず、画面で会社を作り、各社の動きを見られる必要がある。カードの決済は後の段（第23.4節）。
- 本番のドメインはワイルドカード（`*.<本番のドメイン>`）で、会社を足しても DNS と証明書の作業は要らない（第20.4.2節）。会社を作ることは、データベースに会社と最初の管理者を記録することで済む。

## 検討した案

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| **A. 別のプロセスと別のデータベースのロールで作る** | 運営の API を、顧客向けの API と別のプロセスで動かす。運営のロールは運営の表と集計の口だけを触る | 顧客向けの API が破られても運営の操作に届かない（第23.8.2節・第23.8.11節のとおり） | 起動するものが 1 つ増える |
| B. 顧客向けの API に運営の口を足す | ホストが `ops.` のときだけ通す | 作る物が少ない | 顧客向けのプロセスに全社を横断する権限が入る。テナント境界（不変則 I-2）を守る仕組みが 1 か所に重なる |
| C. 画面を作らず、手元のツールを増やす | — | すぐできる | パートナーに渡せない。記録と権限の統制ができない |

## 決定（案）

1. **案 A。** 運営の API は別のプロセス（同じソースの中の別の入口）とし、ホスト `ops.<本番のドメイン>` だけで受ける。データベースは運営専用の領域（`ops` スキーマ）と専用のロールを使う。
2. 運営のロールは、**業務のデータの表を読めない。** 会社と最初の管理者の作成と、件数・金額・状態だけを返す集計の口（決めた関数）だけを使う。
3. **段 1 で作るもの**: 会社一覧（各社の利用者の数・使った日・業務の実行と失敗・AI の費用・保存の量・入れている拡張機能・接続）、会社を作る、会社の詳細（参照）、試用と稼働の切り替え、サーバー全体の稼働状況、ローカルの形の機械の一覧（稼働の知らせ）、運営主体の設定（第23.8.14節）、運営者と操作履歴。
4. **段 2 以降**: 利用の停止と再開（2 人の承認）、ライセンスとシート、サブドメインの変更、代理アクセス、請求とカードの決済。
5. 運営者のログインは、運営主体の Google Workspace（Q-62 の決定どおり）に、M2Office の側のパスキーを重ねる（案。Q-211）。全社に効く権限のため。
6. 会社を作ったら、最初の管理者に渡すログインの URL を出す。運営の画面からはメールを送らない（案。Q-213）。

## 結果

- 良い点: パートナーが画面だけで会社を作り、動きを見られる。運営の権限が顧客向けの API と分かれる。
- 悪い点・残る作業: 運営の表と集計の口の設計、運営者の 2 段目の確かめ、配備の構成（本番の事業者は Q-10）。ローカルの形には運営の画面を入れず、管理者ページの「機械」（第8.6.7節）で足りる分だけを持つ。
