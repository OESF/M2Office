## 背景

2026-11-12 に三浦さんが、コラムの作成が WordPress に下書きを入れるところまで動くことを確かめたうえで、「WordPress が提供する API を可能な限り利用できるようにして下さい」と求めた。

サイトの更新は、いまある固定ページと記事の文（段 1）と、サイトのカテゴリーとタグ（第45.17節）を扱う。WordPress の REST API は、このほかに新しい記事と固定ページ・公開の状態・前の版・画像・コメント・再利用ブロック・メニュー・ヘッダーとフッター・サイトの設定・プラグインとテーマ・利用者などを読み書きできる。

## 決定

1. **どの口も、書くものは承認の後に入れる。** コメントの返事は社外に届くので、なおさら承認を通す。
2. **消すのは WordPress のゴミ箱まで。** 完全には消さない。カテゴリー・タグ・画像は消さない。
3. **プラグインとテーマは、読んで知らせるだけ。** 入れる・有効にする・更新する・消すことはしない。
4. **利用者・アプリケーションパスワード・デザイン（全体のスタイル・テーマの切り替え）は扱わない。**
5. **段 2a → 2b → 2c → 3 の順に作る。** 段 2a は新しい記事と固定ページ・公開の状態・前の版・画像。どの段も、作る前に本物の WordPress で口を確かめる。
6. **秘書が作る記事と固定ページは下書きで作り、承認の画面で公開するかを見せる。**

## 理由

- **承認:** サイトは会社の顔で、社外の人が見る（迂回しない境界 2）
- **ゴミ箱まで:** 頼み違いでも WordPress の側で戻せる。完全に消すと戻せない
- **プラグインは知らせるだけ:** プラグインの更新でサイトが止まることがある。乗っ取りの入口にもなる。更新は WordPress の管理画面やサーバーの自動の更新に任せ、M2Office は「更新が要るものがあります」と知らせることで役に立つ
- **デザインを扱わない:** 見た目の良し悪しは人が見て決めるもので、文のように「直す前と後」で判断しにくい
- **順:** 中小企業のサイトの手間で多い順（記事とページ・画像 → コメント → メニューとフッター）

## 採らなかった案

| 案 | 採らなかった理由 |
|---|---|
| REST API の口をすべて、そのまま秘書のツールにする | 承認の画面で「何が変わるか」を見せられない口が出る。害の大きい口（プラグイン・利用者）も混ざる |
| プラグインを承認の後に更新まで行う | 更新でサイトが止まったとき、M2Office では直せない |
| 完全に消すことも承認の後に行う | 戻せない。消すのは WordPress の管理画面で人が行えば足りる |

## 影響

- サイトの更新の付属の業務とツールが、段ごとに増える
- 管理者の役割が要る段（2c・3）は、会社の利用者か本人の接続を管理者にしている会社だけで使える
