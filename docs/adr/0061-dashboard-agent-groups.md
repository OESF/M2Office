# ADR-0061 ダッシュボードの「業務の状態」を、拡張機能と業務の分野ごとのまとまりで並べる

| 項目 | 内容 |
|---|---|
| 状態 | 採用。仕様書 第 0.212.0 版で実装（2026-10-01。三浦さん「エージェントの数だけ増えてしまう。名刺管理・在庫管理のような大きなブロックを作り、その中にエージェントが何個か存在するという括りにできれば、表示をすっきり減らせるのでは」） |
| 決定日 | 2026-10-01 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第6.7.4.2節・第6.7.4.2.1節・第6.7.4.3節・第6.7.2.1節。ADR-0028（AI に任せる） |

## 背景

- ダッシュボードの「業務の状態」は、使える業務を 1 つずつ、ロボットの絵と受け持ちの件数で並べている（第6.7.4.2節）。
- 業務は、公式で 14、名刺管理で 3、在庫管理で 3 と増え、拡張機能やスキルを入れるたびにさらに増える。並ぶ数が増えるほど、一瞥で「どこが動いているか」が分からなくなる。
- 名刺の取り込み・名刺の修正・まとめてのメールは、利用者から見ればどれも「名刺管理」の仕事である。管理者が知りたいのは、まず「名刺管理は動いているか」である。

## 検討した案

| 案 | 内容 | 良い点 | 悪い点 |
|---|---|---|---|
| A. 1 つずつ並べたまま、待機の業務を畳む | 動いている業務だけを出し、待機は「ほか n 件」にまとめる | 作りが簡単 | 「待機」を出す意味（使われていない業務に気づく。第6.7.4.2節）が薄れる。動き出すたびに並びが大きく変わる |
| B. 管理者が組み分けを作る | 左のメニューのカテゴリーのように、管理者がまとまりを作って業務を入れる | 会社ごとに好きに分けられる | **人に一覧や規則を作らせない**方針（ADR-0028）に反する。作らなければ何も変わらない |
| **C. 定義から決まるまとまりで並べる** | 拡張機能の業務はその拡張機能で、公式の業務は分野（`category`）で 1 つにまとめる | 設定が要らない。拡張機能を入れても並ぶ数は 1 つしか増えない。利用者が拡張機能の名前で覚えている単位と合う | 公式の業務の分野の名前を、運営が決めて保つ必要がある |

## 決定

1. **案 C をとる。** まとまりは、拡張機能の業務ならその拡張機能、公式の業務なら分野（メール・予定・会議・ブリーフ・資料・知識と調べもの）で決める。
2. **業務が 1 つだけのまとまりは、まとまりにしない。** 取り込んだスキル 1 つの拡張機能などで、同じ名前が二重に出ないようにする。
3. まとまりの囲みには、まとめた受け持ちと今日の件数、絵を 1 つ出す。**動いている業務と今日失敗した業務だけを、囲みの中に名前で出す。** すべての業務は囲みを開いたときに出す（既定は閉じる）。
4. 並びは、まとまりの間も中も忙しい順のまま（第6.7.4.2節）。
5. 分野の名前は運営が持つ（`@m2office/shared` の `AGENT_GROUP_LABELS`）。分野の名前が無い公式の業務は、業務 1 つの囲みで出す。

## 理由

- 拡張機能は、利用者が入り切りし、名前で覚えている単位である。その単位で並べれば、拡張機能を足しても並ぶ数は 1 つしか増えない。
- 動いている業務を囲みの中に出せば、開かなくても「名刺管理のまとめてのメールが承認待ち」まで分かる。待機のものまで並べる必要は無い。
- 組み分けを定義から決めれば、管理者は何もしなくてよい。

## 影響

- ダッシュボードの API（`GET /v1/admin/dashboard/live`）の `agents` の各行に、まとまり（`group`: ID と名前）を足す。
- 画面は、まとまりごとに囲みを作り直す。掛け通しの画面では開く操作を出さない。
- スライド作成の分野を `research` から `document`（資料）に改める（文書の作成・表の作成と同じ仕事のため）。
- 「集計」の業務ごとの表は、今回は変えない。並ぶ数が問題になれば、同じまとまりで小計を出す。
