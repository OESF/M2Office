# ADR-0051 店頭サイネージを内蔵の拡張にし、会社の画面に出すことを社外への送信としない

## 背景

小さな店・医院では、店頭や待合に画面を置き、画像と動画を流したいという声が多い。三浦さんはこれまで大規模向けのサイネージの製品を
お客様に提供してきたが、機能が多すぎて運用が大変だった。求められているのは次の程度である。

- 画面は 2 台程度。16:9 の横と縦。画像と動画を流す
- 通常は流し、外のシステムやスタッフからの依頼で案内を割り込ませる（「12番の患者様、レントゲン室にお入りください」「〇〇パンが焼き上がりました」）
- 割り込みではチャイムを鳴らし、15 秒ほどで元の流れに戻る

割り込みは、お客様の目に触れる。第9.4.0節は「社外に出るもの」に人の判断を求めるため、割り込みがそれに当たるかを決める必要がある。
当たるとすれば、呼び出しのたびに承認を待つことになり、呼び出しの役に立たない。

## 決定

1. **サイネージを内蔵の拡張（第12.13節）として作る。既定は切り。** 画面の登録・素材の置き場・画面の側で動くページを持ち、拡張機能では作れないため。
2. **会社が登録した画面に出すことは、社外への送信に当たらないとし、承認を挟まない。** 画面は会社の店頭・待合に置いた会社の端末で、社内の掲示と同じ扱いにする。
3. その代わり、次の境界を守る（第31.14節）。
   - 出す先は、管理者が QR で登録した画面だけ
   - 秘書は人から頼まれたときだけ出し、自分の判断では出さない
   - 外のシステムの受け口から出せるのは、文字と登録した割り込みの画像だけ。外の画像や Web ページは出させない
   - 流れにも Web ページを入れない
4. **割り込みの文は推論に渡さない。** 見た目は決まった計算で作る。受け口の項目の推測には骨組み（名前と値の種類）だけを渡す。文は出し終えて 24 時間で消し、ログに残さない。
5. 画面の鍵・受け口の鍵は、予約の受け口（第29.13.1節）と同じく、作ったときに一度だけ見せ、ハッシュだけを持つ。

## 理由

- 呼び出しは数秒のうちに出なければ意味がない。承認を挟むと使えない。
- 画面は会社の中に置いた会社の端末であり、Web への公開（第29.12節。誰でも見られる）とは違う。
- 承認を外す代わりに、出す先・出せる中身・出すきっかけを狭めることで、取り返しのつかない出し方（鍵の漏れによる勝手な表示、秘書の思い込みによる表示）を防ぐ。
- 医院では患者の番号や名前が文に入りうる。推論に渡さず、残さないことで、患者の情報を外に出さない。

## 影響

- 第9.4.0節の「秘書と業務が自分で決めるもの」に、登録した画面への表示が加わる（道具 `signage.show` は `write-internal`）。
- 端末による音の出し方の違い（ブラウザの自動再生の決まり）は、実機で確かめる（Q-137）。
- 大規模向けの機能（画面の分割・予定表・再生の実績など）は持たない（第31.18節）。
