# ADR-0019 外部公開する API のパスの体系（実装を正とする）

| 項目 | 内容 |
|---|---|
| 状態 | 採用 |
| 決定日 | 2026-09-23 |
| 決定者 | 三浦 |
| 関連 | 仕様書 第13.3節、第9.3.1節、第24.2節、Q-67 |

## 背景

第13.3節は「主要エンドポイント（案）」として書かれ、実装との食い違いが 5 か所あった。
どちらに揃えるかを決めていなかった（Q-67）。

外部公開は Phase 2 であり、**いま外から使っている人はいない**。
直すなら、いまが一番安い。

## 決定

| # | 決定 | 理由 |
|---|---|---|
| 1 | **実装の体系を正とし、第13.3節を書き直す** | 食い違いの多くは実装のほうが妥当だった（下表）。案に合わせると、正しいものを壊すことになる |
| 2 | 依頼（`/v1/jobs`）と実行（`/v1/runs`）を分けたままにする | `Job` と `Run` は別の型である。依頼は業務・入力・依頼者・起動経路、実行は状態・区切りの位置・費用・削減時間を持つ。1 つの依頼が再試行で複数の実行になりうる。案の `GET /v1/jobs/{id}` は 2 つを 1 つの URL に混ぜていた |
| 3 | 管理者だけが使う口は `/v1/admin` の下に置く | 取り付け点で 1 回だけ権限を確かめられる。一般の口と混ぜると、確認がハンドラごとに散り、足し忘れが起きる。案の `GET /v1/audit-events` はこの境界を失う |
| 4 | 本人だけが使う口は `/v1/me` の下に置く | 同じ理由（不変則 I-10） |
| 5 | 画面が使う API と外部公開の API を同じものとする | 第24.2節の「Phase 1 から API 優先」。別系統を作ると、外部の口だけ機能が遅れる |
| 6 | 案のうち妥当だった 2 つは、実装を足して取り込む | 下表の「案が正しい」の 2 件 |

### 食い違いごとの判断

| 案 | 実装 | 決め |
|---|---|---|
| `GET /v1/jobs/{id}` | `GET /v1/runs/{id}` | 実装。決定 2 |
| `GET /v1/audit-events` | `GET /v1/admin/audit-events` | 実装。決定 3 |
| `GET /v1/runs/{id}/artifacts` | 実行の応答に含める | 実装。画面は実行と成果物をいつも一緒に読む。成果物だけを取る口は、必要になったときに足す |
| `POST /v1/knowledge/documents` | `PUT /v1/admin/knowledge/{id}` のみ | **案が正しい**（一部）。ID を呼ぶ側が決める `PUT` しかなく、新規の登録がしにくい。`POST /v1/admin/knowledge` を足す。場所は決定 3 に従う |
| `POST /v1/jobs/{id}/cancel` | 未実装 | **案が正しい**。ただし止める対象は実行なので `POST /v1/runs/{id}/cancel` とする（決定 2） |
| `POST /v1/approvals/{id}` | 画面からのみ | 変えない。外部アプリの認証（第13.4節）が未実装のため、そもそも外から呼べない |

## 検討した点

| 案 | 採らなかった理由 |
|---|---|
| 仕様書の案に実装を合わせる | 決定 2・3 のとおり、案のほうが粗い。正しいものを壊す |
| 外部公開用のパスを別に用意し、画面用は内部扱いにする | 外部の口だけ機能が遅れる。第24.2節に反する。口が 2 つになると、承認の禁止（第13.3節）のような規則を二重に書くことになる |
| `/v1/jobs` を `/v1/runs` に一本化する | 依頼と実行を 1 つにすると、再試行で実行が増えたときに表せない。いまは 1 対 1 だが、型を先に壊す理由がない |
| 中止を `DELETE /v1/runs/{id}` とする | 実行は消えない。状態が `cancelled` になって残る。`DELETE` は誤解を招く |
