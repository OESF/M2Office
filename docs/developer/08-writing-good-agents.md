# 8. 良い業務エージェントの書き方

## 8.0 SKILL.md で書くとき

**本文がそのまま指示です。** 下の第8.1節・第8.2節の「書く・書かない」と「止める条件」は、本文にそのまま当てはまります。

- 段や承認の置き場所は書きません。送る道具（`m2office-tools` の `gmail.send` など）を書けば、M2Office が「作業 → 承認 → 送る」を組み立てます
- 送る中身（宛先・本文）は、本文の指示で「作業の答えに書く」ようにします。承認の画面にそのまま出て、送る段はそのとおりに送ります
- 止める条件（取得できなければ推測せずに報告する）は、本文に書きます
- `description` には「何をするか」と「いつ使うか」を書きます。秘書はこれを手がかりに業務へ取り次ぎます

第8.1節から後ろの `onEmpty`・`constraints`・`present`・`approver` は、JSON で書く形（廃止の方向）の項目です。

## 8.1 指示（instruction）

| 書く | 書かない |
|---|---|
| 何をするか（「議題・決定事項・保留事項に分けて議事録を作る」） | 画面の操作や内部の仕組み |
| 使うツールと、その引数の要点（「document.create で、題名を『議事録』として保存する」） | 「承認なしで送れ」のような基盤の決まりを破る指示（審査で止め、実行でも効かない） |
| **止める条件**（「記録が空なら、議事録を作らずに報告する」） | 推測で埋めてよいという指示 |
| 迷うときの扱い（「判断できないものは『要確認』に分ける」） | 長い前置き |

**1 つのステップには 1 つの仕事を。** 「取得して、まとめて、共有する」は 3 つのステップに分けます。
承認を間に置けるようになり、画面の「進み方」も分かりやすくなります。

## 8.2 止める条件を書く

業務エージェントの最大の失敗は、**取得できなかったものを推測で埋めて、もっともらしい成果物を作る**ことです。

- 取得の段階に `"onEmpty": "stop"` を付け、何も取れなければそこで止める
- 指示に「取得できない場合は推測せず、取得不可として報告する」と書く
- `constraints` に「確認できない金額・日付・約束を書かない」のような禁止事項を置く

## 8.3 承認の置き場所

- 社外や他の人に届く操作（`external-send`）とお金に関わる操作（`financial`）の**直前**に置く
- 承認の画面に出す `present` には、**判断に必要なもの**を書く（「共有先のスペースと、投稿する本文」）
- 本人の用件なら `"approver": "requester"`、本人以外の目を通すべきものは `approverRole` で承認者を指定する
- 承認を増やしすぎない。`read` と `draft` だけの業務は承認なしで価値が出るようにする

## 8.4 ヘルプ

- `summary` は「何を入れると、何をしてくれるか」を 1〜2 文で
- `examples` には、押せばそのまま試せる入力を置く
- `notes` には、止まる条件と、できないことを書く（「社外の参加者は対象外です」）
- 専門用語を使わない（「プロンプト」「トークン」などを利用者に見せない）

## 8.5 Google の権限を小さく保つ

業務が使うツールの権限は、その業務を導入した会社に求められます（第4.2節の「Google の権限」の列）。

- **必要なツールだけを `tools` に書く**。使わないツールを並べると、会社に余計な権限を求めることになる
- **「制限付き」の権限を使うツール（Gmail の読み取り・下書き）は、本当に要るときだけ使う**。M2Office を一般に公開するときに、第三者のセキュリティ評価（CASA）の対象になるため
- ドライブ・ドキュメント・スプレッドシートは、M2Office が作ったファイルと利用者が選んだファイルだけを扱う前提で手順を組む（ドライブ全体を探す業務は作れない）
- 送る・共有する・予定を変える操作は `external-send` になる。直前に承認ステップを置き、`present` に相手と内容を出す

## 8.6 評価のケース

- うまくいく場合、止まるべき場合、境目の場合を用意する
- `expect` は、人が読んで合否を判断できる文にする
- 鍵が無い環境でも確かめられるよう、主なケースには見本の応答（`stub`）を付ける
