# 8. 良い業務エージェントの書き方

## 8.0 SKILL.md で書くとき

**本文がそのまま指示です。** 下の第8.1節・第8.2節の「書く・書かない」と「止める条件」は、本文にそのまま当てはまります。

- 段や承認の置き場所は書きません。送る道具（`allowed-tools` の `gmail.send` など）を書けば、M2Office が「作業 → 承認 → 送る」を組み立てます
- 送る中身（宛先・本文）は、本文の指示で「作業の答えに書く」ようにします。承認の画面にそのまま出て、送る段はそのとおりに送ります
- 止める条件（取得できなければ推測せずに報告する）は、本文に書きます
- `description` には「何をするか」と「いつ使うか」を書きます。秘書はこれを手がかりに業務へ取り次ぎます

## 8.1 本文（指示）

| 書く | 書かない |
|---|---|
| 何をするか（「議題・決定事項・保留事項に分けて議事録を作る」） | 画面の操作や内部の仕組み |
| 使う道具と、その引数の要点（「`document.create` で、題名を『議事録』として保存する」） | 「承認なしで送れ」のような基盤の決まりを破る指示（審査で止め、実行でも効かない） |
| **止める条件**（「記録が空なら、議事録を作らずに報告する」） | 推測で埋めてよいという指示 |
| 迷うときの扱い（「判断できないものは『要確認』に分ける」） | 長い前置き |

手順は番号を付けて書くと、推論が順に進めやすくなります。

## 8.2 止める条件を書く

業務の最大の失敗は、**取得できなかったものを推測で埋めて、もっともらしい成果物を作る**ことです。

- 本文に「取得できない場合は推測せず、取得できなかったとして報告する」と書く
- 「守ること」のような見出しを立て、「確認できない金額・日付・約束を書かない」のような禁止事項を並べる

## 8.3 承認の置き場所

- **承認は書きません。** 送る道具（`gmail.send`・`chat.post` など）を `allowed-tools` に書けば、M2Office が「作業 → 承認 → 送る」を組み立てます
- 承認の画面には、作業の段の答えがそのまま出ます。本文で「送る中身（宛先・本文）を答えに書く」ようにすると、判断しやすくなります
- 依頼した本人以外に承認させたいときは、`metadata.m2office-approver` に `承認者` か `管理者` と書きます
- 社外にもお金にも関わらない送信は、承認が自動で通ります（仕様書 第9.4.0節）

## 8.4 ヘルプ（HELP.md）

- 最初の段落に「何を入れると、何をしてくれるか」を 1〜2 文で書く
- 「使い方」と「注意」（止まる条件・できないこと。例:「社外の参加者は対象外です」）を分ける
- 押せばそのまま試せる実行例は `metadata.m2office-examples` に書く
- 専門用語を使わない（「プロンプト」「トークン」などを利用者に見せない）

## 8.5 Google の権限を小さく保つ

業務が使う道具の権限は、その業務を導入した会社に求められます（第4.2節の「Google の権限」の列）。

- **必要な道具だけを `allowed-tools` に書く**。使わない道具を並べると、会社に余計な権限を求めることになる
- **「制限付き」の権限を使う道具（Gmail の読み取り・下書きなど）は、本当に要るときだけ使う**。M2Office を一般に公開するときに、第三者のセキュリティ評価（CASA）の対象になるため
- ドライブ・ドキュメント・スプレッドシートは、M2Office が作ったファイルと利用者が選んだファイルだけを扱う前提で手順を組む
- 送る・共有する・予定を変える道具は `external-send` になる。M2Office が承認の段を入れる

## 8.6 評価のケース

- うまくいく場合、止まるべき場合、境目の場合を用意する
- `expect` は、人が読んで合否を判断できる文にする
- 本物の推論でケースを実行し、`expect` と結果を見比べて指示を直す（第6.4節）
